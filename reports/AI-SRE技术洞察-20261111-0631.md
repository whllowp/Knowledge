# AI-SRE 技术洞察（第 121 期）

**生成时间**：2026-11-11 06:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：隔离面／租户面（Tenant Isolation / Pooling Boundary）——共享让 Agent 更聪明，也让 A 的事故进入 B 的上下文

---

## 题眼

09-13 arXiv 2609.14780 做了一个 373 次的消融：八个模型配置、两种传输，给多租户工具传一个**校验正确的 tenant 参数**。结果：**26/26 次越界尝试全部被服务**（在 41 次看似有正当理由的尝试里也命中 26 次）；把参数从 MCP schema 里删掉后，「没有一条工具签名能表达这次读取」；但仍有 12/56 次靠**伪造可写作用域**逃出接口。作者给了一句判词：**租户隔离依赖可执行的接口与凭证，不依赖模型是否听话。** 同月另一篇 2605.05287 把另一半说透：检索按**相关性**排序、不按**授权**排序，所以一个租户的查询会把另一个租户的机密顶到 top-k——**模型看到的「最相关」，可能正是「最不该看」**。两篇合起来是一句话：隔离的失败不在模型不听话，在**接口允许它开口、检索允许它先看**。

## 一、发展趋势

**趋势一：多租户的战场从「存储隔离」移到「工具接口」。** 过去租户隔离是库表加 tenant_id、行级权限；Agent 时代，读取由模型发起，tenant 参数一旦进了 schema，就变成**提示词的一部分**——可以被说服、被改写、被伪造。隔离点必须下沉到模型看不见的地方。

**趋势二：共享推理与共享记忆是成本必需，池化不可避免。** 共享前缀缓存、共享 embedding、共享经验库能把成本打下来；但共享的每一层都是**隐式池化**，即使存储隔离，推理时的上下文仍可能混。**租户 ID 写在数据库里，不等于写在 token 流里。**

**趋势三：厂商把「共享经验」做成卖点，隔离从技术问题变成产品策略。** Rootly 让客户 opt-in 贡献脱敏复盘、目标是「AI SRE 的 Stack Overflow」；incident.io 与 ResolveAI 则承诺数据隔离。**同一品类，两种默认值**——买的是安全，还是更聪明，得先选。

## 二、技术现状：三道门，只有一道在 Agent 之下

**检索门：相关性排序不等于授权。** 2605.05287 指出四类问题：检索按相关度捞文档、工具中介泄漏（tool result 把别人的数据带回来）、跨轮上下文累积、客户端编排绕过。它的解法是分层：策略感知的入库、检索时门控、共享推理、**服务端编排**；ABAC 门控实测消除跨租户泄漏且开销可忽略。

**接口门：把 tenant 从 schema 里删掉。** 2609.14780 的对照最硬：参数校验正确也没用，模型被 pretext 说服后照样越界；删掉参数，模型「表达不了」这次读取，才真正挡住。但伪造可写作用域仍能逃出 12/56——**接口不变式需要密码学保护的上下文**，不能只靠字段缺失。

**执行门：隔离要在 Agent 之下。** Google Agent Substrate 给每个 Agent 独占 microVM、Actor 身份与短时凭据，是运行时层最实的隔离；Anthropic／OpenAI 把边界放在工作区与项目；阿里 RAM 多账号、腾讯多租户、字节资源级配额，都停在「账号／资源」层，**没有一家把「这次检索能看哪些租户」做成运行时字段**。

**池化门：经验共享没有分档。** Rootly 的池化是 opt-in，其他家承诺隔离；但「脱敏后共享」的脱敏规则、退出机制、跨租户污染的召回，都没有可导出的证据。**共享经验的收益可讲，泄漏的边界不可讲。**

**四层共享，四种漏法。** 检索索引漏「别人的文档被 top-k 捞出来」；前缀缓存漏「相同前缀跨请求复用，token 级残留」；记忆漏「共享表把 A 的结论写进 B 的注入上下文」；经验／评测库漏「A 的事故成了 B 的 few-shot」。四层各有各的隔离原语，**没有一层有统一的 `tenant_id` 贯穿。**

## 四、技术挑战

**一，相关性排序天然越权。** top-k 是按「像不像」选的，不是按「能不能看」选的；授权若在检索之后做，模型已经读过一遍了。

**二，租户参数是提示词。** 26/26 的越界证明：校验正确挡不住说服；只有让接口「表达不了」才挡得住。41 次「看似有正当理由」的 pretext 里仍命中 26 次——**攻击面不是恶意，是合理的业务解释**。

**三，上下文累积把一次越界变成长期污染。** 跨轮对话、记忆、工具结果都会把别人的数据带进后续上下文；一次泄漏会被反复引用。

**四，隔离有性能价。** set-valued scope 下函数包装的成员判定慢 57 倍；改成 JSON_TABLE 侧连接才恢复索引；权限集大了还有查询计划悬崖。**安全与延迟不是免费的，得在设计期预算。**

**五，池化与效用不可兼得。** 共享经验让 RCA 更准，也让 A 的事故成为 B 的先验；没有分档与退出机制，只能在「更笨」和「更漏」之间二选一。

**六，合规只查静态存储。** 数据驻留、GDPR 管的是「存在哪」，不管「推理时谁的上下文混了谁」；**上下文混合是合规盲区。**

**七，隔离与可观测天然冲突。** 排查要跨租户看日志与轨迹，隔离要求看不见；折中是「审计可见、内容不可见」——**只给元数据（租户、时间、命中条数），不给正文**，但这需要日志层就分好级。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `tenant.*` 字段**：`tenant_id`、`scope_credential`、`enforcement_point`、`retrieval_gate`、`tool_scope_binding`、`pooling_tier`（isolated／anonymized／opt-in）。
- **R2 检索前置授权**：ABAC 在召回前过滤，不在生成后审查；无权限文档不进入 top-k。
- **R3 接口去 tenant**：tenant 从工具 schema 移除，作用域绑定到凭证；模型无法用参数表达越界。
- **R4 跨租户金丝雀**：每季度在 A 的数据里埋唯一标记，检查 B 的输出是否出现；出现即阻断发布。
- **R5 池化分档**：默认 isolated；anonymized 需脱敏审计；opt-in 需合同与退出机制。
- **R6 性能预算**：隔离门控的 p95 增量 ≤5%；超预算先优化索引与查询形态，不降安全。
- **R7 缓存分区**：前缀缓存／KV 缓存按租户分区或加盐；共享池只放公共前缀，且可一键清空。

### 5.2 用户旅程

- **平台架构师**：设计多租户 RCA → 把 tenant 从工具参数拿掉 → 作用域绑凭证 → 压测 p95 增量 3.8% → 上线。
- **安全／合规**：季度金丝雀 → 在 A 的事故描述里埋标记 → 扫描 B 的输出与记忆 → 0 命中 → 签字。
- **值班 SRE**：处理 B 的 P1 → 检索只返回 B 的相似事故 → 不会看到 A 的工单与复盘 → 少了「参考」，但没了泄漏。
- **租户客户**：合同里选 `pooling_tier=isolated` → 拿到不池化的承诺与审计报告 → 接受略低的 RCA 命中率。

### 5.3 实现方案（90 天）

- **0–30 天：盘边界。** 列出四层共享（检索／缓存／记忆／经验库），标出各自的租户载体与当前默认值。
- **30–60 天：装门。** 检索前 ABAC；工具 schema 去 tenant；作用域绑凭证；缓存按租户分区或加盐。
- **60–90 天：验漏。** 建跨租户金丝雀与季度漏测；池化分档写进合同；性能预算进发布门禁。
- **90 天后：红队。** 每季度做一次「 pretext 红队」：用合理业务理由诱导越界，记录命中率；同季度复核缓存分区与记忆注入路径。

**第 75 个市场空白（五项）**：租户边界可声明率、检索授权前置率、跨租户金丝雀覆盖率、池化分档可导出率、隔离性能代价可报率——无一内建；`tenant.*`／`isolation.*` 为**第 44 次无人提字段族**。本地 173／173-kb 连续第 41 期成组启用：余锦泽 03「LLM 只提候选，程序用数据核对给出已验证／候选，SQL 执行前做本体约束校验」＝全库唯一把约束放在 Agent 之下的实现，本期首次当主线；配朱革 15「生产写操作缺少统一权限、审批、限流、审计和回滚控制」、赵恒 25「语义层不是 Agent 的另一个 prompt，而是每一条都用同一份定义」——共享定义提一致性，也提醒共享即边界模糊。判词：**本地把约束放在 Agent 之下，联网侧 9 月才量出「参数校验正确也挡不住 26/26 越界」；两边都没把「这次能看哪些租户」做成运行时字段。**
