# AI-SRE 技术洞察（第 378 期）

**生成时间**：2026-11-27 18:31（Asia/Shanghai）
**本期主题**：构念面／基准分数测的是能力还是格式

## 题眼

同一个模型，换个选项顺序、换个提示模板、换个答案解析器，GSM8K 分数可以差出十几个点；HELM 把同一能力拆成七个场景分别打分，BIG-bench 的两百多个任务里一半以上是格式任务。**基准分是"特定任务 + 特定格式 + 特定评分器"下的测量值，不是能力本身。** 2026 年 EMNLP 的《The Benchmark Is Not the Construct》把这件事说得很直白：我们测的是构念的代理，却把它当构念用。

## 一、发展趋势

第一，基准从"能力证明"退化为"发布素材"。厂商用排行榜证明模型更强，运维用排行榜决定升级——两边都在用一个没有构念效度证据的数字。

第二，格式敏感性成为公开问题。选项顺序、分隔符、few-shot 示例、答案抽取规则都会改变分数；同一个模型在不同 harness 上分数不可比。

第三，评测从静态题集转向任务级。Agent 评测、SWE-bench、τ²-bench 都在往"完成任务"走，但任务的成功判据又变成新的构念问题。

第四，私有评测集成为采购要求。"你们的分数在你们的题上"正在被"我们的任务上通过率"替代。

第五，评分器成为变量。LLM-as-judge 的偏差、规则评分器的抽取失败，和模型能力混在同一个分数里。

第六，统计显著性被引入。置信区间、配对检验、多重比较开始出现在评测报告里（见第 366 期）。

## 二、技术现状

**基准的三种效度。** 内容效度（题目覆盖能力域）、构念效度（分数真的反映该能力）、外部效度（能外推到生产任务）。排行榜通常只保证了第一项。

**格式敏感性是系统性的。** 提示模板、选项顺序、答案格式要求、思维链是否要求，都会改变分数；模型对格式的鲁棒性本身是一项能力，但很少被单独报告。

**评分器是分数的一部分。** 精确匹配会把"正确答案但格式不同"判错；LLM judge 有位置与冗长偏差；规则抽取在代码、数学、JSON 上各有失败模式。

**harness 差异不可忽略。** lm-evaluation-harness、HELM、厂商自评的 prompt 与后处理不同；跨 harness 比较等于跨试卷比较。

**题目抽样误差。** 几百道题的基准，标准误是几个点；相邻名次往往不可区分（第 366 期已量化）。

**基准污染。** 题目进入训练集后，分数反映记忆而不是能力（第 271 期）。

**任务级评测的构念问题。** 任务成功判据、环境版本、工具可用性都会改变通过率；"任务完成"仍是代理。

**分数不可比是默认状态。** 不同 harness 的 prompt、后处理、超时、重试、上下文截断都不同；把两个 harness 的分数放在一张表里，等于把两份不同的试卷合成一个平均分。

**"提升"要先问分母。** 提升几个点，是相对于哪个基线、哪个子集、哪种格式；分母换了，结论可能反转。

## 三、技术竞争力

| 方案 | 测什么 | 构念效度证据 | 格式敏感 | 可外推性 | 适用 |
|---|---|---|---|---|---|
| HELM | 多场景能力 | 分场景报告 | 中 | 中 | 能力对比 |
| BIG-bench | 广泛任务 | 弱 | 高 | 弱 | 探索 |
| lm-eval-harness | 标准基准 | 弱（复现用） | 中 | 弱 | 回归 |
| 排行榜 | 综合分 | 无 | 高 | 弱 | 发布 |
| 私有任务集 | 生产任务 | 强（若设计） | 低 | 强 | 采购/升级 |
| Agent 任务基准 | 端到端完成 | 中 | 中 | 中 | Agent 验收 |

**判读**：六种评测都能给出"一个数字"，只有私有任务集能回答"在我们的任务上、我们的格式下、我们的评分器下，通过率是多少"。排行榜适合做初筛，不适合做升级决策。

**本期反转**：我们一直问"这个模型比那个强多少分"；更该问"这个分数在多大程度上是格式与评分器的函数"——如果换个模板就掉十个点，那十个点不是能力差距，是测量误差。

## 四、技术挑战

**挑战一：构念定义。** "推理能力""工具使用能力"没有操作定义；基准只是操作化的一种。

**挑战二：格式控制。** 要区分"模型不会"与"模型没按格式答"，需要解析失败率与人工复核。

**挑战三：评分器校准。** 规则评分器要报告抽取失败率；LLM judge 要报告与人一致度与偏差。

**挑战四：跨 harness 可比。** 同一模型在不同 harness 上的分数差，需要标注而不是合并。

**挑战五：污染。** 题目泄漏、训练集重叠、记忆化，都会让分数虚高。

**挑战六：统计功效。** 样本量、方差、多重比较决定"提升"是否真实。

**挑战七：外部效度。** 基准任务与生产任务的分布差异，需要任务级回归集来桥接。

**挑战八：评测成本。** 任务级评测比基准贵一个量级；需要分层抽样与优先级。

**挑战九：报告纪律。** 评测报告要写清版本、格式、评分器、样本量、区间、失败分类；不写这些，"提升"不可复核，也无法在事故后回看当时的判断依据。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①能力构念与操作定义；②格式矩阵（模板/选项/答案格式）；③评分器与抽取失败率；④harness 版本锁定；⑤污染检测；⑥置信区间与配对检验；⑦任务级回归集；⑧评测报告模板。

**用户旅程**：定义要测的能力 → 选基准与任务 → 固定 harness 与格式 → 跑多次 → 报告分数区间与解析失败 → 做任务级验证 → 决定升级/回滚。

**实现方案（90 天）**：0–30 天建立任务级回归集（从生产流量抽样、脱敏、标注），固定 harness 版本与格式矩阵；31–60 天加评分器校准、解析失败率、置信区间与配对检验；61–90 天把评测接入发布门禁，排行榜只做初筛。

**验收标准**：任取一次模型升级，能回答"测了哪些任务、格式是什么、评分器是谁、区间多宽、解析失败多少、与生产任务差多少"；答不出就是"用排行榜做决策"。

4. 任务级回归集；
5. 评测报告的统计口径。

## `construct_validity.*`／`format_sensitivity.*` 第 257 次无人提字段族

能力构念、格式矩阵、解析失败率、评分器版本、置信区间、任务分布差异——这些字段在评测报告里通常不存在；存在的是"分数、排名、提升百分比"。
