# AI-SRE 技术洞察（第 251 期）

**生成时间**：2026-11-17 14:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-09 至 2026-11 的公开材料
**本期主题**：影子面／清单外 AI（Shadow AI）——审计抽不到的系统，出事时也找不到属主

## 题眼

2026 年 9 月三份调查把同一件事说清楚了。WalkMe 对 3,750 名职场人的《State of Digital Adoption 2026》显示：45% 在过去 30 天用过未授权 AI，36% 把机密数据一起贴了进去，34% 根本不知道公司允许哪些工具。PagerDuty 对 1,250 名大型企业员工的调查里，66% 承认在用自己认为不被允许的 AI。Deel 引 Verizon 的 858,440 起 DLP 事件：影子 AI 已是员工把公司数据弄出去的第三大途径，同比四倍，源代码排在提交内容第一。Obsidian Security 的说法更直接——低代码入口（Copilot Studio、n8n、Agentforce）不需要中央审批，企业往往在「数百到数千个 Agent 已经在跑」之后才开始建清单。清单不是没建，是建的时候分母已经错了。

## 一、发展趋势

第一条线：治理话术从「禁止」转向「受控启用」。2025 年《Strategic Change》上那篇首个以影子 AI 为对象的同行评审研究已经给出结论：单靠限制不构成治理策略，建议「受控开放＋可监控的灵活性」。2026 年的厂商实践开始跟着这句话走——先发现，再决定是补票还是下线，而不是先封。

第二条线：清单从「资产台账」变成「发现能力」。台账假设你知道有哪些系统；发现能力承认你不知道，并把「多久能发现」当成指标。微软把 AI Agent 发现直接做进 Entra Global Secure Access 的网络检查里，不需要新装东西；开源侧则用 eBPF 在 Pod 层抓「谁在连 OpenAI」。这两件事说明：发现正在从安全团队的项目，变成平台自带的属性。

第三条线：影子 AI 的边界从「人用工具」扩展到「Agent 用工具」。人用 ChatGPT 是数据出口问题；Agent 连生产库、持有凭据、按时代跑，是「一个没有入职手续的员工」。后者的清单难度高一档：它可能没有账号，只有一个 API key 和一段定时任务。

## 二、技术现状

2026 年的发现手段基本落在三层证据上，每层各缺一块：

**网络层**。Entra Global Secure Access 的 AI agent discovery（2026-06-01，preview）用既有网络检查看「从本环境发往互联网的 Agent 连接」，覆盖端点上的本地 Agent（含未托管）与 Copilot Studio Agent，并把活动归因到用户、设备、进程。开源项目 agent-discover-scanner 2.1.0（2026-02-05）走另一条路：用 Tetragon eBPF 盯「Pod → OpenAI 等外部端点」的连接，输出工作负载、二进制、命名空间，另有端点扫描模式覆盖 macOS/Linux/Windows。网络层的共同盲区是：内网自建推理、容器内不产生外部连接的 Agent、以及不走已知域名的代理。

**平台层**。Nudge Security（2026-03-24，RSAC）从已接入的 SaaS 里发现 Copilot Studio、Agentforce、n8n 上的 Agent，并盘点其权限、资源与能力；Obsidian Security（2026-05-22）把缺口拆成「影子 Agent」与「孤儿 Agent」两类——后者是创建者账号已停用、Agent 还在跑。平台层看得准归因和权限，但只能看接进来的平台。

**身份层**。这是最容易被跳过的一层：Agent 用的是谁的凭据？共享服务账号让「归因到人」直接断掉，而清单上写着「已登记」并不等于「知道它代表谁」。

三层的交集才有可用归因：网络层给「在动」，平台层给「谁建的、有什么权限」，身份层给「代表谁」。只有一层，得到的是一张好看但不敢签字的地图。

判读：这张表按「证据层」分，不按厂商分。2026 年的变化是网络层发现开始「随客户端免费附带」，这会把「有没有发现能力」变成默认项，竞争点随之后移到归因与处置。覆盖广不等于能签字：能看见连接，不等于能说清这个 Agent 代表谁、被谁批过。

本期反转：过去比「谁能发现更多」，现在该比「发现之后多久补票或下线」。而清单的准确性不取决于扫描器，取决于「出生点」——每一个能创建 Agent 的入口（低代码许可证、API key 申请、CI 里的服务账号）都是一个未申报的出生点。把入口数当分母，比把员工数当分母更接近真相。

判词：**「CSPM／SSPM／CASB／eBPF／端点扫描／低代码平台日志」全部可采购，「这个 Agent 是谁在何时建的、代表谁、被谁批过、现在还在动什么」不可采购。**

## 四、技术挑战

其一，分母不可知。入口增长快于盘点周期：今天盘完 Copilot Studio，明天业务部门开了 n8n。清单永远滞后，除非把「创建即登记」做进入口本身。

其二，归因断点。共享服务账号、CI 里的长期 token、外包人员的个人 key，都会让「归因到人」在最后一跳失败。清单上有一个名字，不等于有一个人。

其三，禁止的副作用。限制越硬，使用越隐蔽——这是《Strategic Change》研究的核心结论。把「清零」当 KPI，等于把影子 AI 赶进更看不见的地方。

其四，孤儿 Agent。创建者离职、项目解散，Agent 还在按 cron 跑，还持有当时的权限。这一条与属主、退役两期直接相连：没有属主的 Agent 不会自己停。

其五，证明边界。任何发现手段都有盲区。不把盲区写进清单，清单就是一份「假阳性安全」——审计看到的是全绿，事故看到的是一台没人认识的机器。

## 五、需求分解、用户旅程与实现方案

**需求分解**：R1 出生点清单（每个可创建 Agent 的平台/许可证/API key 通道都进分母）；R2 三层发现（网络、平台、身份）并集；R3 归因到人（含共享账号的二次归因）；R4 分级（能碰什么数据、持什么工具、权限多大）；R5 补票或下线（两条路都要有 owner 与时限）；R6 发现时效（TTD 首次外连到被发现、TTI 发现到入清单）；R7 盲区声明（哪些层没覆盖、为什么）。

**用户旅程**：员工在低代码平台建一个 Agent → 首次外连模型或数据源 → 网络层发现「有个东西在动」→ 平台层补上「谁建的、什么权限」→ 身份层确认「代表谁」→ 通知制作者与属主 → 按数据/工具分级 → 补审批（补票）或下线 → 30 天后复验仍合规 → 创建者离职触发孤儿检查。

**90 天实现方案**：0–30 天，做出生点普查（低代码许可证、云 API key、CI 服务账号三张表），同时上线网络层发现，先要「看得见」；31–60 天，接平台层盘点权限、补身份层归因，定义 TTD/TTI 并出第一份周报；61–90 天，把补票与下线做成两条有 SLA 的流程，清理孤儿 Agent，最后写一页「本清单不覆盖什么」的边界声明，随清单一起发布。

第 178 个市场空白（五项）：①出生点分母盘点服务；②TTD/TTI 度量与基准；③跨共享账号的归因到人；④孤儿 Agent 的生命周期管理；⑤发现盲区的边界声明模板。

`shadow_ai.*`（`discovered_at`、`birth_point`、`attribution`、`last_seen`）／`agent_inventory.*`（`owner`、`approved_by`、`last_active`、`data_class`）第 145 次无人提字段族：厂商在卖「发现」，没有一家把「这个发现是在哪个出生点、归因断在哪一跳」写成字段。

本地 173／173-kb 连续第 134 期成组启用（肖汉松 22：把入口许可证当分母、用 eBPF 抓外连、离职即触发孤儿检查，三件事一起做才算清单）。
