# AI-SRE 技术洞察（第 125 期）

**生成时间**：2026-11-11 08:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：赔付面／归因链面（Indemnity / Fault Attribution）——99.99% 可用性赔不了「答错」；出错之后，赔的钱从谁的口袋出

---

## 题眼

08-27 一篇运维实务稿把 SLA 信用里最尴尬的一段写清楚了：客户报障，**先看「Agent 在不在线」**——在，就是可用性问题，拉 uptime 日志、按合同赔、结案；不在线，才进入下一段：**把当时那次请求和工具返回原样重放，重建它看到了什么**。然后只分三类：Agent 推理错、上游数据／工具错、混合原因。前两类合同里通常有主，第三类没有；稿子给了一个默认规则——**如果 Agent 有能力核对却没核对、还放大了上游错误，就算 Agent 侧**；并建议写进合同、设 5 个工作日上限、超时默认判给客户。同月 Mayer Brown 的合同稿把另一头说透：Agent 从「被动工具」变成「代为行动」，合同模型要从 SaaS 转向 BPO——**可用性 SLA 之外，要有准确性 SLA、更宽的赔偿、审计权与决策日志**。这不是纯法律问题：**第一段与第二段的证据都在 SRE 手里**，赔不赔、赔多少，取决于运维能不能在五天内把当时的世界重建出来。

## 一、发展趋势

**趋势一：SLA 从「可用」走向「结果」。** 99.99% uptime 在 Agent 出错时几乎无用；BPO 式合同开始写「99% 发票处理正确」「99% 工单在窗口内处理」「自主动作投诉率 <1%」。**可用性赔的是停机，结果赔的是错误——后者才是 Agent 的主要失效形态**；而信用通常按「停机分钟数」折算，**答错没有分钟数**，于是赔不出来。

**趋势二：责任模型从 SaaS 转向 BPO。** 服务定义、授权边界、护栏、绩效保证、赔偿、审计权、数据归属，六条都要重写；关键一句是「**把 Agent 的工作当作人做的工作来担保**」——勤勉、专业、符合行业标准，而不是「按现状提供、不保证」。

**趋势三：赔偿范围扩到「自主动作」。** SaaS 时代赔偿多只覆盖第三方知识产权；Agent 时代要覆盖「Agent 自主执行服务时造成的第三方索赔」，再用三类除外条款平衡：客户错配、客户数据有误、已升级且客户明确批准的动作。

## 二、技术现状：三段裁决，两段没有证据

**第一段「在不在线」证据最全。** uptime、状态码、超时日志都在监控里，几分钟能判；这一段 SRE 能直接签字。

**第二段「它看到了什么」证据最缺。** 要重放当时的查询与工具返回，依赖 114 期的表计收据、115 期的返回回执、116 期的记录保真；缺任何一层，「重建」就退化成「看它自己写的总结」。**归因的精度，等于证据链最短那块板。** 105 期的同快照重放已经给了工具，缺的是把它接进理赔流程。

**第三段「算谁的」没有标准。** 混合原因没有合同主，只能靠默认规则；规则写没写进合同，决定了这次争议是五分钟还是五周。稿子给的两个可操作点是「单一裁决 owner」与「5 个工作日上限、超时判客户」——**把不确定性变成可预算的条款**。

**保险侧还在早期。** Bloomberg Law 讨论「AI Agent 保险」、市场报告开始统计「Agent 行动保险」；但缺损失历史、缺统一定义，保费与除外责任都靠问卷。**没有可核验的事故记录，就没有可定价的保单。** 这也解释了为什么律所先动：**合同能先写，费率只能等数据。**

**责任链上游先跑。** 模型厂商的条款通常只保证「尽力」、把行为责任留给集成方；平台只保证「服务可用」；客户配置与数据又常被列为除外。**三方都能证明自己没错，损失停在中间。**

## 四、技术挑战

**一，可用性 SLA 与失效形态错配。** Agent 最常见的失效是「在线、答错、还执行了」，不触发停机，也就不触发信用。

**二，重建依赖全链路证据。** 少一层回执，归因就只能靠自述；而自述恰恰是最不可信的一层（115 期）。

**三，混合原因没有主。** 上游数据错、Agent 没核对、客户配置也不对——三方都能举证自己没问题；没有默认规则，争议成本高于赔付金额。

**四，赔偿上限与爆炸半径不匹配。** 合同常把赔偿封顶在 12 个月服务费，Agent 一次错误动作的损失可能是它的几十倍；保险是唯一可能补口子的，但可保性取决于证据。

**五，归因本身要花钱。** 重建一次要几小时到几天，SRE 没权限签字，支持团队不懂技术；**没有专职裁决 owner，流程会在三个部门之间空转。**

**六，赔偿条款与运维指标脱节。** 合同写「准确性 99%」，但运维看板没有「准确性」这一项；写「投诉率 <1%」，但没有工单标签能算。**签得下的条款，量不出来的指标。**

**七，赔付会改变行为。** 一旦按结果赔，团队会倾向少做、少自动化、把动作推给人；**防御性运维是赔付条款的隐性成本**，定价与自治度要一起算。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `indemnity.*` 字段**：`claim_id`、`fault_layer`（agent／upstream／mixed）、`evidence_refs`、`clause_ref`、`payout_state`、`adjudication_days`。
- **R2 三段裁决**：先判可达性，再重放重建，最后三分类；混合原因用合同里的默认规则。
- **R3 证据包**：uptime 日志＋请求/工具回执＋决策日志＋当时配置快照，一次事故一包。
- **R4 合同分层**：可用性 SLA＋结果 SLA＋自主动作赔偿＋三类除外＋审计权。
- **R5 可保性材料**：年度证据包（护栏、审批、回滚、日志完整率），用于投保与续保。
- **R6 度量**：争议率、裁决时长、赔付金额、未保险损失，四项进季度评审。
- **R7 信用计算器**：把合同阈值映射到看板指标，自动算「本次该赔多少、依据哪条」，避免手工对表。

### 5.2 用户旅程

- **值班 SRE**：客户报障 → 先查可达性（在线）→ 触发重放 → 导出证据包 → 交裁决 owner。
- **支持／裁决 owner**：拿到证据包 → 按三类判 → 混合原因套默认规则 → 5 日内出结论 → 赔付或说明。
- **法务**：审合同 → 把默认规则、5 日上限、除外条款写进 SLA 附件 → 年度复核一次。
- **CFO／保险**：用年度证据包投保 → 理赔时提交同一包 → 核对除外责任 → 结算。

### 5.3 实现方案（90 天）

- **0–30 天：盘条款。** 现有合同逐条对照六条 BPO 式条款；标出「只保可用性」的缺口。
- **30–60 天：备证据。** 把 uptime、回执、决策日志、配置快照打成标准包；建重放脚本。
- **60–90 天：演练。** 做一次混合原因争议演练；把默认规则与 5 日上限写进合同；发布裁决 owner 名单。
- **90 天后：投保。** 用年度证据包做投保与续保复盘；把「除外责任」逐条对照内部事故类型，缺证据的补采集。

**第 79 个市场空白（五项）**：结果 SLA 可声明率、归因证据包完整率、混合原因默认规则覆盖率、裁决时长可报率、可保性材料完整率——无一内建；`indemnity.*`／`attribution.*` 为**第 48 次无人提字段族**。本地 173／173-kb 连续第 44 期成组启用：周昕毅 10「不可逆动作仍由人工负责」「白名单动作，恢复失败转人工」＝全库唯一按可逆性分配责任的句子，本期首次当主线；配朱革 15「生产写操作缺少统一权限、审批、限流、审计和回滚控制」、陈忻 29「门禁 100% 通过放行」＝责任前置到门禁。判词：**本地把责任写成「谁批准谁负责」，联网侧 8 月才把「在线≠正确、混合原因怎么判」写成流程；两边都没把「这次赔多少、依据哪条」做成可导出对象。**
