# AI-SRE 技术洞察（第 275 期）

**生成时间**：2026-11-18 06:31（Asia/Shanghai）
**观察窗口**：2026-06 至 2026-11-18
**本期主题**：配额面／多租户公平与配额借用——配额是承诺，但没人证明它被兑现

## 题眼

Cohere 2026-06-17 公开的多租户推理调度方案，开头给了一个极简的反例：**单一全局队列**里，一个组织突发 10,000 个请求，另一个组织只发 5 个——那 5 个“行为良好”的请求排在 10,000 个后面。吵闹邻居不是恶意，是**队列结构**决定的。Cohere 的解法是四层：准入限流器、性能层级（按 SLA 分档）、**赤字轮询（DRR）按租户分配计算预算**（以请求数或 token 数计）、租户内按优先级／截止时间／到达时间排序；并称已在其 SaaS API 与 AWS 等第三方市场全量启用。

这套东西每一层都“可采购”，但合起来暴露了一个没人回答的问题：**四层用的是四种计量单位**——请求数、token 数、GPU 秒、外部 API 调用次数。同一份“配额”，在准入层是 RPM，在调度层是 token 预算，在账单上是美元。当低优先级租户**借用**空闲容量（NVIDIA GTC 2026 的 P81532 明确把“动态配额共享、低优先级租户借闲置容量”作为卖点），借了多少、什么时候还、还了没有，没有任何一层负责记账。Kueue 的 Configurable Preemptions（v0.20 alpha，2026-09-21）甚至专门警告：规则配错或对称时，会触发**级联抢占**与集群范围的持续中断。

## 一、发展趋势

1. **公平从“集群级上限”下沉到“租户级调度”**。Kubernetes 的 ResourceQuota 只封顶命名空间总量，LimitRange 设单 Pod 默认值与上限，PriorityClass 决定压力下谁被驱逐（c3x，2026-09-20）；真正的公平要靠 Kueue 的 cohort＋nominalQuota＋borrowing（Qovery，2026-10-30）。三者解决的是不同问题，混为一谈就会“配额设了、公平没发生”。

2. **借出容量成为默认能力，归还没有默认机制**。NVIDIA 把“低优先级租户借用闲置容量、饱和时保证高优先级最小吞吐并对其余返回 429”写进卖点；Kueue 的 borrowing 允许 ClusterQueue 超出 nominalQuota 使用同 cohort 的空闲额度。借是自动的，还是抢占式的，取决于 owner 回来时有没有地方放。

3. **Agent 把配额单位打散**。一次用户请求可能展开成 N 次工具调用：每次读日志、查工单、调外部 API 都各自有配额（云厂商 API 的 RPM、内部服务的并发、模型的 token）。APIM 的 `llm-token-limit`（2026-08-03）已经在做 per-tenant 的 TPM＋月度 token 上限，并用 `estimate-prompt-tokens` 在转发前预估、拒绝超长提示；但对“这次请求一共花了多少次工具调用”仍然没有配额语义。

4. **429 与 403 的语义正在被客户端抹平**。APIM 的设计是：TPM 超限返回 **429＋Retry-After**，月度配额耗尽返回 **403** 直到重置。但多数 Agent 框架把两者都当“可重试错误”，退避后重试——重试本身继续消耗配额，把“借用额度”吃成“欠债”。

## 二、技术现状

**第一层：准入限流挡不住队列里的不公平。** kvwarden（2026-04-21）在单卡上做 per-tenant token bucket，默认 hero 配置 `rate_limit_rpm: 600`、`rate_limit_burst: 10`，并暴露 `tenant_rejected`、`admission_queue_depth` 两个指标；它的排障表直言“安静租户在洪水下仍被饿死”的常见原因是 `rate_limit_rpm` 设太高。也就是说：限流器只保证“不超额”，不保证“按份额”。

**第二层：公平调度需要显式的“份额”与“轮转”。** Cohere 的 DRR 是经典做法：每个租户有一个 deficit 计数器，轮到时按预算发请求，预算用完就排到队尾。它的好处是把“激进程度”从分配里剔除；代价是需要一个**稳定的预算单位**。以请求数计时，长请求会占便宜；以 token 计时，短请求的固定开销会被忽略。

**第三层：借用没有账本。** Kueue 的 borrowing 是“同 cohort 内借空闲额度”，owner 回来时通过 preemption 收回；被抢占的工作负载按 PriorityClass 排序，低优先级先走。问题在于：抢占发生时，被抢占方已经消耗的资源不会退回，借用方也不会收到“你欠了谁多少”的账单。级联抢占的警告说明这个机制在复杂策略下会自我放大。

**第四层：成本归属把“配额”变成“账单”。** c3x 给的数字很直白：24 个单团队集群约 **$6,800/月**，3 个共享集群约 **$850/月**——共享省下的钱，正是“吵闹邻居”风险的来源。没有成本隔离，一个团队的失控 Deployment 就是所有人的账单。

**判读**：限流器卖“不超额”，调度器卖“按份额”，Kueue 卖“借与抢”，账单卖“谁付钱”。四者之间缺的是**一份跨单位的借用账本**：借的时候记单位与期限，还的时候记是否归还、差多少。

**本期反转**：我们一直把配额当“防滥用开关”，所以只关心“有没有超”；但配额本质是**承诺**——承诺这个租户本周期能拿到多少。承诺需要兑现证明，而当前的指标体系里没有一个“公平性指标”：没有份额偏差、没有饥饿时长、没有借用归还率。**没有兑现证明的配额，只是一张可以被抢占的欠条。**

**判词**：「限流器／队列／DRR／优先级／ResourceQuota／Kueue／APIM 策略」全部可采购，「这个租户本周期应得多少、实际分到多少、被谁借走、是否归还、公平偏差多大」不可采购。

## 四、技术挑战

1. **单位不可通约**：请求、token、GPU 秒、外部调用、美元之间没有汇率；任何“统一配额”都要先声明换算规则，而规则本身会被优化。
2. **借用的会计缺口**：借用发生在调度器内部，账单发生在财务系统，中间没有关联键；抢占后已消耗的算力不退，借方也不欠账。
3. **Agent 扇出**：一次请求 N 次工具调用，配额按请求计会低估、按调用计会惩罚编排质量；需要“结果级预算”而不是“调用级预算”。
4. **重试风暴**：429／403 被统一当可重试，退避策略缺失时，配额耗尽会转化为对上游的重试压力。
5. **公平性不可观测**：现有指标是“拒绝数、队列深度、利用率”，回答不了“租户 A 本应 30%、实得 18%，被谁借走”。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 单位声明：每个配额对象标注计量单位与换算规则（1 请求≈多少 token、多少 GPU 秒），变更走评审。
- D2 分层策略：准入（限流）→ 份额（DRR／fair share）→ 借用（上限＋期限）→ 抢占（优先级＋通知）。
- D3 借用账本：借用时写入（借方、贷方、单位、数量、到期时间），归还时写回（实还、差额、是否抢占）。
- D4 错误语义：429 带 Retry-After 且客户端必须遵守；403 不重试，转人工或降级；框架层默认区分。
- D5 公平性 SLO：份额偏差（|实得−应得|/应得）、饥饿时长 P99、借用归还率、抢占次数/级联深度。
- D6 演练：季度做一次“owner 回归触发抢占”，验证级联深度与通知链路。

**用户旅程（一次 batch 借走交互式配额）**

① 团队 A 的 batch 任务进入共享 cohort，nominalQuota 用尽后开始借用空闲额度（D3 记账）；② 团队 B 的交互式 Agent 流量上升，队列变长（D5 份额偏差告警）；③ 调度器按优先级抢占 batch 的部分 Pod（D2），被抢占任务重试；④ 重试请求再次进入准入，若客户端不遵守 Retry-After 则形成重试风暴（D4）；⑤ 月末账单显示 A 用了 140% nominal，但账单与借用账本对不上（D3 缺口）；⑥ 复盘需要回答“B 被借走多少、A 还了多少”，当前只能靠人工推。

**90 天实现方案**

- **第 1–30 天**：统一单位。给每个配额对象打 `unit` 与 `conversion` 标签；把现有 RPM／TPM／月度 token／GPU 配额列成一张对照表；在网关与调度器日志里加 `tenant_id`、`quota_id`、`borrowed_from`。
- **第 31–60 天**：建账本。调度器在借用与归还时写事件；财务侧按 cohort 汇总；上线三个公平性指标（份额偏差、饥饿时长、归还率）并设阈值告警；把 429／403 的客户端处理改成可配置。
- **第 61–90 天**：演练与门禁。做一次 owner 回归的抢占演练，记录级联深度；把“借用未归还超期”纳入事故分级；每季度重算换算规则，防止单位漂移。

**第 196 个市场空白（五项）**：① 跨单位配额换算标准；② 借用账本的数据模型；③ 公平性 SLO 的指标定义；④ 429／403 的客户端契约；⑤ 抢占级联的可观测口径。

**`quota.*`／`fair_share.*` 第 163 次无人提字段族**：厂商文档谈“支持配额与借用”，不谈“借了多少、还了没有、公平偏差多大”。

**本地 173／173-kb 连续第 151 期成组启用（马云雷 31：配额与成本归属要能对上同一本账）**：本地原型以 kvwarden 的两租户 token bucket（600 rpm／burst 10）为基线，在事件流里加 `borrow_ledger` 字段，用“实得份额 vs 应得份额”出周报；对不上的租户自动开单，而不是等月底账单。
