# AI-SRE 技术洞察 · 第 28 期

## 时间面运维：当"等待"成为可分配、可记账、可失效的资源

> 前 27 期依次覆盖了治理、结果质量、证据来源、人的能力、记忆、供应链、路由、承诺结算、进化、缓存十个平面，但有一个变量始终被当成背景：**时长**。很少有人问"它跑了多久，这段时长由谁承担、能不能被记账、过期之后还算不算数"。本期提出第十九条主线——时间面运维。它与第 25 期"承诺面"的分界是：那期管"对外承诺了几个九"，本期管"兑现这个承诺花了多久，以及人还在不在等"。

---

## 一、发展趋势：三个抽象迁移

**第一，从"调用"迁移到"任务"。** MCP 2026-07-28 修订引入 Tasks：以往同步工具调用只有 30–60 秒窗口，CI、批处理、长期研究类操作根本装不进去；现在服务端先返回 task_id，客户端可继续别的工作并轮询，**任务被接受后客户端不再限制总时长**。Anthropic 在 Claude Code 里加了一条更现实的补丁：老 MCP Server 不需要改造，调用超过两分钟自动转入后台。超时的定义权由此从调用方移到承载方——这是接口语义级的迁移，不是参数调整。

**第二，从"机器等待"迁移到"人类等待"。** Google 在 CI 修复智能体 FlowAgent 上没有拍一个 30 分钟的上限，而是先做 30 天等待普查：人重新回到这条失败流水线的时间分布是 p25 6.72 分钟、p50 27.48 分钟，然后把智能体上限设为 30 分钟。这是把"人愿意等多久"编译成系统常数。

**第三，从"成功/失败"迁移到"三态/未知"。** 火山方舟后台任务的状态机里，`unknown` 与 succeeded、failed 并列，文档明确写"不要将该状态视为成功"；阿里 Qwen Code 在 11 月 1 日给自动修 PR 加了 `inconclusive` 结论。行业第一次承认：**"不知道"是终态之一**。

三者指向同一结论：时长正从实现细节变成契约的一部分。

## 二、技术现状

**Google。** FlowAgent 的生产数据是目前唯一公开的"时间预算"完整样本：256.8 万次失败变更中，前置过滤器在智能体启动前筛掉 178.6 万次（69.5%），只把 42.2 万次交给智能体；上线修复超过 2.8 万次；人工评审 195 例，67.18% 判定正确；单次运行中位 9.85 分钟；**42.2 万次运行中有 12.6 万次（约 30%）的成功修复在交付时已过期被丢弃**。

**Anthropic。** Claude Code 2.1.311（10 月 26–27 日）几乎是一份"时间面缺陷修复清单"：此前标准上下文超过 20 万 token 会直接抛"需要 1M 上下文额度"并丢掉整个会话，现在自动压缩后继续；自托管 Runner 新增 `--hold-idle-file` 与 `--max-hold-min`，让"后台进程还在跑"的会话不被判为空闲而提前退出；`--shutdown-drain-sec` 让 SIGTERM 后停止拉新任务但在窗口内让在途轮询跑完；并修掉一个典型错配——**客户端此前会重试被 API 明确标记为不可重试的请求，在无人值守下造成数分钟乃至无限期挂起**。产品侧还出现两种对立策略：`/loop` 创建 7 天后自毁并最后触发一次；Managed Agents 则给每会话硬预算，触顶即 `budget_reached` 暂停。

**OpenAI。** Codex 0.166.0（10 月 29 日）把重心放在长会话的可检查性：transcript 导航与搜索、线程恢复、以及"消息排队成功但恢复失败"这类中断态修复。其默认重试是 HTTP 4 次、流式中断 5 次，但**缺少"这一步最多重试两次、120 秒砍掉"这类步骤级原语**。开发者社区的要求更尖锐：checkpoint 只保存状态，graceful pause 还必须约束智能体下一步能做什么，且"检查点绝不能静默假设被中断的操作已经成功或已经失败"。

**字节跳动。** 火山方舟的处理最"运维化"：bash 命令正常执行 60 秒未完成即转后台返回 task_id；文档明确提示"不要只轮询 Session 状态判断任务是否完成，应查询对应 Task 的 state"；只要有未结束的后台任务，Session 的 status 会一直是 running——**"忙碌"与"空闲"的语义被改写了**，容量、计费、利用率的既有口径全部要跟着改。

**阿里巴巴。** Qwen Code v0.26.5（11 月 1 日）给无人值守修 PR 设了硬边界：最多推 3 次修复就移交人工，`/autofix-pr status` 显示交接状态，PR 里注明已尝试什么、卡在哪；沙箱内的 verify-pr 发布器自己跑产物检查，检查失败或跑不起来就把这一轮标为 inconclusive 而不是失败。这是把"三次不成即认输"写进产品，而不是留给提示词。

**腾讯。** 腾讯云 ADP 的底座叙事直接围绕时长展开：1 Session : 1 沙箱、存算分离（实例销毁不丢数据、秒级 CoW Fork、**长任务中断原地续跑**）、休眠唤醒 P95 ≤ 300 ms、闲置不计费。

**其他。** DeepSeek Harness 团队 11 月 1 日开源的 Super-agent 给了一组罕见的长尾数据：双层架构完成时间 p50 12.4 分钟、p95 15.7 分钟；单会话加 Subagent 在"中性提示"下 5 次运行一次都没委派，全堵在主会话里被打断，p95 拉到 29.5 分钟——**长尾不是模型慢，是模型自己判断"这活太小"**。其 Router 在积压时合并批处理，单决定分摊时间从 6.4 秒降到 1.6 秒。

**本地知识库补充。** 173 库中李东东（快手电商 B 端）的端云协同实践，是这批材料里唯一从产品侧倒推时延的：纯云端 2–5 秒，"商家经营操作等不起"，于是把高频能力下沉到端侧，目标延迟 < 100 ms。它提示：等待预算从来不只是运维指标，它先是架构决策的输入。

## 三、技术竞争力：六维对比

| 方案 | 时长上限与终止机制 | 超时/重试原语 | 恢复粒度 | 未知态处理 | 等待侧可观测 | 闲置计费 |
|---|---|---|---|---|---|---|
| Google FlowAgent | 30 分钟（由等待普查反推）+ 工具调用 100 次 | 内部自建，按分层重跑测试 | 按失败变更重跑 | 未公开 | 有等待分布普查，无产品化 | — |
| Anthropic Claude Code / Managed Agents | `/loop` 7 天自毁；会话硬预算 `budget_reached`；云任务 100 次/小时 | 不可重试错误已修正；MCP Tasks 无默认总时长 | 会话级 + 沙箱快照 | 重连失败探测 5 分钟后报 unknown | 弱（Monitor 事件流替代轮询，300 s/1800 s） | 按会话计 |
| OpenAI Codex | 无数字上限；靠使用额度自然中断 | HTTP 4 次 / 流 5 次，缺步骤级 timeout | 线程恢复 + transcript | 中断态修复中，未产品化 | 弱 | 按 token |
| 火山方舟 Managed Agents | Task 级状态机六态，含 unknown | bash 60 s 自动后台化 | 沙箱状态自动保存、原生断点续跑 | **unknown 一等状态，明示不可视为成功** | 中（Task state 可查，Session 状态不可作准） | 按资源 |
| 阿里 Qwen Code / STAROps | 修 PR 上限 3 次 + 人工交接 | 轮次级硬边界 | 轮次级 | **inconclusive 显式结论** | 中（status 命令 + PR 注释） | 按调用 |
| 腾讯 ADP / CloudQ | 会话级；异步任务可查状态 | 平台内置 | 原地续跑（存算分离） | 异步任务状态查询 | 中 | 闲置不计费 |
| DeepSeek Harness | 双层调度 + Watchdog 会话 | Router 批处理、积压合并 | 会话级 | 未公开 | 强（p50/p95 完成时间公开） | — |
| 开源（Temporal 类） | 工作流级 timeout / retry 策略 | 成熟但面向确定性步骤 | 事件溯源级 | 需自行建模 | 无 AI 语义 | 无 |

判读：**所有厂商都在补"能跑多久"，没有一家补"跑完还有没有人要"。** 时长上限、断点续跑、未知态建模这三件事在 12 个月内已从"没有"变成"标配"；但"等待侧"仍是空白——除 Google 做过一次普查，没有产品把"人什么时候离开"做成指标，更没有产品把废弃成果计入成本。竞争焦点正从"跑得久"转向"停得准"，而"停得准"的前提是知道人在不在。

## 四、技术挑战

**1. 陈旧产出没有度量。** 30% 的成功修复因过期被丢弃，这个数字在任何 AI SRE 产品的仪表盘上都找不到。它比失败更贵：失败至少释放了队列，过期成果占满了算力、队列和上下文，最后只换来一次删除。**"正确但太晚"与"错误"在运维价值上等价，在成本账上不等价。** 建议引入时效产出率＝被采纳成果 ÷ 全部成功成果。

**2. 检查点的时间盲区。** 检查点记录的是"智能体读到了什么"，不是"它读到的东西现在还成立吗"。从 40 分钟前的检查点恢复，等于用一个过期的世界模型执行新的写操作。恢复的正确姿势不是"接着跑"，而是"先做选择性再验证"：把检查点里的证据打上有效期，过期证据强制重采。这与第 22 期的记忆一致性不同：那期问"同一时刻读到的对不对"，本期问"跨时刻读到的还对不对"。

**3. 重试策略的默认值是写给微服务的。** 只读可以自由重试，写必须带幂等键，不可逆（发送、提交、发布）必须人批且失败不自动重试——这是三条不同权限。但主流框架统一处理：Codex 默认 4/5 次、多数 Agent 框架对所有工具一视同仁。后果是智能体重复发邮件、重复提交半成品订单，或对同一个坏工具无限重试形成**智能体层重试风暴**。重试权限应当由副作用类别决定，而不是由框架默认值决定。

**4. 未知态把不确定性下推给值班。** `unknown` 被正名是一大进步，但它的运维成本是隐性的：一个 unknown 任务需要人去看、去对账、去决定补发还是放弃。平台把状态诚实地说出来了，却没有给出"unknown 的标准处置剧本"，等于把机器的不确定性转成人的工时。

**5. 并发恢复与状态腐坏。** 两个实例同时恢复同一任务会产生重复执行，这是长任务最危险的一类故障，需要分布式锁；而多数 Agent 的恢复能力是在单实例假设下设计的。同时，20 万 token 之后自动压缩让会话不死，但目标在反复摘要中逐层漂移，行业已在日级任务上放弃压缩、改用"整体重置 + 结构化交接文件"：压缩解决 token，不解决保真。

**6. 时间预算不可累积。** 第 25 期把错误预算拆成可加、可上卷、可重构、不透明四类；等待预算属于最苛刻的一类——每次独立重置、不可累积、不可转让，因此**不能像 error budget 那样用燃烧率管理**。一次快不能抵一次慢。现有 SLO 工具箱在这里整体失效，替代工具还没人做。

## 五、展望与建议

1. **把"人在不在"作为任务的一等输入。** 启动时记录截止时间与 human-present 标志；无人在场时禁止不可逆动作。这不是靠审批拦，而是靠时间拦——审批会疲劳，截止时间不会。

2. **时效产出率进 SLO 与成本账。** 分子只算被采纳的成果，"过期丢弃"单列为成本科目。

3. **三态结算替代二态重试。** 写操作恢复前必须归入未发送、已发送结果未知、已确认成功三类；"未知"必须走权威查询收口，禁止直接重发。

4. **给检查点加证据有效期。** 恢复第一步是再验证而非执行，把"证据是否仍成立"做成可机检的前置断言。

5. **重试按副作用分级，覆盖框架默认值。** 只读自由重试、写带幂等键、不可逆禁止自动重试；这不是建议，应写成代码门禁。

6. **长任务设双上限，并用事件流替代轮询。** wall-clock 管等待侧，step/token 管成本侧，两者都要配"到限后怎么收"的剧本；sleep-loop 轮询是采样率问题，太密付请求费、太疏漏掉中间失败。

7. **演练"人的离开"。** 第 20 期演练故障注入，本期建议增加一类：任务中途撤走审批人与值班、拉长响应间隔，看系统是否安全停下而不是继续猜。
