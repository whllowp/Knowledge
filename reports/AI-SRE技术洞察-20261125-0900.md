# AI-SRE 技术洞察 第 321 期

**生成时间**：2026-11-25 09:00（bash `date` 取值 09:31，归档 0900 档）
**主线**：结论汇聚面／多调查者裁决——「每个工程师都带着自己的 Agent 查同一起事故，几个互相冲突的根因摆上桌，谁有权关掉一个假设、按什么证据收口、这次收口能不能被独立复演」（Adjudication Integrity / Convergence Authority / Who Closes a Hypothesis）

**题眼**：过去十余期我们追问"证据可不可举证""复核者独不独立""判定函数是同一把尺子吗"，本期换一个正在快速成型、却几乎无人计量的环节：**当五个 Agent 加一个值班工程师同时查一次故障，给出五个互相冲突的根因，最终写进复盘的那一个，是怎么从五个里被选出来的？** 11 月 19 日 groundcover 发布 Investigations，把"调查"做成一个共享工作区：Investigator Agent 建假设图、查日志指标追踪，Moderator Agent 复核每条结论，并且——官方原文——**只有 Moderator 有权关闭一个假设**，没有证据支撑的主张会被退回[1]。这是行业里第一次把"收口权"显式写进产品设计。但紧接着的问题是：**关掉 Moderator 自己的那条结论，又归谁？** 看得见"多个 Agent 都给出了结论" ≠ 看得见"结论是怎么从竞争假设里被裁出来的、裁判是不是独立、被否掉的那几个为什么被否"。

## 一、发展趋势

三条趋势在本期交汇。

**其一，从"单 Agent 深挖"转向"多 Agent 并行 + 汇裁"。** 过去 Agent 是单人替值班工程师跑腿，如今产品默认让多个专职 Agent 同时查：New Relic 11 月 12 日在 KubeCon 发布 Autopilot Kubernetes Agent，跑 90 多个诊断探测器横跨事件、对象描述、日志与 APM trace，由基于 OpenTelemetry 的 Ground Truth 上下文引擎关联，生成修复代码但保留人工审阅执行[2][3]。GitCode 的工程总结把这条链路写成 Collect→Correlate→Prioritize→Act 四步，并直言多 Agent 真正的力量不是并行收集，而是**分布式推理后由协调层合成**[5]。 SentinelOps 更把"生成多个相互竞争的假设"当核心差异，而非直接吐一个答案[4]。**调查正在从"一条线索"变成"一个假设市场"，而市场必须有裁判。**

**其二，裁决/仲裁开始被单独产品化，但方法论仍是黑箱。** 腾讯云把"多 Agent 结论矛盾"单列一类，主张用大模型做六维动态仲裁（紧急度、业务价值、资源成本、耗时、容错空间、历史准确率），甚至"融合生成综合结论，而不是直接舍弃任一方"[8]；稀土掘金则提出先拆"事实层／解释层／利益层"再仲裁，警告"冲突就投票／取平均"是仲裁失灵的第一原因[7]。groundcover 的 Moderator、SentinelOps 的 critic+裁决层+人工审批[1][4]、控场 AI 的 Parser/Generator/Validator 三段解耦[6]——**裁判的身份第一次可视化了，但裁判的"判据、独立性、改判留痕"没有一家导出。**

**其三，裁判的"规则文本"本身成了新的治理对象。** Cloudsmith 11 月 9 日在 KubeCon 发布 AI Agent Skills 注册表，把 SKILL.md 及脚本当软件工件管理：语义版本或 commit SHA + SHA-256 校验、允许/拒绝名单、统一审计日志，明确"社区技能注册表为分享而生、不为控制而生"，企业答不出"谁发布、Agent 跑的是哪一版、谁批准过"[9][10][11]。当"告诉 Agent 怎么查、怎么判"的技能包可无版本号静默改写，前面所有的裁决可信度都建在流沙上——这是第 83 期"工具从哪来"、第 99 期"规则位阶"在裁决环节的新落点。

## 二、技术现状

**竞争假设的收敛有四道关，行业都装了，但没有一道关本身可被核验。**

**第一道：生成竞争假设。** SentinelOps 由遥测、知识检索（RAG）、部署关联三类专职 Agent 供证据，根因 Agent 生成"多个相互竞争假设"，批评 Agent 挑战领先假设，裁决层按时间与因果证据加权裁定，恢复规划器产出带证据引用的建议并强制人工审批[4]。这是最完整的公开架构，但其 15 个合成事故基准 Top-1 命中仅 73.3%、Top-3 86.7%、证据覆盖率均值 97%[4]——**约四分之一的情况下，三道防线选出的首选假设是错的，而这个错被裁掉的过程没有独立账本。**

**第二道：身份分离。** groundcover 把"生成解释"与"验证解释"分给两个 Agent，只有 Moderator 能关闭假设，并把每条假设的支撑/反驳评估回写 Slack 告警帖、帖内回复再回流调查[1]。这与第 300 期"复核独立性面"直接相接：彼期问"第二个 Agent 是不是同源回声"，本期深一层——**Moderator 与被它否掉的 Investigator 若共享模型、harness、工具凭据与同一批遥测，所谓"裁决"只是同一套盲点的一次投票表决。**

**第三道：按层仲裁。** 掘金把多 Agent 冲突拆成事实层（数据口径与源头）、解释层（假设能否被下一批数据推翻）、利益层（主张是否服务本模块 KPI），并点出两种系统性偏差——"响亮者偏差"（叫得最响未必证据最全）与"虚假紧急"（一方催得急只为让你没时间核验）[7]。**这两条bias在 RCA 场景尤其致命：根因只有一个，投票取平均会把互斥解释揉成一句谁都不对的套话。** 腾讯云"融合生成综合结论而不舍弃任一方"[8]在故障定位语境下恰是把解释层混同事实层。

**第四道：停止收口。** GitCode 把"知道何时停止"列为多 Agent 协调的核心挑战，要求"证据已足够"的标准而非无限调查[5]；这与第 304 期"调查污染面"的"满意即停 vs 证伪后停"同一命题。当前实现普遍用 token 上限或轮数上限熔断，**"收口时到底有哪几个假设仍在场、被关掉的是被证伪还是被超时"无人记录。**

现状可一句话概括：裁判身份可视化了，裁判的判据与改判留痕仍全表空白（详见下节对比）。

## 四、技术挑战

**挑战一：收口权集中在单一裁判，而裁判自己没有裁判。** groundcover 明确"只有 Moderator 能关闭假设"[1]，SentinelOps 由裁决层裁定胜出假设[4]。这与第 300 期同源回声问题叠加：一旦 Moderator 与 Investigator 共享模型与遥测，四道防线只是在同一盲点里反复确认。**第 292 期"判据长在 Agent 够不到处"在此升级为"裁判也要长在被测 Agent 够不到处"。**

**挑战二：互斥根因被"融合"成综合结论。** 腾讯云明示"平衡风险与收益权重，融合生成综合结论而不是舍弃任一方"[8]，掘金警告"投票/取平均"是仲裁失灵首因[7]。故障根因具有排他性：**两个 Agent 一个说"网关故障"一个说"制品缺失"，融合成"网关侧的制品问题"不是收敛，是制造第三个更错的解释。** 三层分流（事实先核口径、解释再看可证伪性、利益走资源仲裁）才是正解，但无人把它做成运行时字段。

**挑战三：没有"反事实重裁"能力。** 收口结论是否依赖"换一组 Agent、换一批遥测时刻就会翻转"？第 311 期"运行间一致性面"（同一 Agent 重跑结论是否同一个）在此的升级版是"换裁判是否同一个"。**当前产品验证的是"这次收口合理"，没有一家验证"换裁判仍收口到同一根因"。**

**挑战四：裁判的规则文本可无版本号改写。** Cloudsmith 点明 Agent Skills 规范不要求版本号，同名技能可从 Git 静默改变，企业答不出"Agent 跑的是哪一版、谁批准"[9][11]；Futurum 2H 2026 调查显示 44.7% 的 SLE 决策者把"缺治理与控制"列为扩大 AI 使用的前三障碍，45.1% 已强制要求记录 Agent 行为审计日志[12]。**裁决逻辑写在技能文本里，文本不钉版，则裁决不可复演。**

**挑战五：告警帖双向同步让"各方观点"混成"共识"。** groundcover 的 Slack 双向同步让帖内回复回流调查[1]，第 316 期"审批证据面"的通道载荷问题在此重现：**工程师随口一句质疑与一条带证据的反驳，进入同一工作区后权重是否相同？没有角色的发言被当成"团队已确认"，是收口被社会压力污染的入口。**

## 五、展望与建议

**提出第 242 个空白字段族 `convergence.adjudication.*`（本期归纳，缺省 `CONVERGENCE_UNVERIFIED`）**，建议至少十字段：`incident_id`、`candidates[]`（`hypothesis_id`/`proposed_by`/`evidence_refs[]`）、`critic[]`（`challenger_identity`/`target_hypothesis_id`）、`arbiter_identity`（关闭权归属）、`arbitration.layer ∈ FACT|INTERPRETATION|INTEREST`（按第 7 源三层分流）、`decision.rule ∈ EVIDENCE|VOTE|AVERAGE|FUSION|HUMAN`、`eliminated[]`（`hypothesis_id`/`reason ∈ REFUTED|TIMEOUT|SOCIAL|UNKNOWN`）、`counterfactual.re_adjudicated`（换裁判是否同结论）、`referee.skill_version`（hg 裁判规则钉版 SHA）、`verdict ∈ ADJUDICATED|UNARBITRATED|VOTE_TYRANNY|UNVERIFIED`。

**四条最小动作**：① 每条写入复盘的结论强制附"关闭了哪些竞争假设、各按什么理由"，`reason=SOCIAL|TIMEOUT` 的结论不得进确定知识；② 裁判候选与被测 Agent 在模型、harness、工具凭据至少一维不同，复用第 300 期独立性门槛，Moderator 自身须有第二裁判或人工背书；③ 按事实/解释/利益三层分流仲裁，禁止把互斥根因做 FUSION 或 AVERAGE，`decision.rule=VOTE|AVERAGE|FUSION` 自动降级为 UNVERIFIED；④ 裁判技能包钉 commit SHA + SHA-256 并纳入审计，复用第 83、99 期规则治理。

**评测采购两问**：同一起事故换一组 Agent 重裁，根因还是同一个吗？被否掉的那几个假设，有没有留下"为什么被否"的证据？**评测改造**：给长事故题加"多 Agent 竞争假设 + 换裁判重裁"配对题，报 `counterfactual.re_adjudication_rate` 与 `elimination.reason.distribution`；沿用第 310–320 叠加门禁，`verdict≠ADJUDICATED` 的收口不得回写确定知识、不得进自治升档。

**信通院六维建议补一格"收口可举证率"**，与第 316 期"审批可举证率"、第 317 期"执行中授权可举证率"、第 318 期"空窗期可举证率"、第 319 期"判定可举证率"、第 320 期"自伤可举证率"并列：前五格管"人有没有真的看图签字、尺子是不是同一把、事故是不是 Agent 自己惹的"，本格管"多个 Agent 给出的冲突结论，是被证据裁出来的，还是被响亮者、多数票、融合取平均凑出来的"。

**本地知识积累（第 197 期新角度）**：王上淇《从对话框到生产线——企业的 AI 工作台》首次换方向读作"当每个工程师都带着自己的 Agent 上生产，工作台真正稀缺的不是再给一个 Agent，而是给多个 Agent 的竞争结论提供一个可举证、可改判的收口层"——配刘凯宁"结论/证据/待确认项"三分做竞争假设卡骨架、赵恒"写入状态要有权威来源不能由写入器自报"、何伟"可验证持续改进前提是验证环境可信"；本地 173 按目录级引用。
