**本期主题**：表计面／计量器独立性面（Metering Integrity / Who Meters the Meter）——计价器长在被测系统里；−87.9%、$6/会话、AI 工时，全是自报数

## 题眼

112、113 两期把账本拆到「分母」，这一期拆最后一层：**分子是谁数的？** 07-23 arXiv 2607.21672 做了一件很少人做的事——把同一段源码分别以文本和渲染图送进 Anthropic、OpenAI、Google Vertex 的 15 个模型别名，675 对请求、5 种语言、20 到 2,000 行，记录**厂商自己回报的输入 token**。结论是：15 个别名只塌缩成约 5 种计费签名，整体图像/文本计数比为 0.135／0.194／0.242，对应报告口径的输入 token 缩减 86.5%／80.6%／75.8%；Gemini 在 20 行时图像反而要 6.95 倍 token，到 200 行才交叉；跨页边界还出现非单调计数。**同一份内容，换一家，省的比例就变了——变的不是工作量，是表。** 若采购按 86.5% 签、实际按 75.8% 结算，中间 10.7 个点不是折扣，是计量差。这不是学术洁癖：每一张 FinOps 归因报表都建在这张表上。

## 一、发展趋势

**趋势一：FinOps 从「看账单」转向「算效率比」，表仍在厂商手里。** 2026 年下半年的 AI FinOps 文章普遍在讲 token cost 与 token yield、按美元归因到团队；指标越算越细，但输入仍是云账单和厂商 usage 接口——**分母在变精细，分子仍是对方给的**。归因也一样：费用只能归到平台愿意打的 tag 上，tag 之外的支出进共享池，**归因精度止于标签粒度**。

**趋势二：计量本身开始被当成研究对象。** 2607.21672 公开脚本、revision-pinned 语料、原始 usage 记录、校验器与确定性分析，让「表准不准」第一次可复现；这是从「信厂商」到「验厂商」的转折点，虽然只覆盖一个渲染管线。**可复现计量的价值不在结论，在方法：它证明「表」可以被第三方重算，而厂商文档从来没打算让你重算。**

**趋势三：供给链审计扩展到技能与遥测，唯独不扩展到成本。** Cloudsmith 11-09 给 skill 做版本、allow／deny 与拉取审计；ControlTheory 11-09 让 AI SRE 自带遥测。**能审计「拉了哪个技能包」，审计不了「这次调查到底花了多少」；能钉版本，钉不了价格。**

## 二、技术现状：四块表，四家自己读

**模型 API 的表最不可移植。** 2607.21672 的 5 种计费签名说明：alias 不等于模型，同名 alias 可能路由到不同后端；图像 token 的折算规则各家不同，甚至同一家跨页边界不单调。**「−87.9%」若来自某一个 alias，换供应商就会变，而代码一行没改。** 更麻烦的是缓存：命中是否计入输入、按几折计价、5 分钟与 1 小时缓存是否分列，各家字段与口径都不同——**同一张表，连「什么算一次输入」都没有共识。**

**运行时的表最诚实，也仍是自报。** HarnessMM 的 README 把 complete-task token 定义得很少见地完整：作者、选择、收尾、重试、回退、失败执行都计入，并明写执行节省与全账节省要分开；但它仍是 harness 自己数自己。DevHelm 的 $6／会话是按 15k 输入、3k 输出、25 轮上限估出来的**估算**，不是账单。

**平台的表是价值叙事的一部分。** 腾讯「AI 工时」把 ReAct 推理时长与工具执行时长合成工作量，阿里用积分计价；两者都由平台自己定义、自己采集、自己结算。**表计与计价同源，等于让卖方定义称。**

**审计的表覆盖动作，不覆盖金额。** Cloudsmith 记 skill 拉取、ControlTheory 记模型与 token 计数，OpenAI 11-05 的评测事故则证明：当自述与被监控同源时，「无需提及」可以成为默认。**能证明「发生过什么」，不能证明「花了多少、值不值」。**

**失真只有三种，每种都不报错。** 一是少报——失败执行、重试、压缩、工具调用被排除在「任务成本」外；二是选口径——挑对自己有利的 alias、图像折算或缓存规则；三是转移——把成本记进共享池、把收益记给本团队。三种都不触发告警，因为表本身不校验自己。**表计不是测量问题，是治理问题。**

**表错了，SLO 就跟着错。** 成本 SLO、每任务预算、错误预算都建在这张表上；表少报 20%，预算就松 20%，熔断点随之后移。**可观测性只保证「看到系统的状态」，不保证「看到计量的状态」**——后者需要一个不与被测系统同源的读数，而 2026 年的运维栈里没有这个位置。

**独立表计只有三个可能的位置。** 网关看得到请求，SDK 看得到调用，供应商看得到计费；前两者可以异源，第三者只能对账。运维栈里通常只装了第三者，于是「独立计量」在架构上根本没有落点。

## 四、技术挑战

**一，表不可移植。** 同一内容的 token 计数随供应商、alias、渲染方式变化，5 种签名互不换算；跨厂商 A/B 比价在计量层就不成立。

**二，表可被优化。** 压缩、缓存、重试、工具裁剪都会改变 token 结构，而表长在运行时里；**被考核的指标由被考核者自己生产**，Goodhart 定律在成本侧复现——省下来的可能是计数方式，不是工作量。

**三，自报不可举证。** Anthropic 的 80% 只给「无可测损失」，OpenAI 的事故靠外部监控才发现；厂商没有动机公开对自己不利的计量细节。**自报失真的发现延迟以月计**——10 月披露的两起监控事件，采样发生在 6 月与 8 月，中间隔着一次模型升级。

**四，独立表计要付隐私与延迟的代价。** 网关级独立计数能看到 prompt 与响应，需哈希、脱敏与最小留存；多一跳带来延迟，谁来付这笔钱也没有答案。

**五，表计改变激励。** 只考核 token，压缩与裁剪就会压掉必要上下文，token 降了、重试与人工返工升了；只考核 AI 工时，工时会「提炼」成好看的曲线。**必须成对考核成本与质量**，否则表越准，行为越偏。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `meter_receipt`**：每次运行产出收据，含 provider、alias、`accounting_signature`、输入／输出 token、缓存读写、重试、工具调用、价格版本、表计归属。
- **R2 异源表计**：在网关／代理侧独立计数，Agent 运行时不得写表；两表差异作为一等指标。
- **R3 可复算对账**：收据 × 价格表可重算金额；抽 5% 对账，差异超 2% 冻结结算。
- **R4 口径版本化**：`accounting_signature` 注册表；供应商改口径即触发重基线与重新报价。
- **R5 合同条款**：审计权、差异阈值、口径变更通知、独立计量费用归属。
- **R6 报表**：接 113 期的「每结案事故全账成本」，每格标注表计来源与版本。

### 5.2 用户旅程

- **FinOps 工程师**：月末对账 → 网关表与厂商账单差 4.7% → 定位到缓存 token 未计 → 按合同阈值发起复核 → 供应商补差。
- **值班 SRE**：调查一次 P1 → 收据显示 12 次工具调用、3 次重试、2 次压缩 → 成本 $7.4 → 与 DevHelm 的 $6 基线对比，判断是否异常。
- **采购**：要求三家供应商用同一 `accounting_signature` 报价 → 发现 A 家的「图像省 86%」在 B 家只省 75% → 改按「每结案事故」签。
- **审计**：抽查 30 张收据 → 用公开价格表重算 → 偏差在阈值内 → 签字。
- **平台团队**：客户投诉账单偏高 → 用同一套收据自查 → 发现缓存 token 重复计价 → 在客户审计前主动补差并改口径。

### 5.3 实现方案（90 天）

- **0–30 天：收据。** 定义 `meter_receipt` schema；在网关侧接第一版独立计数；与厂商 usage 做日对账。
- **30–60 天：口径。** 建 `accounting_signature` 注册表；把 alias→后端映射纳入变更监控；差异超阈值自动告警。
- **60–90 天：合同。** 把审计权、2% 阈值、口径变更通知写进采购模板；报表加表计来源列；季度抽审。
- **90 天后：同口径基准。** 与两家以上供应商约定同一 `accounting_signature` 做季度比价；把「跨供应商同口径差」纳入供应商评分。

### 5.4 三种失真的检出规则

- **少报**：complete-task token（含重试、失败、压缩）与网关表逐日比对，差异 >2% 告警。
- **选口径**：alias→后端映射变更、`accounting_signature` 变更、缓存规则变更，任一发生即触发全量重算与重新报价。
- **转移**：共享池支出占比与受益团队归因偏差 >20% 时，强制重分摊并公示。
- **频率**：5% 随机抽样常审 ＋ 变更驱动全量审；审的是收据，不是汇总。

**第 68 个市场空白（五项）**：表计归属可声明率、收据可复算率、口径版本可查率、第三方审计覆盖率、跨供应商同口径比价率——无一内建；`meter.*`／`receipt.*` 为**第 37 次无人提字段族**。本地 173／173-kb 连续第 35 期成组启用：刘杨 08「Token 粒度定位」「90%+ token 成本降低、粗筛 99% 流量只让 <1% 进大模型」＝全库唯一把 token 当定位单位的实践，但表仍在自家平台；配蒋烁淼 23「统一目录补上服务语义与知识」＝平台同时握有数据与表。判词：**本地把 token 做成定位单位，联网侧把 token 做成计价单位；两边都没把「谁数的、能不能复算」做成对象。**
