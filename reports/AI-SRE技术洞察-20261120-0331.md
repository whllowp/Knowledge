# AI-SRE 技术洞察（第 294 期）

**生成时间**：2026-11-20 03:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-20
**本期主题**：接管面／人机交接与中断状态——接管不是按一个按钮，是把一条正在飞的流水线交出去

## 题眼

2026-05-27，客服平台 Gorgias 的 AI Agent 把对话“过度转人工”，持续约 3.7 小时；事后归因是 OpenAI API 局部降级——Agent 无法自主处理，于是把会话推给人，而 OpenAI 状态页当时并没有相应公告。2026-07-12，Ada 的 playbook 会话在**完成自动步骤之前**就提前转给人工，持续约 32 小时，自动解决率下降；修复是“回滚到正常水平”。两次都不是“Agent 做错了事”，而是“Agent 把自己交出去了”，并且交出去的方式没有被当成故障。CVPR 2026 的 ProSoftArena 给出另一面：在 VSCode 任务上，**人主动接管（HIT）**让 GPT-5 的成功率从 55.6% 升到 100%，平均接管耗时约 16 秒；而“Agent 主动求助（AIA）”模式下成功率仍是 55.6%、接管时间为 0——求助按钮没被用起来。EMNLP 2026 Findings 进一步把“人何时会介入”做成可预测信号，介入预测准确率提升 11.6%–18.4%，接入实时 Web Agent 后用户主观有用性提升 36.8%。

接管这件事，我们一直在测“人能不能点”，没在测“点了之后发生了什么”。

## 一、发展趋势

1. **接管被写进安全状态机**。2026 年一份四态中断模型把运行时分成分级停机（HALT_NONCRITICAL）、全停（HALT_ALL）、紧急（EMERGENCY）与解除，并要求 `human_reset` 是带认证的外部权威；安全降级被定义为“关键任务继续、非关键任务不执行”的形式化性质，而不是口头约定。

2. **端点级 kill switch 成为产品**。CrowdStrike 在 Fal.Con Europe 2026（2026-11-02）发布面向 AI Agent 的 kill switch，宣称在端点实时终止未授权 Agent，并通过集中网关检查提示与响应；这类能力回答“能不能停”，不回答“停在哪一步”。

3. **转人工被当作指标，而不是事件**。客服行业把“转人工率”当效率指标优化；Gorgias 与 Ada 的两次事故说明，异常升高的转人工率本身就是故障信号，只是它没有进入 SRE 的告警面。

4. **介入时机开始可预测**。EMNLP 2026 的介入感知模型、CVPR 2026 的 HIT/AIA 对照，都在把“人什么时候该接手”从经验变成可测量量；但测量的是“该不该”，不是“接手后拿到了什么”。

## 二、技术现状

**第一层：在飞动作不可见。** 接管发生在两步之间，但 Agent 可能已经发出一个未返回的工具调用、一个异步任务、一条已提交的支付。人类看到的是对话，不是“有哪些动作在飞、哪些已不可逆”。

**第二层：权限不随接管转移。** 人接手后，往往仍以自己的账号操作；Agent 用过的委托凭据、已获得的临时权限、已写入的外部状态（工单、邮件、订单）不会自动显式化。于是“接管”只是换了个操作者，没换责任边界。

**第三层：交接状态是自然语言。** 多数系统把“上下文”做成一段摘要或聊天记录；没有结构化的“已完成/未完成/待确认/不可逆”四列表。人类要靠读对话猜进度，Agent 要靠人类复述才知道自己该继续什么。

**第四层：接管本身不演练。** kill switch 装了但没在故障中按过；转人工通道在低峰期通、高峰期排队；HIT 界面在演示里好用，在真实告警风暴里找不到入口。

**第五层：接管失败被当成“体验问题”。** 过度转人工、提前转人工、转人工后无人接，都会落到产品指标而不是事故复盘：没有 SLO、没有 error budget、没有“接管时延”的告警。

**判读**：每家都能回答“能不能停、停了没有、转了几次人工”。没有一家能回答“**接管那一刻有哪些动作在飞、哪些已经不可逆、人类拿到的是什么权限、Agent 已完成与未完成的边界在哪、接管路径上次演练是什么时候**”。而这些正是接管之后第一个小时要用的东西。

**本期反转**：我们一直把接管当“安全阀”——出问题就交给人。实际接管是**一次状态迁移**：迁移要带状态、带权限、带未完成清单，还要能被回放。没有这些，接管只是把 Agent 的混乱换成人的混乱；更糟的是，接管失败（转不出去、转了没人接、接了不知道做到哪）会伪装成“体验问题”，永远不进复盘。**接管能力不是有没有按钮，是交出去的那一刻，对方能不能接着跑。**

**判词**：「kill switch／人工坐席／工单转派／接管按钮／审批流／安全状态机」全部可采购，「接管那一刻有哪些动作在飞、哪些已不可逆、人类接手后拿到什么权限、Agent 已做与未做的边界在哪、接管路径上次演练是什么时候」不可采购。

## 四、技术挑战

1. **在飞状态**：异步工具调用、排队任务、外部副作用没有统一清单。
2. **权限转移**：委托凭据与临时权限不会随接管自动显式化。
3. **交接格式**：自然语言摘要无法表达“已完成/未完成/不可逆”。
4. **接管时延**：高峰期转人工排队，接管本身成为瓶颈。
5. **演练缺失**：kill switch 与转人工通道未经故障态验证。
6. **指标缺位**：接管时延、接管失败率、交接后返工率不进 SLO。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 在飞清单：接管时输出所有未完成动作（工具调用、异步任务、外部写入），标注可撤销性。
- D2 权限交接：把 Agent 的委托凭据与临时权限列成清单，明确哪些随接管失效、哪些转给人类。
- D3 结构化交接单：已完成／未完成／待确认／不可逆四列，附证据链接。
- D4 接管 SLO：接管时延、接管失败率、交接后返工率进 SLO，超标告警。
- D5 故障态演练：在告警风暴与高峰负载下演练 kill switch 与转人工。
- D6 接管审计：记录谁在何时接管、接管前 Agent 做了什么、接管后人类做了什么。

**用户旅程（一次“转不出去”的事故）**

① Agent 处理退款，已提交支付网关请求但未收到回执；② 上游 API 降级，Agent 连续失败后按策略转人工；③ 转人工队列在高峰排到 20 分钟，用户重复提交，产生三笔退款（D4 缺失）；④ 人工接手只看到聊天摘要，不知道有一笔支付在飞（D1 缺失）；⑤ 人类用自己的账号重做退款，与 Agent 的请求撞车（D2/D3 缺失）；⑥ 复盘时系统只记录“转人工 3 次”，没有“接管时延 20 分钟、在飞动作 1 个、重复退款 2 笔”（D6 缺失）。

**90 天实现方案**

- **第 1–30 天**：为关键 Agent 建立在飞动作清单与可撤销性标注（D1）；把委托凭据与临时权限列成交接清单（D2）。
- **第 31–60 天**：上线结构化交接单（D3）；定义接管 SLO 并接入告警（D4）。
- **第 61–90 天**：在高峰与故障态演练接管（D5）；接管审计与返工率复盘（D6）；用一次真实降级验证“转不出去时系统会怎样”。

**第 206 个市场空白（五项）**：① 接管时在飞动作清单规范；② 委托权限的显式交接模型；③ 四列式交接单标准；④ 接管 SLO 与返工率口径；⑤ 接管路径的故障态演练标准。

**`takeover.*`／`handoff_state.*` 第 173 次无人提字段族**：文档谈“如何转人工、如何配置 kill switch”，不谈“接管那一刻系统里还有什么在飞、谁拿到了什么权限”。

**本地 173／173-kb 连续第 161 期成组启用（李东东 16：接管要先给清单，再给按钮）**：本地原型在接管事件里落 `takeover{incident_id, actor, at, in_flight[], irreversible[], authority_transferred[], agent_done[], agent_pending[], time_to_takeover_s}`；接管单必须四列齐全才允许关闭；接管时延与返工率进 SLO。
