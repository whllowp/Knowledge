# AI-SRE 技术洞察（第 164 期）

**生成时间**：2026-11-13 00:15（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：恢复点面／可回滚面（Recovery Point）——备份成功不等于能恢复；Agent 能回滚到昨天，但世界已经不是昨天

---

## 题眼

09-16 Cohesity 发布 Agent Resilience，产品 CPO 的一句话点破了检测与恢复的分工：**「检测能告诉你 Agent 偏离了路径，但它不能把改动回滚。」** 这个产品做的事很具体：**备份 Agent 的记忆与配置，出问题时回到「可疑活动开始之前」的某个时间点，只恢复受影响的那部分**；同时定位并保护它用的数据库、文件系统与向量库，还给一张拓扑图（哪个 Agent 连了哪些系统、能碰哪些数据）。首个支持范围是 **AWS Bedrock 上的 Agent**。

另一份 11-07 的真实恢复演练报告，把「备份成功」与「能恢复」之间的缝撕得更开：**演练是在验证环境里把快照恢复出来、逐项核对**——1.8 秒完成 `pg_restore`、1,496,250 行；但报告专门列了「它不能证明什么」：**不是 RLS 测试、不是与生产库的比对（行数只与 dump 比、不比对内容）、不是整个项目的快照（会话、MFA、Auth 配置、Edge Function 源码都不在）**。最狠的一句是：**「通过的演练只意味着这个快照在那个验证环境、那个时间点恢复成功——是强证据，不是无条件保证。」** **回滚不是「把时间倒回去」，是「把四层状态调回同一个可信点」。**

## 一、发展趋势

**趋势一：从「备份」转向「可回滚」。** 备份是数据副本；回滚是**能把系统带回一个可信状态**——**两者之间差一次演练**。

**趋势二：Agent 的恢复对象变了。** 不只是数据库：**记忆、配置（prompt/工具/模型）、向量库、会话**都要算进 RPO。

**趋势三：恢复开始带「拓扑」。** 要知道一个 Agent 连了哪些系统，**否则恢复了它、却漏了它改过的下游**（144 期编队、146 期属主）。**拓扑是恢复范围的地图；没有地图，恢复就是盲人摸象。**

## 二、技术现状：三层状态，三套 RPO

**记忆层：事实与经验。** 回滚到旧记忆，**可能带回已经被世界否定的结论**（116 期记录-现实漂移）。

**配置层：prompt／工具／模型。** 回滚配置可能把已修复的 prompt 注入带回；**配置版本要与记忆版本配对**（127 期行为发布）。

**数据层：库、文件、向量。** 备份容易、**一致性难**；向量库与源数据不同步，恢复后就是「检索到已删除的东西」。

**会话与凭据：不在快照里。** 演练报告明说「所有人都要重新登录」——**会话不恢复、凭据要重签**（163 期）。

**四种回滚，四种难度。** 数据回滚（有工具）、记忆回滚（有产品）、配置回滚（有版本）、会话回滚（基本没有）；**只做前两种，等于只恢复了一半。**

## 四、技术挑战

**一，回滚记忆≠回滚世界。** 外部系统已经前进；**旧记忆配上新世界，就是新的错误**。

**二，配置与记忆版本错配。** 回滚了记忆、没回滚 prompt；**行为变了，原因找不到**。

**三，恢复范围说不清。** 演练报告列了「不在快照里」的清单；**多数团队没有这张清单**。

**四，清单自报会骗人。** 演练报告提到一次 manifest 估算比实际多 25 万行，**靠 count 才发现**；**备份的自报数字不可信**。

**五，会话与凭据要重来。** 所有人重登录；**业务中断时间被低估**。

**六，演练环境≠生产。** 验证环境过了，**生产依赖、RLS、外部 OAuth 都没测**（报告原文）。

**七，跨系统回滚有顺序。** 先回滚下游还是上游？**顺序错了，会触发新的不一致**（144 期编队）。

**八，回滚会删掉「证据」。** 把被篡改的记忆回滚掉，**也把攻击痕迹回滚掉了**（155 期署名、163 期清理）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `recovery.*` 字段**：`snapshot`、`scope`（memory/config/data/session）、`rpo`、`rto`、`restored_at`、`excluded`、`verified_by`。
- **R2 分层 RPO**：记忆/配置/数据分别设 RPO；**版本配对**（记忆↔配置）。
- **R3 恢复演练**：季度在隔离环境恢复；**列出「不能证明什么」**。
- **R4 一致性对账**：回滚后与外部系统对账；**旧记忆不得直接当事实**（116 期）。
- **R5 会话/凭据重签**：恢复流程包含重登录与凭据重签（163 期）。
- **R6 指标**：RTO/RPO 达成率、演练通过率、回滚后不一致数、排除项覆盖率。

### 5.2 用户旅程

- **SRE**：Agent 行为异常 → 选「可疑活动前」的快照 → 只回滚记忆与配置 → 对账外部数据 → 保留攻击痕迹副本。
- **平台工程师**：季度演练 → 恢复快照 → 逐项核对 → 记录「未覆盖：RLS/外部 OAuth」。
- **安全**：回滚后重签凭据 → 确认旧 token 失效 → 记录排除项。
- **审计**：抽查一次回滚 → 核对快照范围与排除项 → 确认没有「恢复了一半」。

### 5.3 实现方案（90 天）

- **0–30 天：盘范围。** 列记忆/配置/数据/会话四层；标出不在快照里的项。
- **30–60 天：分层 RPO。** 记忆与配置版本配对；季度演练。
- **60–90 天：对账与重签。** 回滚后对账；会话/凭据重签流程；指标上线；季度复盘回滚顺序。

**第 112 个市场空白（五项）**：分层 RPO 可报率、回滚范围可声明率、排除项覆盖率、演练通过率、回滚后一致性可测率——无一内建；`recovery.*`／`rollback.*` 为**第 81 次无人提字段族**。本地 173／173-kb 连续第 72 期成组启用：朱革 15「统一权限、审批、回滚」＝全库唯一把「回滚」写进治理闭环的实践，本期首次当主线；配 52 期恢复、116 期记录。判词：**本地把回滚写进治理，联网侧 2026 年才把「记忆与配置的时间点恢复」做成产品；两边都没把「回滚后四层是否一致」做成验收项。**
