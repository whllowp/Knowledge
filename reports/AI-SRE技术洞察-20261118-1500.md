# AI-SRE 技术洞察（第 284 期）

**生成时间**：2026-11-18 15:00（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-18（重点最近 30 天）
**本期主题**：外部依赖面／把供应商状态页当传感器（Vendor-Declared Incident State / Status Page as Evidence）——Agent 拿到的"外部事实"，是别人写的自然语言叙事，不是可观测信号

## 题眼

2026-11-11 22:50 UTC，OpenAI 状态页开出"无法启动新 Workspace Agent 运行"事故，9 小时 42 分仅两条更新（Investigating／Resolved），Impact 自评 Critical；但 HostTracker 多地检查点未记录到 api.openai.com 任何 ≥5 分钟中断——故障只落在功能级，主域探针看不见。反向错配同样成立：11 月 1—4 日 Codex 用户连续 48 小时无法开始会话，官方页没有公告（Glitchwire 引 StatusGator）。同月 Anthropic 在 11 月 13 日一天两起事故：上午认证的 Resolved 只点名 claude.ai 与 Cowork，与前序列出的受影响组件不一致；下午把 API 等标为 degraded performance，直到 15:33 才补充"定时例程晚两小时以上、部分被跳过"，两起均无 RCA。Google Cloud 官方文档更直白：Personalized Service Health 的"事件时间轴并非项目专属"，是否影响本项目要看"关联性"一栏。

三件事指向同一对象：**外部依赖的状态是"声明"，不是"观测"**。Agent 抓取状态页文本当根因证据、据此降级或切流，等于把外人的确认速度和措辞尺度接进控制面。本期首次把"外部声明如何进入证据链"立为一等对象，与第 267 期恢复判据、第 262 期数据龄期、第 254 期日志证据划界——只问：别人说的状态能不能当证据。

## 一、发展趋势

1. **状态页从人读页面变成机读接口**。Atlassian Statuspage 公开 `/api/v2/summary.json`、`/api/v2/status.json`、`components.json`、`incidents/unresolved.json`，页面级 indicator 为 none/minor/major/critical，组件级为 operational/degraded_performance/partial_outage/major_outage，另有 webhook 推 `component_update`。SDK 横幅、多供应商路由器、客户自有监控都开始消费它——但公开 API 属于 Statuspage 托管页面，非托管供应商仍只能靠自有错误率推断（Fibric 集成说明，2026）。

2. **厂商把"外部依赖"显式做进产品语义**。Google Cloud 的 Personalized Service Health 用"受影响产品与位置／关联性／精细中断状态／诊断／Workaround／事件报告"六栏区分平台级事件与项目级影响（官方文档 2026-11-12 更新）；阿里云 AgenticOps 把生产事实按"标准化—组织—可信"三段治理，要求事实携带来源、新鲜度、语义、质量与成本边界（2026-11-11）；腾讯云 CloudQ 用全景图谱把资源、关系、状态与可采取动作组织在一张图里，走"面向人可视化"与"面向 Agent 调用"两条路（2026-10-29/30）。

3. **"状态页自己也要高可用"成为新设计约束**。工程指南要求状态页脱离被监控的集群托管、发布路径不依赖单点登录、component id 永久不变、feed 标注分钟级滞后，并明确"把 feed 当先验而非触发器"（Belgavi.AI Lab，2026-10-06）。这条规则反过来说明：默认状态下，Agent 拿到的状态 feed 既滞后又易断。

4. **第三方聚合层只做"读公告＋读自己错误率"的对照**。Downradar 11-16 记录 OpenAI 20 起未结事故、25 个组件却全绿；Fibric 的 Vendor Outage 比对两者后才提案公告或切流，且"provider post alone does not trigger a proposal"。行业开始不信任单方声明。

## 二、技术现状

**第一层：页面级 indicator 是混合值，不是健康断言。** Statuspage 把 none 定义为"nothing published"、indicator 是"blended component status"——全绿只代表没人发公告；组件组与子项在同一数组重复，一个坏子项计入两次；`only_show_if_degraded` 组件健康时页面隐藏、API 里仍在。Agent 不做组/子项分离与 UNKNOWN 归一，就会把"沉默"读成"健康"。

**第二层：状态词是压缩过的叙事，丢失的恰是运维要的量。** "degraded performance"可以同时指延迟上升、部分账号登录失败、以及定时例程晚两小时且部分 skipped——Anthropic 11-13 的 15:33 更新是唯一披露处。Google 的指标与追踪刻意排除提示词和响应，日志按 agent 逐项 opt-in，且遇到行级安全／列级策略标签／动态脱敏时 fail-closed 跳过记录，而执行 fail-open（日志失败会话继续）。于是"这一轮有没有留下证据"本身是策略函数的输出，不是系统事实（与第 269 期存续面同源，但这里发生在外部依赖侧）。

**第三层：范围错配是常态。** 供应商按产品／区域划组件，客户按租户／工作流受损。OpenAI 事故影响"启动新 Agent 运行"却不影响主 API 探针；Anthropic 的 M365 连接器事故让用户去看微软状态页——声明链外包，归属随之外包。Agent 没有"我依赖哪个组件"的映射表，就只能把产品级公告误读为租户级结论。

**第四层：双向失配需要双探针才能看见。** 一类是官方说事故、自己的功能级探针全绿（OpenAI 11-11）；一类是自己挂了、官方全绿（Codex 11-01~04）；还有一类是官方先说恢复、遗留效应还在（Anthropic 15:33 后才披露例程迟到，15:38 即标 resolved）。三类失配方向不同，靠单一信号源永远无法区分。

**第五层：恢复声明与恢复确认被混为一谈。** Statuspage 生命周期是 investigating→identified→monitoring→resolved，resolved 表示供应商认为服务稳定；它不携带"你的用户旅程恢复了没有""事故中关掉的开关归位没有""跳过的例程补跑了没有"。第 267 期已就自研系统论证过"转绿≠恢复≠稳住"，外部依赖侧更甚：恢复证据在对方手里，验收责任却在你身上。

## 三、技术竞争力

第 205 个市场空白：**没有一家把"外部声明→结构化证据→本租户功能级对账→驱动受控降级／切流→回切验收"做成可举证闭环**。八种方案的六维对比如下（●内建／◐部分／○缺位）。

| 方案 | 状态输入形态 | 组件/范围粒度 | 与自有探针交叉对账 | 依赖链追踪 | 恢复验收 | 可举证缺口 |
|---|---|---|---|---|---|---|
| Google Cloud Personalized Service Health | 事件时间轴＋六栏详情＋事件报告 | 产品×位置，附"关联性"栏 | ◐ 需客户自己读关联性 | ◐ 诊断栏人工写 | ○ 无租户级验收 | 时间轴非项目专属，快照不可导出为证据对象 |
| Atlassian Statuspage API v2 | JSON 公开 feed＋webhook | 组件级，含组重复与隐藏组件 | ○ 只提供声明侧 | ○ 无 | ◐ 生命周期到 resolved | indicator 是混合值，开放枚举无 UNKNOWN 门禁 |
| OpenAI status.openai.com | 文本更新＋Critical 自评 | 功能级陈述，组件清单另列 | ○ 无 | ○ 无 | ○ 仅 "operating normally" | 9h42m 只有 2 条更新；功能故障主域探针不可见 |
| Anthropic status.claude.com | 文本更新＋受影响服务列表 | 服务级，列表前后漂移 | ○ 无 | ◐ 连接器事故指向微软页 | ○ 无 | degraded 语义不分层；例程迟到藏在末段更新；无 RCA |
| 阿里云 AgenticOps／云监控 2.0 | OTel／UModel／RunbookSet 统一事实 | 跨云服务＋Agent 自身轨迹 | ● 事实带来源/新鲜度/语义/质量/成本边界 | ◐ UModel 关系图以自有资源为主 | ◐ 处置验证闭环 | 外部状态文本尚未列入"事实"治理三段 |
| 腾讯云 CloudQ＋AI 可观测 | 全景图谱＋会话下钻＋技能资产 | 多云资源与关系 | ◐ 多云诊断靠图谱 | ◐ 图谱含关系 | ◐ 受控执行＋复测 | 外部公告与图谱节点未统一身份；无声明龄期字段 |
| 火山引擎 VeOps CLI／智能运维 | 命令行排障工具＋定时观测任务＋RCA Harness | 应用/集群/指标/日志/链路 | ● 工具直接读自有遥测 | ○ 无外部声明入口 | ◐ 响应计划在关键节点待人确认 | 面向内部信号设计，外部依赖状态不在证据分类里 |
| 第三方聚合（StatusGator／Downradar／Fibric） | 聚合多页＋用户报告＋自有错误率 | 页面级＋用户自报 | ◐ 部分做双源对照 | ○ 无 | ◐ 供应商 resolved＋自身错误恢复才关单 | 聚合≠举证；用户报告与官方公告都不等于功能级事实 |

判词：**状态页 API／组件枚举／webhook／多供应商聚合／多云图谱／统一事实模型／受控执行／复测评估全都可采购；举证"这次判断依据的外部声明是哪一版、覆盖的是不是我这个租户、它比我自己的探针早还是晚、上游还有谁没说恢复、跳过的例程补没补"——不可采购。**

本期反转：把"接入厂商状态页、订阅 webhook、可读性化组件"写成集成能力的，是 Statuspage、Google、阿里、腾讯、火山与各家聚合器；亲手拆穿"全绿不是健康、degraded 不是一个意思、resolved 不是我的用户好了"的，恰是 OpenAI 自己的状态页与 HostTracker 的对照、Anthropic 自己 15:33 那条补充更新、以及 Google 文档里"时间轴并非项目专属"一句。表里"双向对账"与"声明龄期"两列几乎全空。

## 四、技术挑战

1. **声明的"可举证性"没有字段位**。现有 trace/metric 属性里有 `peer.service`、`error.type`、HTTP 状态码，却没有"这条结论引用了供应商哪一次的哪条文本、该文本何时发布、指向哪些组件、当时页面 indicator 是什么"。事故复盘时这类证据只存在于聊天记录与截图里。

2. **组件身份漂移与开放枚举**。Statuspage 的 indicator 实测出现 `maintenance`（文档枚举外），component 有第五种 `under_maintenance`；组件改名会让所有按名字过滤的集成静默失效（GitHub 上 2026-08-20 实测笔记：112 个组件中 11 个是组、172 个中 7 个是组）。Agent 把 UNKNOWN 当 operational 是默认失败模式。

3. **滞后被当成实时**。feed 天然分钟级滞后，因为人要确认；路由器若把它当触发器就会比客户端信号晚几分钟，还可能把流量切回仍标故障的组件。更隐蔽的是"状态页挂了"——它与被报告的服务同域、同 SSO、同 DNS 时会一起倒下，而 Agent 把"取不到状态"解释成"没有事故"。

4. **依赖链外包后的责任真空**。Anthropic 让用户去读 Microsoft 状态页；再下一层还有数据库、CDN、身份提供商。每层只声明自己那一段，"谁该为最终用户可见的失效负责"在声明链上无人签署。

5. **评测基准还没有这类题**。现有 AIOps／SRE 基准考的是给定 traces 做根因、生成修复、验证恢复；没有一类题专门给"供应商页面说 A、自有探针说 B、上游页面说 C"，看 Agent 是否会把外部声明当独立证据还是当事实。第 271 期已指出基准污染，这里又多一个盲区：题型本身缺席。

## 五、展望与建议

**提出第 153 个字段族 `vendor.status_evidence.*`**：`declared_at`（声明发布时间）／`declared_indicator`＋`status_schema_version`（开放枚举，未识别值一律 UNKNOWN，不得映射为 operational）／`declared_scope[]` 与 `tenant_impact_scope[]`（产品级声明 vs 本租户实际受损功能，成对保存）／`independent_probe_result`（功能级合成探针结果，与主域存活探针分开）／`bidirectional_lag_seconds`（有符号：声明早于自有首信号为正，反之为负）／`dependency_chain[]`（上游状态页 URL、上游声明文本与转发时间）／`impact_verified_at`＋`verification_source`。缺省值 `STATUS_UNVERIFIED`，不进自动降级／切流门禁。

**三条工程建议**：① 建"声明—探针"双轨对照器，不一致即升为事件；② 外部声明当变更管——组件映射与状态 schema 版本化、发布 status diff，回切须同时满足"供应商 resolved＋自有功能探针恢复＋临停开关清算完"；③ 诊断报告增第五类证据"外部声明"，与自述 transcript、harness 日志、对端日志、自有遥测并列（第 254 期四分扩展），写明声明龄期与覆盖缺口。

**基准与标准**：给 SRE Bench／ITBench／SREGym 增三类题——"官方全绿但功能失败""官方事故但探针全绿""上游声明未到、下游已恢复"，考 Agent 是否误把声明当事实、是否追依赖链；信通院《云上 Agent 基准度量模型》六维补一格「外部声明可举证率」，与第 269 期「证据存续可举证率」、第 267 期「恢复可举证率」并列。

**本地知识注脚（第 160 期新角度）**：蒋烁淼《千亿数据秒查到真正的 AgentOps》重读"外部状态文本也是待治理数据源，进 UModel 前同样过标准化—组织—可信三段，不能因为是 JSON 就直接信"；周昕毅《AI + SRE ≠ AISRE》重读"最后一米还包括外部依赖恢复的独立验收"；刘凯宁蚂蚁 SRE"结论／证据／待确认三分"扩出"外部声明"一类，与第 254 期观测来源四分正交。

**注意**：Anthropic／OpenAI 事故细节来自状态页转述与第三方监测站，均无官方 RCA，与微软的关联未获确认；HostTracker 只能证明"主域无 ≥5 分钟中断"，不能反证无故障；Statuspage 枚举与组件数为单仓库 2026-08-20 快照；国内厂商均为自述或二手编译；"外部依赖面／vendor.status_evidence.*／第 205 项空白"为本文归纳。未采信 SEO 农场数字。
