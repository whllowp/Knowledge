## 题眼

Google 在 Next '26 把 Gemini Enterprise Agent Platform 推成"智能体企业"底座，并首次把 **Agent Topology（智能体交互拓扑可视化，一张实时地图展示 agent 之间、agent 与工具之间如何互相调用）** 列为 SRE 工具一等对象；PayPal 同场展示的 "Agentic SRE" 平台由架构评审、发布、实验、可观测、健康、资源、故障排查等**一整支 agent 队伍**组成，每个 agent 下挂子 agent。同一窗口，阿里 AgentCore 把"运维 Team"做成多智能体协作、腾讯 CloudQ 用 CloudQ+AndonQ+MigraQ 三位专家协同、火山 AgentKit 支持中间层 Agent 串联。

一句话：**运维正在从"一个 Agent 做事"变成"一群 Agent 互相叫对方干活"，但没有任何一层在实时记录"这条指令到底流经了几层、谁在和谁说话、上下文落在哪张图上"——编排拓扑成了新的不可观测盲区。**

## 一、发展趋势

1. **编排从"链式串联"升级为"队伍化协作"。** Next '26 后，头部厂商不再把 Agent 当单兵：Google 的 Agent Gateway 是懂 MCP/A2A 语义的控制面，PayPal 的 SRE agent 生态含 7+ 专门 agent 各自带子 agent，阿里 AgentCore 直接叫"运维 Team"，腾讯数字免疫系统把日志聚类、关联推理、处置调度、复盘进化多个专业 agent 拼进工作流。多智能体已成默认形态。
2. **拓扑可视化被首次点名为 SRE 刚需。** Google 的 Agent Topology 把"agent 如何互调"做成 live map；这与此前 OTel 只追踪单条 span 的范式不同——它要回答的是"谁调用了谁、在哪一层做了决定"。
3. **共享上下文成为协作底座，也是污染面。** Google IAN 用 Hermes 让五个 agent 读同一份上下文（成本 agent 的缩容史、安全 agent 的发现流、发布 agent 的发布日志都进同一个调查上下文）；这把"上下文共享"从特性变成协作前提，也把"一个 agent 的脏上下文污染全体"变成新风险。
4. **本地知识主线呼应**：173-kb 中 朱革（百度 AgentOps）直指多智能体缺"统一版本边界、统一权限/审批/限流/审计/回滚"，肖汉松（从 Harness 到 Loop）把跨 Agent 的"携带证据改派"写成铁律——两者共同预言了"编排需要一张可治理的拓扑"。

- **厂商编排形态各异，拓扑记录缺位**：
  - *Google*：Agent Gateway（MCP+A2A 控制面）+ Agent Topology 可视化 + Hermes 共享上下文；强在"看得见的地图"。
  - *OpenAI*：Govindarajan 在 QCon AI Boston（2026-09）提出 harness 五模式（状态归属、变更串行化、执行定界、工作边界、边缘校验），"模型提议、harness 提交、回执证明"；偏"有序提交"而非"拓扑图"。
  - *Anthropic*：Claude Code / Agent SDK 用 W3C traceparent 把子 agent 的 span 嵌套进父 span，OTel 已能画单链 delegation chain；但"跨 agent 的共享上下文竞争、环形调用"无原生对象。
  - *字节/火山*：AgentKit 支持中间层 Agent 串联、超时自动终止、全局冲突检测；偏"串联 + 护栏"，无拓扑图。
  - *阿里*：AgentCore"运维 Team" + UModel 运行模型把 Workspace/Agent/Session/资源池/Sandbox 关联；偏"实体关联"而非"实时调用图"。
  - *腾讯*：CloudQ+AndonQ+MigraQ 三位专家 + 数字免疫系统多 agent 协同；偏"角色分工"，拓扑隐在编排里。
- **标准层滞后**：OTel GenAI semconv 至 v1.42 有 `invoke_agent`/`execute_tool`，但无"编排拓扑/血缘（lineage）"对象；一张跨 agent 的调用图无法被标准遥测表达。
- **本地原型当主线**：朱革 15「Agent、Skill、Prompt、工具、知识缺统一版本边界、生产写缺统一权限/审批/限流/审计/回滚」+ 肖汉松 22「携带证据改派、单次迭代不可信须持续流转」+ 马云雷 31「轨迹即数字资产」——把"拓扑边须带证据、治理须有统一边界"写成可落地的中国实践雏形。

## 四、技术挑战

1. **编排拓扑不可观测。** 没有一等对象记录"指令流经几层、谁调谁"，故障定位退回到单 span；环形/扇入扇出调用无法被标准遥测表达。
2. **共享上下文污染。** Hermes 式共享上下文让一个 agent 的脏状态进全体调查上下文（呼应 121 隔离面），且比租户隔离更隐蔽——是同一队伍内部的"内源污染"。
3. **版本边界缺失。** 朱革指出 Agent/Skill/Prompt/工具/知识无统一版本边界，调试易污染线上；多 agent 下"哪个版本参与了这次决策"无从追溯。
4. **权限/限流/审计/回滚未统一。** 生产写操作缺统一治理 spine，跨 agent 的熔断、限流、审计、回滚散落各地（呼应 91 不可逆面、136 监控隔离）。
5. **标准语义断层。** OTel GenAI 有 `invoke_agent`/`execute_tool` 但无拓扑/血缘对象，跨厂商拓扑不可组合、不可回放。

## 五、展望与建议

- **把"编排拓扑"立为一等可观测对象**：在 OTel GenAI 提 `orchestration.*`/`topology.*` 字段族（edge_id、caller_agent、callee_agent、shared_context_ref、decision_layer、loop_guard），让一次跨 agent 协作可被画成图、被回放。
- **共享上下文做强隔离 + 版本戳**：上下文按 agent/版本打戳，污染可溯源；借鉴 121 隔离面的租户边界，向内延伸到队伍内上下文。
- **统一治理 spine**：把朱革的"版本边界 + 权限/审批/限流/审计/回滚"做成编排控制面，跨 agent 动作强制走 policy service（OpenAI 式）+ 有序提交（harness 式）。
- **环形/扇出护栏**：在拓扑层加 loop guard 与扇出上限，超时自动终止（火山式）前置到编排层。
- **本地"携带证据改派"上升为拓扑边契约**：每条跨 agent 边须附 `propagation_ref` 与证据（肖汉松 22），把马云雷 31 的轨迹数字资产拼成拓扑血缘。
- **新增市场空白五项（第 91 个，`orchestration.*`/`topology.*`，OTel 第 60 次无人提字段族）**：拓扑可观测率、跨 agent 上下文污染检出率、编排版本可追溯率、统一治理 spine 覆盖率、环形调用拦截率。
