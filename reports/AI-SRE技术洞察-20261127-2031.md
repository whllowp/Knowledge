# AI-SRE 技术洞察（第 380 期）

**生成时间**：2026-11-27 20:31（Asia/Shanghai）
**本期主题**：重放面／解冻日的排序与合并

## 题眼

冻结结束时，几十个变更排在门口。最直觉的做法是"按提交时间逐个合入"；但**合入顺序会改变结果**——A 先在旧 schema 上合并，B 再改 schema，A 的行为就与单独测试时不同。这是 merge skew：每个 PR 都测过，组合起来没测过。

## 一、发展趋势

第一，合并队列（merge queue）从"可选"变成"默认"。GitHub merge queue、GitLab merge trains 在合并前用目标分支的最新状态重跑检查，避免"各自绿、合起来红"。

第二，解冻从"日历事件"变成"调度问题"。不再问"哪天解冻"，而问"按什么顺序、分几批、每批观察多久"。

第三，依赖感知的合并。按服务依赖拓扑排序，先合底层库、再合上层服务。

第四，可逆性分级。可一键回滚的变更先走，不可逆的（数据迁移、外部契约）单独批次、单独窗口。

第五，AI 参与排序。用历史故障与依赖图推荐批次，但推荐需要人工确认。

第六，解冻演练。把"解冻日"当作一次发布演练，提前排练顺序与回滚。

## 二、技术现状

**"同时"是风险来源。** 解冻日的故障率高于平常，不是因为变更更多，而是因为变更同时到达：共享资源争用、依赖同时升级、观察窗口重叠。

**提交顺序不等于依赖顺序。** 按时间合入会把上层服务排在下层库之前；上层在旧库上通过测试，合入后下层才改，行为漂移。

**Merge skew 的两种形态。** 语义冲突（两个 PR 各自正确、组合错误）与时序冲突（新代码先上线、旧数据未迁移）。

**观察窗口被压缩。** 为了"清空积压"，批次间隔从小时降到分钟；指标延迟还没到，下一批已经合入。

**回滚点被覆盖。** 连续合入多个变更后，回滚到"上一个稳定版本"意味着回滚一批，而不是一个。

**审批过期。** 冻结期前的审批在解冻时可能已失效（第 310 期）。

**Agent 放大合并。** 自动合并 Agent 会按"检查全绿"推进，而检查不知道依赖顺序。

**解冻日的"清空积压"是错误目标。** 积压不是债务，是待排序的工作；目标是"按可承受的速率消化"，不是"当天清空"。以清空为目标，就会压缩观察窗口、跳过批次、放宽审批——三个动作都在制造下一次事故。

**合并队列的盲区。** 合并队列保证"每个 PR 在目标分支最新状态上通过"，但不保证"这一批 PR 之间的语义兼容"；它降低 merge skew，不消除依赖顺序问题。

## 三、技术竞争力

| 方案 | 排序依据 | 防 merge skew | 观察窗口 | 回滚粒度 | 适用 |
|---|---|---|---|---|---|
| 按提交时间 | 时间 | 弱 | 易压缩 | 单变更 | 小规模 |
| 按服务分批 | 服务边界 | 中 | 按批 | 按批 | 中等规模 |
| 按依赖拓扑 | 依赖图 | 强 | 按层 | 按层 | 平台化 |
| 按风险分级 | 风险标签 | 中 | 按级 | 按级 | 关键系统 |
| 合并队列 | 目标分支最新状态 | 强 | 逐 PR | 单 PR | 高频合并 |
| 混合（依赖+风险） | 两者 | 最强 | 分层 | 分层 | 大规模 |

**判读**：合并队列解决"组合未测"，依赖排序解决"顺序错误"，风险分级解决"不可逆变更混入"；三者互补，选一个都不够。

**本期反转**：我们一直把解冻当"放行"，所以关注"批不批"；更该把它当"排程"，关注"先谁后谁、隔多久、回滚到哪"。**解冻日的质量，取决于排序，不取决于审批。**

## 四、技术挑战

**挑战一：依赖图不全。** 拓扑排序依赖准确的依赖图；图错了，排序也错（第 173 期）。

**挑战二：观察窗口与指标延迟。** 指标聚合有延迟，窗口太短等于没观察。

**挑战三：回滚点管理。** 连续合并让回滚粒度变粗；需要显式的稳定点标记。

**挑战四：审批时效。** 冻结期前的审批需要重新确认。

**挑战五：共享资源争用。** 多批同时扩容、同时回填，会互相挤压。

**挑战六：Agent 的合并权限。** 自动合并需要知道"这一批是否已观察"。

**挑战七：跨仓库依赖。** 多仓库的合入顺序更难协调。

**挑战八：演练成本。** 解冻演练需要真实积压，平时难以构造。

**挑战九：排序的可解释性。** 按依赖与风险排出的顺序，需要向业务解释"为什么这个变更排后面"；没有解释，排序会被"着急"推翻。

**挑战十：跨团队协调。** 解冻日多个团队同时放行，批次之间互相等待；需要统一的调度者，而不是各自为政。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①依赖图与拓扑排序；②合并队列；③风险与可逆性分级；④批次观察窗口；⑤稳定点标记；⑥审批时效检查；⑦共享资源配额；⑧解冻演练。

**用户旅程**：冻结前登记积压 → 解冻前重算依赖 → 按层/风险排批 → 逐批合入并观察 → 标记稳定点 → 异常时按批回滚。

**实现方案（90 天）**：0–30 天引入合并队列，给积压变更打依赖与风险标签；31–60 天做拓扑排序与批次窗口，标记稳定点；61–90 天做解冻演练与 Agent 合并权限约束。

**验收标准**：任取解冻日的一批变更，能回答"为什么这个顺序、这批观察了多久、回滚会回到哪个点、依赖图哪来的"；答不出就是"按时间排的"。
