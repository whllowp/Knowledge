# AI-SRE 技术洞察（第 146 期）

**生成时间**：2026-11-12 09:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：属主面／责任田面（Ownership）——Agent 没有主人，就没有人给它养老送终；68% 说看得见，82% 发现过没见过的

---

## 题眼

05-08 云安全联盟（CSA）的一份报告把「影子 AI」重新定义了：**它不是「未经批准的软件」，是「未经批准的意识」**——由最懂技术的员工嵌进工作流，用合法企业凭据的 API key，连到没有政策保护的数据源。它给的数字很硬：**影子 AI 使用程度高的组织，泄露成本平均高 67 万美元**（IBM 2025）；**五分之一**的组织经历过与影子 AI 相关的泄露；**2026 年 65% 的组织在过去一年经历过 AI Agent 安全事件，且每一个报告事件的组织都报告了真实业务影响**。报告的归因不是培训、不是政策、不是技术，而是**问责**：**没有任何一个职能拥有 AI 部署的完整生命周期**——从开通、监控到退役；于是每个阶段都成了攻击面。最能说明问题的一组对照：**68% 的组织声称对已部署 Agent 高度可见；同一份调查里 82% 承认过去一年发现过至少一个安全/IT 此前不知道的 Agent 或工作流**。**这不是工具不够，是问责架构没建：没人拥有「从开通到退役」的整条线，于是每一段都漏。**

## 一、发展趋势

**趋势一：属主从「团队名」变成「生命周期责任」。** 写个 owner 字段不难；难的是**开通、监控、轮换凭据、退役**四段都有人认。**没有全生命周期属主，就没有人做这四件事。**

**趋势二：注册表成为治理入口。** AWS 在 4 月推出 Agent Registry，把 Agent 集中登记与治理；微软 Power Platform 支持**转移 Agent 属主**。**登记只是第一步，属主转移与退役才是难点**——**注册表能回答「有哪些」，回答不了「谁负责它活着、谁负责它死掉」。**

**趋势三：影子 Agent 的发现先于治理。** Nudge Security 这类工具把「发现影子 Agent」做成产品；**先看见，才谈得上归属**。而 CSA 的对照说明：**你看见的是「正式部署的」，不是「实际存在的」。**

## 二、技术现状：四类属主，通常一个都没有

**产品属主：它该做什么、不该做什么。** 需求方；**Agent 的行为边界由他定义**，但常常交付后就不管了。

**平台属主：它跑在哪、用什么凭据。** 平台团队；**负责运行时，不负责它做得对不对**。

**值班属主：它坏了谁被叫醒。** 常在交接时丢失；**87% 的告警无人认领，就是因为没有这一栏**（139 期）。

**预算属主：它烧钱谁签字。** 财务/团队；**成本失控时找不到人**（143 期）。

**孤儿 Agent：创建者离职，Agent 还在跑。** 用着离职者的 API key、连着没人维护的数据源；**没有 provenance 与退役机制，孤儿就是默认结局**（136 期孤儿 VM 同构）。

**碎片化不止「没人管」，还有「五个维度各管一段」。** 数据、身份、工具、属主、监督各归不同团队；**单看每段都有主，合起来没人对结果负责**——CSA 把它叫「系统性风险」，而不是「管理疏忽」。

## 四、技术挑战

**一，可见性悖论。** 68% 说高度可见、82% 发现过未知 Agent；**工具只覆盖「走流程的」，覆盖不了「绕流程的」**。

**二，属主是兼职。** 产品、平台、值班、预算四个角色常由同一人兼；**他一走，四个角色同时空**。

**三，孤儿没有触发器。** 离职流程关账号，**不关 Agent**；Agent 用服务账号继续跑。

**四，转移没有仪式。** 属主变更没有交接清单（132 期），**新属主不知道旧属主承诺过什么**。

**五，影子 Agent 的合法性两难。** 一刀切封禁会逼出更隐蔽的部署；**只登记不治理，等于给影子发身份证**。

**六，度量缺基线。** 没有「属主覆盖率」与「孤儿率」的历史数据；**说不清治理有没有变好**。

**七，属主与 IAM 脱节。** Agent 用服务账号跑，**账号属主与 Agent 属主是两套记录**；人走了账号还在，Agent 就还在。

**八，外包与跨租户属主。** 供应商代建的 Agent，属主写谁？**出事时双方都指向合同**（125 期赔付在属主层的复现）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `owner.*` 字段**：`agent_id`、`product_owner`、`platform_owner`、`oncall_owner`、`budget_owner`、`created_by`、`retire_by`。
- **R2 注册表＋发现**：正式注册与网络/身份侧发现并行；**发现结果进同一张表**。
- **R3 四类属主显式化**：每类至少一人，缺项标 `UNOWNED` 并阻断上线。
- **R4 离职转移**：离职流程触发 Agent 属主转移；未转移的进冻结队列。
- **R5 周期证明**：季度属主确认（本人签字），连续两次未确认自动降级。
- **R6 度量**：属主覆盖率、孤儿率、未知 Agent 发现率、凭据轮换率。

### 5.2 用户旅程

- **平台工程师**：新 Agent 上线 → 注册表要求四类属主 → 缺 budget owner 被阻断 → 补齐后开通。
- **安全**：季度发现 3 个未知 Agent → 登记 → 找创建者 → 找不到则冻结并回收凭据 → 记入孤儿清单。
- **HR/IT**：员工离职 → 触发属主转移 → 未转移的 Agent 进入 30 天冻结期。
- **审计**：抽查 20 个 Agent → 核对四类属主与最近确认 → 确认没有孤儿。

### 5.3 实现方案（90 天）

- **0–30 天：盘点。** 注册表＋发现；给存量 Agent 补四类属主，标出 `UNOWNED`。
- **30–60 天：卡口。** 新 Agent 无属主不上线；离职流程接转移；季度确认上线。
- **60–90 天：清孤儿。** 冻结无主 Agent、回收凭据；发布属主覆盖率与孤儿率；季度通报未确认属主。

**第 98 个市场空白（五项）**：四类属主覆盖率、孤儿率、未知 Agent 发现率、属主转移完成率、凭据轮换率——无一内建；`owner.*`／`steward.*` 为**第 65 次无人提字段族**。本地 173／173-kb 连续第 58 期成组启用：周昕毅 10「L3 数字分身：长期身份、持续闭环、责任边界明确」＝全库唯一把「责任边界」写进数字分身的实践，本期首次当主线；配朱革 15「统一权限、审批、审计」、79 期「在编」。判词：**本地把责任边界写进 L3 定义，联网侧 2026 年才量出「68% 可见 vs 82% 未知」；两边都没把「这个 Agent 的四类属主是谁」做成上线必填。**
