# AI-SRE 技术洞察（第 183 期）

**生成时间**：2026-11-13 15:00（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：时序保真面／事故时间线重建（Temporal Fidelity: Incident Timeline Reconstructability）——多自治体共处置一场事故时，「到底按什么顺序发生了什么、谁导致谁」退化为不可证伪的重建问题

---

## 题眼

Google Cloud Next '26 把「跨 agent、工具、上下文的可追溯性」当成卖点（Virtana／theCUBE 同声：「调试需要跨 agent、工具与上下文的可追溯」），OpenAI 的对齐检测却把「重放整个上下文窗口以还原事件」做成**人工 L2 流程**——恰恰说明自动重建时间线根本不存在。PayPal「Agentic SRE」7+ agent 各带子 agent，让**并发失序成为默认**。本文首次把「这场事故的时间线能否被单调重建」立为一等运维对象：**我们能观测每个参与者，却无法把它们重组成一条可信时间线；没有时间线，根因（160）、责任（166）、审计（162）都立在不牢的地上。**

## 一、发展趋势

**趋势一：可观测的重心从「单点信号」转向「跨实体时序」。** 当运维主体从「人＋脚本」变成「一群自治体＋人＋基础设施自动化」，孤立的指标、日志、追踪都看得见，但谁先谁后、因果方向看不见（135／138 期）。

**趋势二：长程自治把「时间线失真」从边缘推到中心。** Google Next '26 明列长程 agent 五大失效（context rot、premature completion、lossy compaction、shallow plans、lossy self-evaluation）；theCUBE 据此断言「token 管理已是头等可靠性议题」。**压缩与摘要会直接删掉事件本身，时间线随之断裂。**

**趋势三：重建开始被当作工程问题而非复盘附录。** OpenAI 对齐检测让调查 agent 回看「整个上下文窗口」来还原事件——这是时间线重建的人工雏形；但它停留在 L2，没有变成可导出字段（162 期）。

## 二、技术现状：时间线为何不可重建

**失序一：异步到达。** 多 agent 并发，告警、动作、恢复以 event-time 与 processing-time 错位到达；同一次故障里「谁先动、谁后动」在日志里是乱的。

**失序二：重试与重放制造幽灵事件。** 一次动作被重试、被 replay，日志里出现多个「相同」事件；因果链被幽灵副本污染，误把重试当独立根因。

**失序三：Agent 改写共享状态，前态消失。** 它把配置、记忆、工单改掉之后，故障前的状态被覆盖；时间线只记录「之后」，没有「之前」（与 168 可逆性呼应：168 管撤不撤得回，本期管撤之前前态有没有被记下来）。

**失序四：压缩丢弃事件。** 长程 agent 为腾上下文而摘要，细节被丢；下一轮需要「当时发生了什么」时，记录里已经没有那件事（呼应 Google context rot，但角度是时间线而非内存）。

**失序五：时间线非单调。** 没有 versioned、monotonic 的时间线对象；同一场事故每次查询都得到不同「真相」，**重建结果本身不可重复、不可复核**。

**失序六：评测不量重建。** SRE-Bench v2／ORCA-bench／Incident-Arena 都以 OTel 插桩为底座，却无一评测「能否重建时间线、重建出的顺序对不对」（接 137／167 期）。

## 四、技术挑战

**一，可观测被误当可重组。** 「每个 actor 都打了点」不等于「它们能拼成一条线」——这是本期最核心的认知错位。

**二，幽灵事件无法剔除。** 重试／重放副本混入因果链，自动归因（160）会把噪声当根因。

**三，前态无留存。** Agent 改完即覆盖，事后复盘找不到「改之前什么样」，根因与责任都悬空。

**四，压缩即删事件。** 长程 agent 摘要上下文，事件从记录里消失，时间线出现空洞。

**五，重建结果非单调。** 没有 versioned 时间线对象，重建不可重复、不可复核，审计（162）失去锚点。

**六，评测盲区。** 基准有 OTel 不评重建，生产侧无重建率指标，时间线失真无人发现。

**七，跨实体时钟不齐。** agent、人、基础设施自动化各用各的时钟与重试语义，「同一时刻」难对齐。

## 五、展望与建议

### 5.1 需求（按优先级）

- **R1 `timeline.*` 字段**：`timeline_id`、`monotonic_version`、`event_ordering_confidence`、`phantom_event_count`、`pre_state_retained`、`causality_chain_auditable`。
- **R2 单调时间线对象**：versioned、append-only 的事故时间线，每次重建带版本号可复核。
- **R3 幽灵事件去重**：按 action_id＋retry_token 合并重试／重放副本。
- **R4 前态快照**：Agent 改写共享状态前强制落前态快照（接 168 可逆性）。
- **R5 重建率指标**：timeline_reconstructability_rate、事件顺序置信度、前态保留率。

### 5.2 用户旅程

- **SRE**：事故复盘 → 拉单调时间线 → 发现幽灵事件混入 → 去重 → 核对前态快照 → 确认因果链可审计。
- **安全**：调查 agent 不再靠人工重放上下文窗口，直接读 versioned 时间线还原事件。
- **平台**：新 agent 上线 → 时间线重建率检查 → 低于阈值阻断（接 170 期）。
- **审计**：抽查 20 起事故 → 核对单调版本与因果链 → 确认重建可复核。

### 5.3 实现方案（90 天）

- **0–30 天：对象。** 定义单调时间线 schema；存量事故补建版本号。
- **30–60 天：去重与前态。** 幽灵事件合并器；改写前快照（接 168）。
- **60–90 天：指标与门禁。** 重建率看板；低于阈值阻断上线；评测增重建维度（接 137／167）。

**第 129 个市场空白（五项）**：时间线重建率、事件顺序置信度、幽灵事件检出率、前态保留率、因果链可审计率——无一内建；`timeline.*` 为**第 98 次无人提字段族**。本地 173／173-kb 连续第 88 期成组启用：马云雷 31「轨迹数字资产＝可回放、版本化的动作轨迹」首次当主线——全库唯一把「agent 动作轨迹」做成可回放资产的实践，正是时间线重建的原材料；配 肖汉松 22（全局调度器：分派、等待＝动作须有顺序与栅栏）、周昕毅 10（灵魂三问①须引用实时指标／日志／拓扑＝取证需可观测底座）。判词：**本地把 agent 轨迹做成可回放数字资产，联网侧 2026 才把「跨 agent／工具／上下文可追溯」当卖点；两边都没把「这场事故的时间线能否被单调重建」做成一等字段。**
