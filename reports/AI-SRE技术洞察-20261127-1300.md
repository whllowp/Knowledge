# AI-SRE 技术洞察 第 333 期（2026-11-27 13:00）

## 工具在场面 / Tool Presence & Availability Integrity——「Agent 说『我查过了，没问题』，可那次会话里，存储巡检工具压根没被加载进上下文」

> **题眼：第 329 期问的是"信号互斥时采信哪一路"，第 332 期问的是"多路一致是不是共因"，这两期都默认 Agent 的感官是齐全的。本期要问的是更早的一步——在被采信之前，Agent 手里到底有没有那件工具？工具缺席在实践中被静默地解释成了"检查通过"，而这两种状态在日志里长得一模一样。** 2026 年 11 月 18—19 日，Anthropic 与 Google 几乎同时把"工具按需加载/编排下沉"推到主流工作台与 API 预览里，省账效果确凿；但 Agent 的"感官配置"从此变成每次会话都可能不同的运行时状态，而这件事从未被记录、被举证。

---

## 一、发展趋势

11 月中下旬，三条一线动态把"工具供给方式"从后台配置变成了前台议题。

**Anthropic Claude Code Code Mode（v2.1.323+，11-18 披露）：** 模型不再逐条发起工具调用，而是先写一段 JavaScript 脚本，把多步调用、条件判断、循环、结果过滤编排在同一段代码里本地连续执行，只把必要结果送回上下文；内置工具定义从 16 个精简为 3 个核心入口。第三方实测（bestagent.dev 拆解请求载荷）：未开启时每轮默认发送 16 个工具定义、首轮约 38,000 tokens；开启后高频 MCP 取数场景累计处理 token 下降 62%—77%，真实 API 账单省 22%—23%。但它是**默认关闭**的实验特性，需 `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`；官方明确给出理由——Auto 模式的安全分类器只能"整段大致看一眼代码"，无法像逐条调用那样对运行期动态拼出的每条路径逐一细查；客户端会刻意忽略项目目录配置文件里的开关（防clone 外部仓库被暗中打开），用户开启企业监控导出或禁用遥测则直接拒绝启动。

**Google Gemini API Tool Retrieval（11-19 官方博客，Interactions API 预览）：** 加一个 `tool_search` 工具、给长尾工具设 `defer_loading: true`，模型仍看得见所有工具的名称与描述，但完整参数 schema 不进上下文；需要时按名索取，API 在同一次请求内完成"搜索→加载 schema→function_call"三步，全程记在 `interaction.steps` 里。支持服务端与客户端（`execution: "client"`）两种模式、远程 MCP 服务器整体延迟加载、与前缀缓存兼容；官方点名三大痛点：输入 token 膨胀、延迟上升、**候选列表越长工具选择准确率越低**；AI Studio 文档给出的量级是"几十个函数声明每次请求就可能消耗上万 token"。

**AgentsRoom 的自测（11-03）：** 把 MCP 工具定义从约 95,000 token 削减到约 40,000，做法是让关闭的工具根本不列给代理；同时公开了 Claude Code 默认就用 tool search 延迟加载 MCP 工具定义、`ENABLE_TOOL_SEARCH=false` 或给服务器标 `alwaysLoad` 会让它重新全量进入上下文、MCP 结果超 10,000 token 警告/25,000 截断、`/context` 可按来源拆分占用。

一件事被三家用三种方式同时做到：把工具从"固定声明"改成"运行时供给"。降本是真的，代价却被记在了一个没人看的地方。

## 二、技术现状

现状一句话：**工具在不在场，正在被成本优化悄悄决定，而"在场性"不是任何可观测字段。**

传统 SRE 有一个隐含前提：值班工程师的工具箱是稳定的——他不会因为没有加载"数据库慢查询"工具就把慢查询当成"没问题"。Agent 没有这个前提。在 Code Mode 下，模型侧只剩 3 个入口，真正被调用了哪些内部能力，取决于那段脚本怎么展开；在 Tool Retrieval 下，长尾工具的 schema 没进上下文，模型"看得见名字、看不见参数"，一次检索失败就会让它绕开本该用的工具；在 AgentsRoom 式削减下，被关掉的工具根本不在候选里。三种机制都让 Agent 的行为空间在会话间漂移，但主流可观测栈记录的仍是"调用了什么"，不是"当时能调用什么"。

可观测侧，OTel GenAI 语义约定把 `gen_ai.tool_call` 纳入 span，Anthropic MCP SDK 的 OTel 集成（芝士猫 11 月综述）给出工具调用追踪、错误传播与 Shadow Agent 检测，第三方基准称跨供应商工具调用追踪准确率 >99.5%、每调用约 +5ms 开销、错误根因分析时间从 10 分钟降到 2 分钟。这些数字说明"调用过什么"越来越透明；可它们都无法回答"没调用是因为不需要，还是因为工具不在场"。

平台侧，阿里云 AgenticOps 把落地难点总结为三道墙——"数据采不到、上下文读不懂、能力验不准"，其云监控 2.0/AgentLoop 已将 Agent 自身的运行轨迹、成本与质量纳入观测；腾讯云 CloudQ 以"用 AI 管运维、用可观测管 AI"把 Token 消耗、工具调用与任务质量关联，并在慢回答会话中下钻到具体调用节点；信通院《云上 Agent 基准度量模型》给出功能/安全/可靠/体验/性能/成本六维与五项要求。这些都覆盖了"工具调用"这一层，没有一家把"工具集在会话间是否一致、缺席是否被误判为正常"做成一等字段。第 323 期问过"谁审过埋点计划"、第 313 期问过"压缩后证据还在不在场"，本期指出它们的上游盲区：**先于信号与上下文存在的，是感官本身的可获得性。**

## 三、技术竞争力：主要厂商/方案对比

下表按"工具供给是否可举证、缺席是否被记录、否定性结论是否有在场工具支撑"比较——这是本期提出的新维度。

| 方案 | 工具供给方式 | 在场性是否记录 | 缺席可否解释 | 否定结论有无工具支撑 | 工具在场可举证性 |
|---|---|---|---|---|---|
| Anthropic Claude Code Code Mode | 模型写脚本编排，内置定义 16→3 | 否（记录脚本与执行，不记"本可调用但未加载"） | 否 | 否（脚本没查=没查，无"本应查"基线） | 空白（默认关闭即因无法逐条细查） |
| Google Gemini Tool Retrieval | `defer_loading` + `tool_search` 按名加载 schema | 部分（三步记在 `interaction.steps`） | 部分（可见名称/描述，但加载失败无语义） | 否 | 部分（检索轨迹可查，缺席原因不可查） |
| Anthropic MCP SDK + OTel 集成 | MCP 工具统一追踪 + Shadow Agent 检测 | 否（追踪已调用，不追踪"未加载"） | 否 | 否 | 部分（调用链强，供给面空白） |
| AgentsRoom 工具削减 | 关闭的工具不列给代理，`/context` 拆分占用 | 部分（按来源列占用） | 是（配置层面显式关闭） | 否（未区分"不相关"与"没能力查"） | 部分（本地可查，无跨会话基线） |
| OpenAI Performance Factory | 对抗复核推翻前一结论，100 条抽检约 70% 准确 | 未见（复核结论，不复核感官） | 未见 | 部分（复核提高结论可靠性） | 空白（查得对≠该查的都查了） |
| 阿里云 AgenticOps 三道墙 | 云监控 2.0/AgentLoop + UModel/BRiSE | 部分（Agent 轨迹、成本、质量入库） | 未见 | 部分（三道墙保入库质量） | 空白（未声明工具集版本） |
| 腾讯云 CloudQ / 可观测 | 统一入口取证 + AI 可观测关联工具调用 | 部分（下钻到调用节点） | 未见 | 部分（复测与评估验证效果） | 空白（"慢回答"可查，"没查到"不可查） |
| OTel GenAI 语义约定 | `gen_ai.tool_call` span + 质量信号 | 否（span 未带 available_vs_loaded 字段） | 否 | 否 | 空白 |
| 本地 173：刘凯宁《蚂蚁 SRE 基于 Agent 的应急根因定位实践与踩坑》 | 人工定义工具边界与三分结论 | 主张工具权限显式化，未做成字段 | 主张待确认项单列 | 有（结论/证据/待确认三分） | 空白（新角度见第五节） |

**结论：** 可采购的能力集中在"把调用记全"（schema 加载轨迹、OTel span、下钻分析），没有一家把"这次会话本来能用哪些工具、实际加载了哪些、缺席的那些为什么没被用、以及'无异常'结论是否有在场工具支撑"做成一个可查询、可门禁的一等对象。下一轮竞争不是"能接多少工具"，而是"敢不敢声明这次结论是在完整感官下得出的"。

## 四、技术挑战

**挑战一：工具缺席是最像"检查通过"的沉默。** 第 285 期讨论过信号静默，但信号沉默至少面板上有空；工具没被加载时，Agent 只是不提它，报告里留下的是一段条理清晰的"已核查各项、无异常"——读者无法区分"查了没事"和"没能力查"。这是最危险的负事件形态：不是出错，是该发生的事没发生且没有痕迹。

**挑战二：降本优化改变了证据能力却无人审批。** Code Mode 把安全分类器从"逐条审"变成"整段看"，Tool Retrieval 把候选从全量变成按名检索，这些是权限/感官边界的实质变更，在多数团队里却作为"性能优化"发布，不走 CAB、不重定基线。第 61 期讲过"记住了什么是一次无人审批的状态变更"，本期是它的工具版：**少装了什么工具，同样是无人审批的状态变更。**

**挑战三：否命题无法举证。** "数据库无慢查询"要有慢查询工具在场才能成立；"无异常"是典型的否命题，其可举证性完全依赖工具集完备性，而现有评测（ORCA、ITBench-AA、R2Act、SWEOps-Bench）考的是"这一次答对没有"，没有一道题强制报告当时的工具覆盖率。

**挑战四：跨会话工具漂移使历史结论不可比。** 同一个 Runbook 上周跑出"正常"、这周跑出"异常"，可能只是工具集换了版本或长尾工具被设为延迟加载；没有 `toolset_version` 钉版，第 328 期的"同证据重跑"和第 331 期的"结论保鲜"都建立在变动的感官上。

**挑战五：便利与可审计的取舍被藏进默认值。** Code Mode 默认关闭、需要环境变量开启、企业监控导出开启时拒绝启动——这是厂商替用户做的风险判断，但用户侧的 SRE 规范没有对应的"什么时候必须关掉降本特性以保证取证完整"的条款。

## 五、展望与建议

**提出第 254 个空白字段族 `tool.presence.*`**（承 #310~#332 可举证率系列叠加）：

```
tool.presence.* {
  session_ref,
  declared_toolset[],              // 本会话可见的名称+描述（含 deferred）
  loaded_schema[],                 // 真正加载了完整参数 schema 的工具
  deferred_not_called[],           // 可见但未检索的长尾工具
  retrieval_mode ∈ SERVER | CLIENT | PRELOADED | SCRIPT_EMBEDDED | UNKNOWN,
  toolset_version,                 // 工具清单与 harness 版本钉版
  absence_reason ∈ NOT_APPLICABLE | DEFERRED_NOT_CALLED | FILTERED_BY_POLICY
                  | NOT_REGISTERED | TOOL_ERROR | UNKNOWN,
  coverage_claim,                  // "已检查 X、无异常"一类否命题声明
  claim_tool_bindings[],           // 声明中的每项检查绑定到在场工具
  negative_check_supported,        // 否命题是否有在场工具支撑
  harness_mutator,                 // 谁改了工具集（CodeMode/检索/权限过滤）
  counterfactual.tool_preloaded_claim_changed,  // 强制全量加载后结论是否翻转
  verdict ∈ TOOL_PRESENCE_ATTESTED | ABSENCE_MASKED_AS_CLEAN
          | TOOLSET_DRIFTED | UNVERIFIED
}
```
缺省 `TOOL_PRESENCE_UNVERIFIED`；`verdict≠TOOL_PRESENCE_ATTESTED` 的否命题结论不得作为"已独立复核"依据，不得据此自治升档（承 #310~#332 叠加）。

**四条最小动作：**（1）把"声明可用/实际加载/缺席原因"三份清单随每次结论落盘，否命题必须绑定在场工具；（2）工具检索失败、schema 加载失败一律三态化上报，不许退化成"未使用"；（3）工具集变更（含开启 Code Mode、改 `defer_loading`、关 MCP 服务器）视为接口变更，走 CAB 并重定评测基线；（4）每次取证做一次"全量工具强制加载"的 A/B 配对题，报 `negative_check_unsupported_rate` 与 `claim_flip_rate_on_preload`。

**采购三问：** 能否导出本次会话的工具在场清单与版本？能否区分"没调用"与"没加载"？"无异常"结论能否逐项绑定到当时在场的工具？三问有一问答不上，就不要把它的"已核查"写进事故复盘。

**本地原型（第 209 期新角度）：** 刘凯宁《蚂蚁 SRE 基于 Agent 的应急根因定位实践与踩坑》过去读作"把工程判断交给工程、结论/证据/待确认三分"，本期首次改读为——**三分法能防住"证据不足还下结论"，防不住"工具没在场却声称查过"；第四分应当是"这次检查所用的工具当时是否可用、是否加载、是否失败"**。配周昕毅"AI + SRE ≠ AISRE"的边界意识、何伟"生成与验证分离"、赵恒"语义层版本化"可得一条完整判词：证据要有主人、结论要有保质期、感官要有在场证明。

**信通院补格：** 在六维五项之外补"工具在场可举证率"一格，与 #316~#332 已提出的十七格并列。
