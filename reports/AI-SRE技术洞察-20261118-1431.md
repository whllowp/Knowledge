# AI-SRE 技术洞察（第 283 期）

**生成时间**：2026-11-18 14:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-18
**本期主题**：流式一致性面／同一个模型，两条渲染管线——流式与非流式不是同一条输出的两种传输

## 题眼

2026-09-28，vLLM 的一个修复 PR 把一件小事写进了标题：非流式的 `derender` 路径把整段 token 一次 `decode()`，当生成在**多字节字符中间**停下（`max_tokens` 截断时很常见），尾部不完整的字节序列变成替换字符 U+FFFD——`/v1/completions` 用 `max_tokens=1` 会返回 `' �'` 而不是 `''`；同文件的流式路径恰恰不会，因为它按 delta 走 `detokenize_incrementally`，会把不完整字节留在缓冲里（vLLM PR #59133，2026-09-28）。同一天段的另一边，2026-10-30 一个 Agent 框架的 PR 记录另一种分歧：DeepSeek、百度千帆的流式工具调用把**累计到当前的完整参数**在每个 chunk 重发，累加器仍用 `+=`，拼成 `'{...}{...}{...}'`、`json.loads` 失败后被静默清成 `'{}'`——一次被破坏的工具调用，日志里看不出异常（hermes-agent PR #35718）。再往前，2026-09-01 一份 Agent 运行时笔记写的是同一类问题：工具调用续传 chunk 把 `name` 以空串重发，`id`/`name` 被清空，组装出的块到达循环时名字是 `""`，工具注册表拒绝“未知工具”请求——该模型从此**无法运行任何工具**（deepseek-harness 架构笔记）。

三个 bug 都不是“模型变差了”，而是“流式与非流式是两条不同的渲染管线”。

## 一、发展趋势

1. **流式成为默认，测量方式随之改变**。2026 年流式是聊天与语音 Agent 的默认交付方式，性能单位从“请求延迟”变成“首 token 延迟＋增量间隔＋末块时间”，护栏、追踪、日志的判断对象也从“完整响应”变成“逐个 delta”（FutureAGI，2026-05-06）。

2. **两条管线重新合流，但合流处暴露差异**。vLLM 把离线重建（derender）做成独立 API，文档直接承认：解析器把 reasoning、content、tool_calls 切得与在线服务**不一样**，而且“不匹配不会报错”（vLLM Derenderer 文档，2026-11-05）。

3. **“增量”与“累计”两种提供方语义并存**。有的提供方每个 chunk 只发新片段，有的重发“到目前为止的全部参数”；客户端若只按一种假设写累加器，另一种就会被拼坏——而且失败是静默的（hermes-agent，2026-10-30）。

4. **传输层随时可以把流变回块**。gzip 需要攒够压缩块才输出，`proxy_buffering` 又把上游碎片先缓冲；二者与 SSE 同开，客户端看到的就是“只返回第一个字就停住”（华为云社区，2026-10-24）。Next.js 的压缩中间件对 `text/event-stream` 同样生效，监听端“连上了、但一个事件都没收到”（terrapod PR #71，2026-03-12）。

## 二、技术现状

**第一层：解码路径不同，边界字符不同。** 流式走增量 detokenizer，会保留不完整的 UTF-8 字节；非流式批量 `decode()` 把尾部残缺字节直接替换成 U+FFFD。CJK 与 emoji 在截断场景下最容易暴露：同一次生成，流式给出干净的半句，非流式给出带替换符的半句。

**第二层：工具调用组装是独立的一层语义。** 累计重发提供方让 `+=` 变成重复拼接；空串续传让身份字段被清空；并行工具调用的 delta 还会交错。任何一个假设写错，得到的不是报错，而是 `'{}'` 或空名字——工具照常被调用，只是参数错了、或者压根没调。

**第三层：末块才有元数据。** OpenAI 的 `usage` 只在最后一个 chunk 出现，且“流被中断或取消时可能收不到这最后一个 usage chunk”；Anthropic 的 delta 明确是 best-effort，“最终事件携带完整内容”，而提前结束（错误或中断）的请求**不产生最终事件**。于是中断的流既没有完整文本，也没有 token 账。

**第四层：传输层把“流式”变成“批量”。** 压缩与缓冲不会报错，只会让事件晚到或不到；探针看到 TCP 已连、HTTP 200，用户看到空白。

**第五层：日志记的是另一条管线。** 多数系统落库的是“最终组装文本”或“非流式重放结果”，而用户看到的是增量序列；护栏在增量上放行、在完整文本上拒绝，或反之，都会造成“日志说合规、用户说被冒犯”。

## 三、技术竞争力

| 方案／机制 | 传输 | 增量解码 | 工具调用组装 | 末块元数据 | 中断可见性 | 与非流式一致 |
|---|---|---|---|---|---|---|
| OpenAI Chat Completions 流 | SSE | 增量 | 增量 delta | usage 仅末块 | 中断丢末块 | 未承诺 |
| Anthropic Messages 流 | SSE | 增量 | 增量 delta | 末事件携带 | 错误无末事件 | 未承诺 |
| vLLM 在线流 | SSE | 增量 detokenizer | 服务端解析 | 有 finish | 有 | 与 derender 可能不同 |
| vLLM derender 重建 | 离线 | 批量 decode | 独立解析器 | 有 | 无 | 文档承认可能不同 |
| 自建 SSE + Nginx | SSE | 自行实现 | 自行实现 | 自定义 | 取决于缓冲 | 取决于实现 |
| BFF/压缩中间件 | HTTP | 透传 | 透传 | 透传 | 易被 gzip 吞 | 否 |
| 聚合框架（LiteLLM 等） | 多协议 | 依赖适配 | 累加器假设 | 归一化 | 弱 | 未验证 |
| 累计重发提供方 | SSE | 增量 | **累计重发** | 有 | 弱 | 否 |
| 日志／回放系统 | 批量 | 不适用 | 不适用 | 不适用 | 记录的是重放 | 否 |

**判读**：每家都能回答“流式接口是否返回了 chunk、首 token 多快”。没有一家能回答“**用户屏幕上看到的这段、日志里落下的那段、把同一请求改成非流式再跑一次得到的那段，三者是否同一段**”。而在事故与合规里，要的正是这个等式。

**本期反转**：我们一直把流式当“传输优化”——同样的输出，早一点给用户。实际它是**第二条渲染管线**：解码边界不同、工具调用组装语义不同、末块元数据归属不同、传输层随时能降级成批量。把流式当传输，就会用非流式的日志去证明流式的行为；把两者当同一件事，就会在 `'{}'`、`""`、U+FFFD 上反复踩坑，而且每次都以为“模型不稳定”。

**判词**：「流式 API／SSE／增量 detokenizer／工具调用组装库／网关／压缩中间件／日志与回放」全部可采购，「用户看到的这段、日志记下的这段、非流式重放得到的那段是否同一段，以及不一致发生在解码、组装、传输还是记录」不可采购。

## 四、技术挑战

1. **边界字符**：多字节字符被截断时，只有增量解码保留正确字节。
2. **累计 vs 增量**：提供方语义不统一，累加器必须可判别、可失败。
3. **空 delta**：续传 chunk 用空串/null 表达“无变化”，容易被误当新值。
4. **压缩与缓冲**：gzip/代理缓冲静默改变交付时序。
5. **中断无末块**：没有最终事件，就没有完整文本与 usage。
6. **日志口径**：落库的是组装结果，不是用户看到的序列。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 双管线等价测试：关键请求同时走流式与非流式，比对规范化文本、工具调用参数、finish 原因。
- D2 组装器判别：按提供方语义选择增量或累计模式，累计模式做幂等拼接，拼接后必须 `json.loads` 成功，失败即告警。
- D3 空值语义：明确空串/null 表示“无变化”，不得覆盖已有身份字段。
- D4 末块兜底：中断时从增量缓冲重建文本与用量，并标注“不完整”。
- D5 传输体检：对 SSE 路径断言“事件到达间隔”，而不只是连接成功。
- D6 记录口径：日志同时保存原始 delta 序列与组装结果，标注两者差异。

**用户旅程（一次“半句话被执行”的 Agent 事故）**

① 用户问“把上周报表发我”，界面开始逐字显示；② 提供方用累计模式重发工具参数，框架 `+=` 拼出 `'{...}{...}'`，`json.loads` 失败后被清成 `'{}'`；③ 工具以空参数被调用，返回“未找到”，Agent 回答“没有报表”（D2 缺失）；④ 与此同时代理开了 gzip，用户端流在第一个事件后停住，用户只看到“好的，我来”（D5 缺失）；⑤ 日志落库的是非流式重放结果，看起来完全正常（D6 缺失）；⑥ 复盘时无法回答“用户看到的、日志记的、重放得到的，哪一段是真的”。

**90 天实现方案**

- **第 1–30 天**：对三条关键链路做双管线等价测试，产出差异清单（D1）；给组装器加提供方语义判别与失败告警（D2/D3）。
- **第 31–60 天**：中断兜底与用量重建（D4）；SSE 路径的到达间隔断言与 gzip/缓冲体检（D5）。
- **第 61–90 天**：日志双写（delta 序列＋组装结果）与差异标注（D6）；用一次真实截断与一次真实中断回放，验证“三份文本”能被解释。

**第 204 个市场空白（五项）**：① 流式/非流式双管线等价测试规范；② 工具调用增量与累计语义的判别协议；③ 空 delta 与身份字段的保护规则；④ SSE 到达间隔的传输断言；⑤ delta 序列与组装结果的双口径记录标准。

**`stream_equivalence.*`／`delta.*` 第 171 次无人提字段族**：文档谈“如何开流式、如何读 chunk”，不谈“同一请求的两条管线是否等价、差异出在哪一层”。

**本地 173／173-kb 连续第 159 期成组启用（赵恒 25：流式日志要能说清用户到底看到了哪半句）**：本地原型对每次流式请求落 `stream_capture{request_id, provider, mode=incremental|cumulative, deltas[], assembled_text, tool_calls[], finish_reason, interrupted}`，并与非流式重放做文本规范化比对；差异超阈值触发“双管线不一致”事件。
