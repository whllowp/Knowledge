# AI-SRE 技术洞察 · 第 84 期｜时间基准面：证据各自为真，却不在同一个时刻

> 生成时间：2026-11-06 09:00（GMT+8）｜范围：2026 年，重点最近 30 天｜本地知识源：`E:\Knowledge\Knowledge\preview\173`（31 篇）
> 本期主线（第七十五条）：**时间轴是前六期共用的坐标系，却唯一没被当成运维对象**。79 组织层、80 执行层、81 验收层、82 配置表、83 样本框之后，本期问五者共同站在其上的东西：证据上的时间戳是谁的钟、代表哪一段、能否放在同一条线上。与 20 证据链、73 计量面、81 弃权面、83 采样面划界——分母之外还有窗口，存在性之外还有同时性。

## 一、发展趋势：时间在变细、变多、变分段，没有一层负责说明它们能不能相加

10-15 IT 架构师联盟给出最小反例：订单 API 10:00 发布 v42，10:03 五分钟窗口 P95 从 120ms 升到 900ms，Agent 引用「10:02 的连接池超时日志」判定「新版本导致连接池耗尽」——那条日志实际 09:57 发生在仍跑 v41 的旧实例上。三条记录全部真实、全部附出处：E1 09:57 发生 / 10:02 被采集观察，E2 10:03 求值并向前统计五分钟，E3 10:00 开始接流量，结论却全错。**引用校验只能证明没有伪造出处，补不出「慢请求运行在 v42 上」**（自媒体分析、案例系假设构造）。

OTel 日志数据模型早用两个顶层字段区分时间：`Timestamp` 是「事件发生时间，由源端时钟测量」且源端时间未知时允许缺失；`ObservedTimestamp` 是「采集系统观察到事件的时间」，外部来源由 OTel 代码自己的钟测量。而截至 11-02，OTel GenAI 的 agent span 与 metrics 文档仍全部标记 Development，独立仓库 2026-06 迁出后未 cut release，连「一次 run 的时长」「每 run 调用数」都在重做未发布。**日志侧早给了双时间，智能体侧连「一次运行多久」都还没定稿**。

最近 30 天方向一致：10-14 Anthropic Claude Platform OTel 导出公测（span 默认只带时长、状态、token、模型与工具名，发往 AWS 的 API span 单独成 trace）；10-22 Google Cloud 发布 Agent Compute Engine；其智能体可观测性文档 11-02 更新（trace 给执行路径、派生指标算调用数与总 token，内容另存 GCS）；10 月底腾讯云开发者社区提出「把发布、配置、扩缩容事件**接入同一条时间轴**」；阿里云 AI 网关把请求拆成鉴权/缓存/护栏/模型/输出检测五段子 span，理由是「首字变慢时能定位是护栏慢还是排队长」。**每多一段就多一口钟，却没有一层负责说明这些时间能不能相加**。

## 二、技术现状：四种时间、无主空档、以及一个没有边界的「过去」

一条证据上至少四个时间：①事件时间（源端钟）②观察时间（采集钟）③求值时间（范围选择器向求值时刻之前取样，10:03 的五分钟窗口横跨 10:00 发布）④生效时间（变更接流量、202 Accepted 已受理未落地）。工具适配层通常只返回一个 `timestamp`。OTel 甚至建议「转换到只支持单一时间戳的格式时，用 Timestamp，否则用 ObservedTimestamp」——**降维本是给弱接收方用的，Agent 恰是只接一个数却要拿它排因果的接收方**。

第二种失真是聚合：P95 抹掉实例与版本，瞬时选择器可能返回回看范围内最近样本。修法是固定查询入参（表达式、start/end/step、聚合口径、结果快照），用 `event_time` / `observed_time` / `scope` / `version` / `usable_for` / `not_for` 重写引用——**证据不再是「存在的事实」，而是带时间语义与适用范围的断言**。

第三种是长程任务让时间从点变成区间，中间大段无主空档。HITL 审批（80 期幂等窗口短于审批窗口）、Anthropic 10-09 后台 workflow run、排队重试，都塞进同一个 `duration`。本地 173 库最刺眼：肖汉松 badcase **平均修复 12.6 天，修复和验证只需数小时**，其余全是等待人工分析/确认/关单；casa 判词「**空白、等待、失败都没有设计**」。79 期按 session-hour 计费与 82 期成本科目在此合成：**账单按墙钟走，那 12 天既无 span 也无科目**。

第四种是回放边界。「采集到 ≠ 后端已可查询」：10:03:30 可查的记录能进 10:04 的响应，10:05 才可查的不能倒灌；CloudTrail 有 `DELIVERY_DELAY`、SaaS 审计 API 最终一致，取证指南要求「窗口关闭后重查再宣布动作不存在」。**没有 as-of 边界的复盘，等于用今天的数据给昨天的 Agent 补证据**——78 期「必须做时间旅行的 SLO」的过去态版本。

最接近完整答案的反在取证/合规侧：NHIMG 要求「先因果后时钟」（同一 trace 父子链给真实顺序，与宿主机钟无关）、「逐源测 skew 而非假定」（CloudTrail `eventTime` 是宿主钟的请求完成时间、Entra `createdDateTime` 是登录发起时间、span 起止来自被埋点进程）、原值与归一化值分列。scixa 更直接：忽略时钟纪律会产生一条**人工审核者看起来早于模型产出就已批准**的时间线；须同带 event/ingest time、声明假定 skew、绝不静默排序；「若 decision id 无法 join 特征库 snapshot id，时间线恰在最关键处有个洞」——**absence is data**，78 期负事件家族在时间层的对应物。

## 三、技术竞争力：双时间能否机器读出、skew 是否声明、回放能否冻结

| 方案 / 厂商 | 双时间语义 | 时间来源声明 | 跨源对齐与 skew | 长程挂起归属 | as-of 回放 | 时间字段成熟度 |
|---|---|---|---|---|---|---|
| OTel Logs Data Model（规范） | ✅ Timestamp / ObservedTimestamp 两顶层字段 | ✅ 明确「源端钟」「采集钟」 | ❌ 未涉及 | — | ❌ | Stable |
| OTel GenAI 约定（11-02） | ❌ 仅 duration / TTFT / TPOT | ❌ | ❌ | ⚠️ run duration 指标草案 | ❌ | 全 Development、无 release |
| Anthropic Claude Platform OTel（10-14） | ❌ 默认仅「延迟」等元数据 | ❌ | ⚠️ AWS 上 API span 独立成 trace | ❌ | ❌ | 公测 beta |
| OpenAI Agents SDK tracing | ❌ started_at / ended_at UTC | ❌ | ❌ | ⚠️ 审批、guardrail 记为事件 | ❌ | 默认开；ZDR 策略下不可用 |
| Google Cloud Observability（11-02 文档） | ❌ 由 span 派生指标 | ❌ | ❌ | ❌ | ❌ | GA；内容另存 GCS |
| 阿里云 AI 网关 / CMS 2.0 | ❌ | ⚠️ 分环节子 span | ❌ | ❌ | ❌ | 网关方案；CMS 插件默认 DISABLED |
| 腾讯云 CloudQ / 社区方案 | ❌ | ⚠️「接入同一条时间轴」 | ⚠️ 变更关联 | ❌ | ❌ | 看板能力 |
| 火山引擎 AgentKit | ❌ | ❌ | ❌ | ⚠️ 30 分钟硬超时 | ❌ | 端到端观测 / 评测 |
| 取证侧（NHIMG / scixa） | ✅ 原值与归一化值双列 | ✅ 逐源声明假定 skew | ✅ 先因果后钟、逐源测偏移 | — | ✅ 回放包＋查询入参 | 方法论，非产品 |
| 本地 173 工程实践派 | ✅ 双时态＋编辑日志回放 | ✅ 服务端时间戳 | ⚠️ 核实时序与业务依据 | ✅ 等待被单列 | ✅ 宽窗复查 / 未复检标注 | 项目内约定 |

判读要克制。规范层双时间最完整却只管日志，GenAI 侧连 run duration 未定稿；模型厂商最诚实也最薄（83 期 Anthropic 把账本交给 Usage API，本期它把时间交给 span 却没说用哪口钟）；云厂商方向最对但那是**看板能力不是证据契约**（无双时间导出、无 skew 声明、无 as-of 冻结）；国内平台派可控最好，时间语义散落在「使用限制」页。完整工程答案来自取证方法论与本地 173 库，两者均不可采购。分野三问：**双时间能否机器读出／skew 是声明还是假定／回放能否冻结 as-of**。

**本地 173 库连续第五期成组启用，首次升级为「时间治理原型」**：余锦泽 03「当前生效版本＝基线＋编辑日志回放」、编辑日志带服务端时间戳、时序图谱区分事实有效时间与系统记录时间的**双时态**，并把「时间窗口过短」固化为「宽窗复查与未复检标注」；刘凯宁 05 把「**核对时间窗**、执行权限与查询状态」列为取数三检查，要求「围绕流量来源、传播关系和**动作时序**验证候选」「端侧与服务端信号关联后仍需核实时序和业务依据」；刘杨 08 把 duration 打碎成**逐 token 耗时＋候选概率**（「追到 LLM Span 只剩输入、输出和耗时」）；周昕毅 10「关联事件＝时间窗口・拓扑关系」；刘宗明 06 与李东东 16 把等待显式建模（「等待、调整还是停止」「默认 5 分钟卸载」）。判词：**联网侧在给时间补字段，本地工程实践派早把时间做成版本机制、一等证据与成本主体**。

## 四、技术挑战：五处结构性缺口

**其一，「最近」没有定义。** RCA 先验「找最近变更」在四种口径下指向四个事件；75 封网、78 到期负事件的先验失明在此更彻底——不是记录缺失而是**排序键缺失**，时钟一漂整套叙事没有公证人。

**其二，规范允许折叠。** OTel 单时间戳建议面向弱接收方，而 Agent 强推理弱时间语义；`Timestamp` 允许缺失、`ObservedTimestamp` 用采集侧钟，压成一个数后迟到日志不可识别，且**没有任何字段记录发生过这次折叠**（82 期配置层负事件的时间层镜像）。

**其三，生效时间不在 trace 里。** 202 Accepted 与 200 同标「成功」，下游队列可能几秒甚至永不落地，Agent 读旧值继续推理、每步 200。修法是给 trace 加一层**世界状态**锚点——80 期「超时是观察不是结果」的跨系统版：不是结果未知，而是**另一系统的生效时刻不在图上**。

**其四，时钟偏差不进指标不告警。** 各主机独立维护时间、容器继承宿主钟、虚拟化宿主负载影响时钟；改时间本身应进审计。scixa 警告：一条「审批早于产出」的时间线会让对方专家折价全部证据。

**其五，等待无 owner 无科目。** 12.6 天、HITL 挂起、后台 run 全混在 `duration`；79/82 期成本科目还缺「**等了多久、等的是谁**」。

**第三十八个市场空白**：时间基准台账／双时间保留率／跨源时钟偏差／as-of 边界四项无一内建；对比表「双时间」「as-of」两列几乎全空。OTel GenAI 至今无 `time.*` 字段族——继 72 `identity`、79 `billing_unit`、80 `attempt`、81 `abstain`、82 `config.effective`、83 `sampling` 之后，本期这一族仍无人提。

## 五、展望与建议

1. **证据契约七字段**：`event_time` / `observed_time` / `evaluation_time` / `effective_time` / `clock_source` / `skew_bound` / `as_of`；适配层保留表达式、start/end/step、聚合口径与结果快照，禁止只存「最近五分钟」。
2. **双时间不折叠门禁**：只给单一时间戳则标 `time_semantics=unknown`、禁入因果候选集，把 81 期 ABSTAINED 从「证据够不够」扩到「可不可比」。
3. **as-of 回放器**：每次工具响应带 `as_of` 与 `coverage`，迟到数据不倒灌；回放包存当时实体/版本映射及有效时间。
4. **时钟成为一等 SLI**：`clock.skew_ms`、NTP 状态、时间变更进审计；跨源排序先取 trace 父子因果链，无父子则逐源实测并声明偏移。
5. **等待归属账本**：挂起时长与有效工作、计费时长三账分记，产出「等待占比」而非「平均耗时」。
6. **规范与采购**：向 OTel genai 提 `time.*`；采购条款要机器可读时间语义清单、双时间导出、as-of 快照；混沌新增「时钟偏差/迟到日志/窗口漂移」题型。

**结论**：83 期「样本框没上线」推到更底层——**坐标系还没上线**。能力按层分工已清楚（规范管日志、模型层管时长、云厂商管分段、取证侧管对齐），却没有一家把「这些时间属于同一条线」当作可验证、可采购、可 SLO 化的承诺。79「编制制度」、80「写序制度」、81「不写的制度」之后，本期是：**时间轴制度还没上线**。
