# AI-SRE 技术洞察（第 370 期）

**生成时间**：2026-11-27 10:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：语义约定面／遥测 schema 的版本迁移与静默空仪表

## 题眼

OpenTelemetry 的语义约定（semantic conventions）已经不是"建议命名"，而是**遥测的 schema**：属性名、类型、单位、稳定性等级都写在规范里，SDK、Collector、后端、仪表盘按同一份名字对齐。规范里给每个属性标了 stability——`development`、`stable`、`deprecated`；改名不是改注释，是改数据。

2026 年最典型的迁移是数据库属性：`db.system` 一类的旧名逐步让位给带命名空间的 `db.system.name` 等新名。名字一换，**按旧名过滤的仪表盘不会报错，只会变空**；告警规则不会失败，只会永远不触发。这不是"依赖升级"，是**一次没有编译期检查的 schema 变更**。

## 一、发展趋势

第一，可观测性从"各家自定义"走向"跨厂商契约"。OTel 语义约定覆盖 HTTP、数据库、消息、RPC、K8s、GenAI；厂商后端与采集器按同一份属性名解析，仪表与告警因此可以跨后端迁移。

第二，GenAI 语义（`gen_ai.*`）成为增长最快的部分。模型调用、token 用量、工具调用、Agent 会话都在这套命名下快速演进；演进速度快意味着稳定性等级低，**今天写的仪表明年可能对不上**。

第三，语义约定开始影响成本与基数。属性名与取值域决定了时间序列的数量；一个"方便"的标签（用户 ID、请求 ID）会把基数打爆——语义约定在规范层面对此有约束，但约束不是强制。

第四，迁移从"一次性改名"变成"双写窗口"。采集端同时发旧名与新名，后端两套都能查；窗口结束后旧名退场。双写的成本、时长与退场判据，成为新的运维面。

第五，语义约定开始进入采购与合同条款。买方要求厂商按 OTel 命名输出，否则迁移成本由买方承担；"可导出、可对齐"成为可观测性产品的新比较维度。

## 二、技术现状

**稳定性等级是承诺，不是标签。** `stable` 的属性可以依赖；`development` 的属性随时可能改名或改类型；`deprecated` 的属性有退场时间表。仪表盘如果依赖 `development` 属性，等于把告警建在流沙上。

**改名是静默的。** 查询语言按字符串匹配属性名；旧名没有数据时，`rate()`、`sum by()`、告警表达式都不会报错，只会返回空或零。空仪表与"系统正常"在视觉上无法区分。

**跨语言 SDK 不总是一致。** 同一份约定，不同语言的 SDK 落地进度不同；Collector 的转换器、后端的兼容层、仪表的查询，任何一层没跟上，数据就断层。

**GenAI 语义仍在快速迭代。** token 计数、模型名、工具名、会话 ID 的命名与语义在 2026 年多次调整；依赖这些属性做成本核算或质量分析的仪表，需要按版本锁定。

**语义约定与基数互相牵制。** 约定鼓励"低基数、可聚合"的属性；但业务方常把高基数标识塞进标签。约定管命名，管不了取值域。

**迁移工具存在，但不普及。** 有的后端提供属性重写/别名；有的靠 Collector 的 transform 处理器；有的只能改仪表。没有统一"语义版本"字段告诉查询"这条数据用的是哪版约定"。

## 三、技术竞争力

| 方案/能力 | 语义版本管理 | 改名兼容 | 主要代价 |
|---|---|---|---|
| OTel SDK + semconv | 按库版本 | 双写/转换器 | 跨语言不一致 |
| OTel Collector transform | 规则级 | 可重写属性 | 规则漂移 |
| Prometheus 命名约定 | 无版本字段 | 无 | 改名即断 |
| 厂商 agent | 厂商内置映射 | 部分 | 锁定 |
| 后端属性别名 | 后端级 | 查询兼容 | 不统一 |
| 仪表即代码（GitOps） | 可审查 | 可批量改 | 迁移工作量大 |

**判读**：可采购的是"SDK + Collector + 约定文档 + 迁移工具"；不可采购的是"这条遥测用的是哪版约定、改名后谁还在读旧名、双写窗口多长、仪表是否静默空、GenAI 属性是否稳定"。

**本期反转**：我们一直把语义约定升级当成依赖升级——改个版本号、跑一遍测试。实际上它是**schema 变更**：没有编译期检查，没有运行时错误，只有"仪表变空、告警不响"。**遥测的兼容性不是 API 兼容性，是查询兼容性。**

## 四、技术挑战

**挑战一：空仪表的不可见性。** 旧名无数据时，面板显示"无数据"或零；值班看到的是"平静"，不是"失明"。需要"属性存在性"检查，而不是"数值阈值"检查。

**挑战二：稳定性等级的治理。** 谁来决定能不能依赖 `development` 属性？需要把"属性稳定性"纳入仪表评审，像依赖版本一样记录在发布清单里，并定期复核。

**挑战三：双写窗口的退场判据。** 双写多久、怎么证明没人再读旧名、旧名何时删——没有查询日志就无法回答。

**挑战四：GenAI 语义的快速演进。** 成本与质量仪表依赖 token/模型/工具属性；约定一变，历史对比就断。需要按版本保留口径。

**挑战五：跨厂商迁移。** 换后端时，属性名、单位、聚合语义都可能变；"同一份遥测"在不同后端不是同一张图。

**挑战六：语义约定没有属主。** 它被 SDK 团队、采集团队、仪表团队、SLO 团队同时依赖，却没有一个人负责"我们用的是哪版、什么时候升、升完谁验证"。没有属主的契约，会在下一次升级时静默断裂。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①语义版本台账（每条遥测用哪版约定）；②属性稳定性准入；③改名双写与退场判据；④空仪表检测；⑤GenAI 属性版本锁定；⑥跨后端迁移验证。

**用户旅程**：SDK 升级 → 新属性名上线、旧名双写 → 仪表同时查新旧名 → 观察窗口内确认新名有数据、旧名无查询 → 旧名退场 → 删除旧仪表与旧告警 → 记录语义版本。任何一步缺失，都会留下"永远不触发"的告警。

**90 天实现方案**：0–30 天，盘点依赖 `development`/`deprecated` 属性的仪表与告警，建立语义版本台账；31–60 天，给改名属性加双写与空值检测，仪表改为"属性存在性 + 数值"双检查；61–90 天，把语义版本纳入变更评审，定义 GenAI 属性的锁定与迁移流程。

**第 282 个市场空白（五项）**：语义版本台账；属性稳定性准入；双写退场判据；空仪表检测；GenAI 属性口径锁定。

**`semconv.*`／`telemetry_schema.*` 第 249 次无人提字段族**：所有采集器都报"支持 OTel 语义约定"，没有一个字段报"这条数据用的是哪版约定、哪些属性是 development、改名后谁还在读旧名、仪表是否因空值而失明"。

**本地 173／173-kb 连续第 237 期成组启用（肖汉松 22：语义约定升级不是依赖升级，是 schema 变更；遥测的兼容性不是 API 兼容性，是查询兼容性）。**
