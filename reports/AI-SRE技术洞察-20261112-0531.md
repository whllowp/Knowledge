# AI-SRE 技术洞察（第 139 期）

**生成时间**：2026-11-12 05:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：告警面／信号质量面（Alert Quality）——告警不是越多越安全；一晚上 200 条里只有 2 条要动手

---

## 题眼

incident.io 的 2026 on-call 指南给了两个很具体的数：**一个班次「2–3 起可行动事故」是健康基准**；以及「每次换班都在放大关键上下文丢失的风险」。而 Rootly 今年的数据补上另一半：**告警量比一年前更高，非工作时间的告警接近翻倍**——AI 让 PR 频率翻倍（i = c × p 里的 c 上去了），**告警跟着翻倍**。于是运维团队面对的不是「有没有告警」，而是「**这一晚 200 条里，有几条值得叫醒人**」。**告警系统的成功指标，应该是「叫对了多少次」，不是「叫了多少次」。**86 期说过「告警安静不等于修好了」；本期问的是反面：**告警吵闹，不等于有事**。

## 一、发展趋势

**趋势一：告警从「覆盖率」转向「可行动率」。** 传统做法是「每个指标都配阈值」；现在更关心「这条告警触发后，人能做的那件事是什么」。**没有动作的告警是噪音，不是安全网。**

**趋势二：Agent 既在减少告警，也在制造告警。** 调查 Agent 能把多个信号聚成一条结论（降噪）；但 Agent 自己也会失败、重试、卡住，**每多一个 Agent，就多一类「它不工作了」的告警**。更麻烦的是，**Agent 生成的告警往往没有 owner**——它报的是「我失败了」，而人不知道该找谁。

**趋势三：告警规则本身是生产变更。** 改阈值、加静默、换路由，都会改变「谁被叫醒」；但多数团队改告警不走变更评审（127 期的行为发布问题在告警层复现）。

## 二、技术现状：四个指标，通常只看一个

**数量：最容易看，最没用。** 告警总数、每班次数；**数量下降可能只是静默变多**（132 期「静音是暂时不看」）。

**可行动率：真正该看的。** 触发后有人做了动作的比例；**2–3 起/班是基准，超过就是噪音**。

**去重率：被低估的。** 同一根因触发 40 条告警；**没有去重，人就学会忽略**。

**误报成本：没人算。** 一次误报 = 一次唤醒 + 一次上下文切换；**夜班误报的代价是第二天的事故**。

**告警的三种坏，坏法不同。** 无动作告警（叫了也白叫）、重复告警（同因多条）、过期告警（规则还对、系统已变）；**前两种靠字段就能治，第三种要版本与审计**。

**告警与 SLO 脱节。** 告警阈值常与 SLO 无关（拍脑袋的 90%）；**SLO 变了，告警不跟着变**——131 期的承诺与告警是两张皮。

## 四、技术挑战

**一，可行动率没有字段。** 告警触发后有没有动作，通常不在告警系统里；**没有 `action_taken`，就算不出来**。

**二，Agent 告警无人负责。** Agent 失败告警该发给谁？平台团队、Agent owner、还是模型供应商？**没有 owner，告警就默认被忽略**。

**三，静默会掩盖问题。** 静默是「暂时不看」；**没有到期与复盘，静默就变成永久关闭**。

**四，规则变更绕审计。** 改阈值、加静默，往往直接在控制台点；**没有变更单，事故复盘时找不到「谁改的」**。

**五，降噪与漏报的取舍。** 聚合太狠会漏掉独立故障；**没有对照，就不知道降噪有没有降掉真信号**。降噪前后要跑同一批历史事故，报「少叫了几次」与「漏了几次」。

**六，疲劳不可见。** 夜班被叫醒几次、第二天状态如何，**没有数据，就不会被当成可靠性问题**。

**七，告警路由与值班表耦合。** 告警发给「当前值班人」，而不是「能处理它的人」；**换班时告警路由跟着换，交接没写清就会漏**（132 期）。

**八，多团队共享告警渠道。** 一个频道里混着五个团队的告警；**每条都合理，合起来就是噪音**。分频道不难，难的是分完还有人看。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `alert.*` 字段**：`rule_id`、`trigger`、`action_taken`、`dedup_key`、`silenced_until`、`owner`。
- **R2 可行动率**：按规则统计「触发后有动作」的比例；低于阈值的规则进清理清单。
- **R3 去重与聚合**：同根因聚合为一条；**聚合规则本身要有版本**。
- **R4 Agent 告警归属**：每类 Agent 告警有 owner 与处置手册；无 owner 不进值班。
- **R5 静默到期**：静默必须带到期时间与理由；到期未续自动恢复。
- **R6 规则变更审计**：告警规则变更走评审；季度审计一次全量规则。
- **R7 告警预算**：每团队每班次告警条数上限，超限必须清理或聚合，不能靠值班人硬扛。

### 5.2 用户旅程

- **SRE**：夜班收到 12 条告警 → 8 条同一根因（聚合）→ 2 条需动作 → 2 条误报 → 记 `action_taken` → 交班时把「2 条未闭环」写进交接包。
- **平台负责人**：季度看板 → 可行动率 41%、去重率 78% → 下线 60 条零动作规则 → 下季度复核可行动率是否升、漏报是否增。
- **Agent owner**：收到「Agent 失败」告警 → 按手册处理 → 修完把该告警改为「仅记录」。
- **审计**：抽查 30 条静默 → 核对到期与理由 → 确认没有永久静默。

### 5.3 实现方案（90 天）

- **0–30 天：埋点。** 记录 `action_taken` 与 `dedup_key`；统计基线。
- **30–60 天：清理。** 零动作规则下线；静默加到期；Agent 告警配 owner。
- **60–90 天：审计。** 规则变更进评审；季度全量审计；疲劳指标进复盘。
- **90 天后：预算。** 每团队设告警预算；连续超限的团队做规则清理，而不是加人。季度复盘把「夜班唤醒次数」与「次日事故率」放一起看。

**第 91 个市场空白（五项）**：可行动率可报率、去重率覆盖率、Agent 告警归属率、静默到期率、规则变更审计率——无一内建；`alert.*`／`signal.*` 为**第 60 次无人提字段族**（与 138 期同号，因并发覆盖，见索引说明）。本地 173／173-kb 连续第 54 期成组启用：肖汉松 22「全局调度器……进入等待」＝全库唯一把「分派与等待」写成一级组件的实践，本期首次当主线；配周昕毅 10「告警能否给优先级与影响面」＝告警本该携带判据、刘凯宁 05「结论/证据/待确认」。判词：**本地把「告警要能判断」写进 AISRE 三道检验，联网侧 2026 年才给出「2–3 起可行动事故/班」的基准；两边都没把「这条告警有没有让人动手」做成字段。**
