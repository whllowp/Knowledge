# AI-SRE 技术洞察（2026-11-03 00:00 期 · 第 38 期）

**本期主线：写入面运维——智能体的每一次写，都是一次生产变更（第二十九条主线）**
前 37 期先后覆盖治理、根因、演练、组织、记忆、路由、供应链、承诺、进化、缓存、时间、知识供给、接口、轨迹、配给、边界、判据、输入、运行态、协同等平面，但始终有一个对象未被正面解剖：智能体**对外部世界的写入**。第 37 期留下钩子——"恢复 agent 不会撤销它已改过的记录和交易"；第 26 期管的是智能体改写自身文件；本期管的是它改写**我们**的系统：写入了什么、写重了怎么办、两个智能体同时写怎么办、写错了怎么收回来。

## 一、发展趋势

**写入正在被重新路由进变更流水线。** 本周 Grafana ObservabilityCON 2026（旧金山）给出最清晰信号：Managed Sandboxes 公测中，Grafana Assistant 克隆仓库、结合生产遥测定位代码、准备修复，最终以**开一个 Pull Request 等人评审**收尾——智能体的"修复动作"被压缩成一次人类审批的变更申请，而不是直接落库的写操作。同期 GA 的 Agent Observability（OTel 支持）让"agent 干了什么、花了多少"与其他服务同标准呈现；其《2026 可观测现状报告》显示 68% 受访组织已让 AI 越过调研进入试点或生产，但对"只读调查"的舒适度为 85%，对"完全自主修复"仅 52%——**行业对写入的信任度比读低 33 个百分点，这正是写入面成为独立运维对象的民意基础。**

**确定性引擎接管写入的"临门一脚"。** Dynatrace 在 Perform 大会发布 Dynatrace Intelligence：确定性 AI（因果实时上下文）+ 智能体 AI（护栏内推理决策）双轨，实测外部 SRE agent 与确定性 agent 协作后，问题解决率提升至 12 倍、速度快 3 倍、成本减半——潜台词是**智能体负责想，确定性管线负责写**。国内侧，阿里云 AgenticOps 全栈发布中，云效研发智能体以"数字分身"形态继承使用者本人的资源权限执行提交与变更，开发者审核确认；标准化侧，IETF《Idempotency-Key HTTP 头》草案 08 版（10-22 更新）进入冲刺，为非幂等写入的容错给出第一个互联网级规范。

## 二、技术现状

**分布式系统年代解决过的两个老 bug，正被智能体编队全数复发。** 典型事故链：客服智能体调 create_refund，30 秒超时，框架重试第二次成功——**客户收到两笔退款**，因为第一次实际已提交、只是响应丢了；同时另一台分诊智能体把整个标签数组读出后整写回，把四秒前写入的 refund-issued 标签覆盖删除——**两次调用都返回 200，trace 干净，系统状态错误**。这两个故障（重复写入、丢失更新）在支付与数据库领域早有成熟解：幂等键 + If-Match 版本前置条件 + 记录级租约；智能体编队把它们带回来，是因为多数框架把写工具当函数调用，而它实际是对共享状态的网络请求。更隐蔽的是智能体放大器：模型不信任第一个响应就重发调用、harness 从检查点恢复后重放步骤、HTTP 层重试策略与推理层重试同时开火。

**两大 SDK 的写入门禁已成型但形态迥异。** OpenAI Agents SDK 提供 needs_approval 声明、审批中断挂起与可序列化 RunState 恢复（注意：本地 shell 与 apply_patch 默认不需要审批）；Anthropic Claude Agent SDK 定义五级权限评估顺序——hooks 可直接拒绝 → deny/ask 规则 → 权限模式 → allow 规则 → canUseTool 运行时回调，且 plan 模式下文件编辑与 shell 写入**即使命中 allow 规则也强制进回调**。IETF 草案补上协议层：缺键回 400、同键换载荷回 422、原请求处理中重试回 409，并要求服务端做载荷指纹检测防"换内容重放"。

**国内实践补上"写前的确定性门禁"一环。** 本地 QCon 库中 XTransfer 陈忻的金融级实践给出可直接移植的三件：其一，AST 确定性扫描基座（Sonar/PMD 行业规范+自研架构红线）先做语法级拦截——确定性、高吞吐、零幻觉，再交给 LLM 做语义复审；其二，统一代码指纹抹平不同智能体（XCR/OpenCR/Codex）的输出差异，源码注入评估跨引擎一致率 100%（548/548），使"谁写的"可归一追责；其三，专家反馈（确认/误报）持续标注回流，问题采纳率从 40-50% 提到 67%、全仓扫描从 2-3 周缩至 3-4 天——写入门禁不是一次性的闸门，而是越用越准的记忆飞轮。这与联合国大学 7 月《Agent Harness 治理报告》的结论互证：并行只并行只读工具，写入操作并行会产出不可复现的状态并摧毁后续审计依赖的轨迹。

## 三、技术竞争力

| 方案 | 写入通道形态 | 幂等/并发防护 | 审批位置 | 回滚归属 |
|---|---|---|---|---|
| Grafana Managed Sandboxes | 修复以 PR 收尾，人评审合并 | 继承 Git 语义天然可重放 | PR merge 即审批 | Git revert，归属管线 |
| Dynatrace Intelligence | 确定性 agent 执行动作 | 策略驱动工作流+审批 | 策略门（可配） | 平台内建 |
| OpenAI Agents SDK | 工具声明 needs_approval | RunState 序列化，幂等留给开发者 | 运行中断点 | 开发者自建 |
| Anthropic Claude Agent SDK | 五级权限评估+plan 模式强制回调 | hooks 拒绝在先 | canUseTool 回调 | 开发者自建 |
| 阿里云 AgenticOps（云效） | 数字分身代行提交 | 权限=使用者本人 | 开发者审核确认 | 继承 DevOps 流水线 |
| 火山引擎 AgentKit/Managed Agents | 托管执行+身份服务 | 智能体身份平台（邀测） | 组织级纳管 | 平台托管 |
| 治理框架（OWASP LLM06 等） | 授权放下游系统而非模型 | — | 高影响强制人批 | 要求预设 kill-switch |

**判读**：写入的"审批环节"已普遍收敛（调查自主、变更人批，四家事故响应厂商 2026 年夏四周内先后公布同一边界），但**幂等与并发防护几乎没有厂商内建**——两大 SDK 都把"重试无害"留给开发者，这正是 opennash 那条立场的市场空白："写工具不带幂等键和版本前置条件，就不该拿到生产权限。"竞争分野正从"能不能写"转向"写得多可靠"。

## 四、技术挑战

**其一，回滚计划不允许由智能体定义。** rajivonai 架构守则一针见血：执行智能体脚本的确定性管线必须天生知道如何恢复状态（Terraform 变量改错了就 git revert），"永远不要让 LLM 去修它自己刚造成的事故"——回滚是写入的影子，影子也必须确定性。**其二，幂等键的生成权。** 两个捷径都失效：每次调用随机 UUID 让重试变成新操作；对全部参数做哈希则因模型改写自由文本（"Refund for duplicate charge" 变成 "Refunding duplicate charge on order 456"）而哈希漂移、重复写入穿透。正确做法——键由 harness 从 run_id+步骤 ID+目标记录+业务意图字段派生，**模型完全不参与**。**其三，陈旧读驱动新写入。** 智能体基于缓存证据执行变更，写的是"世界已经不是那样"的操作；需 evidence_age_ms 类新鲜度字段 fail-closed。**其四，多步写的原子性。** 智能体一次任务常落多笔写：工具结果、会话项、任务状态、审计事件。进程在第两笔与第三笔之间死掉，恢复后的运行会看到自相矛盾的状态；跨服务无单事务时，只能显式记录操作状态并由恢复 worker 补偿（transactional outbox）。**其五，双账本分离。** 模型成功率与验证后成功率必须分列，绿色模型指标可以掩盖红色操作指标——一个"全部调用返回 200"的智能体，可能正在系统性地写坏记录。

## 五、展望与建议

1. **写入工具生产准入双证制**：幂等键 + If-Match 版本前置条件，缺一不发生产凭据；并要求载荷指纹校验防换内容重放。
2. **变更信封（mutation envelope）**：每次写入携带 intent_id、policy_digest、idempotency_key、evidence_age_ms、rollback_owner 五字段，policy_digest 在提交时刻做等值校验，堵住"计划时与提交时策略漂移"。
3. **PR 作为分级写通道**：低风险自动合并（CI 过+静默期）、中风险一人审、高风险双人+平台负责人；智能体风险分类置信度低于 80% 一律默认高风险——过度门禁损失几分钟，门禁不足损失一晚上。
4. **凌晨两点测试**：智能体的变更引发事故时，不在场的人能否在五分钟内理解并撤销？答不了，就先改变更管理模型。
5. **按证据晋升自主级**：只读→建议→审批执行→自动执行，每个动作类别凭审计记录逐级毕业，"凭证据而非凭乐观晋升"。
