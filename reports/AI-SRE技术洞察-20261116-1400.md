# AI-SRE 技术洞察（第 218 期）· 评测装置面／榜单可比性（Benchmark Provenance / Comparability）

**生成时间：2026-11-16 14:00　|　覆盖范围：2026 年（重点最近 30 天）　|　主线：第一百八十八条全新立面**

---

> **题眼**：SRE-Bench 榜单上 GPT-6 Astra 99.2%，同一榜单独立测量最高的 Claude Opus 5.5 只有 33.6%——65 个点不是能力差距，是装置差距。Grafana o11y-bench 官方直接写明「1.0 与 1.1 分数不可比」；Radar 拿下 SREGym 95.2% 的前提是拿掉 kubectl、只留它自己的 MCP 入口；Singularity-Bench 则专门造了 Breakwater 防 Agent 刷分。当榜单越来越漂亮，真正该问的是：**这个分数是在什么装置下跑出来的，换到我的环境还成不成立。**

---

## 一、发展趋势

过去 30 天，AI-SRE 评测出现一次安静的转向：行业不再只问「分数高不高」，开始问「这个分数可比不可比」。

三个信号同时出现。其一，**基准密集涌现**——SRE-Bench（262 任务，11-06 更新）、SREGym-0508（90 个真实 Kubernetes 故障，NeurIPS 2026）、Grafana o11y-bench 1.1（64 任务，10-28）、ITBench-AA、RCAtlas、Cloud-OpsBench 同台，SREGym 已被 Datadog 用作 Scout 1.0 的外部校验。其二，**自报与独立测量开始分化**：SRE-Bench 榜首 99.2% 是厂商自报、四尝试、Max(With Tools)，独立测量最高仅 33.6%（vals.ai），榜单自己标注「harness、预算、任务集会改变同一模型的分数」「单次与四次尝试不可混算」。其三，**防作弊独立成门**：11-12 的 Singularity-Bench 预印本引入 Breakwater，红队发现常规 Harbor 评测即便加了 LLM 裁判仍有奖励黑客漏洞。

一句话：**榜单正从「能力的成绩单」变成「装置的产品页」——分数首次被公开承认为配置的产物。**

## 二、技术现状

把最近的分数拆开，会发现每个数字都是一条乘积式：

**分数 = f(模型版本 × harness × 工具与权限边界 × 推理档/尝试次数 × 评分规则 × 数据状态 × 评分器版本)**

四类装置依赖决定一个分数能否迁移。

**模型与推理档维度**：o11y-bench 1.1 明确「一个模型、harness、工具集或努力级别下得到的结果，不能假设迁移到另一个」；RCAtlas 更极端——同一批事故，简单 harness（单次调用/SQL agent）PR@1 达 65–77%，硬编码 SOP 的编排 Agent 只有 16–53%，加推理档最多换来几点、却把运行时拖长可达 7 倍。

**工具与权限边界维度**：Radar 的 95.2% 之所以能核验，是因为「agent 容器里没有 kubectl、没有 kubeconfig，270 次运行的每次读写都是一次 Radar MCP 调用」——这既是可复现性的条件，也是装置选择：分数衡量的是「限定单一 MCP 入口」下的能力，不是「给它 shell」下的能力。反过来，o11y-bench 提醒带部分权限、变化的面板、真实事故压力下 Agent 表现会不同。

**评分规则维度**：ITBench-AA 对任何遗漏根因的任务直接记零；o11y-bench 1.1 把「检查 Agent 实际改了什么」写进判分，但仍承认 LLM 裁判有判断误差；SRE-Bench 的 Fully Solved（六任务全过才算）与 Capability Score（逐题计分）在同一批数据上给出两个不同的数。规则不同，排名就不同。

**数据与噪声维度**：o11y-bench 64 个任务全部是合成遥测、非真实事故；Radar 坦承「带噪声的独立榜单还没跑」。Parny 的评测指南给出的反例更直白：要专门测「无关告警是否与事故保持分离」「缺数据时是说证据不足还是照样猜」，并且「按每起事故出记分卡，而不是一个平均分」。

读表的结论很清楚：**前七行各说各话，第八行根本不进榜**。Dynatrace、Datadog 在 Forrester Wave AIOps Q4 2026 拿下 Leader（24 项标准、Dynatrace 16 项满分），那是分析师的「当前产品」打分，与 SRE-Bench 的跑分又是两套装置——Forrester 自己强调「治理重于自治」「零信任、最小代理」，恰恰说明能力分与可托管性分不能互相兑换。国内平台侧披露了认证维度（阿里 UModel 3200+ 定义、腾讯全景图谱、火山 RCA Harness 约束层），却无人公布「在何种装置下、由谁测、能否独立复现」。

## 四、技术挑战

**一是自报主导、独立稀缺。** 榜首多为 provider-reported，独立测量零星且分数断崖；采购若照榜单选，买到的是装置不是能力。

**二是装置即结论。** 拿掉 kubectl、只留单一 MCP，既让分数可核验，也把「工具权限」这个先决条件藏进了脚注。换一套工具，排名可能翻转——陶炳哲的本地数据早已给出预演：同权重同挂牌价，供应商吞吐差 23 倍。

**三是噪声与真实缺席。** 带噪榜没跑、遥测全合成，干净题的漂亮分数无法外推到 2 点的脏数据现场。

**四是评分器与作弊两个盲区。** LLM 裁判自带判断误差；Breakwater 需五项防护（查环境二进制、路由阻断、终止进程、外部日志隔离、受限执行）才能挡住已测攻击——这等于承认：**一个分数可能同时是「被高估的」和「被刷出来的」**，而计算可复现、结果可复现、抗操纵是三件独立的事。

**五是平均分掩盖类型。** 一个在数据库事故上正确、在网络事故上错误的工具，平均分毫无意义却最容易被采购看中。

## 五、展望与建议

本期提出第五类负事件家族成员——**「分数是真的，装置是隐的」**：动作全对、流程合规、退出码 0，只是这个数字在换装置后不成立。建议新增 `bench.provenance.*` 字段族（**第 156 个市场空白、第 122 次无人提字段**）：

- `harness_version`：框架及版本、推理档、尝试次数；
- `tools_scope`：工具集与权限边界（含是否限定单一 MCP 入口）；
- `scoring_rule`：评分规则（零分制/逐题分/Fully Solved）；
- `data_regime`：合成/真实、带噪/无噪；
- `measurement_source`：自报/独立、评分器版本与可比性类别。

**落地三步**：① 任何外部分数进采购材料前，先补一行「装置脚注」，缺装置声明的一律标 `PROVENANCE_UNKNOWN`、不作比较依据；② 用自家 20 起历史事故做同一装置的 A/B 对照（类比 207 期盲测），只比同装置下的相对排名；③ 每次模型/harness/评分规则变更触发复测，并把「与上一版不可比」写进发布说明（对齐 127 期行为发布）。

**本地原型（第 111 期）**：**孙鹏 11「先显式化评分标准、再读取而非生成」**首次当主线——全库唯一把「评分装置」本身立为对象的实践；配 **陶炳哲 30「模型与 harness 必须联合评测、成本排序会翻转」**。判词：本地把评分标准显式化、把 harness 当自变量，联网侧 10–11 月才把「分数不可比」写成榜单脚注；**两边都没把装置参数做成可导出的字段**。

判词收束：**榜单、跑分、Leader 认证、基准分全部可采购可引用，举证「这个分数在何种装置下产生、换到我的默认配置还成不成立、两次分数能不能比」不可采购。**
