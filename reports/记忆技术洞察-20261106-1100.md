# 记忆技术洞察（第 8 期）｜2026-11-06 11:00

> 系列定位：AgentMemory 领域每小时技术洞察，聚焦 2026 年（尤其近 30 天）。前七期主线：写入侧独立化 → 负空间 → 可寻址性 → 切分 → 净现值 → 插座化 → 空集。七期共享一个从未被写出的前提：**记忆只有一个作者**——一个 Agent 顺序地写、顺序地读。本期拿掉这个前提。

## 一、发展趋势：从"写进去"到"写者之间谁说了算"

第一，单写者假设在部署层已经失效，且被三股力量同时推翻：**扇出**（主 Agent 拆子 Agent 并行，一个任务多个写入点）、**多端**（同一用户手机与网页同时写同一份画像）、**团队**（多人多 Agent 共库）。信号很密：TencentDB 本月把 Team Memory 推成 Beta，配三级角色与四档可见性（private/team/restricted/agent-specific）；Hy-Memory 的 MemHub 1.0.6 加入 CLI/API **多用户支持**；连社区插件 dsh-memory-evolve 也把"多设备/多用户部署"写进版本页。

第二，定位话术变了。TencentDB 给了一句很准的对照：**"RAG 只回答'能不能找到'，Team Memory 还要回答'谁能用、哪一版有效、哪个 Agent 该拿到'"**。"找到"已被商品化；"哪一版有效"正是并发问题——它预设同一属性有多版本，且须有人裁决。

第三，真正的技术信号来自意外之处：代码编辑器。Zed 的 DeltaDB 把 Agent 上下文拆成 CRDT，本地落 SQLite，用 DAG 连接，每个节点一个 delta，断网可先写后同步，一张 DAG 可停驻多个 frontier。其取舍值得照抄：**不用版本向量**，因"参与者短命——人和 Agent 不断进出，计数写入后不能丢，向量只会膨胀"；改用因果祖先查询；血统与载荷分离。

第四，判据从"哪个对"变成"为什么两个都在"——缺的不是更强的消解算法，而是**把未消解状态表达出来的接口**。

## 二、技术现状：三种并发、五型冲突、三代解法

**2.1 三种并发形态，三种不同的失败**

| 形态 | 场景 | 冲突性质 | 正确解法 | 现状 |
|---|---|---|---|---|
| 扇出 | 子 Agent 并行写同任务 | 同值多份（重复写） | 幂等 + 唯一键 | 部分有 |
| 多端 | 同用户多设备 | 同属性异值、乱序到达 | 因果序 / 逻辑时钟 | 几乎无 |
| 团队 | 多人多 Agent 共库 | 同属性异值、**可信度不同** | 权威裁决 + 未决态 | 起步 |

三者产物不同：扇出→重复条目（浪费存储、干扰检索）；多端→**旧值覆盖新值**（用户看到"记错"）；团队→**低可信值覆盖高可信值**（错误扩散全组）。一个机制解三种，只解一种。

**2.2 冲突五型，第五型被系统性忽略**

前四型是数据库的老朋友：**覆盖型**（读-改-写非原子）、**分叉型**（两条并存且都高置信）、**竞态型**（写序与因果序不一致）、**幽灵型**（读到中间态）。第五型记忆特有：**失支型**——上游事实变了，被矛盾的那条改了，但由它派生的信念、计划、动作仍被接受，尽管已失支撑。

StateGraph（arXiv:2611.02912）把这件事做成了标题："状态变更是局部的，其后果不是。"它用反事实验证恢复依赖边——问"若前提消失，下游还能活吗"，把"支撑依赖"与"语义相关"分开，只在严格依赖失败且无独立支撑路径时失效。自建 StateChangeBench（50 例，标注级联深度）上，Impact-F1 深度 1 领先 CUPMem 复现 6.9pp，深度 3+ 领先 26.0pp。梯度说明：**越深的派生越没人管，而越深的派生越危险**。第五型是并发的时间维度——写入瞬时、支撑持续；并发控制不该只在写事务里做，还要在派生链上做。

**2.3 三代解法，各自漏了什么**

第一代是数据库老答案：唯一约束准入、乐观锁回写、写入边界决策。腾讯云那篇说得很直接——"把这三样放进共享存储，比在 Prompt 里写'请注意不要重复劳动'有效一万倍；模型会忘记嘱咐，数据库不会违反约束"。某助手真实 issue 印证：写入是"先查有无同类，有则更新无则插入"，两轮对话几乎同时到达，两进程都查到"没有"，双插入后一条被模型抽成"南京"，用户就看到 Agent 在杭州与南京之间跳。修法不是调检索，是补"同一实体同一属性唯一"。

第二代是逻辑时钟与 CRDT。一个生产案例拆得干净：手机时间误差可达 ±2 秒，抓包显示手机端 10:00:00.123、网页端 10:00:00.125，但网络延迟使服务端**先收 .125 再收 .123**，手机的"偏好科技股"被网页的旧"偏好消费股"覆盖且无法复现；引入向量时钟后可识别"不可比"并转冲突流程，代码只多约 200 行。另一套四层架构放弃强一致，用 LWW + Lamport 时钟 + clientID 决胜，2 万并发收敛 300ms 内。判据由此清晰：**金融类不可接受"大概率正确"，助手类可接受"最终一致"**。

第三代把"分叉"当正常结局。MINDSET（2610.08586，11-03）把新片段归入四种状态转移之一：强化 schema、取代当前状态、**创建情景分支**、另起新 schema；能量分平衡一致性/矛盾性/历史保留/碎片化，稳定性规则防孤立矛盾推翻既有记忆；LongMemEval 知识更新 69.23% 对 Vector RAG 64.10%。MEMOIR（2611.07631，11-05）从另一头补：压缩前用 screening gate 检验"答案相关证据是否还在"，100 次审计合并 0 观测损失、95% 上界损失率 2.95%。共同点——**合并与取代都必须留下可审计判定，而不是只留一个更短的结果**。

**2.4 六个指定项目本期状态**

- **Hy-Memory / MemHub**：`hy-memory` 2.0.14；MemHub 1.0.6 加 11 语言、lite/pro/ultra、**CLI/API 多用户**、写入重试与 provider 宕机暂停。多用户只到账号隔离，无跨用户冲突策略。
- **TencentDB Agent Memory**：Team Memory Beta 快迭代，三级角色 + 四档可见性；L0→L3 分层、四类资产。并发语义仍是版本覆盖，未公开冲突检测。
- **OpenViking**：v0.5.2.1，41.6k★。`peer` = git identity（origin URL 归一化），使同一仓库跨子目录、worktree、clone、机器保持同一 peer，fork 因 origin 不同而分开；`recallPeerScope: all` 扫用户下所有 peer。
- **ReMe**：0.4.1.11 + DSH 插件 0.1.2（registry 11-04 更新，版本未变）。纪律是"从源重建派生索引，永不迁就索引改写源记忆"。多 Agent 共享靠文件层，无写冲突协议。
- **dsh-memory-evolve**：新增无限画板、技能自我进化、跨工具会话搜索。多设备部署只提供"远端版本检测 + 红点"，**能提示版本不一致，不能消解内容冲突**。
- **ReMe2Ops**：仍无独立实体，按 ReMe 运维化路径理解，本期无新进展。

**2.5 一条被忽略的前置：身份先于锁**

冲突率的分子分母都由身份解析决定——先有"谁和谁算同一个写者"，才有"什么算冲突"。OpenViking 用 git identity，TencentDB 用 Agent 实例加角色，MemHub 用账号，BreachWeave 把写权限收口到单一 Manager（独立 JSON + rename 原子写 + 目录锁）。四者都在回答同一问题：**作用域边界画在哪。**画窄则真冲突漏检，画宽则无关 Agent 互相覆盖。而评测里这一点没有任何变量。

## 三、技术竞争力：并发能力与市场地位基本无关

| 方案 | 写者模型 | 冲突检测 | 冲突结局 | 失支处理 | 身份解析 | 可举证 |
|---|---|---|---|---|---|---|
| DeltaDB（Zed） | 多（人+Agent） | CRDT + 因果 DAG | **保留分叉**（frontier/timeline） | 血统图可查 | 每 delta 带作者 | 血统/载荷分离 |
| MINDSET | 单会话多轮 | 能量分 + 稳定性规则 | **四态**：强化/取代/分支/新 schema | 无 | 无 | 版本化 schema |
| StateGraph | 单写者 + 依赖图 | 反事实验证 | 仅失效严格失支者 | **唯一显式** | 无 | 依赖边 + 反事实 |
| MEMOIR | 单 | 合并前 screening gate | 合并 / 不合并 | 无 | 无 | 100 次审计合并 |
| TencentDB | 团队多写者 | 无公开机制 | 后写覆盖 | L0 删不传播 L1 | 实例 + 角色四档 | 元数据/内容分离 |
| Hy-Memory | 多用户（1.0.6） | 未见 | 图式归纳覆盖 | 无 | 账号 | diff 链（代码侧） |
| OpenViking | 多设备/多仓库 | 未见 | L1 覆盖 | 无 | **git identity** | 路径历史 |
| ReMe | 多 Agent 共享 | 文件层（隐含） | 人改优先 | 无 | workspace | Markdown diff |
| dsh-memory-evolve | 多设备/多用户 | 版本号比对（仅提示升级） | 后写覆盖 | 归档不注入 | 无 | 五轨文件 |
| BreachWeave | 多 Solver 并行 | 目录锁 + 单写者收口 | 写权限收口 | 无 | Manager/Solver | 假设状态机 |
| Mem0 | 多（三级作用域） | 未见 | LLM 判定增删改 | 无 | user/agent/session | 无 |
| Zep / Graphiti | 多 | 双时序边失效 | 边失效（留历史） | 部分 | group_id | 双时序 |

三条读法。**其一，有并发语义的四个方案里三个不是记忆产品**——DeltaDB 来自编辑器，其余三个来自论文；装机量最大的几个恰在"后写覆盖"档。**其二，"保留分叉"只有 DeltaDB 做到产品级**，记忆产品全军单主干。**其三，唯一显式处理失支型的是 StateGraph，而它连产品都不是**——清晰空位。

## 四、技术挑战

**其一，LWW 的正确性依赖一个不可信的全序。**"后写覆盖"隐含三前提：全局可比时钟、同一作用域、权威可传递。多写者下三个全不成立——时钟漂移是常态，作用域由身份决定，"后写更可信"在团队场景常恰好相反（新手 Agent 覆盖专家结论）。

**其二，存储顺序不等于事实权威。** 这是本月最锋利的一句工程判据（PLUR 验收测试）：即使写入完全串行、版本号严格递增，也推不出"后写那条在事实层面更可信"，因为两个写入者可能都没有证据压过对方。该测试让两会话同时从 R0 提出 Casey 与 Riley，正确答案是"待确认"而非二者之一；三层证据（写入响应 / 冲突元数据 / 新会话答案）缺一即判失败。

**其三，"未决"进不了 API。** 写入只有成功与失败两种返回，系统被迫二选一：静默覆盖（丢信息）或拒写（阻塞 Agent）。务实原则是**"宁可保留存疑的预约，也不要轻易删除——停滞比事故便宜"**，但要落地需 `status: conflict + candidates + revisions + requires` 这类返回值，目前零实现。这与第 7 期空集同类：`[]` 之外还需要 `[?]`。

**其四，冲突没有评测位。** LoCoMo、LongMemEval、BEAM、MemArena、AML 二期全为单写者串行设定；MemArena 信任维度只测权限越界。全领域只有 PLUR 那把夹具把"两会话同改一条"当可验收项。没有变量就没有供给动机，与第 7 期"评测切掉弃答"同构。

**其五，与删除/血统的交叉未被讨论。** 一个写者 `forget` 一条记忆，另一个正基于它生成派生——删除传播与失支的乘积，无人处理。分支的存储代价同样空白：DAG frontier、快照钉住、分支回收，GC 语义尚不存在。

## 五、展望与建议

**第一，把"裁者"请出来。** 记忆系统有写者、有读者，没有裁者；冲突时系统自任裁者，却缺少裁决所需的信息（谁的证据更强）。可行路径是让裁者外置为显式角色（人或策略引擎），系统只负责把冲突完整摆到裁者面前。

**第二，目标从"收敛"改成"可解释的分歧"。** 记忆的正确性判据本身是概率性的——同一用户不同时间说不同话，两条都真。用收敛性做 KPI 只会逼出"静默择一"。可解释分歧的判据是：任一时刻能说清为什么这几条都在（作用域、时效、说话人、证据）。

**第三，写侧三条不变量可直接进规范。**①同一实体同一属性任一时刻最多一条有效记录（唯一键 + upsert）；②任一有效记录必须能指回支撑；③写入必须携带因果前置（last-read revision），不可比时拒绝而非覆盖。

**第四，采购侧加一项两会话夹具。** 虚构事实、两独立会话、同一 R0 起点同时提交矛盾更正，看三件事：两条是否都还在、冲突元数据是否可读、新会话是答"待确认"还是硬选一个。**无法暴露冲突的集成，只能按单写者工作流验收。**

**预测**：12 个月内会出现"记忆分支"作为独立原语（对齐 DeltaDB 的 timeline / MINDSET 的 contextual branch），并伴随第一个把 `unresolved` 写进返回值的记忆 API；配套评测维度是"冲突检出率 + 未决表达率"，而非准确率。## 参考来源
