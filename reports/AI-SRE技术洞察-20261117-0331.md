# AI-SRE 技术洞察（第 239 期）

**生成时间**：2026-11-17 03:31（Asia/Shanghai）
**观察窗口**：2026 年内，重点 2026-10-18 至 2026-11-17（近 30 天）
**本期主题**：触达面／告警送达（Notification Delivery）——告警产生了，不等于人知道了

## 题眼

- **PingParrot（2026-09-05）**：一条推送是**最佳努力投递，不是保证送达**——手机静音、勿扰模式、没电、通知横幅只显示六十秒就滑进没人看的通知中心，任何一环都能让 P1 无声消失；**IETF 定义推送的标准也只保证事件到达用户设备，不保证用户确认**。它的结论很硬：**“重复直到确认”优于单次推送**。
- **fivenines（2026-08-15）**：给出可操作基准——大多数生产服务的**首次确认时间（TTA）应低于 5 分钟**，**误升级率低于 5%**；并在时间轴上写清“第 5 分钟升级到备份、第 10 分钟叫团队负责人”，**按属主路由而不是按方便路由**。
- **AlertOps（2026-08-18）**：P1 在凌晨两点触发、ServiceNow 记录完美，值班工程师的手机却面朝下躺在勿扰里；**“给睡着的人打一个电话”不叫寻呼策略**——多通道、持续升级、确认直到有人应答、以及一个可靠的邮件转短信替代品。
- **PagerDuty 文档（2026-06）**：`dedup_key` 去重、事件编排抑制、按严重级别动态通知——这些机制解决的是“别发太多”，**不解决“发了有没有到”**。
- **PostHog PR #74876（2026-07-30）**：给告警加**送达 SLO 监控**时踩到真问题——每次告警发送阻塞共享线程池最多 10 秒，并发告警会耗尽池子、拖垮无关任务；**等待确认本身要隔离、要有界**。

## 一、发展趋势

**从“告警质量”转向“送达质量”。** 过去两年行业把力气花在降噪：去重、抑制、动态通知、告警分级（第 139 期）。但 2026 年的几份实践材料把镜头往后移了一格：**告警产生了，不等于人知道了**。PingParrot 说单次推送是最佳努力，fivenines 把 TTA 与误升级率写成指标，AlertOps 说“叫醒睡着的人”需要策略而不是一次电话，PostHog 发现“等确认”会堵塞共享资源。四条线指向同一个判断：**送达是一个独立的可靠性环节，需要自己的 SLO、自己的降级链、自己的证据**。

## 二、技术现状

**送达是一条链，不是一次动作。** 告警产生 → 路由（按属主/严重级别）→ 通道（电话/短信/IM/邮件）→ 设备（推送/铃声/勿扰）→ 人（看见/理解）→ 确认（ACK）→ 升级（超时）。**每一跳都会丢**，而多数团队只监控第一跳和最后一跳。

**“重复直到确认”是当前最有效的工程手段。** 单次推送把可靠性押在“人正好在看手机”；重复+升级把可靠性押在“总有一次会被看见”。代价是必须处理重复通知的风暴与误升级。

**通道健康几乎无人监控。** 邮件转 SMS 网关、第三方短信、电话线路、IM webhook 都会静默失败；它们不在你的 SLO 里，却决定 P1 能不能到人。

**确认（ACK）是送达的唯一证据。** 没有 ACK 的“已发送”只是日志里的一行字；TTA 才是可运营的指标。

**Agent 也开始发通知。** Agent 发 Slack、开工单、打电话——**它发的通知谁确认？** 如果 Agent 只记录“已通知”，它与“已发送”一样不可举证。

**判读**：电话、短信、推送、IM 都是货架能力；**“这条告警在第几秒到达了谁的哪台设备、谁在第几秒确认”没有一家把它做成逐跳可查的证据**。本期反转：第 139 期说“告警的信噪比是运维质量的第一道闸”，本期补一句——**闸后面还有一段路，路也会断**。判词：**「告警平台」「短信」「电话」「IM 机器人」全部可采购，「举证这条告警逐跳到达并被谁确认」不可采购**。

## 四、技术挑战

1. **单次即最佳努力**：推送标准只保证到设备，不保证看见；静音、勿扰、没电、横幅过期都是合法失败。
2. **重复与风暴的平衡**：重复直到确认会放大通知量；按告警去重不够，要**按事故去重**。
3. **通道静默失败**：网关、线路、webhook 坏了没人知道，因为它们不在业务 SLO 里。
4. **误升级伤信任**：误升级率高于 5% 会让值班人学会忽略升级。
5. **等待确认会占资源**：同步阻塞等 ACK 会拖垮共享池（PostHog PR 的真实故障）。
6. **Agent 通知无回执**：Agent 说“已通知”时，往往只有发送日志，没有送达与确认。

## 五、需求分解、用户旅程与实现方案

**需求分解（P0→P3）**
- P0 送达 SLO：`delivery_success_rate`、`p95_delivery_latency`、`ack_rate`、`tta_p95`、`false_escalation_rate`。
- P0 逐跳回执：告警 ID → 路由决策 → 通道 → 设备 → 人 → ACK，每跳落 `notify_hop`。
- P1 重复直到确认：按事故去重（`incident_key`），未 ACK 按 TTA 阶梯重复。
- P1 通道健康：对每个通道做主动探针（合成告警），失败自动切换下一通道。
- P2 升级策略：按属主路由、按严重级别分级、误升级率纳入复盘。
- P3 Agent 通知回执：Agent 发的每条通知必须绑定 ACK 与超时兜底，否则视为未送达。

**用户旅程（四条）**
1. 凌晨 P1：电话+短信+IM 三通道并发，90 秒无 ACK 升级备份，5 分钟叫负责人；全程留逐跳记录。
2. 主通道静默：合成告警发现短信网关失败，自动切电话并在状态页标注通道降级。
3. 值班人误点“稍后”：不算 ACK，按未确认继续升级。
4. Agent 开工单：工单系统返回受理号才算送达，超时未受理转人工并记录“Agent 通知未确认”。

**90 天实现方案**
- 第 1–3 周：埋点逐跳回执与五项 SLO，先量出当前 TTA 与误升级率。
- 第 4–6 周：重复直到确认 + 按事故去重；等待 ACK 改为异步、有界、隔离线程池（吸取 PostHog 教训）。
- 第 7–9 周：通道健康探针与自动切换；夜间/安静时段策略。
- 第 10–13 周：Agent 通知回执规范；季度演练“主通道全断”与“值班人全程不响应”。

**第 167 个市场空白（五项）**：`notify_hop` 逐跳回执覆盖率、`delivery_slo` 送达 SLO 覆盖率、`ack_rate` 确认率、`tta_p95` 首次确认时间、`false_escalation_rate` 误升级率。`notify.*`／`delivery.*` 为**第 133 次无人提字段族**；本地 173／173-kb 连续第 123 期成组启用（蒋炎炳 23 把交接写成“签字确认”，本期重读为：**交到了不等于对方收到了**——本地对“确认”的直觉是对的，但同样没有把“送达”做成逐跳可查的证据）。
