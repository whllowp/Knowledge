## 题眼

11 月 13 日 Netflix 公开其可观测性本体与知识图谱架构，有一处反直觉的设计：**他们拒绝在图谱里使用通用的 `Service` 实体类型**，理由是"每个工具对 service 这个词的理解都不一样"。取而代之的是单一 `ops:Application` 类型，每一条都拿约 49,000 条软件目录校验，校验不过的实体根本不许进图。同期 Datadog 的 Bits 文档写得更直白：告警给服务打的是 `billing-svc`，APM 与日志用的是 `billing_service`，必须写一条规则把它们认作同一个；没有 service tag，Agent 就只能退回"监控器名称"这种弱信号。

**此前 286 期把知识图谱、根因图、服务拓扑当作背景板反复引用，却从未把它本身立为一等对象——更没问过一句：这张图里的节点，凭什么就是同一个东西?** 本期首次把"实体消歧"立为一等对象，只问一件事：指标库、日志主题、链路 span、配置记录、CMDB 里那个名字，指向的是不是同一个生产实例。与往期划界：#237 基数面问"标签有多少种取值"、#254 日志面问"记录是自述还是观测"、#284 外部依赖问"上游声明 vs 自有探针"、#262 数据龄期问"证据多旧"——本期都不问，只问**这条边连的是不是对的那两个节点**。索引中"实体消歧""同物不同名""命名漂移"均为 0，全新立面确认。

## 一、发展趋势

三条方向在最近 30 天合流，把"服务身份"从数据建模细节推成 Agent 正确性的地基。

**其一，头部公司开始把关系本身当一等数据。** Netflix 的架构把应用、事故、部署、告警、基础设施依赖连成 RDF 三元组，存储于自建的 QuipuDB（基于 Rust redb）；enricher 管道一部分确定性生成、一部分用 LLM 解释非结构化信息，输出统一经 SHACL 校验——实体类型、URI 命名、软件目录对不上就拒收。关联引擎跨 13 类信号、以 10 分钟时间窗按接近度与严重度打分，低于 0.6 的链直接丢弃。支撑 AutoRCA 的关键决定是：**专家 Agent 之间不直接互发消息，而是通过图读写同一批类型化实体**——本体成了接口，直接通信会造成紧耦合与 schema drift。

**其二，身份标准在收敛，但框架层仍是一片空白。** OneUptime 9 月的治理指南给出规范：同一负载在 trace 里叫 `checkout-api`、在 metrics 里叫 `checkout`、在日志里是 `app=cart`，跨信号关联必然失败；应当用 `service.name`／`service.instance.id`／`service.version`／`deployment.environment.name`／`k8s.*` 组成的规范属性集，并给每个字段指定唯一权威来源。SDK 回退出的 `unknown_service:<进程名>` 在生产环境应视为质量事故。但 11 月 10 日的框架横评显示：Claude Agent SDK 无 agent identity 概念、自身不产遥测；OpenAI Agents SDK 稳定版同样没有身份概念，原生 OTel 导出仅在 11 月的预览构建里；Google ADK 是少数会把 Agent Registry 标识写进遥测的。标准在数据层收敛了，在 Agent 层还没开始。

**其三，服务目录的角色被改写。** 分析 Datadog、SigNoz、Elastic 三家后的判断很到位：服务目录过去是"给人看的资产台账"，评价画得全不全；现在它是"给机器读的检索索引"，评价标准变成 AI 能不能查得到、查得对、查得快。Elastic 11 月 4 日发布的 nightshift AI SRE 把知识图谱连到 GitHub 源码，直接指认"可能是哪次提交引入了异常"，并把调查记忆逐次累积——图谱从静态资产台账变成了会长的记忆体。

## 二、技术现状

当前栈在"画图"上已经产品化，在"图中的节点是否为同一实体"上普遍留白。

**跨入口对齐是根因准确性的显式前提。** 腾讯云 11 月一篇工程文章把它列为"模型越强越准"成立的第一前提：**指标库里的服务名、日志主题里的服务名、配置项记录里的服务名，必须能对齐到同一个实例**；做法是给指标关联模型标识与实例标识、给链路关联服务标识与实例标识，再用统一标识把资源拓扑与调用拓扑接起来，确实缺标识时用 IP／端口／MAC 物理主键兜底。同一篇文章给出一组冷数据：在多智能体根因系统里加入专门的"证伪"角色后，单服务故障定位准确率从 21.3% 升到 33.3%；而 2026 年一项云环境实证把失败归到三处不透明，其中一处正是"智能体之间用自然语言摘要交接导致细节丢失"——**实体在交接中被悄悄换了**。

**异名同物是常态，且靠人肉规则兜。** Datadog 把"跨系统名称映射"列为 `bits.md` 的第一优先级，并强调要写成 rule 而不是 description：描述只是复述 Agent 从遥测里本来就能推断的东西，规则才解决它推断不出的命名错配。它同时警告陈旧 runbook 链接"比没有链接更糟，因为它把 Bits 指向错误的看板或已下线的服务"。满帮基于阿里云 AgentCore 的生产实践走了另一条路：把应用、接口、中间件、基础设施档案与稳定性规则、业务关系关联，粒度细化到接口级，先确定异常所属业务再沿知识图谱收窄，宣称核心链路根因定位中位数 1 分钟、准确率大于 90%（厂商自述）；其中取证与确定性判定由代码规则执行、过程可抽检，这一点与本期"身份要有出处"同构。

**有的方案选择不建图。** SigNoz 的 Service Map 由 OTel trace 自动派生：节点是被观察到的依赖端点，只有 span 能配出 caller 与 callee 才画节点，服务身份直接来自 `service.name` 语义约定；其 MCP server 提供 40+ 工具，官方称 OTel 原生属性让 Agent 用更少 token 做更可靠的根因追踪。IBM Instana 则用 `service.name`＋`service.instance.id` 把 span 链到 OTel 实体，再经 `k8s.pod.uid`／`container.id`／`process.pid`＋`host.id` 链到基础设施实体，并明确要求同一服务的 metrics 与 traces 的 resource 属性一致——它同时承认一个坑：K8s 里 SDK 给的是容器内 PID，而 Instana 实体用的是宿主 PID，这条链在容器里并不可靠。

## 三、技术竞争力（主要厂商／方案对比）

以"实体消歧"维度重排格局。"建图／接目录／导 OTel"人人都报，"身份出处／别名批准人／边何时观测"两列几乎全空。

| 方案／厂商 | 身份主键 | 跨系统异名对齐 | 实体写入校验 | 别名/边可举证（谁、何时、证据） | 对 Agent 的接口 | 判断 |
|---|---|---|---|---|---|---|
| Netflix 本体＋AutoRCA（11-13） | 单一 `ops:Application`＋约 49,000 条软件目录 | 拒绝通用 Service 类型，从定义上消歧 | SHACL＋URI 规范＋目录校验，不过不进图 | 强：事故讨论中的假设、被否解释、缓解决策回写图中 | 强：本体即接口，Agent 通过图通信而非互发消息 | 唯一把"实体类型不统一"当架构前提解决 |
| Datadog Bits Investigation（10 月）＋`bits.md` | service tag＋监控器 id | 强：`billing-svc`↔`billing_service` 写成 rule 而非 description | 弱：靠 monitor hygiene 与 runbook  pruning | 中：反馈要求点名根因、服务与指标并链证据 | 中：四类知识源可见，但依赖目录治理 | 异名对齐最工程化，出处与审批仍靠人 |
| Google Knowledge Catalog／Agent Registry（11-13/15） | 联邦元数据＋血缘＋Agent Registry 标识 | 强：业务定义＋信心分，权限检查后检索，不搬数据 | 中：人工核准的 context 才向 Gemini 推广 | 中：有血缘与可信指标，别名批准人未成字段 | 强：ADK 把 registry id 写进遥测 | 上下文最全，偏业务语义非运维实体 |
| SigNoz Service Map＋Noz MCP | OTel `service.name`＋trace context | 弱：身份仅来自语义约定，无跨源别名层 | 弱：只有能配出 caller/callee 的 span 才画节点 | 弱：边是时间窗聚合，无独立证据对象 | 强：OTel 原生属性、40+ MCP 工具、token 省 | 最轻，把消歧责任推给插桩质量 |
| IBM Instana OTel 关联 | `service.name`＋`service.instance.id`＋宿主/Pod id | 中：显式映射链到 k8s／容器／进程／主机实体 | 中：要求 metrics 与 traces 的 resource 一致 | 弱：容器 PID 与宿主 PID 不匹配即断链 | 中：实体链自动建，跨云需逐项核对 | 基础设施关联最细，容器边界仍脆 |
| 满帮×阿里云 AgentCore（11 月） | 应用／接口级业务档案＋图谱 | 中：先识别业务归属再沿图收窄 | 中：确定性判定由代码规则执行、可抽检 | 中：采集与判定可追溯，身份来源未披露 | 中：诊断建议≠执行授权，四类预设自愈动作 | 业务归属先行，是消歧的国产务实路线 |
| 腾讯云 AIOps 统一图模型（11 月） | 模型标识＋实例标识＋物理主键兜底 | 强：明写"三个入口同一对象"为准确性前提 | 中：资源拓扑与调用拓扑以统一标识关联 | 弱：边的观测时间、身份变更记录未成字段 | 中：证据链可逐条核对，绑定平台 | 最直白点破前提，字段化尚未完成 |
| Anthropic／OpenAI Agent SDK | 无稳定 agent identity 概念 | 无：身份由宿主 IAM 主体或 API key 顶替 | 无：SDK 自身不产符合 GenAI 约定的 agent span | 无 | 弱：OTel 导出仅限预览构建／第三方插桩 | 模型最强、身份最弱，税留给集成方 |

## 四、技术挑战

**第一，异名同物与同名异物同时存在。** `billing-svc` 与 `billing_service` 是异名同物；生产的 `orders` 与预发的 `orders` 是同名异物。前者让证据被拆成两半，后者让证据被错误合并——而错误合并更危险，它会把无关证据拼成一个自洽的解释。环境标签与稳定资源标识不是装饰，是消歧的最小必要字段。

**第二，别名是无人署名的语义决策。** 一条"`billing-svc` 等于 `billing_service`"的规则由谁写、何时写、依据什么写、服务拆分后是否还成立——现有系统普遍不记。这与 #237 预聚合那类"无人署名的语义决策"同构，但后果更重：基数错了丢的是分组，身份错了丢的是整条因果链的指向。

**第三，边会过期。** 一条"服务 A 依赖服务 B"的三元组可能属于三个月前已下线的部署。每条连接都该回答"什么证据确立了这条关系、什么时候观测的"；缺少时效标注的图会把历史路径当成当前路径，而任何新增信号都能在上面走出一条通顺的解释。

**第四，多 Agent 交接处身份漂移。** 2026 年实证把"用自然语言摘要交接导致细节丢失"列为三大不透明之一。Netflix 的解法值得细看：Agent 不互发摘要，而是把类型化结果写回同一个本体。本质是把身份契约当接口——**可替换的是 Agent，不可替换的是实体的定义**。

## 五、展望与建议

**把实体解析做成一等字段。** 提出第 208 项市场空白 `entity.resolution.*` 五字段：`entity_canonical_id`（稳定标识，不是名字）／`identity_tuple`（name＋environment＋instance＋version）／`identity_source_per_field`（逐字段权威来源）／`alias_edges[]`（跨系统别名，带批准人、生效时间与证据）／`resolution_confidence`＋`resolved_at`（解析把握与观测时刻）。缺省 `IDENTITY_UNVERIFIED`，不进自动执行门禁——与 #286 的 `EVIDENCE_CUSTODY_UNVERIFIED` 同构，先能举证再谈自动化。

**给目录换一套验收标准。** 不再问"画得全不全"，改问三件事：AI 查不查得到、查得对不对、查得快不快。把 `unknown_service:*` 列为质量事故；给每个身份字段指定唯一权威来源，禁止应用默认值、Helm release 名、抓取 job 与日志代理重映射相互竞争；OTel resource 到后端标签的映射是实现配置而非标准，必须拿真实导出数据回归验证。

**把别名当变更管。** 名称映射进配置库并署名，服务拆分／合并时触发映射复核；诊断报告强制写明"这条日志、这次部署、这个指标属于哪个实体、依据什么标识认定"。在评测集中增设两类题：同名异物（生产 vs 预发）与异名同物（三系统三个名字），并把 Datadog 那套"组合错误导致归因到错组件"的交互题型纳入——工具级测试抓不到它。

**信通院六维补「实体可举证率」一格**：统计有多少比例的根因结论能逐条说明实体身份来源、别名批准人与边的观测时间。

**本地知识沉淀。** 本期新角度取自 173 讲义中蒋烁淼《千亿数据秒查到真正的 AgentOps》——把"统一数据模型与预聚合"重读为"**身份先行于查询**：没有稳定身份，秒查只是更快地查错对象"；配赵恒《AI Native 数据语义层》的可执行 Semantic Runtime，把"服务"定义成可执行语义而非字符串；再配刘凯宁蚂蚁 SRE"结论／证据／待确认项"三分，扩出第四分——**这段证据属于哪个实体，凭什么认定**。
