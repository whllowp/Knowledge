# AI-SRE 技术洞察（第 252 期）

**生成时间**：2026-11-17 15:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-10 至 2026-11 的公开材料
**本期主题**：多语言面／非英语可靠性（Multilingual Reliability）——英文跑通的 Agent，换个语言就换了个产品

## 题眼

2026 年 ACL 长文《Lost in Execution》给出一个很窄但很致命的结论：在中、印地、伊博三种语言上测工具调用，大量失败不是「没听懂」，也不是「选错工具」，而是**参数值的语言不匹配**——模型把该填服务名、枚举、时间的地方，填成了用户的语言。同一时期，EACL 2026 Findings 的 MAPS 基准发现多语言 Agent 在性能与安全上同时退化；另一篇 ACL 2026 论文把多 Agent 内部统一用英文的代价量化为统计显著的「English-Forcing Tax」（四种语言各 300 条样本）。工程侧的证据更直接：Tessellate 仓库 2026-10-05 的审计注释写着，CJK 约一字一 token，按「四字符一 token」估算会让上下文超窗最多四倍，而 Ollama 从前端截断——先丢的是系统提示和 grounding 规则。英文正常的 Agent，中文先丢规则。

## 一、发展趋势

第一条线：多语言从「界面翻译」变成「契约适配」。过去的本地化是文案与日期格式；Agent 的本地化是工具 schema、枚举值、实体名、单位、时区在调用前被规范化成同一套契约。翻译解决人看得懂，规范化才解决机器填得对。

第二条线：评测从「多语言理解」转向「多语言执行」。MMLU 式的选择题分数只说明模型认识这个词，不说明它能把一句指令填成正确的工具参数。MLCL、MAPS 这类基准测的是执行与安全，这才是运维在意的部分。

第三条线：token 经济学开始区分文字系统。CJK 与拉丁字母的 token 密度差 2–4 倍，这是 2026 年多个开源项目在补的 bug：估算器按字符数除以四，中文预算被低估 8–12 倍。对 Agent 而言，这不是账单问题，是**上下文截断顺序**问题。

## 二、技术现状

把 2026 年的材料按故障位置摆开，多语言 Agent 的失效集中在四个点：

**其一，参数值语言不匹配。** MLCL 的错误分析显示，意图理解正确、工具选择正确，失败发生在参数生成：用户用中文说服务名，模型把中文名填进要求英文枚举的字段；或者把「明天上午十点」写成自然语言而不是 ISO 时间。更危险的是「成功执行错对象」——工具接受了这个值，动作落到了另一个资源上。

**其二，翻译引入的实体合并与锚点错配。** LILT 2026-03-12 的分析给出机制：亲属称谓在韩语中被合并成一个词、版本锚点与指针在翻译后指向不同词，模型于是把两个版本当成两个对象，检索到过期内容。翻译不是无损的，损失会以「幻觉版本」的形式出现在运维动作里。

**其三，English-Forcing Tax。** 多 Agent 架构默认内部用英文通信，末端再回译。ACL 2026 那篇论文用四种语言、每语言 300 条样本测出这条路径有统计显著的成本，且通过 Bonferroni 校正。也就是说「内部统一英文」不是免费的抽象层，而是一项要计价的损失。

**其四，上下文预算按字符估算。** Tessellate 的审计与 hermes-agent 的 PR #59121 都在修同一类 bug：按 4 字符/token 估算，CJK 被低估 8–12 倍；Ollama 的截断策略从前往后丢，系统提示与 grounding 规则最先消失。结果是一条隐蔽的故障链：中文用户 → 上下文超窗 → 规则被截 → Agent 做出规则外动作，英文用户完全复现不了。

## 三、技术竞争力

|---|---|---|---|---|---|
| 通用 LLM 直连（英文 prompt） | 模型自带多语言 | 意图强、参数弱 | 未验证 | Lost in Execution（ACL 2026） | 参数值语言、枚举映射 |
| 翻译前置（译入译出） | 覆盖广、成本低 | 中 | 未验证 | LILT 2026-03-12 | 实体合并、锚点错配、术语 |

| 多语言执行基准（MLCL/MAPS） | 诊断工具 | 只测不修 | 只测不修 | ACL/EACL 2026 | 样本规模、生产分布 |

判读：厂商说的「支持 100 种语言」指理解与生成，不是参数值规范化，也不是安全等价。真正决定生产可用性的是有没有可测试的规范化层。

本期反转：过去把多语言当成「翻译质量」问题，现在要当成「接口契约 + 上下文预算」问题。翻译得再好，参数值不归一，动作就会落在错对象上；预算算得再准，截断顺序不对，中文用户先丢规则。多语言可靠性的单位不是 BLEU，是「同一意图在每种语言下产生同一组规范化参数」的通过率。

判词：**「翻译 API／多语言模型／本地化文案／多语言 prompt 模板」全部可采购，「同一意图在每种语言下被规范化成同一契约、上下文预算按真实 token 计、拒绝策略在各语言等价」不可采购。**

## 四、技术挑战

其一，参数空间没有语言标签。工具 schema 是英文写的，用户输入是本地语言，中间缺一层「值归一」。这层不做，模型只能猜，猜对的概率随语言长尾迅速下降。

其二，评估集的样本量与分布。MLCL、MAPS 的样本规模有限，语言覆盖集中在少数几种；生产里的语言分布往往是长尾，且混用（中英夹杂、方言、缩写）。

其三，安全策略的语言不对称。护栏与拒答规则多在英文上训练与调优，非英语下既可能误杀（连接第 248 期），也可能漏放；MAPS 已经把「性能与安全同时退化」作为结论，但还没有跨语言等价的验收标准。

其四，CJK 预算与截断顺序。估算器低估、运行时从前往后截断，两个 bug 叠加会把系统提示挤出去。修复要同时改估算与截断，并断言规则仍在上下文里。

其五，成本结构。同一任务中文 token 数是英文的数倍，按语言分桶的成本核算在多数平台里还不存在。

## 五、需求分解、用户旅程与实现方案

**需求分解**：R1 参数值规范化层（实体、枚举、时间、单位、时区五类映射，可单测）；R2 工具 schema 的多语言契约（枚举别名与后端值分离）；R3 真实 token 预算（按模型 tokenizer 计，CJK 单独校准）；R4 截断顺序策略（系统提示与安全规则永不先丢，超窗时显式失败）；R5 跨语言等价测试（同一意图 × N 语言 × 同一断言）；R6 安全等价验收（拒绝率、误杀率按语言分桶）；R7 按语言分桶的成本与配额。

**用户旅程**：中文值班员用中文下达「把支付服务回滚到上一个版本」→ 意图与工具选择正确 → 规范化层把「支付服务」映射到 `payment-api`、把「上一个版本」映射到具体 revision → 工具调用成功且落在正确对象上 → 上下文预算按真实 token 计，规则未被截断 → 若超窗则显式报错而不是静默丢规则 → 等价测试显示三语参数一致、拒绝率无显著差异。

**90 天实现方案**：0–30 天，盘点工具 schema 中的枚举与自由文本参数，建立第一批实体/枚举映射表，给参数规范化层写单测；31–60 天，替换 token 估算器为 tokenizer 实测并加 CJK 校准，改截断策略为「保规则、显式失败」，上线中英双语等价测试集；61–90 天，扩到日/韩，建立按语言分桶的安全与成本报表，把「跨语言参数一致率」纳入发布门禁。

第 179 个市场空白（五项）：①参数值规范化中间件；②按语言的真实 token 预算与截断策略；③跨语言拒绝等价验收；④术语/实体映射表的版本管理；⑤English-forcing 成本的度量口径。

`locale.*`（`param_norm`、`token_budget`、`truncation_order`、`security_parity`）／`param_norm.*`（`entity_map_version`、`enum_alias`、`time_format`）第 146 次无人提字段族：平台在卖「多语言支持」，没有一家把「这条调用在哪种语言下、哪个参数被归一成了什么」写进 trace。

本地 173／173-kb 连续第 135 期成组启用（朱革 15：中文 runbook 的枚举映射表 + CJK token 预算校准 + 截断顺序断言，三件事一起做才敢让中文值班员放手）。
