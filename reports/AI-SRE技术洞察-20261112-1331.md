**本期主题**：上下文预算面（Context Budget）——上下文不是免费的；28 个工具定义就能把 8K 窗口撑爆；截断不报错，Agent 只是开始看不懂

## 题眼

05-24 arXiv 2605.26165 把一个工程常识变成了可测的曲线：**工具 schema 和检索内容抢的是同一个上下文窗口**。作者在 14 个模型（1.5B–32B 本地模型＋一个前沿 API 模型）、6,566 次受控调用、8K/16K/32K 三档预算、28 个工具定义上做了系统实验：**8K 档位下，JSON schema 直接把窗口撑爆，平均 EM 掉到 2.6%**；换成压缩 schema（省 44–50% token）后，**平均 EM 拉回 +20.5 个点**（六个完全恢复的模型 +24.7 个点）；**而在 32K 档位、两种格式都放得下时，五个模型里四个的差距 ≤1 个点**——**说明这不是「压缩让模型变聪明」，是纯粹的预算效应**。HotpotQA 上同样场景 **+48 个点**；前沿模型上 **JSON 大约 494 个工具就溢出，压缩后 800 个以上还能跑**。**上下文不是「越大越好」的容器，是一张要分配的预算表；不分配，就被工具吃光。** **494 个工具就溢出的前沿模型，挡不住「全公司工具都接进来」的冲动。**

## 一、发展趋势

**趋势一：从「扩窗口」转向「管预算」。** 窗口再大也有上限；**真正的问题是「这 32K 分给谁」**——系统提示、工具、历史、检索、输出预留。

**趋势二：工具 schema 成为一等成本。** 150 期说「目录越大越难找」；这一期补上：**目录越大，光是「告诉模型有哪些工具」就把预算吃完了**。**工具不是免费的：每个工具都要在每轮对话里被复述一遍。**

**趋势三：截断从「性能问题」变成「正确性风险」。** 溢出与截断不报错；**Agent 会在缺证据的情况下给出一个通顺答案**（96 期合式错值）。

## 二、技术现状：五块预算，通常只算一块

**系统与工具：最容易被低估。** 28 个工具就能在 8K 档撑爆；**工具越多，留给证据的越少**。

**历史与会话：线性增长。** 多轮对话把历史越堆越长；**没有摘要/回收，预算被过去吃掉**（61 期压缩、SemaGC 一类上下文回收）。

**检索证据：被挤压的一方。** 预算不够时，检索结果被截断或干脆不检索；**Agent 看起来「没查到」，其实是「没地方放」**。

**输出预留：常被忘。** 不预留输出 token，模型会在中途被截断；**半句话的结论比没有结论更危险**。

**截断策略：最不透明。** 丢最旧、丢最低相关、还是丢中间？**不同策略对应不同失效模式**，但多数系统不声明。

**上下文有三种死法，症状不同。** 溢出（根本没放进去，EM 崩）、截断（放进去一半，答得通顺但缺证据）、腐烂（都放进去，长上下文里关键信息被稀释）；**三种都不报错，只是答案悄悄变差**。

## 四、技术挑战

**一，溢出是二值的。** 8K 档从「能跑」直接掉到 2.6% EM；**不是慢慢变差，是突然不会**。

**二，工具数量在涨。** 目录越大，schema 预算越大；**494 个工具就溢出的前沿模型，挡不住「全公司工具都接进来」**。

**三，截断不声明。** 系统悄悄丢历史/证据；**Agent 不知道自己「忘了」**。

**四，预算分配没有标准。** 系统提示占多少、工具占多少、证据占多少；**没有默认值，每个团队自己拍**。

**五，压缩有损。** 省 token 的压缩可能丢掉关键约束；**压缩后的 schema 与真实 schema 不一致，会引发参数错**（137 期）。

**六，成本与正确性耦合。** 省 token 省钱，但可能掉 EM；**账要一起算**（143 期）。

**七，多轮历史是慢性增长。** 每轮都加，**没有回收机制就会在某轮突然溢出**；溢出点不可预测。

**八，压缩与审计冲突。** 压缩后的上下文无法原样复现；**复盘时看到的不是模型当时看到的**（116 期记录-现实漂移）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `context.*` 字段**：`window`、`system_tokens`、`tool_tokens`、`history_tokens`、`retrieval_tokens`、`output_reserve`、`truncated`。
- **R2 预算分配**：按任务类型设默认配额；**证据至少保留 X%**。
- **R3 schema 压缩**：工具多时启用压缩；**压缩版与真实 schema 做一致性校验**。
- **R4 截断声明**：溢出时标记 `truncated=true` 并说明丢了哪段；**不静默**。
- **R5 工具裁剪**：按任务只挂相关工具；**别把全目录塞进上下文**（150 期）。
- **R6 指标**：上下文利用率、schema 占比、截断率、溢出后 EM 掉幅。

### 5.2 用户旅程

- **平台工程师**：接入 60 个工具 → 8K 档溢出 → 启用 schema 压缩＋按任务裁剪 → 恢复 → 把「工具数」纳入发布检查。
- **Agent**：检索前检查预算 → 证据不足时明确说「证据被截断」→ 不硬答。
- **SRE**：发现某类任务 EM 骤降 → 查 `truncated` → 定位是工具 schema 吃满。
- **审计**：抽查一次运行 → 核对预算分配与截断记录 → 确认没有静默丢失证据。

### 5.3 实现方案（90 天）

- **0–30 天：埋点。** 记录五块 token 与截断标记；统计溢出率。
- **30–60 天：分配与压缩。** 按任务设配额；工具多时压缩；溢出显式标记。
- **60–90 天：裁剪与复测。** 按任务裁工具；对比压缩前后 EM；季度复盘；工具数进容量规划。

**第 102 个市场空白（五项）**：五块预算可报率、schema 压缩率、截断可观测率、溢出后 EM 可测率、工具裁剪覆盖率——无一内建；`context.*`／`budget.*` 为**第 69 次无人提字段族**。本地 173／173-kb 连续第 62 期成组启用：余锦泽 03「上下文装配、工具调用、结果校验」＝全库唯一把「装配」写成流水线环节的实践，本期首次当主线；配 61 期压缩、150 期目录。判词：**本地把上下文装配写进流水线，联网侧 2026 年才量出「28 个工具撑爆 8K、EM 2.6%」；两边都没把「这次任务给证据留了多少预算」做成运行时字段。**
