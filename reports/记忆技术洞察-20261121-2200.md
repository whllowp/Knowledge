# 记忆技术洞察 · 第 133 期（20261121-2200）

**主题：记忆的「零结构回看」（index-free lossless recall）——把完整历史存成纯文本日志、用正则按需回看，不要 embedding、不要检索索引、不要记忆抽取、不要额外模型，就能在精确细节任务上把有损摘要的 21% 推到 95—97%。前 132 期一路给记忆加结构：知识图谱（#28）、形态升维（#121）、双轴折叠（#132）、剂量适配（#131）；共同预设是"要检索就得先建索引/抽取/表示"。11-18 提交的 GrepMem（arXiv 2611.25123，南加州大学 Ziyan Yang／Taiwei Shi／Jieyu Zhao，cs.CL/cs.AI）从反方向追问：当数字存储让"全留"近乎免费，记忆系统究竟需要多少结构？与 #129 划界（那期靠状态—证据分离让紧凑状态可丢细节，本期连状态结构都不要，原样留存再 grep）、与 #122 划界（那期学一个重排器决定每条读多少，本期检索是精确词法、零学习检索器，RL 只学"何时 grep"）、与 #79 呼应（检索第一性从"像不像→有没有用"再推进到"最朴素的词法匹配能不能赢"）。**

> 洞察范围：2026 年（近 30 天为主）。四维度：发展趋势 / 技术现状 / 技术竞争力 / 技术挑战。

## 一、发展趋势

记忆架构出现一股"减法"支流：不与结构化系统比组织能力，而是把工作上下文与持久历史彻底分开——工作上下文照常有损压缩以保证推理不被撑爆，完整历史却只增不改、逐字留存，需要时靠正则回看。这不是否定结构化记忆，而是把它降为"默认不必建、建了须证明值得"的可选项。判据也在迁移：从"用什么表示记忆"转向"哪类问题真的需要无损"。

## 二、技术现状

GrepMem 架在 SUPO 的摘要循环上：上下文逼近窗口时生成摘要、重启上下文，同时把每条用户消息、工具调用、输出与摘要逐字追加进纯文本日志；首次压缩后开放唯一工具 grep_history（大小写不敏感正则，按时间顺序返回匹配行、周边上下文与原始位置，支持分页与 count-only 计数模式）。Qwen3.5-9B 在五种策略（ReAct／Masking／SUPO／MemGPT／GrepMem）上用同一 GRPO 配方训练，任务级二值奖励，摘要与 grep 查询均无独立监督，32K 上下文，训练集 4000 条（70% 单问、15% 三问会话、15% 合成长流）。

## 三、技术竞争力

RL 后五任务均分 GrepMem 66.4 最高（MemGPT 56.3／Masking 30.3／SUPO 29.8／ReAct 13.0）。ContextBench KV 97.4%、Log 95.3%，有损基线仅 6.6—20.7%；BCP-Multi 46.9%，超 SUPO 8.8、超 MemGPT 7.0 点；该任务每集压缩 25—27 次，正是被摘要漏掉的发现靠 grep 找回。token 上落在五任务精度—成本帕累托前沿：ContextBench 仅用 MemGPT 的 29%，BCP-Multi 比 SUPO 多 6%、AMA-Bench file 反少 5%；输入流从 33K 增到 968K token，GrepMem 基本不降，SUPO/Masking 趋近于零。

## 四、技术挑战

①词法天花板：不记得原词、只记得概念时正则失效，"未知未知"既不能被摘要召回也无法被 grep 命名——与 #120 静默遗漏叠成双重盲区。②检索开销真实：AMA-Bench stream 花 SUPO 的 2.3 倍 token、每轨迹约 19 次 grep，换来的领先仅 0.9 点且不显著。③增益是问题类型条件而非单纯模型条件：因果/状态变化类问题摘要足以保住，无损几乎无益。④单模型 Qwen3.5-9B、受控基准，置信区间只反映题目差异、不反映训练运行差异。

## 五、需求分析

长程 agent 的典型痛点是"早期看到的标识符，几步之后才变关键"，压缩时无法预知。用户要的不是更精巧的摘要，而是两条承诺：细节不因压缩而永久丢失、找回成本可控。选型方还需要一个"零结构"基线，用来判断图谱、索引、抽取管线到底带来了多少净收益——五家开源项目都在建结构，没人给出"不建会怎样"的对照。

## 六、用户旅程

每轮交互与工具输出既进工作上下文、也逐字追加进日志；上下文满则摘要重启并解锁 grep；agent 自决何时按名称/标识符/正则回看，分页取回原始行与位置，count-only 先探数量；上线后按三本账记账——任务准确率、总 token、grep 调用次数，并按"问题是否依赖被摘要丢弃的精确值"分层披露增益，避免在因果类任务上误报无损收益。

## 七、具体实现方案

①双速存储：工作上下文有损压缩、归档日志无损只增，压缩只作用于活跃窗口而非档案，这是 #132 双轴折叠的边界重划。②零索引接口：单一 grep_history 正则＋分页＋计数，省掉 embedding、索引与抽取模型，把 #5 记忆税从 token 扩展到基础设施。③把检索训进策略：GRPO 用任务奖励联合优化动作/摘要/grep，无独立查询标注，增益集中在可 grep 的任务（Log Triage +20.3、KV +3.5、BCP +6.0），因果任务近零（−0.6／+0.3）。④验收：AML 增 grep-over-log 维度（精确值召回率／每轨迹 grep 次数／词法失败率／帕累托位置），以"摘要丢的细节能否被 grep 找回"验收。五项目经 tag/release API 核实：OpenViking v0.5.5、Hy-Memory v2.0.17＋MemHub v1.0.8、TencentDB-Agent-Memory v2.0.4、dsh-memory-evolve v26092802、ReMe v0.4.2.3——五家全做抽取/索引/结构化，零纯日志零索引基线，倒挂延续。反证：单模型、受控基准、词法检索、stream 场景开销翻倍，不作外推。

## 八、本期新观点

1. **复杂度不是记忆的前提，"零结构"是必须建立的基线**（深化 #5/#96 记忆税）——纯日志＋正则在精确任务上胜过索引系统；记忆税不止 token，还有 embedding／索引／抽取的基础设施成本，五项目倒挂延续。
2. **有损/无损不是二选一，而是两速分工**（边界重划 #113/#132，深化 #129）——只压活跃窗口、档案永不压；GrepMem 比 #129 更进一步，连紧凑状态结构都省掉，原样留存再按需 grep。
3. **无损的价值是"问题类型条件"，不止"模型条件"**（深化 #131 剂量适配）——精确值/日志条目类 95—97%，因果/状态变化类增益不显著；"问题何时揭晓"不等于"是否需无损"，判据是答案是否落在摘要丢弃的细节里。
4. **RL 学的是"何时 grep、grep 什么"，不是训练检索器**（接 #108 信用分配／#79 效用优先）——零学习检索器、无查询标注，增益与 grep 可解性高度耦合，从 new angle 澄清"检索决策可被任务奖励端到端学会"。
5. **共享检索工具把各家拉平，优势只在"自己的历史"上显现**（新角度）——AMA-Bench file 人人可 grep 源轨迹时各策略趋同；GrepMem 的独占价值来自搜索别人搜不到的自身遗失历史，而非 grep 本身。
6. **"无损存储免费、无损检索不免费"**（深化 #122/#124）——帕累托前沿与 29% token 是效率面，stream 场景 2.3× token／19 次 grep 换 0.9 点是成本面；记忆税须把工具调用单列，词法盲区须入账。
