# AI-SRE 技术洞察（第 320 期）

- 生成时间：2026-11-24 05:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：撤销面／权限撤销的生效延迟——删掉账号不等于收回能力

## 题眼

2026-10-18，safeguard.sh 的一篇文章用一句话回答了标题问题：**“自包含的 JWT 在过期前一直有效，除非 API 去查别的什么东西。”** 因为 API 本地验签、校验声明，从不回问签发方——这既是它快的原因，也是签发方无法把令牌“拉回来”的原因。可选项只有四种：短寿命、刷新令牌撤销（RFC 7009）、`jti` 拒绝列表、或改成每次请求都要自省的 opaque token。

2026-05-05，Zluri 的一篇身份治理文章给出了更日常的场景：你的 Celery beat 每四小时跑一次同步；用户在 9:03 被 Okta 停用；下一次同步在中午。**那三个小时里，一个仍然有效的会话令牌、API key 或 OAuth 授权，依然解析到一个已离职的身份。** 文章把这段窗口称为“访问控制层里的提权向量”，而不是理论风险。

同一系列的另一篇（2026-06-08）指出熵更大的问题：Entra ID 对用户是**软删除**——从目录删除用户并不会立刻硬删除，下游应用可能收不到 DELETE，账号保持活跃、没有 provisioning 日志，看起来“人还在”。

云上还有时间尺度更小但同样致命的窗口：AWS IAM 是最终一致，访问密钥、策略、角色的变更平均要 3–4 秒传播到各区域副本；在这段时间里，**已标记删除的密钥仍可能被接受**。临时凭证更直接——它们在过期前一直有效；要提前失效，得挂一个按 `TokenIssueTime` 拒绝的会话策略（`RevokeOlderSessions`），而该策略自身还要约 30 秒传播；服务关联角色甚至不能这样撤销。

反过来，也有把撤销做成同步的设计：2026-10-19 的一份 Agent 凭证服务文档写的是“每个请求都检查权限；删除授权或停用 Agent 立即生效；无缓存，下一个请求返回 403”。

## 一、发展趋势

**第一，撤销从“删除记录”变成“让副本失效”。** 能力在签发后会被复制：无状态令牌、会话缓存、网关 key 缓存、OAuth 授权、STS 临时凭证、Agent 上下文里的凭据、下游应用账号、CI secret。

**第二，TTL 被当作撤销的上限。** 短寿命不是撤销机制；它只是把“最长暴露时间”压到一个可接受窗口。

**第三，撤销开始要求证据。** 不是“我已删除”，而是“撤销后是否还有被接受的请求”；这需要按 principal/credential 记录的“最后接受时间”。

**第四，Agent 让副本数量翻倍。** 凭据可能出现在提示词、工具配置、记忆、缓存、日志里；停用一个 Agent 账号，不等于收回它已经拿到的所有能力。

**第五，身份治理从“入职/离职”扩展到“会话与凭证生命周期”。** SCIM 只管账号状态；会话、令牌、授权、缓存要各自撤销。

## 二、技术现状

**无状态令牌。** 本地验签，签发方无法拉回；除非每次请求查拒绝列表或自省。

**轮询式 SCIM。** 同步间隔就是撤销窗口；批量任务失败时窗口更长；软删除让下游永远收不到事件。

**最终一致。** IAM 变更传播有秒级到分钟级窗口；删除后短时间仍可能被接受。

**临时凭证。** STS 凭证到期前有效；提前失效依赖会话拒绝策略及其传播时间；部分角色类型不支持。

**Agent 凭据。** 常被缓存或嵌入；工具侧可能持有长期 key；撤销 Agent 身份不等于撤销其工具授权。

**观测缺口。** 撤销通常只记录“操作成功”，不记录“之后是否仍有请求被接受”。

## 三、技术竞争力

| 方案 | 撤销时延 | 覆盖面 | 实现成本 | 主要风险 |
|---|---|---|---|---|
| 短 TTL + 刷新令牌 | 分钟–小时 | 中 | 低 | 窗口内仍有效 |
| `jti` 拒绝列表 | 秒级（查表） | 中 | 中 | 存储单点、fail-open |
| Opaque token 自省 | 请求级 | 高 | 中高 | 每请求开销 |
| SCIM 实时同步 | 秒级 | 中（账号） | 中 | 下游支持差异 |
| 轮询 SCIM | 分钟–小时 | 中 | 低 | 同步窗口 |
| IAM 会话拒绝策略 | 秒级（含传播） | 中 | 中 | 角色类型限制 |
| 每请求权限检查 | 请求级 | 高 | 高 | 延迟与可用性 |

判读：买得到 IdP、SCIM、拒绝列表、自省、会话策略；买不到“撤销之后还有哪些副本能用、最后一个被接受的请求是什么时候、窗口有多长、Agent 缓存里还有没有”。

本期反转：我们一直把“撤销”当删除一条授权记录。实际上撤销的正确单位是**副本**——每一个已经拿到能力的副本都要被证明不再被接受。删账号只是撤销的开始。

判词：「IdP／SCIM／JWT 拒绝列表／令牌自省／会话策略／密钥轮换」全部可采购，「撤销后还有哪些副本有效、最后一个被接受的请求在何时、窗口多长、Agent 缓存与日志里是否还有凭据」不可采购。

## 四、技术挑战

**其一，无状态与可撤销的矛盾。** 本地验签快，但无法拉回；自省可撤销，但每请求都要问。

**其二，副本不可枚举。** 令牌、会话、缓存、下游账号、CI secret、Agent 上下文，清单永远不全。

**其三，传播时间不可见。** IAM 最终一致、SCIM 轮询、策略传播，各有窗口；仪表只报“操作成功”。

**其四，软删除语义。** 目录软删除不触发下游事件；账号“看起来在”。

**其五，Agent 特殊性。** 凭据进入提示词/记忆/日志；撤销身份不等于撤销工具授权。

**其六，fail-open/fail-closed 抉择。** 拒绝列表或自省服务故障时，放行还是拒绝，都会造成事故。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 安全/身份团队：需要副本清单、撤销窗口、最后接受时间。
- 平台/SRE：需要撤销操作的可观测性与回滚。
- 业务属主：需要知道离职/停用后哪些能力仍可能被使用。
- Agent 团队：需要凭据不落上下文、工具授权随 Agent 一并撤销。
- 复盘者：需要区分“已删除”“已传播”“仍被接受”。

**用户旅程（一次“离职后仍能访问”）。**

1. HR 在 9:03 停用账号；IdP 标记成功。
2. 下游应用靠四小时轮询同步，会话与 API key 仍有效。
3. 被停用者用旧会话导出数据；日志显示“正常授权请求”。
4. 复盘发现 IdP 记录“已撤销”，应用记录“无异常”。
5. 团队加短 TTL，窗口从 3 小时缩到 15 分钟，仍存在。
6. 真正缺的是“撤销后是否还有被接受的请求”的证据。

**实现方案（90 天）。**

- 第 1–2 周：副本清单——令牌、会话、API key、OAuth 授权、STS 凭证、下游账号、CI secret、Agent 上下文。
- 第 3–4 周：撤销语义分级——立即（每请求检查）、短窗口（拒绝列表/自省）、上限（TTL）；按资产敏感度选择。
- 第 5–6 周：SCIM 改造——事件驱动替代轮询；软删除映射为停用；失败重试与告警。
- 第 7–8 周：云凭证——会话拒绝策略、传播时间监控、服务关联角色的替代方案。
- 第 9–10 周：Agent 治理——凭据不落提示词/日志；工具授权与 Agent 身份绑定；停用时级联撤销。
- 第 11–12 周：撤销证据——记录 principal/credential 的最后接受时间；撤销后 24 小时扫描“仍被接受”的请求。
- 第 13 周：演练——离职、密钥泄露、Agent 停用三种场景，验证窗口与证据。

**验收标准。** 任一次撤销，能回答：副本有哪些、哪些立即失效、窗口多长、最后被接受的请求在何时、是否还有缓存凭据。

**第 232 个市场空白（五项）**：撤销副本清单；撤销窗口度量；最后接受时间；Agent 凭据级联；撤销后扫描。

**`revoke.*`／`capability_copy.*` 第 199 次无人提字段族**：`revoke.copies`、`revoke.window_seconds`、`revoke.last_accepted_at`、`capability_copy.location`、`revoke.evidence` 在 IdP、网关与 Agent 之间没有统一语义；平台只报“操作成功”。

**本地 173／173-kb 连续第 187 期成组启用**（朱革 15）：本地知识库把“删除”与“失效”分开记账；本期把撤销落成副本清单与生效证据。
