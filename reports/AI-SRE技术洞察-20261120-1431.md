# AI-SRE 技术洞察（第 305 期）

- 生成时间：2026-11-20 14:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：合并面／多活写冲突的合并语义——“谁赢”是业务决定，不是数据库配置

## 题眼

2026-07-16，super-productivity 的一个 PR 标题很直白：*unfreeze the disjoint-field merge to stop data loss*。冻结期间，同一实体不同字段的并发编辑按**整实体 LWW** 处理——后到的一侧用完整快照覆盖，另一侧的编辑“静默且永久地丢失”；例子是“把任务改名”碰上“另一台设备把任务标完成”，改名就没了。

同一仓库 2026-07-11 的 issue 给出另一面：LWW 的更新被当成 merge 应用，赢家把可选字段清成 `undefined`，JSON 传输又丢掉 `undefined`，于是**被清空的字段在远端复活**。丢失与复活，是同一套语义的两种失败。

2026-01-10 的一篇分析把根因说透：多活按物理时间排序时，云内时钟漂移按 **1–50ms** 计，跨地域更大；两台健康服务器、正常网络、无 bug 的代码，照样“用更旧的写覆盖更新的写”。这不是基础设施故障，是**时间被当成了仲裁者**。

## 一、发展趋势

**第一，多活从“数据库能力”变成“业务合约”。** Oracle GoldenGate 的 2026-10-25 实战文开头就是一句：先决定**谁拥有数据**，再谈冲突解决。路由到属主（owner routing）用一次 WAN 往返换掉冲突窗口；不路由，就得接受冲突并在应用层定义合并。

**第二，LWW 仍是默认，但默认正在被拆开看。** MariaDB 的多活方案（2026-11-11）明确规则：时间戳大者胜，相同时服务器 ID 大者胜；并承认这是**启发式**，不是正确性证明。云厂商文档也常把 LWW 写成“简单可靠”，省掉了“会丢哪一类编辑”。

**第三，CRDT 从论文走进边缘同步。** 华为云 2026-11-11 的实践报告给出数字：间歇连接场景 96%–99% 操作可用、完全离线 100%、本地推理中位延迟 <10ms，收敛靠“合并”而不是“投票”。代价同样明确：元数据随历史增长，需要 GC 或压缩。

**第四，程序化写入开始与人工编辑抢同一份状态。** 2026-10-28 的 CRDT 复盘指出：服务端发起的变更（AI 生成、自动化、数据库同步）如何与客户端并发编辑共存，比纯人工协同更复杂；**先把写入权限与冲突策略设计清楚，再谈合并函数**。

**第五，合并开始被要求“可解释”。** 复盘里越来越多出现“这次合并按哪条规则、丢了哪个字段、为什么选这一侧”的追问；能回答的团队，才有资格说“多活可用”。

## 二、技术现状

**数据库层。** DynamoDB Global Tables、Cassandra、MariaDB Galera 等提供 LWW 或“最后写入者胜 + 服务器 ID 决胜”；冲突解决发生在写入路径，业务无感，也无账。Oracle 的 before-image 方案能比较列级差异，但补充日志让 redo 翻倍、每列都随 trail 传输。

**CRDT 层。** Yjs／Automerge 等在实时协同与离线优先场景成熟；计数器、OR-Set、序列 CRDT 各有适用面。风险在“整实体 LWW 冒充 CRDT”——DynamoDB 的计数器不是完整 CRDT，购物车合并仍会丢。

**应用层。** 常见三种：字段级合并（disjoint-field merge）、操作日志（op-log）重放、人工对账。super-productivity 的教训是：字段级合并被冻结后回退到整实体 LWW，**回退本身成了数据丢失源**；而 op-log 的“补丁并集”又依赖 payload 里 `undefined` 的序列化语义。

**可观测层。** 合并冲突通常只在应用日志里留一行；没有“冲突率、丢失字段数、复活字段数、按业务实体的分布”。SRE 看不到，业务也看不到，只有用户在工单里说“我改的东西没了”。

## 三、技术竞争力

| 方案 | 丢失风险 | 复活风险 | 时钟依赖 | 元数据开销 | 可解释性 | 运维负担 |
|---|---|---|---|---|---|---|
| 整实体 LWW（DB 内） | 高（并发字段） | 中（清空字段） | 高（物理时钟） | 低 | 低 | 低 |
| 字段级合并 | 中 | 中 | 低 | 低 | 中 | 中 |
| CRDT（OR-Set/计数器） | 低 | 低 | 无 | 高（需 GC） | 中 | 高 |
| 服务端排序 + LWW（Figma 式） | 中（字符级编辑） | 低 | 无（用序号） | 低 | 中 | 中 |
| 属主路由（单写者） | 极低 | 低 | 无 | 低 | 高 | 中（WAN 延迟） |
| 应用层对账/人工合并 | 低 | 低 | 无 | 低 | 高 | 极高 |

判读：没有“最优合并”，只有“哪种丢失可以接受”。设计属性（颜色、位置）用 LWW 可接受；文本、金额、库存、权限不能接受整实体覆盖。买得到多活数据库与 CRDT 库，买不到“这次合并丢了什么”的账本。

本期反转：我们习惯把冲突解决当成数据库选型的一个勾选项（“支持多活”）。实际它是**业务语义的编码**——哪一侧代表真实、哪些字段可丢、程序化写入与人工写入谁优先，都必须先写下来；不写，默认就是“物理时间较大的那个赢”，而物理时间在 2026 年的云里并不可信。

判词：「多活数据库／Global Tables／Galera／CRDT 库／op-log 框架／属主路由」全部可采购，「这次合并按哪条规则、丢了哪个字段、复活了哪个字段、程序写入与人工写入谁优先、丢失能否被用户感知之前发现」不可采购。

## 四、技术挑战

**其一，时间不是仲裁者。** 1–50ms 漂移足以让“后写”变成“先写”；跨地域 NTP 更不可靠。用时间戳决胜等于把正确性押在时钟上。

**其二，整实体覆盖会吃掉并发字段。** 两个用户改同一记录的不同字段，整实体 LWW 让一方全丢；字段级合并又需要“字段存在性”与“清空”的明确语义，否则出现复活。

**其三，清空与缺失不可区分。** JSON 丢 `undefined`、稀疏更新、null 语义不一致，让“清空”在传输中变成“没改”，复活由此产生。

**其四，程序化写入没有“人”的上下文。** Agent 自动改状态时，它不知道另一端有人正在编辑；合并规则若不给程序写入单独等级，自动化会稳定地覆盖人工。

**其五，冲突不可观测。** 冲突率、丢失率、复活率没有指标；用户感知是唯一告警，通常已经晚了几天。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 业务属主：需要逐实体声明合并规则（哪些字段可 LWW、哪些必须并集、哪些禁止并发写）。
- 平台团队：需要冲突账本（冲突数、按规则分布、丢失/复活计数）与回放能力。
- SRE：需要冲突率异常告警，以及“合并规则变更”的变更记录。
- 安全/合规：需要知道程序化写入（Agent）与人工写入的优先级及审计。

**用户旅程（一次“改名消失”的事故）。**

1. 用户在 A 设备改任务名，B 设备同时把任务标完成。
2. 两端离线，重连后同步；整实体 LWW 选 B 侧快照，A 侧改名永久丢失。
3. 用户在 A 设备刷新，看到旧名字，以为没保存，再改一次；冲突继续。
4. 另一条路径：B 侧清空截止日期（`undefined`），JSON 丢弃该字段，合并后 A 侧旧截止日期复活。
5. 支持团队收到“数据错乱”工单，日志只有一行“conflict resolved”，无法定位。
6. 复盘结论是“同步有 bug”，但真正的 bug 是**合并语义从未被定义**。

**实现方案（90 天）。**

- 第 1–2 周：列出所有多活/离线写入的实体，逐字段标注合并策略（LWW／并集／禁并发／属主路由），形成一张“合并契约表”，业务属主签字。
- 第 3–4 周：消灭整实体 LWW 覆盖——至少改成字段级补丁，并显式编码“清空”为 `{field: null, tombstone: true}`，传输层不得丢字段。
- 第 5–6 周：给程序化写入（Agent/自动化）单独优先级与标记，默认低于人工写入；需要覆盖时走显式“接管”并留审计。
- 第 7–8 周：冲突账本——每次合并记录规则 ID、输入版本、胜出侧、丢失字段、复活字段；以实体类型聚合冲突率。
- 第 9–10 周：时钟治理——不把物理时间当唯一裁决；用服务端序号、混合逻辑时钟或属主路由；NTP 偏差纳入监控。
- 第 11–12 周：回放与演练——用真实冲突样本重放合并，验证“改名+完成”“清空+保留”等组合；把结果纳入发布门禁。
- 第 13 周：告警与验收——冲突率突增、丢失/复活计数 >0 即告警；复盘必须能回答“丢了什么、复活了什么、按哪条规则”。

**验收标准。** 任一次多活写入冲突，能回答：规则 ID、双方版本、胜出侧、丢失/复活字段、用户是否已感知、是否需要人工修复。

**第 217 个市场空白（五项）**：合并规则契约表；冲突账本与丢失/复活指标；程序化写入优先级；时钟偏差与仲裁方式登记；合并回放与门禁。

**`merge_policy.*`／`conflict.*` 第 184 次无人提字段族**：`merge.rule_id`、`merge.loser_fields`、`merge.resurrected_fields`、`merge.clock_source`、`merge.actor_class` 在主流多活方案里均无统一语义；厂商只报“冲突已解决”。

**本地 173／173-kb 连续第 172 期成组启用**（马云雷 31）：本地知识库把“多活的前提是能说清谁拥有数据”列为架构决策第一条；本期把它落成合并契约表与冲突账本。
