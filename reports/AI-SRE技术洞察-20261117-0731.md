# AI-SRE 技术洞察（第 243 期）

**生成时间**：2026-11-17 07:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-10-18 至 2026-11-17
**本期主题**：显存面／KV 缓存与抢占（KV Cache & Preemption）——Agent 的上下文越长，被挤掉的概率越大

## 题眼

2026-11-05 的 PACE（arXiv 2611.10240）做了个残酷实验：Qwen3-8B 跑 10 万 token 的编码会话，KV 预算只给 2,048 token（2%），即便保留策略「按计划」命中了每个需要的片段，准确率仍从 99.6% 掉到 93%——因为定义用到时已经隔了 9 万 token。同一时间段的 Penelope（arXiv 2611.00391，SGLang 实现）指出 Agent 负载放大了「位置不对称」：早期 token 被反复复用，晚期 token 只用一次，通用 LRU 逐出的恰好是要复用的那段；两档 GPU+CPU 缓存下 TTFT 最多降 76%、JCT 降 60%。《LLM Inference Handbook》第二卷（2026-10-07）则记下两条运维事实：vLLM 的抢占默认 `recompute`，被抢的请求**从零重新 prefill**；Agent 流量里队列等待可占端到端时延的 58%。

## 一、发展趋势

**第一，容量单位从「请求」换成「token」。** 一个 10 万 token 的会话顶几十个普通请求，按 QPS 扩容必然错配。2026 年做 Agent 容量规划，第一张表是「每会话 token × 并发会话数 × 平均驻留时长」。

**第二，抢占从边角料变成一线故障源。** 过去只在大促压测里看到 preemption，现在长上下文 Agent 常态化触发。它不报错、不熔断，只让 TTFT 和 JCT 变长；在十步任务里，一次抢占会被后续每一步放大。

**第三，逐出策略开始「懂 Agent」。** Penelope 按片段而非按块逐出，跨 GPU/CPU 统一管理；PACE 则证明「保留对的 token」还不够，还要保留它们之间的依赖。研究方向已经从「缓存命中率」转向「行为正确率」。

**第四，量化与卸载成为两条正规路线。** UltraQuant（EMNLP 2026 Industry）把 4-bit KV 缓存用到上下文密集的 Agent，要求质量、驻留与吞吐联合评估；LMCache 一类把 KV 卸到 CPU/远端存储，换容量但加带宽成本。

**第五，测量工具先行。** PrefixBench-H100（arXiv 2609.19657）在单张 H100 上系统扫 prefix 长度、后缀多样性、并发、输出长度与缓存配置，回答「前缀复用到底什么时候真的省」。没有这类基线，「开前缀缓存」只是信仰。

## 二、技术现状

**vLLM** 的抢占有两种模式：`recompute`（默认，丢弃 KV、重新 prefill）与 `swap`（换出到 CPU、需要时换回）。前者浪费算力，后者吃 PCIe 带宽；两者都让尾延迟变难看。Handbook 建议把 **preemption count** 作为 Prometheus 计数器暴露，持续非零即容量或水位问题。

**SGLang** 用 RadixAttention 做前缀树复用，共享系统提示与多轮历史；Penelope 在其上改成「片段级」缓存，记录缺失片段、选择性重算、保留后缀，把 GPU 与 CPU 当一个逻辑缓存管。

**PACE** 的结论对 SRE 最刺：只盯「需要的 token 还在不在」会高估质量。长会话里定义与使用点相隔越远，模型对缓存内容的依赖越强；「命中」不等于「理解」。

**UltraQuant** 给出工程折中：非对称 K/V 处理、Walsh–Hadamard 旋转、块级缩放，把 4-bit KV 做得可用；但它要求同时报告任务质量、缓存驻留与吞吐，单看显存节省会误导。

**PrefixBench-H100** 提供可复现的测量框架：reuse-on/off 对照给出「关掉前缀缓存」的绝对代价，`tokens_per_block` 消融检验内存与 kernel 的权衡在 TensorRT-LLM 1.x 上是否仍成立。

现状判断：**调度器越来越聪明，但「逐出后答案还对不对」仍不在任何厂商的 SLO 里。**

## 三、技术竞争力

| 方案 | 代表 | 机制 | 代价 | 可观测性 | 证据强度 |
|---|---|---|---|---|---|
| 重算抢占 | vLLM 默认 | 丢 KV、重新 prefill | 算力与 TTFT 暴涨 | preemption 计数 | 源码与文档，生产数据少 |
| 换出抢占 | vLLM swap | KV 换到 CPU | PCIe 带宽、换回延迟 | swap 计数 | 同上 |

| 卸载到 CPU/远端 | LMCache 等 | 分层存储 | 带宽与复杂度 | 命中与带宽 | 工程实践，缺统一基准 |
| KV 感知路由 | Dynamo/llm-d | 按前缀亲和调度 | 路由复杂度 | 命中率 | 厂商方案 |
| 扩 GPU／扩副本 | 自建 | 加显存 | 成本线性 | 利用率 | 取决于团队 |
| 缩短上下文 | 自建 | 摘要/裁剪 | 信息损失 | 需 eval 兜底 | 取决于团队 |
| 限流长会话 | 自建 | 配额/TTL | 体验下降 | 拒绝率 | 取决于团队 |

**判读**：能力层全在开源里——vLLM、SGLang、LMCache、量化内核都能直接用。分水岭在「证据」：谁能说清「这个会话在 14:03 被逐出了哪 3,000 token、逐出后同一问题的答案是否改变」，谁才敢把长上下文 Agent 放进生产。

**本期反转**：以前把 KV 缓存当性能优化，现在要当**工作记忆的可靠性问题**。缓存命中率是成本指标，行为正确率才是可靠性指标；两者在长会话里会分叉。

**判词**：「GPU、vLLM/SGLang、量化内核、前缀缓存」全部可采购，「这个 Agent 的哪段上下文在何时被逐出、逐出后答案是否仍然正确」不可采购。

## 四、技术挑战

**其一，抢占静默。** 没有错误码，只有变慢；SLO 上看是 P99 TTFT 抖动，根因在显存水位。

**其二，放大效应。** 十步 Agent 里一次重算，后续每步都可能再触发；JCT 非线性膨胀。

**其三，位置不对称。** 系统提示与早期工具结果被反复读，晚期观察只用一次；LRU 的假设在 Agent 负载上不成立。

**其四，命中≠正确。** PACE 的 99.6%→93% 说明「token 在」与「语义在」是两件事；现有评测几乎不测逐出后的行为。

**其五，压缩的隐性代价。** 4-bit KV 省一半显存，但质量损失是分布式的，靠抽样看不出来。

**其六，多租户争抢。** 共享推理集群里，一个长会话能把邻居挤到重算；没有按 token 的配额，公平性无从谈起。

**其七，成本归因。** 抢占导致的重算算在谁的账上？按请求计费掩盖了「被逐出者的浪费」。

## 五、需求分解、用户旅程与实现方案

**需求分解（五项）**：① 容量按 token 计、按会话分层；② 抢占与逐出可观测、可归因；③ 逐出策略对 Agent 负载有感知；④ 压缩/卸载有质量门禁；⑤ 长会话有配额与降级路径。

**用户旅程（推理平台 SRE）**：告警「P99 TTFT 抬升」→ 看 preemption count 与 KV 使用率 → 定位到某类长会话 → 查逐出日志与 prefix 命中 → 调水位/开 swap/换片段级策略 → 跑 Agent eval 对比逐出前后准确率 → 灰度 → 固化容量模型。

**90 天实现方案**：
- **0–30 天**：接入四个指标——preemption count、KV cache usage、prefix hit rate、queue wait（与 TTFT 分开）；按会话长度分桶出 P50/P99；建立「每会话 token」容量表。
- **31–60 天**：交互与批处理分队列，长会话设 token 配额与 TTL；评估 recompute vs swap 的成本；对 4-bit/卸载做小流量 A/B，质量用固定 Agent eval 兜底。
- **61–90 天**：把「逐出后正确率」纳入发布门禁；做一次抢占演练（人为压水位），验证降级链；产出容量与成本归因月报。

**第 171 个市场空白（五项）**：逐出审计日志、逐出后行为回归、token 级配额与计费、抢占归因账本、长会话降级策略库。
