# AI-SRE 技术洞察（第 158 期）

**生成时间**：2026-11-12 18:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：界面面／计算机使用面（Computer-Use）——同一个任务、同一个模型，跑第二次就失败；UI 是没有 schema 的 API，可靠性要先从「重复跑」开始

---

## 题眼

04-20 arXiv 2604.17849 把一句运维直觉变成了可测结论：**计算机使用 Agent 在真实任务上进步很快，有些甚至超过人类；但即使任务与模型都不变，一个 Agent 这次成功，下一次重复执行同样的任务却可能失败**。作者在 OSWorld 上用重复执行＋配对统计，拆出三个不可靠来源：**执行中的随机性、任务规格的歧义、Agent 行为的波动**；结论是可靠性同时取决于「任务怎么被写清楚」与「行为在多次执行间有多稳」。同月另一篇（2607.28367）直接问：**基准是不是把计算机使用 Agent 判错了分**？**一次成功是演示，重复成功才是可靠性；而 UI 操作连「成功」都还没有统一定义。** **UI 是最古老的接口，也是最没有契约的接口——它没有版本号，只有改版通知。**

## 一、发展趋势

**趋势一：评测从「跑一次」转向「重复跑」。** 单次 pass@1 会高估；**要看重复执行下的成功率与方差**，甚至看「失败后能否恢复」。

**趋势二：UI 从「点坐标」转向「可验证的进程」。** 只看最终页面不够；**要看每一步的状态变化**（WindowsWorld 的进程中心评测、CUJBench 的浏览器到后端故障诊断）。**过程可验证，才谈得上「哪一步错了」。**

**趋势三：歧义从「模型的错」变成「规格的错」。** 任务没说清，Agent 只能猜；**允许它问，比让它猜更可靠**（109 期受领面）。

## 二、技术现状：UI 是没有 schema 的 API

**选择器：脆。** 按钮名、DOM 结构、坐标都会变；**没有版本、没有契约**（137 期工具契约的反面）。

**错误语义：没有。** 点错按钮可能「成功」提交了错误表单；**没有 4xx/5xx，只有看起来正常的页面**（96 期合式错值）。

**判分：容易错。** 最终状态对了、过程错了也算成功；**基准把过程错判成对，团队就会高估可靠性**。

**歧义：没人管。** 「把实例扩到 3 台」——哪三台、哪个区、要不要重启；**规格不写清，行为就不稳**。

**三种界面，三种稳定性。** DOM 选择器（最脆）、可访问性树（较稳）、纯视觉（最通用但最不可解释）；**选哪种定位方式，决定改版时会不会全挂**。

## 四、技术挑战

**一，一次成功会骗人。** 演示看一次，生产跑千次；**方差比均值更重要**。

**二，UI 变化无通知。** 前端改版、按钮改名；**没有 schema diff，只有「今天点不到」**。

**三，判分与过程脱节。** 最终页面对了，可能中间多删了一条数据；**过程级证据缺失**。

**四，歧义被当成模型能力。** 任务写不清，模型只能猜；**猜对了是运气，猜错了是「模型不行」**。

**五，恢复能力没人测。** 点错之后能不能退回；**没有 undo，就没有第二次机会**（95 期收容）。

**六，证据不可复现。** 截图有时间戳但无 DOM/后端状态；**复盘时无法确认「当时页面长什么样」**（116 期记录）。

**七，截图会骗人。** 页面渲染成功不代表提交成功；**要拿后端状态对账，不能只看图**。

**八，跨应用状态不同步。** 浏览器提交了、后台还没落库；**Agent 看到「成功」就继续下一步**。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `ui.*` 字段**：`task_spec`、`run_id`、`steps`、`final_state`、`process_evidence`、`ambiguity_asked`、`recovered`。
- **R2 重复执行评测**：同一任务跑 N 次，报成功率与方差；**单次通过不算通过**。
- **R3 过程级验证**：每步记录 DOM/接口/后端状态；**最终状态对但过程错，判失败**。
- **R4 歧义澄清**：规格不足时允许提问；**记录「问了什么、答了什么」**。
- **R5 恢复能力**：每步可 undo/可重试；**恢复成功率进指标**。
- **R6 指标**：重复成功率、方差、过程正确率、澄清率、恢复率。

### 5.2 用户旅程

- **平台工程师**：新界面任务上线 → 跑 20 次 → 成功率 70%、方差大 → 补规格、加选择器兜底 → 换可访问性定位。
- **Agent**：规格含糊 → 提问「扩哪三台」→ 拿到答复再执行 → 记录澄清。
- **SRE**：界面任务改版 → 选择器失效 → 回滚到上一版 → 补 a11y 定位。
- **审计**：抽查 20 次执行 → 核对过程证据与最终状态 → 确认没有「假成功」。

### 5.3 实现方案（90 天）

- **0–30 天：重复跑。** 选 10 个高频界面任务，各跑 20 次，建基线。
- **30–60 天：过程验证。** 每步留证据；判分改「过程＋结果」。
- **60–90 天：歧义与恢复。** 澄清流程；undo/重试；指标看板；改版回归跑。

**第 109 个市场空白（五项）**：重复成功率可报率、过程证据覆盖率、澄清率、恢复率、选择器稳定性可测率——无一内建；`ui.*`／`computer_use.*` 为**第 76 次无人提字段族**。本地 173／173-kb 连续第 67 期成组启用：周昕毅 10「三次现场检验须引用实时指标/日志/拓扑」＝全库唯一把「证据必须实时可核」写成硬要求的实践，本期首次当主线；配 116 期记录、131 期 SLO。判词：**本地把实时证据写成硬要求，联网侧 2026 年才量出「同任务重复跑会失败」；两边都没把「这个界面任务重复 N 次的成功率」做成交付指标。**
