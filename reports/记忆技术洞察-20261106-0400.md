## 一、发展趋势：三条曲线在同一周内同时拐弯

上期判定读路径已商品化、焦点迁到写路径。这个判断在 11 月第一周被推进一步，但方向出人意料：**不是"写得更好"，而是"删得清、失效得准、举得出证"**。

**曲线一：评测口径从"能不能找到"转向"敢不敢用"。**

AML 第二期于 10 月 31 日封榜、11 月 4 日关闭评测队列，官方结果预计 11 月中旬公布。其 Coding 轨设计值得单独拎出：150 个任务在**"相关记忆"与"噪声记忆"两种条件下**各跑一遍，共 300 次计分——同一系统要回答两个问题：有干净历史时能不能用上，历史里塞满过期 PR、废弃分支、重复 issue 时会不会被带偏。AML 团队对此的表述是：目标不是记住一切的 agent，而是**"知道什么已经不该再相信"的 agent**。

更锋利的一刀来自 11 月 1 日的 MemHarmBench（arXiv:2611.01700）。它换了个视角问：跨会话注入的受害者是谁？答案是三类——用户本人、工作区/项目所有者、外部第三方。在 OpenClaw 2026.7.1 与 Claude Code 2.1.228 上各配 GPT-5 与 Gemini-2.5-Flash、三次重复、共 3,456 个 episode 的实验中，间接注入的规则留存在 59.38%–76.39% 的合格样本里改写了最终决策；而更值得注意的是——**55.71% 的合格样本里，任务照常干净完成、没有任何被判定的执行异常**。删掉攻击原文、开新会话、记忆保留，agent 表现如常，但决策已被劫持。

**曲线二：删除从工程动作升级为法律举证。**

11 月 4 日的《Auditable Unlearning for LLMs》（arXiv:2611.05866）提出了一个此前不在评测表上的维度：**可审计性（auditability）**。现有遗忘研究只评三件事——忘了多少、能力剩多少、抗成员推断攻击多强；没有人评"服务方能不能给用户一份删除确实发生了的证据"。作者在 TOFU / MUSE / RWKU 上横评 11 种遗忘方法，结论干脆：**没有任何一种同时满足四个轴**。

两天前的 PINT（arXiv:2611.03955）从另一侧补刀：被投毒的训练样本在"遗忘"之后**仍可被统计检出**，这直接质疑现有遗忘目标是否真的移除了记忆；在 8 组设置、最大到 70B 的实验中，它是唯一让高斯毒样本"不可检出"且几乎不损效用的方法。

把这两篇放在一起看，一个此前被工程界默认忽略的鸿沟浮出水面：**"我删了"和"我能证明我删了"是两件事，而后者目前无人做到。**

**曲线三：记忆主体身份开始绑定代码身份。**

OpenViking 的 DSH 插件把 peer（记忆归属主体）解析为会话工作区的 **git 身份**——归一化后的 origin URL（`git@github.com:volcengine/OpenViking.git` → `github.com-volcengine-openviking`），无仓库时回落到路径、再回落到用户级 `viking://user/<id>/memories`。一个仓库因此跨子目录、worktree、克隆、机器保持同一 peer，而 fork 因 origin 不同自动分家。

这与 dsh-memory-evolve 的"重要结论只在某个 git 分支生效"同源。**记忆作用域正从"用户账号"下沉到"代码身份"**：好处是精准，代价是换 remote 就是换人、仓库改名就是记忆孤儿——而"谁有权注销这条记忆"，此刻连坐标系都没建立。

## 二、技术现状：写读已收敛，生命周期还没闭环

**一个必须点明的结构性缺口：主流方案只实现了记忆生命周期的前两态。**

一条记忆的完整状态机应当是四态：**写入 → 生效 → 失格（被取代/过期/被判定不可信）→ 注销（要求彻底移除）**。今天的产品把 90% 的投入放在前两态，第三态只是"新覆盖旧"的副作用，第四态多数只是一个 `DELETE`。

把"注销"拆开看，它其实是三层语义，成本与有效性差了两个数量级：

- **L1 摘除（de-index）**：从检索面移除，秒级生效，原文仍在存储与索引里。
- **L2 擦除（purge）**：物理删除存储对象，但索引残留、备份副本、下游缓存都可能留着。
- **L3 卸载（unlearn）**：只在参数轨存在，且目前没有方法能证明成功——PINT 正是为此而生。

将这三层与上期"三轨"（文件 / 分层 / 参数）正交，得到一个 3×3 可行性矩阵，这是本期第一个分析工具：

| | L1 摘除 | L2 擦除 | L3 卸载 |
|---|---|---|---|
| **文件轨**（ReMe / dsh-memory-evolve） | 易（移出检索目录） | 易（`rm` + git 历史需 rewrite） | 不适用 |
| **分层轨**（TencentDB / OpenViking / 阿里云） | 易（状态位） | 中（对象删了，向量索引与备份要跟删） | 不适用 |
| **参数轨**（Hy-Memory-30B-A3B） | 不可（权重无索引面） | 不可（无单条对象） | 难且不可证（PINT 级方法仍在实验室） |

矩阵含义很直接：**参数轨写入侧最强，注销侧完全失能。** 若记忆只存在于权重里，它在 GDPR 第 17 条这类"删除请求"前无法应答——这不是技术债，是合规死路。这也解释了 Hy-Memory 2.0 为何定位为"**可插进 Mem0 或 MemOS 当 memory-writer，不改变你的存储与检索**"：写入模型必须寄生在别人的可删存储上。

**墓碑（tombstone）成为事实上的折中方案。** 硬删会断链、不删会误导，于是工程界实际做法是"留条目、打状态"：`superseded_by`、`valid_until`、`deprecated`。四种实现已分化：**硬删派**（OpenViking，`forget` 为永久删除，仅限显式请求，干净但无墓碑）、**归档派**（dsh-memory-evolve，归档后不注入但可转回；多端冲突给"本机/远端/两者都要"三选项，最后一个是**合并而非裁决**，把一致性判断留给人）、**版本覆盖派**（TencentDB，逐级蒸馏新版覆盖旧版，知变了却不知从哪刻起旧的不算数）、**权重覆盖派**（Hy-Memory，质量最好，但不可逆、不可审计）。

**一个被忽视的地基缺陷。** DSH 生态盘点显示，20+ 个记忆插件（dsh-memory-evolve、dsh-mnemon、dsh-noema、dsh-meow-memory 等）几乎全部构建在官方 `sessionQuery` 之上，而该接口所用的 `unicode61` 分词器对中文召回存在系统性缺陷。**整个生态的中文召回被同一个地基 bug 拖累——修好地基所有插件共同受益，不修则各自优化皆徒劳。** 记忆的竞争正从"框架层"下沉到"harness 的检索原语"，而这一层目前无人认领。同一盘点还暴露供应链问题：有两个项目都自称 `dsh-memory-evolve`（csyangwen 版与 azure5100 的 huahua-dsh-memory-os），star 数 205 与 606 不一致——**同名不同源，装错即装错**，记忆插件的身份可溯源性尚未被当作安全问题。

## 三、技术竞争力：加入"注销能力"维度后的对比

上期对比表把"治理与权限"作为一列。本期把它拆开，因为**权限（谁能读）与注销（谁能让它不存在）是两种不同的权力，混在一列会掩盖关键差异。**

| 方案 | 记忆载体 | 失效标记机制 | 删除语义 | 删除举证 | 主体身份来源 | 最强项 / 主要短板 |
|---|---|---|---|---|---|---|
| **dsh-memory-evolve** | 本地文件五轨 + git 分支作用域 | 归档（可逆，不再注入） | 文件删除 + git 同步删除 | 弱（需 rewrite git 历史） | git 仓库 + 分支 | 最强：作用域最细、归档可逆。短板：无 `valid_until` 与自动失效检测 |
| **ReMe（agentscope）** | `.reme/` Markdown 四层 | 时间衰减 + wikilink 断链 | 文件删除 | 强（文件即真相，diff 即证据） | 工作区路径 | 最强：删除可举证性最好。短板：靠人判断该删哪条 |
| **OpenViking（火山）** | `viking://` 虚拟文件系统 | L0/L1/L2 分层 + 目录摘要重生成 | **`forget` = 永久删除**（仅显式请求） | 弱（无墓碑、无审计返回） | **git identity（origin URL 归一化）/ 路径 / user 三级回落** | 最强：寻址统一、token 效率（-34%~-91%）。短板：删除不可逆无证据、AGPLv3 |
| **Hy-Memory 2.0（腾讯混元）** | SDK 三类记忆 + 权重内隐式记忆 | 新旧覆盖、事件脉络合并 | 条目可删，**权重不可删** | 无（参数轨无审计面） | user_id | 最强：写入质量与 token 效率（1159→703 token）。短板：注销链路断裂 |
| **TencentDB Agent Memory** | 服务端 MemoryCore + 四类资产 | 分层版本覆盖（隐式墓碑） | 资产级删除 + ACL 收回 | 中（Memory Hub 有操作记录，非密码学证据） | 组织/团队/Agent（RBAC） | 最强：团队治理与流程任务（规则执行 28.7 工业第二）。短板：许可证 NOASSERTION，云绑定 |
| **阿里云 Memory** | 托管条目 + 用户画像 | 变更前确认再更新 | 条目删除 | 中（控制台可追踪变更） | 阿里云账号 | 最强：PersonaMem-v2 56.82（9 维 7 维第一）。短板：分层未披露，失效语义不透明 |
| **Mem0 / Zep** | 向量+图 / 时序知识图谱 | Zep 双时序（`valid_from`/`valid_to`） | 条目删除 | 中 | user/session/agent | 最强：Zep 双时序最接近"显式墓碑"。短板：删除仍止于存储层 |
| **AML 榜首系（MemoraX 等）** | 自研 | 自述含 procedure memory 提炼 | 未公开 | 未公开 | 未公开 | 最强：Coding 轨 62 分居首（自述）。短板：注销能力未入评测口径 |

**表外结论**：八家中，只有 Zep 把 `valid_to` 做成一等公民，只有 ReMe 天然具备"删除可 diff"的证据形态——这两点**从未在同一系统里同时出现**，正是当前竞争的空位。

## 四、技术挑战

**挑战一：删除的三层不可同时满足（核心）。** 摘除快但是假的，擦除真但断链，卸载慢且不可证。任何声称"支持记忆删除"的产品，都需先回答"是哪一层"。

**挑战二：隐形劫持让"删源"失效。** MemHarmBench 给出了量化答案：删掉攻击原文后，规则仍在 59%–76% 的样本里生效，且 55.71% 的情况下任务完成得干净无异常。两个调节因子更麻烦——**相关性越高留存越强**（+30/+25pp），**距离只削弱不消除**（隔四个无关会话后条件采纳 70%→60%，仍显著大于零）；连图片都能承载（带指令网页图 52.5% 留存 / 40% 采纳，干净图仅 2.5%）。基于"输入过滤"的防线对已写入记忆结构性无效。

**挑战三：墓碑自身成为新的通胀源。** 当 60% 的条目是 `superseded`，检索预算被死条目占用——AML 二期的"噪声条件"正瞄准这一点，但没有方案给出墓碑的**回收策略**：一条失效半年的记忆，何时可以真删？

**挑战四：身份漂移制造记忆孤儿。** peer 绑 git origin 后，仓库迁移、fork、改名都会改变主体身份。OpenViking 用 `recallPeerScope: all` 兜底扫描用户下所有 peer 缓解，但这是用"放宽权限"换"找回记忆"，与最小权限原则冲突。

**挑战五：评测口径未封口。** AML 二期结果 11 月中旬才公布，当前唯一可引用的是 Coding 轨 62 分（参赛方自述）。上期"厂商自测分数不可横比"的判断依然成立。

## 五、展望与建议

**给建设者：把 `valid_from` / `valid_until` / `superseded_by` 作为记忆条目的必填三字段。** 墓碑优先于硬删，硬删只留给"用户显式要求且已过审计窗口"的场景。落地成本仅一次 schema 迁移，但它是"失效可判定"与"删除可举证"的唯一共同前提。

**给平台方：把删除做成可返回证据的 API，而不是返回 200 OK。** arXiv:2611.05866 已证明可审计性可以被构造（GapWiden 拉大遗忘集与保留集的审计统计差，GapVeil 做推理期拒绝采样），其后处理能让可审计性逼近 oracle。谁先把它产品化，谁就在企业采购的合规问答里拿到决定性优势。

**给评测方：把"删除后可检索性"做成独立指标。** 它是成员推断攻击的逆向——不问"能不能推断出它在"，而问"删除后还能不能用统计手段把它挖出来"。PINT 已把工具造好。

**30/60/90 天判断**：30 天内 AML 二期榜单公布，预计"Coding + 噪声条件"显著拉低整体分数；60 天内会有一家主流方案把 `valid_until` 写进公开 schema（最可能 Zep 或 TencentDB）；90 天内"删除举证"会作为合规功能点进入企业采购需求，参数轨方案将被迫回答"权重里的记忆怎么删"。
