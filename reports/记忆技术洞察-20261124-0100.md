# 记忆技术洞察 · 第 137 期（20261124-0100）

**主题：记忆的「运行时逐出」（runtime context eviction）——同一条上下文，对 agent 是记忆，对服务端是共享 HBM 里的 KV 占用。前 136 期把成本记在单会话的 token、读多少、看多清与取回是否便宜上（#5／#122／#124／#132），共同预设"删上下文只是 agent 自己的事"；11-20 提交的 Contexture（arXiv 2611.26980，南洋理工＋A*STAR＋微软＋SuperMem，cs.DC）把判据移到 serving 层：并发会话抢同一 KV 池时，删什么由工具操作的时序取代决定，何时删由全局压力与前缀驻留决定。与 #97 划界（那期管单会话的 KV 栖居与重水化，本期管多会话共享池的吞吐）、与 #133 划界（那期连状态都不要、原样留存再 grep，本期按后续操作精确剪掉已被取代的跨度）、与 #5 深化（记忆税从每任务 token 扩到 SLO 吞吐与每会话能耗）。**

> 洞察范围：2026 年（近 30 天为主）。四维度：发展趋势 / 技术现状 / 技术竞争力 / 技术挑战。

## 一、发展趋势

长程 agent 反复重发增长的历史，瓶颈从"提示有多长"外移为"共享 KV 池装得下几个会话"。压缩、摘要、观察掩码都只看见单会话的逻辑上下文，看不见并发压力与缓存驻留；运行时 KV 管理又看不懂工具执行。趋势是把执行语义与全局缓存状态合流，把上下文裁剪做成服务端的运行时策略。

## 二、技术现状

Contexture 分两步。Session Tracker 从工具调用名与参数识别操作类型、目标和结果：后读或后改取代旧观察，重跑规范化命令取代旧输出，同一测试重跑通过才取代失败结果；一轮输出全被取代后，该轮调用与推理也成候选，系统提示与任务描述永留，候选经默认两轮宽限期才成熟。Policy Actuator 用只读驻留探针查前缀缓存：删点后无缓存 token 即"冷提交"；否则只在 KV 池压力超 80% 且失效 token 不超所删的 6 倍时提交。运行时只过滤模型输入、保留 harness 全史与模板标记，约 7K 行 Python 落在 vLLM 0.26。

## 三、技术竞争力

追溯 token 来源发现最终历史 64% 可判为取代候选，零额外模型调用。八组配置中，SLO 吞吐较四类基线最优者提升 20—73%，五组胜观察掩码 7—63%；其余三组掩码吞吐高 6—25%，但准确率掉 9—28 点。Contexture 相对空载无逐出平均准点率 +1.4、最差 −3.7；每完成会话 GPU 能耗降 2—11%。消融：仅选取降 25% prefill／41% p90 TPOT，冷提交再降 37% prefill，压力门再抬峰值 4%。

## 四、技术挑战

①轨迹回放不等于真实执行：实跑吞吐比回放低 9—13%（无逐出低 2—5%）。②删点使后续缓存前缀失效，混合注意力只存块对齐状态，重算成本是下界。③驻留探针读数是单会话请求下的单边陈旧，只会高估代价；工具映射不了的操作只能留。④宽限期是倒 U：0/1/2/3/4/5 轮准确率为 86/84/88/83/81/81，长留反而累积陈旧。⑤HBM 从 1.75M 增到 4.44M token，增益由 32% 降到 14%。

## 五、需求分析

服务方要的是在多会话争抢 KV 池时仍守住尾延迟 SLO，且不靠加卡或反复摘要来换吞吐；agent 方要的是被删的只是已被后续操作覆盖的旧观察，验证中的编辑不被提前抹掉，harness 历史与审计链不变。双方共同的硬约束是：省下的 KV 必须真转化为每秒完成的会话，而不是把成本藏进重算或准确率回退。

## 六、用户旅程

会话带 session ID 进入服务；Tracker 异步解析新消息、标记取代跨度，保留两轮供核验。每次请求先查候选是否成熟，再问驻留探针删除点后有无缓存：没有就冷提交，有则等压力过线且不超重算上限才提交。过滤器删内容、留工具标记；harness 持全史，模型见短提示。面板按 SLO 吞吐、准确率、能耗、重算 token 分账，不报单一"压缩率"。

## 七、具体实现方案

①逐出放在 serving 层而非 harness：全史可审计、短提示进模型（接 #97／#133）。②候选由工具操作类型＋目标＋结果的取代规则生成，失败结果须同测重跑通过才删，宽限期默认两轮并按任务回归标定。③提交分冷提交与压力门：代价按删点后缓存 token、收益按删掉 token 计，上限 6；探针超时或跟踪失败回退全长。④验收：AML 增 runtime-eviction 维度（SLO 吞吐／准点率／每会话能耗／重算 token／逐出后任务回归），以"同 SLO 下多跑几个会话且不做坏"验收。五项目经 GitHub tag/release API 核实：OpenViking v0.5.5、Hy-Memory v2.0.17＋MemHub v1.0.8、TencentDB-Agent-Memory v2.0.4、dsh-memory-evolve v26092802、ReMe v0.4.2.3——五家都在条目／向量／图谱层管记忆，零共享 KV 压力可见性、零前缀驻留探针、零工具取代逐出，倒挂延续。反证：单论文、两模型两 harness、回放为主、仅 vLLM 0.26 实现、未映射工具与多模态工具未测，不作外推。

## 八、本期新观点

1. **记忆税新增第五本账：共享 KV 池下的 SLO 吞吐与每会话能耗**（深化 #5／#122／#124，划界 #97）——单会话省 token 不等于并发多完成会话，压缩摘要在共享池压力前可能反而降吞吐。
2. **可删性由工具操作的时序取代判定，而非语义冗余或模型自信**（新角度）——64% 最终历史 token 是取代候选且零模型调用；失败结果不被无关操作抹掉、测试须同测重跑通过，把"什么算过时"从内容判断改为执行事件判断。
3. **"删什么"与"何时删"必须解耦**（深化 #97 位置几何）——冷提交零代价立即删，否则等压力过线并设重算上限；删上下文会失效后续缓存，节省 HBM 与牺牲复用是两种相反的经济账。
4. **吞吐、准点率、能耗必须三账并列**（接 #132／#135）——观察掩码三组配置吞吐反超却掉 9—28 点准确率；Contexture 平均 +1.4 点、最差 −3.7 点，单看"压缩率"或"延迟"都会选错策略。
5. **保留时长是倒 U 的请求级甜点**（呼应 #135 用户级寿命）——宽限期两轮 88% 最高，过短抹掉验证中的编辑、过长累积陈旧，与逐条记忆寿命同形但发生在每次提交决策上。
6. **扩容与卸载不能替代逐出＋五项目倒挂**（接 #5／#96）——H100 增益 32%、H200 仅 14%，叠加 LMCache 仍 +23%；AML 补 runtime-eviction 维度，以"同 SLO 多跑会话且不做坏"验收。
