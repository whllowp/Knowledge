# AI-SRE 技术洞察 · 2026-11-03 05:00 期（第 42 期）

**本期主线：自治面（等级面）运维——"允许自主到几级"不再是部署时写死的一行配置，而是一个运行时逐动作解析、随生产情境涨落、可被一键全局收回的变量。**

与前期分界：第 20 期（审批替代谬误）管审批流程是否形同虚设；第 34 期（确定性面）管边界的工程构造；第 26 期（判据面）管判据由谁定义；第 17 期（身份凭据面）管"我是谁、代替谁、停没停"。本期管的是它们的输出——自治等级这个值本身如何被计算、存储、降级、毕业与收回。另：第 35 期曾以中文二手转述引用 Google SRE 白皮书并标注"待英文原文核实"，本期已完成原文核验，多处失真一并澄清。

## 一、发展趋势

最近一周，"自治等级"从论文概念同时落进三处：**Google 官方 SRE 站点发布英文原版《AI in SRE: How Google is Engineering the Future of Reliable Operations》**（Papapanagiotou、Malesevic、Heiser、Meshenberg 署名），**微软 Azure SRE Agent 官方文档定稿 Run Modes 概念页**，**Mezmo 推出 agent-agnostic 的 Governance 治理产品（内测）**。加上 11 月 2 日信通院《云上 Agent 基准度量模型》把"辅助诊断→审批执行→限定自治"写进认证标准，等级语义首次同时出现在论文层、产品层、标准层。

趋势的实质是一条规则的三种表述：**自主权必须按动作逐次解析，而不是按系统一次性授予**。Google 白皮书原文给出的完整形态是"Actuation Agent（内部代号 Actus）实时管理调用者的自主级别"——当智能体请求 L3 执行、但检测到风险评分升高或生产状态异常时，Actus 自动将其降级为 L2、拦截执行并向人类 SRE 发出审批请求。也就是说，"此刻你是几级"是执行平面在每个动作上算出来的，输入变量包括进行中的部署、错误预算状态、活跃事件与时段——原文的经典例子：从负载均衡器摘除一个 cell 在平时是低风险动作，在区域高峰时段就是高风险。

## 二、技术现状

当前实现呈四种形态，工程成熟度差异极大。

**Google：等级内嵌执行层，语义最完整。** L0-L4 五级表按 Monitor/Investigate/Mitigate/Actuate/Self-Direct 五个职能逐级放权：L1 仅辅助分析（官方数据：仅信息辅助即实现 10% MTTM 降低）；L2 可执行但须人批；L3 对界定清晰场景免审批行动（要求"与无人监督风险成正比"的显著更高精确性）；L4 处理超出线性 playbook 的复杂事件。支撑体系三件套：Nightly Evals 接入 Everest 评估平台，用 LLM-as-a-Judge 评推理轨迹、用确定性评分要求最终缓解输出精确匹配 Golden 数据参数（而非"回滚"这类模糊建议）；评估数据分 Bronze/Silver/Gold 三级，衡量 True Precision 与 Observed Precision 的差距以保留统计安全余量；L2→L3 晋级只有在人工验证的 Golden 评测集上取得"持续、统计显著的成功率"后才放行。另有 Red Button 端点：SRE 可即时暂停全部在途代理动作、阻止新动作、或**全局撤销整个舰队的 L3 权限**。原文还给出量化基线：Investigation Dashboards 使发现项增加 195%、支持事件 MTTM 降低约 44%——期 35 二手转述中的"L0-L4"与"44% MTTM"经核验属实，但所谓"Actus 三闸"系转述失真：Actus 不是三道闸门，而是实时管理自主级别的执行智能体。

**Azure SRE Agent：等级与权限显式解耦，文档最扎实。** 官方文档把两件事分开："Run modes 控制审批流程——动作前要不要问人；Permissions 控制资源访问——能不能够到这个资源。两者都必须满足，智能体才能行动。"Review/Autonomous 两档按响应计划（response plan）与定时任务分别设置，agent 级默认值兜底。两个细节极具诊断价值：其一，Review 模式**只拦截 Azure 基础设施操作**，发邮件、发 Teams 消息、查外部数据源"按智能体的推理与响应计划指示自行进行"——等级治理存在明确的覆盖边界，需要 Tool Access Policies（allow/ask/deny）与 Hooks 兜底，且文档自己承认工具策略"匹配时覆盖 run mode 默认值"；其二，官方建议的毕业机制："从 Review 开始，观察 2-4 周，当你发现自己总在批准同一类触发器时，就把那一类切换到 Autonomous。"

**Mezmo Governance：外挂式策略引擎。** agent-agnostic 定位，七项接入前控制：fail closed（策略检查出错或超时则动作不执行）、默认策略 fallthrough 为拒绝、每智能体独立身份与最小权限、读/提议/执行/升级四类权限分离、高风险须人批且"智能体不得批准自己或修改约束自己的策略"、批准动作限定目标+过期时间+执行频率、审计轨迹单时间线记录证据/批准/命令/结果。审批收窄同样走毕业制："在监督结果足以证明更窄审查路径合理之前，常规动作保持人批。"

**国内双模与标准收口。** 腾讯云可观测平台 TCOP 采用探索模式（AI 自主）与规划模式（人机协同）双模驱动；火山引擎智能运维助手（公测）以"响应计划"把告警触发的 Runbook 流程固定为"自动分析、人工确认收尾"，等级本质上是写死在计划里的静态值。信通院标准把"限定自治"设为第三阶段验收项，等级第一次成为可认证指标。

## 四、技术挑战

**自治解析器成为新的关键路径组件。** 情境感知等级需要实时读取错误预算（SLO 系统）、进行中部署（CD 系统）、活跃事件（on-call 系统）——这个解析器自己挂了怎么办？fail closed 意味着全部停摆：可用性与自治被耦合进同一个故障域，Mezmo 把 fail closed 列为第一控制，却没有回答解析器自身的可用性 SLI。

**等级语义三层叠加，最终生效值不可预测。** Azure 同一智能体身上同时存在 agent 默认值、响应计划级设置、工具策略覆盖（文档明示 overrides）三层，叠加后的实际等级需要推演才能得知；等级的"有效配置视图"没有任何厂商提供。

**跨厂商等级不可比。** Google L3 ≠ Azure Autonomous ≠ 信通院"限定自治"：放权维度（五职能）、粒度（五级 vs 两档 vs 三阶段）、判定主体（执行层 vs 计划配置 vs 认证验收）全不相同，等级数字在采购与审计中不可横向引用。

**等级评定本身是判据问题。** "novel/高风险"由谁判定、用什么判据，最终落回第 26 期判据面问题——等级系统把判据问题包了一层而不是解决了它；毕业制的"监督结果"由谁记账、按什么口径算"持续统计显著"，Google 用 Everest+Golden 数据给出内部答案，行业无公共口径。

## 五、展望与建议

1. **先解耦后分级**：采纳 Azure 的双变量定义（审批流 × 资源权限）作为组织内基线语义，再谈分几级——多数团队连"能不能碰"与"要不要问"都还混在一处。
2. **毕业制直接照抄**：为每类动作记录"人工批准率"，连续 2-4 周接近 100% 批准的触发器类自动提请降审；反向的 Red Button 等价物（一键全局撤销某级自主权）应作为准入验收项写进采购条款。
3. **等级进遥测**：推动每动作审计记录（Mezmo 八字段）向 OTel GenAI 语义约定提交 level/expiry 字段，让"当时是几级、谁批的、何时过期"可查询——这是把自治面从制度变成 SLO 的第一步。
4. **按 L 级验收而非按 Demo 验收**：参考信通院三阶段框架，要求供应商说明等级解析位置与情境变量清单；答不出"你家的 L3 在谁身上、什么时候会降级"的方案，按论文级能力对待。
