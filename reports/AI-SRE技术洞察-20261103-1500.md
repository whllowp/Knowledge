# AI-SRE 技术洞察（第 51 期）· 读侧面运维——"只读"是运维里最贵的四个字

> 洞察范围：2026 年，重点为 2026-10-04 至 2026-11-03。本期为第四十二条主线：前 50 期把"写"当作变更（第 38 期）、把"读"当作无害；本期拿掉"读无副作用"这个前提。

## 一、发展趋势

最近 30 天有三条线同时往"读"上聚拢，且方向互相矛盾。

**其一，训练侧把"多轮探针读"确立为 SOTA 路径。** HarnessSQL（arXiv:2610.12274，10-08 首版、10-14 v3）把数据库智能体重新定义为"检查 schema、执行探针查询、诊断报错、修正假设"的有状态多轮过程，并指出单轮生成式训练与真实部署之间存在结构性脱节。其结果相当刺眼：在 Spider 2.0-SQLite 上，Qwen3-8B 从 15.5% 提升到 45.2%，14B 从 22.2% 提升到 54.8%，在 BIRD-Interact、LiveSQLBench 等分布外交互基准上同样领先。这条结果的含义超出准确率本身：过去我们把"读一次"当基线，现在最强的做法是"读很多次、每次读一点、读错再读"。**读放大不是工程缺陷，是被训练目标奖励出来的行为。**

**其二，治理侧把读的执法点从应用层下沉到数据层。** Oracle 在 AI Database 26ai 中推 Deep Data Security——把细粒度授权与数据可见性策略绑定到终端身份、角色与运行时上下文，并把 SQL Firewall 放进内核拦截异常 SQL 活动；其论据是"智能体以机器速度运行后，应用层已成为瓶颈与单点"。国内同构的动作出现在 11-03：电科金仓公开表述"数据不出库不是技术选择，而是合规底线"，主张语义对象与物理表同内核共生，行级权限、字段级脱敏、行为审计直接复用到 AI 链路，并用一句话概括路线差异——"靠提示词约束大模型不要越权，像口头说教；数据库底层权限管控是实实在在的围栏"。

**其三，工具侧把"只读"当安全标签批量发放。** 腾讯云开发者社区收录的 PostgreSQL 多模式 MCP 服务器，卖点是"所有查询都在 READ ONLY 事务中执行"，范围控制仅靠 `search_path` 与 schema 白名单；金仓 KingbaseES MCP Server 的 restricted 模式用 AST 白名单强制只读，而白名单里同时放开了 SELECT、EXPLAIN、SHOW 与 **VACUUM**。VACUUM 会重写数据页、占用大量 IO、可触发锁等待——它不是只读语句。这不是某一家写错了文档，而是"只读"这个词在 2026 年已经从属性退化成了标签。

## 二、技术现状

### 2.1 读有三重"只读"，产品普遍只做了第一重

**权限只读**：事务级 READ ONLY 或账号只授 SELECT。它只禁止写语句，不禁止 `pg_sleep` 式的资源占用、不禁止读文件类函数、不禁止跨 schema 全表扫描。

**资源只读**：读不产生可观测的系统副作用。这一层几乎无人交付，而它才是"只读拖垮主库"的真正机制。

**语义只读**：读不改变对世界的判断。只读副本滞后 30 秒时，根因分析看到的是 30 秒前的世界；跨库读没有统一快照，结论建立在拼接的时间上。这一层与第 47 期"事实三重时间"、第 50 期"时间戳自述性"直接咬合。

### 2.2 真正的成本不在数据量，在解析与元数据争用

这是本期最反直觉、也最需要纠正的一条判断。第 36 期我们把智能体的查询形态概括为"宽而浅"，据此认为列存与向量化会自然消化掉这部分负载。但探针读的真实形态是**极窄极密**：`SHOW TABLES`、拉 DDL、`EXPLAIN`、试跑一条带 `LIMIT 10` 的语句，扫的行极少，密度极高。

这种负载打的不是 IO，而是**优化器与数据字典**。智能体每次生成不同的 SQL 文本，执行计划无法复用，于是硬解析次数、预备语句/游标数量、catalog 锁与 plan cache 抖动被成倍放大——这是 DBA 熟悉的"硬解析风暴"，智能体只是把它从每秒几十次推到每秒几百次。它完美解释了三个现象：为什么一个只有 SELECT 权限的账号能把主库打挂；为什么"加了只读副本"之后故障只是换了台机器；为什么按扫描字节计费的数据仓库看起来很便宜、延迟却崩了。

由此得到一条工程判据：**读的可运维性 ≈ 模板化率**。把自由 SQL 收敛成参数化查询模板，等于给读加了编译缓存——同一模板复用计划、可预算、可复现、可比较。

### 2.3 被忽略的第四种副作用：读即出域

读的结果一旦进入上下文，就同时进入了模型供应商、日志平台与轨迹存储（第 32 期）。行级脱敏挡不住**聚合推断**：多次分组计数足以反推个体，而运维查询偏偏需要精确值定位故障，k-匿名与差分隐私在这里不可用。更少被提及的是，读痕迹本身就是一份敏感资产——"谁在何时查了哪个客户的哪条记录"，本身就是一份客户名单。

### 2.4 现状判读

数据库厂商在补"执法点"（把控制下推到内核），可观测厂商在补"结果"（Grafana 10 月已把 SLO 直接架到 agent 行为上），而**中间的"读的过程"没有人管**：没有一家把读放大率、模板化率、快照可证率做成智能体的一等指标。

语义层在此获得了一个新解释。第 25 期我们把语义层读作"指标口径的编译器"；从读侧面看，它更像是**读的编译缓存**——语义层不是让模型更懂业务，而是把自由 SQL 收敛成参数化模板，从而让读第一次变得可缓存、可预算、可复现。这也解释了 Snowflake 今年 8 月那组内部评测为何差距如此之大：58 道内部题上，走语义上下文的路径 86.3% 正确率、每题 0.59 美元；直连 MCP 的路径只有 24.1%、每题 1.76 美元。差的不是模型，是读的形态（该数据为二手转述，待原文核实）。

## 四、技术挑战

**第一，只读不可证。** 目前没有任何产品能出具"这次读是只读的"证明。可验证的只读至少需要三证：语句类别（AST 级而非关键字级）、资源上界（扫描行数、CPU 时间、时长）、快照标识（读到的是哪个版本）。缺任何一证，"只读"就只是配置项。

**第二，模板化与表达力直接冲突。** 模板化越强越安全越便宜，但长尾问题答不了；而 HarnessSQL 恰恰证明长尾靠的是自由探针。唯一可行解是**读的两档制**：探索档在沙箱副本上跑自由 SQL、严格配额、结果不外带；生产档只走参数化模板。两档之间需要一条明确的"结论晋升"通道，而这通道目前不存在。

**第三，资源护栏会误杀。** 智能体的读是试错式的，`EXPLAIN` 预检阈值定太紧会阻断正确路径，定太松形同虚设。按扫描行数一刀切是错的，应按"读意图"分级：定位类、验证类、取证类各有不同上界。

**第四，聚合推断没有工程解。** 只能靠"查询目的绑定"——把每一次读绑到一个已声明的故障假设上，读不出假设范围就拒答。这实际上是把第 42 期的"自治等级"从动作侧延伸到读取侧。

**第五，读痕迹的存储悖论。** 为审计要留全量读痕迹，而读痕迹本身既是新的泄露面又是新的成本项。第 32 期的轨迹治理三权（写入门禁/读取分级/保留冻结）需要原样搬到读痕迹上。

**第六，跨副本一致性无字段可依。** HA 架构下读被路由到不同副本，同一个 RCA 会话内可能读到不同时刻的世界，而返回结果里没有任何字段告诉模型这件事。

## 五、展望与建议

**指标层**：为读设四指标——模板化率（参数化查询占比）、读放大率 QAR（结论所需查询数 × 单查询解析成本）、快照可证率（带 read_at + snapshot_id 的读占比）、读越界阻断率。

**工程层**：读的两档制 + 双计量配额（扫描行数与解析次数同时计，后者往往先到顶）；读结果必须携带 `read_at` / `snapshot_id` / `replica_lag` 三字段，缺失者不得进入根因结论。

**采购层**：三问即可筛掉大多数方案——能不能出具只读三证？护栏计的是扫描行还是解析次数？读痕迹存在哪、谁能读、留多久？

**标准层**：建议 OTel 在数据库语义约定中增补 `db.read.rows_scanned`、`db.read.template_id`、`db.read.snapshot_lag` 三个属性。这是让"读"进入 SLO 的最小前提，也是把第 50 期的时间证据从 span 级推到行级的唯一路径。

一句话收束：**写错了可以回滚，读错了会形成一个被所有人相信的结论**——所以读比写更需要门禁。
