# AI-SRE 技术洞察（第 377 期）

**生成时间**：2026-11-27 17:31（Asia/Shanghai）
**本期主题**：幂等面／幂等键与去重窗口——重复是常态，去重是承诺

## 题眼

幂等键不是 HTTP 头，是业务对"同一件事"的定义。Stripe 的幂等键保留 24 小时，同键不同参数直接报错；SQS FIFO 的去重窗口只有 5 分钟；Kafka 的 exactly-once 只在单分区单事务内成立。三个数字说明同一件事：**去重窗口由系统决定，业务重复由重试与扇出决定，两者从不对齐。**

## 一、发展趋势

第一，重试从例外变成默认。客户端、网关、队列、Agent 工具链都会重试；"只执行一次"要靠显式幂等，而不是靠网络可靠。

第二，幂等从接口属性变成业务契约。同一个支付、同一封邮件、同一次部署——"同一件事"的键由业务定义，不是由请求 ID 定义。

第三，去重窗口被重试周期追赶。Stripe 24 小时、SQS FIFO 5 分钟、Lambda Powertools 的状态记录按 TTL；重试或重放窗口超过去重窗口时，旧键被重新执行。

第四，Agent 让副作用变多。一次决策触发多个工具，每个工具都要幂等；没有键的工具只能靠人工对账。

第五，证据需求上升。"这次请求执行了几次"要能回答，而不只是"最终状态对"。

第六，跨服务传播成为常态。网关生成键、服务透传键、下游用同一个键去重；键在某一跳丢失，去重就断链。

## 二、技术现状

**幂等键五要素。** 谁生成（客户端/网关/服务）、作用域（账号/租户/资源）、载荷绑定（同键不同载荷必须拒绝）、结果存储（返回同一结果，不是重新执行）、保留期（覆盖最大重试/重放窗口）。

**"处理中"是一个状态。** Lambda Powertools 把键写成 in-progress，完成后再写 completed；并发同键请求被拒绝或等待，而不是并行执行。

**去重窗口是硬边界。** SQS FIFO 5 分钟去重；超过窗口的重复会被再次投递。窗口与重试策略必须一起设计。

**exactly-once 是局部保证。** Kafka 事务保证单分区内不重复；消费者写外部系统仍需幂等键，否则"读一次写两次"。

**同键不同载荷必须失败。** Stripe 在键匹配但参数不同时返回错误；静默用旧结果会让调用方以为新请求被执行。

**键的传播会断。** 网关生成键、服务重试时重新生成、异步任务用新 ID——每一次重新生成都是一次新的"同一件事"。

**数据库唯一约束是最后一道。** 幂等键表 + 唯一索引 + 事务内写入，能兜住大部分重复；兜不住的是"外部副作用已发生、本地记录未写"。

**键表本身是热点。** 每个写请求都要查一次键表，键表成为写路径上的额外往返；分片、缓存与 TTL 清理都要设计，否则幂等层自己变成瓶颈。

**窗口外重复没有仪表。** 大多数系统只统计"命中幂等键"的次数，不统计"窗口外又执行了一次"；后者才是真正的双写风险。

## 三、技术竞争力

| 方案 | 键的作用域 | 去重窗口 | 同键不同载荷 | 结果存储 | 适用 |
|---|---|---|---|---|---|
| Stripe Idempotency-Key | 账号+键 | 24 小时 | 报错 | 存响应 | 支付/写接口 |
| IETF Idempotency-Key 草案 | 资源+键 | 服务定义 | 建议 422 | 服务定义 | HTTP API |
| AWS Lambda Powertools | 函数+键 | TTL 可配 | 报错 | DynamoDB | Serverless |
| SQS FIFO 去重 | 队列+去重 ID | 5 分钟 | 不适用 | 无 | 消息去重 |
| Kafka 事务 | 分区+生产者 ID | 事务边界 | 不适用 | 无 | 流处理 |
| 数据库唯一约束 | 表+键 | 永久（除非清理） | 冲突 | 行本身 | 最终兜底 |

**判读**：六种机制都能"挡住一部分重复"，都不能回答"这次请求在业务上执行了几次、每次的副作用是什么、去重窗口之外还有没有重复"。幂等是接口层的承诺，副作用账本才是业务层的证据。

**本期反转**：我们一直把幂等当"防止重复提交"的优化；它其实是"重复是常态"的前提下的正确性基础——没有幂等键的写接口，在重试默认化的今天，等价于没有事务。

## 四、技术挑战

**挑战一：键的语义。** 请求 ID 不等于业务键；同一业务事件的不同请求要用同一个键，不同业务事件不能用同一个键。

**挑战二：窗口对齐。** 去重窗口 < 重试窗口 = 重复穿透；窗口太长 = 存储膨胀与键碰撞。

**挑战三：载荷绑定。** 同键不同载荷必须拒绝，但"载荷"的规范化（字段顺序、空值、时区）本身是坑。

**挑战四：处理中崩溃。** 写 in-progress 后崩溃，重试看到 in-progress 是等待还是重做？需要超时与所有权。

**挑战五：外部副作用。** 邮件已发、支付已扣，本地记录未写——幂等键救不了，只能对账。

**挑战六：跨服务传播。** 键在每一跳都要透传，任何一跳重新生成都会断链。

**挑战七：Agent 工具。** 工具没有幂等键时，重试就是重复副作用；需要工具侧支持或编排层去重。

**挑战八：清理。** 幂等键表要按窗口清理；清理早于重试窗口，旧重复会重新执行。

**挑战九：审计口径。** 财务与合规要"执行了几次、每次何时、谁触发"，而幂等键表只保留最后一次结果；完整审计需要独立的副作用账本。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①业务键定义；②键的生成与传播；③载荷绑定与冲突拒绝；④in-progress/completed 状态机；⑤去重窗口与清理；⑥外部副作用的对账；⑦重复率指标；⑧Agent 工具的幂等能力。

**用户旅程**：客户端生成键 → 网关透传 → 服务查键（新/进行中/已完成）→ 执行并写记录 → 返回同一结果 → 重试命中记录 → 窗口外重复由对账发现。

**实现方案（90 天）**：0–30 天定义业务键与作用域，写接口强制 Idempotency-Key，建幂等键表与唯一索引；31–60 天加 in-progress 状态与超时所有权、载荷哈希冲突拒绝、窗口与清理策略；61–90 天做重复率与窗口外重复的对账，Agent 工具接入同一个键。

**验收标准**：任取一次写请求，能回答"键是什么、谁生成、作用域多大、执行了几次、每次副作用是什么、窗口多长、清理何时发生"；答不出的写接口就是"重复即双写"。

## `idempotency.*`／`dedup_window.*` 第 256 次无人提字段族

业务键、载荷哈希、in-progress 所有者、执行次数、窗口到期时间、窗口外重复计数——这些字段在写接口的 schema 里通常不存在；存在的是"请求 ID、时间戳、状态"。
