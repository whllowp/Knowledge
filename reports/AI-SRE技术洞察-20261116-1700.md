# AI-SRE 技术洞察（第 224 期）

> **题眼**：2026 年 11 月，NVIDIA 把 AIOps 平台 Minerva 摆上台面，明确要抓的不是"坏掉"的部件，而是"没坏但正在变坏"的部件——一块仍在规格内、却比同负载兄弟卡明显更热的 GPU。这戳穿了 SRE Agent 最大的结构性盲区：**Agent 是事件驱动的（告警→诊断→处置），而灰失效偏偏没有事件**。告警阈值是 Agent 的传感器边界，没跨过阈值的退化在系统里存在、在 Agent 的世界里并不存在。行业把"降噪 80%""多窗口 burn-rate""统一图谱"写进产品页，却几乎无人回答：*这次退化没触发任何告警，你到底看没看见？*

## 一、发展趋势

2026 年的 Agentic Ops 叙事几乎全建立在"事件"之上：告警来了给优先级（携程 10）、跨系统取证（腾讯 CloudQ 10-29）、关联变更定因（阿里 STAROps）、围绕目标持续观察（阿里云 AgenticOps）。这套范式处理**急性故障**已相当成熟。但最近 30 天三条线索同时浮出，指向被忽略的另一半：

其一，**检测重心从"绝对越阈"转向"相对异常"**。NVIDIA Minerva 用无监督模型为部件学习常态、再与同类部件比较，多变量模型把温度、功耗、频率、利用率与作业状态联合判断，在部件彻底失效前抓到退化——因为同步训练按最慢的 rank 前进，一块亚阈值退化卡就能让整份作业、数百块健康 GPU 一起空转。这是"灰故障"第一次被一家主流厂商作为 AIOps 产品的**首要目标**写进公开材料。

其二，**AI 服务自身的高可用统计正在给灰失效做注脚**。截至 11 月中旬第三方监测显示，近 90 天 claude.ai 报 99.54%、ChatGPT 组 99.26%——但同批数据也记录了大量"主机应答正常、我的请求却失败"的缝隙，以及 11 月 12 日微软 365 大故障同时波及 Claude 与 ChatGPT 连接器（模型健康、链路断裂）。可用性数字越漂亮，越容易掩盖"没到宕机、持续劣化"的中间态。

其三，**SRE 方法论已给慢变量留位置，但留得很低**。Google 多窗口 burn-rate 里，慢燃烧（约 2×/24h，agent 模式用 3 天窗口）被明确"路由到工单或低优先级队列"。主流指导默认慢性退化**不值得半夜叫人**——工程上合理，却让灰失效在流程层获得永久延期通行证。

趋势判断：**2026 下半年，Agent 可观测的竞争焦点会从"看得更快"转向"看得见没报警的东西"**。谁先把"相对异常 + 基线治理 + 跨层关联"做成 Agent 可消费的一等信号，谁就占据下一轮差异点。

## 二、技术现状

把当前能力拆成"检测—归因—处置"三段看，灰失效的断点在第一段，且是连锁性的：

- **检测段**：静态阈值对硬故障有效，对慢变量两难——调低则在正常负载波动时告警泛滥，调高则错过缓慢偏移。Burn-rate 多窗口进了一步，但仍依赖"错误"这个已定义事件；对"step time 慢慢变长""成本数据延迟""质量悄悄下滑"这类没有明确 bad event 的退化，同样需要有人先定义 SLI。业内一条反直觉经验："always 500 errors/min"会被吸收为新常态——**阈值漂移本身就是灰失效的产物**。
- **归因段**：证据被组织边界切开。网络侧看接口计数器，计算侧看节点与 GPU 健康，ML 团队只看 step time 变长。每一面都正确，但因果关系藏在交接里。单 Agent 只拿一个视角的遥测，天然看不见跨层慢退化。
- **处置段**：灰失效没有明确起点，也就没有"回滚目标"。#222 已论证"回滚≠恢复"，灰失效更极端——根本没有一个可回滚的"那次变更"，因为它是多因素累积。

可观测栈五层（动作日志/成本/质量评分/漂移检测/业务影响）里，第三、四层正为对付"Agent 静默退化"而生：某咨询案例中，销售 Agent 引用六个月前废弃的定价档，因 CRM 迁移时集成静默断开、又无质量评分，11 天无人发现，23 个潜客拿到错误报价、4 份合同按错价签了。这类故障没有 5xx、没有告警、没有变更窗口——是灰失效在业务层的翻版，主角从 GPU 换成 prompt 与 connector。

## 三、技术竞争力（主要厂商/方案对比）

| 厂商/方案 | 灰失效是否为一等目标 | 相对/同行比较能力 | 跨层关联底座 | 慢变量→Agent 消费路径 | 未越阈退化可举证 |
|---|---|---|---|---|---|
| **NVIDIA Minerva**（AI 工厂 AIOps） | **是**，明确以 gray failure 为核心命题 | **强**：无监督同行比较 + 多变量（温度/功耗/频率/利用率/作业态） | 动态拓扑知识图，随作业启停更新 | Sherlock Agent + MCP，基于实时证据对话式下钻 | 部分：给出证据链，但未公开"未越阈"比例 |
| **Google Cloud**（SRE 方法论 / OTel） | 部分：慢燃烧 burn-rate 有专门窗口 | 弱：偏绝对阈值与预算消耗率 | Cloud Trace + OTel，关联强 | 慢燃烧 3 天窗口→**默认进工单/低优先级** | 弱：路由降级，无"看见即记录" |
| **Anthropic**（OTel tracing / 自托管） | 否：偏事件与 Trace 语义 | 弱 | OTel GenAI 语义约定 | 追踪优先，质量/退化评估非内建 | 弱 |
| **OpenAI**（Control Room / 四层失配） | 部分：监控"模型偏离自身基线"接近 | 中：失配监控识别行为漂移 | 自建运行时绑定 | fail-closed 偏急性；慢漂移走 review 队列 | 部分：但 11 月被曝监控标记率仅 42.9%/57.1% |
| **字节跳动**（AgentLoop / 火山 RCA Harness） | 否：偏急性根因 | 弱 | RCA Harness + IAM | 告警按联系人聚合、2h 降级，面向已发告警 | 弱 |

| **腾讯**（CloudQ / AI 可观测） | 否，且**方向相反**：低通滤波器把召回让渡给精确率 | 弱 | 全景图谱 + "AI 调用 AI" | 从"告警救火"到"证据驱动自愈"，起点仍是告警 | 弱：牺牲的正是亚阈值召回 |

**判读**：唯一把灰失效上升为产品第一性目标的是 NVIDIA Minerva——把"相对同行异常"做成检测原语，用拓扑图把跨团队证据拼成因果图。Google 有方法论却把慢燃烧降级进工单；阿里、腾讯有统一上下文与图谱，却以阈值/告警为入口，腾讯甚至主动牺牲亚阈值召回换精确率。除 NVIDIA 外，**"相对异常检出／未越阈漂移可举证／基线污染标记"三列几乎全空**——这是本期第 160 个市场空白：做"没有事故的事故"的可采购能力尚未成型。

## 四、技术挑战

1. **事件驱动的范式错配**。Agent 的触发器是事件；灰失效的定义恰是"无事件"。不改造触发器，再强的诊断 Agent 也没有输入——这不是模型能力问题，是架构问题。
2. **基线的自我污染**。长期运行的慢退化会重写"正常"的统计基线；Agent 用被污染的基线做判断，越判越觉得正常，形成正反馈。现有系统鲜有基线版本化与污染告警。
3. **相对异常的"同类"难定义**。与谁比？同负载兄弟卡、同实例、同区域？分组错了，peer comparison 会把正常差异当异常、把真实异常当正常——分组本身需要领域知识。
4. **流程层的永久延期**。慢燃烧被路由到 ticket，没有 owner、SLA 与升级条件，等于慢性退化被制度化忽略——M365 故障"模型健康、连接器断裂"正是跨层耦合无人负责的后果。
5. **可审计性缺口**。第三方对 64 起已核实 AI 事故的分析指出：事故几乎都能从日志重建，但外部无法核查"评审搜了哪些记录""告警与补救是否真生效"——一条告警从 sent 到 received 到 observed effect 必须拆成三个事件，否则"发了告警"被当成"处理了故障"，慢退化在实现层被悄悄注销。
6. **评测盲区**。主流基准（SRE-Bench、RCA-Bench、Cloud-OpsBench）都是"给一个已发生故障看能否定位"——测的是急性响应，无一测"给一段缓慢劣化序列，Agent 能否在跨阈前检出"。

## 五、展望与建议

- **立 `gray.failure.*` 五字段 OTel 语义草案**：`peer_relative_anomaly_rate`（相对同行偏离度）、`subthreshold_drift_detected`（未越阈漂移检出标记）、`baseline_contamination_flag`（基线污染标记）、`slowburn_disposition`（慢燃烧的处置去向与 owner）、`cross_layer_signal_join_rate`（跨层信号关联率）。无此字段，"看不见"与"看了没报"在数据层同形。
- **把"相对比较"升格为一等检测原语**：为每个关键部件显式定义 peer group 与比较窗口，上报相对偏离度而非只有绝对值；温度在规格内但高于兄弟卡 3σ，应生成可消费信号。
- **基线版本化与污染检测**：区分"原始基线"与"滚动基线"，滚动基线相对原始基线单调漂移超阈值即告警；杜绝 Agent 用被污染的"正常"自我说服。
- **给慢燃烧接上升级路径**：ticket 也要有 owner、SLA 与"N 次未闭环自动升级"；把 #220 的 ack→acted 计时推广到退化类工单。
- **跨层关联 + 相对异常组合**：复用拓扑/知识图谱把"每一面都正确"的分散信号拼起来，让 Agent 从"异常接口"反查到"受影响作业"，从"作业变慢"正查到"那条亚阈值链路"。
- **补评测与标准**：给基准加入"慢退化注入"题型（跨阈前检出得分）；建议信通院六维模型补"灰失效可检出率"一格。

**本期新观点**：#220 讲"告警被判不算数"，本期讲"压根没告警可判"；#222 讲"这次是不是那次变更"，本期讲"没有'那次'——是累积"。灰失效不是更难的急性故障，而是与事件驱动范式正交的另一类问题；行业需要的不是更聪明的诊断，而是**在症状尚不构成事件时就产生可消费信号**。可采购的是阈值、图谱与降噪；不可采购的是"这次没越阈的退化，你凭证据说你看见了"。
