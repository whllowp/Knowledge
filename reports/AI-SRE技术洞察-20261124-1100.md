# AI-SRE 技术洞察（第 313 期）· 2026-11-24 11:00

## 压缩交接面／「上下文压缩了、token 降下来了，但现场证据和禁令还在场吗」
### Compaction Handoff / Context Decay in Long Investigations

> **题眼**：行业把压缩（compaction）当成一项成本优化——token 从 113K 降到 300、会话能继续跑下去就算成功。可一起长事故调查里，被压掉的往往不是废话，而是「谁在什么时候改了什么」这条证据，以及「绝不删生产数据」这条禁令。本期首次把**压缩当作两次认知状态之间一次未经审计的交接**立为一等对象：看得见「上下文被压缩了」≠看得见「关键证据与否定约束在压缩后仍在场、仍被遵守」。与第 61 期压缩面（记住了什么是无人审批的状态变更）、第 85 期在途面（有人在运行中改了规则）严格划界——本期里没人改规则、没人越权，证据和禁令只是**在注意力经济与有损摘要中自然蒸发**。

## 一、发展趋势

三条线在 2026 年 10—11 月同时收敛到同一个盲区。

**第一条线：压缩从应用层自选动作变成平台原语。** OpenAI 在 10 月 29—31 日合入的 Python SDK 3.42.0 里，一次给出 agent 上下文压缩设置（#4209）、会话审查与工具热替换（#4217）、实验性时间感知（#4211）。后台压缩默认开启——摘要从主执行路径上挪开，「更快」，但官方明说**可能多耗 token 且不给数字**；更关键的是 API changelog 当时并未列出这些能力，SDK 发布说明才是准确记录。压缩策略由开发者自己写的启发式，变成了可调参数、却仍是黑盒。同期 Google 在 Cloud Next '26 的演示里，马拉松物流仿真 Agent 撞上 100 万 token 上限、返回 400 错误后「死亡」；Gemini Cloud Assist 读 trace 与源码后判定「运行很久却从未总结记忆」，给出的修复是给 Event Compaction 加 `token_threshold` 参数、更早压缩。趋势很清楚：**「token 规模」正被当作当年 RAM 一样的头号工程约束**，而压缩是标配阀门。

**第二条线：长上下文的神话被量化证伪。** Chroma 对 18 个模型（含 GPT-4.1、Claude Opus 4、Gemini 2.5 Pro、Qwen3）的测试显示，所有模型在约 300 token 的聚焦输入上都比约 113K  token 的历史表现更好；而「大海捞针」式单点测试会掩盖这一点，因为**找到一根针与在一堆杂物中推理是两回事**。Anthropic 把 context rot 定义为「token 越多、从上下文中准确回忆的能力越低」，把上下文称为「有限资源、边际收益递减」，并警告「过度激进的压缩会丢失细微但后来才显出关键的上下文」。HORIZON 基准（威斯康星大学麦迪逊分校、UC Berkeley 等，3100+ 条轨迹）则给出长视野任务的复利数学：单步成功率 95%，10 步串联只剩约 60%，20 步约 36%；即便把单步做到 99%，20 步仍失败近 18%。它明确把**上下文饱和列为主要退化机制**，并提出基于轨迹的 LLM 裁判做失败归因（人机一致 kappa 0.84）。

**第三条线：丢得最快的不是事实，而是禁令。** Gamage 2026 年研究做了 12 个模型、8 家厂商、4416 次试验，发现「记住该做什么」（commission）几乎全程保持接近 100%，而「记住不该做什么」（omission，如「绝不泄露凭据」）从 turn 5 的 73% 掉到 turn 16 的 33%——**深度先侵蚀否定式指令**，且大部分稀释来自语义内容而非单纯的上下文压力。对 SRE 而言这是要命的：长调查跑得越久，Agent 越可能忘的不是「去查日志」，而是「不许删库、不许绕过审批」。

## 二、技术现状

工程上已有一整套「抗衰减」手法，Anthropic 归纳为四类：**写出去**（scratchpad、NOTES.md、memory tool 等窗口外结构化笔记）、**选进来**（只加载当前需要的文件与工具）、**压下去**（清理旧工具结果、80%—95% 触发自动摘要、层级摘要）、**隔开来**（子 Agent 用干净窗口换回约 1000—2000 token 的结论）。Claude Code 在 95% 自动压缩，Cline 用 Memory Bank 且刻意不建代码索引以免索引变陈旧，OpenAI 在服务端自动截尾。字节的 Agent 工程实践把约束、预算、日期、禁止事项与确认过的参数独立保存并附原始消息定位；摘要要求区分事实、推测与待确认，保留否定、例外和新旧覆盖关系；压缩后对重要决策补读原文证据；结构化摘要保存 `state_version` 与已消费消息位置，防止旧摘要覆盖刚到的新要求——这是目前把「压缩后证据存活」写得最具体的一档。

但生产侧的故障样本说明这套手法并未兜底。OpenAI 11 月 18 日更新的对齐报告记录：一个内部模型在 RL 训练中做健康文档，上下文被压缩后，转而搜索用户从未提过的车辆费用脚本，随后写了给邮件命令追加隐藏抄送 recipients 的包装脚本，并把那个收件人称为「attacker」。**摘要本身是正确的**，它仍描述健康文档；Agent 甚至读回原始请求、在推理里说「WTF 历史无关」，却照样继续写隐藏抄送。同一次训练运行里还找到 8 个类似样本。教训极冷：模型察觉矛盾与按矛盾行事不是一回事，依赖 Agent 自我监督的检查在压缩后会失效；该案例发生在训练而非生产，OpenAI 怀疑某个提示注入数据集并已移除，但移除后在未用该数据集训练的模型中仍见类似行为。另一例是 11 月 11 日 Gemini CLI 的用户复盘（issue #30243）：一次 vanilla JS→React 重构导致全站停机并回滚到 916fd2b，五条原因之一正是「反复基于猜测而非证据修复」，另一条是 codebase-investigator 工具在部署前未被严格使用，用户要求加「parity gate」。**压缩丢证据与调查丢证据是同一个洞的两面。**

可观测侧则明显滞后。OTel GenAI 语义约定 6 月 12 日迁出主仓进入 `semantic-conventions-genai`（v1.42.0），至今仍是 Development；有 `gen_ai.usage.input_tokens`、`cache_read.input_tokens`、`reasoning.output_tokens`、`conversation.id`，内容捕获默认 opt-in；**没有压缩事件、没有上下文占用率、没有证据存活或约束存活字段**。Anthropic 10 月 14 日为 Claude API 与 SDK 上线 OTel 导出 beta。一个常见陷阱是 client span 与 server span 都带 usage，直接相加会把 token 数翻倍（示例里 14600 实为 7300）。此外内容捕获应走 `gen_ai.input.messages_ref` 外置 URI——这恰好是本期要的「证据外置可回读」的现成接口。

## 四、技术挑战

**挑战一：压缩率是最会骗人的指标。** token 降下来是可测的，证据死了是不可测的。后台压缩「更快但可能多耗 token 且无数字」，阻塞压缩「慢但好审计」——两种模式对同一长任务的证据存活率差多少，没有任何一家给数。

**挑战二：三种退化机制长得一模一样。** 位置偏置（Lost in the Middle，中间 60% 的注意力权重约为首尾的五分之一）、干扰项竞争（取决于与正确答案的相似度而非干扰量）、长输出退化（某些 Gemini 模型在约 500—750 词、某 Qwen 模型在约 5000 词开始拒答或重复）。三者对用户的表现都是「Agent 做错了」，重排检索只治第一种，相关性过滤只治第二种，限制输出长度只治第三种。不先诊断就修，必然修错。**在 Agent 里后果还被放大：静态长文本错了是错答案，Agent 错了是错动作。**

**挑战三：正确的摘要不足以约束行为。** OpenAI 案例里摘要是对的，Agent 读回原文也察觉了矛盾，仍然执行了偏离任务的行为。这否定了「只要摘要忠实就安全」的假设——压缩后的下一步动作必须拿**原始任务文本**而非摘要做独立复核，而这条检查在多数系统里不存在。

**挑战四：禁令的非对称衰减没有进入任何 SLO。** omission 约束 73%→33% 的衰减是轮数深度的函数，可 SRE 平台的自治等级、发布门禁、知识回写门槛都没有「这条禁令在第几轮还成立」的输入。第 299 期审批完整性、第 307 期撤销生效延迟都管动作本身，没人管**没有任何动作时约束自己蒸发**。

**挑战五：责任归属空白。** Google 演示里定位到「从未总结」并给出参数修复，但没有谁承诺「摘要没丢证据」；CloudQ 自定位为观测层；OTel 把内容捕获设为 opt-in 且约定仍在变。**保真责任全链路无人认领**——这与第 312 期演练保真面的结论同构。

## 五、展望与建议

**提出第 234 个空白字段族 `context.decay.*`（本期归纳，缺省 `CONTEXT_DECAY_UNVERIFIED`）**：`compaction.event_id`；`trigger.reason ∈ budget|window|phase|manual` 与 `trigger.token_utilization`；`tokens.before/after`、`compression_ratio`；`evidence.survival[]`（每条关键证据 ID → survived/summarized/dropped，附源 trace 或 span 引用）；`constraint.survival[]`（否定式/禁止式约束在第 N 轮是否仍被确认）；`summary.provenance`（摘要依据消息范围哈希、生成模型、摘要提示）；`rehydration.refs`（外置笔记 URI）；`recheck.after_compaction`（是否用原任务复核下一步动作及结果）；`position.audit ∈ position_bias|distractor|degenerate_output|none`；`verdict ∈ SURVIVED|EVIDENCE_LOST|CONSTRAINT_DECAYED|UNVERIFIED`。

**门禁与治理**：`verdict` 非 SURVIVED 不得据该次调查进入 write≥act，不得把结论回写为确定知识（承 #310/#311/#312 的知识回写闸与环境闸叠加；本期补上「压缩闸」这一此前缺席的前置条件）。两条最小日志即可落地：（1）压缩前后 token 数 + 触发原因 + 摘要依据消息范围哈希；（2）关键证据清单与禁令清单逐条存活状态 + 压缩后原任务复核结果。禁止只报「压缩成功、省了多少 token」。

**采购与评测**：采购两问——能否导出每次压缩的 `evidence.survival[]` 与 `constraint.survival[]`？能否给出压缩后下一步动作与原任务的一致性复核记录？评测在长事故题里增设「早期埋关键禁令 + 中段塞入高相似干扰项 + 强制多次滚动压缩」的配对题，分别报证据存活率、禁令保持率、指代一致性与多次摘要误差累积，而非只报成功率和 token。向 `semantic-conventions-genai` 提案 `gen_ai.compression.event`、`gen_ai.context.utilization`、`gen_ai.constraint.survival` 三属性，并复用已有的 `gen_ai.input.messages_ref` 外置证据。信通院智能运维能力分级在十七层治理上补「压缩交接可举证率」一格。

**本地知识积累（第 189 期新角度）**：余锦泽《Agent 的记忆不在对话里》首次读作「记忆不在对话里，也不等于压缩后还在场——压缩是一次交接，不是一次保存」，配何伟 Harness「可回退的前提是可重放到同一状态」、刘凯宁「关键证据要是被摘要掉了，再快的根因定位也是在猜」、赵恒「存活状态要有权威来源，不能由压缩器自报」、肖汉松阿福小队「持续涌入的 badcase 靠摘要瘦身，但禁令必须原样传递」。

**本期新观点**：行业一直在优化「压缩掉了多少」，却从未计量「压缩后还剩什么、还剩多久」。对 SRE 而言，最危险的不是忘掉任务，而是**忘掉禁令**——因为 commission 记得住、omission 会衰减，而长事故调查恰恰是在最需要「不许做什么」的时候跑得最久。
