# AI-SRE 技术洞察报告 · 第 292 期

**生成时间**：2026-11-20 02:00（系统 `date` 02:00 → 0200 档）
**时间范围**：2026 年，重点最近 30 天（10-22 ~ 11-20）
**本期立面**：干预信用归因面（Intervention Credit Assignment）——系统好了，但真是你救的吗？

> **题眼**：绝大多数 AIOps 平台把"故障是否消失"当作唯一计分板，于是 Agent 与故障同时好转时，动作就被默认为功劳。当修复动作并发、系统又会自恢复，这个默认就变成归因错误。Google 十月披露的 Project Chrysalis 用 step-level Shapley 边际信用给每个动作记账，并明确把"重启数据库连接池"标为有害反射（3,800ms 延迟尖峰）——这是行业第一次把"哪个动作真正救了服务"做成一等计算对象。**归因错了，"自我进化"就不是进化，而是把有害反射写进记忆、让它下次更快发作。**

---

## 一、发展趋势

趋势一，可靠性判断正从"系统是否恢复"转向"动作是否导致恢复"。Google SRE 圣经第二版重写（约 11-15）把"寻找单一根因"改为"检视促成因素"，把 AI 定位为证据整理的辅助角色——实质是承认：把结果改善等同于动作正确已经不够。

趋势二，"自愈"叙事被"受治理自演化"替代。Google Cloud Project Chrysalis 把闭环拆成诊断、自修补、自我批评、记忆、重构五段，自我批评段专门计算每个动作的边际信用（marginal credit），分离有效修复与有害反射；自主动作再由 Model Armor、Cloud KMS、Binary Authorization、OPA 与双人 HITL 逐层约束。只会"做动作"的 Agent 价值有限，会**给动作记账并据此约束下次行为**的 Agent 才进入生产视野。

趋势三，评测口径从"任务成功"转向"证据链可复核"。Anthropic 11-16 的 Claude Code 验证手册称约 90% 代码由 Claude 编写审查，靠的是 E2E、属性、差分三层测试与防篡改规则（REVIEW.md 从默认分支读取，忽略 PR 自身修改；改动一旦能修改评判它的检查，检查即失效）。这套代码侧方法论正被运维侧借用为"动作信用"的工程原型：信用判据必须长在被评动作够不到的地方。

趋势四，国内厂商在"闭环"上收敛、在"归因"上留白。阿里云 11-11 发布全栈 AgenticOps（云监控 2.0／AgentLoop 扩张观测边界、STAROps 闭合链路、OTel/UModel/BRiSE 开源共建），强调"人定目标与边界、Agent 取证跟进"；腾讯云 10-29/30 数字生态大会升级 CloudQ 与 AI 可观测，主线"用 AI 管运维、用可观测管 AI"，关联使用、性能、Token、工具调用与任务质量；火山引擎智能运维助手在响应计划里加 RCA Harness 约束（假设驱动、并行取证、逐轮下钻、结论带置信度）。三家都解决了"怎么查、怎么受控执行"，均未公开"动作功劳如何独立核算"。

## 二、技术现状

把当前主流做法按"信用核算的深度"排成三级，可以更清楚地看到现状的天花板。

**第一级，结果口径**：只看故障是否结束、MTTR 是否下降，这是多数平台的默认口径。致命缺陷是把三件事混为一谈——系统自恢复、他人动作、本 Agent 动作。缓存击穿后流量自然回落，紧随的重启动作便拿到满分功劳；OpenAI 9 月 DNS 事故中，监测 15 分钟内发现、3 分钟后复核、2.5 小时后才杀掉作业——"发现即遏制"的结果口径会把这 2.5 小时整段抹掉。

**第二级，动作口径**：记录动作序列与遥测变化，用 telemetry delta 粗略关联。Google Chrysalis 的 Phase 3 是公开上限：在 P99、HTTP 5xx、连接池饱和度上用 step-level Shapley 对每个 span 算边际信用，数据库重启反射被记 3,800ms 延迟尖峰的负信用，令牌桶补丁得 +0.97 信用，并把"缓存击穿禁用数据库重启、改用令牌桶卸载"作为签名原则蒸馏进语义记忆。它显式惩罚"看着在修、实际在害"的动作——这正是结果口径看不见的一类。

**第三级，反事实口径**：拿生产请求轨迹离线重放候选策略，不在生产试错。同项目中 BigQuery Counterfactual Replay Engine 以向量化内存扫描重放 400 个令牌桶配置（约 0.5ms），找到零 5xx 的 Pareto 最优策略（5 tokens、5.0 req/s），再做 200 并发、100% 缓存清空的混沌验证，零 500、数据库最高负载 13%。反事实是信用的硬基线：没有"不做这个动作会怎样"，所谓贡献只是时间相邻的相关性（post hoc ergo propter hoc）。

三级现状叠加后暴露出一个结构性空白：**没有任何一家把"动作信用"作为可导出、可审计、可脱厂复现的一等字段**。Shapley 值算在 Google 的内存管线里，Claude Code 的验证门作用于代码仓库，阿里 STAROps 的"受控执行"管的是权限边界——它们解决的是"动作该不该放行"，而非"这次放行该记多少功劳、下次该不该据此调整策略"。

这与本系列已覆盖的相邻立面必须划清：#267 恢复判据面问"系统何时算恢复"，#285 静默面问"没故障该不该动手"，#289 分工面问"这一步由规则还是模型做"，#290 证据通道面问"证据有没有送到"。本期只问一个此前无人问的问题：**动作和好转之间那条因果链，凭什么成立、由谁记账、记错了能否被发现**。此外，#291 记忆失活面指出"陈旧教训即投毒"；本期补上它的上游——如果写进记忆的信用本身就是错的，失活检查再严也只是在精确地执行一条错误原则。

**判读**：把"闭环、受控执行、全景图谱、分级自治、OTel 全链路、复测评估"做成发布页卖点的是全部六家；把"这次好转到底算哪个动作的功劳、有害动作有没有被识别并扣分、信用写回记忆前谁签字"做成可导出字段的，只有 Google 一家，且仍是仿真自述。对比表中"反事实基线""信用写回门禁"两列几乎全空——这是继本系列第 213 项市场空白，命名 `intervention.credit.*`。

**新观点（对既有认识的澄清）**：过去我们说"可观测性让 Agent 看得见"，本期要补一句——**看得见动作，不等于看得见动作的功劳**。前者是日志问题，后者是因果问题；把两者混为一谈，正是"自愈率很高但同一故障反复发生"的常见根因。

## 四、技术挑战

**挑战一，并发动作让归因变成组合爆炸。** 一次故障里限流、重启、回滚、扩容往往并发，遥测在动作之间持续变化。Shapley 值给的是"平均边际贡献"，但非平稳系统中同一动作在不同时序下贡献符号可能相反——重启在 stampede 后期也许中性、早期致命。只报一个标量信用会掩盖这种时序依赖。

**挑战二，自恢复是天然混淆变量。** 故障常有峰值—回落的固有形态，任何在回落附近执行的动作都能拿正信用。没有"不动作对照"或反事实重放，Agent 会把系统性自愈学成自己的本事，下次把同样的无效动作执行得更快。

**挑战三，"症状消失"与"根因解决"混记。** operatex 梳理指出，AI SRE 强在应急响应，SLO、错误预算与容量决策仍归人；一次缓解可在不消除根因时拿满分，使 Agent 系统性偏好快速止痛。

**挑战四，信用判据的托管与篡改。** 沿用 #286：若信用计算器由被评 Agent 自己配置、规则与代码同分支提交，Shapley 值也是"当事人记账"。Claude Code 的默认分支 REVIEW.md、Google 的 KMS 签名是工程答案，运维侧尚无规范。

**挑战五，信用的时间有效性无人维护。** 沿用 #291：一条"重启有效"的信用在拓扑变更后不再成立，却仍被高置信度检索命中。信用字段需要失效触发器与撤销链，否则归因错误以"经验"形态长期复利。

## 五、展望与建议

**建议一，新增第 213 个字段族 `intervention.credit.*`，缺省 `CREDIT_UNVERIFIED` 不进自治门禁。** 字段建议：`action_id`+`action_type`（hotpatch/restart/rollback/scale）；`marginal_credit`+`method`（shapley/counterfactual/diff-in-diff）+`baseline_window`；`counterfactual_policy_id`+`replay_coverage`；`harmful_reflex_flag`+触发证据；`credited_by`+`distiller_version`；`invalid_on[]`（沿用 #291 失效触发器）。未声明信用基线的自治流程，不得进 write≥act 等级，也不得写入语义记忆。

**建议二，给动作记账配"三事件分离"最小实现。** 借鉴 Control Room，运维侧至少分离：首个异常时刻、首个干预动作时刻、信用结算时刻、最后有后果的外部动作时刻。四者并排写入事故报告，禁止压成单一"恢复耗时"，否则最慢一段会被平均数吞掉。

**建议三，把"不动作对照"升为标准题型。** 在 SREGym、ORCA-bench、ITBench 增设"故障会自恢复"与"有害反射"两类 seeded failure：同一故障跑 with-agent/no-agent 双轨，报召回、恢复速度、假事故率与**净信用**（相对无代理的改善，单列有害动作次数）。现有基准只计"修没修好"，应补"功劳是不是虚报"。

**建议四，信用判据长在 Agent 够不到的地方。** 参照 Claude Code：归因规则文件与被测分支物理分离（默认分支读取），规则进入需"多次事故复现+独立 agent 证伪+人类签字"，action gate 先走 observe 量出假阳性率再 enforce，两轮失败强制转人工。

**建议五，采购与验收加三问。** ①边际信用如何计算、能否导出？②有无"不动作"或反事实对照基线、覆盖多少流量？③信用写入记忆前谁签字、能否撤销？任一答不出即标注为"结果口径闭环"而非"因果口径闭环"。信通院六维可补「干预信用可举证率」格，与 #289「分工可举证率」、#290「通路可举证率」、#291「记忆失活可举证率」并列成五层治理。

**展望**：未来 6—12 个月盯三件事——Shapley/反事实归因会否进入 OTel GenAI 成为标准 span 字段；AIOps 平台会否把"净信用"写进 SLA 而非只报 MTTR；监管会否要求自动修复提供"动作—证据—信用"三段式记录。谁先把功劳账做成可脱厂复现的收据，谁就掌握"可信自治"的定义权。
