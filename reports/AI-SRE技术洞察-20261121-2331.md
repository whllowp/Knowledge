# AI-SRE 技术洞察（第 312 期）

- 生成时间：2026-11-21 23:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-22 至 2026-11-21）
- 本期主题：优先级面／优先级反转与头部阻塞——加了优先级，低优任务开始饿死

## 题眼

2026-05-19 的一篇工程复盘给出一组很具体的数字：某团队在 70B 推理集群上按业务线划分 P0（实时对话）、P1（批量分析）、P2（离线摘要），预期 P0 毫秒级、P1 秒级、P2 分钟级。上线一周后，P2 平均等待从 30 秒涨到 **8 分钟**，超时失败率从 0.1% 涨到 **12%**，而 GPU 利用率始终在 **65%** 左右——资源没打满，低优任务却跑不动。

根因不是容量，是 strict priority 下的头部阻塞：P0 请求源源不断，P1/P2 永远轮不到执行窗口；白天 P0 有明显波谷，可波谷期的闲置算力也没被低优任务用起来，因为调度器永远先看 P0。

2026 年 6 月的 Clairvoyant 论文把同一现象写进标题：串行 LLM 后端（如 Ollama）在 FCFS 下产生 **Head-of-Line Blocking**——高利用率时，一个短的事实查询可以排在长生成任务后面几分钟。

2026 年 vLLM 的 PR #45561 则暴露了更隐蔽的一种：优先级调度只在 KV 缓存不足时才抢占；当瓶颈是 `max_num_seqs`（运行队列满）时，等待队列的循环无条件退出，**高优请求排在低优运行请求后面，直到有槽位空出**——这就是教科书式的优先级反转。

## 一、发展趋势

**第一，优先级从“配置项”变成“语义承诺”。** 给请求标 P0，等于承诺“它不会被低优任务挡住”。2026 年的实践开始承认：这个承诺在三种情况下会失效——锁被低优持有、队列被低优占满、批处理把长短请求绑在一起。

**第二，固定权重开始让位于“借用 + 回收”。** 加权公平队列（WFQ）理论上给每级保底带宽，但在 GPU 上有三个硬伤：不同优先级请求难以拼成高效 batch（批处理撕裂）、固定比例无法适应流量潮汐（权重僵化）、空闲容量不能借给低优（借贷缺失）。2026 年的方案转向“借用空闲 + 高优回来时回收”。

**第三，预测式调度进入串行/边缘后端。** Clairvoyant 用轻量词法特征预测响应长度，在串行后端做 SJF（最短作业优先）式排序，以缓解长短请求混排的头部阻塞；它承认这是 sidecar 级补丁，不是连续批处理的替代。

**第四，队列公平从“比例”走向“可解释的等待”。** 2026-06-28 的 Agent 模式资料把“优先级排序”与“路由（谁来干）”和“调度（何时干）”分开，并给出适用条件：只有注意力稀缺、而非 CPU 稀缺时，排序才值得复杂度；否则 FIFO 就是正确答案。

**第五，真实系统里的反转开始被当 bug 修。** 2026-07-06 的一个开源项目 PR 记录了生产中的调度器优先级反转：循环监控任务饿死了到期抓取积压（甚至影响到下游），修复方式是恢复严格的一级优先并补回归测试——先写失败测试，再改代码。

## 二、技术现状

**资源型反转。** 低优任务持有锁、连接、KV 块、文件句柄，高优任务排队等它释放；表现是“高优延迟高，但资源利用率不高”。

**队列型反转（饿死）。** strict priority 下，高优持续有请求，低优永远排不到；WFQ 能保底，但权重固定、批处理撕裂、空闲不能借。

**批处理型反转。** 连续批处理把长短请求拼进同一 step，长请求拖慢整批；调度器为了吞吐把低优请求放进 batch，高优请求的 TTFT 被拉长。

**架构型反转。** 串行后端（单请求处理）在混合负载下天然 HOLB；多级代理、sidecar、网关队列各排一次，反转可以在任意一层发生。

**观测盲区。** 仪表通常只有“各优先级平均延迟”与“GPU 利用率”；缺“低优等待时间分布”“高优被谁挡住”“空闲容量为何没被借用”。于是“利用率 65% 却说容量不足”成了常见误判。

## 三、技术竞争力

| 方案 | 反转防护 | 批处理效率 | 空闲利用 | 实现复杂度 | 主要风险 |
|---|---|---|---|---|---|
| FCFS | 无 | 高 | 中 | 低 | 长短混排 HOLB |
| Strict Priority | 无（饿死低优） | 高 | 低 | 低 | 低优永久饥饿 |
| 加权公平队列（WFQ） | 部分（保底） | 低（撕裂） | 低 | 中 | 权重僵化 |
| 借用 + 回收 | 中高 | 中 | 高 | 高 | 回收抖动 |
| SJF / 预测式排序 | 中（缓解 HOLB） | 中 | 中 | 中（需预测） | 预测错误、长任务饥饿 |
| 分池（按优先级隔离） | 高 | 中 | 低（碎片） | 中 | 容量浪费 |
| 抢占式调度 | 高（可抢占运行中） | 中 | 中 | 高 | 状态丢失、重算成本 |

判读：买得到优先级字段、队列、权重、抢占开关；买不到“这次高优延迟是被哪个低优任务挡住的、挡住了多久、空闲容量为什么没被借走、回收时会不会把低优打死”。

本期反转：我们习惯把“加优先级”当成解决延迟分层的答案。但优先级只规定**顺序**，不规定**进展**：低优任务可能永远轮不到，高优任务可能被低优持有的资源卡住，批处理会把两级绑在同一条延迟上。真正的承诺不是“高优优先”，而是“每一级都有进展保证，且反转可被观测”。

判词：「优先级队列／WFQ／抢占／分池／SJF／GPU 调度器／延迟监控」全部可采购，「这次高优延迟被哪个低优任务挡住、低优等待分布如何、空闲容量为何没被借用、回收时谁被牺牲、反转发生在哪一层」不可采购。

## 四、技术挑战

**其一，三种反转同源不同形。** 资源型、队列型、批处理型需要不同的检测信号与修复手段；只加优先级会制造第二种。

**其二，批处理与公平天然冲突。** GPU 喜欢同质 batch；公平要求混排。撕裂的代价是吞吐，不撕裂的代价是延迟。

**其三，空闲容量不可借。** strict priority 下高优波谷的闲置算力无法给低优；借用机制又要在高优回来时快速回收，回收抖动会伤低优。

**其四，预测会错。** SJF 依赖响应长度预测；预测错时长任务被反复插队，形成新的饥饿。

**其五，跨层反转。** 网关、sidecar、调度器、后端各自排队；修复一层可能把反转推到另一层。

**其六，观测不指向责任。** 平均延迟与利用率无法回答“谁挡住了谁”，复盘只能猜。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要按优先级的等待时间分布、阻塞归因、空闲借用率与回收次数。
- 业务属主：需要知道自己的任务在最坏情况下能拿到多少进展保证。
- 调度团队：需要“借用 + 回收”的参数与回退策略（回收过猛会打死低优）。
- 容量规划：需要区分“容量不足”与“调度反转”，避免用扩容掩盖饥饿。

**用户旅程（一次“加了优先级反而更慢”的事故）。**

1. 团队给实时对话标 P0、批量分析 P1、离线摘要 P2，使用 strict priority。
2. 白天 P0 持续有流量，P2 排队从 30 秒涨到 8 分钟，超时率 12%；GPU 利用率只有 65%。
3. 值班按“容量不足”扩容；扩容后 P0 更快，P2 仍饿死——因为调度器永远先看 P0。
4. 改用 WFQ，P2 有了保底，但不同优先级请求拼不成高效 batch，整体吞吐下降。
5. 夜间 P0 骤降，P2 仍只拿到固定权重的那一份，空闲算力没有被借走。
6. 复盘写成“优先级配置不当”；真正缺的是**进展保证与反转归因**。

**实现方案（90 天）。**

- 第 1–2 周：建立优先级语义台账——每级的等待目标、进展保证（最小配额/最大等待）、可被抢占的条件。
- 第 3–4 周：观测三件事——按优先级的等待分布、GPU 利用率缺口、高优请求的阻塞归因（等锁/等槽位/等批次）。
- 第 5–6 周：调度策略升级——从 strict priority 改为“保底 + 借用 + 回收”：低优有最小进展，高优波谷时空闲可借，高优回来时按预算回收。
- 第 7–8 周：批处理治理——按优先级/长度分桶，避免长短混批；高优请求可跳过批或走小批快路径。
- 第 9–10 周：抢占与幂等——被抢占的请求要能安全重放（幂等键、检查点），避免回收造成重复副作用。
- 第 11–12 周：跨层排查——网关、sidecar、后端各层的队列长度与等待时间打通，定位反转发生在哪一层。
- 第 13 周：演练与验收——人为制造高优洪峰，验证低优仍有进展、高优不被低优持有资源挡住、回收不造成二次饥饿。

**验收标准。** 任一次延迟分层事件，能回答：高优被谁挡住、挡了多久、低优是否有进展、空闲是否被借用、反转在哪一层、扩容是否真的必要。

**第 224 个市场空白（五项）**：优先级进展保证台账；阻塞归因（等锁/等槽/等批）；空闲借用与回收预算；批处理分桶策略；跨层队列统一视图。

**`priority.*`／`inversion.*` 第 191 次无人提字段族**：`priority.progress_guarantee`、`priority.blocked_by`、`priority.borrowed_capacity`、`priority.reclaim_count`、`priority.inversion_layer` 在调度器、网关与 GPU 推理引擎之间没有统一语义；平台只报“各优先级平均延迟”。

**本地 173／173-kb 连续第 179 期成组启用**（赵恒 25）：本地知识库把“优先级”与“进展”分开记账；本期把优先级反转落成阻塞归因与借用回收。
