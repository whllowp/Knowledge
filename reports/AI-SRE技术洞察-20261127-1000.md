# AI-SRE 技术洞察 第 331 期（2026-11-27 10:00）

## 结论保鲜期面 / Verdict Freshness Integrity

> **题眼：诊断写下时的世界，和现在引用它的世界，还是同一个吗？** ——SRE Agent 把"结论"（根因判定、痊愈状态、写入记忆的规则、批准的处置方案）当成永久资产存起来，却没人给它标生产日期。行业已经计量了结论"对不对"（真值可靠性）、"能不能复演"（决策可复演）、"依据哪一路信号"（跨源冲突），唯独没人计量"结论还新鲜吗、过期了谁负责重新举证"。

---

## 一、发展趋势

2026 年 11 月，SRE Agent 的三条一线进展把"结论的时效性"第一次推到台前，虽然它们各自都没用这个词。

**Google 开源 AQuA（Ambient Quality Agent，10-08 官方博文、11-13 InfoQ 报道）**，把生产会话采样、聚类、验证、归因做成一个跑在请求路径之外的旁路服务。关键设计有三点：每个发现必须引用部署时不可变源码快照的有效行；"洞察的价值在于引用依据，而非自报置信度"；问题状态 NOW/RECURRING/RESOLVED 中，**RESOLVED 是"连续 14 天未再观察到"自动置位**。这是一条隐性的"痊愈判定法则"——沉默被当成了痊愈。Google 自己承认两个限制：单次最多采样 1000 个会话会漏掉罕见故障，replay 不忠实复现外部状态（例如第三方系统里那个座位在原始时刻是否真的可订）。

**Anthropic 11-06 工程博客《The components of agent memory》**把记忆拆成四层（会话日志、Agent 自写笔记、wiki 表征、每会话无条件加载的注入上下文），并给出反直觉的结论：验收不该测"记得对不对"，该测"**一条错的东西能活多久、能扩散多远**"。注入层 token 最少却全局生效，一条错笔记每次开场都被读一遍；"做梦"（dreaming，空闲时对照日志校对笔记）才可能修正。官方宝可梦实验里，把"山洞在东侧"记错并升级为"山洞已通关"的笔记，让 Agent 反复跳出单向台阶、三次后放弃；做梦校对回到正确位置后，那一次直接走进山洞到了下一座城市。

**OpenAI 11-09 Control Room** 则相反：它把终止权做成**持久且下沉**的——每个研究任务绑定唯一 job_id 与已批准的 safety case，推理引擎每次产出前向中央服务鉴权，一旦标记终止，后续请求一律拒绝，35 秒上界来自鉴权缓存。这是"撤回（revocation）"的工程化，但 fail-closed 也意味着撤回机制故障会误伤全部任务，且"不杀进程、只断供"——终止是输出的断供，不是世界的复位。

三条线合起来勾勒出一个共同缺口：**结论被写入（诊断、痊愈判定、记忆条目、批准的 safety case）之后，默认长期有效；而它锚定的那个世界（代码 revision、拓扑版本、模型 pin、依赖版本、用户偏好、外部系统状态）一直在变。** 没有生产日期、没有过期触发条件、没有重新举证责任人。

## 二、技术现状

现状可以概括为一句话：**证据链做得很厚，结论的保鲜期却是空白。**

可观测性侧，阿里云在云栖提出 AgenticOps 的"三道墙"——采集标准化（LoongSuite/OBI，基于 OTel）、统一语义建模（UModel）、能力评测（BRiSE），目标是"事实可采、故障可读、能力可验"。腾讯云 11 月的 AIOps 实战文章给出三层内核（数据底座、根因推理、多智能体执行），强调根因定位"附带完整证据链，运维人员能逐条核对"，并引用 OTel 在生产环境超过 78% 采用率的说法。AWS DevOps Agent 的接入矩阵已覆盖 CloudWatch/CloudTrail/EKS、Datadog/Dynatrace 等第三方告警、GitHub/GitLab 代码与 CI、以及 MCP/A2A/Skills 扩展。这些都是**把证据取回来、把过程记下来的能力**，没有一项回答"这条证据支撑的结论，还作不作数"。

评测与治理侧同样如此。ORCA-bench、ITBench-AA 等基准在 11 月持续发酵，衡量的都是"这一次答得对不对"；CTBench 让 15 位平均 20 年经验的专家双盲标注，量化了"人类自己也不一致"（RCA 仅 56.4%）；第 330 期据此提出真值可靠性面，解决的是尺子的刻度误差。但这些工作都默认一个静态世界：**同一道题、同一份证据、同一把尺子**。一旦代码改了、拓扑换了、模型换代、用户偏好被覆盖，昨天被专家签字确认的根因，今天就可能是一个精致的错误。

运维知识图谱是这个问题最集中的地方。Netflix 11-25 公开的运维知识图谱实践、腾讯 CloudQ 的运行图谱 RAG、以及 Meta Diviner（arXiv 2610.21281）提出的 agentic RCA 四阶段生命周期，都把知识入库设计成"回放 + 质检 + 属主审批"——**入库时有守门人，入库后没有保质期**。Meta Diviner 自己列出的诊断缺陷第一条就是"过期上下文"。这构成了一个刺眼的不对称：我们花大力气保证知识"进得干净"，却任由它"放得太久"。

## 三、技术竞争力：主要厂商/方案对比

下表按"结论能否被追溯到一个世界快照、是否设过期触发、撤回能否传播到下游"三列来比较，而非按功能丰富度。这也是本期提出的新评价维度。

| 方案 | 结论载体 | 是否锚定世界快照 | 保鲜/过期机制 | 撤回传播 | 保鲜可举证性 |
|---|---|---|---|---|---|
| Google AQuA | 发现→聚类→问题状态 | 是（部署时不可变源码快照 + 引用行号） | RESOLVED = 14 天未再观察；无 TTL/重举证 | 无回开机制；replay 不忠实外部状态 | 部分（引用可查，"痊愈"不可证） |
| Anthropic 记忆四层 | 笔记/wiki/注入上下文 | 否（无 revision/来源时效字段） | 做梦校对（离线、非保证）；注入层永久生效 | 无传播；改笔记不重建 wiki 与注入 | 空白（官方只报扩散，不报保鲜） |
| OpenAI Control Room | job_id 终止 + 批准 safety case | 是（job_id 绑定批准方案） | 终止持久、fail-closed；safety case 无过期 | 强（推理层每次鉴权、断供即传播） | 部分（撤销可证，正确性不可证） |
| 阿里云 LoongSuite/UModel/BRiSE | 调查上下文 + 评测集 | 部分（OTel 标准化采集） | 三道墙解决入库质量，无出库保鲜 | 无 | 空白 |
| 腾讯云 AIOps / CloudQ | 证据链 + 运行图谱 RAG | 部分（图谱 RAG） | 未见 TTL/重举证字段 | 未见 | 空白 |
| AWS DevOps Agent | Skills（runbook 技能化）+ 调查结论 | 部分（关联代码/CI 变更） | 事件预防建议，无技能版本保鲜 | 未见 | 空白 |
| 字节跳动 Seed Laminar | 异步 RL 产出的策略/权重 | 是（版本一致的权重快照） | 权重持续更新，但旧结论无失效通知 | 断供式（失败副本重启续跑） | 空白（模型换代使旧判定过期） |
| Laminar（观测平台） | 生产 trace→回归数据集 | 是（OTel trace ID） | 失败模式聚类，无结论 TTL | 未见 | 空白 |
| 本地 173：余锦泽《Agent 的记忆不在对话里》 | 跨会话记忆条目 | 否 | 提出记忆外置与检索，未涉及过期 | 未涉及 | 空白 |

**结论**：可采购的能力集中在"锚定快照"这一列（AQuA、Control Room、Laminar），但没有任何一家把"结论时效"做成一个可查询、可门禁的一等字段。厂商竞争的是"能不能给出结论"，下一轮竞争将是"敢不敢为结论的保鲜期签字"。

## 四、技术挑战

**挑战一：痊愈判定把沉默当证据。** AQuA 的 14 天未复发、告警平台的"连续 N 分钟正常"、人工复盘的"已恢复"——共同缺陷是"没观察到"不等于"不存在"。若根因在采样盲区（1000 会话上限之外）或外部状态漂移（replay 不复现），结论会带着 RESOLVED 标签继续错误。更麻烦的是，一旦标为 RESOLVED，重新调查的触发条件就被移除了。

**挑战二：记忆的错误是全局且静默的。** 注入层每条会话无条件加载，一条错误规则的扩散半径等于全部会话；做梦校对是非确定性的离线过程，无法保证何时修正；"57 个事实合并成 41 个"揭示记忆压缩本身就是有损的。检索命中率高，只会让错误被更自信地调用。

**挑战三：撤回与写入不对称。** Control Room 证明撤回权下沉可行的同时，也暴露了代价：fail-closed 让撤回机制本身成为单点；35 秒来自缓存，缓存换吞吐的账必须算清；"不杀进程只断供"意味着被撤回的判断可能仍在其他副本、下游 Agent、缓存的摘要里继续生效。撤回的可达性（revocation reachability）没有被计量。

**挑战四：跨层过期检测缺位。** 一个根因结论锚定的是代码 revision + 拓扑版本 + 模型 pin + 依赖版本 + 用户偏好 + 外部系统状态六元组。任一层变化都可能使它过期，但现有系统没有把这六层的变化事件订阅到结论上。模型换代（字节 Laminar 式的持续权重更新）、依赖升级、偏好覆盖都在静默发生。

**挑战五：责任归属空白。** 结论过期后仍被引用造成事故，责任在写下结论的 Agent、批准的方案 owner、还是引用时未校验的下游？没有字段记录 last_reattested_by，事故复盘只能停在"模型幻觉"。

## 五、展望与建议

**提出第 252 个空白字段族 `verdict.freshness.*`**（承 #310~#330 可举证率系列叠加）：

```
verdict.freshness.* {
  subject_ref,                      // 结论对象：根因/RESOLVED/记忆规则/skill/批准方案
  asserted_at,
  world_snapshot_ref,               // 代码 revision/拓扑版本/模型 pin/依赖版本/偏好快照
  freshness_ttl, expiry_trigger[],  // 过期时长与显式触发事件
  reattestation_due_at,
  last_reattested_at, reattested_by,
  stale_signal[],                   // 哪些底层已变
  referencing_count_while_stale,    // 过期后仍被引用的次数
  revocation_reachability,          // 撤回是否传播到注入层/wiki/下游/缓存
  counterfactual.snapshot_swapped_verdict_changed,
  verdict ∈ FRESH|STALE_REATTESTED|STALE_IN_USE|REVOKED_INCOMPLETE|UNVERIFIED
}
缺省 VERDICT_FRESHNESS_UNVERIFIED；verdict≠FRESH/STALE_REATTESTED 不计入"已独立复核"合规声明、不作自治升档。
```

**四条最小动作**：① 每个结论写入时强制附带 world_snapshot_ref，六元组任一变化即产生 stale_signal；② RESOLVED 从"沉默 N 天"改为"沉默 N 天 + 世界快照未变 + 重举证到期复查"，否则退回 STALE_IN_USE；③ 记忆写入层给注入条目加来源、有效期与 revision，过期条目自动降级为"按需查"而非"开场注入"；④ 撤回做成可达性检查（注入层、wiki、下游 Agent、缓存摘要四处对账），而非只改一处。

**采购三问**：你们的结论能否导出 world_snapshot_ref？RESOLVED 的置位条件是否包含"世界未变"？撤回一次判断，能否证明下游全部失效？

**配对评测题**：给同一结论做 A/B——A 组世界快照不变，B 组只改一个底层依赖版本（不改证据文本），测量 `verdict_freshness_violation_rate`（B 组仍被采信比例）与 `reattestment_hit_rate`。建议信通院六维评估补一格"结论保鲜可举证率"，与 #316~#330 的十四格并列。

**新观点收束**：**结论不是事实的镜像，是某一时刻世界快照的压缩包；解压它的世界变了，包还在，内容已经错了。** 可观测性走到了"信号有主人"（#322）、"真值有刻度误差"（#330），下一步必须走到"结论有保质期"。否则我们只是在规模化地复用过期判断——而且因为有完整证据链，错得格外自信。
