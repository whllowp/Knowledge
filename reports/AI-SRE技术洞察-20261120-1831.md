# AI-SRE 技术洞察（第 309 期）

- 生成时间：2026-11-20 18:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：噪声邻居面／共享资源上的相互干扰与归因——“谁在吃我的余量”是证据问题，不是隔离问题

## 题眼

2026-08-25，openFuyao 社区发布众核编排系统 MCO，开篇第一句就把问题说透：众核混部集群里，离线业务对共享硬件的“无声侵占”——LLC 缓存冲刷、块设备 I/O 队列挤占、内存回收压力——**Cgroup 无法完全隔离**，于是成为在线业务长尾延迟抖动的根源。它采集的干扰信号是 LLC miss rate 与 occupancy、块 I/O 的 P95/P99、PSI 的 I/O 与 memory 压力。

2026-08-10，GPUMachines 的一篇分析给出另一半：*Attribution is not isolation*（归因不是隔离）。共享批处理把多个租户的请求放进同一个 step，单请求的 p99 不再归属于某个租户；平台能做的是“估计每个请求该占多少”，而不是“证明这次延迟是谁造成的”。

两句话合起来就是本期的问题：**隔离可以让干扰变小，归因才能让干扰被处理。** 而 2026 年的工具链，前者买得到，后者买不到。

## 一、发展趋势

**第一，混部从“省钱手段”变成“默认架构”。** ElastiCo（2026-08-08）把训练与离线推理放进同一批 GPU：训练在周期性空闲阶段仍独占整卡，离线推理突发又过度配置，结果 GPU 平均利用率只有约 25%。它用“资源形态变换 + 弹性影子定价 + 干扰感知混部”把利用率推到 46%，JCT 最多降到 1/2.94，吞吐提升 2.02 倍。

**第二，干扰感知开始进入调度器。** openFuyao 的 MCO 把“节点干扰分析”做成 Volcano 的调度输入：选节点阶段就规避高干扰节点，再用 Kata 虚拟机级隔离切断物理串扰。调度与隔离变成两层防护，而不是一个开关。

**第三，干扰信号从“CPU 指标”扩到“共享资源族”。** 美团容器云的公开案例（2026-04-24）回顾了从 Google 2013 年的 CPI 预测，到 openEuler 用 eBPF 采集 SLI 的演进；原因是单一 CPI 只适用于 CPU 密集型应用，而真实干扰来自缓存、I/O、内存回收多个方向。

**第四，GPU 层的干扰被单独研究。** 2026 年的弹性 MIG 论文按租户采集 p95/p99/p999、NVML、PCIe 计数器，用驻留时间与冷却期防抖动；HAMi 的共享 GPU 实验则提醒：`nvidia-smi` 看不到真实分配，限额是否真的生效要单独证明。

**第五，干扰开始有安全含义。** 2026-09-07 的一项测量显示，共享 GPU 上可以通过时序侧信道识别邻居在跑哪个模型（单卡 0.60 倍噪声底，张量并行下 2.02 倍）；隔离不足不只是性能问题。

## 二、技术现状

**资源隔离层。** cgroup v2 管 CPU/内存/IO 权重；MIG 切 GPU 显存与算力；Kata/云 Hypervisor 做物理隔离；SPDK/IO 隔离做队列。隔离能限住“用量”，限不住“共享结构的争用”（LLC、内存带宽、PCIe、NVLink）。

**干扰检测层。** PSI 提供“有多少时间在等资源”，是当前最通用的信号；LLC miss/occupancy、块 I/O 尾延迟、steal time、GPU SM 利用率与显存带宽是补充。单看任何一个都会误判——PSI 高可能是自身 IO 模式变了，不一定是邻居。

**归因层。** 平台通常只有“受害者视角”的时序与“加害者视角”的资源曲线，缺“调度事件”这一环：哪个 Pod 在何时被放到同一节点、超卖比多少、谁与谁时间重叠。没有这一环，归因只能靠猜。

**共享批处理层。** 连续批处理把多请求拼进一个 step，吞吐上去了，单请求延迟被摊平；LLMVisor 类工作试图按 step 分配“每个请求该占多少”，但这是**估计**，不是证据。

**安全层。** 时序侧信道说明“共享”本身会泄露信息；对多租 GPU 平台，隔离级别同时是性能与保密的边界。

## 三、技术竞争力

| 方案 | 解决的问题 | 干扰可见性 | 归因能力 | 代价 | 适用场景 |
|---|---|---|---|---|---|
| cgroup v2 权重/限额 | 用量上限 | 低 | 无 | 低 | 通用容器 |
| PSI + eBPF SLI | 等待压力 | 中 | 弱（无加害者） | 中 | 混部节点 |
| LLC/IO 计数器 | 缓存与队列争用 | 中高 | 弱 | 中 | 延迟敏感在线业务 |
| MIG / 显存切分 | GPU 资源隔离 | 中 | 无 | 中（碎片化） | 多租推理 |
| Kata/VM 隔离 | 物理串扰 | 低（隔离后看不见） | 无 | 高（密度下降） | 强隔离要求 |
| 干扰感知调度（Volcano 等） | 选节点规避 | 中 | 弱（事前） | 中 | 混部集群 |
| 弹性 MIG 控制器 | 动态重配 | 高（按租户 p99） | 中（需控制器日志） | 高 | 多租 GPU 平台 |
| 共享批处理（连续批） | 吞吐 | 低 | 极弱 | 低 | 推理服务 |

判读：买得到隔离、采集、调度规避；买不到“这次 p99 是谁造成的”这一句可举证的话。平台把“干扰检测”做成指标面板，但事故复盘要的是**时间重叠证据**：受害请求、加害任务、同一节点/同一卡、同一时间窗。

本期反转：我们习惯把噪声邻居当成“隔离没做好”，于是加限额、切 MIG、上 Kata。但干扰的伤害不在“平均值变差”，而在“尾延迟不可归因”：同一个 SLO 破裂，可能是邻居、可能是自身流量、可能是共享队列，三者用现有仪表分不开。**先建归因，再谈隔离**——否则隔离只是把不可解释的延迟挪到另一个池子。

判词：「cgroup／MIG／Kata／混部调度器／PSI 采集／GPU 共享／尾延迟监控」全部可采购，「这次 p99 是谁造成的、干扰从哪个共享资源进来、超卖比多少、受害请求与加害任务的时间重叠证据、下一次调度是否还会把两者放一起」不可采购。

## 四、技术挑战

**其一，干扰是多源的。** LLC、内存带宽、块 I/O、PCIe、GPU 显存带宽同时争用；单信号阈值必然误报。

**其二，受害者与加害者视角不对称。** 受害方只有延迟曲线，加害方只有资源曲线；没有调度事件，两条曲线对不上。

**其三，共享批处理破坏请求级归因。** 一次 step 里混着多个租户，p99 属于“这一步”，不属于“这个请求”。

**其四，超卖比是财务参数，不是技术参数。** 超卖由成本目标决定，干扰由共享结构决定；两者在同一张账单上，却不在同一套指标里。

**其五，隔离与密度的取舍没有统一答案。** Kata 降密度、MIG 碎片化、cgroup 限不住缓存；选型必须按业务尾延迟敏感度分层。

**其六，安全边界被忽略。** 时序侧信道证明共享会泄露；干扰治理若只看性能，会把保密问题留在原地。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要“受害请求—加害任务—调度事件”的三方关联，以及超卖比与干扰率的联合视图。
- 业务属主：需要知道自己的尾延迟对邻居的敏感度，以及被干扰时的降级策略。
- 调度团队：需要干扰感知的放置策略与回退策略（规避失败时怎么办）。
- 安全：需要共享资源的隔离级别与侧信道风险评估。

**用户旅程（一次“尾延迟莫名翻倍”的事故）。**

1. 在线推理服务 p99 从 800ms 涨到 2.3s，平均延迟几乎没变。
2. 节点 CPU 利用率 55%、内存充足，常规仪表全绿；PSI 的 IO 与 memory 在故障窗口抬升。
3. 同节点上刚调度进一批离线批处理，LLC occupancy 上升、块 I/O 队列变长。
4. 平台无法证明“批处理导致推理变慢”：两者时间重叠，但没有放置事件与超卖比的关联视图。
5. 值班先扩容，尾延迟短暂缓解；第二天同节点再次混部，问题复现。
6. 复盘写成“容量不足”；真正缺的是**干扰归因**与放置策略。

**实现方案（90 天）。**

- 第 1–2 周：给混部节点建干扰信号基线——PSI（CPU/IO/memory）、LLC miss/occupancy、块 I/O P95/P99、GPU SM 与显存带宽；按节点与业务分层。
- 第 3–4 周：打通调度事件——记录每次放置的节点、同节点租户、超卖比、时间窗；与延迟曲线做关联查询。
- 第 5–6 周：定义“干扰事件”——受害业务 p99 超基线 N 倍、同节点存在资源争用信号、时间重叠成立；三者齐备才立案。
- 第 7–8 周：放置策略——对尾延迟敏感业务打标，调度器优先避开高干扰节点；规避失败时明确回退与告警。
- 第 9–10 周：隔离分层——强隔离（Kata/独占）给 P0，MIG 给多租推理，cgroup 给一般业务；每层记录密度代价。
- 第 11–12 周：安全评估——对共享 GPU 做侧信道风险评估，明确哪些租户组合不允许共卡。
- 第 13 周：演练与验收——人为制造邻居干扰，验证能否在 10 分钟内定位到任务与资源；复盘必须带时间重叠证据。

**验收标准。** 任一次尾延迟异常，能回答：受害请求、同节点任务、争用资源、超卖比、时间重叠证据、放置策略是否本可避免。

**第 221 个市场空白（五项）**：三方关联（受害/加害/调度事件）；干扰事件立案标准；超卖比与干扰率联合视图；尾延迟敏感业务的放置标签；共享资源侧信道风险评估。

**`interference.*`／`noisy_neighbor.*` 第 188 次无人提字段族**：`interference.victim_request`、`interference.aggressor_task`、`interference.shared_resource`、`interference.overlap_window`、`interference.overcommit_ratio` 在调度器、cgroup 与 APM 之间没有统一语义；平台只报“节点负载高”。

**本地 173／173-kb 连续第 176 期成组启用**（朱革 15）：本地知识库把“干扰”与“容量”分开记账——容量不足是买得不够，干扰是放得不对；本期把两者落在同一张时间重叠证据上。
