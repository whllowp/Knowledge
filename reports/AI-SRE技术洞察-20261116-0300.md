# AI-SRE 技术洞察（第 202 期）

**生成时间**：2026-11-16 03:34（北京时间，经 `date` 命令获取）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：审计空洞面／记录沉默面（Audit Gap / Record Silence）——一条日志"没出现"，可能是合规策略故意跳过、可能是记录管道出错、也可能是真的什么都没发生；三种原因在表里长得一模一样，而 Agent 偏偏把"没记录"读成"没异常"

**题眼**：Google Cloud 2026-11-13 的 Data Cloud 更新里藏着一句该读两遍的话——面对行级安全、列级策略标签、动态脱敏的知识源，一个 **fail-closed 检查会跳过记录**；而执行 **fail-open，记录失败永不打断会话**。官方分析直白点破："**在你数据受保护最强的地方，transcript 按设计就有洞；`agent_events` 里少一轮，可能是策略结果而不是 bug——先确认，再当它是故障**"。同一周 OpenRCA 2.0 给这个现象起了个名字：**presence bias，沉默被读成健康**。六家把"每一步都记、导出到你自己的表"讲成可观测的胜利，没有一家把"**这一轮为什么没有记录**"做成一个字段。

## 一、发展趋势

2026 年 Agent 可观测的主线是"记录得更多"：OTel 成为入场券，全量 span、逐步 transcript、成本计量被塞进同一张表。但最近 30 天出现了三条反向曲线，指向记录得"更诚实"。

第一条是**合规开始主动给日志打洞**。Google 11-13 把运营遥测（Cloud Monitoring 指标、Cloud Trace 净化 span）与对话内容分治：净化 span 有意排除用户提示、模型回复、内部思考与生成的 SQL；更深的 transcript 审计按 Agent 逐个开启，由服务写入客户自有 `agent_events` 表——**但只要知识源用了行级安全、列标签或动态脱敏，那一轮就不记**。保护越强，记录越空。

第二条是**评测开始惩罚"沉默即健康"**。OpenRCA 2.0（2026-06，11 月持续被引用）在 500 起事故上标注因果路径，11 个前沿模型正确点名根因服务 76.0%、落到已验证路径 61.5%、精确恢复根因集合仅 20.7%；作者点名三种失败模式：过早承诺、**presence bias（服务停止发数据被当成健康）**、最响信号捕获。SWEOps-Bench（11-04）更狠：55 个真实 K8s Operator 缺陷，故障发现 72.7%–90.9%、端到端关闭仅 14.5%–52.7%，并记录了"**告警被清除、却没通过绑定该故障的检查**"这类假闭合。

第三条是**治理把"过程可审计"写进标准，却没定义审计的空洞**。信通院《云上 Agent 基准度量模型》六维中"过程可审计"被腾讯云 CloudQ 等首批认证引用，但可审计的对象默认是"**记录下来的那部分**"。数据都在、日志很满，唯独"这一轮为什么缺"无人负责。

三条曲线交汇出一个新对象：不是证据够不够（第 101 期）、不是原件能不能拿到（第 94 期）、不是数据归谁（第 194 期），而是**缺席本身是否被记录、被解释、被计分**。

## 二、技术现状

本期把"日志的缺席有无语义"立为一等对象，与近几期显式划界：第 94 期取证面管"事后能否拿到未被改过的原件"，第 101 期证据可得面管"Agent 开口前证据集缺哪几样"，第 187 期隐私面管"全内容 vs 元数据"的零和，第 194 期数据主权管"遥测归谁"，第 185 期度量主权管"尺子谁定"。本期只问一件事：**一条没出现的记录，系统知不知道它没出现，能不能说出为什么**。

缺口之所以危险，是因为三种原因在日志里**塌缩成同一个空值**。一是策略性跳过（合规要求不记），二是记录管道失败（fail-open 设计下不打断会话，错误被吞），三是真实无活动。现有栈没有 `skip_reason` 字段把它们分开，于是排障者、审计者、评测器面对同一个"什么都没有"的格子。最锋利的后果正是 presence bias：**沉默被当成健康**——服务不再发数据被读作正常，跳过记录的敏感查询被读作没发生，清掉告警被读作修复完成。

这一期是对往期判词的**换角度澄清**：第 94 期说"trace 允许遗忘、证据不允许"，本期补一句——**当遗忘是合规要求时，遗忘这件事本身必须留下证据**；第 187 期说"full-content 归因强但泄 PII、metadata-only 合规但归因弱"，本期补一句——真正的第三种选择是"**按源声明净化范围＋对跳过打标**"，而不是在两难里二选一。本地 173 库里，刘凯宁 05「结论／证据／待确认项」的三段式诊断报告，恰好把"不知道"写进了产物结构；施宏斌 14「从识别、展开、质疑到验证，还缺什么证据」把缺口当成方法学一环。判词是：**本地把"缺"显式写成字段，联网侧 Google 11-13 却把"跳过"做成对审计者不可见的沉默；两边都没把"为什么没有记录"做成可导出字段**。

|---|---|---|---|---|---|---|
| Google（BigQuery/Looker 11-13） | 强：净化 span 明确排除 prompt/回复/思考/SQL | 弱：官方承认"少一轮可能是策略结果而非 bug"，无原因码 | 弱：fail-closed 跳过＋fail-open 执行，洞被设计出来 | 强：transcript 按 Agent 逐个 opt-in | 中：写入客户自有 `agent_events`，但缺轮无标签 | 弱：Prism 测答案准确率，不测空洞 |

**反转判读**：最硬的态度来自评测侧——SWEOps-Bench 把"告警清除但检查没过"直接判失败，OpenRCA 2.0 把"沉默读成健康"列为三大失败模式之一；最软的一环恰恰在产品的记录层。六家把"全量采集、导出到你自己的表"讲成可观测胜利，Google 甚至诚实到写出"少一轮可能是策略结果"——却转身把这句话留在博客里，没有变成一行 `skip_reason`。判词：**OTel、全量 span、客户自有表、 fail-closed 授权、净化与脱敏全部可采购；举证"这一轮为什么没有记录、沉默不是健康"，不可采购**。

## 四、技术挑战

第一难是**原因塌缩**：策略跳过、管道失败、真实空闲共用同一个空值，缺的是可区分的枚举与来源戳。第二难是**fail-open 的代价被转嫁**：为了让会话不中断，记录错误被吞掉，审计完整性成了隐形牺牲品——这与 OpenAI Control Room 把 fail-closed 用在推理授权上形成刺眼反差：**闸门用 fail-closed，账本用 fail-open**。第三难是**合规与取证的零和**：越保护的数据越没记录，出事时越无法举证"我们确实合规地没记"。第四难是**评测盲区**：Prism、RCA-Bench、ITBench 测的是答案对不对，不测"记录的全不全"；一条看着健康的 trace 配一个错的答案，正是 XYBench（11-13）揭示的状态——模型专注底层目标仅 35%–41%，人类参考 55%。第五难是**假闭合**：R2Act（07-06）里最强模型点名正确服务 91.4%–99.7%，但给出规则接受的修复仅 36.8%–60.3%；755 份被拒方案中 513 份选了事故根本没要求的动作——"修好了"的记录和"修好了"的事实之间存在系统性裂缝。

## 五、展望与建议

建议把"缺席"升为一等字段族 `audit.silence.*`，五项最小集：`skip_reason`（policy / error / idle 三值枚举）、`sanitized_scope`（本轮净化了哪些属性）、`silence_not_health`（静默不得计为健康的显式布尔）、`closure_verified`（关闭告警与通过故障绑定检查双条件）、`completeness_slo`（每任务记录完整度目标）。这是第 142 个市场空白、`audit.silence.*` 第 111 次无人提字段族。

落地三步：其一，对敏感源把"跳过"从静默改成**带原因码的占位事件**——记录"这一轮按策略未记"，而不是留空格；其二，把 fail-open 的记录失败**单独计数并告警**，让账本与闸门采用同一套失败姿态；其三，评测扩展——在 SREGym/SWEOps-Bench 类基准里加入"缺轮检测率"和"假闭合率"，并要求净化范围随 trace 导出。对采购方，把一句话写进合同：**能举证"这一轮没记录是因为合规跳过、且该跳过本身已被记录"**，才算过程可审计。
