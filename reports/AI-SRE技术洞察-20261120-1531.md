# AI-SRE 技术洞察（第 306 期）

- 生成时间：2026-11-20 15:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：检出面／告警有效性验证——安静不等于安全，可能是盲

## 题眼

2026-09-13，Zenodo 上一份 v4 论文的标题问得很准：*Quiet or Blind?* 它测的不是“规则写得像不像”，而是**把规则执行起来**：15 个模型配置、7 家组织，生成检测规则后逐条跑，看排除子句（exclusion）到底压掉了多少误报、又吃掉了多少真攻击。

结论对 SRE 同样成立：一条规则对运营者收两次费——每次误报收分析员时间，每次漏报收驻留时间；而**排除子句**同时决定这两笔账。用文本相似度评、或用“抓住了哪些攻击”评，都看不见“这条规则之所以安静，是因为它瞎了”。

这正是告警有效性验证的核心难题：**沉默是两种状态的叠加**——系统正常，或检测失效。只测“触发时是否触发”，永远分不开这两者。

## 一、发展趋势

**第一，验证从“规则语法”下移到“规则执行”。** 2026-11-16 的一个开源仓库把 Grafana 告警规则在 CI 里用 `pint` 与 `promtool` 双工具校验，并从单一事实源派生 Prometheus 原生规则文件、派生文件不入库——消灭“手写副本漂移”。语法与单测成为最低门槛，而不是终点。

**第二，四层验证开始成型。** runbook.academy 的告警测试课程把验证分成：静态校验（`promtool check rules`）、单元测试（`promtool test rules`，给定序列断言是否触发）、集成/回放（把历史数据灌回规则）、生产金丝雀（定时翻转指标，走完整条链路）。第四层才回答“告警真的会到人”。

**第三，金丝雀告警的“缺席即信号”被认真对待。** 该课程给出一段真实配置：每小时翻转一次指标、持续 6 分钟、规则 `for: 5m`；配套一条元告警——`time() - alertmanager_last_evaluation_timestamp_seconds` 过大即报警，意思是“Alertmanager 已经 5 分钟没评估规则”。金丝雀不响时，你无法区分“链路正常”与“金丝雀自己没跑”，所以要用**元告警**盯住告警系统本身。

**第四，检测工程开始承认“维护比新增更值钱”。** 2026-05-15 的一份检测工程成熟度材料直言：多数检测项目的价值损失，来自**欠维护的既有检测**，而不是缺少新检测；阈值漂移、排除子句堆积、覆盖地图过期，都会让规则“看起来还在”。

**第五，Agent 场景把问题推高一层。** 2026-09-20 的一份 Agent 入侵检测研究给出排序原则：动作级控制一旦触发，**不能被“读了 Agent 解释之后”的叙述级判断压掉**；把 C2 式判断当回溯假设、而不是告警。也就是说，验证的不只是规则，还有“谁能否决告警”。

## 二、技术现状

**静态与单测层。** `promtool`、`pint`、各厂商的规则 lint 已普及；问题在于单测只证明“给定这段序列会触发”，不证明“线上会产出这段序列”，也不证明“阈值覆盖了真实分布”。

**回放层。** 把历史指标/日志灌回规则引擎，能发现“过去 90 天本应触发却从未触发”的窗口；难点是数据保留期、采样与标签基数——回放的数据往往不是线上那份。

**生产金丝雀层。** 定时制造一个可预期的坏信号，走完整链路（规则→路由→抑制→通知→升级）。它能验证管道，但不能验证“真实故障会不会被这条规则抓住”；且金丝雀本身会制造噪声，需要标记与静默规则。

**排除子句与抑制规则层。** 这是“安静”的主要来源。排除子句把某类已知噪声压掉，同时压掉了同类真信号；抑制规则让 A 告警压住 B 告警，在 B 才是根因时制造盲区。两者都很少有“压掉了多少真阳性”的度量。

**LLM 生成规则层。** 2026 年的新变量：规则由模型从威胁报告/事故复盘生成，评审仍靠“读起来合理”。执行式评估（把规则跑在正负样本上）开始出现，但负样本（本应触发却没触发）远比正样本难构造。

## 三、技术竞争力

| 方案 | 验证对象 | 能发现“盲目”吗 | 漏报可见性 | 误报成本 | 维护负担 |
|---|---|---|---|---|---|
| 规则 lint / 语法校验 | 规则文件 | 否 | 无 | 无 | 低 |
| 单元测试（promtool test rules） | 给定序列 | 部分（仅覆盖写死的用例） | 低 | 低 | 中 |
| 历史回放 | 过去窗口 | 中（依赖数据保留与采样） | 中 | 低 | 中高 |
| 生产金丝雀 | 完整链路 | 否（只证管道通） | 无 | 中（噪声） | 中 |
| 元告警（盯评估器） | 告警系统自身 | 是（针对“没在评估”） | 高 | 低 | 低 |
| 排除子句审计（正负样本） | 排除规则 | 是 | 高 | 中 | 高 |
| 执行式评估（LLM 规则） | 规则在样本上的行为 | 是（若负样本充分） | 中高 | 中 | 高 |
| 事故后“本应触发”复盘 | 真实事故 | 是（事后） | 高 | 无 | 中 |

判读：买得到 lint、单测框架、回放平台、金丝雀工具、元告警模板；买不到“这条规则在真实分布上漏了什么”的持续度量。多数团队停在第二层，把“单测绿”当成“告警有效”。

本期反转：我们习惯用“告警有没有响”判断可靠性，用“误报多不多”判断质量。但告警的有效性是**三值**的：该响时响、不该响时不响、以及**无法判断时能否自知**。前两个靠样本，第三个靠元告警与“本应触发”清单——缺了第三个，安静永远是可疑的。

判词：「告警规则引擎／lint／单测框架／回放平台／金丝雀／元告警模板／通知路由」全部可采购，「过去 90 天哪条规则本应触发却从未触发、哪条排除子句压掉了多少真信号、金丝雀自己停跑多久、谁否决过告警」不可采购。

## 四、技术挑战

**其一，负样本不可构造。** 真实故障的稀有性与多样性，使“本应触发”的样本集天然稀疏；没有负样本，漏报率无从估计。

**其二，排除子句的收益与代价不同源。** 压掉噪声的证据（工单量）与压掉真信号的证据（漏报事故）不在同一张表上，评审时只见前者。

**其三，金丝雀的自我指涉。** 金丝雀走同一条链路，链路故障时它也不响；“不响”与“正常”不可区分，必须靠元告警或外部心跳。

**其四，回放数据不是线上数据。** 保留期、采样率、标签基数、聚合窗口都变了；回放绿不等于线上绿。

**其五，Agent 让“谁能否决告警”成为新变量。** 叙述级判断可以压掉动作级告警；验证必须覆盖“否决路径”，而不只是“触发路径”。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- SRE：需要每条告警的“最近一次真实触发/最近一次金丝雀通过/最近一次本应触发却未触发”三时间戳。
- 检测工程：需要排除子句的正负样本审计，以及规则变更的影响评估。
- 平台：需要元告警（评估器停摆、通知链路断、抑制规则过宽）与金丝雀编排。
- 管理/审计：需要“告警有效性”季度报告，而不是“告警数量”月报。

**用户旅程（一次“没响”的事故）。**

1. 数据库连接池打满，应用 5xx 上升；按设计应触发 `DBPoolExhausted`。
2. 该告警三个月前因“噪声大”加了一条排除子句，匹配了这次的表名模式。
3. 值班只看到“延迟升高”告警，误判为下游慢；30 分钟后才从用户投诉知道真相。
4. 复盘问“为什么没响”，规则单测是绿的——单测样本里没有这个表名。
5. 再查：过去 90 天这条规则真实触发 0 次，金丝雀只验证了通知链路，从未验证该规则。
6. 结论写成“告警配置遗漏”；真正缺的是**规则有效性的持续验证**。

**实现方案（90 天）。**

- 第 1–2 周：给每条 P1/P2 告警建三时间戳（真实触发、金丝雀通过、本应触发未触发），先暴露“从未触发”的规则清单。
- 第 3–4 周：补元告警——评估器心跳、通知链路心跳、抑制规则命中计数；金丝雀停跑本身要能报警。
- 第 5–6 周：排除子句审计——每条 exclusion 标注“压掉的样本来源、最近复核时间、复核人”，用正负样本各跑一遍。
- 第 7–8 周：历史回放——用保留期内数据跑“本应触发”清单，按规则聚合漏报窗口；回放数据与线上数据的差异单独标注。
- 第 9–10 周：LLM 生成规则纳入执行式评估——每条规则必须带正负样本集与通过标准，评审看行为不看文风。
- 第 11–12 周：否决路径审计——记录“哪条告警被哪条规则/哪个人/哪个 Agent 判断压掉”，把否决纳入复盘。
- 第 13 周：季度有效性报告与门禁——新增/修改告警未通过四层验证不得上线；连续两季“从未触发”的规则强制复核。

**验收标准。** 任一条 P1 告警，能回答：最近一次真实触发是什么时候、最近一次金丝雀通过是什么时候、过去 90 天本应触发却未触发的窗口有哪些、排除子句压掉过什么、谁否决过它。

**第 218 个市场空白（五项）**：告警有效性三时间戳；排除子句正负样本审计；评估器与通知链路的元告警；回放数据与线上差异标注；否决路径审计。

**`alert_test.*`／`detection_validity.*` 第 185 次无人提字段族**：`alert.last_true_positive_at`、`alert.exclusion_audit_id`、`alert.missed_window_count`、`alert.canary_last_pass_at`、`alert.suppressed_by` 在主流告警平台里均无统一语义；平台只报“告警已发送”。

**本地 173／173-kb 连续第 173 期成组启用**（蒋炎炳 23）：本地知识库把“告警有效性”与“告警数量”分开记账；本期把它落成三时间戳与否决路径。
