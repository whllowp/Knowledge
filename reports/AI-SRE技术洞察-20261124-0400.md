# AI-SRE 技术洞察（第 307 期）· 撤销生效延迟面

**——"令牌已吊销"≠"所有会话、派生凭据与后台循环都已失效"（Revocation Propagation Latency / Credential Revocation Effective Delay）**

> **题眼**：你在设置页点掉一个 Agent 的授权，页面瞬间变成"已撤销"，红色按钮变灰。十秒后，三小时前那个"盯着仓库、自动给新 PR 打标签"的循环可能还在跑。设置页没说谎，但没说全——它撤的是"接下来"，不是"已发生"。AWS 与 Okta 的实测把它量化成三只不同步的钟：**阻断新请求 1 秒、已发令牌存活约 5 分钟、禁用 Agent 身份本身 86 分钟**。看得见"按钮已变灰"≠看得见"它真的停了、且所有派生凭据都已失效"。本期首次把**撤销从发出到全层生效之间的延迟**立为一等对象。

本期与第 298 期（可逆性面）划界：298 问"回滚成功后副作用是否已撤销"，落在**动作之后**；本期问"撤销指令发出后还有多少执行面在认旧凭据"，落在**权限本身**。与第 199 期（身份面）、第 281 期（开关面）也不同：身份问"用谁的凭据"，开关问"功能对谁生效"，本期问"收回凭据这件事，多久、在哪几层、凭什么证明完成"。

## 一、发展趋势（2026 年，重点近 30 天）

1. **撤销时效从"合规话术"变成"可测量的实测项"**。11 月，AWS 与 Okta 的参考设计（Okta Cross App Access 配 Bedrock AgentCore Identity）首次把"撤销后 Agent 还能 acting 多久"做成实测：阻断新请求约 1 秒、已发令牌活到过期约 5 分钟、beta Agent API 停用排队生效 86 分钟。作者强调这是自家租户配置、非产品保证——价值不在数字，而在"把三只钟量出来"。

2. **标准组织开始补"凭据如何结束"这一段**。IETF WIMSE 的 AIMS 草案（六家公司作者：Defakto、AWS、Zscaler、Ping、OpenAI、Okta）9 月 15 日被采纳，11 月 2 日 -01 版新增弃用（deprovisioning）阶段、**比凭据活得久的会话**、发送者约束令牌：接受方须在凭据过期时重新验证，收到撤销/风险信号即结束或降权会话，弃用标识符不得重新分配。配套草案（Credential Delegation、AIID）进一步提出执行前状态检查（Resolve）+ 有界缓存 + fail-closed、级联撤销与防篡改审计链。但几乎全是 Informational draft、厂商作者、无部署结果。

3. **"Kill switch"营销热与技术现实拉开差距**。Resilient Cyber 11 月梳理：CrowdStrike 端点终止仍标"soon"；Okta 的"instant kill switch"在脚注把运行时层押到 Q4 GA；MuleSoft 9 月 GA 的开关只对经其代理的流量生效；Google Gemini Enterprise 最快停止是删除 Agent（破坏性），网关 deny 全球生效约 2–7 分钟以上；AWS StopRuntimeSession 立即终止单个会话，但策略只筛显式配置的 API 路径。结论直白："目前没有独立基准测量 Agent 停止延迟。"

4. **评测开始戳破"页面说停了"的幻觉**。KillBench（EMNLP 2026 Findings）把 kill switch 做成网页文本信号，测 5 个模型、550 个恶意任务：最好的 AutoGuard 平均停摆率仅 47.1%，法律告示 22.6%，对抗后缀 3.7%，模型间差约 5 倍；更关键是**分不清好坏**——GPT-5.2 良性任务完成率从 78.7% 掉到 0.8%。论文承认没测凭据型协议与签名端点。

5. **市场数据指向"身份已解决、遏制仍空白"**。VentureBeat 8 月调研：约五分之四已处理 Agent 身份的企业仍无法可靠遏制失控 Agent；Kiteworks 红队显示 60% 无法快速终止、55% 无法隔离；Salt 称仅 17.5% 能自动停止生产中的意外 Agent；97% 非人身份权限过度、仅 12.5% 能追踪完整执行路径。撤销速度正成为"控制权"的事实判据。

## 二、技术现状

今天的撤销能力，本质上是**四张延迟由大到小的牌**，外加一条只缩小爆炸半径不改延迟的规则。

**短 TTL + 刷新轮换**：令牌短命，撤销靠自然过期。access token 普遍约一小时（GitHub App 安装令牌写死一小时），最坏延迟一个 TTL，验证开销近零；refresh token 轮换（RFC 9700 思路）让旧 token 复用即触发整条授权吊销，是保险丝，但**不能追溯作废资源服务器已接受的 access token**。

**令牌内省（RFC 7662）+ 短缓存**：资源服务器每次拿 token 问授权服务器"还活着吗"，`active:false` 即死。撤销即时生效，延迟压到一个缓存 TTL（秒到分钟级），但授权服务器从此成为每次调用的在线依赖。

**凭证代理，动作时取用**：Agent 运行时**根本不持有 token**，每次工具调用前找代理要一个几秒级租约，用完即弃。撤销的上限从"令牌寿命"变成"写入一条数据的速度"——观微录据此判断它是 Agent 场景"最正确的姿势"，代价是多一个必须高可用的核心组件。

**受众绑定 + 禁止转发**（RFC 8707，已写入 MCP 授权规范）：MCP server 被定位成 OAuth 资源服务器，签发令牌绑定指定 resource，禁止"A 的 token 原样转给 B"。它不缩短撤销延迟，只回答"一张过期票还能刷开几扇门"。

标准层的缺口很具体：RFC 7009 的撤销端点定义在**客户端与授权服务器之间**，只负责把凭证"注销"，资源服务器何时知道"标准压根没规定"；撤销 refresh token 连带作废 access token 也仅 SHOULD 非 MUST。无状态 JWT 验签的取舍就是"用撤销延迟换验证零开销"——门禁扫签名就放行，你被拉黑也要等手环到期。

判词：**短 TTL、令牌内省、凭证代理、受众绑定、CAE、kill switch、审批墙、动态因果图——几乎每项都可采购；"这次撤销发出后，还有哪几类凭据、会话、后台循环仍在认旧票，最坏多久失效，由谁独立验证"——全表几乎无人做成可导出的证据字段。** 分化的关键不在"有没有撤销功能"，而在**撤销是否能被独立举证到全层**。

## 四、技术挑战

1. **三只钟不同步，且没有一只被产品承诺**。阻断新授权、已发令牌寿命、禁用 Agent 身份本身——三者可相差两个数量级。把任何一只当成"撤销完成"都是错的；而 Google 对已删 Agent 的 ID token 寿命"没有文档"，成为一个开放缺口。

2. **撤销是向前止损，不是向后撤回**。三层命中完全不同：**token 层**——本地验签下一次调用照样成功到过期；**上下文层**——已经读进模型的数据擦不掉（撤了 wiki 权限，半小时前拉的三页还在"记忆"里）；**动作层**——计划队列里排着的动作，凭证失效后可能重试、绕路，或取决于错误处理而静默跳过。三层的残余都不在撤销射程内。

3. **语义变更查不出来**。用户把 scope 从"读写"改成"只读"，token 仍然有效，凭证有效性检查不会报警——只有对比"任务启动时的权限版本号"与"当前版本"才能发现。这要求别在任务开始时给权限拍快照，每次动手前都看当下的规则（"安检设在登机口而非售票处"）。

4. **401 被误当普通网络错误**。不少实现收到 401 就重试三次报"任务失败"，用户再点一次又弹重新授权——而正确语义是**挂起并重新协商**。

5. **kill switch 分不清好坏，签名回执不等于真停**。AgenTrust 的 cMCP 网关实验给出三类反例：**已准入调用仍能在 shutdown 期间完成**、**直连工具路径能在网关停止时产生效果（网关记录里看不到）**、**历史拒绝回执在恢复后仍能验证**。停止命令、签名拒绝、后续无效果是三种观察；把签名拒绝当成"持续且普遍停止"的证据，正是被证伪的读法。

6. **控制平面本身是隐藏单点**。CSA 11 月"五天四平台"研究：11/12–15 微软 365、Anthropic、OpenAI、AWS 相继故障；模型多样性没换来数据层韧性（一个 M365 网关故障同时打断 Copilot、Anthropic 与 OpenAI 的连接器）；身份与会话控制面（Anthropic 11-13 登录事故、AWS 11-15 IAM Identity Center）是常被忽视的单点。Agent 在空结果上"完成"、跳过排定任务而不告警——在 guardrail 被削弱的路径上继续处理，风险更大。

## 五、展望与建议

**核心观点**：撤销不是一次点击，而是一条**需要被举证到全层的传播链**。"按钮已变灰"是被展示的状态，"所有派生凭据、会话与后台循环都已失效"才是被证明的事实。二者之间，隔着三只不同步的钟与四个执行层。

给工程与治理的具体建议：

- **新建字段族** `revocation.effective.*`（本地第 228 个无人提字段族）：`revocation.requested_at / effective_at`、`propagation_seconds`、`three_clocks{new_request_blocked_at, issued_token_expiry_at, identity_disabled_at}`、`credentials[]`（token/session/tool-secret/derived/queued 逐类）、`stale_session_inventory[]`、`context_residual`（已入上下文不可回收须显式标注）、`permission_version / task_permission_version`、`bearer_scope`、`revoke_verified_by ∈ independent_gateway|introspection|issuer_signal`（禁自报）、`kill_switch_drill_at`、`verdict ∈ REVOKED_EVERYWHERE|PARTIAL|STALE|UNVERIFIED`，缺省 `REVOCATION_UNVERIFIED`。
- **把"停止"做成三态而非一态**：将"已发停止命令 / 已观察到效果 / 后续确无效果"分别落账，签名回执只证明第一类；独立观测者（网关/代理）记录第二、三类。
- **强动作走凭证代理 + 权限版本号**：会写数据、花钱、对外发消息的工具，凭证代理、版本检查、人工闸门一个都不能省；401 与版本不匹配一律挂起交还人，禁止自动重试。
- **纳入混沌与采购**：季度演练"撤销后循环仍在跑""跨云派生 token 仍可用""kill switch 误停良性任务"；采购问三句——"最坏多久全层失效、覆盖哪几类凭据、能否导出独立验证依据"。
- **评测补题**：给基准加"撤销后仍 acting""空结果上完成""401 后静默跳过"三类题，报 stop-latency 与 benign-false-stop 双指标。
- **标准与信通院**：向 OTel GenAI 与 WIMSE AIMS 提案撤销时效属性；信通院《云上 Agent 基准度量模型》补「撤销可举证率」一格，成十四层治理。
- **本地原型（第 183 期新角度）**：朱革《百度 SRE Agent 规模化落地实践》的"安全托管"过去读作"给权限的治理"，本期首次读作"**托管的试金石不在发权限那一刻，而在撤权限之后——能否证明派生凭据、会话与排队动作都已失效**"；配刘凯宁蚂蚁 SRE"三分"扩第十八分"撤销延迟几秒、覆盖几类凭据、谁独立验证"；配赵恒"权威来源"扩到"撤销生效的权威来源是网关独立观测，非身份平台自报"。
