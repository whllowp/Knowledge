# AI-SRE 技术洞察（第 358 期）

**生成时间**：2026-11-25 20:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：续流面／断线重连与事件续传——重连成功，不等于没有丢

## 题眼

MCP 在 **2026-07-28** 的修订里做了一件很少被讨论的事：把 Streamable HTTP 的 **SSE resumability 与 `Last-Event-ID` 一起移除**了。官方迁移说明写得很直白：流式响应断开后，**in-flight 请求丢失**，客户端必须用**新的 request ID 重新发送**。同一次修订还删掉了 `Mcp-Session-Id` 与 initialize 握手——协议向无状态回摆，代价是"续流"退回了"重试"。

另一边，Microsoft Foundry 在 2026-10-13 的 Agent 流式指南里把两条规则写死：**用 per-turn 的 stream ID**（绝不复用多轮对话 ID），以及**由 backing 决定晚到的订阅者能否 replay、流能否跨容器重启**。第三份材料来自 opencode 的 PR #25658：`/global/event` 之前忽略 `Last-Event-ID`，断线期间的事件**静默丢失**；修复是 1024 条环形缓冲、单调 ID、`lastSentId` 去重，心跳不计入可恢复流。

断线是常态。问题不是"重连了吗"，而是"断的那一刻，丢的是什么"。

## 一、发展趋势

第一，长连接成为 Agent 的默认形态。一次工具调用可能跑几分钟，客户端可能切后台、过代理、换网络；连接断开不再意味着任务结束，而是意味着"订阅者掉了"。

第二，协议在"有状态续流"与"无状态重发"之间分叉。SSE 的 `Last-Event-ID` + 服务端事件存储是一条路；MCP 2026-07-28 选了另一条：不留会话、不留游标，断了就重发。两条路都能工作，但它们的**失败语义完全相反**——一条是"可能丢"，一条是"可能重"。

第三，恢复语义开始进入规范。SEP-1699（Final，2025-10-22 创建）允许服务端在计算中主动断开、让客户端走 SSE polling；规范要求服务端在开流时**立即发一个带 id、data 为空的 priming 事件**，好让客户端拿这个 id 作为 `Last-Event-ID` 重连。ruby-sdk 0.24.0（2026-07-12）随后接入了这条重连逻辑。

## 二、技术现状

**续流的三要素**：一个**位置**（event id / seq / offset）、一个**窗口**（服务端保留多少事件、保留多久）、一个**幂等**（重复投递时客户端或服务端能否识别）。缺任何一个，"续"都会退化成"丢"或"重"。

**位置必须由业务定义，不能由传输层发明**。kitsunium 的 SSE SDK（2026-10-26）把这个判断写进文档：客户端保存最后一个非空 id，重连时通过 `Last-Event-ID` 带回；**SDK 不 replay**，只把游标交给 handler。理由是——"放在流里的 replay buffer，会在需要 resume 的那一刻恰好是空的；reconnect 是一个新连接、新流。能跨流存活的 buffer 其实是应用存储，它必须回答保留多少、保留多久、replay 是否安全——这些是事件含义的问题，不是传输的问题。"

**窗口大小决定事故形态**。opencode 的 ring buffer 是 1024 条；超过窗口的断线，客户端只能从"最老的可恢复点"续，中间的洞要么补拉、要么承认丢失。Foundry 的指南把选择权交给 backing：内存队列只能 replay 到进程重启，持久日志可以跨重启，但延迟与成本更高。

**心跳不是事件**。opencode 明确把 `server.connected` 与 `server.heartbeat` 排除在可恢复流之外——它们是每连接的信号，不是业务事件。把心跳计入 id 序列，会让游标漂移。

**断线后的三种语义**：①**续**（从 Last-Event-ID 之后 replay，可能重复，需去重）；②**丢**（无窗口/无游标，断线即丢失，如 MCP 2026-07-28 的 in-flight 请求）；③**重**（客户端用新 request ID 重发，可能重复执行，需幂等）。三种语义都"重连成功"，但业务结果不同。

**per-turn stream ID**：Foundry 强调不要复用多轮对话 ID 作为 stream ID。复用会让"这一轮的恢复点"与"整段对话的位置"混在一起，晚到的订阅者无法判断自己缺的是哪一轮。

## 三、技术竞争力

| 方案/协议 | 恢复语义 | 位置 | 窗口 | 主要盲区 |
|---|---|---|---|---|
| SSE + Last-Event-ID | 续（可重复） | event id | 服务端 ring/日志 | 窗口外即丢 |
| MCP 2026-07-28 | 重（in-flight 丢失） | 无 | 无 | 需幂等重发 |
| WebSocket 自建 | 取决于实现 | 自定义 seq | 自定义 | 无标准、易漏 |
| 轮询 | 重/续 | offset/cursor | 服务端 | 延迟与重复 |
| Foundry hosted agents | 续（backing 决定） | per-turn stream ID | backing 决定 | 跨重启依赖存储 |
| Kafka 消费 | 续（offset） | offset | 保留期 | 重平衡与重复 |

**判读**：这张表最关键的一列是"恢复语义"，而它恰恰最少被写进架构文档。团队通常只写"支持断线重连"，不写"断线后是续、是丢、还是重"。

**本期反转**：我们一直把"重连成功"当成恢复完成的标志。实际上重连只是建立了新连接，真正的恢复要回答三个问题：从哪个位置续、窗口里还有没有、重复的怎么去重。**MCP 2026-07-28 的反向选择提醒我们：无状态不是免费的，它把"续流"的成本转移给了"幂等重发"。**

## 四、技术挑战

**挑战一：三种语义混用。** 同一个系统里，通知流用"续"、工具调用用"重"、日志用"丢"，但对外都叫"支持重连"；故障时无法判断用户到底丢了什么。

**挑战二：窗口与保留期是隐式契约。** 客户端不知道自己能断多久；服务端不承诺保留；超过窗口后，客户端只能从"可恢复点"续，中间是洞。

**挑战三：重复执行。** "重"语义要求每个请求幂等；Agent 的工具调用（发邮件、下单、删资源）往往不幂等，重发即重复副作用。

**挑战四：可观测性缺失。** 指标通常只有"重连次数"，没有"重连后从哪个 id 续、replay 了多少条、去重了多少条、有多少条永久丢失"。

**挑战五：背压与恢复窗口互相挤压。** 慢客户端会让 replay ring 被追尾，窗口被迫截短；而截短窗口又会把"可续"变成"只能重"。恢复能力不是静态配置，它随负载变化。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①每类流的恢复语义声明（续/丢/重）；②位置字段（event id/seq/offset）与生成规则；③窗口大小与保留期；④重复投递的去重键；⑤断线后的可观测（replay 条数、去重数、丢失数）。

**用户旅程**：用户在看一个跑了 4 分钟的 Agent 任务 → 网络切换，SSE 断开 20 秒 → 客户端带 `Last-Event-ID` 重连 → 服务端从 ring buffer replay 这 20 秒的事件，但其中 3 条与实时流重复 → 客户端按 event id 去重 → 用户看到连续输出。若窗口只有 10 秒，客户端只能从最老可恢复点续，中间 10 秒是洞；若协议是 MCP 2026-07-28，客户端只能重发，服务端必须保证这次重发不会把任务跑两遍。

**90 天实现方案**：0–30 天，给每类流标注恢复语义，补上位置字段与去重键；31–60 天，为 SSE 类流加 ring buffer 与 replay 指标，为"重"类流加幂等键与重复检测；61–90 天，做一次"断线 30 秒/5 分钟/跨重启"的三档演练，验收"丢了多少、重了多少、续了多少"。

**第 270 个市场空白（五项）**：恢复语义声明；位置字段与规则；窗口与保留期；重复去重键；断线后的可观测。

**`stream_resume.*`／`replay_cursor.*` 第 237 次无人提字段族**：所有平台都记录"重连次数"，没有一个字段记录"这次重连从哪个位置续、replay 了多少、永久丢了多少"。

**本地 173／173-kb 连续第 225 期成组启用（肖汉松 22：重连是重新握手，续流是重新对齐；前者靠网络，后者靠游标）。**
