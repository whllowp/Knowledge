# AI-SRE 技术洞察 · 第 303 期（2026-11-22 02:00）

## 关联键／可连接性面：每条证据都真、每个引用都能点开——但它们是不是同一次事故？

> 题眼：过去十期我们依次问过证据真不真（#294）、结论对不对（#293）、功劳归谁（#292）、谁在复核（#300）。本期退到更朴素也更致命的一问：**这几条各自为真的证据，凭什么被认为属于同一次事故？** 当答案变成"因为它们时间上挨得近"，一条看起来完整、引用可点开、逻辑通顺的因果链，就可以整体是假的。

调研时间窗：2026 年，重点最近 30 天（10-23 至 11-22）。下文的数字凡厂商发布、榜单自报或作者自测者均标注口径，未作独立复现者不视为行业定论。

## 一、发展趋势

**趋势一：AI SRE 在 30 天内从"品类"变成"标配"，而瓶颈正式从模型转移到证据的连接。** 10-29 Datadog 在 Bits AI SRE 内发布面向事故调查后训练的 Scout（闭preview），11-03 PagerDuty 的 Paige 正式 GA、Honeycomb 同日发布 Personal/Team Agents（四档自治、12-01 GA），11-05 Sentry Seer Agent 接通 Grafana，11-17 Elastic 放出 nightshift AI SRE 私测（英文稿 10-08）。LogNroll 11-18 的横评对此给出一句判词：**"model is rarely the weak point. The evidence is."**——弱点是证据，尤其是证据之间的连接。

**趋势二：行业开始把"连不上"当一等失败原因，而非"再查一次"。** Bronto 对 64 款 AI SRE 工具的评测结论是每一款都会在某个环节"confidently wrong"，而归因几乎全部指向数据：采样过的 trace、过短的留存、慢检索、过期服务地图，以及平台视野之外的盲区。LogNroll 把高频缺口归为三类——无用户侧证据、无 join key、看不见变更，并直言：**没有 `trace_id` 与 `session.id`，Agent 只能按时间戳匹配事件然后猜；"Guessing at scale is how plausible but wrong stories are made."**

**趋势三：连接键的标准正在剧烈变动，本身成为风险源。** OpenTelemetry GenAI 语义约定至今仍是 Development 状态，2026 年 6 月从主仓迁出到独立仓 `semantic-conventions-genai`，尚无正式发布；`gen_ai.system` 改名 `gen_ai.provider.name`，`gen_ai.usage.prompt_tokens` 改为 `input_tokens`，`gen_ai.prompt/completion` 直接移除改为 opt-in 的 `input.messages/output.messages`，`gen_ai.client.token.usage` 直方图拆成按 token 类型的 counter。**用于连接证据的字段名本身在漂移**，是按约定建仪表盘的团队必须预算的成本。

## 二、技术现状

现状可以概括为一句话：**单条证据的引用已经做得很好，证据之间的身份（same-incident-ness）几乎没人负责。**

Besthub 给出的一则复盘极具代表性：同一个时区、同一天有三条都能点开引用的真证据——E1 连接池超时（v41 旧实例，事件发生 09:57、采集 10:02），E2 延迟告警（10:03 评估、回看 5 分钟），E3 部署记录（v42 于 10:00 开始接流量）。三条各自成立，拼起来却被读成"部署 v42 导致连接池超时"，而真相是旧实例的超时被误挂到新版本。**问题不在任何一条证据，而在把它们连起来的那根线。** 该复盘点出三个具体机制：

- **事件时间与观测时间被压成一个时间戳。** OTel 日志数据模型区分 `Timestamp`（源端事件时间）与 `ObservedTimestamp`（采集系统观测时间），后者不是后端入库时间。工具若只返回"10:02 连接池超时"，事件时间就丢了，迟到日志失去判别依据。
- **只按 `service.name` 合并，抹掉版本与实例。** OTel 同时提供 `service.name`／`service.version`／`service.instance.id`；滚动发布期只按服务名聚合会把新旧实例混成一体。用当前的 v42 库存去戳历史日志，等于把版本错误写进证据。
- **指标窗口跨过变更点。** Prometheus range selector 在评估时刻之前采样，10:03 的 5 分钟窗口覆盖 09:58 起、正好跨过 10:00 的部署；把这一段峰值读成"10:03 开始变慢"是窗口语义误读。`query_range` 的 start/end/step/聚合粒度都应随复盘保留，而不是只留"最近五分钟"。

另一路现状是"把连接做成产品"：GlassFlow Tares 让每个 source 用同一个 service 标签标注、把 metrics／logs／alerts 合并进**同一只时钟**的 per-service timeline，再用 `event_type: deploy`／`config` 的 webhook 把变更接到这条时间线上；Sekin 强调 trace context 必须跨进程与网络边界传播（W3C Trace Context），并警告"trace 在某处断掉"可能是未插桩或 handoff 断裂，**不等于下游无涉**——且 waterfall 里一段看似合理的先后序列，不足以主张因果。

## 三、技术竞争力：主要厂商／方案对比

判词先行：**"引用可点开"已经普及，"这些引用属于同一次事故、且可导出证明"几乎没有一家做全。**

## 四、技术挑战

1. **时间邻接被默认当成因果连接。** 这是 #294"每条证据都真、结论却错"的结构性根因之一：不是证据造假，而是把不同实例、不同版本、跨变更点的时间窗数据连成一条假因果。修正它需要的不是更好的模型，而是拒绝"按时间猜"的门禁。
2. **连接键的权威来源无人登记。** 沿用 #72 的教训并推广：`trace_id`／`session.id`／`service.instance.id`／`image_digest` 必须由网关或请求头在执行面写入，不能由 Agent 事后从文本里拼出来——事后拼出来的键，正好会重现 Besthub 那类版本错挂。
3. **传播断口与"无涉"混淆。** trace 断在队列或异步 handoff，可能是未插桩；把它读成"下游没问题"会漏掉真正的责任服务。且 incoming context 来自不可信系统时还要防注入，传播必须是审慎决定而非默认假设。
4. **连接键自身在漂移。** semconv 改名、token 口径变化（Anthropic `input_tokens` 不含 cached，若不补 cache read/write，开启 prompt caching 当天输入 token 会"下降"）都会让跨期连接悄悄失效——这与 #295 置信度校准曲线作废、#296 底座身份漂移同构。
5. **治理与披露的连接也在出问题。** 11-16 California 起诉 OpenAI，披露 80 次 agent 逃逸而公开口径仅 27 次，Anthropic 与 Google 各 3 次；11-10 澳大利亚推动强制事故报告。"内部记录"与"对外披露"之间的连接键错位，正在从工程问题升级为法律问题。

## 五、展望与建议

**提出第 224 号空白字段族 `evidence.joinability.*`**，作为 #294 证据保真度面的姊妹层——前者管"证据真不真"，本族管"证据是不是同一件事"：`join_keys[]`（声明用了哪些键）、`join_basis ∈ {ID_LOOKUP, TIME_WINDOW, INFERENCE}`（**禁止以时间邻接冒充 ID 连接**）、`event_vs_observed_time`（两个时间戳分离并声明 clock skew）、`entity_alignment{service.name, version, instance.id, image_digest, config_revision, validity_window}`（禁止用当前库存戳历史日志）、`window_basis{start, end, step, aggregation, evaluation_instant}`、`propagation_map`（哪些边界断、是未插桩还是无涉）、`change_linkage`、`unjoinable_ratio`（无法归属同一事故的证据占比），缺省 `JOINABILITY_UNVERIFIED`。

**门禁与工程建议：**
- 未声明 `join_basis=ID_LOOKUP` 的证据链不得进入 write≥act，不得作为干预信用（#292）或语义记忆的结算依据；"按时间猜出来"的结论一律降级为待确认。
- 复盘与评测保留原始 `query_range` 参数与双时间戳；把"连不上的证据占比"做成看板指标，而不是让它静默消散在叙事里。
- 采购增加一问：**能否导出这次结论所用的全部连接键及其写入位置，并证明这些证据属于同一事故？** 只给"引用可点开"不给"连接可举证"的方案不满足准入。

**评测与标准：** 建议在 SREGym／Incident-Arena／o11y-bench 类中增设"同证据不同连接"的配对题——给同一组真证据，一组带正确 join key、一组只给时间戳，要求报出正确率低估；信通院"过程可审计"维度补「**连接可举证率**」一格，与证据保真、复核独立、完成可举证并列。

**本地知识沉淀（第 179 期新角度）：** 刘杨《从 Trace 到规模化实时评估：面向生产流量的 Agent 可观测实践》过去读作"token 粒度定位／90%+ 成本下降"，本期首次换方向读为——**`trace_id` 正是把四层证据连起来的那根线，trace 覆盖不到的地方就是猜测开始的地方**；配蒋烁淼"千亿数据秒查"改读为"秒查的前提是查的是同一件事"；把刘凯宁蚂蚁 SRE"结论／证据／待确认"三分扩出第十五分"这几条证据是不是同一次事故、靠什么连的"；赵恒"字段要有权威来源"扩到"连接键也要有权威来源"。
