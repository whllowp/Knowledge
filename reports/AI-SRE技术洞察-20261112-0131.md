# AI-SRE 技术洞察（第 134 期）

**生成时间**：2026-11-12 01:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：文档时效面／知识腐烂面（Doc Freshness / Knowledge Rot）——Agent 读的 runbook 比人读的更容易过期；「新鲜度是排序偏好，不是硬过滤」

---

## 题眼

Microsoft Azure AI Search 在 2026-09-17 更新的文档里写了一句关键限定：**新鲜度感知检索（freshness-aware retrieval）是「排序偏好」，不是「硬过滤」**——旧文档只要「与查询高度相关」，仍然会排在前面。它的适用场景里赫然写着 **runbook、服务通告、运维指引**；配置方式是在知识源上挂一个 `boostingDuration`（如 `P90D`），靠索引里的 `last_modified` 打分；官方还提醒：**日期缺失、过期或不一致，会直接降低新鲜度信号的质量**。另一篇工程博客的标题把结果说破了——**「为什么你的编码 Agent 总挑旧文档」**。**人读旧 runbook 会先怀疑；Agent 读旧 runbook 只会照做。** 更麻烦的是，**旧文档往往更长、更具体、命令更全**——在 relevance 排序里，它天然比刚写三行的新文档更容易被选中。

## 一、发展趋势

**趋势一：文档从「参考资料」变成「运行时依赖」。** Agent 在推理时检索 runbook/SOP，**文档错误直接变成动作错误**，而且不报错、不编译、不告警——**它是负事件家族里最安静的一类**。

**趋势二：检索系统开始处理新鲜度，但只给「偏好」。** Azure 的 freshness policy 是排序信号；想按日期硬过滤，官方明确要求「用 filter，不要指望 freshness」。**这意味着：只要你的旧文档足够「相关」，它就会被捞出来。**

**趋势三：文档腐烂的速度快于模型折旧。** 112 期说 harness 半年过期；文档随每次发布、每次改配置、每次换 IP 而过期——**它的半衰期按周算**。

## 二、技术现状：三种腐烂，一个没有字段的资产

**事实腐烂：** IP、端口、命令、控制台路径变了，文档没改；Agent 照抄，执行失败或改错对象。**失败还能发现；改错对象往往不能。**

**意图腐烂：** 步骤还能跑，但前提已经不成立（比如「先重启」在引入状态机后不再安全）；**这类最危险，因为它「看起来还能用」**。

**归属腐烂：** owner 离职、频道解散、升级路径失效；文档还在，**没人能为它负责**。

**现有工具：** 链接检查（docs-as-code CI）、文档腐烂扫描（docrot、stillvalid 一类工具）、检索侧新鲜度加权（Azure）；**但没有一个把「这份文档对当前版本是否仍然成立」做成运行时字段**。

**文档有三个版本，只有一个是运行时用的。** 写的版本（草稿）、发布的版本（wiki 页）、**部署的版本（Agent 实际检索到的那份快照）**；前两个有历史，第三个通常没有。**你改完文档，Agent 可能还在读索引里的旧快照**——索引重建有延迟，缓存有 TTL，谁都没把「部署版本」标出来。

**文档腐烂的经济学：更新很贵，事故更贵，但账单不在同一张表上。** 更新是文档团队的工时，事故是 SRE 的夜班；**没人把两者放一起算，腐烂就永远排在待办末尾**。

## 四、技术挑战

**一，相关性会压过新鲜度。** 旧文档往往更长、更具体、关键词更全；**在 relevance 排序里，旧文档天然占优**。

**二，新鲜度不是正确性。** 刚更新的文档也可能错；**时间新 ≠ 事实对**。

**三，事实与指引需要不同策略。** IP/端口这类事实该硬过滤（只认当前版本），流程指引可以加权；**用一套策略管两类，必然有一类出错**。

**四，没有「当前版本」这个锚。** 文档很少声明「适用于 vX」；Agent 也无从判断 vX 是不是现在这版——**128 期的模型身份问题，在文档层复现**。

**五，没人对过期负责。** owner 离职、团队重组；**文档没有到期日，就没有人被迫更新**。

**六，Agent 的引用不可核。** 它说「根据 runbook」但不给版本；**复盘时无法确认它读的是哪一版**。

**七，检索日志不记文档版本。** 你只能看到「检索命中了 3 条」，看不到「命中的是 v7 还是 v3」；**没有日志，就没有腐烂归因**。

**八，多租户/多语言让文档分叉。** 同一份 runbook 在 A 租户更新、B 租户没更新；**跨租户的 Agent 可能读到两个互相矛盾的版本**（121 期的隔离问题在文档层复现）。

**九，AI 写文档形成自我循环。** 用 Agent 从 Agent 输出里生成文档，错误会被写成「规范」；**再被下一个 Agent 当权威引用**——这是 116 期记录污染的文档版。

**十，文档的读权限没跟上。** Agent 检索时可能读到它无权执行、甚至无权看的文档（121 期的租户边界）；**知道怎么做**和**被允许做**是两件事。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `doc.*` 字段**：`doc_id`、`owner`、`last_verified`、`volatility_class`（fact／guidance）、`applies_to_version`、`retrieval_policy`。
- **R2 分级检索**：事实类硬过滤（只认当前版本）；指引类用新鲜度加权。
- **R3 到期与归属**：每份 runbook 有 owner 与 `review_by`；到期未复核自动降权并告警。
- **R4 Agent 引用版本**：回答里带 `doc_id@version`；无版本引用视为未引用。
- **R5 度量**：过期文档占比、断链率、文档-事故不匹配率、引用可核率。
- **R6 演练**：季度「旧文档陷阱」演练——植入一份过期 runbook，看 Agent 与人都能否识破。
- **R7 检索日志**：记录每次命中文档的 `doc_id@version`，供复盘与腐烂归因；不记版本视为不可审计。
- **R8 文档折旧表**：按 `volatility_class` 定折旧周期，到期未复核自动降权；折旧率进季度评审。

### 5.2 用户旅程

- **SRE**：改完配置 → CI 标记关联 runbook → 强制更新 → 打新版本与 `last_verified` → 重建索引并确认「部署版本」已切。
- **Agent**：查 runbook → 先按 `applies_to_version` 过滤 → 取当前版 → 回答带 `doc_id@version`。
- **文档 owner**：收到到期提醒 → 复核或标记废弃 → 未处理则自动降权。
- **审计**：抽查一次 Agent 决策 → 核对引用版本与当时配置 → 确认文档成立。
- **平台负责人**：季度看板 → 过期文档占比 34%、引用可核率 12% → 把文档复核纳入发布门禁。

### 5.3 实现方案（90 天）

- **0–30 天：盘点。** 列出 top 50 runbook；标 owner、last_verified、volatility_class。
- **30–60 天：分级。** 事实类加版本过滤；指引类接新鲜度加权；CI 加链接与版本检查。
- **60–90 天：演练。** 植入过期文档做陷阱演练；上线四项指标；季度复核到期文档。
- **90 天后：折旧表。** 给每类文档定折旧周期（事实 30 天、指引 90 天），到期自动降权；把「文档事故」计入复盘分类。

**第 88 个市场空白（五项）**：文档版本可声明率、到期复核覆盖率、引用可核率、文档-事故不匹配可测率、旧文档陷阱检出率——无一内建；`doc.*`／`freshness.*` 为**第 57 次无人提字段族**。本地 173／173-kb 连续第 50 期成组启用：何伟 02「约定验收标准、知识回流」＝全库唯一把「知识回流」写进交付闭环的实践，本期首次当主线；配刘凯宁 05「结论/证据/待确认项三分」、朱革 15「统一版本边界」。判词：**本地把知识回流写成流程，联网侧 9 月才承认「新鲜度只是排序偏好」；两边都没把「这份文档对当前版本是否成立」做成运行时字段。**
