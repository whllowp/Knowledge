# AI-SRE 技术洞察（第 315 期）

**生成时间**：2026-11-25 02:00（周三）
**本期主线（第 268 个全新立面）**：积压回灌面／恢复后时序倒置——**"消息一条没丢，但两天前排队的指令被当成了现在的新指令"**（Backlog Replay / Post-Recovery Instruction Ordering / The Zero-Loss Trap）
**与上期关系**：第 314 期「诊断稀释面」问的是证据太多挤掉根因；本期问的是证据/指令的**时态身份**在恢复瞬间被折叠——不是读得准不准，是"这句话此刻还算不算数"。

> **题眼**：2026-11-12 微软 365 网关故障持续约 36 小时。微软把邮件超时窗口延长到 48 小时，延迟消息被**扣住而非丢弃**，零丢失。周六恢复时，两天的指令按排队顺序一次性抵达，接在邮箱上的 Anthropic、OpenAI 连接器同时复活——Agent 把积压读成了"现在"。一位客户周四邮件要求改收货地址、下午已电话改好，周五积压邮件落地，Agent 当作新请求把地址改回去并确认。每一步都合理，裂缝出在"Agent 被告诉的"与"同事已经做过的"之间。**恢复恢复了邮件，没有恢复决策的顺序。**

## 一、发展趋势

**趋势一： outage 叙事从"可用性"转向"恢复后的时态完整性"。** 过去十年 SRE 的恢复判据是"服务可用、数据不丢"。11 月这一组级联故障把第三个维度推上台面：数据不丢，不等于数据的**时间身份**没被改写。48 小时的扣留是正确决策（宁可延迟不可丢失），却制造了一个此前无人建模的状态——**积压队列的瞬时排空**。CSA 11-19 研究简报《Five Days, Four Platforms》记录了 11-12 至 11-15 微软 365、Anthropic、OpenAI、AWS 四平台在同一窗口故障，并指出"在两三家模型商之间做对冲"的企业并未获得冗余：M365 网关故障同时打断了 Copilot、Anthropic 的 M365 连接器和 OpenAI 连接器，它们**同一时刻降级**（该简报一手页已下线，本文据二手转述）。

**趋势二：静默失败谱系补齐了最后一块——"空结果被读成健康"。** 第 232 期写过"该跑没跑的静默缺席"，第 290 期写过"没收到被读成没事"。11 月窗口里两者合并成一个更危险的形态：定时任务在故障期**整轮跳过且无告警**，或"完成"了但工具返回空/部分结果——一个因不可达而返回空的邮箱，被读成"没有新邮件"。分诊、合同监控、财务对账类 Agent 的静默跳过会逐日复利。BlinkOps 对 2026 年数起 rogue-agent 事件的复盘进一步给出判据：**严重性是时间线，不是某一时刻的事实**（severity actually could decrease or increase over the course of an event），一条低危开局的事件应随证据累积重新打分。

**趋势三：治理先于工具成为主流处方。** 面对积压回灌，一手评论给出的不是新监控产品，而是三件治理物：**一名具名的人**在故障前书面规定 Agent 何时暂停/恢复；一份**共享的"已处理事项"记录**，Agent 改动前先读；一条**冲突交人**的规则。借用无人机操作的 **lost-link rule**（失联即按预设安全动作，而非自主继续）与"两订单演练"。这与加州总检察长 11-16 起诉 OpenAI（首例针对 agent 行为而非模型输出的州级执法，指向 per-tool allowlist、动作预算、不可篡改审计轨迹）形成合流：**Agent 的恢复权正在被法律与工程同时收编为一项需要授权的动作**。

## 二、技术现状

**（1）恢复侧的"时态三分离"尚未产品化。** 一条指令至少有三个时刻：`event_time`（客户发出）、`delivered_time`（系统排空投递）、`processed_time`（Agent 执行）。DEV 的 SRE 实战指南给出硬规则：**LLM 产出的时间戳是数据，不是元数据**——它应进入被哈希存储的 payload，而不是拿来排序的 span 属性；排序只能来自 ingress 端自己掌控的钟。它列出四种"时间答错"的原因（陈旧上下文注入、副本时钟偏移、模型自报时间当真、幻觉），指出前三种恰恰是当前仪表盘看不见的。DT 的建议是混合时间戳 `agent.started_at.hybrid`（wall:logical, monotonic），并以 `agent.prompt.sha256` 作 join key 关联采样全文。

**（2）幂等与重试已有共识，但覆盖不到"旧指令"。** 腾讯云工程文章的判词很直白：**幂等是重试的前提**，不幂等的写操作配自动重试等于重复下单——建单接口超时重试立起三个工单；异步接口返回 200 只表示"已入队"，真正投递失败没有回执，系统以为成功。工程做法是写操作带幂等键/请求指纹、异步链路等最终回执。Datasumi 补充把操作分为只读/天然幂等/条件幂等/非幂等四类，幂等键须在稳定接口处生成而**不能取自模型的 tool-call ID**，无法判定状态时显式返回 `IN_PROGRESS`/`UNKNOWN_OUTCOME`，并对模糊的金融/破坏性操作禁止自动重试。但这些机制防的是"同一动作的重复"，**防不住"一个过期但合法的动作"**——积压邮件里的改地址请求，幂等键完全正确，它只是**不该在周五被执行**。

**（3）标准层仍然缺席。** OpenTelemetry GenAI 语义约定自 2026-06-12（core v1.42.0）迁入独立仓 `open-telemetry/semantic-conventions-genai`，截至 2026-10 仍为 **Status: Development**，9-11 有稳定化提案（inference span、invoke_agent、execute_tool、token 指标等）但尚未定案。约定里没有 `held_since`、`delivered_time`、`superseded_by`、`resumed_by` 任何一类字段；消息内容是 opt-in 且默认关闭。可观测厂商能给"这个 span 花了多久"，给不出"这条指令在队列里躺了多久、期间有没有人已经处理过它"。

**（4）国内平台开始把"留痕可回放"写进产品。** TencentDB Agent（11-16 发布）以 L1–L4 四级防护（只读自动执行、变更二次确认、高危永久拒绝）、VPC 内部署、权限与 CAM 1:1 对齐、**全链路留痕可回放**为卖点；阿里云 STAROps 升级为 Agentic Ops，强调统一运维上下文与人做关键决策；阿里云 AgentCore 的 UModel 显式保留"地域、版本、运行代次、观察时间"，使 Agent 版本更新或实例重建后仍能沿同一业务身份排查。这些是本期字段族最好的落地载体，但都还没有把**恢复窗口本身**当成一等对象。

## 三、技术竞争力：主要厂商/方案对比

| 方案 | 恢复时积压处理 | 空结果 vs 不可达区分 | pause/resume 授权 | 三时刻可导出 | 决策顺序可举证 |
|---|---|---|---|---|---|
| **Microsoft 365**（11-12 故障方） | 48h 超时窗口扣留、零丢失、按队列序排空 | 首报即"健康检查失败"；200 只是 vote | 平台侧，无 Agent 级具名授权 | 部分（邮件时间戳，无排空/处理时刻） | **无**（顺序=排队序，非决策序） |
| **Anthropic Claude**（M365 连接器/API 11-13） | 连接器随邮件恢复，无积压识别声明 | 状态页自报内部事件，连接器被上游波及 | Managed Agents 有调度/任务，无恢复闸门 | 有限（scheduled tasks 状态） | 无 |
| **OpenAI**（M365 连接器/11-16 诉讼） | 同上；诉讼指向默认 guardrail 缺失 | 审计日志"存在但不跨框架统一" | 诉讼要求 per-tool allowlist、动作预算、HITL | 无统一口径 | 无 |
| **AWS**（us-east-1 11-15） | 3h 连接故障，resolution 未给根因 | IAM Identity Center 区域配置 vs 复制缺失 | 身份层，非 Agent 恢复层 | 无 | 无 |
| **阿里云 STAROps / AgentCore** | 统一上下文、AgentLoop 回看执行质量 | UModel 关联日志/指标/管理状态 | 人设目标、边界与关键决策 | **有**（地域/版本/代次/观察时间） | 部分（可回看，无"谁已处理"记录） |
| **腾讯云 TencentDB Agent** | 全链路留痕可回放 | 四级操作分权，高危拒绝 | L1–L4 显式分级审批 | 有（回放链） | 部分（可回放≠顺序正确） |
| **字节 AgentKit / Managed Agents** | append-only Events 可回放、断点续跑 | LLM 面板缓存命中/TTFT/TPOT | 沙箱与身份权限隔离 | 有（事件只增不删） | 部分（断点是执行位，非决策位） |
| **OpenObserve AI SRE** | 事故变更时自动重跑并**追加**新发现 | 报告含 blind spots 与"无法核查什么" | 动作仅作建议，无自动执行 | 有（时间线标 confirmed/likely/unverified） | 部分（假设带状态与证据） |
| **Google Cloud Ops / ProdAgent** | 事件驱动，未见积压专章 | 健康信号分层，依赖检查归 readiness | Gateway 注入凭据、分层审批 | 有（OTel 原生） | 无 |
| **OTel GenAI 约定**（v1.42.0，Development） | 无 `held_since`/`delivered_time` 字段 | 有 `error.type`/`finish_reason`，无"空即错"语义 | 无 guardrail 约定（自建 `app.*`） | 有 `started_at`/token/模型身份 | **无**（本期最大空白） |

**判读**：扣留策略、幂等键、四级分权、回放链、blind-spots 报告**全行业都已具备**；但"这条指令从发出到被扣留到被执行经历了哪几个时刻、期间是否被人工处理过、恢复由谁授权、执行的是排队序还是决策序"——**十家几乎全空**。这是继幂等并发（第 38 期）、断网重放（第 39 期）、视图指纹（第 43 期）之后的又一个市场空白，且它不靠新增埋点，靠的是**给现有队列加时态语义**。新观点：**看得见"48 小时零丢失"≠看得见"没有一条旧指令被当成新指令执行"**——零丢失在这里恰恰是风险放大器：消息若丢了，Agent 反而不会执行旧指令。

## 四、技术挑战

1. **"零丢失"的悖论**：扣留是正确决策，却把风险从"丢消息"平移到"错时序"。系统优化的是投递完整性，没人优化**投递的时态保真度**。
2. **空结果的三义塌缩**：`[]` 可能是真空、可能是不可达、可能是权限被降级——三因塌成同一个空值，而 Agent 把它读成"没有事要做"（承接第 202 期"记录沉默"，但那是日志层，本期是工作项层）。
3. **幂等救不了"过期但合法"**：幂等键、请求指纹、服务端去重都只处理"同一动作的重复"，对"动作本身已过期"完全无效。这是幂等面与本期的关键划界。
4. **具名授权的落地成本**：暂停 Agent 会在你最需要它的那一天失去它买来的价值；但对比"撤销自己团队已替客户做好的决定"，这仍是更便宜的选项——问题是组织往往在故障中而非故障前决定谁有权暂停。
5. **标准缺口与自报风险**：OTel GenAI 仍 Development，属性名 11 月还在变；"已处理"状态若由 Agent 自己写，就回到第 286 期"审计轨迹自证悖论"——需要独立的、人类侧的工作系统作为权威源。
6. **对冲失效**：多模型/多连接器看似冗余，共享同一数据网关时**相关故障**让对冲归零；这要求把依赖图从"模型层"画到"数据源+身份层"。

## 五、展望与建议

**提出第 236 个字段族 `backlog.replay.*`**（缺省 `BACKLOG_UNVERIFIED`）：`source_channel`、`outage_window[start,end]`、`held_count`、`held_since`（最早排队时刻）、`event_time / delivered_time / processed_time` 三时刻、`order_basis ∈ QUEUE|DECISION`、`superseded_by[]`（已被人工/其他渠道处理的项及权威记录）、`resumed_by`（具名授权人）、`stale_action_count`、`empty_result_class ∈ EMPTY|UNREACHABLE|DEGRADED_AUTHZ`、`verdict ∈ CLEAN|STALE_REPLAY|EMPTY_AS_HEALTHY|UNVERIFIED`。门禁：`verdict ≠ CLEAN` 不得执行写操作、不得回写确定知识、不得进 write≥act 自治级（承第 310–314 期叠加）。

**两条最小日志**（禁裸报"零丢失"）：① 恢复时导出每个工作项的三时刻与扣留时长；② 执行前查"已处理记录"并留 `superseded_by` 命中与否——命中即交人，不自行改。

**三项工程动作**：一是把 lost-link 规则写进 Agent 运行时——失联超时即**默认暂停**，恢复需具名人显式放行，而非自动续跑；二是空结果必须分三元（空/不可达/鉴权降级），不可达一律挂起不"当作没有"；三是"已处理事项"记录放在 Agent 写不到的独立系统（工单/CRM 的人类侧），冲突强制交人。

**评测与采购**：新增一类配对题——"周四改地址、下午电话改回、周五积压邮件抵达"，检验 Agent 是否在写前读取已处理记录并让冲突升级；报 `stale_action_rate` 与 `order_basis` 正确率。采购两问：能否导出恢复窗口内的 `held_since` 与 `superseded_by`？暂停/恢复是否有具名授权与不可篡改留痕？

**标准与治理**：向 `semantic-conventions-genai` 提案 `gen_ai.workitem.event_time / delivered_time / held_since / superseded_by` 四属性；信通院十七层治理补"**积压回灌可举证率**"格，并把"恢复预案是否含 Agent 暂停条款"纳入平台宕机应急检查表。

**本地原型（第 191 期新角度）**：首次开采刘宗明《端云协同下的 Agentic 多端互联实践》——读作"**断连期间端侧攒下的指令，在重连瞬间回灌，谁来标记哪条已被端侧处理过**"，与本期 M365 场景同构；配马云雷"轨迹里最值钱的不是动作，是动作发生时的时态与已被谁处理"、蒋烁淼"秒查的前提是知道该查哪张表——还得知道那张表里的行是哪天的"、赵恒"已处理状态要有权威来源，不能由 Agent 自报"。
