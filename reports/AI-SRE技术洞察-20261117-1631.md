# AI-SRE 技术洞察（第 253 期）

**生成时间**：2026-11-17 16:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-05 至 2026-11 的公开材料
**本期主题**：切换面／区域故障转移与回切（Failover & Failback）——切过去只是上半场，切回来才是事故

## 题眼

2026 年 10 月 20 日，Google Cloud 伦敦区 europe-west2 的 b 可用区因机房电力事件离线。按设计，同区另外两个可用区应当继续扛住；但 Computer Weekly 11 月 10 日的复盘列出 Revolut、HSBC、DPD、Royal Mail 等机构出现中断，连英格兰与威尔士远程庭审的视频平台也停了。同年 5 月，AWS 一处数据中心大厅制冷失效，Coinbase 承认主交易所为降延迟跑在单可用区，备份系统「在故障中没有按预期工作」。AWS Builder Center 9 月 1 日统计：九次重大故障有八次落在 us-east-1，而多 Region 架构也会被拖进去，因为身份与 DNS 路由悄悄假设弗吉尼亚还活着。三份材料指向同一件事：单可用区故障足以打穿「高可用」，而切换之后的回切，几乎没有团队演练过。

## 一、发展趋势

第一条线：韧性叙事从「基础设施韧性」转向「业务韧性」。Computer Weekly 的结论很直接：基础设施韧性不等于业务韧性，关键在依赖映射、切换授权与恢复演练。多可用区是供应商的承诺，依赖图才是你自己的事实。

第二条线：回切被正式承认为更难的一半。Azure 的可靠性文档写明清回切比切换复杂：故障期间原主可能仍在写入，数据同步与冲突处理要单独设计；Astronomer 的 DR 文档更具体——故障转移会反转复制方向，反转之后备用集群无法再恢复被覆盖的数据；回切要先停写、再提升原主。2026 年之前，回切多是脚注；2026 年开始成为正文。

第三条线：Agent 进入切换链路。切换决策、容量核验、DNS 改配、回切对账，都开始被 Agent 承接。但 Agent 擅长「切过去」，因为那是一个有明确成功信号的动作；回切没有单一成功信号，它要求数据对得上、写入不丢、依赖已恢复——这正是 Agent 最不擅长的多条件验收。

## 二、技术现状

把 2026 年的案例按失败位置拆开，切换链路有五个断点：

**其一，共享依赖不在切换范围内。** 伦敦事件里，单可用区故障仍打穿多家机构，原因是 DNS、身份、控制面、第三方支付等共享依赖没有随业务一起切。你切了计算，没切「谁在给你发令牌」。

**其二，容量未验证。** IT168 2026-03-02 对中东机房火灾的复盘写道：有跨 Region 容灾的团队恢复更快，但也有团队发现备用 Region 从没演练过，DNS、连接配置、容量验证一个都没跑通，现场比没有备用方案还乱。

**其三，备份不等于可恢复。** Coinbase 的备份「没有按预期工作」，说明备份成功率与恢复成功率是两个指标，平时只测前者。

**其四，回切的数据账。** Azure 文档指出故障期间原主可能仍写入；Astronomer 文档指出故障转移反转复制后备用侧数据无法回传。两条合起来：切过去这段时间的写入，要么在备用侧，要么在原主侧，回切时必须先对账，否则静默丢一段。

**其五，演练只演上半场。** Zenodo 2026 年 6 月的《Anatomy of a Recovery》复盘一次 SAP 迁移：2.5 小时恢复关键服务，结论包括「云不等于韧性」「回切值得与切换同等严谨」「混沌工程应常备」。多数团队的 game day 到「服务在备用区起来了」就结束，回切从未被计时。

## 三、技术竞争力

| 单 Region 多可用区 | 自动（区内） | 单 AZ 故障 | 无需回切 | 伦敦 2026-10-20 | 共享依赖、控制面、region 级 |
| 多 Region 热备＋DNS 切换 | 手工/半自动 | Region 级 | 需重建复制方向 | AWS 8/9 落 us-east-1 | DNS TTL、身份依赖、容量 |

| 状态页与客户沟通 | 不切换 | 透明 | 不解决 | 第 244 期 | 只告知不恢复 |
| 不切换（接受停机） | 无 | 无 | 无 | — | 业务损失 |

判读：2026 年的变化不是「切换变难了」，而是「回切被承认是独立工程」。上表十行里，只有双活真正不需要回切；其余每一行都需要一份「故障期间写去哪了」的账。厂商卖的是切换编排，回切的对账逻辑仍要自己写。

本期反转：过去 DR 的验收标准是「能不能切过去、RTO 多少」；现在要加两条——「回切 RTO」与「回切数据差」。切换是可用性事件，回切是正确性事件；前者有仪表盘，后者只有对账。

判词：**「DNS／负载均衡／跨区复制／DR 编排／备份软件」全部可采购，「这次切换是谁授权的、切过去期间哪些写入没回来、回切时数据差多少」不可采购。**

## 四、技术挑战

其一，依赖图不完整。控制面、身份、DNS、第三方 API 的依赖往往不在业务架构图里，切换时才发现。

其二，授权不清。谁有权宣布切换、谁有权宣布回切，多数组织没有书面答案；Agent 介入后，这个问题从「人」变成「策略」。

其三，写入账缺失。故障期间原主与备用两侧都可能接受写入，没有 write journal 就无法对账。

其四，回切窗口与业务峰值冲突。回切要停写，停写要选窗口，窗口又要避开业务高峰——这是排期问题，不是技术问题。

其五，Agent 的「切过去就报成功」。切换的成功信号明确（健康检查通过），回切的成功信号是多条件的（数据一致、依赖恢复、无丢失），Agent 容易把前者当后者。

## 五、需求分解、用户旅程与实现方案

**需求分解**：R1 切换依赖图（含控制面/DNS/身份/第三方）；R2 切换与回切的双授权（谁批、批什么、留痕）；R3 故障期写入日志（两侧写入都要可追溯）；R4 回切前置检查（停写、对账、依赖健康）；R5 双 RTO 指标（切过去 RTO、切回来 RTO）；R6 回切数据差报告（按表/按记录）；R7 演练覆盖回切（game day 必须计回切时间）。

**用户旅程**：区域故障告警 → 值班判断是否切换 → 授权记录 → 执行切换（DNS/流量/容量核验）→ 业务在备用区恢复 → 故障期间持续记录两侧写入 → 原区恢复 → 停写备用 → 对账 → 回切 → 验证数据差为零 → 复盘同时报告两个 RTO。

**90 天实现方案**：0–30 天，画切换依赖图（把 DNS、身份、控制面、第三方列入），明确双授权人；31–60 天，加故障期 write journal 与回切前置检查清单，第一次完整演练「切过去 + 切回来」并计时；61–90 天，把回切数据差做成报表，纳入季度演练与发布门禁，Agent 只允许在授权范围内执行切换步骤。

第 180 个市场空白（五项）：①回切 RTO 度量与基准；②切换/回切双授权留痕；③故障期双侧写入账；④控制面/DNS/身份依赖图；⑤回切数据差对账工具。

`failover.*`（`decision_by`、`capacity_verified`、`write_journal`、`deps_checked`）／`failback.*`（`stop_write_at`、`reconcile_diff`、`rto_back`、`approved_by`）第 147 次无人提字段族：平台在卖「一键切换」，没有一家把「切过去这段写了什么、回切差多少」写进记录。
