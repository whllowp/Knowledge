# AI-SRE 技术洞察 · 第 324 期

## 可观测性原生设计面 / Machine-Legible System Design——「把更聪明的模型丢进一套看不透的系统，没用」

- **时间及范围**：2026-11-27 02:00 档（`date` 取 02:37）；限 2026 年，重点近 30 天。
- **期号**：本实例上一期 323（01:00 测量生成面）顺延 324；主线第 277 全新立面；字段族 245；本地连续第 200 期。E 盘并行实例另有不同序列，以文件戳 0200＋本实例序列标识。
- **划界**：#322 信号可归因面问「数字记在谁头上」；#323 测量生成面问「谁审那份埋点计划」；#47 世界模型面问「组织级事实从哪来」。本期退到更靠前的一层：**被观测系统本身在设计与编码时，有没有为机器读者留出入口——命名、运行时、依赖暴露面是不是一种架构属性**。

**题眼**：Anthropic 11-17 披露 Claude Docs 在两周混沌循环后承受 20 亿请求仅 60 次服务器错误、629 次发布零回滚，给出的原因不是模型更聪明，而是「有名字的数据库查询、不用垃圾回收的运行时、每一轮都有遥测，才把循环跑通；把更聪明的模型丢到一套看不透的系统上，是不够的」。同期 OTel 七 Agent 生成插桩的官方复盘承认：Claude Agent SDK 包裹闭源 CLI，框架不暴露的数据「研究与规划找不回来」；ORCA-bench 用 1079 个任务证明拿掉源码访问，每个前沿模型都变差，最弱的模型 40% 直接编造根因。三源指向同一件事：**SRE Agent 的诊断上限在它被叫来之前，就由被测系统的可读性写死了**。看得见「我们上了 Agent」≠看得见「这套系统本来就允许 Agent 看懂」。

## 一、发展趋势

**趋势一：可读性从观测层的附加功能，回退为编码期的架构属性。** Anthropic 的可测量性清单是「有名字的查询、无 GC 运行时、每轮遥测」——全部是被测服务的内部结构，不是后来加的探针。为压测自修复而选 Rust（无 GC、最少依赖、vendor 锁定），使单文档内存从 3GB 降到 180MB、Pod 从 500 降到 50，约 12.5 万美元推理账单替代了「一个团队六个月」的工作。这条经验把成本从「训练更强的排障 Agent」挪到「把系统改造成机器可读」。

**趋势二：暴露面成为测量的硬上限，且补不回来。** OTel 11-12 的生成式插桩 harness 覆盖 CrewAI、LangGraph、Google ADK、Claude Agent SDK 等 12 个框架，但官方写死一条边界：闭源 CLI 内部 Agent loop、工具分发、模型调用都不可见，插件只能报告跨进程边界的东西，「研究规划无法恢复框架不暴露的数据」。可读性不是观测精度问题，是框架暴露面问题——更聪明的 Agent 补不回一个没有的信息。

**趋势三：源码访问被实证为诊断能力的决定变量。** ORCA-bench（11-04 更新，1079 任务）显示：移除源码访问后最好模型简单任务 25.3%、困难任务 10%，最弱模型 40% 编造根因。ITBench-AA 11-17 榜单最好 56.2%、最新型号反降至 38.2%。这些数字往期用作「评测基准」素材，本期换一个方向读：**分数差里有多少来自被测系统对 Agent 的开放程度，而不是 Agent 的推理能力**。

**趋势四：国内平台开始把「可读性」做成产品语义层。** 阿里云 AgenticOps 用 UModel（3200+ 定义、10 个观测域）统一实体关系，AgentSight 走 eBPF 补进程级事实，STAROps 用统一运维上下文做发现—分析—处置闭环；腾讯云 11 月升级 Agent Runtime 矩阵，以 AgentCFS 独立工作区、Agent Bucket 独立 Space、受控挂载与 Agent 级读写 QoS，给多 Agent 共享环境建立可读且可隔离的文件语义，并明确「同步状态与云端提交确认，便于交付前核实文件已上传」。可观测入口正在从指标平台下沉到运行时与文件系统。

## 二、技术现状

六家在「被测系统对 Agent 可读到什么程度」上，现实位置差异明显。

Google 侧，《SRE》第二版（InfoQ 11-15）把可观测配置下沉内部开发者平台，Gemini CLI 已在真实故障中拉告警、做因果分析、关联时序、提缓解方案，人确认后重启；但 Komodor CTO 称「约 30% 可独立解决」为演示口径。11-13 BigQuery 智能体可观测性 GA，把会话记录当业务记录入客户自有表，却在 RLS/动态脱敏时按设计跳过写入——**系统对读者可读，不代表对调查者完整**。

Anthropic 11-12 的 Claude Tag 把指标定义收进语义层、分析步骤写进 Markdown Skills，每轮重新加载：改一句定义下一次查询就换口径，无配套重定基线。11-03 原生 OTel 轨迹接入 Databricks MLflow（Zerobus Ingest＋Unity Catalog），把执行次序而不是最终答案交出来。11-13 两起事故（认证 2 小时、API 2.5 小时）状态页所列受影响组件与实际通知措辞不一致，定时任务晚 2 小时以上或部分跳过。

OpenAI 11-09 的 Control Room 把信任边界放在推理网关：任务领唯一 ID、绑定已批准安全论证，引擎每次生成前回查，停令到断供最长 35 秒；它管的是「任务还能不能产出 token」，不管「这套系统能不能被读懂」。字节火山 DevOps Agent 处于公测，RCA Harness 以假设驱动并行取证、专家 Agent 配 IAM 只读角色；VeOps CLI 把指标、日志、Trace、告警能力交给通用 Agent，文档直陈要解决「跨产品怎么关联、结论怎么审计」。

阿里云 AgenticOps 全栈（云监控 2.0、AgentLoop、STAROps、云效智能体）把 Agent 轨迹、成本、质量纳入观测，LoongSuite 即 OTel 生成式插桩来源；STAROps 在证据不足时不越界定因。腾讯云 CloudQ 以全景图谱组织资源、关系、状态与动作，既给人看也给 Agent 调用，慢回答可下钻到具体调用节点；搜狐畅游已落地 22 个运维智能体，人均管理机器规模为两年前的 3.9 倍（客户口径）。

**共同现状**：每家都能导出遥测、都能装 Agent；没有一家公开「被测系统为机器读者暴露了哪些内部事实、哪些因框架闭源永远拿不到、拿不到时诊断掉多少分」这类字段。

## 三、技术竞争力：主要方案对比

| 方案（近 30 天证据） | 可读事实来自哪里 | 内部事实暴露面 | 取证时是否受隐私裁剪 | 源码/框架不可读的声明 | 关键短板 |
|---|---|---|---|---|---|
| **Anthropic Claude Docs／混沌循环**（11-17） | 有名字的 DB 查询、无 GC 运行时、每轮遥测 | 服务自身为压测改造过 | 未公开 | 未公开盲区清单 | 自报口径；12.5 万美元为标价估算 |
| **OTel 七 Agent 生成插桩**（11-12 官方） | 12 框架 hook/callback＋注册表比对 | 仅跨进程边界 | 内容默认 `NO_CONTENT` | 有：闭源 CLI 盲区「不可补回」 | coverage 只度量不门禁；自定义属性撞标准 |
| **Google Gemini CLI／BigQuery**（11-15／11-13） | 告警＋时序＋因果；会话记录入自有表 | 配置下沉平台 | 是：RLS/脱敏时跳过写轮 | 未公开 | 缺轮可能是策略非 bug；30% 为演示口径 |
| **OpenAI Control Room**（11-09） | job_id、获批安全论证、推理授权状态 | 仅推理网关一薄层 | 不适用 | 不适用（不管可读） | 35 秒不含检测；不撤已发副作用 |
| **阿里云 AgenticOps／UModel**（11 月持续） | 3200+ 定义统一实体关系、eBPF 补进程事实 | 云内资源与轨迹可查 | 按权限策略 | 未公开 | 90%+ 等数值为厂商自测，口径不可相减 |
| **火山引擎 DevOps Agent／VeOps CLI**（公测） | RCA Harness 取证、IAM 只读角色、CLI 暴露遥测 | 云产品内部能力 | 未知 | 公测文档未声明 | 缺公开基准；能力以公测文档为准 |
| **腾讯云 CloudQ＋Agent Runtime**（11-03／11 月） | 全景图谱＋AgentCFS/Bucket 文件语义＋提交确认 | 云 API 长出来的资源与动作 | 受控挂载与 QoS 限定 | 未公开 | 恢复时间、人效为客户口径 |
| **ORCA-bench／ITBench-AA**（11-04／11-17） | 任务内是否给源码访问 | 源码可见与否直接计分 | 不适用 | 是：量化了拿掉源码的掉分 | 榜单快照、测试床非生产 |

**判读**：生成插桩、统一语义层、受控挂载、推理急停、全景图谱全可采购；「这套系统为机器读者暴露了哪些事实、哪些因闭源或脱敏永远拿不到、拿不到时诊断掉多少分、谁批准了这次暴露面的变更」五列几乎全表空白。

## 四、技术挑战

**挑战一：可读性债在编码期就欠下，观测期还不上。** Rust、无 GC、有名字的查询是重构成本；一旦运行时与命名选错，后期只能靠更贵的探针和更大的模型补救。目前没有团队把「Agent 可读性」列入架构评审清单，它是压测中偶然暴露的属性。

**挑战二：裁剪与可读性正相关于风险。** 隐私策略跳过写轮、内容默认 `NO_CONTENT`、闭源 CLI 不暴露内部状态——越是需要取证的高价值区间，机器读者看到的越少。这与遥测供给面的方向性偏差同构，但发生在更底层：不是探针被裁剪，而是系统结构没给探针留位置。

**挑战三：分数里分不出能力与被读程度。** ORCA 的源码可见/不可见落差、ITBench 上最新型号反降，都可以解释为「被测系统可读性差异」而非推理退化。当前榜单不记录 `source_access`，跨模型、跨版本的排名因此不可比。

**挑战四：可读性的变更没有审批。** OTel 官方观察到 Coding Agent 为 CrewAI 加 `gen_ai.crewai.*` 自定义属性撞标准前缀；Claude Tag 改一句 Markdown 定义就换口径。系统暴露面被 Agent 和文档 quietly 改动，却没有「谁批准了这次可读性变更、谁重定基线」的记录。

## 五、展望与建议

**新观点**：前 12 期我们要求「行为可举证、测量可举证」，本期退到起点——**可观测性不是给 Agent 装一只眼睛，而是把被观察的世界修成有形状、有名字、有边界的样子**。Anthropic 的说法最直白：把更聪明的模型丢进看不透的系统，不够。可读性是一种编码期的架构属性，且它的上限由框架暴露面和隐私策略共同写死；不声明这个上限的 Agent 方案，其诊断分数不可解释。

**字段族 245 `system.legibility.*`**（缺省 `LEGIBILITY_UNVERIFIED`）：`subject_id`／`designed_for`（machine_reader／human_only）；`exposed_facts[]{name,source,granularity,version}`——被机器读者可见的内部事实清单；`opaque_regions[]{component,reason∈CLOSED_SOURCE|POLICY_REDACTED|NOT_INSTRUMENTED,declared_by}`；`source_access ∈ FULL|PARTIAL|NONE`；`legibility_delta_withheld`（同一任务拿掉源码/内部事实后的掉分，ORCA 式配对）；`exposure_change[]{revision,approver,rebased_at}`；`verdict ∈ LEGIBLE_DECLARED|PARTIAL_OPAQUE|UNDECLARED_OPAQUE|UNVERIFIED`。门禁：verdict 为 `UNDECLARED_OPAQUE` 或 `UNVERIFIED` 时，该 Agent 的诊断分数不得进横向排名、不得作为自治升档依据（承 #310~#323 逐层叠加）。

**四条最小动作**：①架构评审加一条「Agent 可读性问题」——关键内部状态有没有稳定名字与可查入口；②把闭源、脱敏、未插桩三类盲区显式列成清单随系统交付，禁止用更自信的模型输出填补；③评测强制记录 `source_access` 并报 `legibility_delta_withheld`，无配对不给名次；④暴露面的任何变更（自定义属性、语义层定义）视为接口变更，需审批并重定基线。

**采购三问**：这套系统对机器读者暴露了哪些内部事实？哪些区间因闭源或脱敏永远不可读、有没有声明？拿掉源码访问后诊断掉多少分？

**评测与标准**：在 ITBench-AA／ORCA 之外增「可读性配对题」——同一事故给完整内部事实与仅公开遥测两版，报 `legibility_delta_withheld`；把盲区声明完整性计入总分。OTel GenAI 提四点：`exposed_facts`、`opaque_regions`、`source_access`、`exposure_change`。信通院六维补「机器可读性可举证率」格，与 #316 审批、#317 授权、#318 空窗、#319 判定、#320 自伤、#321 收口、#322 归因、#323 测量八格并列。

**本地知识积累**：第 200 期新角度重读何伟《从生码到可信交付：Harness For Hybrid Coding 实践》——把「可信交付」向前推一格读作「交付物只有在生成时就被机器读懂，才谈得上可信验证」，配刘杨「从 Trace 到规模化实时评估」（评估标签须绑代码版本）、刘凯宁「把大模型关进确定性笼子」（约束要长在 Agent 够不到的地方）、赵恒「数据语义层」（事实源需权威）。173 目录按目录级引用。
