# AI-SRE 技术洞察（第 245 期）

**生成时间**：2026-11-17 09:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-10-18 至 2026-11-17
**本期主题**：定制面／微调与适配器（Fine-tuning & Adapters）——基座升级那天，你的微调模型去哪了

## 题眼

2026-09-10，阿里云 ACK Gateway with Inference Extension 给出多 LoRA 的分阶段发布：同一个基座跑多个 adapter 版本，改 `InferenceModel` 的 `targetModels` 权重就能把流量从 `travel-helper-v1` 挪到 v2，不用动 HTTPRoute。2026-09-24 与 10-02，开源项目 Relax 的两个 PR 把 adapter 发布做成「不可变版本＋会话绑定＋安全回收」：同一 Session 的后续生成固定用同一个 `immutable lora_path`，commit 之后旧版本仍允许已绑定会话继续，直到没有绑定才回收。2026-05-22 的 ReLoRA（arXiv 2606.02606）则直接承认：现有评测只看离线重适配时间，**没测在线 SLA、请求级延迟与多租户干扰**。安全侧更冷：EMNLP 2026 Findings 的「When Safety Routing Breaks」用 100 条良性微调样本就让拒答塌陷；ACL 2026 的相似性分析把原因追到对齐数据与微调数据的表示相似度。

## 一、发展趋势

**第一，adapter 从「训练产物」变成「可发布制品」。** 有版本、有内容摘要、有基座校验、有灰度权重、有回收策略——它正在获得和容器镜像同等的待遇。

**第二，基座升级成为一等运维事件。** 微调模型不是独立存在的，它是「基座＋adapter＋数据」的函数；基座换代，adapter 的语义随之漂移。ReLoRA 把这类场景命名为「evolving LLM services」，用知识复用把重适配从数天压到数小时。

**第三，多租户共享基座成为默认。** 一个基座挂几十上百个租户 adapter，靠路由与批处理共存；冷启动、显存驻留、相互干扰从论文问题变成值班问题。

**第四，安全回归被单独拎出来。** 良性微调就能削弱拒答，且「少样本可恢复」意味着 internal representation 还在——问题不是能力丢失，是路由被改写。上线前的安全评测因此必须针对「微调后」而不是「基座」。

**第五，灰度从模型级下沉到 adapter 级。** 按权重切版本、按会话绑定版本、按租户隔离版本，三种粒度同时存在。

## 二、技术现状

**ReLoRA** 用低秩知识复用把旧 adapter 的知识迁到新基座，减少全量重训；它明确把在线 SLA、请求级延迟、多租户干扰列为未覆盖项——这恰好是 SRE 的题库。

**Relax** 的 PR 体现了生产级细节：adapter 导出时封不可变版本与内容身份、校验基座；所有固定目标 pin 住、resident、ready 后才 commit default；跨 tool turn 与 abort/resume 绑定同一 native LoRA 实例；GPU drain 后 fence 迟到操作、逐个 retire；并且**禁止底层透明重发**——HTTP 超时不等于后端没接受，重试只能由上层状态机决定。

**阿里云 ACK** 把灰度做成网关能力：`targetModels` 权重 0→100 渐进，按输出质量监控每档；`InferenceModel` 与 HTTPRoute 解耦，回滚就是改回权重。

**NVIDIA NemoEntitystore** 提供 adapter 的存储、版本、元数据与动态加载，让 NIM 实例不重部署基座就能挂租户 adapter，支持多租户与版本追踪。

**LateFuse**（EMNLP 2026 Industry）给冷启动数字：编码器多租户场景，PEFT 顺序加载在 N=100 时 14.4 秒、N=1,000 时 1,180.7 秒；LateFuse 的 AdapterStore 预加载是 0.05 秒与 0.29 秒，差 299–4,071 倍。

现状判断：**发布、灰度、回收的工具链在成形，但「升级后行为等价」与「微调后仍然安全」两件事，仍靠各家自建评测。**

**判读**：训练框架、LoRA 服务、网关灰度、adapter 存储都能买或能抄。分水岭在证据：这个回答由哪版基座、哪版 adapter、哪份训练数据产生；基座升级后，同一批输入的行为差异有没有被量过；良性微调之后，拒答率还在不在。

**本期反转**：过去把微调当「模型定制」，现在要当**依赖管理**——adapter 依赖基座，基座依赖版本，评测依赖快照；三者任一漂移，线上行为就不可复现。

**判词**：「GPU、训练框架、LoRA 服务、网关灰度、adapter 存储」全部可采购，「这个回答由哪版基座＋哪版 adapter＋哪份数据产生，且升级后行为等价、微调后仍然安全」不可采购。

## 四、技术挑战

**其一，基座升级的语义漂移。** 同一 adapter 挂到新基座，输出分布会变；没有 A/B 与固定 eval，只能等用户发现。

**其二，安全塌陷。** 100 条良性样本即可削弱拒答；上线评测若只跑基座，等于没测。

**其三，会话中途换版本。** 热更新时进行中的会话若被切到新 adapter，前后文风格与工具契约都可能变；必须 pin 版本到会话结束。

**其四，冷启动与驻留。** 租户 adapter 越多，加载越慢、显存越紧；空闲 adapter 占着显存是纯成本。

**其五，回收与墓碑。** 旧 adapter 何时能删？还有会话绑定、还有审计需求时不能删；删了之后旧回答无法复现。

**其六，评测缺口。** 论文自认没测在线 SLA 与多租户干扰；工程侧又常只测离线 loss。

**其七，数据授权。** 微调数据里的 PII、客户数据、许可证，随 adapter 一起分发；没有 lineage 就说不清。

## 五、需求分解、用户旅程与实现方案

**需求分解（五项）**：① adapter 可不可变发布、可校验基座；② 会话绑定版本、升级不打断；③ 升级前后行为等价可举证；④ 微调后安全回归必测；⑤ 回收有规则、删除有审计。

**用户旅程（模型平台 SRE）**：基座新版本发布 → 盘点受影响 adapter → 离线重适配/知识复用 → 固定 eval 集对比 → 安全回归（拒答/越狱）→ 灰度 5%→50%→100% → pin 会话、观察 → 旧版本保留 → 回收与墓碑。

**90 天实现方案**：
- **0–30 天**：给每个 adapter 补元数据（基座版本、数据版本、训练配置、eval 快照、安全评测结果）；建立固定 eval 集与「升级前后差异」基线；禁止无名 adapter 上线。
- **31–60 天**：adapter 不可变发布＋会话 pin；灰度按权重切，回滚=改权重；补安全回归到发布门禁；统计冷启动与驻留成本。
- **61–90 天**：做一次基座升级演练（含回滚与旧版本回收）；把「行为等价」纳入发布 checklist；产出 adapter 生命周期 runbook 与审计包。

**第 173 个市场空白（五项）**：adapter 血缘台账、升级等价验收、微调后安全回归服务、会话级版本 pin、adapter 回收审计。
