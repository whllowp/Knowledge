# AI-SRE 技术洞察（第 206 期）

**生成时间**：2026-11-16 06:00（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：假命中面／提示词缓存命中率的可证伪性（Phantom Cache Hit / Cache-Hit-Rate Integrity）——缓存失败不抛异常，只寄账单；当 99% 的命中率无法被证明，它就是最贵的假数

---

## 题眼

11 月，Datadog 官方博客公开了一次内部排查：应用"看着启用了提示词缓存"，实际却没命中——三次请求各 18 万+输入 token，每次 $0.74–0.82，缓存 Hits 记录为 0；根因是时间戳写进了可复用指令的**最前面**、工具列表由 Go map 迭代导致**顺序每条不同**。更刺眼的是排查过程本身：应用和网关可能把同一次模型调用**各记一遍**（成本算两遍），有的记录**干脆缺 cache 字段**，让缓存"看起来没启用"。同月，Revefi 复盘把一句话钉成了行业警句：**「缓存失败不抛异常，它们只寄账单。」**——他们发现排名第五六七的 Agent 命中率接近零，「像当初的我们一样安静地烧钱」，修好后单个 Agent 年化省约 30 万美元。而火山引擎的官方文档写得更直白：**「HTTP 200 或配置回显不能单独证明命中，实际命中以缓存 Token 大于 0 为准。」**

**三个独立来源，指向同一个被行业集体忽略的事实：缓存命中率是一个"数字在、却可能是假的"指标。它不报错、不告警、不影响任务成功率，只是安静地把成本抬高几倍。**

## 一、发展趋势

**趋势一：命中率从"观测指标"变成"定价假设"。** 腾讯 Hy4 直接把 95% 缓存折扣、82% agentic 命中率写进价格模型（$0.042/M 命中 vs $0.834/M 新输入）。**命中率一旦进定价，假命中就不再只是技术债，而是扭曲 P&L 的财务变量**（205 期）。

**趋势二：命中率做成一等仪表盘，但"可证伪性"没人做。** 火山把"缓存命中率/缓存 Tokens"列为服务监控一级指标，Anthropic Console 有 Caching 视图，OpenAI usage 面板拆分缓存指标；**六家都给你一个数字，没有一家给你"这个数字怎么证伪"**（185 期：尺子谁定）。

**趋势三：路由亲和成了命中的隐性前提。** 火山 Prompt Cache Key 明说"尽力而为、不承诺命中"，扩缩容/发布/故障切换都会重路由。**命中率越来越是"请求落在哪个副本"的函数，而不是"我的前缀稳不稳定"的函数。**

## 二、技术现状：从"开关"到"可证命中"的三态塌缩

**态一，开关打开（配置回显）。** 团队普遍的验收标准——`enable_caching=true`、控制台绿灯。**这是最弱的一态。**

**态二，命中发生（usage 佐证）。** `cached_tokens > 0` 才算真命中；Anthropic 需区分 `cache_read_input_tokens` 与 `cache_creation_input_tokens`，后者是"写"不是"中"。**多数团队停在第一态，把第二态当成了默认成立。**

**态三，命中可证伪（前缀哈希 + 归因）。** 记录每轮 `prompt.sha256`，才能区分"是我方 Agent 重写了上下文"还是"供应商丢了缓存条目"（CSDN DevPress 11 月）；没有这一态，**未命中就是一笔糊涂账**。

**现状：三态被塌缩成一态。** 行业把"开关打开"当成"命中发生"，把"命中发生"当成"命中可归因"；**于是 99% 的会话平均命中率里，可以藏着某一次被时间戳打断后的全额重读**——平均值正好掩盖了最该被看见的那次（"按会话平均"是最常见的自欺口径）。

## 四、技术挑战

**一，沉默失败。** 缓存失效不抛异常、不发告警，只抬高账单（Revefi）。

**二，三态塌缩。** 配置回显被当成命中发生，缺 usage 佐证。

**三，归因缺失。** 没有 `prompt.sha256`，无法区分本地重写与供应商丢弃（CSDN）。

**四，双重计数。** 应用与网关各记一次调用，命中率分母与成本同时被污染（Datadog）。

**五，平均值自欺。** 会话级 90% 命中掩盖某一次 0% 的全额重读。

**六，路由非承诺。** 扩缩容即失效；命中率成了物理位置的函数（火山）。

**七，评测盲区。** ITBench／RCA-Bench／SWEOps-Bench 只测任务成功率，**没有一项测"命中率是否可证伪"**——命中率造假不影响榜单得分。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `cache.proof.*` 字段**：`prefix.sha256`（每轮前缀哈希）、`cache.hit_verifiable`（usage 佐证）、`cache.double_count_free`（去重计数）、`cache.miss_reason`（结构化原因码）、`cache.per_turn_rate`（每轮命中率）。
- **R2 三态分离**：开关／命中／可证命中分开上报，**禁止用配置回显冒充命中**。
- **R3 每轮口径**：按轮次而非会话平均上报 `cached_tokens/total`，**让全额重读那一次露头**。
- **R4 未命中当变更信号**：命中率突降先查 prompt 版本／工具顺序／JSON key 顺序，再查供应商（接第 24 期）。
- **R5 去重对账**：应用与网关以 `request_id` 归一，成本与命中率同源。
- **R6 指标**：前缀哈希覆盖率、命中可证率、未命中归因率、双重计数检出率、每轮命中率。

### 5.2 用户旅程

- **平台工程师**：账单突增 → 查每轮命中率 → 发现某轮 0% → 比对 `prompt.sha256` → 定位到时间戳前置。
- **SRE**：命中率告警 → 读 `miss_reason` → 判断是本地变更还是供应商丢条目 → 决定回滚 prompt 还是报障。
- **财务**：按可证命中核算 ROI → 不让 82% 的定价假设替实际命中率说话。
- **审计**：抽查任一 Agent → 命中率可被 usage 与前缀哈希复原。

### 5.3 实现方案（90 天）

- **0–30 天**：给所有模型调用补 `prompt.sha256` 与 usage 三字段（读／写／总量），关掉会话平均口径。
- **30–60 天**：应用与网关去重对账；上线 `miss_reason` 枚举（`prefix_changed`／`below_threshold`／`ttl_expired`／`provider_dropped`）。
- **60–90 天**：命中率进变更门禁与成本模型；把"命中可证率"写进采购条款与评测基准。

**第 145 个市场空白（五项）**：命中可证率、前缀哈希归因率、未命中原因码覆盖率、双重计数检出率、每轮口径采纳率——无一内建；`cache.proof.*` 为**第 114 次无人提字段族**。本地 173／173-kb 连续第 104 期成组启用：**30 陶炳哲「同权重同挂牌价，供应商吞吐差 23 倍、成本排序会翻转」首次当主线**——本期靠它把"供应商侧差异 vs 我方前缀稳定性"的归因难题立起来；配 08 刘杨（`agent.prompt.sha256` 作为 trace 与载荷的 join key，本期深化为命中归因键）、14 施宏斌「可验证 Eval」。判词：**本地把"供应商差异与成本弹性"写进路由评测，联网侧 11 月才把"命中率不可证伪"当一等问题；两边都没把前缀哈希与命中佐证做成可导出字段。**
