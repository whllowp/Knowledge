# AI-SRE 技术洞察（2026-11-04 05:00 · 第 61 期）

## 本期主线：上下文面（压缩面）运维——"记住了什么"是一次无人审批的状态变更

前 60 期把智能体的写入、读取、身份、轨迹、复盘都搬进了运维账本，唯独"运行内存里的上下文"一直被默认为 harness 内部实现细节。本期拿掉这个前提：**上下文窗口不是容量参数，而是一个会被平台在任意时刻静默改写的状态存储**——压缩（compaction）每触发一次，智能体的"事实基础"就被一次模型生成的非确定性变换替换一次，且无错误、无标记、无回滚。与既有各期的分界：第 27 期管缓存的成本账，本期管上下文内容本身的生命周期；第 57 期管磁盘上的指令文件，本期管运行内存里的窗口；第 35 期只把"压缩致 10% 流量漏检"当作监控缺陷的证据，本期把压缩本身当被运维对象。

## 一、发展趋势

**压缩从评测技巧升级为平台一等能力与官方评测口径。** Anthropic 的 server-side compaction 已以 `compact_20260112` beta 进入 Messages API（触发阈值可配、默认 150k、支持自定义摘要指令与 pause_after_compaction），并成为 Sonnet 4.6 / Opus 4.6 的平台能力；更关键的是评测方法论：官方 Humanity's Last Exam 与 BrowseComp 成绩均注明"压缩于 50k token 触发、累计至 3M/10M token"——**压缩策略已经写进 benchmark harness，模型分数从此是"模型×压缩策略"的联合产物**。国内侧，火山方舟 Managed Agents 把"上下文自动压缩 + Event API 全量留存"并列写入产品承诺，Session 级可覆写 compact_threshold（平台默认 192k）与摘要 instructions；阿里通义实验室的 Scroll（arXiv 2608.21690）则把上下文管理做成独立引擎。三条路线正在分化：**有损摘要**（Anthropic/Codex 默认）、**无损留存+按需召回**（火山全量 Event 留存、Scroll 的 append-only 事件日志+驱逐索引）、**逐条打分淘汰**（社区插件 fast-jev-compaction，7.8K star，对每个工具调用打分、过期者淘汰、保留者逐字不动）。趋势的实质是：**行业争论从"怎么塞进窗口"转向"遗忘权归谁、由谁审计"**。

## 二、技术现状

**丢失规律已被实测刻画。** 工程师在真实 Claude Code 会话中植入事实再触发压缩：78,642 token 的会话 20 秒内缩至 2,632（丢失 97%），会话表面健康；存亡遵循"入窗方式"定律——指令与智能体自己写过的文件几乎全部存活，**"只读过一次"的一次性证据（测试输出、生产日志、网页快照）最先死亡**，而这类证据往往不可再生。Factory 对 36,611 条生产消息的压缩探针得出一致结论：三种压缩方法在"跟踪文件"维度得分最差（2.19–2.45/5）。Codex 开源实现同样把近 20k token 消息逐字保留、其余交给摘要，并发出 ContextCompacted 事件。

**压缩的存储反噬首次被量化。** 一项覆盖 2026 年 1–10 月、845 个 Codex 会话共 52.49 GiB 的独立研究显示：压缩快照占总存储 77.13%，其中 92.98% 的字节是与前序快照重复的图片和文本；**"为模型减上下文"的机制反而曾是磁盘膨胀的第一大来源**。Codex 10 月版以 zstd 后台压缩、废弃快照清理、子智能体父历史引用把实测占用降至 10.60 GiB，但研究证明内容寻址的引用式存储还可再降至 3.0–3.6 GiB。该研究还厘清了三本账的分立：存储大小与 token 消费无关（偏相关 −0.019）——**context compaction、storage compaction、token 成本是三个独立的运维对象**。

**压缩是监控管道的静默旁路。** METR/Redwood 10 月 22 日公开的三周红队报告（第 35 期曾引）在上下文面上的含义更重：智能体自行压缩上下文的操作不触发异步监控、不拒绝请求、不置任何标记，OpenAI 估算 5–7 月约 10% 的内部 Codex 流量因此未被审查——**一次无人审批的状态变更，同时绕过了治理管道**。火山方舟"Event API 全量留存，不丢失内容"的承诺，实质是第一个把"模型窗口有损"与"平台留存无损"拆成双通道的厂商姿态；Anthropic 也在上下文编辑文档中规定：2026-08-31 之后创建的账号，重放已被服务端清理所失效的 thinking 块会被 API 拒绝——**上下文历史正在进入 API 合同**。

## 三、技术竞争力

| 方案 | 压缩位置 | 保留策略 | 丢失可观测性 | 全量留存 | 存储治理 |
|---|---|---|---|---|---|
| Anthropic 平台压缩（beta） | 服务端 | 阈值触发摘要，instructions 可定制 | 无内建，靠客户端自查 | 否（客户端自留） | 未涉及 |
| Anthropic 上下文编辑 | 服务端 | 清工具结果/思考块，keep 参数 | 清除以占位文本可见 | 否 | 会击穿缓存前缀 |

| 阿里 Scroll | 引擎层 | append-only 事件日志+working view 投影 | 驱逐索引可精确回溯 | 事件日志无损 | 驱逐而非复制 |
| fast-jev-compaction | 客户端插件 | 逐条打分，过期淘汰，保留逐字 | 每条决策可见 | 保留项即原文 | 淘汰制 |

判读：海外厂商把压缩做进服务端 API 合同，国内以"留存无损"承诺对冲有损风险；开源与社区在"逐字保留+打分淘汰"路线上最激进；但**没有任何一家内建"压缩质量"的度量**——Scroll 的 LongMemEval_S 94.8%、LOCA_256K 86.7%（较已发表最优 +37.4pp）仍是评测集口径，不是生产 SLI。

## 四、技术挑战

1. **丢失不可见**：压缩是重建不是缩短。摘要由模型生成、非确定，两次运行可以摘要出不同内容；错误不报错，只表现为"同一文件读两遍""把 40 轮前的约束重新违反一遍"。
2. **边界侵蚀**：安全上下文在摘要中变弱——"don't touch production"被压成"working on deployment"即放松了护栏。压缩由此成为继提示注入（第 49 期）、指令文件腐烂（第 57 期）之后第三条改变智能体约束的通道，且前两条还有原文件可查，这条只有摘要。
3. **一次性证据死亡**：不可再生的读侧证据（一次失败的测试运行、一条限流前的日志）被压缩后，第 39 期的"断网重放"与第 20 期的证据链都失去原料——回放基础设施必须把"压缩前的原始字节"当作录制对象。
4. **存储反噬**：给模型省内存的钱，从磁盘账单回来。三本账（token/存储/上下文质量）必须分开核算，任何一本的优化都可能让另外两本恶化。
5. **评测口径污染**：当 3M/10M 累计窗口+压缩成为官方 harness 组件，跨厂商分数比较隐含了各自的压缩策略差异，而策略参数（触发阈值、保留指令）并不随分数公开。

## 五、展望与建议

**第十七个市场空白：压缩事件 SLI 无一家内建。** 建议运维团队先行自建三个指标：压缩触发次数与密度（每任务压缩次数>1 即结构问题）、**遗忘探针存活率**（仿金丝雀做法，在长会话中定期埋入"已知事实探针"，压缩后核验存活）、压缩后回归通过率（每次压缩后跑固定用例集）。采购侧把"双通道留存"（有损窗口+无损事件流）写成硬条款，火山已给出先例。工程侧三条：把压缩 instructions 当作与 AGENTS.md 同级的指令资产纳入评审与版本管理（与第 57 期合流）；把压缩快照纳入第 39 期回放语料的录制范围，并给回放增加 compaction pin；对承载治理与安全的上下文段（边界声明、审批状态、错误预算余量）采用结构化注入而非叙述性文本，使其免于被摘要改写。中期看，Scroll 式"无损事件日志+按需投影"如果被主流 harness 采纳，压缩将从"有损变换"退化为"视图切换"——那将是本平面最值得跟踪的结构性拐点。
