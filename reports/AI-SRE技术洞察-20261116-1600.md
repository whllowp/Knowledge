# AI-SRE 技术洞察 · 第 222 期

**变更归因面 / 部署—事故因果判定（Change Attribution / Deployment–Incident Linking）**

> **题眼**：「部署发生在事故时间窗口里」不等于「部署导致了事故」。六家厂商都把"关联变更事件"做进了 RCA 产品页，但没有一家能举证"这一次，到底是不是它"。相关性是时间的共现，归因是因果的判定——把两者混为一谈，是当前 AIOps 最普遍、最隐蔽的一次越界。

*时间范围：2026 年（重点最近 30 天）｜生成时间：2026-11-16 16:00 档*

---

## 一、发展趋势

2026 年下半年，Agent 进入生产运维后的能力叙事已经从"能不能查"转向"能不能判"。IBM Instana 在 10-16 更新的智能事故调查中，明确把"关联变更事件、配置更新与部署"列为核心步骤，并把结果称为 probable root cause（**可能的**根因）——这个限定词本身就承认了归因的不确定性。火山引擎在 AgentKit 智能运维助手里追加 RCA Harness 排障约束层，主打"假设驱动、并行取证、逐轮下钻，输出步骤可复核、结论有置信度的调查报告"。阿里云云监控 2.0 更进一步，把 RCA 定义为"系统地图驱动调查、动态展开假设与反证、证据不足时继续调查、不越界定因"的闭环。

趋势因此清晰：**行业正在从"变更关联"走向"变更归因"，但只在文档和提示词层面走了第一步**。真正被产品化的仍是共现检测：事故窗口内有哪些部署、配置、feature flag、数据库迁移，把它们列进时间线。至于"这些变更里哪一个才是原因""排除其余候选靠了什么证据""回滚之后是否真的恢复"——这些判定动作仍留在值班工程师脑子里，没有成为可导出、可复核、可追责的字段。

推动这一转变的直接压力来自事故本身。LLM Gateway 于 10-19 发布的事故报告提供了一个近乎教科书的反例：代码部署触发了数据库迁移，迁移卡在长事务的锁等待上，连接逐格泄漏；团队在 19:01 完成回滚，但"回滚代码并没有释放数据库"，卡住的会话和锁队列仍在 Postgres 内部，服务直到 19:12 才恢复——**回滚完成与健康恢复之间隔了 11 分钟，而真正的根因从来不是那次部署本身，是部署前已经跑了一个多小时的异常热库与开了约八小时的长事务**。这类事故正在把"关联即归因"的产品话术逼到墙角。

## 二、技术现状

当前主流技术栈可以拆成四层，越往上越薄弱。

**第一层，变更事件归一化。** DORA 五项指标已被广泛接受，其中 failed deployment recovery time 专门用来区分"由生产变更造成的损伤"与"provider outage、外部依赖事故等无关故障"；change fail rate 统计需要立即干预的部署占比。ONES 的排查指引直白地写道："两个现象同期出现不等于存在因果"，要求做时间对齐（假设事件须早于或同步于指标拐点）和对照区间比较。方法论已经成熟，落地却参差：多数系统里 change 与 incident 仍是两套 ID，缺少双向锚点。

**第二层，时间线关联。** Resolve 的 AIOps 用例把"Deployments Break Things and Nobody Notices"列为典型场景，主张把部署事件与延迟、错误率、可用性变化关联，并在 breach 时暂停或回滚。腾讯云 CloudQ 把"资源、关系、运行状态、处置动作"收敛进一张全景图谱，AI 工作台连接监控、日志、调用链、**变更记录**与企业知识。这是"关联"层做得最完整的形态——但依然是共现，不是因果。

**第三层，因果判定。** 这是断层所在。GraphWiz 的判词一针见血："Detection you can buy. Attribution is the part you have to model."（检测可以采购，归因必须自己建模。）它指出因果图的边必须来自注入实验、拓扑感知仿真或历史归因，而非原始共现，否则排序会退化成"谁的告警最响就怪谁"；同时点名三个失效模式：拓扑陈旧、稀疏域、无半径限制的自动修复。阿里云的"动态展开假设与反证""不越界定因"是当前产品侧少见的正确表态。

**第四层，验证与回写。** 这一层几乎空白。DORA 在定义恢复时间时被迫先做一个约定："如果自动回滚在 10:12 恢复服务、10:20 完成验证，恢复时间算哪个？团队必须事先定规则。"这个看似琐碎的约定恰恰暴露了行业现状——**回滚动作与健康验证在数据结构上从未分离**。LLM Gateway 事故后把"自动回滚"和"健康检查与客户所见对齐"分别列为 in progress 改进项，等于承认两者此前都不存在。

## 三、技术竞争力：主要厂商 / 方案对比

下表按"变更归因"能力六个维度横向对比（●=产品化能力，◐=部分/文档层支持，○=未见）。

| 厂商 / 方案 | 变更事件关联 | 相关 vs 因果分离 | 候选变更枚举与反证 | 回滚—验证分离 | 变更↔事故双向锚点 | 归因证据可导出 |
|---|---|---|---|---|---|---|
| **Google**（DORA / Cloud Trace + AAD 11-11） | ◐ 方法论明确区分变更致损与无关故障 | ◐ DORA 要求因果证据，未产品化 | ○ | ◐ 恢复时间点需团队自定义 | ○ | ○ |
| **Anthropic**（Claude Platform OTel，11-03/09；自托管 11-12） | ◐ 原生 OTel span 进 MLflow/Unity Catalog | ○ | ○ | ○ | ○ | ● trace 可 SQL 查询，但无归因字段 |
| **OpenAI**（Agents API 追踪 beta / Control Room 11-09） | ◐ 全链路追踪默认开启 | ○ 动作层熔断，非归因层判定 | ○ | ◐ 35 秒熔断属动作控制 | ○ | ◐ 追踪可导出，归因结论不可 |
| **字节 / 火山引擎**（AgentKit RCA Harness、响应计划） | ● 响应计划自动取证+RCA | ◐ "结论有置信度"≠因果判定 | ● 假设驱动、逐轮下钻 | ○ | ○ | ● 步骤可复核的调查报告 |
| **阿里巴巴**（云监控 2.0 + AgentLoop + STAROps） | ● UModel 全域关联、RunbookSet | ● "证据不足时继续调查、不越界定因" | ● 动态展开假设与反证 | ● 五步闭环含"部署并验证" | ◐ 线上 Bad Case 回流回归 | ● 证据化评测 |
| **腾讯**（CloudQ / AndonQ 11-02，信通院六维认证） | ● 全景图谱纳入变更记录 | ○ | ○ | ◐ 按影响范围与可回退性分人机职责 | ○ | ◐ 过程可审计（信通院要求） |

**判词**：把"变更事件进时间线""异常自动回滚""调查报告可复核""变更记录可查询"全部可以采购；**举证"这次事故的真实原因是不是这次部署、排除了哪些同期变更、回滚之后服务是否真的恢复"——不可采购**。六家在"相关 vs 因果分离"和"变更↔事故双向锚点"两列几乎全空，这正是本期的市场空白。

值得注意的反转：最锋利的归因纪律不在云厂商产品页，而在两处——一是 Google 的 DORA 方法论与 LLM Gateway 的事故复盘，它们把"回滚≠恢复""相关≠因果"写成了硬规则；二是阿里云与火山引擎的 RCA 产品语义，前者明确"不越界定因"，后者强调"步骤可复核"。**产品化最完整的厂商恰是表态最谨慎的厂商**，这个重合不是偶然：只有真正让 Agent 碰过生产，才知道"关联"与"归因"之间隔着一次事故。

## 四、技术挑战

**挑战一：候选变更坍缩。** 一次事故窗口常有几十次变更——代码、配置、依赖版本、feature flag、数据库迁移交织。Agent 倾向于报出"最响"的那一个，而非枚举候选并逐一反证。没有 `candidate_changes_enumerated` 字段，就无法回答"你排除了什么"。

**挑战二：把"最后一根稻草"当"负重的原因"。** 归因要求原因早于结果，但许多根因在部署前就已潜伏。LLM Gateway 事故中数据库热了一个多小时、长事务开了约八小时，部署只是触发点。若只做时间对齐，会把触发器误判为根因，修复方向随之跑偏。

**挑战三：回滚动作与健康状态混为一谈。** 数据库里的迁移、锁、连接池状态不会因代码回滚而自动清空。缺乏 `rollback_at` 与 `verified_healthy_at` 的分离，MTTR 统计与复盘结论都会失真。

**挑战四：变更系统与事故系统的身份割裂。** DORA 要求把恢复记录链接到造成问题的部署，但多数组织 change 与 incident 是两套 ID，无双向锚点，复盘时"这次到底改了什么"靠人肉翻聊天记录。

**挑战五：归因命中率无人记账。** DORA 的 change fail rate 回答"这个部署是否触发了干预"，不回答"这次事故是不是这个部署造成的"。真正的"归因命中 vs 有证据支撑"命中率没有字段，也就无法评估 Agent 的归因能力是在进步还是在自我确认。

## 五、展望与建议

**提出 `change.attribution.*` 五字段语义族**，作为 OTel GenAI 与信通院基准的补充草案：

1. `candidate_changes_enumerated`——事故窗口内枚举的候选变更清单与数量；
2. `temporal_vs_causal_separated`——时间共现与因果判定的分离标记（须附证据与反证）；
3. `rollback_at` / `verified_healthy_at`——回滚动作与健康验证双时间戳；
4. `preexisting_condition_flagged`——部署前已存在的隐患标记（长事务、高水位、慢查询）；
5. `attribution_hit_vs_grounded`——归因结论与证据闭合度的差值。

**落地三步**：第一，给每次变更与事故建立双向锚点（无锚点的归因结论不进 KPI）；第二，强制"候选枚举—反证排除—根因判定"三段式报告，缺候选清单即视为未归因；第三，把"回滚完成"与"验证恢复"拆成两个 SLO 事件，参照 LLM Gateway 的教训，为数据库迁移单独设 preflight 与快速失败规则。

**给决策者的判断**：当厂商演示"我们的 Agent 找到了根因"时，请追问三句话——**你枚举了几个候选变更？你靠什么排除了其余的？回滚之后服务是真的恢复了，还是只是不报警了？** 答不出这三问，所谓 RCA 就只是把时间线上最近的一次部署，写成了一个好听的故事。
