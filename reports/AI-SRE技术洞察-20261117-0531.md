# AI-SRE 技术洞察（第 241 期）

**生成时间**：2026-11-17 05:31（Asia/Shanghai）
**观察窗口**：2026 年内，重点 2026-10-18 至 2026-11-17（近 30 天）
**本期主题**：传输面／网络长尾（Network Tail）——p99 不是应用慢，是重传在替应用背锅

## 题眼

- **阿里云开发者社区（2026-05-11）**：一次真实排障——订单查询服务 **P99 从 80ms 飙到 4823ms**，QPS 不高、CPU 35%、内存 60%、DB 无慢查询、APM 链路追踪“看不出任何异常”；用户就是喊慢。最后靠 tcpdump 抓包与内核 socket 状态定位到 **TCP 重传**。作者的原话很刺：**所有应用层指标都告诉你“没事”，但用户说慢**。
- **Cloudflare（2026-05-05）**：DENIC 为 `.de` 顶级域发布了损坏的 DNSSEC 签名，**数百万域名在几小时内不可达**；解析链从根到 `.de` 再到每个域名，**任何一环断了，下面全部验证失败**；1.1.1.1 靠 serve-stale 缓冲了冲击，恢复靠修 DS/KSK 链。
- **UptimeRobot（2026-05-05）**：同一事件的观测侧数据——`.de` 监控告警量涨到平时晚间的 **3–4 倍，峰值约每分钟 10,000 条**；问题“坐落在大多数站点自身基础设施之下”，**你的站点没改任何东西，可用性却归零**。
- **MeshTrek/eBPF 测量开销研究（Brown）**：基于内核 eBPF uprobe 的观测，每次探针触发两次上下文切换；高请求率下**测量机制本身会不成比例地影响尾延迟（p99），把观测到的尾巴做大**——**你以为在测 p99，其实在制造 p99**。
- **AI Infra Book 路径实测（2026-08）**：同一 ASR 负载、连接保持，**p99 在调优客户端后从 1026.5ms 降到 373.5ms**；到了 LLM 流式场景，“总延迟”同时掩盖了首 token 等待与流能否跟上两件事。

## 一、发展趋势

**尾延迟的归因，正在从应用层下沉到传输层。** 2026 年的几份材料拼出一条共同的因果链：应用指标全绿、APM 无异常、用户仍说慢（阿里云案例）；一个 TLD 的 DNSSEC 记录坏了，整片域名不可达（Cloudflare/UptimeRobot）；观测工具自己把 p99 做大（eBPF 研究）。它们指向同一个转向：**p99 不是应用层的属性，而是“应用 + DNS + TCP/TLS + 观测”整条链的属性**。Agent 让这件事更尖锐——一次任务要串行调用十几个工具，**每一跳的传输尾部都会乘起来**（第 217 期乘法可靠性），而你的仪表盘还在看 HTTP 时长。

## 二、技术现状

**四层各自有盲区。** L7 APM 看 HTTP 耗时，看不到重传、RTT、连接建立、TLS 握手、DNS 解析；L4 指标（重传率、RTT、cwnd）在云厂商监控里通常要单独开；DNS 与 TLS 往往由平台团队拥有，**故障时没人认领**；eBPF 能下沉，但探针开销会扰动尾部。

**重传的代价不是“多一个 RTT”。** 超时重传触发拥塞窗口收缩、后续请求排队、连接池被占；一次丢包可以让一批请求同时慢下来，表现为**间歇性、成批的 p99 尖刺**，而不是持续高延迟。

**DNS 是全局单点。** `.de` 事件说明：注册局的 DS/KSK 链一坏，**所有下游域名的可用性同时归零**；serve-stale 能缓冲，但前提是你的解析器支持、且 TTL 没被提前清掉。

**测量会改变被测对象。** uprobe 上下文切换、采样与聚合、sidecar 转发，都会在尾部放大开销；**观测系统必须先证明自己不是 p99 的来源**。

**Agent 的传输行为被忽略。** 连接是否复用、是否 keep-alive、是否每次工具调用新建 TLS、是否串行、是否跨区——这些决定尾部，却很少出现在 Agent 的设计文档里。

## 三、技术竞争力

| 方案/层次 | 观测层次 | 重传可见 | DNS 可见 | TLS 可见 | 测量开销 | 可举证性 |
|---|---|---|---|---|---|---|
| APM（L7） | HTTP/gRPC 时长 | 无 | 无 | 无 | 低 | 中（只有结果） |
| 云厂商网络监控 | L4 流量/重传 | 部分 | 无 | 无 | 低 | 中 |
| eBPF（内核态） | L4/L7 混合 | 强 | 部分 | 部分 | 中（可扰动尾部） | 强 |
| 服务网格（Envoy） | L7＋连接 | 部分 | 无 | 部分 | 中 | 中 |
| tcpdump/抓包 | 全包 | 强 | 强 | 强 | 高（事后） | 强（原始证据） |
| DNS 解析器（1.1.1.1 等） | 解析链 | 无 | 强（serve-stale） | 无 | 低 | 中 |
| QUIC/HTTP3 | 传输多路复用 | 部分（可部分可靠） | 无 | 内建 | 低 | 中 |
| Agent 网关 | 工具调用链 | 弱 | 弱 | 弱 | 低 | 弱 |
| 理想态（本期） | 逐跳：DNS/TCP/TLS/L7 | 强 | 强 | 强 | 低且可校准 | 强（逐跳） |
| 仅日志 | 无 | 无 | 无 | 无 | 低 | 无 |

**判读**：APM、抓包、eBPF、网格都是货架能力；**“这一个慢请求在 DNS、TCP、TLS、L7 各花了多少、重传了几次”没有一家把它做成默认的逐跳字段**。本期反转：第 67 期说“我们的可用性是别人状态页的函数”，本期补一句——**我们的延迟是别人 DNS 与内核重传的函数**。判词：**「APM」「抓包」「eBPF」「服务网格」全部可采购，「举证这一个慢请求在传输层各跳的耗时与重传」不可采购**。

## 四、技术挑战

1. **应用层全绿的假象**：APM 只看应用处理时间，传输等待被算进“客户端慢”。
2. **重传的间歇性**：不是持续高延迟，而是成批尖刺；采样窗口一大就被平均掉。
3. **DNS/TLS 归属不清**：平台团队与业务团队都不认领，故障时互相等。
4. **观测开销扰动尾部**：探针越细，p99 越不可信；需要校准而非默认相信。
5. **Agent 串行放大**：十几跳工具调用，每跳 p99 叠加；连接不复用等于每跳多一次握手。
6. **跨区与弱网**：端侧/移动场景的重传与切换，应用层完全看不见。

## 五、需求分解、用户旅程与实现方案

**需求分解（P0→P3）**
- P0 逐跳耗时：`dns_ms`、`tcp_connect_ms`、`tls_ms`、`ttfb_ms`、`download_ms`，按请求落字段。
- P0 传输指标：`retrans_rate`、`rtt_p99`、`conn_reuse_rate`、`resolve_fail_rate`。
- P1 尾部归因：慢请求自动标注“应用慢/传输慢/DNS 慢/TLS 慢”，进入事件附证。
- P1 连接治理：Agent 工具调用强制连接复用与 keep-alive；跨区调用显式声明。
- P2 DNS 韧性：解析器支持 serve-stale、多解析器、TTL 监控、DNSSEC 链监控。
- P3 观测校准：对 eBPF/网格探针做开销基准，确认其不制造 p99。

**用户旅程（四条）**
1. 用户报“慢”：系统先给逐跳分解，若传输占 90%，直接转网络团队而不是查代码。
2. `.de` 类事件：DNS 解析失败率上升，状态页标注“上游解析异常”，serve-stale 生效。
3. Agent 串行工具：第 7 跳超时，回放显示是 TLS 握手而非工具本身；网关改为连接复用后消失。
4. 观测升级：新探针上线前跑开销基准，p99 变化超过阈值则回滚。

**90 天实现方案**
- 第 1–3 周：接入逐跳耗时与四项传输指标；先量出传输在 p99 中的占比。
- 第 4–6 周：慢请求自动归因；Agent 网关连接复用改造。
- 第 7–9 周：DNS 多解析器与 serve-stale；DNSSEC 链监控。
- 第 10–13 周：观测开销校准；季度演练“注册局 DNSSEC 故障”与“跨区丢包”。

**第 169 个市场空白（五项）**：`net_tail.*` 逐跳耗时覆盖率、`retrans_rate` 重传率可见率、`dns_ms`/`tls_ms` 分项覆盖率、`conn_reuse_rate` 连接复用率、`probe_overhead_p99` 观测开销校准率。`net_tail.*`／`transport.*` 为**第 136 次无人提字段族**；本地 173／173-kb 连续第 125 期成组启用（陶炳哲 30 的“端侧优先、云端兜底、纯云端弱网不可用”重读为：**弱网不是部署环境，是传输层的 SLO**——本地把弱网写成了选型理由，却没把重传率做成指标）。
