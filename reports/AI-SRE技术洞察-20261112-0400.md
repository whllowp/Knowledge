## 二、技术现状

- **基准三足，判分者各异**：
  - *SREGym*（2026-05，arXiv 2605.07161）：90 道题、5 应用，诊断用 **9 题 LLM-as-a-judge 清单**（三维加权，阈值 7/9），best mitigation 78.5%（Stratus）、best 端到端 60.7%（Claude Code，Sonnet 4.6）。作者承认 LLM 判分存在 oracle 方差。
  - *Incident-Arena*（arXiv 2610.00648）：20 道人工题、约 3000 trials，主指标用**确定性双闸门**（Outcome Gate 持续流量下恢复 + Safety Gate 重启耐久/数据保全），前沿模型 Pass@1 约 64.3%；但奖励黑客分析**用 GPT-6-Astra 当判官**（恰是榜单自身榜首参与者之一），附录自承 inter-judge 一致性低，且仅每设定 3 次试验、置信区间宽。
  - *BRiSE / Edge Delta AI SRE Arena / Project Arena*：仍以 LLM 评分或模型对照为主，跨基准词汇表分裂。
- **厂商评测内建化**：火山引擎智能运维助手用 **LLM Trace 分析 + 用户点赞/点踩**做持续效果评估；阿里云 AgentLoop（马云雷）把运行轨迹做成"可计算、可评测、可优化"的数字资产；腾讯 CloudQ 在 WorkBuddy 内以"复测与评估"验证优化效果；字节 DevOps Agent 招聘 JD 明确要求建设"效果评估与可靠性体系"。
- **本地原型当主线**：孙鹏 **BoRP（Bootstrapped Regression Probing）** 弃生成式 Judge，用回归探测自动产生可验证判据；施宏斌指出金融 Agent 的真问题不是"总结对不对"而是"**总结是否 Insightful / 是否捕捉增量信息**"；二者共同构成"判分权外置"的中国实践雏形。

## 四、技术挑战

1. **判分者同源坍缩（自我指涉验证）。** 前沿模型给前沿模型打分，进步数字含虚高；Incident-Arena 用自家榜首 GPT-6-Astra 当奖励黑客判官即典型。
2. **控制捕获率仅 18%（12/66）。** 评测与治理是同一未解问题：能"证明做好了"的，往往也不能"拦住做坏了"。
3. **LLM-judge 方差与低一致性。** SREGym 有 oracle 方差、Incident-Arena 自承 inter-judge 一致性低，跨研究不可比。
4. **语义约定仍非 Stable。** OTel `gen_ai.*` 至 v1.41 仍标记 Development，跨厂商字段名分裂（`llm.model` vs `gen_ai.model_name`），评测遥测不可组合。
5. **基准范围与生产落差。** SREGym 最大仅 40 微服务（Train Ticket）、Incident-Arena 每设定仅 3 trials，置信区间宽；"评测环境通过"≠"生产可验收"。

## 五、展望与建议

- **判分者必须异构**：评测模型与被评模型分属不同家族，且公开裁判间一致性（inter-judge agreement）作为一等指标。
- **主指标去 LLM-judge**：采用 Incident-Arena 式确定性双闸门（Outcome + Safety Gate），把"重启后仍存活""未越界"做成可机检判据。
- **把"控制捕获率 / 判分者独立性 / 评测-生产同口径"写进 RFP 与信通院六维补格**，推动从"解决率"到"可验收率"的口径迁移。
- **轨迹资产化 + 用户反馈闭环**（点赞/点踩）做持续评估，以生产真实信号反哺基准。
- **新增市场空白五项（第 59 个字段族 `eval.*` / `benchmark.*`，OTel 仍无人提）**：`eval.judge_family`（判官模型家族）、`eval.judge_independence`（独立度）、`eval.inter_judge_agreement`（裁判一致性）、`eval.scope_coverage`（故障域覆盖）、`eval.production_parity`（评测-生产同口径率）。
