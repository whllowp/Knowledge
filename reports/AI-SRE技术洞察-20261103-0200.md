# AI-SRE 技术洞察 · 第 40 期

**主题：并发面运维——智能体的爆炸半径由"同时能碰多少"决定**

统计窗口：2026-10-04 — 2026-11-03｜生成时间：2026-11-03 02:50｜本期主线：第三十一条（并发面/同刻面）

一个智能体慢慢做错事，你能在 trace 里看见。十个智能体同时做对事，每条 trace 都干净，账上是错的。前 39 期把智能体拆成三十个平面逐一审视，都默认了一个前提：动作按顺序发生。本期把这个前提拿掉。

## 一、发展趋势

三条线在十月底同时到位。

基础设施线：Google 10-29 的 GKE 网络数据平面博文把"高密度并发 agent"写成基础设施命题——顶级研究机构提出百万级并发代码沙箱诉求，Agent Sandbox 达到每秒 300 个沙箱启动、亚秒级就绪，Agent Substrate 在 20 万 agent 基准上做到 500 次激活/秒、暂停恢复 500 毫秒内。同文暴露了一个此前没人当运维问题看的瓶颈：集群网络身份上限 65,536 个，而 agent 工作负载习惯为每个 pod 生成唯一标签（agent-id、时间戳、claim-uid），身份分配是串行的，直接卡住 pod 创建。

理论线：10-02 的 arXiv 2610.03140《Tracking State Footprints》把多智能体协调直接定义为数据管理问题——当前编排器"排任务序，但不排状态序"，于是简单编码任务也出现并发异常。更早的六月立场论文说得更直白：多智能体失败"本质上是并发控制问题"，因为"推理跨秒到分钟，工具执行是毫秒"，它把这叫时间不对称，并断言现有工作流"默认良性交错"。

产品线：Anthropic 与 OpenAI 都把并行工具调用设为默认（分别用 `disable_parallel_tool_use`、`parallel_tool_calls` 收窄），但两家文档都明说"不规定执行顺序"；Cisco 在 AgenticOps 叙事里给出最朴素的判据——"AI 不仅执行更快，更能瞬间完成海量决策，一旦偏差，影响范围也以同样速度扩大"；国内一侧，嘉为鲸智 V2.3 把两阶段执行确认做成标准动作，百度 AgentOps 则直接把"并发层面"与用户、模型、系统并列为写操作失控的四类高危之一。

判断：并发正从性能参数变成正确性参数；讨论重心从"能不能并行"转向"并行时谁定序、谁负责"。

## 二、技术现状

**为什么老办法一起失效。** 数据库三十年前就解决了并发写，原理没变，变的是时间尺度。一次事务的读写在同一段代码里，微秒级；一次智能体的读—思考—写跨越模型推理、工具调用、上下文重装，秒到分钟。读写窗口被拉长三到四个数量级，两个经典策略的假设同时破产：悲观锁要在这段时间里一直持有，代价不可接受；乐观控制要在这段时间里假设不被撞，一旦被撞就要重算，而"重算"在智能体里等于重跑一次推理加已经发生的副作用。六机制横向对比（锁、版本校验、条件写、串行化事务、单写者队列、租约）结论一致：都建立在"读写间隔短"这个前提上。

**现在能用的三件半。** 其一，按资源键的 FIFO 串行化：同键写排队、读排在写后、跨键仍并行。它不提供正确性，只让冲突变少、让模型的顺序得以保留。其二，条件写（If-Match / revision / CAS），这才是正确性边界：冲突以 409 出现在 transcript 里，模型重读、重决策——"loud beats lost"，响一声胜过悄悄覆盖。其三，两阶段人工闸门：把变更拆成 reserve（校验、锁版本、置 pending）与 confirm（审批后落库），使排他域只被持有毫秒而不是一个午休。剩下半件是租约加 fencing token，产品里几乎见不到。

**被忽略的对象：状态足迹。** 上述论文的价值在对象而非结论：把任务描述成"足迹"：在三个作用域里读了什么、写了什么，即智能体自己的上下文与本地文件、编排器的计划与任务状态、外部系统（代码库、数据库、Web 服务）。三者的可见性、可回滚性、可复现性完全不同，而现在的编排器一个都不记。没有足迹就没有"这次读到的版本"，也就没有条件写的前提。

**并发压爆的不是 CPU。** 65,536 值得记住：并发度先撞上的是命名空间类资源——网络身份、连接池、配额、锁表槽位，而不是算力。这类资源是耗尽型而非饱和型，曲线撞墙前完全平坦，撞上即断崖，没有慢速劣化可看。监控历来擅长饱和型（CPU 85% 报警），对耗尽型几乎盲视。把高基数标签从 labels 挪到 annotations 是正解，但"为性能合并身份"会牺牲隔离，这笔交换必须显式签字。

**观测上最硬的一处缺口。** 并发故障的证据形态是"两个成功加一个错值"：每条 trace 自洽、时间戳齐全、错误率为零，错的是两条 trace 之间的关系。现有 trace 是线性时间轴，没有 happens-before；两个 span 谁先谁后只能靠墙钟猜，而墙钟跨进程不可比。这类事故在现场几乎不可证，往往等到对账才暴露——一位工程师记录的上线两天后事故即是：2.6% 工单的仓库标记不一致，智能体成了替罪羊，根因是同一订单命中两条并行流，后端部分落库、智能体重读后"纠正"，写出第二个冲突更新。

## 三、技术竞争力

| 方案 | 并发控制机制 | 冲突如何暴露 | 审批与排他域的关系 | 边界与空白 |
|---|---|---|---|---|
| Google（GKE Agent Sandbox / Substrate） | 隔离域代替互斥，一 agent 一沙箱；身份空间治理 | 无应用层冲突语义，靠隔离与租约 | 不涉及 | 强在密度与身份，弱在"同一外部资源的两个写" |
| Anthropic（Claude API / Managed Agents） | 并行工具默认开启，开关只收单轮；执行序由调用方定 | 无内建冲突返回，靠工具自身 | 审批在 harness，与排他域无关 | 文档明确不规定执行序 |
| OpenAI（Responses / Agents SDK） | `parallel_tool_calls` 总开关；session 单一所有者 | 依赖下游 409 / If-Match | `needs_approval` 挂在工具层 | 无资源键级互斥 |
| Microsoft（Foundry durable state） | If-Match 条件写（预览） | 版本冲突显式返回 | 不涉及 | 存储侧正确，工具侧仍需自建 |
| Grafana（Managed Sandboxes） | 以分支加 PR 合并解决冲突 | 合并冲突显式 | 人审 PR | 只适用可合并的代码类变更 |
| 腾讯云（CloudQ / AgentObs） | 按动作影响范围与可回退性分级；会话·轮次·步骤可观测 | 靠影响面分级而非冲突检测 | 关键节点人工确认 | 无资源键排他域 |
| 火山引擎（方舟 Managed Agents） | 同一 Agent 多并行 Session，事件只增不删可回放 | 事后回放定位 | 不涉及 | 事件流利于定序，无并发控制语义 |
| 嘉为蓝鲸（鲸智 V2.3 / BK-CLI） | 两阶段执行确认：预览计划再确认 | 计划预览即冲突暴露点 | 审批先于执行，天然两阶段 | 无跨 agent 排他域 |
| 学术（footprint / CC 立场论文 / HakiCC） | 足迹记录、语义冲突解决、事务化外部接口 | 冲突作为一等对象 | 提出但未产品化 | 无生产实现与公开基准 |

三点判读。第一，三条路互不替代：海外把并发做成基础设施属性（隔离、身份、密度），国内把并发做成流程属性（两阶段确认、影响面分级），学术把它做成数据管理问题（足迹、事务接口）。

第二，执行序成了 harness 的私有权。两家 API 都把开关交给调用方，又都声明不规定顺序，等于把"谁先谁后"这个决定正确性的变量，放进了一段没有声明、没有测试、没有审计的框架代码里。

第三，审批与互斥被错误地耦合。审批挂在工具调用内部，等于在这段时间里持有排他域——等待一次人工批复可能是半天。真正需要的是 reserve/confirm 两阶段：审批期间只持有预留态，不持有锁。目前只有嘉为 BK-CLI 与学术方案在形式上做对，云厂商大平台都没做。

## 四、技术挑战

**归责。** 两个智能体各自逻辑正确、组合错误——第 29 期叫仲裁真空，这里是它的并发版本。顺序即策略：谁定序，谁承担结果。但顺序恰恰是唯一没人记录的东西，出了事只能归因于"当时调度器怎么排的"。

**重算的价格。** 乐观控制的赌注是 transform 的成本，而智能体的 transform 是一次完整推理加已发生的副作用。带外部副作用的步骤不可重放，只能在"升级为串行化点"与"改写为 saga"之间选；这意味着冲突重试在写入面根本不免费，它可能要你再付一次账单和一次不可撤销的变更。

**语义合并的自证。** 智能体相对数据库的新能力是"不 abort，读懂冲突再合并"。但机械合并成功不等于结果合理，模型自证"这次合并说得通"正是第 35 期讲过的判据自证。耦合字段必须显式声明，合并规则必须确定性，模型只能提议不能裁定。

**并发吃掉可复现性。** 第 39 期把断网重放通过率当作复现充分性 SLI，那个定义默认单线程。并发下即使断网、即使响应全部录制，交错不同结果就不同——回放通过率在并发系统里没有定义，除非把交错序一并录下。这是本期对上一期最直接的修正。

## 五、展望与建议

1. **写工具补第三证。** 第 38 期提的"幂等键加 If-Match"双证只解决重复与丢失更新，还需第三证：排他域声明（资源键集合加冲突策略）。空声明视为不可上线，声明过宽视为串行化税，二者都要在评审里被问。
2. **把审批从锁里挪出来。** 统一采用 reserve/confirm 两阶段，预留态带 TTL 与 fencing token，超时自动释放并告警。这一条几乎零架构成本，收益是把人工等待从关键路径摘掉。
3. **冲突率进仪表盘，但要按三段读。** 低于 0.5% 疑似假并行或声明过宽；1%—5% 健康；高于 10% 说明分工重叠，该拆队列而非调参。它和多数 SLI 不同，不是单调向好。
4. **并发预算并入配额总账。** 第 33 期管 token 额度，本期管"同时在做几件事"：设全局并发上限与每资源键竞争上限，防止每个 agent 各自克制、全局过载的惊群。
5. **轨迹补因果、回放定交错。** span 增 resource_key 与 causal_predecessor；回放前固定交错序（schedule pin），把"断网重放通过率"升级为"断网加定序重放通过率"。
6. **半径公式进变更评审。** 爆炸半径约等于并发扇出乘以不可逆比例。把并发扇出（同一 run 内并行工具调用数、同键竞争者数）作为可采集量写进变更单。
