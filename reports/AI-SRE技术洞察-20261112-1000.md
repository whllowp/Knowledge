# AI-SRE 技术洞察（第 148 期）

**生成时间**：2026-11-12 10:00（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：运维知识图谱面／推理底座面（Operational Knowledge Graph）——Agent 先翻图、再开口，可这张图是昨天的；它自信地在一个可能过期的世界里做根因与修复决策

---

## 题眼

同一周（10 月底），腾讯 CloudQ 把「全景图谱」推上多云 AIOps 智能体底座、Google 用 Entity Context Graph 托住调查、阿里用 Fabric 统一上下文、字节用 AgentKit 中间层串联——**全行业在给 Agent 织一张「可推理的图」**。腾讯云把这张图说得很漂亮：**从真实云 API 数据长出来、授权即用、无需前置治理，把资源、关系、状态、处置动作织进同一张图，多跳一路走通 CVM→CLB→域名→业务模块，结论和证据链一起给你**。但同一段话里藏着一个没回答的问题：**增量刷新频率是多少？** 一次凌晨扩容、一次没登记就生效的变更、一条正在漂移的依赖，就能让图与现场脱节，而 Agent 不会知道。最能说明问题的是题面自带的对照：**图越被当成「Agent 推理的事实底座」，它越该是「活的」，可行业把它做成「快照」**。这是负事件家族里唯一「指标在报、告警在响、Agent 在推理，但推理所依赖的那张关于『世界长什么样』的图，是昨天的」的成员。

## 一、发展趋势

**趋势一：知识图谱从「辅助展示」升级为「Agent 推理底座」。** 过去图谱是给人看的「一图胜千言」（架构可视化、拓扑大屏）；2026 年它变成 Agent「先翻图、再开口」的认知层。腾讯 CloudQ、Google Entity Context Graph、阿里 STAROps Fabric、字节 AgentKit 都在做同一件事：把分散的资源、依赖、状态、历史经验织成一张可被 Agent 查询的图。

**趋势二：从静态 CMDB 到「活图」。** 行业共识是图要「从真实数据长出来」（CloudQ 授权即用），但大多仍是 T+1 资源快照。**图若要托住秒级故障响应，必须增量订阅变更事件流与实时遥测**，否则图与现场天然有时差。

**趋势三：多跳推理取代大模型凭空脑补。** 腾讯云 Ontology 文章把根因/影响面回溯写成「图上的路径问题」——顺着边走几步，吐出来的影响面可验证，比让 LLM 自由发挥稳得多。这是图谱相对于纯 RAG 的核心价值。

**趋势四：图谱成为可审计证据链载体。** 每个结论回溯到具体节点/边，既让人在授权前看清依据，也让链路可审计——在运维场景，「可追溯」比「准」更先被买单。

## 二、技术现状：四类图谱，通常只有前两类

**资源拓扑图（给人看）**：CloudQ 全景图谱、阿里 Fabric、传统可观测厂商的 entity graph，解决「资源之间谁依赖谁」的可视化，但多为快照。

**实体上下文图（给 Agent 查）**：Google Triage & Investigation Agent 的 Entity Context Graph，配合 Observed/Approved/Derived 三层事实与 append-only 审计，把「这个实体此刻是什么状态、谁确认的」做成结构化事实——是目前最像「可信底座」的形态。

**运维本体＋语义层（让图会推理）**：yunpan.plus 的 Running World 工程把数据层拆成 infra（低频变更）/可观测（秒级失效）/knowledge（非结构化高密度）三块，认知层用 ontology 定义实体与约束、语义层做实体对齐与关系抽取，再构建带图查询与逻辑推理的全景图谱——这是把「图」和「推理」接起来的完整方法论。

**知识库 RAG（历史经验）**：CIOAge 五层架构的推理层把企业专属运维知识库、历史故障案例、业务约束规则喂给 LLM 做多跳因果推理；但知识库本身会过期（与第 134 期文档时效同源）。

**普遍缺口**：图是快照而非流；边无置信度与来源（Agent 无法判断这条依赖是否可信，呼应第 54 期 provenance）；跨云多源实体对齐两难（第 122 期实体归一两套记录）；图谱新鲜度不可观测；Agent 推理不强制引用具体节点/边。

## 四、技术挑战

**一，图是快照，遥测是流。** T+1 资源图 vs 秒级故障；凌晨扩容、未登记变更让图与现场脱节，Agent 无从察觉。

**二，图谱新鲜度不可观测。** 没有「这张图几秒前更新」的指标，也就没有「图是否已过期」的告警——最该稳的底座最盲。

**三，边无置信度与来源。** 一条依赖关系可能是推断的、过期的、或未经验证的；Agent 无法区分「铁证依赖」与「猜的边」，呼应第 54 期 provenance 缺口。

**四，推理-图谱一致率缺失。** Agent 结论不强制引用具体节点/边 ID，无法复核「它踩在哪条边上得出这个结论」，与第 135 期运行真相「结论挂证据」同源。

**五，跨云多源对齐难。** CloudQ 说打通多云，但语义层割裂、实体归一两套记录（第 122 期），图的跨源一致性靠人肉。

**六，知识库 RAG 幻觉。** 历史故障/runbook 过期（第 134 期），Agent 在多跳推理里引用一条已失效的经验却不自知。

**七，图谱被误用不自知。** 图不全时 Agent 仍自信推理（与第 111 期地基面、第 135 期运行真相同构）：底座缺一块，推理链却照跑。

**八，评测盲区。** ITBench-AA、Cloud-OpsBench 等基准测 RCA 能力，但**不测图谱新鲜度、不测推理-图谱一致率**——能力在实验室里被量，底座在生产里裸奔。

## 五、展望与建议

### 5.1 需求（字段族）
- **R1 `graph.*` 七字段**：`graph_id`、`freshness_slo`、`last_refresh_ts`、`edge_confidence`、`edge_source`、`agent_queryable`、`staleness_flag`。
- **R2 活图架构**：图增量订阅变更事件流＋实时遥测，不做 T+1 快照。
- **R3 置信度+来源边**：每条边带 `source/confidence/verified`（深化第 54 期 provenance）。
- **R4 推理-图谱引用**：Agent 结论须引用具体节点/边 ID（深化第 135 期结论挂证据）。
- **R5 跨源对齐**：复用第 122 期实体归一双轨。
- **R6 评测扩展**：把图谱新鲜度/推理-图谱一致率做成基准项（ITBench-AA、Cloud-OpsBench 扩展）。

### 5.2 实现路线（90 天）
- **0–30 天：盘点。** 给存量图谱补 `last_refresh_ts` 与边 `source`；发布图谱新鲜度 SLO。
- **30–60 天：活图。** 图订阅变更事件流；Agent 结论强制引用节点/边 ID；未引用标 `UNGROUNDED`。
- **60–90 天：校验。** 边置信度打分＋跨源实体对齐；信通院六维补「图谱可验证率」「推理-图谱一致率」两格。

**第 99 个市场空白（五项）**：图谱新鲜度 SLO 达标率、边置信度可声明率、推理-图谱引用率、跨源实体对齐率、图谱-现场一致率——无一内建；`graph.*`／`kb.*` 为**第 66 次无人提字段族**。本地 173／173-kb 连续第 59 期成组启用：周昕毅 10「AI+SRE≠AISRE：AI 如何真正进入生产运维闭环」＝全库唯一把「知识沉淀＋持续闭环（L3 数字分身：长期身份、持续闭环、责任边界）」写进生产运维实践，本期首次当主线；配马云雷 31「让轨迹成为数字资产」（轨迹＝持续更新的知识底座）、刘凯宁 05「蚂蚁 SRE 基于 Agent 的应急根因定位」（RCA 依赖知识库与确定性笼子）。判词：**本地把知识沉淀和闭环写进生产运维（周昕毅 L3 持续闭环、马云雷 轨迹资产），联网侧 2026 年才由 CloudQ/Fabric/Entity Graph 把它做成「图」；两边都没把「这张图几秒前更新、每条边可不可信、Agent 结论引了哪条边」做成可导出字段。**
