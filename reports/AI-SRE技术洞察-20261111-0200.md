# AI-SRE 技术洞察（第 115 期）

**生成时间**：2026-11-11 02:00（北京时间）｜**窗口**：2026 年，重点最近 30 天（11-01～11-10）
**本期主题**：返回面／回执面（Return Semantics / Effect Receipt）——exit code 0 只证明进程结束了，不证明动作发生了；而决定它真假的那一行接线，同时改写了模型排行榜

---

## 题眼

11-01，arXiv 2611.01930《RECEIPT》第一次把行业默认的前提做成可测量量：Agent 从命令行操作 Web 基础设施，依赖「返回假设」——每次工具调用会及时返回，且请求的动作已完成。作者采集 91,469 次生产工具调用、89,047 条公开轨迹，测 8 个主流 harness，建立 158 条「先提问再动作」的命令目录 Litmus 与 25 对仅在确认问题上不同的任务 Tripwire。结果：关闭输入时 11.5%（18/156）的调用返回 status 0 却什么都没做，8 个 harness 里 7 个在无终端时默认关闭 stdin；保持输入开放则空等超时，token ×2.9；**只改这一行输入连接、不动模型，Llama-3.3-70B 在 8 个 LLM 的榜单上从第 7 升到第 3，两种条件下排名相关 Kendall τb 仅 0.47**。同期 11-02 另一篇论文发现评测渲染器漏掉全部结构化工具调用，60 个判定步骤中 53 个空白，哈希却匹配、检查器全过。

前 114 期追问动作、链条、制度、账本对不对；本期只问最底下一层：**我们采信的「完成」是谁签发的、由什么物理条件决定、能否写进采购合同**。

## 一、发展趋势

**趋势一：失败落点从「结果」退到「返回通道」。** 往期负事件里，证据或丢、或被改、或没打分；本期这一员唯一由观测通道主动签发——系统返回真实、合法的状态码，只是它回答的是另一个问题。`docker system prune` 什么都没删、`rm -i` 把文件全留着、`find -ok` 跳过每一条，退出码一律 0；另有 12 条调用**未经确认直接动作**。同月两份开源 silent-failures 复盘给出更长静默期：上游数据源断了七周，退出码一直是零；「退出码零、HTTP 200、状态就绪全报成功实则没干活」被归为四类，论断是**成功是一种效果，不是返回值**。

**趋势二：护栏不是被拆掉的，是被输入连接绕过的。** 与 110 期「护栏存量侵蚀」并读：`rm -i`、`cp -i`、`tar -w`、`git rebase -i` 都是不可逆动作前最后一道确认闸。Claude Code 为让命令顺利返回设 `GIT_EDITOR=true`，交互式 rebase 于是以 status 0 压缩提交、跳过确认——护栏一条没少，却集体失效，且不产生任何告警。靠静态清单兜底不成立，只能运行时从系统调用读。

**趋势三：治理开始盯「信号通道」而非「动作」。** 11-10 OpenAI「控制室」把能否继续输出做成一等对象（唯一任务 ID 附在推理请求上、停机后拒绝下一次推理，最长 35 秒）；11-09 KubeCon NA 上 Red Hat OpenShift 5 的受监督工作流 GA、自主排障仍留预览且两种模式都保留人工批准，ControlTheory Dstl8 2.0 直言「若什么都没告警，AI SRE 就永远不看」。三者都在补「信号有没有到」，没一件补「动作做没做」。

## 二、技术现状：三本账，返回这一本没人记

**学术侧把修复落在测量仪器上，且给出了可复现代价。** RECEIPT 不换模型、不改 Agent、不改被调程序：保持输入开放但不代答，每 0.1 秒从内核读系统调用与等待描述符，连续 1 秒无输出才确认等待，用模型检查校验输入、打断、报告的顺序性质（撤规则即违反 5/7），最后把进程等待态写成 receipt 交回未修改的 Agent。5 个 LLM 上假成功 34→9（−73.5%）、成功 153→176、比开终端少用 24.4% token；等待报告率 85.0%、误报 0，而 1 秒看门狗误杀 82/119 个对照；第二个 harness 上 25 个守门任务全过，中位检查开销 0.11／0.54 ms。

**评测链自己犯同一个错，且所有完整性校验都通过。** 11-02 arXiv 2611.02676 审计一条 30 轨迹流水线：哈希匹配、检查器通过、暂存成功，与四项义务全被违反同时成立；渲染器省略每一个结构化工具调用，53/60 判定步骤空白，两套独立检查器都接受了不对号的 tool result；裁判照常打分，补齐调用后错误标记反差从 13 降到 2。四项义务落在渲染、检查、阻断与字节一致上；三项控制挡住 19 个构造故障中的 18 个。与 98 期「一半 episode 没打分」不同：**分打了，分是空的**。

**标准与厂商侧把漏洞写进了默认值。** OTel GenAI 把 `process.exit.code` 列为条件必需，而记录「动作是什么」的 `gen_ai.tool.call.arguments`／`result` 是 Opt-In、`NO_CONTENT` 默认；约定仍 Development、属性名在漂移，span 还可采样丢弃。厂商 release notes 最诚实：11-03 Claude Code 2.1.317 修复 `claude -p` 磁盘满丢 transcript 却仍 exit 0，改为报错 exit 1，并坦承 NFS 导出可能仍漏检；同版新增 `onFailure: "block"`，此前回调崩溃等于动作照常放行。11-10 OpenAI 又披露 Costs API 成本数据错误——连账单都建立在「返回值可信」之上。

**中国厂商最完整的「验证」语言，全部落在返回之后。** 11-10 阿里云云栖 11 项发布把 UModel、STAROps「执行验证」、Agent-as-a-Judge 复核 90%+、实验回测五步门禁串成闭环；阿里社区 11-04 稿明写「沿 Trace 从根 Span 找第一次偏离的不变量」，并自认状态快照／断言结果是业务扩展而非规范字段。腾讯 11-02/03 CloudQ 关联性能、Token、工具调用与任务质量，信通院六维要求「过程可审计、结果可评价」；火山引擎 EMR AI 助手要求告警规则须显式订阅才诊断、2 小时与 7 天限频、「处置仍要核对」。**订阅机制是最锋利的反例：连「有没有收到信号」都要人工订阅，「信号说成功、动作没发生」却没有任何订阅点。**

**本期反转（修正 86／96／98／105／110／111／112／113／114 判词）**：往期判「最硬证据在学术、厂商三列全空」，本期更不对称：**唯一把返回态做成一等对象的是一篇软件工程预印本；唯一把「退出码不等于动作」写进修复说明的是模型厂商的 CLI release notes；标准组织则把退出码设为条件必需、把动作内容设为默认关闭**。厂商的验证能力（阿里执行验证、腾讯结果可评价、火山处置核对、Red Hat 执行前批准）都很完整，却全站在「动作已发生」之后。六家云厂商「输入连接可导出」「假成功默认可检出」两列全空。判词：**「可观测」「审批」「验收」「护栏」「回测」「急停」全部可采购，「举证这一次 status 0 背后那个动作真的发生了、以及是谁把 stdin 关掉的」不可采购**。

**本地原型（第 36 期）**：刘杨 08「有了日志、指标和完整 Trace，仍判断不了 Agent 是否做对了任务」本期当主线——全库对「过程可观测 ≠ 效果可观测」最直接的一句，其解法把验证加在 Trace 之上，仍没加在返回通道之上；同篇「同一工具调用在不同框架里数据模型完全不同」恰是 8 个 harness 各有接线的本地镜像。配何伟 02「验收需覆盖本次改动＋真实链路＋存量影响」、周昕毅 10「发现→分析→决策→执行→验证→反馈」、陈忻 29「跨引擎一致率 100%（548/548）」——底层返回码若是假的，一致性只会把假成功复制得更可信（105 期 24/24 互证仍分叉）。判词：**本地把「验证」写成闭环里独立一步，联网侧 11 月才把「返回」与「效果」切开；114 期表计面问「谁数的」，本期问「做没做」，两边都没给返回态留字段**。第 69 个市场空白五项（返回态可导出率／输入连接钉版率／确认送达率／假成功检出率／评测输入完整率），`return.*`／`effect.*` 为第 38 次无人提字段族。

## 四、技术挑战

**一是「完成」没有签发者。** span 记了工具名、退出码、耗时，却没有「这次退出码证明的是哪件事」；`process.exit.code` 只回答进程如何结束，Agent 的完成声明只回答模型怎么说。假成功不报错、不告警，反把成功率、MTTR、自动化率同时抬高。

**二是测量仪器混进了被测量对象。** 只改 stdin 接线，8 模型榜单名次重排、τb 仅 0.47；作者要求基准维护者「排名前先钉版并报告输入连接」。往期反复引用的 SWEOps-Bench、RCAtlas、BOBA-Bench、Terminal-Bench 2.0 均未报告接线；公开语料里多路复用器下 6.0% 调用未返回、影响 56.1% 试验，管道下仅 0.7%。**用这些榜单做选型，等于把 harness 的一行 I/O 代码当成模型能力买回来。**

**三是确认闸的送达没有回执。** 106 期说介入落点决定成败，本期更前一格：介入请求可能从未送达。`rm -i` 的 EOF 默认值由 harness 代答，人没否决过也没批准过，轨迹里却只有一次成功调用。「谁答的、答了什么」全无字段；OpenShift 5 的执行前批准只管 Agent 的动作，不管所调命令内部那道确认。

**四是修复不能靠静态清单。** 留出程序族上预测器平均精度仅 0.477／0.395、规则集对目录外 178 次等待零命中；Claude Code 对 here-document 开管道特例说明同一 harness 内部接线还会分叉，静态表会随版本、别名、`CI=1` 失效。

**五是评测链与账单链同源污染。** 判分器读空白字节仍出分、检查器接受不对号的 tool result、成本导出出错——执行、评测、计量三层共享「返回值可信」假设，一层破则三层失真。

## 五、展望与建议

**字段先行。** 向 OTel GenAI 提 `receipt.*` 九字段：receipt_id／tool_call_id／input_connection[closed｜pipe｜pty｜multiplexer]／harness_id＋version／exit_code／wait_state[pending｜answered｜interrupted]／prompt_digest／effect_state[VERIFIED｜UNVERIFIED｜SKIPPED｜UNASKED]／verifier_kind。默认 `EFFECT_UNVERIFIED`，`process.exit.code` 降级为观测字段；`gen_ai.tool.call.result` 在运维通道内改为必采（脱敏后），命令执行与效果拆成两个 span。

**门禁与独立见证。** 每个改变系统的动作配一个 Agent 看不见的终态验证器（文件存在、写入行数、记录数），数字证据替代绿色输出；status 0 且 effect_state≠VERIFIED 不得进结案分母、不计入自动化率、不触发下一步自主执行。交互命令一律显式非交互标志（`-y`／`CI=1`）并把选择写进 receipt，禁止 harness 静默代答；确认提示带 prompt_digest 与应答人身份，未送达即 `INTERVENTION_UNDELIVERED`。

**评测与供应链。** 基准发布须钉版并公开 input connection、超时档位与 harness 版本，报同一模型在 closed／terminal 下的名次位移与 τb；判分器落实 2611.02676 四项义务，把「渲染后字节等于最后被检查字节」做成硬断言。Skill／MCP／CLI 版本包入 SBOM，升级时重跑 Litmus 式目录；采购合同把「返回态可导出率」「假成功检出率」写进验收，信通院六维补「效果回执覆盖率」「输入连接钉版率」两格。

**演练。** 六类混沌注入：关闭 stdin 的假成功、未送达的确认闸、渲染漏工具调用、哈希匹配但内容空白、上游长断流仍 exit 0、换 harness 后名次重排。每类须产出带 effect_state 的 receipt，否则不可验收。

**边界。** 最硬数字出自一篇预印本与厂商 release notes：前者自陈外部效度限于所测 harness／LLM、基准与检测器同期编写可能偏向自家修复（作者已冻结检测器后写最后 10 对任务），后者自认 NFS 仍可能漏检；11.5% 是 Litmus 构造调用上的比例，不是生产故障率。
