# AI-SRE 技术洞察（第 325 期）

- 生成时间：2026-11-24 10:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：门禁面／发布门禁到底验证了什么——绿色是一个状态，不是一份证据

## 题眼

2026-10-26 披露的 CVE-2026-66874 给“门禁绿”下了一个很锋利的注脚：Gitea 在 pull request 事件里从 PR 头部读取工作流定义；当工作流的分支/路径过滤把执行排除时，它**伪造一个 skipped 状态**发回去。而 skipped 状态在分支保护里**被算作成功**。于是 fork 作者可以提交一个“匹配必需检查上下文、但故意不运行”的工作流，让组织必需的检查看起来已满足，而工作流一行都没执行。

这不是某个平台的孤例，而是门禁的通用问题：**绿色只说明“某个状态被写成了 success”，不说明“验证真的发生过”。**

2026-10-17 的一篇权限分析指出，GitHub 分支保护默认**对管理员与拥有 bypass 权限的自定义角色豁免**；只有勾选“禁止绕过”后规则才约束所有人。2026-07-05 的一份分支保护审计快照则展示了更常见的现实：`enforce_admins = false`，owner 可以绕过全部规则；必需检查名单也是“过期”的——新加的 `secret-scan`、`workflow-sast` 还没被列进 required checks。

再看测试本身。2026-06-05 的一个流水线场景记录：一个必需检查在“无代码变更”的 PR 上约 30% 概率失败，重跑就绿；开发者学会了反复点“Re-run failed jobs”直到通过。后果有两层：**两个真正坏掉的测试被噪声掩盖**；以及所有人开始把红色必需检查当成无意义。团队的本能是“加自动重试”，但那会把噪声和真故障一起藏起来。

2026-09-14 的一个 PR 则给出了正确动作：nextest 的重试把“重试后通过”报告成普通通过，真实间歇性 bug 藏在后面；修复是**把重试计数显式化**——重试通过打印 `FLAKY n/m`，CI 在步骤摘要里展示计数。

## 一、发展趋势

**第一，门禁从“布尔值”转向“证据包”。** 不只问“绿不绿”，而问“这次 SHA 上、实际执行了哪些检查、跳过了什么、重试了几次、缓存命中没有”。

**第二，skipped 语义被重新审视。** 跳过不等于通过；条件不满足、路径过滤、手动取消都不应写成 success。

**第三，重试开始被计数而非隐藏。** flaky 通过要显式标记，趋势要可见；否则“绿”是重试堆出来的。

**第四，选择性测试的盲区被承认。** 测试影响分析（TIA）能省时间，但动态派发、数据依赖、新测试都可能漏；需要定期全量跑作为校准。

**第五，门禁配置自身需要审计。** bypass 名单、required checks 名单、enforce_admins、缓存信任边界，都是“谁能把红变绿”的入口。

## 二、技术现状

**跳过。** 路径过滤、分支过滤、条件表达式、手动取消，都可能产生 skipped；部分平台把它算成功。

**重试。** 自动重试、手动重跑、`--retries`，让间歇失败消失；不计数就等于没有。

**选择性执行。** TIA、`--changedSince`、只跑受影响包，都可能漏掉跨模块影响；动态语言尤其难。

**缓存。** CI 缓存跨分支共享，命中即跳过构建/安装；被污染或被误用时，“测试通过”可能跑在旧产物上。

**绕过。** 管理员豁免、紧急合并、bypass 列表、规则集未覆盖的分支。

**过期。** required checks 名单与工作流不同步；新增检查没被要求，旧检查已删除却仍在名单。

## 三、技术竞争力

| 方案 | 防跳过 | 防重试掩盖 | 防选择性漏测 | 可审计 | 主要风险 |
|---|---|---|---|---|---|
| Required status checks | 低（skipped 算成功） | 低 | 低 | 中 | 名单过期 |
| Merge queue | 中 | 低 | 低 | 中 | 队列配置 |
| 分支保护 + enforce_admins | 中 | 低 | 低 | 中 | bypass 名单 |
| 重试计数（FLAKY n/m） | 中 | 高 | 低 | 高 | 需改造报告 |
| TIA + 定期全量 | 中 | 低 | 中 | 中 | 动态派发盲区 |
| 缓存隔离/只读 token | 中 | 低 | 低 | 中 | 配置复杂 |
| 门禁证据包 | 高 | 高 | 高 | 高 | 实现成本 |

判读：买得到分支保护、merge queue、TIA、重试、缓存；买不到“这次到底跑了什么、跳过了什么、重试了几次、缓存是否命中、谁批准绕过”。

本期反转：我们一直把门禁绿当“验证通过”。实际上绿色是一个**状态写入**，不是一份**执行证据**；跳过、重试、选择性执行、缓存命中、管理员绕过、名单过期，六种路径都能让它变绿，而验证没有发生。

判词：「required checks／merge queue／分支保护／TIA／重试／缓存」全部可采购，「这次门禁实际执行了哪些检查、跳过与重试各多少、缓存是否命中、谁批准绕过、名单是否覆盖当前工作流」不可采购。

## 四、技术挑战

**其一，skipped 的语义。** 平台把它当成功，团队也习惯性接受；改语义会影响大量流水线。

**其二，重试与 flaky 的边界。** 重试能救网络抖动，也会掩盖真 bug；没有计数就无法区分。

**其三，选择性测试的不可判定性。** 动态派发在一般情况下不可精确判定；只能靠保守规则与定期全量。

**其四，缓存信任边界。** 缓存跨分支共享；写权限、键设计、只读 token 都要配。

**其五，绕过的人性。** 紧急合并、管理员豁免是真实需求；没有审计就无法追责。

**其六，名单同步。** 工作流增删与 required checks 名单不同步，是长期漂移。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要门禁证据包、重试计数、缓存命中审计。
- 安全：需要 bypass 审计、skipped 语义、缓存信任边界。
- 开发者：需要明确的红/绿语义，不被 flaky 噪声训练成“无视红灯”。
- 发布负责人：需要“这次验证了什么”的可读摘要。
- 复盘者：需要区分“没跑”“跑了没过”“重试后过”“绕过”。

**用户旅程（一次“门禁绿但没验证”）。**

1. PR 修改路径命中过滤条件，工作流被跳过，状态写成 success。
2. 分支保护看到 success，允许合并。
3. 另一个 PR 的必需检查 30% 概率失败，开发者重跑直到绿；两个真 bug 被噪声掩盖。
4. 审计发现 required checks 名单还是旧的，新检查没被要求。
5. 紧急发布时 owner 绕过分支保护，没有记录。
6. 复盘无法回答“这次到底验证了什么”。

**实现方案（90 天）。**

- 第 1–2 周：门禁语义——skipped 不计 success；路径过滤必须显式声明；手动取消单独状态。
- 第 3–4 周：重试治理——所有重试点清点；重试通过标记 FLAKY n/m；趋势看板。
- 第 5–6 周：证据包——每次门禁产出：SHA、检查清单、执行/跳过/重试计数、缓存命中、执行者、耗时。
- 第 7–8 周：选择性测试——TIA 规则保守化（动态派发放大到文件级）；每周全量跑校准。
- 第 9–10 周：绕过审计——bypass 名单最小化；每次绕过记录理由、批准人、事后复核。
- 第 11–12 周：名单同步——required checks 从工作流自动派生；漂移告警。
- 第 13 周：演练——注入跳过、重试、缓存污染、绕过，验证证据包能识别。

**验收标准。** 任一次合并，能回答：执行了哪些检查、跳过/重试多少、缓存是否命中、谁批准绕过、名单是否最新。

**第 237 个市场空白（五项）**：门禁证据包；skipped 语义修正；重试计数；TIA 校准；绕过审计。

**`gate_evidence.*`／`verification_receipt.*` 第 204 次无人提字段族**：`gate_evidence.executed_checks`、`gate_evidence.skipped_checks`、`gate_evidence.retry_counts`、`gate_evidence.cache_hits`、`verification_receipt.bypass_approver` 在 CI、SCM 与发布平台之间没有统一语义；门禁只报“通过/失败”。

**本地 173／173-kb 连续第 192 期成组启用**（李东东 16）：本地知识库把“状态”与“证据”分开记账；本期把门禁落成证据包与重试计数。
