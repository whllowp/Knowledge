## 一、发展趋势：智能体成为第二个"执剑人"，期望态机器迎来对家

运维行业花十年建立了"期望态机器"——GitOps reconciler、配置中心、IaC 策略引擎，核心承诺是：任何偏离声明的状态都会被拉回。2026 年 10-11 月的动态显示，一台对家机器上线了：智能体以与 reconciler 完全相同的频率、更大的动作面，持续向同一批被管对象施加变更。

三个信号落在最近五周内。其一，AWS DevOps Agent 的 GitOps 集成架构（dev.to/aws-builders，Eyes, Not Hands）把这条红线写成了教条："推理与执行解耦"——智能体经 Bedrock AgentCore 上的只读 MCP 读集群，唯一写路径是 Kiro CLI 无头提交的 GitOps PR，人合并后由 Argo CD reconcile；其动因场景极典型：一次坏配置合并后 Pod 崩溃循环，值班员花 40 分钟才得出结论"回滚那个 commit"。其二，嘉为蓝鲸 2026 秋季发布的鲸舟 V6.3 把"对比发布前、期望与实际配置"做成了 AI 报告分析智能体的出厂能力，AI 预检智能体则核对介质、参数与变量渲染——期望态与实际态的三态比对从人看 diff 变成智能体读三态。其三，携程周昕毅披露的生产数据（173 库）：累计任务 5,638 个中配置自愈 3,452 个，占 61%——配置修复已是智能体运维最高频的产出，而非长尾场景。

趋势判断：配置正在从"变更的载体"升格为**人与智能体之间的权限合约**。谁有权定义期望态、谁有权豁免期望态，将成为 2027 年运维权限体系的主战场；而"期望态覆盖率"（多少配置资源真正进了声明式管理）将取代 CMDB 完整率成为新的治理北极星。

## 二、技术现状：三套机制并存，但盲区恰好开在智能体最爱动手的地方

现存期望态机制有三套。GitOps 侧：Argo CD 以 selfHeal/prune 周期比对（默认约 3 分钟），官方文档明确其用途是"自动回滚手工改动"；配置中心侧：Nacos/Apollo 提供灰度发布、快照留存与审计（蓝鲸本期把两者统一编排，支持差异核对与回滚冲突检查）；策略侧：Sentinel/OPA 类 policy-as-code 在 plan 阶段拦截。智能体的接入形态也分三种：eyes-not-hands 只读加 PR（AWS 架构）、平台代执行（蓝鲸标准操作数字人：自然语言解析意图、匹配执行计划、过审批策略与高危命令拦截）、以及最危险的**旁路直改**——智能体直接改 ConfigMap、环境变量乃至 MCP 配置。第 49 期已记录反例：Forever Security 11-02 披露恶意 AGENTS.md 可令 Codex 篡改全机 MCP 配置——配置投毒即行为改写。

盲区在哪：大量 GitOps 实践为减少误报，把 ConfigMap/Secret 的 data 字段列入 ignoreDifferences（机制出自 Argo CD 官方用法）——**被排除在漂移比对之外的，恰恰是智能体最常改的键**。期望态机器宣称"没有漂移"，实际上是没有可见的漂移。此外，智能体读到的是多层解析后的生效值（默认值→平台→集群→实例），它"看到配置"与"改到源头"往往不在同一层，现状无一家在 diff 报告里标注改动落在第几层。

## 三、技术竞争力：主要方案对比

| 方案 | 智能体写路径 | 期望态来源 | 漂移检测范围 | Agent 动作标注 | 回滚/豁免机制 |
|---|---|---|---|---|---|
| AWS DevOps Agent + Argo CD | 仅 GitOps PR | Git 仓库 | 全量（含 PR diff） | PR 可追溯 | 人审批 merge |
| 嘉为蓝鲸鲸舟 V6.3 | 平台代执行+预检 | 配置中心+发布模板 | 发布前/期望/实际三态 | 发布报告留痕 | 快照回滚+冲突检查 |
| Argo CD 原生（无智能体） | 人类 kubectl/PR | Git | 全量但可 ignoreDifferences | 无 | selfHeal 自动拉回 |
| 携程智能运维（周昕毅） | 平台自愈动作 | 内部配置基线 | 自愈场景内 | 任务台账 | 任务闭环验证 |
| 阿里云 STAROps（6-30 商业化） | 智能体处置建议 | CMDB+全景图谱 | 巡检覆盖面 | UModel 归属 | 人工确认链 |
| 腾讯云 CloudQ | 全景图谱处置动作 | 资源关系图谱 | 巡检策略范围 | 会话级记录 | 受控执行门禁 |
| LaunchDarkly MCP | 智能体直管 flag 工作流 | flag 平台 | flag 值域 | 审计日志 | trigger 工作流回退 |

判读：把写路径收编进 PR 的阵营（AWS 型）安全性最高但吞吐最低，61% 的配置自愈需求塞不进人审队列；平台代执行阵营（蓝鲸/国内云）在审批与三态比对上最完整，但期望态来源仍是平台私有而非 Git；**"Agent 变更 PR 化率"与"漂移检测是否含智能体动作"两列全行业几乎全红**——继 38/39/43/44/45/47/49/50/51/52/53 期后第十二个市场空白，且是首个"机器对机器、零人工见证"的空白。

## 四、技术挑战：拉锯战、权威分裂与漂移归属

**挑战一：两个执剑人的拉锯战。** 阿里云开发者社区的实战文记录了经典现场：运维在流量高峰手工扩容 3→10，selfHeal 三分钟后拉回 3——"我明明是为了扩容，为什么 ArgoCD 又改回去？"期望态机器没有"紧急豁免"语义；反向问题更危险：智能体的"临时修复"没有回写期望态的通道，修复成功了，漂移却被自我合理化地长期留在生产里（对第 30 期圆谎效应的配置层复现）。

**挑战二：权威期望态分裂。** Git、配置中心、平台默认值、供应商随升级改写的默认参数（第 41 期退役传导链的配置余波）四层叠加，"正确的值"取决于问哪一层。智能体按检索到的文档改值，按 Helm 默认值渲染，按运维口头指示生效——三个"正确"可以同时为真。

**挑战三：漂移归属不可分辨。** 人改的漂移与 agent 改的漂移在 etcd 与审计日志里长得一样；没有 is_agentic 标注（Google GEAP 的双重归因思想尚未进入配置层），事后取证只能靠猜。而配置又是智能体的指令载体（AGENTS.md、MCP 配置、skill 权限清单），配置面被改写等于行为面被改写——漂移治理与第 49 期对抗面在此合流。

## 五、展望与建议

1. **给智能体的变更发"配置护照"**：agent 侧所有配置写动作强制携带（agent_id、变更层、期望态来源引用、回滚键）四字段，缺一不发凭据——与第 38 期变更信封五字段对齐。
2. **豁免要有租期**：紧急扩容类临时漂移以 TTL 租约存在，到期自动触发"回写期望态或回滚"二选一流程，杜绝拉锯战双方的静默固化。
3. **盲区清单化**：把 ignoreDifferences 排除项做成显式清单进评审，凡排除项对应的键禁止智能体直改，只走 PR。
4. **配置面 SLO 四指标**：漂移发现时延 p95（目标小于一个同步周期）、期望态覆盖率、agent 变更 PR 化率、临时漂移回写率。采购问一句"你们的 diff 报告能标出改动落在第几层配置吗"，即可筛掉大多数伪期望态方案。
