# SREAgent 领域技术洞察报告（第 304 期）

**调查污染面 —— 你查得越多，越可能找到一个"看起来对"的错答案**
（Investigation Contamination / Search-Induced Spurious Causality / Over-Search）

- 生成时间：2026-11-24 01:00（北京时间）
- 范围：2026 年，重点最近 30 天（10 月下旬—11 月下旬）
- 方法：联网调研 Google、Anthropic、OpenAI、字节跳动、阿里巴巴、腾讯及独立厂商公开资料，叠加本地知识源 `E:/Knowledge/Knowledge/preview/173` 讲义，与 `index.md` 历史 303 期查重后取全新立面

> **题眼**：Causely 11 月横评有一句被低估的判词——"每一次额外的日志查询或探针，都花费 token 和时间，并给 Agent 多一次找到某个'拟合'解释的机会"。同期 Chiron 在 ORCA-bench 上给出反直觉数据：给 Agent 实时关联上下文后，token 从 143 万降到 15.4 万，根因命中率却从 30.9% 升到 46.2%。两者合起来推翻了运维界一条默认假设——**"多查一会儿，结论就更可靠"**。在概率意义上，探针次数就是多重比较次数：查得越多，偶然拟合出一条"逻辑通顺的错因果"的概率越大。本期首次把**调查行为本身**（查多少、按什么顺序查、看到什么才停）立为一等治理对象，与第 294 期证据保真面（单条证据真不真）、第 303 期关联键面（证据是否同一事故）显式划界。

## 一、发展趋势

**1. 从"给出答案"到"关闭问题"，调查成为主战场。** 阿里云 STAROps 让用户设定持续目标，Agent 围绕目标观察、调查、处置并验证；腾讯云 CloudQ 以全景图谱打通多云资源与处置动作。价值不再产生于"回答得快"，而在调查—处置—验证的闭环是否成立。

**2. 上下文层作为独立品类浮现，"查找"被前置为"给线索"。** Causely 通过 MCP 把因果图交给 Agent，在 OTel Astronomy Shop 基准上把"原因类问题正确率"从 75% 拉到 100%，工具调用从 19 降到 4、token 从 30.8 万降到 12.3 万、健康集群误报从 4/12 降到 1/12。Chiron 走另一条路：把关联状态在飞行中算好，交一份"小而相关"的简报，在 SREGym 上对纯规则的 Jev 决策模型同样有效——**少发现反而多答对**。收益来自上下文本身，而非更强模型。

**3. 成本从账单项升格为运行护栏。** Google Cloud 11 月 14 日在 BigQuery/Looker 统一 Agent 可观测时给出令牌配额与字节扫描上限，理由直指"递归 Agent 循环造成的失控推理账单"；火山引擎 AgentKit 把 Token 消耗纳入数据观测，评测拆成效果/性能/成本三维。调查成本不再是事后财务问题，而是运行时约束量。

**4. 反"单一根因"成为主流方法论。** 谷歌 11 月发布的《SRE》第二版借 David Blank-Edelman 的观点质疑"hunting a single root cause"，主张考察 contributing factors；书中把"用 AI 做 SRE"定位为 Agent 收集证据、人决定含义。一个被过度搜索拼出来的"漂亮单一根因"，恰是应被拆解的对象。

**5. 防污染从训练侧延伸到运行侧。** ResolveAI 11 月 18 日发布 SRE-1（27B），训练时每个工具都钉在告警触发时刻（"no peeking"），禁止读到后续 commit 或工单，单次通过率从 6.9% 升到 38.8%；字节 AgentKit 11 月 19 日上线"固定 Skill 版本、新版不自动替换"。前者防未来信息泄漏，后者防底座静默更替——都是把信息源边界显式化。

## 二、技术现状

**主流调查路径仍是"满意即停"，而非"证伪后停"。** 从告警出发向外搜索，直到某个解释"说得通"就收笔。Causely 的支付案例极具代表性：checkout 报错，Agent 找到依赖服务的重启并据此提交 PR，真正原因却是 payment 变更（本身无告警、无基础设施症状）。重启是真的、引用可点开、推理合理，结论却指向错误对象。这里缺的不是模型能力，而是**在搜索开始前就知道故障如何传播的那张图**。

**上下文注入是最有效的单一杠杆，但尚无标准。** Causely 的九项自查把工作分成两半：前半查遥测（error span 是否带 reason、unknown_service、单 span trace 占比、日志 severity 与 body 是否一致），后半追问 Agent 产出（最近十个 PR 有几个改的是告警服务而非致因服务、能否说出"排除了什么"、证据时间是否对齐、修复合入后原告警是否清除）。几乎没有一项进入现有 SRE 平台的字段规范；OTel GenAI 语义约定正在收敛，但"探针日志"仍无对应语义。

**预算与终止机制普遍是硬上限，不是证据充分性判据。** Google Cloud Next '26 演示里，Simulator Agent 因累计超 100 万 context token 崩溃，修复方式是给 Event Compaction 加阈值提前压缩。业界常见做法是设最大迭代数、token 预算与超时——这些防止"跑飞"，却不回答"证据够了没有"。Akmatori 给出另一面：其廉价模型解出最难的故障，却因跳过一条命令漏掉最简单的那个——**省查询与多查询各有各的错法**。

**工具目录膨胀本身成为污染与成本源。** "三十工具悬崖"上，Anthropic 指出 Claude 在 30—50 个工具后选择准确率下降；OpenAI 建议单轮少于 20 个函数；Speakeasy 实验中 107 工具时模型开始幻觉出不存在的工具名。把监控、日志、追踪、工单、发布全接进来，等于把 Agent 放进充满诱饵的菜单。

**本地知识源的印证。** 刘凯宁《蚂蚁 SRE 根因定位实践与踩坑》提供"调查步骤要能被复盘"的约束；孙鹏《探测式评测管线》提示探测本身应被计分；蒋烁淼《AgentOps》提醒"秒查"前提是查的对象正确；刘杨《从 Trace 到实时评估》指出 trace 覆盖率决定猜测从何处开始。本期首次把这四枚碎片收敛到"调查纪律"主线。

## 四、技术挑战

**1. 多重比较在运维调查中没有对应概念。** 统计上检验次数 n 上升，至少一次偶然显著的概率随之上升；Agent 每发一条查询就是一次检验。没有假设计数与惩罚机制，查 100 条日志几乎必然能拼出一条"说得通"的因果链。

**2. 顺序依赖使结论不可复现。** 先看到哪条证据就形成哪个假设，同一事故换探针顺序可能得到不同根因。这与第 39 期"断网重放"不同：重放固定了输入，固定不了 Agent 自己决定的查询序列。

**3. 历史经验是便利也是污染源。** Google 四步法从已关闭工单备注提取"最成功修复步骤"并排序，本质是把过去结论当今天的先验；若备注记的是"改了告警的服务"而非致因服务，污染会被流水线化复制。

**4. 上下文腐烂与工具膨胀叠加。** Anthropic 观察到 Agent token 用量约为对话的 4 倍、多 Agent 约 15 倍；前 10 步守得住约束、后 10 步开始"context rot"，再叠加 30—50 工具后的选择退化，调查越长越容易在错误方向上越自信。

**5. 欠搜索与过搜索两难。** 压预算会漏掉简单故障，放预算会制造伪因果；现有基准只判"根因对不对"，不判"查了多少步、该不该停"，无法给停止规则提供训练信号。

**6. 责任界面不清。** 人保留执行权不等于能独立复核调查过程——若探针日志、排除项、顺序与成本不可导出，审批者看到的仍只是一份被 Agent 预塑好的结论包（呼应第 299 期）。

## 五、展望与建议

**1. 立字段族 + 门禁。** 提出第 225 号字段族 `investigation.contamination.*`：`probe_budget{allowed,consumed,stop_rule}`、`probe_log[]`（每步记 hypothesis/basis/result/changed_conclusion）、`hypothesis_count` 与 `spurious_fit_risk`、`ruled_out[]`、`lead_source∈PREMISE|SEARCH_FOUND`、`order_independence{tested,result}`、`cost_per_solved_task`、`verdict∈VALIDATED|OVERSEARCHED|CONTAMINATED|UNVERIFIED`，缺省 `INVESTIGATION_UNVERIFIED`。未声明停止规则、无排除项、顺序敏感的结论，不得进 write≥act 自治、不得计入干预信用、不得沉淀为语义记忆。

**2. 停止条件改成"证据充分性"。** 放行需同时满足：可被证伪的因果链、至少两个已记录的排除项、客户面信号验证；token/迭代上限只作熔断。

**3. 评测增双轨。** 同题给 with/without 上下文两版，报根因命中率、探针数、token、误报事故数；新增"顺序敏感性"配对题与"欠搜索"题（最简故障只需一条命令），分别计量过搜与漏搜。

**4. 收敛工具目录。** 按场景切片，单轮可用工具控制在 20 个以内；工具定义外置为按需读取的 SKILL 文件，降低常驻 token 与幻觉概率。

**5. 采购三问。** 能否导出本次结论的全部探针日志与停止规则？能否给出 with/without 上下文同题对照？"排除了什么"是否进入 PR/工单可复核？三问皆否，所谓"闭环"只是在更快产出可被质疑的结论。

**6. 标准补格。** 建议信通院 AIOps 评估在"过程可审计"维度增列「调查可举证率」，与证据保真、连接可举证、复核独立可举证、完成可举证并列，补齐"调查纪律"一环。

**本期新观点小结**：第 294 期说"读到的证据可能是假的"，第 303 期说"证据可能是不同事故的"，本期说"证据都真、也属同一事故，但你为找到它所做的那 19 次查询，本身就可能把结论推向一个漂亮的错答案"。**运维自动化的下一道门槛不是查得更快，而是知道什么时候已经查够。**
