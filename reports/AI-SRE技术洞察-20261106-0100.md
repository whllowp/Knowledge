## 到期面（Expiry）：唯一"提前知道日期"的故障，却唯一被系统性当成突发处理

> 时间：2026-11-06 01:00（GMT+8）｜覆盖：2026 年 10 月—11 月初｜本地知识库：E:\Knowledge\Knowledge\preview\173
> 主线：第六十九条主线「到期面」。与第 45 期（该来的信号没来）、第 54 期（期望态漂移）、第 75 期（封网）逐条划界。

### 引子：一个刚刚过去的零点

2026-11-06 00:00，是中国台湾地区证书机构 TWCA 旧中级证书的废止时限。此前 10-30，外部研究者在 Mozilla Bugzilla 通报其部分证书序列号随机位不足（约 24 bit，规范要求 ≥64 bit）。当地数字发展主管部门盘点涉及 962 个机关、9,772 张网站证书；11-01 已完成重新签发并把新证书文件邮件发给原申请人；到 11-02 晚，完成安装 926 张，占 9.5%。**签发一天做完，安装三天做了不到一成。**

这就是本期主线：签发完成度与生效完成度之间，没有共享的度量单位。

## 一、发展趋势：到期的四重位移

**（1）周期位移：从"年"到"六周"。** CA/B 论坛 SC-081v3 已于 2026-03-15 生效，公有 TLS 证书上限降至 200 天，2027-03 降至 100 天，2029-03 降至 47 天；Let's Encrypt 在 2026-01-15 把 160 小时（约 6.5 天）的 shortlived 配置与 IP 证书转为正式可用。按年计的续期次数是 1 次 → 1.8 → 3.6 → 7.8。这不是"更安全一点的证书"，而是把一个年度仪式改成了一条常态化流水线。

**（2）责任位移：签发上移，生效留在原地。** 腾讯云 2026-01-29 把 SSL 证书从"单张售卖"改为"订阅服务"，1 年期订阅期内系统自动生成 2 张证书，公告紧接着写了一句关键的话："第 2 张证书生成后，需您重新部署，方可正式生效。"火山引擎走得更远（到期前 15 天自动循环签发，可附加"证书托管"实现云产品自动替换），但仍把硬件、NAS、第三方 SaaS、客户端内置证书留在人工侧。阿里云 2026-09-07 起把"公网域名监控 + 自动托管 + 服务器部署"打包成基础版/标准版/专业版/旗舰版按年售卖，旗舰版 100 个域名、100 个服务器节点——**厂商把"部署"明码标价，恰恰证明部署才是成本主体。**

**（3）定义权位移：到期日从"字段"变成"流"。** RFC 9773（ARI，2025-06）让 CA 直接下发"建议续期窗口"，客户端在窗口内随机取点以削峰。更关键的是应急用法：CA 只要把窗口推到过去，遵从 ARI 的客户端就会立即续期。据厂商博客转述，Let's Encrypt 在 2026-03-17 做过一次 mass revocation 演练——生产环境一张不吊销，只把受影响证书的 ARI 窗口改成"立即续期"。对只看 notAfter 的系统，这次"被迫提前到期"完全不可见。**到期日不再是资产属性，而是外部输入。**

**（4）对象位移：到期的不再只是证书。** 同构的东西排成一列：OAuth access token（HubSpot 30 min、Google 60 min、Salesforce 15 min–2 h）、OIDC 会话、SPIFFE SVID、STS 临时凭证、订阅额度、模型快照、封网窗口、灰度豁免。共同点是：**有一个确定的时间点，且失效时不产生任何变更事件。**

## 二、技术现状

**客户端侧：规则从"固定天数"改成"生命周期比例"。** certbot 5.8 每次运行向 ARI 取窗口、在窗口内随机取时刻；acme.sh 3.1.6 内建 ARI 且默认跟随；lego 5.5.2 在无 ARI 时回落到"生命周期 2/3 处"。Let's Encrypt 建议在 crontab、脚本、runbook 里搜 60/80/83 这类硬编码值——"第 60 天续期"在 200 天下留 140 天余量，64 天下只剩 4 天，45 天下已经在过期之后。

**观测侧：能回答"谁"，答不了"还有多久"。** Google Cloud 的 Gemini Enterprise Agent Platform 已把 Agent 可观测性做成完整视图：OTel GenAI 语义约定、模型/工具/用量分层、双归因日志——审计里同时记录基于 SPIFFE 的 agent 身份（principal://）与发起人，并以 is_agentic=true 过滤自主动作。这个设计把"谁在动手"回答得很干净，但答不了"这个身份还有 38 分钟到期"；而在 SPIRE/Vault 短凭证体系下，后者恰恰是 agent 长任务最常撞的墙。

**Agent 侧：TTL 与任务时长的结构性错配。** WIMSE 的 workload identity practices 写了一条可反向读的规则："Tokens SHOULD NOT exceed the lifetime of the workloads they represent"（-00 §4.4／-05 §5.4）。工程读法应是：**当任务比 token 长，正确动作是让任务可续，而不是把 token 拉长。** 一次 6 小时的 run 面对 30 分钟的 token 要刷新 12 次，每次都是一个失败点、一个竞态点、一个审计断点。

**失败形态：不是崩溃，是漂移。** Scalekit 的总结值得抄进 runbook：token 中途失效时 agent 通常不抛异常，而是把空工具结果解释成"没有数据"、产生部分写入、或编出一条看起来在推进的恢复路径——"Agents don't crash, they drift." MojoAuth 补了第二刀：失效后回退到 service account 把活干完，等于把"代用户授权"静默换成"自主执行"。**到期因此是一个权限性质的静默变更点。**

**台账侧：同一资产有多个到期时刻。** 一个公开实测：某检测工具对 github.com 报"有效期至 2027-01-11"，而实际服务的 ECDSA 证书 2026-11-29 到期、RSA 证书 2026-12-30 到期，相差六周；工具读的是 CT 日志里最新签发的那张，而那张并未被服务。多算法双证、多副本分批签发、多集群灰度——**到期台账的主键不能是域名，只能是 (域名, 算法, 部署点, 签发批次)。**

**国内双时钟。** 火山引擎公告里有一句易被忽略的话：国际标准证书服务时长 199 天，**国密标准仍为 1 年**；代码签名证书从 39 个月降到 460 天。国内企业将长期同时运行两套到期节奏，而 SM2 证书链的续期工具链成熟度远低于 ACME 生态。

**平台侧：巡检清单里有"证书到期"，但没有"到期"这个对象。** 腾讯云在 2026-10-29/30 全球数字生态大会上把 CloudQ 从运维治理平台升级为多云 AIOps 智能体，底座是把资源、关系、状态、可处置动作组织在一起的全景图谱，巡检值守是主打场景；阿里云 OpenAgent 在 2026-10 发布 Skill/CLI，可被其他智能体集成调用，9 月已接入 STAROps 做根因分析。证书到期在这类产品里是巡检规则表的一行——**它被检查，但没有被建模**：没有续航比、没有续期链路的分段打点、没有"提前量分布"。

## 三、技术竞争力

| 方案 | 续期自动化 | 生效闭环 | 提前量可编程 | 未来态遥测 | Agent 凭证续航 |
|---|---|---|---|---|---|
| Let's Encrypt + ARI | 强（窗口下发） | 无（deploy hook 自负） | 强（CA 可推窗口） | 无 | 不适用 |
| certbot / acme.sh / lego | 强（比例+随机） | 弱（reload 常被漏） | 中（只读窗口） | 无 | 不适用 |
| 腾讯云证书订阅 | 强（自动生成下一张） | 弱（公告明示需重部署） | 弱（固定提前量） | 无 | 不适用 |
| 阿里云自动化服务 | 强（分级售卖） | 中（云产品托管） | 弱 | 弱（域名监控） | 不适用 |
| 火山引擎证书中心 | 强（提前 15 天循环） | 中（可选托管替换） | 弱 | 弱 | 不适用 |
| AWS ACM / GCP CertMgr | 强 | 中（限托管资源） | 弱 | 弱 | 不适用 |
| SPIRE + Vault | 强（自动轮转） | 强（短 TTL 兜底） | 强（TTL 即策略） | 部分（TTL 可查） | 部分 |
| CloudQ / OpenAgent | 巡检发现 | 无 | 无 | 无 | 无 |

三句判读：

1. **"续期自动化"这一列已经填满**，不再构成差异化；真正的空列是"未来态遥测"与"Agent 凭证续航"。
2. 云端订阅把 O(1) 的签发做到极致，却把 O(N) 的生效留给客户——"生效闭环"一列只有身份基础设施靠"短 TTL 兜底"真正闭上了，因为它的失效是设计内的，不是事故。
3. AIOps 智能体目前是"巡检的执行者"而非"到期的所有者"：它能发现还有 7 天到期，但不会说"这张证书的续期链路在第 3 段（写盘）已失败两次"。

## 四、技术挑战

**一、到期是"负事件"，在变更流里没有指纹。** RCA 的第一性动作是"找最近变更"，而到期的成因是"某件事没做"，它在任何变更记录里都不存在。这要求期望态模型新增一类对象：**必须发生但未发生**。与第 45 期分界：那是"该来的信号没来"（观测缺失）；与第 54 期分界：那是"状态偏离"（结果偏离）；本期是"应发生动作的缺失"，且它有一个确定的时间点。

**二、分母错位。** 到期的分母不是"证书数"，是"证书数 × 部署点数"。TWCA 的 9,772 张落在 962 个机关里，签发 1 天完成、安装 3 天 9.5%，说明**完成度必须按部署点计，按证书计会系统性高估**。任何"续期成功率 99.8%"的报表，只要分母是签发单，就预测不了事故。

**三、缺少"未来态"遥测。** 现有监控语义是"当前值 vs 阈值"；到期需要的是"未来某时刻的值 vs 已规划的续期事件"——**这是唯一必须做时间旅行才能观测的 SLO**。可行近似有两条：把"剩余有效期"作为 gauge 常态采集（而非告警时现算）；在续期五段（申请/校验/写盘/重载/对外生效）各打一点，并对"下一张证书是否已存在于目标部署点"发心跳。缺了最后这条，"申请成功"会一直冒充"续期成功"。

**四、到期 × 封网 = 撞窗。** 第 75 期说过封网冻的是发布，封网同样冻续期。阿里大于双十一二峰封网为 11-09 10:00 至 11-10 10:00（72 小时），一张 200 天证书落在任意 72 小时窗口内的概率约 1.5%；若续期只能提前 30 天做，实际暴露窗口被放大十倍。47 天时代，这变成每 47 天一次 6.4% 的硬撞——**封网规则若不给"到期"开豁免通道，封网本身就会制造到期事故。**

**五、Agent 的续航比没有定义。** 建议引入 runway = 凭证剩余 TTL ÷ 任务剩余 p99 时长，要求 > 1 并留 20% 余量。runway < 1 时应拒绝启动（fail-fast），而不是启动后靠 fallback 撑完。同时"401 必须上报、不许绕行"要写进工具契约——绕行在 trace 上表现为一次成功的工具调用，是**唯一看起来没有错误的故障**。

**六、学习能力没有按频率加密。** 续期次数涨 7.8 倍，但复盘周期、演练周期、值班培训周期都没变。低频大事故靠复盘学习，高频小事故只能靠自动化与阈值学习，而我们仍在用为前者设计的流程处理后者。

## 五、展望与建议

**给平台方（三条最小改造）**

1. **到期台账**：主键 (域名, 算法, 部署点, 签发批次)，字段至少含 notBefore / notAfter / 签发批次 / 部署确认时间 / 续期链路最后成功段。这张表应被 agent 直接查询，而不是靠人从控制台截图。
2. **续航比进 SLO**：runway 作为与错误预算并列的度量；对 agent 会话按"凭证剩余时长"分桶统计任务完成率，能直接暴露漂移。
3. **负事件进变更流**：给"应发生未发生"的动作发一条带负号的变更记录（expected_action_missing），让 RCA 的"最近变更"查询不再结构性失明。

**给使用方（三条纪律）**

1. 把"续期"拆成签发验收与生效验收，后者必须在目标部署点上做外部 TLS 握手验证，而不是看控制台状态。
2. 封网日历与到期日历做交集检查，把"到期"列为封网豁免的合法理由。
3. 对 agent：token 边界即检查点（可暂停、可重取、可从持久状态恢复）；401 不重试、不 fallback、直接 checkpoint + 审计。

**一个方向性观察：取消"到期"这个变量。** 2026-07 的 draft-winmagic-wimse-condition-bounded-credentials-01 提出"条件约束凭证"：密钥硬件根 + 在场证明，凭证没有固定过期日，有效性由"工作负载及其姿态是否被测量到"决定，条件失效"由密钥的缺席来执行，而不是靠撤销消息"。它当下只适用于稳定、可度量的平台，但指出了一条路——**到期的终极解法不是更好的提醒，而是把时间谓词换成存在谓词**。对 SRE 而言，这意味着终有一天"证书还有几天到期"会变成没有意义的问题；但在那之前，我们仍要为每一个确定的时间点，准备一条可验证的生效链路。
