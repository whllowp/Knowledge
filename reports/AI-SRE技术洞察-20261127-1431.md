# AI-SRE 技术洞察（第 374 期）

**生成时间**：2026-11-27 14:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：目录时效面／属主与目录的腐坏，指向错的人比没有目录更危险

## 题眼

服务目录里最危险的不是缺条目，而是**条目还在、属主已经不在**。一个写着"负责人 A"的服务，A 离职八个月；一个写着"值班组 B"的组件，B 组两年前就合并了；一个标着 `tier: 1` 的服务，实际三个月没人调用。

目录是声明，不是事实。事实要靠三个时间戳交叉验证：**最近一次变更、最近一次被调用、最近一次值班/告警**。三者对不上，目录就在腐坏。

## 一、发展趋势

第一，平台工程把目录当入口。Backstage 式门户、软件模板、Scorecard 都以 `catalog-info.yaml` 为单一来源；入口越集中，腐坏的代价越大。

第二，所有权从"文档"变成"字段"。`owner`、`system`、`domain`、`dependsOn` 被写进描述符，进入 CI 与门禁；字段一旦被消费，就不能只靠人记。

第三，AI Agent 开始读目录。Agent 查"该找谁""依赖谁""能不能下线"，读的就是这份声明；目录腐坏直接变成 Agent 的错误建议（第 372 期工具目录同病）。

第四，降本与合规都在问"谁负责"。云资源、数据副本、AI 系统都要属主；目录时效从"体验问题"变成"审计问题"（第 353 期孤儿资源）。

第五，目录开始有 SLO。新鲜度、覆盖率、属主有效率被当作平台指标；"目录 404"比"目录指向错人"更容易被发现，后者才是主要形态。

第六，Scorecard 与成熟度评估把目录当输入。可靠性与安全评分读目录字段；字段陈旧，评分就成了自我安慰。

第七，AI 系统也被要求登记。模型卡、系统清单、用途与属主进入目录；AI 治理让"目录时效"从体验问题变成合规问题（第 301 期）。

## 二、技术现状

**属主是字符串，不是关系。** `owner: team-a` 写死在 YAML 里，团队重组后没人改；字符串不会过期，人会。

**服务退役不删条目。** 下线流程走了，目录条目还在；新同学按目录找人，找到的是已解散的组。

**依赖是手写的。** `dependsOn` 靠人维护，实际调用关系只有流量与追踪知道；两者不一致时，没人知道信哪个。

**目录与值班表不连通。** 目录写属主，值班表写排班；两边各自更新，事故时电话打给不在班的人（第 132 期交接）。

**tier 是自报的。** 关键性由团队自己填，没人复核；`tier: 1` 的服务可能只是"老板关心过"。

**Agent 读到的目录没有时间。** 它不知道这条 `owner` 是何时写的、依据什么；于是把过期声明当当前事实（第 373 期时态）。

**目录与资源不连通。** 云上资源有标签，目录里有服务；两边靠人对齐，标签漏打、改名、跨账号都会让"服务"与"账单"对不上（第 353 期孤儿资源）。

**搜索与别名在退化。** 服务改名后旧名仍是入口，搜索返回两个结果；人凭记忆点开旧的，Agent 凭索引读到旧的。

## 三、技术竞争力

| 方案/能力 | 目录维护 | 属主校验 | 依赖发现 | 时效指标 | 主要缺口 |
|---|---|---|---|---|---|
| Backstage | 描述符 | 弱 | 手写 | 可扩展 | 需自建校验 |
| 云厂商 CMDB | 自动发现 | 中 | 部分 | 有 | 不覆盖 SaaS |
| APM 服务图 | 自动 | 无 | 强 | 弱 | 无属主 |
| 内部表格 | 手工 | 无 | 无 | 无 | 必然腐坏 |
| Agent 读目录 | 只读 | 无 | 弱 | 无 | 无 as-of |

**判读**：可采购的是"门户、CMDB、APM 服务图、值班系统、Scorecard"；不可采购的是"这条属主是谁在何时依据什么写的、这个人还在不在、这个服务还在不在被调用、依赖图与目录是否一致、目录上次校验是什么时候"。目录的可信度不来自条目数量，来自校验记录。

**本期反转**：我们一直把目录当"查得到"，它其实是"信得过"；查得到只证明条目存在，信得过要求三个时间戳同时新鲜。

## 四、技术挑战

**挑战一：属主是组织关系，不是技术字段。** 组织一改，目录就旧；自动同步 HR/IdP 又涉及隐私与权限。

**挑战二：依赖发现需要流量。** 静态扫描只能看到声明，真实依赖在调用链里；采样、异步、批处理都会漏。

**挑战三：退役没有强制门。** 服务下线没有"目录条目必须删除"的卡点；条目比服务活得久。

**挑战四：校验成本高。** 人工复核几百个条目不可持续；自动校验又容易误报（"最近无调用"可能只是低峰）。

**挑战五：Agent 放大了错误。** 人读错目录会打电话确认，Agent 读错会直接执行；目录错误从"不便"变成"动作错误"。

**挑战六：隐私与可见性。** 属主信息、值班表、依赖关系本身是内部敏感数据；目录越全，泄露面越大。

**挑战七：多目录并存。** 门户、CMDB、APM、值班表各有一份；没人定义哪份是主，冲突时靠人裁决。

**挑战八：时效指标没有分母。** "90% 条目有属主"不说明属主有效；要报"属主仍在该组织、该服务最近 30 天仍有调用"的比例。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①条目生命周期（创建/变更/退役）；②属主关系（人/组/值班表）；③依赖自动发现；④时效三时间戳；⑤过期与孤儿标记；⑥Agent 只读且带 as-of。

**用户旅程**：新服务注册（属主+系统+依赖）→ 变更（自动更新）→ 值班（与排班打通）→ 事故（找到在班的人）→ 退役（条目删除并有卡点）→ Agent 查询（带时间与置信度）。任何一步缺失，目录就开始腐坏。

**最小可行版本**：先只做"属主有效性"——把 `owner` 与组织/IdP 对齐，每周标出指向已离职或已解散组的条目；仅这一条就能消掉大部分"打错电话"。

**90 天实现方案**：0–30 天，给条目补三个时间戳与属主校验，定义"过期"阈值；31–60 天，把 APM 调用图与目录对账，标记不一致；61–90 天，退役流程加目录卡点，Agent 查询返回 as-of 与置信度。

**验收标准**：随机抽 20 个条目，能在不询问任何人的情况下回答"属主是谁、此人是否在组织内、服务最近是否有调用、依赖图是否与目录一致、上次校验何时"；答不出的比例就是目录的腐坏率。

**第 286 个市场空白（五项）**：属主时效校验；依赖图对账；退役卡点；目录 as-of；Agent 读目录的置信度。

**`catalog_freshness.*`／`owner_of_record.*` 第 253 次无人提字段族**：所有平台都报"有目录"，没有一个字段报"这条属主何时写入、依据什么、此人是否还在、服务是否还在被调用、依赖图与目录差多少、Agent 读到的目录是哪个版本"。

**本地 173／173-kb 连续第 241 期成组启用（赵恒 25：目录写着属主 A，A 已经离职八个月，事故电话还是打给他）。**
