# AI-SRE 技术洞察 · 第 66 期
## 删除面运维——"删掉了"是运维里唯一一个以"看不见"为成功标志的动作

> 覆盖维度：发展趋势 / 技术现状 / 技术竞争力 / 技术挑战 | 时间窗：2026 年 10 月—11 月 4 日
> 本期主线（第六十七条）：删除与保留（遗忘面）。与第 22 期记忆面分界：那期管"写什么、谁能写"，本期管"怎么让它不存在"；与第 61 期压缩面分界：压缩是"少记"，删除是"不记"，而压缩恰恰生产了最难删除的派生物；与第 45 期发起面互为镜像：那期是"该来没来"，本期是"该没还在，但看起来没了"。

---

## 一、发展趋势

**1. 记忆产品的竞争点，下半年从"记得多"转向"忘得干净"。** 2026 年上半年主流叙事仍是容量与巩固（OpenAI 的异步"做梦"、Claude 的文件式记忆、Letta 的分层记忆），下半年开始出现反向指标：删除路径、导出路径、可携带性被并列为选型三问。行业盘点已把"记忆可携带权"列为下半年首要议程，并给出第一条工程军规："为遗忘设计——删除路径和写入路径同等重要"。

**2. 合规侧从"告知同意"转向"全链条留痕 + 删除权"双轨。** 11 月 2 日人民论坛网的全链条治理论述给出最明确的一组中国口径：一边要求"开放数据导出备份渠道、落实个人信息删除权"，一边要求高风险模型退役后审计档案至少留存 5 年、"不得随服务关停直接删除"。**同一份数据，法律同时要求它消失和它存在**。欧盟侧同步：AI Act 8 月 2 日普遍适用，第 12 条要求全生命周期自动记录；金融审计口径更硬，AI 审计轨迹留存 5—7 年。

**3. 平台侧把"删除"改写成"隔离"与"分层"。** 10 月 29—30 日腾讯全球数字生态大会上，Agent Runtime 产品矩阵升级给出的答案不是删除能力，而是三种替代品：AgentCFS 的冷热分层让"长期保留的数据按访问频率流转"；Agent Bucket 以独立 Space 管理不同用户和智能体的数据；AI 网关提供"用量限额、隐私脱敏和调用追踪"。**用隔离划边界、用分层降成本、用脱敏代替不存**——这是国内平台的主流路径选择，工程上成立，但语义上并不等于删除。

**4. 删除正从运维动作变成架构属性。** 唯一能被数学验证的删除方式只有密钥销毁：按主体粒度加密，删除时销毁该主体的解密密钥，密文退化为不可解随机噪声。GDPR 第 17 条的监管实践已接受这一形式。这意味着删除能力是**设计期属性**，晚做就做不了——你无法给三年前写进向量库的明文补一把当时不存在的钥匙。

## 二、技术现状

**记忆侧：删除 API 已普遍存在，但回执只有一句话。** 阿里云 Agentic Memory 提供 `DELETE /memories/{memory_id}`，响应体是 `{"message": "Memory ... deleted successfully"}`——没有副本清单、没有残留抽样、没有执行范围。Anthropic 的 Memory Tool 更进一步把删除权交给了模型：由模型自主判断何时调用文件删除，用户说"忘掉"只是一个请求，是否执行、执行到哪一层由模型决定。当执行删除的是被删除对象本身，删除就从控制退化成了请求。

**证据侧：保留期正在悄悄决定复盘的可查窗口。** 观测平台的通行分层是 trace 7 天、metric 30 天、log 90 天，删除靠 TTL 自然过期完成，没有审批、没有回执、没有"删错了"的回滚。RAG 与排障实践里已有一个精确表述："找不到相关窗口的数据是 gap，而非空结果"——**证据的缺失与证据的不存在同形**。BTW Media 的标题提供了另一种时间不对称：主机只活了二十小时，月度峰值却记住了它——**资产退场了，账还在**。

**冲突侧：三种删除委托人互不知情。** 数据主体（PIPL 第 47 条，限期删除）、监管与诉讼（legal hold、AI Act 第 12 条、退役后 5 年档案）、运维自身（TTL 省钱）会对同一条记录提出相反诉求。现实是三条流程各走各的：DSAR 工单不会去查是否命中未结案事故，TTL 到期不会去查这份日志是否正在被复盘引用，legal hold 也不会通知记忆库暂停清理。删除冲突矩阵至今没有任何一家产品内建。

**派生物侧：删了原件，影响还在。** 一份被删会话至少留下六种派生物：摘要、embedding、图谱的边、评测集样本、SLO 与巡检基线（第 65 期）、供应商侧尚未过期的缓存前缀（第 27 期）。行业已承认定位困难："在向量空间里定位并删除某一条特定个人事实极其复杂、且难以验证"。更麻烦的是顺序——**摘要往往比原文更持久，因为它更短、更常被引用、更像"结论"**。

**删除的破坏力有公开尺度。** 一起案件中删除脚本运行 17 小时清空 89TB 模型与训练数据，当事人以破坏计算机信息系统罪获刑 5 年 10 个月——**删除者留下的痕迹比被删对象更长**。

## 三、技术竞争力

| 方案 | 删除粒度 | 覆盖载体（自述） | 删除可验证性 | 与保留义务的冲突处理 | 派生物治理 |
|---|---|---|---|---|---|
| Microsoft（Copilot + Purview） | 单条记忆 / 会话，分类族相互独立 | 会话与记忆分属不同搜索类别 | 界面删除 ≠ 保留版本消除 | 交由 eDiscovery / 保全并行 | 未公开 |
| OpenAI（ZDR / store=false） | 会话级（企业合同） | 供应商侧不留存 | 合同承诺，非技术回执 | 企业合同排除 | 不训练即不派生 |
| Anthropic（Memory Tool） | 文件级，模型自主调用 | 客户端存储后端 | 模型自报 | 无内建 | 无 |
| 阿里云 Agentic Memory | 单条 memory_id | 记忆服务内部 | 返回 message 文本 | 无内建 | 无 |
| 腾讯云 Agent Runtime | 用户 Space 隔离 + 冷热分层 | CFS / Bucket / Obs 三段 | 以隔离代替删除 | 分层保留 | 线上记录沉淀为数据集 |
| 火山引擎 Mem0 记忆库 | 单条记忆 | 记忆库内 | API 返回 | 无内建 | 无 |
| Datadog / Grafana | 保留期到期（按产品分层） | 按产品 TTL | 到期即不可查 | 保留期即证据寿命上界 | 无按主体删除 |
| 开源自建（Mem0 / Letta / Zep） | 向量 ID | 主库 + 索引 | 需逐库人工核对 | 自建 | 无 |

**判读一：海外在卖"承诺"，国内在卖"隔离"，开源在卖"可控"。** OpenAI 与 Anthropic 的删除能力本质是合同条款与技术承诺（ZDR），验证发生在法务层而非工程层；腾讯与阿里给的是隔离域、分层与脱敏，把"删不干净"这个难题转换为"看不见也算安全"；开源自建把记忆做成文件与 Git，可回滚、可 diff、可审计——但**回滚恰恰是删除的反面**，一个能 checkout 回昨天的系统，无法承诺今天的数据已经不存在。

**判读二：Microsoft 暴露的缺口最具代表性。** 其官方搜索指南写明"删除 Copilot 对话不会删除其关联记忆"，且记忆被归入与联系人共用的 `IPM.Contact` 存储分类。这句话的技术含量在于：同一份内容在两个分类里有两套生命周期，而用户只有一个删除按钮。**分类即权限，分类也是删除的边界**——这是所有"多模态记忆"产品共同的盲区。

**判读三：第二十二个市场空白。** 至今没有任何厂商把删除做成可导出指标。厂商只给 `deleted successfully` 一句话，而运维至少需要四个数：删除覆盖率（已确认副本 / 全部副本）、删除时延 p95、复活率（删除后又出现在检索结果中的比例）、派生物残留率。有第三方实测称主流产品的记忆删除"行为不可预测"、已删记忆会悄悄复活（转述口径）——**复活率不是极端案例，而是缺少分母时的必然结果**。

## 四、技术挑战

**1. 分母不可知。** 一次删除至少跨九类载体：主库、向量索引、对象存储、CDN、备份快照、供应商侧日志、缓存、评测集与数据集、以及上述派生物。没人能说清第九类里有多少条来自这次请求。**分母不可知，覆盖率就不可算，删除就不可承诺**——这是所有删除 SLA 立不起来的根因。

**2. 保留与删除的对立无法用流程消解。** 要复盘就得留遥测，要合规就得删个人信息，两者在同一张表上。当前唯一可行的工程解法是分账：原文按最短期限删，指标与结构化的"事件骨架"按最长期限留，用骨架支撑复盘、用删除账本支撑合规。这要求从采集端就分离"可识别字段"与"可统计字段"，而多数团队是在事故之后才发现两者混在同一个 span 里。

**3. 缓存是不可寻址的删除盲区。** KV 缓存与 prompt 缓存按前缀块存储，你不知道哪一块对应哪一条记录，也没有按主体失效的接口。删除请求只能等 TTL 自然到期。第 27 期的结论在这里反过来咬人：缓存把成本降下来了，也把"删除的完成时间"从秒级拖到了小时级甚至天级。

**4. 激励错位。** 删除不产生可见功能，只产生风险与工单；保留不产生可见成本，只产生存储账单。没有外部审计压力时，删除路径必然最后实现——这正是"写入路径建好了、生命周期没建"的组织学解释。

**5. 误删与漏删在指标上完全同形。** 删除意图识别本质是语义判断，删多了和删少了都不会触发告警。**这是唯一一类失败时没有任何信号的运维动作。**

## 五、展望与建议

**给架构侧（Day-1 决策，晚做无效）**
1. **按主体分密钥**。用户/租户粒度独立加密，删除=销毁密钥。这是唯一可验证的删除形态，也是唯一能同时满足"立即彻底"与"可审计"的路径。
2. **采集端分离可识别字段与可统计字段**，让"删原文、留骨架"在物理上成立。
3. **删除清单（deletion manifest）九类载体登记制**，每个载体指定属主与回执方式；没有属主的载体视为未覆盖。

**给运维侧（可本周落地）**
4. **删除回执替代"successfully"**：逐载体签名回执 + 删除后 24 小时残留抽样（用原查询重放，命中即复活）。
5. **删除 SLA 四指标**：覆盖率、时延 p95、复活率、派生物残留率。复活率 > 0 即视为删除面故障，与第 45 期缺席 SLI 同级处理。
6. **季度删除演练："删一条，查九处"**。抽样一条测试数据逐载体验证，把删除从"相信"变成"验过"——与第 56 期注入目录同构，一个管"制造故障"，一个管"制造不存在"。
7. **删除冲突矩阵进工单系统**：DSAR 命中 legal hold 必须硬阻断并留痕，禁止人工 override；TTL 到期前对"近 90 天被复盘引用过"的遥测自动延期。

**给采购与治理侧**
8. **把四个删除指标写进合同**，与第 25 期"可承诺性分级"合流：能给出覆盖率分母的供应商列 Type I，只能给"successfully"的列 Type III。
9. **保留期与证据寿命对齐**：关键事故相关遥测的保留期，不得短于复盘与审计要求的最长年限。否则第 60 期"复盘写完即定稿"会变成"复盘写完，证据已过期"。

**一句话判断**：2026 年之前，运维的对象是"让系统处于某个状态"；此后多了一类对象——**让系统不处于某个状态，并且能证明它不处于**。前者有仪表盘，后者目前只有一句 `deleted successfully`。
