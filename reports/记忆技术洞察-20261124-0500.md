# 记忆技术洞察 · 第 141 期（20261124-0500）

**主题：记忆的「原生架构化」（native memory architecture）——记忆不再只是 agent 外部库或服务层 KV 池，而是模型计算图里的一类一等状态。前 140 期追问存什么、取哪条、读多清、证据能否回来、信念此刻是否成立、经验会不会反噬（#79／#122／#132／#126／#139／#140），共同预设记忆在模型之外；11-20 提交的 MemOnce（arXiv 2611.27973，Chang Nie 等，cs.CL）把历史压成末层隐状态的 1/r 子集，一次检索、按需解码为各层 KV，1M 上下文状态缓存降 1313×。与 #137 划界（那期在服务层逐出已生成的 KV，本期从源头不生成多层 KV）、与 #133 对照（那期零结构纯文本回看，本期是可学习紧凑表示）、与 #131 呼应（检索预算也呈倒 U）。**

> 洞察范围：2026 年（近 30 天为主）。四维度：发展趋势 / 技术现状 / 技术竞争力 / 技术挑战。

## 一、发展趋势

长程交互的成本中心正从"上下文长度"移到"状态架构"。Transformer 逐 token 逐层存 KV，缓存随 N 线性涨、预填二次算；Mamba／RWKV／GDN 把历史压成定长状态却丢细节；外部库可管可改却难端到端优化。2026 年的新方向是把记忆做成可学习、可扩容、按需激活的架构组件：存末层表示，用临时解码的 KV，历史池下沉 CPU／SSD，活跃状态恒定。

## 二、技术现状

MemOnce 拆成写、索引、读三函数：写端每段只留末层末端 1/r 状态（r=8）入持久库；索引端用查询末 token 投影做余弦，从长期池取 Top-K=64，短期窗口保留最近 16 段（约 8K 原 token）；读端用逐层轻量 MLP 把激活状态解码成各层 KV。主干每阶段交错三个线性块与一个稀疏注意力块；预训练联合优化，后训练只调索引、解码投影与编码端 LoRA，生成期主干冻结。

## 三、技术竞争力

五项记忆基准跨 4K—1M：2B 平均 51.17（全上下文 49.33，+1.84），4B 60.07（54.30，+5.77），高于 M+ 41.39、Metis† 31.76。32K 记忆负载下通用推理 65.98（基线 65.88），而全量 SFT 38.40（−27.48）、软提示 47.66（−18.22）、线性状态 43.35（−22.53）。预填 32K 1.38s、1M 41.36s，较 Hybrid 快 6.9×、较 M+ 快 35.8×，活动 GPU 缓存恒 25MB；128K 查询 64.24ms 对 M+ 772.5ms、RAG-Rewrite 1094.3ms；零样本检索 R@10 69.21。

## 四、技术挑战

①检索预算倒 U：K=0／16／64／128 为 36.83／59.72／60.07／58.86，多取反被低相关状态拖累。②r=8 近乎无损（差<0.3%）依赖"段末状态概括整段"的架构耦合，换骨干须重验。③SSD／CPU 下沉假设 20MB PCIe 搬运稳定，长尾延迟未展开。④从零预训练只到 1B，作者自陈长程编码与多步工具任务未验证。⑤单骨干 Qwen3.5、单一裁判。⑥不解决撤回与接口静默变更（#139／#140）这类语义失效——状态再紧凑也会忠实保存已失效内容。

## 五、需求分析

长会话助手与代码 agent 的痛点不是"找不找得到"，而是 1M 上下文下缓存爆、首字慢、记忆改造把通用能力拖垮。用户要同一个模型既记得住多会话细节，又不因加载记忆而变笨变慢。产品须把"每查询活动状态多大、搬运多少字节、通用分掉多少"列为可观测指标，而不是只报召回率与压缩比。

## 六、用户旅程

用户跨周对话后发新请求：系统先用当前请求对持久记忆库做一次索引，取 64 条长期块与最近 8K 原 token 对应的短期块组成活动状态；逐层解码 KV 后只把这些 KV 拼在本轮输入前参与注意力，历史池留在 CPU／SSD；回答期主干冻结、不写权重。面板并列展示活动状态 MB、PCIe 传输量、预填与解码延迟、记忆分与通用分，供用户判断"省得是否划算"。

## 七、具体实现方案

①写端以段为单位缓存末层末端 1/r 隐状态，跨段线性状态默认丢弃（r=8 时保留 0.5255 对丢弃 0.5235）。②索引只算一次并跨层复用：128K 下 60.39ms 查询前向＋3.85ms 从 SSD 取 20MB，较 32 层逐层检索的 1150MB／772.5ms 快 12×。③读端逐层 MLP 解码保住注意力表达力，K=64 为默认，K=128 反降 1.21 点。④记忆税增列"状态架构税"：缓存复杂度 O(CD) 对 O(LND)、跨层检索次数、PCIe 搬运与通用回退（接 #5／#137）。⑤五项目经 tag／release 核实：OpenViking v0.5.5（11-23 提交新增 queuefs PostgreSQL 持久后端、grep 正则迁 Rust 降阻塞），Hy-Memory v2.0.17＋MemHub v1.0.8、TencentDB v2.0.4、dsh v26092802、ReMe v0.4.2.3——均在外部库侧优化吞吐，无一做原生状态架构。

## 八、本期新观点

1. **记忆主体第三次上移：从外部库到 serving 层再到模型计算图**（接 #137 划界）——比较轴新增"谁持有记忆"：显式库、共享 KV 池、学习到的可扩容状态三者各有成本结构。
2. **压缩从省钱改为改成本结构**（接 #5／#137）——"删 KV"变成"按需解码 KV"：持久库 Lr× 压缩、活跃状态 O(CD)，记忆税须记复杂度与解码投影，而非只看 token 数。
3. **跨层路由次数是独立的效率维度**（深化 #122／#124）——单次索引复用 12× 快于逐层检索，读多少之外还要问"为读它付了几层路由"。
4. **检索预算倒 U 是架构超参而非越多越好**（呼应 #131 但机制不同）——K=128 比 K=64 反降 1.21 点，原因是低相关状态注入噪声，不是弱模型被淹没。
5. **保真与通用兼得的条件是历史以模型熟悉的 KV 形式进入**（新角度）——生成期冻结主干，通用分 +0.10；软提示／线性状态／全量 SFT 分别 −18.22／−22.53／−27.48，给出权重写入之外的第三条路。
6. **五项目倒挂＋AML 补 native-memory-architecture 维度**——以"1M 下既省又准且不伤通用"验收，登记活动状态 MB、跨层检索次数、PCIe 字节与通用回退四栏；OpenViking 的持久后端与 Rust 正则仍属外部库吞吐优化。
