# AI-SRE 技术洞察 第 232 期（2026-11-16 22:00）

## 例行承诺面／定时任务的静默缺席（Routine Commitment / Silent Absence of Scheduled Runs）

> **题眼**：过去 231 期都在问「动作做错了没有」，本期问一个更冷的问题——**「本该发生的动作，压根没发生，谁来发现」**。定时巡检、每日对账、周期刷新是 SRE Agent 唯一「没人请求也会发生」的动作；也正因没有请求者，它失败时没有调用方报错、没有人来追问，沉默被默认读成成功。11-13 Anthropic 状态页自己写下「scheduled tasks and routines could run more than two hours late, and some runs had been skipped」；11-11 OpenAI 一次九小时的 Workspace Agent 启动中断，把「这次没跑」留成一条没有 error 的空白。缺席不是一次失败的调用，而是一次**从未发生的调用**——trace、日志、指标里都没有它的位置。把「支持定时任务」写进产品页很容易，举证「今天九点那次例程到底跑没跑」很难。

## 一、发展趋势

三条 2026 年的趋势在本月同时收敛到「例行承诺」这个盲区。

**第一条：SRE Agent 从「被叫才动」转向「自己按期动」。** 阿里 STAROps 10 月升级把 Agentic Ops 定义为「用户设定一个持续的运维目标，由 Agent 围绕目标观察环境、发现异常、展开调查」，官方举例正是「持续关注核心应用的发布情况，在新版本发布后检查运行状态」——这是一种**面向未来的持续承诺**，而不是一次问答。腾讯 11-02/03 的 CloudQ 升级把「跨产品取证、告警调查和主动巡检」列为 Agent 承担的三类重复工作；远望/信通院同批强调运维智能体要「过程可审计、结果可评价」，但评价的对象仍是一次任务，不是「承诺序列的履约率」。

**第二条：调度器本身成了可靠性依赖，而且各家语义互斥。** 11 月的运维社区集中披露了这类故障：有团队「10 月 7 日到 15 日七个工作日只跑了三天早报，三天什么都没有」；有人「3:15 的一次性任务零运行、无报错，两天后才发现」；一个自动编码管线「三天半烧完 3000 分钟 GitHub Actions 配额，任务停了我两天没注意到」。根因不是模型，是调度器：cron 遇到休眠直接跳过；launchd 的 `StartCalendarInterval` 会在唤醒后补一次；systemd timer 需 `Persistent=true` 才补；而 Claude Code 的会话级定时任务官方明示「No catch-up for missed fires」，且会话内创建的周期任务「7 天后自动过期」。同样一句「每天九点」，在四种调度器下是四份不同的承诺。

**第三条：平台故障留下一条「沉默的尾巴」。** 11-13 Anthropic 一天两次故障，下午那场把 API、Managed Agents、connectors 一并卷入，恢复通告里承认定时任务「晚两个多小时，部分运行被跳过」，但两场故障均未发布事后报告。OpenAI 11-11 22:50 起近十小时无法启动新的 Workspace Agent run；11-05 的 Work/Dots 故障被外部复述为「早报没跑、网站检查没做，而没有任何东西通知你」；Codex 11-01～04 的故障里，一份配置文件解析失败让定时任务在启动阶段停掉，用户寄出 HAR trace 后由 AI 支持 agent 从服务端日志里查到，同期至少八次定时运行失败——而官方状态页那几天没有对应公告。平台宣布「已恢复」与「欠下的例程补没补」是两件事，后者没人报。

## 二、技术现状

工程侧已经存在正确做法，但它是**外部补丁**，不是平台能力。

社区给出的通用解法是 dead man's switch：任务结束时向 Healthchecks.io 之类的服务发一个 ping，约定时间没收到 ping 就告警。「缺席本身就是信号」——机器没开、应用没开、排期过期、任务在创建任何东西前就崩了，四种原因被一次性覆盖。两个关键细节决定了它是否真的有效：**要在结束时 ping，不是开始时**；**要盯业务结果（邮件发出、记录写入、工单创建），不是进程 exit 0**。Hermes Agent v0.23.0（11-05）的 cron 设计把这些写成了默认约束：脚本任务空 stdout 是「静默一次 tick」，补跑窗口被夹在 2 分钟到 2 小时之间，`--grace-minutes` 可覆盖，且默认禁止被调度的会话创建/删除 cron（需显式开启 `cron.allow_agent_scheduling`），并把幂等列为「 cardinal rule」——因为容器重启、手动重跑都会让同一份承诺重复兑现。

平台侧则刚刚开始把这类信息变可见。Google 11-13 把 1P/3P Agent 的遥测统一落进客户自有的 BigQuery `agent_events` 表：每轮记录 input/output/thought/cached/total token 与 turn latency，日级 token 配额处于 preview，每查询字节扫描上限已可用。但它同时明文写下一条对本期至关重要的事实：**逐轮隐私检查是 fail-closed 的**——知识源用了行级安全、列级策略标签或动态脱敏，该轮就不写日志；写入失败则执行 fail-open，会话继续。于是「`agent_events` 里缺一轮，可能是策略结果而不是 bug」。这是行业第一次由平台方亲口承认：**缺席有语义二义性，日志的空白既可能是没做，也可能是做了不许记**。Anthropic 侧，Managed Agents 支持 cron+IANA 时区、最短 1 分钟、每组织上限 1000 个、会话预算按次复制；Google 的 Prism 开源评测工具把测试结果写进日分区表，与生产日志并排——但比对的是答案质量，不是「这天的例行运行到齐了没有」。

## 四、技术挑战

**挑战一：缺席没有主体。** 交互式任务失败有调用方报错，定时任务没有请求者；没有请求者就没有监督者。要在系统里表达「缺席」，必须先有一个外部主体持有「应到清单」——而 Agent 自己不会声明「我本该九点跑」。

**挑战二：缺席的二义性。** Google 已经证明空白可能是策略跳过。在系统里「没记录」至少三种来源：没跑、跑了没记、跑了但内容被脱敏规则挡掉。三者混成同一个空表，任何自动补偿都可能把合规跳过「补」成一次违规重跑。

**挑战三：履约语义不可移植。** skip / catch-up / coalesce / expire 四种策略下，「连续三天没出报」分别是三次违规、三次延迟合并成一次、一次正常过期或一次配额耗尽。没有 `catch_up_policy` 字段，跨调度器迁移的行为差异会被误读成模型能力变化。

**挑战四：结果回执比进程退出更难。** 定时 Agent 可以跑完循环、记下成功，却让最后那次 CRM 写入静默 no-op；也可以「已发送」但重复发送。exit 0 与「我跑了」的自报都不算证据，必须验下游状态。

**挑战五：自调度改变承诺集合。** Hermes 默认禁止被调度会话改 cron 是有道理的：一旦 Agent 能增删自己的例程，承诺集合本身就成了可被静默修改的对象——而你监控的是旧清单。

**挑战六：组织层面的归属。** 例程的 owner 往往是最初搭建者，人已转岗；11-13 那类故障之后，没有具名责任人去核对「欠的那几次补没补」。这与第 231 期的责任链直接相接。

## 五、展望与建议

1. **把 `routine.commitment.*` 五字段写进 OTel GenAI 提案**，缺省 `ABSENCE_UNVERIFIED`；每次调度生成一条 `expected` 记录，运行结束生成一条 `fulfilled` 记录，两者用同一个 `commitment_id` 关联，只有配对成功才算履约。
2. **应到清单从配置反向生成，不由 Agent 自报**：cron/routines/scheduled tasks 的注册表是唯一真源；每日对账 `expected_run_count − actual_run_count`，差值进 SLO，连续两日非零即告警，并区分 skip/catchup/expire。
3. **外部打卡 + 结果回执**：每个业务关键例程在结束时会 ping 独立监控，盯下游产物（邮件、记录、工单）而非 exit 0；grace period 按缺席代价分级；ping 的是业务结果，不是过程。
4. **给缺席加归因字段**：`absence_reason ∈ {not_started, skipped_by_scheduler, skipped_by_policy, failed_pre_output, expired}`；Google 的 fail-closed 跳轮必须落成一个可导出的 reason，禁止用空表代替。
5. **平台故障结算单**：恢复通告必须附「故障窗口内欠下的例程清单及补跑状态」；把「补跑完成率」纳入第 230 期知识保鲜与第 226 期疗效归属的共同验收——例程欠账是最容易被「状态页全绿」掩盖的一种未恢复。
6. **限制自调度并验幂等**：默认禁止被调度会话增删自身排期；所有例程按 upsert／sent 状态／确定性文件名设计，能连续跑三次不出事；把「连续三次调度不产生副作用」纳入演练。
7. **本地与基准补格**：09 吴垚把定时与告警/变更/应急并列为四类事件触发，本地已具备分类骨架，缺的是履约字段；建议在信通院六维的「过程可审计、结果可评价」下各补一格「例行承诺可举证率」，并在 SRE 基准中加入「定时任务被静默跳过」题型——现有榜单只测被触发的一次任务，不测没被触发的那些。
