# AI-SRE 技术洞察（第 381 期）

**生成时间**：2026-11-27 21:31（Asia/Shanghai）
**本期主题**：记忆容量面／记忆淘汰与预算

## 题眼

Agent 的记忆库通常会一直变大：每次对话都写入，每次检索只取 top-k。**写入是 1 次，读取是 N 次**——一条过时、重复或错误的记忆，会被反复检索、反复影响回答。

## 一、发展趋势

第一，记忆从"全存"转向"预算"。给每个用户/会话设 token 或条数预算，超限触发合并或淘汰。

第二，淘汰策略从 LRU 转向"重要性 + 时效 + 相关性"加权（Generative Agents 的三因子检索）。

第三，记忆合并（consolidation）：把相似条目合并成一条，而不是无限追加。

第四，分层记忆：工作记忆（上下文）、情景记忆（会话）、语义记忆（长期事实）分别管理。

第五，记忆的可观测：记录命中率、重复率、淘汰量、被淘汰条目的影响。

第六，记忆的删除与保留进入合规视野（第 307/351 期）。

## 二、技术现状

**记忆是带语义的缓存。** 它加速"回忆"，但缓存会过期、会脏、会挤占；与普通缓存不同的是，记忆的"错误"会改变 Agent 的判断，而不只是返回旧值。

**四类淘汰，各有代价。**
- 按时间：旧记忆先走，可能丢掉仍然有效的事实；
- 按重要性：重要但不常访问的条目留下，可能挤掉高频事实；
- 按相似度：合并相似条目，可能把两个不同用户的事实混为一条；
- 按容量：满了就删，删除顺序取决于数据结构而非业务。

**记忆膨胀的代价是检索精度。** top-k 检索在条目变多后，噪声比例上升；相关条目被埋，回答开始引用过时记忆。

**写入即承诺。** 一条错误记忆写入后，后续每次检索都可能放大它；写入门的缺失（第 238 期）会在这里复利。

**去重不是合并。** 相同事实的不同表述会被当成两条；合并需要判断"是否同一事实"，而不只是相似度。

**淘汰的沉默性。** 淘汰通常不报错、不告警，也不写审计；Agent 只是"想不起来"了。没有淘汰日志，就无法区分"忘了"与"记错了"——这两种失败需要完全不同的修复。

**记忆的热度与重要性不是一回事。** 高频记忆不一定重要（例如寒暄），重要记忆不一定高频（例如过敏史）。只按访问频率淘汰，会先删掉最重要的事实。

**预算要按主体分，不按库分。** 一个共享记忆库的总预算，会被最活跃的主体吃掉；按用户/租户分配预算，才能让每个主体都有"记得住"的空间。全局预算下，安静的用户先失忆。

## 三、技术竞争力

| 方案 | 容量控制 | 淘汰依据 | 合并 | 可观测 | 适用 |
|---|---|---|---|---|---|
| 向量库 + TTL | 有 | 时间 | 无 | 弱 | 简单场景 |
| Mem0 类记忆层 | 有 | 重要性/时间 | 有 | 中 | 通用 Agent |
| Zep 类会话记忆 | 有 | 会话边界 | 部分 | 中 | 对话产品 |
| 自建（DB+向量） | 自定 | 自定 | 自定 | 自定 | 深度定制 |
| 无预算（全存） | 无 | 无 | 无 | 无 | 早期原型 |

**判读**：能买到"存储与检索"，买不到"该记什么、该忘什么、合并后是否仍是同一事实"。

**本期反转**：我们一直把记忆当"越多越好"的资产，所以关注写入与检索；更该把它当"有预算的缓存"，关注淘汰与合并。**记忆的价值不在存了多少，而在检索时还剩下多少对的。**

## 四、技术挑战

**挑战一：淘汰的可解释性。** 为什么这条被删？没有记录，就无法复盘"Agent 为什么忘了"。

**挑战二：合并的正确性。** 相似不等于同一；合并错会把两个主体的事实混淆（第 321 期）。

**挑战三：写入与淘汰的竞态。** 正在被检索的记忆被淘汰，回答会引用到一半。

**挑战四：多租户预算。** 一个租户的记忆膨胀，会挤占共享存储与检索配额（第 275 期）。

**挑战五：删除的传播。** 淘汰不等于删除；淘汰的条目可能还在备份与向量索引里（第 369 期）。

**挑战六：评测。** 记忆质量难以离线评测，只能看"回忆任务"的通过率。

**挑战七：成本。** 记忆存储与检索也是成本项，且随用户数增长（第 331 期）。

**挑战八：冷启动。** 新用户没有记忆，Agent 表现与老用户不同（第 136 期）。

**挑战九：记忆的热度偏差。** 高频访问的记忆被保留，低频但关键的事实被淘汰；需要"重要性"与"访问频率"分开建模。

**挑战十：跨会话主体混淆。** 同一设备、同一家庭、同一浏览器下的多个用户，记忆可能共享；主体边界不清时，淘汰与合并都会出错（第 321 期）。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①记忆预算（条数/token）；②淘汰策略与记录；③合并与去重；④分层记忆；⑤检索质量指标；⑥删除传播；⑦多租户配额；⑧记忆评测集。

**用户旅程**：用户对话 → 写入候选 → 写入门（第 238 期）→ 记忆库 → 检索 top-k → 回答；后台按预算淘汰/合并，记录原因。

**实现方案（90 天）**：0–30 天设预算与淘汰记录；31–60 天做合并规则与检索质量指标；61–90 天做删除传播与多租户配额。

**验收标准**：任取一次回答，能回答"用了哪几条记忆、它们何时写入、是否被合并过、为什么没被淘汰"；答不出就是"全存 + top-k"。

## 第 293 个市场空白（五项）

1. 记忆预算与淘汰记录；
2. 合并正确性校验（同一事实判定）；
3. 记忆检索质量指标（命中/噪声/过时）；
4. 淘汰与删除的传播；
5. 记忆评测集。

## `memory_evict.*`／`memory_budget.*` 第 260 次无人提字段族

预算、淘汰原因、合并来源、检索噪声比——这些字段在记忆库里通常不存在；存在的是"创建时间 + 向量"。
