# AI-SRE 技术洞察（第 331 期）

- 生成时间：2026-11-24 16:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：计量面／用量计费与账单争议——计费单位不是事实单位

## 题眼

2026 年 EMNLP Findings 的 CoIn 论文把一个很难被审计的收费方式写清楚了：商业 LLM API 越来越多地在返回答案前生成“推理 tokens”，但提供商通常**隐藏推理轨迹、只返回最终答案**；用户按这些**看不见的 token** 付费，而它们往往占成本的多数。论文指出，这打开了一个口子——提供商可以多报用量，或注入低成本的合成 token，而用户没有任何手段验证真实性。

同一研究线在 2026 年 5 月的一篇后续工作里给了更冷的结论：已有的三种审计方式**都可以被规避**，相对 CoIn 的最高虚增达到 **1,469%**。

这不只是“供应商是否诚实”的问题，也是“我们自己是否算得清”的问题。2026-07-26 的一份计量研究笔记列了几条会直接推翻成本结论的事实：同一个 Agent 任务在不同运行之间 token 用量可以相差 **30 倍**；一次 Anthropic 运行里，20 个任务中的 2 个吃掉了 **43%** 的支出；**失败的运行照样计费**；模型对自己会用多少 token 基本没有预测力（相关系数 r ≤ 0.39）。它因此主张：成本的最小单位应该是“**完成的任务**”，而不是 token，并且要给分布和误差条。

2026-09-11 的一篇中文实践文章补上了重试这一层：本地等待超时，只说明**本地**没有及时拿到结果，不能证明上游没有处理；重发前要判断操作是否适合重试，涉及外部写操作还要考虑幂等，否则会把业务操作重复执行。它给出的边界是概念性的——每任务最大模型调用数、最大任务时长、最大重试次数与退避——并明确这些**都不能直接保证金额上限**。

## 一、发展趋势

**第一，从“按 token 计费”转向“按完成任务计费”。** 同一任务方差 30 倍，token 单价无法回答“这个功能一次要花多少钱”。

**第二，看不见的推理 token 成为审计焦点。** 推理 token 被计费但不可见；审计需要统计信号（推理占比、tokens-per-char、实际服务模型）而不是单点对账。

**第三，重试与取消的计费语义被单列。** 失败也计费；超时重试可能重复执行；取消后已生成的 token 是否计费取决于流式与取消时机。

**第四，缓存折扣变成健康指标。** 缓存输入约为新鲜输入的十分之一价格；真实 Agent 流量中，输入缓存命中率中位数约 84%，top decile ≥94%；低于 80% 通常意味着缓存键或路由出了问题。

**第五，账单从“数字”变成“证据链”。** 每笔费用要能追溯到调用、任务、尝试次数、聚合桶与计价规则；否则争议无法裁决。

## 二、技术现状

**计价维度多。** 输入/输出/缓存/推理/图片/工具调用/批处理/服务层级；同一请求在不同维度上计价不同。

**token 计数不一致。** 分词器版本、消息格式、工具 schema、图片编码都会改变计数；客户端估算与服务端账单可能不同。

**重试双计。** 超时重试、幂等重试、自动重试都会产生新调用；没有幂等键就无法区分“重试”与“新任务”。

**聚合与归属。** 小时桶、项目/租户/功能归属、跨云折扣、承诺用量；聚合规则不同，账单不同。

**审计信号。** 推理占比异常、tokens-per-char 漂移、实际服务模型与请求模型不一致；这些是信号，不是证明。

**争议处理。** 没有逐调用证据时，只能按账单总额协商；有证据时才能定位到具体任务与尝试。

## 三、技术竞争力

| 方案 | 成本可见性 | 争议可裁决 | 抗重试双计 | 实现成本 | 主要风险 |
|---|---|---|---|---|---|
| 按 token 计费 | 中 | 低 | 低 | 低 | 推理/缓存不透明 |
| 按完成任务计费 | 高 | 中 | 中 | 中 | 任务定义难 |
| 缓存折扣 | 高（若可见） | 中 | 不适用 | 低 | 命中率漂移 |
| 幂等计量（任务 ID） | 中 | 高 | 高 | 中 | 需贯穿调用链 |
| 小时聚合桶 | 中 | 中 | 中 | 低 | 丢失明细 |
| 审计信号 | 中 | 中（信号非证明） | 低 | 中 | 需要基线 |

判读：买得到计费 API、用量导出、缓存折扣、聚合报表；买不到“这笔费用对应哪些调用、哪些是重试、失败为什么也计费、推理 token 是否真实、缓存命中率为何下降”。

本期反转：我们一直把账单当“上游报的数”。实际上计费是一次**数据管道**：分词、计价、重试、聚合、归属，每一层都会改变数字。成本的最小单位不是 token，是**完成的任务**；账单的最小证据不是总额，是**逐调用的可复现记录**。

判词：「用量 API／计费导出／缓存折扣／预算告警／聚合报表」全部可采购，「这笔费用对应哪些调用、哪些是重试、失败为何计费、推理 token 是否真实、缓存命中率为何下降」不可采购。

## 四、技术挑战

**其一，不可见的推理 token。** 计费但不可见；审计只能靠统计信号。

**其二，分词与格式差异。** 客户端估算与服务端计数不一致；版本升级会改变计数。

**其三，重试语义。** 超时不等于未处理；没有幂等键就无法区分重试与新任务。

**其四，失败也计费。** 失败运行照样产生 token；预算模型要覆盖失败。

**其五，聚合不可逆。** 小时桶/项目归属会丢失明细；争议时无法回溯。

**其六，缓存健康。** 命中率下降常是缓存键/路由问题，不是价格问题。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 财务/FinOps：需要按任务/功能/租户的成本与误差条。
- 平台/SRE：需要计费管道、幂等键、缓存命中率、失败成本。
- 产品：需要“一次任务多少钱”的分布，而非单价。
- 安全：需要检测异常推理占比与服务模型替换。
- 争议处理：需要逐调用审计证据。

**用户旅程（一次“账单翻倍”）。**

1. 月末账单翻倍；用量报表显示 token 增长 20%。
2. 排查发现重试翻倍：超时重试没有幂等键，同一任务被计费两次。
3. 另一部分来自推理 token 占比升高；用户看不到推理内容。
4. 缓存命中率从 90% 掉到 70%；缓存键包含请求 ID，导致几乎全 miss。
5. 失败运行仍计费，预算模型未覆盖。
6. 争议时只能按总额协商，无法定位到任务。

**实现方案（90 天）。**

- 第 1–2 周：成本单位——按完成任务统计成本分布（P50/P95/长尾），保留 token 明细作为分解。
- 第 3–4 周：幂等计量——任务 ID 贯穿调用链；重试复用任务 ID，计费去重。
- 第 5–6 周：调用级账本——记录模型、输入/输出/缓存/推理 token、服务层级、尝试次数、失败原因。
- 第 7–8 周：缓存健康——命中率、缓存键设计、按租户/功能的命中分布；低于阈值告警。
- 第 9–10 周：审计信号——推理占比、tokens-per-char、实际服务模型；标注为信号而非证明。
- 第 11–12 周：预算与护栏——每任务调用数/时长/重试上限；失败成本纳入预算。
- 第 13 周：对账演练——模拟重试、缓存失效、推理占比异常，验证账单可解释。

**验收标准。** 任一笔费用，能回答：对应哪些调用、哪些是重试、失败多少、推理占比、缓存命中、归属哪个任务。

**第 243 个市场空白（五项）**：任务级成本分布；幂等计量；调用级账本；缓存健康基线；审计信号。

**`metering.*`／`billing_evidence.*` 第 210 次无人提字段族**：`metering.task_id`、`metering.attempt`、`metering.cached_input_ratio`、`metering.reasoning_ratio`、`billing_evidence.call_ledger` 在计费 API、可观测性与 FinOps 之间没有统一语义；报表只给总额。

**本地 173／173-kb 连续第 198 期成组启用**（肖汉松 22）：本地知识库把“账单”与“证据”分开记账；本期把计量落成任务级成本与调用账本。
