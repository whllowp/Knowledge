# AI-SRE 技术洞察（第 369 期）

**生成时间**：2026-11-27 09:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：向量索引面／标记删除、过滤召回与重建债务

## 题眼

2026-07-03 的一篇测量论文把"过滤检索"的代价量化了：同一份向量、同一个 HNSW 索引，无过滤时 recall@10 是 **0.978**；当 95.2% 的向量被过滤掉，recall@10 跌到 **0.316**——**三分之二的相关结果没被返回**。把过滤改成"先过滤、再在子集上算距离"（pre-filtering），召回恢复到可接受水平，代价是延迟与工程复杂度。

另一份 2026 年的索引研究指出：HNSW/IVF 这类 ANN 索引**没有稳定的"删除"定义**——所谓删除是标记 + 图修补 + 周期重建；修补可能破坏连通性，基于计数的剪枝可能把已删除节点"清"掉，索引尺寸只增不减。

## 一、发展趋势

第一，向量检索从"能不能查到"进入"删得掉吗"。RAG 与 Agent 记忆让向量库变成长期存储，删除请求（用户撤回、数据保留到期、错误入库）必须落到索引层，而不只是数据库行。

第二，过滤检索成为主路径。多租户、权限、时间窗、类型过滤都在查询时叠加；过滤比例越高，ANN 索引的图遍历越容易走进"全是被过滤节点"的区域，召回骤降。

第三，索引维护从"建一次"变成"持续重建"。段合并、墓碑清理、参数调优（`m`、`ef_construction`、`ef_search`）都需要周期性的全量或增量重建；重建期间的双写与切换成为新的运维面。

第四，合规把"删除是否生效"变成可证明性问题：向量是数据的派生副本，删除原文不等于删除向量；向量又不可逆，无法用"再算一次"验证。

## 二、技术现状

**删除是标记，不是移除。** 主流实现把删除记为 tombstone，查询时跳过；物理回收依赖段合并或重建。删除后的索引仍然占空间、仍然参与图遍历，只是在结果里被过滤。

**图修补会破坏结构。** HNSW 删除节点时要修补邻居连接；修补策略（重连到谁的邻居、是否双向）不同，召回与连通性都不同；某些实现干脆"只标记不修补"，靠重建兜底。

**过滤与 ANN 的顺序决定召回。** 先 ANN 再过滤（post-filter）在过滤率高时会返回不足 k 条或低质结果；先过滤再 ANN（pre-filter）召回高但可能退化为暴力扫描；折中是"分区/分片 + 每片内 ANN"。

**参数不是一次调好的。** `ef_search` 提高召回也提高延迟；`m` 提高连通性也提高内存；数据分布变化（新租户、新语言、新模态）会让原参数失效。

**删除验证没有"反向查询"。** 关系库可以 `SELECT` 验证行没了；向量库无法证明"这个向量不在索引里"，只能证明"查询不返回它"——而查询本身有召回率。

**重建是高风险变更。** 全量重建需要源数据、算力与时间；蓝绿索引需要双写与原子切换；切换后旧索引的删除、备份与回滚都要定义。

**向量索引也会膨胀。** HNSW 的图边、墓碑、重复写入的旧版本都会留在段里；段合并只回收一部分；当墓碑比例升高到一定程度，查询延迟与召回通常同时恶化——这是重建的硬触发之一，而不是"等存储满了再说"。

## 三、技术竞争力

| 方案/能力 | 删除语义 | 过滤支持 | 主要代价 |
|---|---|---|---|
| pgvector HNSW | 标记 + 重建 | 后过滤为主 | 召回随过滤率下降 |
| pgvector IVFFlat | 标记 + 重建 | 后过滤 | 列表数/探针调参 |
| Lucene/Elastic HNSW | 段删除 + 合并 | 过滤+图遍历 | 合并期资源 |
| 专用向量库（托管） | 标记 + 压缩 | 原生过滤 | 口径不透明 |
| 分片 + 每片 ANN | 分片内标记 | 分片键过滤 | 路由与热点 |
| 暴力精确检索 | 真删除 | 任意过滤 | 延迟与成本 |

**判读**：可采购的是"索引 + 重建 + 监控"；不可采购的是"这个向量是否真的不在索引里、过滤后召回还剩多少、重建期间双写是否一致"。

**本期反转**：我们一直把向量删除当成数据库 `DELETE` 的延伸。实际上它是**索引重建的触发器**：标记删除只改变"返回不返回"，不改变"占不占空间、参不参与遍历、修不修补图"。**删除的验收不是"查不到"，而是"重建后索引里没有它，且重建前后的召回可比"。**

## 四、技术挑战

**挑战一：删除的可证明性。** 没有反向查询，只能靠"删除后查询不返回 + 审计日志 + 重建记录"三件套；对合规而言，这比关系库弱，也比对象存储的"删除即不可读"弱。

**挑战二：过滤召回的测量。** 过滤率、过滤字段的选择性、过滤与 ANN 的顺序，都会改变 recall；上线前要在真实过滤分布上测，而不是在无过滤基准上测。

**挑战三：重建的双写与切换。** 重建期间的新写入要同时进新旧索引；切换要原子；切换后旧索引要保留一段时间用于回滚。

**挑战四：墓碑的累积。** 高频删除/更新会让墓碑比例升高，查询变慢、召回变差；需要按墓碑比例触发重建，而不是按时间。

**挑战五：多租户的隔离。** 共享索引 + 过滤是最省资源的做法，但也是召回与越权风险最高的做法；按租户分片能隔离，但小租户的索引碎片化。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①删除语义（标记/物理/重建）；②过滤召回测量；③重建触发条件（墓碑比例、召回下降）；④双写与原子切换；⑤删除审计与合规证据；⑥多租户隔离策略。

**用户旅程**：用户撤回一条记忆 → 应用删除数据库行 → 向量库标记删除 → 查询不再返回，但索引仍占空间 → 墓碑比例超过阈值触发重建 → 重建期间双写、切换后旧索引保留 7 天 → 审计记录"删除时间、重建时间、重建后查询验证"。

**90 天实现方案**：0–30 天，盘点向量索引的删除路径与墓碑比例，建立过滤召回基线；31–60 天，实现按墓碑比例触发的重建与双写切换，补删除审计；61–90 天，把"过滤后召回"纳入发布门禁，定义多租户隔离策略与回滚演练。

**第 281 个市场空白（五项）**：删除语义台账；过滤召回测量；重建触发条件；双写切换一致性；删除合规证据。

**`ann_delete.*`／`recall_under_filter.*` 第 248 次无人提字段族**：所有向量库都报"支持删除"，没有一个字段报"删除是标记还是物理、墓碑比例多少、过滤后召回多少、重建后是否验证过、删除能否被证明"。
