- 本期主题：连接面／连接池耗尽与连接排队——每层都“还没满”，合起来已经满了

## 题眼

2026-06-05 一份 PgBouncer 场景记录：约 30 个应用 Pod，各自应用层池 20 条连接，直连 Postgres，`30 × 20 = 600`；数据库 `max_connections` 是 **200**。峰值时应用报 pool timeout、数据库报 `FATAL: sorry, too many clients already`。数据库 CPU 并不高，只是**连接槽用完了**；每连接仍占 5–10 MB 服务端内存与调度开销。把 `max_connections` 提到 1000“修好”了——直到下一次。

2026-09-18 Inngest 复盘：一次来自 Vercel Marketplace 集成的账号删除级联，把主库阻塞到耗尽 PgBouncer。**16:18–16:42 UTC** 两个 PgBouncer 实例同时拒绝新连接，平台多数服务够不到数据库，运行调度与事件确认停摆；**17:50–18:12** 缓解措施上线期间出现第二波、影响面更大。

另一条线：tinyfish 的记录里，前端 3 次重试、网关 3 次、服务 3 次，一次失败认证最终变成 **64 次**数据库尝试，错误率每 30 秒翻倍（4%→8%→16%→32%），而**每一层都报告自己的重试逻辑正常**。

## 一、发展趋势

连接正在从“基础设施细节”变成“跨团队共享的有限资源”，原因有三。

**第一，池化层变多了。** 早期只有应用池和数据库直连；现在典型链路是应用池 → 池化器（PgBouncer／RDS Proxy／Supabase Pooler）→ 数据库槽位 → 上游 SaaS 限额。每一层都有自己的上限、自己的排队、自己的超时，且**互相不知道对方的存在**。

**第二，池化语义开始影响正确性。** 2026-02 的 PgBouncer 邮件列表里，用户报告事务池模式下 prepared statements 报 `bind message has 43 result formats but query has 47 columns` 与 `unnamed prepared statement does not exist`——事务池会把语句的会话上下文借给别的连接。他们不能改应用代码，也不能切会话池，因为连接数太高。**连接复用省下的资源，用会话语义付账。**

**第三，连接风暴已经是独立的故障类型。** ScyllaDB 2026-07-01 的文章标题就是“在连接风暴中把 p99 降 1000 倍”：一次部署或重启让所有客户端同时重连，数据库在“从 TCP SYN 到可查询”的每个阶段被压垮。他们的解法是准入控制：限流、缓存、把不可避免的 CPU 工作让出、按服务级隔离。**连接建立本身被当成负载来治理，而不是当成免费动作。**

## 二、技术现状

**应用侧。** HikariCP 的 `connectionTimeout` 默认 30 秒，池满时请求排队而不是快速失败；很多框架把“排队 30 秒后超时”记成一次普通错误，重试层再把它放大。Firecrawl 2026-06-10 的 PR 直接把索引库的每进程池缩小到 6，理由写得很清楚：事务池会复用服务端连接，**每进程的大池买不到吞吐，只会吃掉全局 `max_client_conn`**。

**池化器侧。** PgBouncer 的 `max_client_conn` 是全局上限，与每个应用自己的池上限无关；两边都“留了余量”，合起来却超卖。Inngest 的复盘说明，池化器自己也可能成为单点：两个实例同时拒绝连接时，应用看到的不是“数据库慢”，而是“连不上”。

**数据库侧。** 提高 `max_connections` 是最常见的“修复”，但它把内存与调度开销一起抬高，且不改变排队结构；RavenClaude 的场景明确写了，这是把问题推到下一次峰值。

**可观测性侧。** 仪表通常报“活跃连接数／池大小／等待时间”，但很少报**每个租户、每个查询类型、每个重试来源**占了多少槽位；于是事故复盘只能看到总量满，看不到谁把槽位吃掉了。

**AI 运维场景的特殊性。** Agent 的每次工具调用可能各自建连、各自重试；一个“查一下订单状态”的任务在扇出后可能是几十条连接。连接池按进程配置，而 Agent 的并发是按任务动态生成的——**配置是静态的，负载是动态的**。

## 三、技术竞争力

| 方案 | 连接复用 | 排队可见性 | 语义保真 | 多租户计量 | 故障隔离 | 运维负担 |
|---|---|---|---|---|---|---|
| 应用内池（HikariCP 等） | 进程内复用 | 有等待计数，无来源 | 完整 | 无 | 进程级 | 低，但易超卖 |
| PgBouncer 事务池 | 跨进程复用 | 有全局队列 | **破坏会话语义** | 弱 | 实例级 | 中 |
| 云托管池化（RDS Proxy 等） | 托管复用 | 指标有限 | 基本保真 | 弱 | 托管 | 低 |
| 数据库代理／网关 | 可做路由 | 可加标签 | 取决于实现 | 可做 | 可做 | 高 |
| 服务网格连接池 | 连接级 | 有指标 | 保真 | 弱 | 强 | 中高 |
| Agent 运行时按任务建连 | 无 | 无 | 保真 | 无 | 弱 | 高 |

判读：可采购的部分高度成熟——池、池化器、代理、网格、托管服务都能把连接数压下来。缺口在**计量与归属**：没有一层能回答“这 200 个槽位里，多少属于租户 A、多少是重试放大、多少是长事务占着不放”。事务池还额外用会话语义换复用，这个代价通常不在选型表里。

本期反转：我们把连接池当“性能优化”，默认池越大越稳。实际池是**配额**：每层都有自己的配额，层与层之间不对话；应用池调大只会在池化器处排队，池化器调大只会在数据库处排队，数据库调大只是把内存压力推后。**连接问题的根因不是池太小，是没有人对“总槽位”负责。**

判词：「连接池／池化器／代理／服务网格／托管数据库／连接监控」全部可采购，「这 200 个槽位此刻被谁占着、排队的是哪些租户、重试放大了几倍、事务池借走了谁的会话、下一次峰值前谁会先满」不可采购。

## 四、技术挑战

**其一，四层上限不可通约。** 应用池按进程、池化器按全局、数据库按槽位、SaaS 按配额，四种单位无法直接相加；任何一层单独扩容都不改变瓶颈位置。

**其二，会话语义与复用冲突。** 事务池下 prepared statements、临时表、`SET`、 advisory lock 都可能跨会话泄漏；要保语义就得用会话池，而会话池正是连接数压不下来的原因。

**其三，重试放大没有账本。** 每层都“只重试 3 次”，乘起来是 64 次；每层都认为自己是正常的，因为放大发生在层与层之间。

**其四，长事务与慢查询占槽。** 一个被遗忘的事务可以把槽位占到超时；连接池看到的是“活跃”，看不到“在等锁”。

**其五，Agent 的并发是动态的。** 静态池配置对动态扇出天然不匹配；按任务建连会把压力直接转给数据库。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台团队：需要一个**总槽位账本**，把应用池、池化器、数据库、SaaS 配额换算到同一单位（可用槽位·秒），并标出当前占用者。
- 租户团队：需要看到自己的排队时间与拒绝率，而不是只看全局错误率。
- 事故指挥：需要一条“谁在什么时候把槽位吃满”的时间线，包含重试放大与长事务。
- Agent 平台：需要按任务声明连接预算，并在扇出前做准入，而不是扇出后重试。

**用户旅程（一次连接耗尽事故）。**

1. 峰值到来，应用池先满，请求开始排队；仪表显示“池使用率 100%”，但没人知道是哪个租户。
2. 30 秒后 `connectionTimeout` 触发，应用层重试；重试把压力翻倍。
3. 池化器 `max_client_conn` 达到上限，开始拒绝新连接；此时数据库可能并不忙。
4. 错误率陡增，告警触发；值班先看数据库 CPU，发现正常，误判为“应用 bug”。
5. 有人调大 `max_connections`，压力短暂缓解；长事务仍占着槽位，第二波在缓解措施上线时到来。
6. 复盘时只能给出“连接数超限”，给不出“谁占的、重试放大了多少、哪条长事务没释放”。

**实现方案（90 天）。**

- 第 1–2 周：盘点四层上限，画出“应用池→池化器→数据库→SaaS 配额”的换算表；把每层的单位、默认值、当前值写进一张配置表。
- 第 3–4 周：在应用侧给每次取连接打标签（租户、任务 ID、重试序号），把等待时间与拒绝计数上报；池化器开启 `max_client_conn` 与队列深度指标。
- 第 5–6 周：建立“总槽位账本”看板：当前占用、排队、拒绝、按租户与重试来源分解；设置“槽位占用 >80% 且排队 >5 秒”的早期告警。
- 第 7–8 周：重试治理——全链路统一重试预算（总尝试次数而非每层次数），对“池满”类错误快速失败并降级，不做指数退避重试。
- 第 9–10 周：长事务与慢查询治理——识别占槽超过阈值的事务，设置 `idle_in_transaction_session_timeout`，对 Agent 工具调用加语句级超时。
- 第 11–12 周：Agent 连接预算——按任务声明最大连接数，扇出前准入；接入 kill switch，可在连接风暴时按租户降级。
- 第 13 周：演练——模拟“30 Pod 同时重连”和“长事务占满槽位”，验证账本能定位到租户与重试来源，而不是只报“满了”。

**验收标准。** 任意一次连接耗尽告警，10 分钟内能回答：哪一层先满、被谁占、重试放大了几倍、哪条长事务未释放、下一个会满的是哪层。

**第 214 个市场空白（五项）**：跨层槽位账本；按租户/任务/重试序号的连接归属；事务池语义损失的显式声明；连接预算的准入控制；连接风暴演练与恢复判据。

**`pool.*`／`connection_slot.*` 第 181 次无人提字段族**：`pool.wait_ms`、`pool.reject_total`、`connection.slot_owner`、`connection.retry_depth`、`connection.tx_age_s` 在本期引用的所有方案里均无统一字段；各家只报池内计数。

**本地 173／173-kb 连续第 169 期成组启用**（何伟 02）：连接池问题在本地知识库里对应“资源边界”条目，强调“上限不是容量，是责任边界”；本期把它从单机池扩展到四层槽位。
