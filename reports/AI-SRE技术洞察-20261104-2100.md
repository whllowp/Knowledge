# AI-SRE 技术洞察 · 第 75 期

**2026-11-04 21:00｜主题：冻结面（封网面）——封网封的是发布，不是变更**

> 本期主线：变更冻结作为一等运维对象（第六十六条主线）。与前 74 期的划界：第 54 期配置面管"期望态漂移"，本期管"某段时间内允不允许改"这一时间谓词；第 42 期自治等级管"谁有资格做"，本期管"什么时候谁都不能做，例外除外"；第 20 期演练面管"制造故障"，本期管"禁改"，两者恰好互为镜像——冻结期是唯一只能练、不能改的窗口。

---

## 一、发展趋势

**1. 冻结日历正在变成四段，而行业只治理第二段**

阿里大于 11-02 更新的双十一保障公告给出一份可直接对照的时间表：一峰封版自 10-14（智能客服、小程序）/10-17（商家工具）18:00 起至 10-21 10:00，二峰封网 11-09 10:00 至 11-10 10:00；而扩容截止卡在一峰 10-19 16:00、二峰 11-08 16:00——比封网开始还早一天。海外同构：某压测厂商给出的 2026 黑五日历是 11-13 全冻（代码、配置、标签、模板一并冻）、11-23 至 11-30 峰值周仅例外、12-01 起分批解冻。

把这些时间点排成序列会发现，一次封网其实是四段时间：**冲刺（封网前）→ 封网 → 峰值例外 → 解冻**。平台公告只治理第三段，风险却主要产生在第一段（抢发）和第四段（集中兑付）。冻结的治理对象因此被系统性缩小。

**2. 冻结从组织纪律下沉为策略谓词**

Google Cloud Deploy 已把冻结写成 `rolloutRestriction` 规则：IANA 时区、`oneTimeWindows`/`weeklyWindows`、可限制 ADVANCE/APPROVE/CREATE/RETRY_JOB/ROLLBACK 等八类动作，并且有一个关键维度 `invokers: USER | DEPLOY_AUTOMATION`（不填默认两者都管）。AWS 侧把冻结退化为日历状态查询：SSM Change Calendar 以 iCalendar 2.0 存事件，DEFAULT_OPEN/DEFAULT_CLOSED 两态，自动化里用 `GetCalendarState` 断言（配额 10 QPS）；同时 Change Manager 自 2025-11-07 起不再向新客户开放。Argo CD 用 cron 表达的 sync windows，deny 覆盖 allow，另有 `manualSync` / `syncOverrun` 两个逃生阀。

判读：**审批型变更管理产品在退场，谓词型冻结在进场**。冻结正变成一条任何自动化都能查询的布尔值——但今天查询它的仍然只有部署系统。

**3. 业务侧在同一个窗口里大规模上线"会写数据"的智能体**

淘宝"千问 Go!"打通 40 亿件商品库；京东"东东"覆盖选品、比价、凑单、售后；抖音豆包"帮你选"直连商城与直播间；淘天"店小蜜"从话术机器人升级为可查库存、改地址、发券、处理退款的执行型客服，特步、小米接入后转人工率分别下降 55%、45%（11-02、11-04 报道）。

判读：封网期人类发布数趋零，而**能发起写操作的智能体密度在同一个窗口达到全年峰值**。冻结假设的"变更是少量、可枚举、可签字"的前提，在业务侧已经不成立。

## 二、技术现状

**（1）三层现状：日历可查、审批可签、供应商无冻结**

- 日历层（可查询）：AWS Change Calendar、Cloud Deploy deploy policy、Argo CD sync windows。
- 审批层（可签字）：聚石塔"变更中心"的紧急发布申请；AWS Change Manager 的 change freeze approver。
- 供应商层（不存在）：模型权重、路由、CDN、第三方 Agent 平台都没有"你的封网"概念。冻结半径等于组织边界，而依赖在边界外。

**（2）冻结的计量单位是"发布"，风险的单位是"写入"**

封网公告的措辞是"禁止应用修改、更新与发布、云资源弹性升级"——一个以部署事件为单位的枚举。而智能体的每次工具调用都是一次状态变更：不进 pipeline、不生成 release、不需要审批，也不出现在任何冻结报表里。于是"封网期间零发布"和"封网期间写入量创新高"可以同时为真，且两者都能拿出证据。这是本期最核心的机制判断：**冻结不是失效了，是分母换了而报表没换**。

**（3）invoker 二维在智能体面前失效**

`invokers` 只区分 USER 与 DEPLOY_AUTOMATION，默认两者都管。智能体带着人的令牌调 API，在策略看来就是 USER；它若挂在 CI 里，又长得像 DEPLOY_AUTOMATION；它两者都不是——它是"以人的身份、行使自动化的频率"的第三类。第三类没有名字，于是没有策略分支，只能落到默认值上（推断，基于字段语义）。第 55 期讲"谁在动手"，这里给出它的时间谓词版本：**冻结策略按身份分叉，而身份在 agent 时代已经不可靠**。

**（4）冻结顺手把"恢复"也冻了**

Cloud Deploy 的可限制动作里包含 ROLLBACK 与 TERMINATE_JOBRUN。把"冻结改变"实现成"冻结动作"，就会连回滚、重试、终止一起冻掉——封网期最不该限制的三个动作恰好首当其冲。

**（5）冻结锁死自适应，而峰值恰恰最需要自适应**

阿里公告把"云资源弹性升级"写进禁令，扩容截止早于封网一天。这等于峰值期容量被冻结在预测值上；而 2026 的流量形状最不可预测：购物智能体的请求几乎无缓存复用，每轮对话都打到商品库与推荐服务（ManageEngine 在 Q4 冻结复盘中直接把"AI 购物智能体"列为 2026 冻结计划完全没算的流量形状）。**冻结把系统从自适应模式切回固定容量模式，这个切换本身是一次未被记录的重大变更。**

**（6）解冻不是恢复，是兑付**

Charity Majors 2019 年的判断被反复引用：她职业生涯最严重的几次故障都发生在假期封网之后。机制有二：批量变更把 N 个小风险洗成 1 个大风险，排障时"爆炸半径"包含整批提交；封网期取消了日常发布带来的重启周期，被重启掩盖的潜伏缺陷（内存泄漏、连接泄漏）静默累积，在解冻后第一次发布时集中爆发。冻结没有消除风险，它把风险**贴现**了。

**（7）破窗通道的形状**

2025-12-05 Cloudflare 为紧急防护一个新披露漏洞，走的正是"不逐步发布、数秒内推全量"的快路径，约 28% 的 HTTP 流量受影响约 25 分钟。**例外通道因此承载了 100% 的变更风险，且是全校验链最短的一条路**——审批被设计成刹车，运行时却是油门。

## 三、技术竞争力

| 方案 | 冻结表达 | 可拦动作 | 调用者区分 | 破窗通道 | 解冻编排 | agent 写入受控 |
|---|---|---|---|---|---|---|
| Google Cloud Deploy | 策略 YAML + 时区/周期窗 | 8 类 rollout 动作（含回滚） | 二分：USER / 部署自动化 | 改策略或走例外审批 | 无 | 否（第三类无分支） |
| AWS SSM Change Calendar | iCalendar 2.0 事件，OPEN/CLOSED | 取决于调用方是否断言 | 无 | 关闭日历或人工放行 | 无 | 否（需自建断言） |
| Argo CD Sync Windows | cron + duration，deny 优先 | 仅 sync 层 | 无（手动/自动靠 manualSync） | manualSync / syncOverrun | 无 | 否（只覆盖 GitOps 路径） |
| 阿里聚石塔（封网+变更中心） | 公告 + 封版窗口 | 发布、更新、弹性升级 | 无（人工审批） | 变更中心紧急申请 | 公告式分批 | 否 |
| 国内云厂商通用（腾讯/火山等） | 公告 + 工单 + 值守 | 以平台策略为准，未见公开机器可读冻结接口 | 无 | 人工审批 | 人工分批 | 否（检索截至 2026-11 未见产品化） |
| 事件平台（PagerDuty 类） | 冻结通知、值班标注 | 无执行权 | — | — | 提醒 | 否 |
| Agent 框架（Agents SDK / Claude 权限） | 无时间维度 | 工具级 allow/deny | 有主体、无时间 | 改配置 | 无 | 部分（动作级，非时间级） |

判读三点：**其一**，最完整的三个方案都在"部署"这一层，天然看不见 API 写入、配置热更、知识库重建这类不经过 deployment 的变更；**其二**，唯一具备"按调用者分叉"能力的 Cloud Deploy，分叉维度恰好被智能体打穿；**其三**，全表七列中"解冻编排"整列为空——没有一家提供解冻排序器，解冻至今是人工分批。这与第 74 期的"部分修复无尺可量"同构：**风险的前半段（冻结）已产品化，后半段（解冻）仍是手工艺**。

## 四、技术挑战

**① 冻结覆盖率无法计算（第二十九个市场空白）**。覆盖率 = 受冻结约束的状态改变类型 ÷ 实际改变系统状态的类型。分母不可枚举（同第 66 期删除覆盖率），于是"冻结已生效"只能自证。四个本应存在而无一内建的指标：冻结覆盖率、冻结期写入密度（写入数/分钟 vs 基线）、破窗率（例外变更数/冻结期变更总数）、解冻洪峰幅度（解冻 72h 内变更数/月均）。

**② 冻结不可判**。智能体在动手前无法查询"现在能不能写"：`GetCalendarState` 有 10 QPS 配额，OTel 没有 `change.freeze.state` 字段，MCP 工具描述里没有冻结语义。结果是 agent 只能靠系统提示词里的一句话"当前处于封网期"，而这既不可审计也不可验证。

**③ 冻结期 RCA 先验失效**。"最近变更"是根因分析最强的先验，几乎所有 AI RCA 都在吃这个先验。封网三周后，"最近变更"指向三周前，先验从强信号退化为噪声；而封网期的变更恰恰是例外通道里的高风险变更。**冻结期是 RCA 精度最低、而事故代价最高的窗口**，这个组合没有任何度量覆盖。

**④ 解冻洪峰无编排**。冻结债务在解冻后 24-72 小时集中兑付，缺少按风险排序、按依赖分批、按错误预算设阈的调度器。行业默认做法是"人肉分批"，与第 40 期并发面揭示的惊群同源。

**⑤ 冻结半径小于依赖半径**。模型供应商不发封网公告；CDN、支付、第三方 Agent 平台各有一套冻结日历，且互不知情（Evaluat 的实操建议里"别忘供应商的冻结日历"仍是人工核对项）。

## 五、展望与建议

**把冻结写成状态，而不是写成公告。** 三步落地：一是把冻结做成可查询谓词（`change.freeze.state`、`change.window.id`、`change.exception.id`），网关与工具层在每次写入前断言；二是 invoker 扩为三类（人 / 部署自动化 / 代理），代理默认最严；三是冻结对象从"动作名"改为"状态改变"，回滚、缩容、只读永久豁免。

**把解冻当成一次发布来设计。** 需要解冻排序器：按风险分档（数据迁移 > 配置 > 代码）、按依赖拓扑分批、设"解冻预算"（类比错误预算，超额自动暂停），并对解冻后 72 小时提高监控灵敏度与回滚就绪抽查。

**把冻结期当成演练窗口，而不是空窗。** 不能改就只能练：冻结期是全年唯一可以合法做破坏性演练、容量拐点探测与恢复演练的时段，但很少有团队把它排进演练日历。建议把"封网期演练"写进变更流程，与第 56 期注入目录、第 20 期演练证据链合流。

**采购侧加两条**：供应商是否提供机器可读的冻结接口与例外审计导出；重大活动期间供应商自身的变更冻结承诺（含模型权重与路由）。

> 一句话总结：封网从来不是"让系统不变"，而是"让变更变得可见"。当变更的执行者从人换成智能体，可见性就先塌了——本期补的是这一块。
