# AI-SRE 技术洞察 · 第 31 期

**主题：接口面运维——智能体的运维上限，取决于系统给它留了几扇门**

2026-11-02 15:00｜覆盖窗口：2026-10-26 — 2026-11-02｜第二十二条主线

## 一、发展趋势

前 30 期的主线几乎都在"智能体这一侧"：怎么治理它、怎么评它、怎么记、怎么路由、怎么结算。本期换到另一侧——被运维的系统本身。有一个反复出现却少被命名的经验事实：同一个模型，接不同的接口，能力差一个量级。开源 Kubernetes 面板 Radar 给出了最直白的一刀——内置 MCP 把拓扑、健康、事件、日志预处理后交给模型，同一模型定位故障比裸 kubectl 快 3 倍。模型没变，门变了。

三个方向正在合流。**其一，接口从"人机界面"变成"机器界面"。** 快手在 75 位架构师的研讨中把"系统 CLI 化"打到 95 分，与"多 Agent 打通"并列最高，高于"模型评测与选型"的 88 分；其架构蓝图把"工具层（Skill / CLI / MCP）"单列为五层之一，分工是：CLI 面向本地执行与自动化、MCP 跨系统能力调用、Skill 固化特定工作流、A2A 负责编队协同。改造前后的表述极准——"AI 像爬虫爬接口，失败率高"→"CLI 标准化调用，覆盖率 >99%"。接口面不是给智能体加权限，而是把"爬"换成"走门"。

**其二，接口进入平台治理。** Google 10-28 开放 Connected Apps 平台，明确路由由 server instructions 与 tool descriptions 决定，并明文禁止"用过宽或欺骗性能力描述诱使模型选中自己"。描述第一次同时成为竞争手段与合规对象——这意味着工具描述的质量不再是工程细节，而是分发权。

**其三，协议层开始为接口面让路。** MCP 2026-07-28 版把协议核心改为无状态——一次工具调用一个请求，会话管理从连接里剥离。接口清单因此从"连接内的私有状态"变成"可分发的公共资源"，网关才有条件只按方法路由、按调用计费，而不必解析整个 JSON 体。

## 二、技术现状

### 2.1 云厂商：把运维能力做成"命令面"

**Azure MCP Server 3.0** 于 10-29 标记 GA（3.0.0 版本 10-12 落地，历经 50 轮 beta）。值得记的不是"能连 Azure"，而是三件事：① 新增 **SRE Agent toolset，一次给 55 条命令**；② Terraform toolset 把"能看"升级为"提得出流水线能接受的改"——aztfexport 导出存量资源、引用 Azure Verified Modules、conftest 先校验 plan 再 apply；③ 结构化输出需显式开 `--structured-output-mode`，默认仍是纯文本，说明厂商为兼容性主动付了代价。安全上把护栏前移到接口层：新建存储账户默认关闭 Shared Key、Event Hubs 关本地认证、数据面与管理面全量 anti-SSRF、遥测不再记录参数值。

**阿里**走"能力外供"。10 月 OpenAgent 发布 Skill 与 CLI，可被其他智能体调用，同时上架 Skills 门户、GitHub（alibabacloud-aiops-skills）、skills.sh、ClawHub；9 月已把 RCA 与定位路由给 STAROps、把网络问题路由给 NAPal，HITL 审批仅对白名单开放。更值得记的是 OSS Agent 的边界处理：删除类、生命周期、WORM、数据复制、覆盖写等高危动作**暂不支持直接执行，只给控制台跳转链接**（10-28 起按 Credits 商业化，每月 1500 免费额度）。

**腾讯**把接口面开在"可试错"上。10-30 披露 Agent 创建的 TDSQL-C 实例日均超 2 万、增速 80 倍、活跃破 100 万；支撑它的是数据库分支、独立只读计算资源，以及 Serverless 从 0.25 CU 扩到 32 CU 用 75 秒、负载结束 10 秒回落。Mynet 的自然语言查询走独立只读资源——不是给 Agent 更大权限，而是给它一个搞不坏生产的地方。

### 2.2 学术界给了一记反直觉的证伪

arXiv:2609.11999（Mak 等）在 174 个 TheAgentCompany 任务与 480 个 APEX-Agents 任务上，比较三类接口：裸 shell、类型化工具目录、受限程序化调用（Opus-4.8 与 GPT-5.5 双模型）。结论对当下"把一切包成 MCP 工具"的做法不利：**只给 bash 反而全面胜出**——TAC 高 21.8–24.5pp，APEX 高 4.8–7.4pp，每任务成本 $0.37 对目录方案 $1.20；在 shell 之上再加一层目录，收益 −0.6pp（置信区间跨零，等于零）；再加一层"智能体自建工具库"，仍是 −1.6pp。

原因在**组合**：94.3%（TAC）/ 96.5%（APEX）的 shell 调用含管道、逻辑符、命令替换或控制流标记。真实运维动作本来就是组合的（`get | grep | jq`），工具目录只能靠增加调用次数去逼近，中位调用数因此从 14.0 压到 12.8、从 13.0 压到 7.5，完全重复调用从 16.2% 掉到 0.3%。代价也清楚：受限程序化调用虽省下 97.6k 未缓存输入 token，工具调用成功率只有 **65.2%**，而类型化目录是 **93.3%**。

### 2.3 失败归因开始落到"边"上

Scale AI 的失败分类学（41 种模式，三族：用户 / Harness / 环境）给出一个关键抽象：每个失败由**交互边 + 责任方**唯一确定。同一个"调错参数"，可能是 schema 没写清（Harness 责任）、模型不懂 JSON Schema（模型责任），也可能是上游 API 文档过期（第三方责任）——三种修复路径完全不同。GPT-5.5 作评委在族级一致性 κ=0.76，意味着这套归因可以自动化，不必全靠人工标注。

**判读**：竞争重心已从"工具有多少"转向"门开得多准"。海外厂商在**接口治理**上领先——AWS 的"对抗性孪生"是本期唯一把"预期被拒绝"写成发布门禁的方案，Azure 把护栏塞进接口层；国内厂商在**可逆动作空间**上更实用——阿里"不开口只跳转"、腾讯"分支 + 只读 + 秒级弹性"，都不追求动作更全，而追求搞坏了不心疼。开源方案赢在**上下文预处理**这一项，且性价比最高。最大的分歧点是：所有厂商都在"目录化"，而唯一的对照实验说表达力比整洁度更值钱。

## 四、技术挑战

1. **表达力与可治理性互斥。** shell 强但不可枚举、不可审计、不可限流；目录可枚举却输了 24.6pp。折中的"受限程序化调用"两边不占：省 token 但成功率最低（65.2%）。目前没有一个方案同时给出"可组合 + 可审计 + 高成功率"。
2. **"可放弃"被误当"可回滚"。** 跳转控制台、分支、只读副本、沙箱快照，四者的共同点只是"不污染主库/主集群"，外部副作用（已发出的通知、已扣的款、已开的工单）一件都没撤回。第 28 期的"三态结算"在这里仍然缺位。
3. **描述即接口，也即攻击面。** 描述决定路由（Google 已承认），于是描述既是竞争位（SEO 化），也是投毒位（第 23 期）。而 MCP 规范把 `destructiveHint` 默认设为 true、`readOnlyHint` 默认 false——默认值站在保守一侧，但绝大多数 server 并不显式覆写。
4. **接口清单的时效没人管。** `tools/list` 有了 `ttlMs`，却没人把"接口漂移"和"Skill/CLI 版本"与模型版本联合 pin。第 23 期的 pin-and-diff 只覆盖了"装进来的工具"，没覆盖"系统自己长出来的命令"。
5. **归因落不到边。** 生产遥测只记"工具调用失败"，不记"是 schema 歧义、文档过期还是模型不会用"。没有边级标注，41 种失败模式就退化成一个成功率数字。
6. **存量系统没有门。** Postman 2025 年对 5,700+ 开发者的调查显示，只有 24.3% 会"为智能体设计 API"；而 Gartner 预计 2026 年底 40% 的企业应用将内含任务型智能体（2025 年不足 5%）。门装得比人来得慢。

## 五、展望与建议

**第一，把接口面当资产盘点，而不是当权限清单。** 对每个 SRE 动作标注三轴：可逆性（可撤销/可放弃/不可逆）、表达力（单点/可组合）、可枚举性（静态目录/动态命令）。三轴决定它该走 CLI、走 MCP 还是只给跳转链接。快手的"工具层"单列一层，正是这个意思。

**第二，读写分道。** 读走 shell（要组合、要探索、要便宜），写走类型化工具（要枚举、要审计、要审批）。"全目录化"是用写侧的纪律去惩罚读侧的效率——这是本期最重要的工程结论，也是最容易被厂商叙事带偏的地方。

**第三，写动作三件套：dry-run、幂等键、影响面声明。** 缺 dry-run 的动作默认降级为"只给跳转"，阿里的做法应成为默认值而非特例。腾讯的分支与只读资源说明：给智能体一个能搞坏的地方，比给它更多权限更有效。

**第四，把负测试写进发布门禁。** AWS 的"批准模型应成功、未批准模型应被拒，缺拒绝即构建失败"是目前最可复制的一条。同理，每个只读工具都应有一条"越权调用必被拒"的断言。

**第五，上下文预处理优先级高于加工具。** Radar 的 3 倍与"描述质量使任务完成时间降 40%"是同一条规律的两面：模型不缺动作，缺的是被整理过的事实。把拓扑、变更、依赖合并进一次调用，比新增十个工具更划算。
