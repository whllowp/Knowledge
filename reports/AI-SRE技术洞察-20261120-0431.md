# AI-SRE 技术洞察（第 295 期）

**生成时间**：2026-11-20 04:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-20
**本期主题**：视窗面／工具输出的截断与采样——Agent 读的是窗口，不是数据；它答得越确定，越没人问它看到了多少

## 题眼

2026-11-15，一篇题为《Same Simulation, Different Evidence》的论文把“工具输出到底值不值”拆成三段：数据是否被**构建**出来（build）、是否**到达** Agent（exposure）、Agent 是否据此**答对**（closure）；每个阶段失败对应不同补救。它的头条数字很冷静：把工具输出改为内联（inline）后，Claude Opus 4.6、Sonnet 4.6、GPT-5.4 的准确率变化只有 −0.6 到 +0.2 个百分点，置信区间跨零——说明“给 Agent 看工具输出”本身不是答案，关键是**它看到的是哪一段**。另一组数字更刺眼：没有模拟器时，所有模型都过不了 46.2%，而多数类基线是 32.9%——题目要求真正使用工具，可工具给的东西经常不够用。

同月，一个 MCP 元数据包的文档写得很实在：响应按预算阶梯渲染，**没有一档放得下时，就把最便宜的渲染截断并追加显式 cut marker**；预算还有 MinBudget/MaxBudget 的夹紧逻辑（mcpmeta，2026-09-27）。再往前，Kubernetes 文档里 `kubectl logs --limit-bytes=500` 只返回前 500 字节，超限部分直接不返回（2026-09-23）；Elasticsearch 的 `from + size` 超过 `index.max_result_window`（默认 10000）会报错——这是少数**显式失败**的截断（2026-10-24 考古、09-18 实战文）。2026-03 的一份 Agent 配置文档则把“上下文压力”做成进度条：到压缩阈值的 60% 提示、85% 警告，然后触发压缩，把旧消息摘要掉。

三件事拼起来：截断无处不在，显式截断是少数，而**截断之后 Agent 仍然自信作答**是常态。

## 一、发展趋势

1. **截断从异常变成常态**。日志、搜索结果、工具响应、上下文窗口都有上限；Agent 的每一次“读”都是一次带预算的采样，而不是一次完整读取。

2. **显式截断开始有规范**。MCP 预算包会在裁剪后追加 cut marker，并把预算夹在 Min/Max 之间；这比“悄悄少返回几行”进步，但仍要求调用方真的去读那个标记。

3. **上下文压缩成为默认动作**。压缩阈值、压力条、摘要触发被产品化；压缩本质是**有损重写**，丢哪些字段由策略决定，不由事实决定。

4. **“证据暴露率”开始被单独测量**。论文把 build／exposure／closure 分开，意味着“工具返回了”和“Agent 看到了”和“Agent 用上了”是三件事；SRE 的日志平台只保证第一件。

## 二、技术现状

**第一层：字节上限。** `kubectl logs --limit-bytes` 截的是**前** N 字节还是后 N 字节、是否包含最关键的启动错误，取决于实现；Agent 若只看尾部，就会错过“第一次失败”。

**第二层：结果窗口。** Elasticsearch 的 `from + size` 有 10000 的硬顶，超出直接报错；但大量封装层会把报错吞掉、返回前 10000 条，调用方看到的是“成功”。分页 API 的 `has_more` 字段被忽略，是最常见的静默截断。

**第三层：预算裁剪。** MCP 的响应预算按档位渲染，最小档也放不下时截断并加标记；标记本身占 token，且不同实现的标记文本不同，Agent 未必把它当“证据不完整”的信号。

**第四层：压缩重写。** 上下文到阈值后，旧消息被摘要；摘要保留“结论”，丢掉“证据引用、时间戳、被排除的假设”。之后 Agent 再回答时，依据的是一份二手叙述。

**第五层：指标不覆盖。** 日志平台报“查询耗时、返回条数”，不报“本次结果占匹配总数的比例”；Agent 框架报“工具调用成功”，不报“看到的数据占比”。于是“基于 0.3% 的日志得出结论”这件事，在任何仪表上都不可见。

## 三、技术竞争力

| 方案／机制 | 上限类型 | 默认上限 | 截断是否显式 | 超限行为 | 保留哪一段 | Agent 可感知 |
|---|---|---|---|---|---|---|
| `kubectl logs --limit-bytes` | 字节 | 无（需显式设） | 是（参数） | 截断返回 | 由实现定 | 弱 |
| Elasticsearch `from+size` | 结果窗口 | 10000 | 是（报错） | 报错 | 前 N 条 | 中（若读错误） |
| 分页 API | 页大小 | 50–100 | 部分（has_more） | 返回首页 | 前 N 条 | 弱 |
| Loki/CloudWatch 查询 | 行数/事件数 | 数千 | 部分 | 截断返回 | 前/后由参数 | 弱 |
| MCP 响应预算 | token | 由配置 | 是（cut marker） | 裁剪+标记 | 最便宜渲染 | 中 |
| Agent 上下文压缩 | token | 阈值 | 是（压力条） | 摘要旧消息 | 结论 | 弱 |
| APM 查询结果 | 条数 | 数百–数千 | 部分 | 截断 | 前 N 条 | 弱 |
| 浏览器/DevTools | 条数 | 数千 | 是（提示） | 截断 | 前 N 条 | 中 |

**判读**：每家都能回答“返回了多少条、花了多久、有没有超限”。没有一家能回答“**这次回答基于匹配总量的百分之几、截掉的是头还是尾、截断标记有没有被 Agent 读到、结论对缺失的那部分是否敏感**”。而在排障里，缺失的那一段往往就是根因。

**本期反转**：我们一直把“工具调用成功”当成“证据到手”。实际工具返回的是**一个视窗**：字节视窗、结果视窗、token 视窗，每一层都可能裁掉关键段，而且多数不报错。Agent 的自信不来自它看到了全部，而来自它不知道自己没看到。**可观测性的下一步不是“多给数据”，是“给数据加分母”。**

**判词**：「日志平台／搜索 API／分页／采样器／MCP 预算／上下文压缩器」全部可采购，「这次回答基于多少比例的数据、截掉的是哪一端、截断标记有没有被读到、结论对缺失部分是否敏感」不可采购。

## 四、技术挑战

1. **截断方向**：保留头还是尾，决定 Agent 看到的是“起因”还是“后果”。
2. **静默成功**：封装层吞掉超限错误，调用方以为拿到了全量。
3. **标记不被读**：cut marker、`has_more`、`truncated` 字段存在，但 Agent 未必消费。
4. **压缩有损**：摘要保留结论、丢掉证据，后续推理无法回溯。
5. **无分母**：返回条数与匹配总数不一起给出，无法计算暴露率。
6. **敏感度未知**：结论对缺失部分是否稳健，没有任何度量。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 分母字段：每次工具返回携带 `matched_total` 与 `returned`，并计算暴露率。
- D2 截断方向声明：明确保留头/尾/中段，附“被截掉部分的位置”。
- D3 标记消费：Agent 必须把 `truncated`／`has_more` 当证据缺口，而不是普通文本。
- D4 压缩保留证据键：摘要至少保留时间戳、来源 ID、被排除假设，不只保留结论。
- D5 敏感度断言：结论若依赖缺失段，必须显式标注“基于部分数据”。
- D6 暴露率进 SLO：排障结论的暴露率低于阈值时，升级为“证据不足”而不是“已定位”。

**用户旅程（一次“日志只看尾部”的误判）**

① 服务报 5xx，Agent 调日志接口取最近 500 行（D1/D2 缺失）；② 真正的第一处错误在两小时前的启动阶段，早被截掉；③ Agent 看到尾部全是重试超时，判定“下游超时”，建议扩容（D5 缺失）；④ 扩容后错误率不降，因为根因是配置错误导致的连接池耗尽；⑤ 复盘时日志平台显示“查询成功、返回 500 行”，没有任何“本次只覆盖 0.4%”的记录（D1 缺失）；⑥ 团队把问题归为“模型判断力不足”，而不是“证据被截断”。

**90 天实现方案**

- **第 1–30 天**：给日志/搜索/工具封装加 `matched_total` 与 `returned`（D1）；在响应里声明截断方向（D2）。
- **第 31–60 天**：让 Agent 把截断标记作为证据缺口处理（D3）；压缩摘要保留证据键（D4）。
- **第 61–90 天**：结论敏感度断言（D5）；把暴露率写进排障 SLO，低于阈值时升级为“证据不足”（D6）。

**第 207 个市场空白（五项）**：① 工具返回的暴露率字段规范；② 截断方向与位置声明标准；③ 截断标记的 Agent 消费约定；④ 压缩摘要的证据保真要求；⑤ 结论敏感度与“证据不足”升级口径。

**`exposure.*`／`truncation.*` 第 174 次无人提字段族**：文档谈“如何限制返回条数、如何压缩上下文”，不谈“这次回答覆盖了多少、缺的那段会不会改变结论”。

**本地 173／173-kb 连续第 162 期成组启用（闪英迪 28：日志要带分母）**：本地原型给每次工具返回写 `tool_view{tool, matched_total, returned, truncated_at=head|tail|middle, cut_marker_seen, exposure_ratio}`；结论生成时若 `exposure_ratio` 低于阈值，强制标注“基于部分数据”；压缩摘要保留 `source_ids[]`、`timestamps[]`、`excluded_hypotheses[]`。
