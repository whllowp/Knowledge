# AI-SRE 技术洞察（第 334 期）

- 生成时间：2026-11-24 19:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：落盘面／原子写入与崩溃一致性——写成功不是一次系统调用，是一条协议

## 题眼

2026 年 3 月的一篇论文把文件系统 API 的问题说得很直白：Unix 把文件操作呈现为**状态转换**，而实现现实是**随时间执行的协议**；因此文件系统语义本质上是因果的、协议性的，不是瞬时的。它进一步指出一种“跨层时间假设泄漏”：应用假设 `fsync` 定义了持久化边界，但文件系统可能只是**把页标记为干净**，并没有真正持久化。

2026-11-20 的 OpenOffice 文档保存路径分析给了一个更具体的画面：用户打开之前保存的文档，发现里面全是 `#` 字符——不是文件损坏，而是**大约正确长度的零字节**，没有 PK zip 头，类型检测落到纯文本过滤器，`0x00` 显示为 `#`。两个缺陷叠加：替换前先截断目标文件，且没有保证替换内容已落盘。零字节不是“写坏了”，是“截断了、但新内容没到”。

2026-06-29 的 ArcadeDB issue #4830 把同一条链走完：快照解压、标记文件、rename 交换**都没有 fsync**（`FileOutputStream` 关闭时没有 `getFD().sync()`；`Files.writeString` 没有同步；`Files.move` 没有父目录 fsync），随后备份被删除。断电发生在交换与回写之间，数据库重开就是损坏且**没有回滚**。

2026-07-20 的 issue #5378 则是另一种失效：`GraphBatch` 批量加载时临时放宽 WAL flush 策略（合理），但 `close()` 恢复的是**引擎默认值**而不是用户配置的 `txWalFlush=2`。此后每一次事务都静默地不再 fsync-per-commit，79 tx/s 变成 4,120 tx/s，**没有报错、没有日志、没有信号**。

## 一、发展趋势

**第一，从“调用 fsync”转向“定义协议”。** 应用需要的是原子替换、崩溃一致、可恢复，而 FS 提供的是 fsync/rename/O_DIRECT 等原语；两者之间要写协议。

**第二，目录项成为落盘的一部分。** rename 之后不 fsync 父目录，崩溃后目录项可能回退；这是最常见的遗漏。

**第三，配置与默认值的静默降级。** 批量加载、迁移、升级会临时放宽持久化策略；恢复时若回到默认而非用户配置，durability 被静默降级。

**第四，崩溃一致性测试进入 CI。** 注入断电/崩溃、检查零字节、部分写、目录回退。

**第五，AI 训练检查点把问题放大。** 检查点大、写入频繁、恢复代价高；崩溃一致性与完整性检测成为硬要求。

## 二、技术现状

**三层语义。** page cache 接受 → 文件系统提交 → 设备落盘；`write()` 返回只表示第一层。

**零字节文件。** 截断 + 新内容未落盘；ext4 `data=writeback` 或应用未 fsync 时常见。

**rename 原子≠持久。** POSIX 保证 rename 原子性，但崩溃时目录项与数据可能不同步；需要父目录 fsync。

**fsync 错误被忽略。** 有研究统计仅约 9% 的应用正确处理 fsync 失败；失败后继续写会扩大损坏。

**配置降级静默。** 临时放宽后未恢复用户配置；吞吐上升被当成优化，实际是 durability 降级。

**检查点完整性。** 部分写、截断、零区间要在加载时检测，损坏的检查点不能用于恢复。

**对象存储不提供同名语义。** 覆盖写要么整体替换对象、要么产生新版本；多段上传、分片、生命周期规则都会改变“写成功”的含义。把本地文件系统的原子替换假设直接搬到 S3 类存储，是最容易踩的跨层假设泄漏。

## 三、技术竞争力

| 方案 | 崩溃一致性 | 实现复杂度 | 性能开销 | 可验证性 | 主要风险 |
|---|---|---|---|---|---|
| 直接 write | 低 | 低 | 低 | 低 | 部分写/零字节 |
| write+fsync | 中 | 低 | 高 | 中 | 目录未同步 |
| temp+fsync+rename+dir fsync | 高 | 中 | 高 | 高 | 遗漏目录 |
| O_DIRECT | 中 | 高 | 中 | 中 | 对齐/绕过缓存 |
| WAL/日志 | 高 | 高 | 中 | 高 | 配置降级 |
| 检查点+校验和 | 高 | 高 | 中 | 高 | 检测成本 |

判读：买得到文件系统、对象存储、WAL、检查点库；买不到“这次写入在崩溃后是否完整、目录项是否持久、配置是否被静默降级、损坏能否在加载时被拒绝”。

本期反转：我们一直把“写成功”当成一个布尔值。实际上它是**一条协议**：写到临时文件、fsync 内容、rename 到目标、fsync 父目录、验证读回；少一步，崩溃窗口就多一段。零字节文件不是磁盘坏了，是协议少了一步。

判词：「文件系统／对象存储／WAL／检查点库／原子写工具」全部可采购，「这次写在崩溃后是否完整、目录项是否持久、fsync 失败是否被处理、配置是否被静默降级、损坏能否在加载时被拒绝」不可采购。

## 四、技术挑战

**其一，语义分层。** 应用假设的持久化边界与 FS 实际提供的不同。

**其二，目录项遗漏。** rename 后不 fsync 父目录，崩溃后目标可能不存在或指向旧 inode。

**其三，错误处理。** fsync 返回错误后继续写，可能造成不可恢复损坏。

**其四，静默降级。** 批量/迁移路径放宽策略后未恢复。

**其五，检查点检测。** 零区间、截断、位翻转要在加载时发现。

**其六，测试困难。** 崩溃注入需要可控的断电/回滚环境。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 存储/平台：需要原子写协议与目录 fsync 规范。
- 数据库/SRE：需要 WAL 配置一致性与降级检测。
- 训练平台：需要崩溃一致检查点与完整性检测。
- 安全/合规：需要可证明的持久化证据。
- 复盘：需要知道损坏发生在哪一层。

**用户旅程（一次“保存后文件变零字节”）。**

1. 应用打开旧文件准备覆盖。
2. 先截断目标文件，再写新内容。
3. 写入返回成功（page cache 接受），应用认为已保存。
4. 断电；新内容未落盘，文件长度为 0。
5. 用户打开文件，看到 `#`；类型检测失败。
6. 复盘发现：没有临时文件、没有 fsync、没有目录 fsync。

**实现方案（90 天）。**

- 第 1–2 周：原子写协议——临时文件、fsync 内容、rename、fsync 父目录；写失败保留旧文件。
- 第 3–4 周：错误处理——fsync 失败视为写入失败；记录并停止后续写。
- 第 5–6 周：目录与元数据——所有 rename/创建/删除后 fsync 父目录；测试目录回退。
- 第 7–8 周：配置一致性——批量/迁移路径的临时策略恢复用户配置；启动时校验 durability 配置。
- 第 9–10 周：检查点完整性——加载时校验长度/校验和/零区间；损坏拒绝恢复。
- 第 11–12 周：崩溃注入——CI 注入断电/回滚，验证零字节、部分写、目录回退。
- 第 13 周：证据留存——每次写入的协议步骤与结果；复盘可定位。

**验收标准。** 任一次写/保存/检查点，能回答：走了哪几步协议、目录是否同步、fsync 是否成功、配置是否用户值、崩溃后是否完整。

**第 246 个市场空白（五项）**：原子写协议规范；目录 fsync 检查；fsync 错误处理；配置降级检测；崩溃注入测试。

**`durability.*`／`fsync_protocol.*` 第 213 次无人提字段族**：`durability.temp_file`、`durability.dir_sync`、`durability.fsync_error`、`fsync_protocol.steps` 在文件系统、数据库与检查点库之间没有统一语义；应用只报“写入成功”。

**本地 173／173-kb 连续第 201 期成组启用**（何伟 02）：本地知识库把“写入返回”与“崩溃后完整”分开记账；本期把落盘落成协议与证据。
