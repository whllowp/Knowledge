# AI-SRE 技术洞察（第 137 期）

**生成时间**：2026-11-12 03:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：工具契约面／注册表漂移面（Tool Contract & Registry Drift）——版本钉住了，行为没钉住；11 周里 59 个工具 7 个变了

---

## 题眼

10-24 arXiv 2610.33633（ProbeID）把一件被忽视的事量了出来：**Agent 靠「可复制的描述」选工具，而描述无法证明「跑的是哪个实现」**。它用「schema 合法的探针＋规范化响应」对照可信准入参考，模糊时**弃权**；在 MCP-IdentityDrift 缓存上严格判定 **hit@1 = 0.956**，而**描述路由器接近随机**；agent bank 上 64 个探针可拒绝全部可达替换、512 个可拒绝有界距离替换。最硬的一句在最后：**十一周里，59 个真实工具中有 7 个在版本已 pin 的情况下仍然改变了响应**（11.9%）。同月 10-12 一篇中文工程稿从另一侧补刀：**MCP 工具只把一个字段改成可选，Agent 就开始替用户猜参数**——因为 schema 不只做校验，**它直接参与模型如何理解与选择动作**。

## 一、发展趋势

**趋势一：工具从「接口」变成「契约」。** 名称、输入 schema、输出 schema、描述、错误语义，五样里任何一样变化，都会改变 Agent 的行为；**而工具注册表通常只给名字与描述**。名字与描述是**路由信号**，不是身份证明——**这就是 ProbeID 要解决的问题**。

**趋势二：版本 pin 被证明不够。** ProbeID 的 7/59 是第一个「pin 了还漂」的公开量化；同类证据还有 128 期的模型 alias 漂移——**pin 的是标识，不是实现**。

**趋势三：验证从事前审批转向运行时可证。** 过去审「这个工具是谁发布的」；现在要问「此刻响应我的这个实现，是不是我批准的那个」——**探针＋规范化响应＋弃权**成为可执行方案。**弃权不是失败，是产品决策：宁可降级，不可猜。**

**为什么现在爆发：MCP 生态在扩张，工具数涨得比 owner 快。** 一个团队接 20 个 server、上百个工具，**每个 server 的维护者可能根本不认识你**；工具变更不会进你的变更系统，**漂移是默认状态，不是异常**。

## 二、技术现状：契约五要素，注册表只给两样

**名称与描述：可复制、不可证。** 任何实现都能自称同名、抄同一段描述；**描述路由器在漂移场景接近随机**（ProbeID）。

**输入 schema：改一个 optional 就改行为。** 字段变可选 → 模型开始「合理猜测」；**参数是猜的，结果就不可归因**（124 期参数溯源）。

**四种「兼容」变更，四种行为破坏。** 加 optional（模型开始猜）、放宽枚举（模型选到新值）、改默认值（不传就变行为）、改错误码（失败被当成功）；**发布说明写「兼容」，Agent 侧是 breaking**。

**输出 schema：常被当成「格式」忽略。** 输出结构变化会让下游解析失败或静默丢字段；**ADR 里才开始出现「输出 schema 演进策略」**。

**错误语义：最容易被悄悄改。** 同一错误从 `isError` 改成正常返回、或从异常改成空结果；**Agent 会把失败当成功**（115 期返回面）。

**版本与注册表：只钉名字。** ProbeID 证明 11 周 7/59 漂移；注册表本身也会漂（同名的 server 换人维护）。**pin 一个名字，等于相信「名字背后永远同一个实现」——而这句话没有任何机制保证。**

## 四、技术挑战

**一，描述可复制。** 名称与描述是路由信号，不是身份证明；**换个实现抄同一段描述，路由照样命中**。

**二，版本 pin 不覆盖行为。** 7/59 在 pin 下漂移；**没有响应级验证，pin 只是心理安慰**。

**三，schema 变更被当成兼容。** 加 optional、放宽枚举、改默认值，都被标成「向后兼容」；**对 Agent 是行为变更**。

**四，弃权有代价。** 模糊就弃权会降低自动化率；**不弃权就会把「猜的」当「确定的」**。

**五，探针有盲区。** ProbeID 自己说：**两个工具，如果 bank 里没有探针能触达其漂移，就永远通过**；覆盖度是硬边界。

**六，响应噪声。** 工具输出天然有噪声（时间戳、ID）；**规范化做不好，误报会把验证变成噪音**。

**七，探针有成本。** 每个工具每日多次探针，乘以工具数就是一笔调用账；**全覆盖不现实，按风险分层才是正解**。

**八，组合漂移更难测。** 单工具验证通过，但 A 的输出喂给 B、B 的 schema 变了——**组合契约没有探针**。

**九，责任边界不清。** 工具漂移导致事故，**算工具 owner 的、Agent 平台的、还是调用方的**？没有契约哈希，连「谁改的」都说不清（125 期归因问题在工具层复现）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `tool.*` 字段**：`tool_id`、`server`、`contract_hash`、`schema_diff`、`identity_proof`、`probe_coverage`。
- **R2 契约哈希**：名称/输入/输出/描述/错误语义五样一起 hash；任一变化触发评审。
- **R3 运行时探针**：schema 合法探针＋规范化响应；对照准入参考，模糊时弃权。
- **R4 版本化 allow-list**：按 `tool_id@contract_hash` 放行，不按名字。
- **R5 弃权语义**：`TOOL_IDENTITY_UNKNOWN` 时降级为只读或转人工，不静默执行。
- **R6 覆盖度**：报探针覆盖率与已知盲区；盲区工具列入高风险清单。
- **R7 组合探针**：对高频工具链（A→B）做端到端探针，覆盖单工具探不到的衔接漂移。

### 5.2 用户旅程

- **平台工程师**：接入 MCP 工具 → 录契约哈希与探针集 → 每日跑探针 → 第 9 周命中漂移 → 阻断该版本。
- **SRE**：事故复盘怀疑工具变了 → 查 `identity_proof` → 确认 3 天前响应变化 → 加入探针盲区清单。
- **工具 owner**：改输出 schema → 走 ADR → 提前通知 → 更新探针与 allow-list。
- **审计**：抽查 20 次工具调用 → 核对契约哈希与准入参考 → 确认没有「同名不同实现」。

### 5.3 实现方案（90 天）

- **0–30 天：录契约。** 给 top 20 工具算契约哈希；建探针集与规范化器。
- **30–60 天：跑验证。** 每日探针；漂移告警；allow-list 按哈希放行；弃权语义接入。
- **60–90 天：补盲区。** 统计探针覆盖率；盲区工具提高抽检；季度红队替换一个工具看能否识破。
- **90 天后：红队常态化。** 每季度用「同名不同实现」替换一个低风险工具，验证探针与弃权是否生效；未检出的进盲区清单。

**第 90 个市场空白（五项）**：契约哈希可导出率、运行时身份验证覆盖率、漂移检出率、弃权语义覆盖率、探针覆盖度可报率——无一内建；`tool.*`／`contract.*` 为**第 59 次无人提字段族**。本地 173／173-kb 连续第 52 期成组启用：朱革 15「Agent、Skill、Prompt、工具和知识缺少统一版本边界」＝全库唯一把「工具也要版本边界」写出来的句子，本期首次当主线；配刘凯宁 05「结论/证据/待确认项三分」、余锦泽 03「程序核对给出已验证/候选」。判词：**本地把工具版本边界写成规模化障碍，联网侧 10 月才量出「pin 了还漂 7/59」；两边都没把「这次调用是不是那个实现」做成可验签的判定。**
