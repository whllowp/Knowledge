# AI-SRE 技术洞察（第 372 期）

**生成时间**：2026-11-27 12:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：工具目录面／Agent 看到的工具清单，是一份会过期的缓存

## 题眼

Agent 调用工具时，模型看到的不是"系统里现在有什么工具"，而是一份在会话开始时被序列化进上下文的**工具描述**：名字、用途、参数 schema、示例。MCP 的 `tools/list` 返回工具与 `inputSchema`，服务端还可以发 `notifications/tools/list_changed` 提示客户端刷新；OpenAI 的 function calling、Anthropic 的 tool use 也是同一形态——**描述先于调用**。

问题在于：工具改名、下线、改参数、改权限，都发生在描述被序列化之后。模型仍按旧描述调用，失败被归因成"模型不会用工具"，而不是"工具目录过期了"。

## 一、发展趋势

第一，工具协议标准化。MCP 把工具发现、调用、变更通知做成协议；A2A 把 Agent 间任务做成协议。协议解决"怎么发现"，但不解决"发现的是不是当前版本"。

第二，工具注册表化。平台开始维护工具目录：谁发布、版本、owner、权限、配额、SLA。注册表是控制面，工具是数据面。

第三，能力发现与权限绑定。工具不再是"一个函数"，而是"一个带身份、配额、审计的能力"；调用前要判断"这个 Agent 此刻能不能用"。

第四，工具描述进入评测。工具描述写得好不好，直接影响调用成功率；描述本身成了需要回归测试的资产。

第五，工具下线成为变更。下线一个工具等于一次破坏性 API 变更，需要弃用窗口、迁移路径、兼容层。

## 二、技术现状

**三条时效路径，各自会腐坏。** ①会话启动时缓存：长会话里工具变了，Agent 不知道；②网关转换：MCP 工具被转成 OpenAI/Anthropic 格式，转换层丢字段或改名；③人工维护的文档/提示词：最容易过期。

**schema 变更静默。** 参数从必填变可选、字段改名、类型从 string 变 integer，工具仍"存在"，调用仍"成功"，但语义变了。这类变更没有 404，只有错值。

**错误分类把目录问题伪装成模型问题。** 工具不存在返回 404，参数不匹配返回 400，权限不足返回 403；如果 Agent 统一显示"工具调用失败"，人只会去调 prompt。

**权限变更不在描述里。** 工具描述不写"谁能用"；Agent 拿到工具不等于有权限，调用时才失败。

**工具版本与模型版本耦合。** 同一个工具在强模型上"会用"、在弱模型上"不会用"；评测结论随模型变，工具目录却没有版本。

**长会话让缓存过期更明显。** Agent 会话从几分钟变成几小时，工具目录在会话中途变更的概率显著上升。

**描述质量在弱模型上被放大。** 同一个工具描述，强模型能补全意图，弱模型直接按参数名硬填；工具目录的"说明书"质量因此成了模型分层变量。

**目录里没有"成本"字段。** 工具描述不写调用一次要花多少钱、多少 token、多少下游配额；Agent 在规划阶段无法按预算选择工具，只能先调用再发现超支。

**工具度量缺失。** 大多数平台按接口统计成功率，不按工具统计"参数不匹配率""权限失败率"；目录问题因此永远混在总错误率里。

## 三、技术竞争力

| 方案/能力 | 工具发现 | 变更通知 | 版本/权限 | 主要缺口 |
|---|---|---|---|---|
| MCP | `tools/list` | `list_changed` | 无原生 | 客户端是否刷新 |
| OpenAI function calling | 请求内联 | 无 | 无 | 每次自带 |
| Anthropic tool use | 请求内联 | 无 | 无 | 每次自带 |
| LangChain/LlamaIndex | 注册表 | 无 | 部分 | 缓存策略 |
| 工具网关 | 代理发现 | 可加 | 可加 | 转换丢字段 |
| 自建注册表 | 完整 | 完整 | 完整 | 维护成本 |

**判读**：可采购的是"工具协议、注册表、网关、权限系统、审计"；不可采购的是"这个工具描述是哪一版、Agent 缓存了多久、变更有没有到达它、失败是工具不存在还是参数不匹配、权限变更是否同步"。

**本期反转**：我们一直把工具当成"模型的能力"，但它其实是**一份带版本的外部契约**；Agent 的可靠性不只取决于模型会不会用，还取决于它拿到的说明书是不是最新的。

## 四、技术挑战

**挑战一：变更通知到不了长会话。** 协议有 `list_changed`，但客户端可以选择不刷新；刷新又会破坏正在进行的调用。

**挑战二：转换层是有损的。** MCP → OpenAI 的转换会丢 `outputSchema`、注释、示例；下游只看到"简化版工具"。

**挑战三：错误码不区分目录问题。** "工具不存在""参数不匹配""权限不足"被同一个错误处理分支吞掉。

**挑战四：权限与描述分离。** 工具描述不携带权限信息，Agent 无法在规划阶段排除无权工具。

**挑战五：评测不覆盖工具目录。** 评测用固定工具集，生产工具在变；评测绿不代表生产可用。

**挑战六：下线没有窗口。** 工具被直接删除，旧会话与旧客户端立刻失败；没有弃用期与兼容层。

**挑战七：目录被多个 Agent 共享。** 一个 Agent 的工具变更会影响其他 Agent；没有租户/团队视图，变更影响面无法评估。

**挑战八：缺少"最后验证时间"。** 目录不知道上次真实调用成功是什么时候；一个三个月没人调用的工具，是可用还是已坏，没人知道。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①工具注册表（版本/owner/权限/状态）；②变更通知与刷新策略；③转换层字段保真；④错误码分级（不存在/参数/权限/超时）；⑤规划期权限过滤；⑥工具目录的回归评测。

**用户旅程**：Agent 启动 → 拉取工具目录（带版本）→ 规划时按权限过滤 → 调用 → 失败时按错误码分类 → 目录变更通知 → 会话内刷新或新会话生效 → 下线走弃用窗口。缺任何一步，工具目录都会变成"看起来有、实际不能用"。

**90 天实现方案**：0–30 天，给工具目录加版本与 owner，错误码拆成四类；31–60 天，接 `list_changed` 并定义刷新策略（长会话定时校验），转换层加字段保真测试；61–90 天，把工具目录纳入评测与门禁，下线走弃用窗口与兼容层。

**第 284 个市场空白（五项）**：工具目录版本；变更到达证明；转换保真；错误码分级；下线窗口。

**`tool_registry.*`／`capability_drift.*` 第 251 次无人提字段族**：所有平台都报"支持工具调用"，没有一个字段报"Agent 缓存的工具描述是哪一版、变更是否到达、失败是目录问题还是模型问题、权限变更是否同步、下线有没有窗口"。
