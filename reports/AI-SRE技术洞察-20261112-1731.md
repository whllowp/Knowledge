## 题眼

11-10 微软披露了一个叫 **Lazarus** 的技术：**改动不到 10 个「休眠神经元」（平时几乎不激活的权重），就能给模型植入后门，不需要重新训练，而且 Agent 在标准安全评测里表现完全正常**。触发可以是一个日期——到了那天，Agent 在日常任务里**用它原本就有的权限，下载并运行攻击者指定的代码**。微软强调攻击门槛：**只要拿到改权重的权限**（被攻破的账号、开发流水线、存储系统），**自研模型同样暴露**。检测路径也很硬：**前沿 Agent 能看出异常的权重修改，但可靠检测必须与「原始未修改权重」做 diff——所以 provenance（模型从哪来、中间有没有被改）是关键**。微软研究员的原话是：**「没有哪种扫描能毫无疑义地证明模型是安全的。」** **后门不是「模型变笨」，是「模型在等一个信号」——而行为测试测不到「等」。** **更麻烦的是：它平时比正常模型还要「正常」，因为它必须通过所有评测。**

## 一、发展趋势

**趋势一：攻击从「提示注入」下沉到「权重层」。** 注入改的是输入，**Lazarus 改的是模型本身**；输入过滤、内容审核都挡不住。**防线要往下沉一层，但大多数团队的检测还停在最上面一层。**

**趋势二：检测从「行为评测」转向「权重取证」。** 跑 benchmark 测不出触发条件；**要拿 checkpoint 与声明的基座做 diff**，并看「少量向量的大改动」这个特征。

**趋势三：provenance 从合规项变成安全项。** 128 期说模型会静默更新，137 期说工具会漂移；**这一期说：连权重都可能在交付链上被改**。**不知道模型从哪来，就无法证明它没被改。**

## 二、技术现状：四层后门，一层比一层难查

**权重层：Lazarus 类。** 改几个神经元，**行为正常、触发才变**；检测要基线 diff。

**数据层：投毒微调。** 训练数据里埋触发模式；**合法微调也会大改权重，和植入难以区分**。

**工具层：恶意 MCP server。** 工具描述或返回里藏指令；**Agent 照做**（92／137 期）。

**记忆层：被写入的「事实」。** 记忆里塞一条「遇到 X 就执行 Y」；**下次会话照做**（116 期记录污染）。

**三种触发，一种比一种难测。** 日期（到时自动激活）、输入（文档/工单里的暗号）、工具（某个工具名/参数）；**日期触发最阴——它连输入都不需要**。

## 四、技术挑战

**一，行为测试测不到条件。** 触发不出现时，模型 100% 正常；**评测通过不等于没有后门**。

**二，合法微调与植入难分。** 微调本来就会改权重；**只能靠「少量向量大改动」这类统计特征**。

**三，provenance 链断点多。** 开发者→构建→存储→部署，**每一段都可能被改**。

**四，内部模型也暴露。** 只要流水线被攻破，**自研模型不比第三方安全**。

**五，运行时限制有代价。** 最小权限、沙箱、限出口会降低 Agent 能力；**安全与可用性要显式取舍**。

**六，没有「证明安全」的方法。** 微软自己说无法证明；**只能做「可证伪」的检查**。

**七，第三方模型合同不覆盖权重。** 供应商保证「模型安全」，**不保证「交付给你的权重没被改」**；要合同级 provenance 条款。

**八，回滚也未必干净。** 回滚到旧 checkpoint，**旧 checkpoint 可能同样被改**；基线要来自可信构建。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `model.*` 字段**：`checkpoint`、`base_model`、`weight_diff`、`provenance_chain`、`signed_at`、`trigger_tests`。
- **R2 部署前 diff**：每个 checkpoint 与声明基座比；**少量向量大改动即阻断**。
- **R3 触发测试**：按日期/文档/工具名造触发样本；**加入发布门禁**。
- **R4 provenance 链**：记录模型从开发到部署的每一跳；**断点即视为不可信**。
- **R5 运行时限制**：最小权限、沙箱执行、出口限制、高危工具人工批准。
- **R6 指标**：provenance 完整率、部署 diff 覆盖率、触发测试通过率、出口拒绝率。

### 5.2 用户旅程

- **平台工程师**：新模型上线 → 与基座 diff → 通过 → 记录 provenance → 部署 → 更新后再次 diff。
- **安全**：季度触发测试 → 造 20 个触发样本 → 观察行为变化 → 异常即回滚。
- **SRE**：Agent 突然执行可疑命令 → 查出口日志 → 阻断 → 回溯 checkpoint 是否被改。
- **审计**：抽查模型 → 核对 diff 与 provenance → 确认没有「来源不明」的权重。

### 5.3 实现方案（90 天）

- **0–30 天：补 diff。** 部署前与基座比；统计异常改动。
- **30–60 天：补触发测试。** 建样本集；进发布门禁；provenance 链记录。
- **60–90 天：收紧运行时。** 最小权限、沙箱、出口限制、高危审批；季度演练；合同补 provenance 条款。

**第 108 个市场空白（五项）**：权重 diff 覆盖率、provenance 完整率、触发测试通过率、出口拒绝率、高危工具审批覆盖率——无一内建；`model.*`／`provenance.*` 为**第 75 次无人提字段族**。本地 173／173-kb 连续第 66 期成组启用：余锦泽 03「SQL 执行前做本体约束校验」＝全库唯一把「执行前校验」写成硬门槛的实践，本期首次当主线；配 128 期模型身份、137 期工具身份。判词：**本地把「执行前校验」写成门槛，联网侧 2026 年才证明「10 个神经元就能埋后门」；两边都没把「这个 checkpoint 与基座逐权重一致」做成部署前置。**
