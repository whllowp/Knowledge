# AI-SRE 技术洞察 · 第 323 期

## 测量生成面 / Instrumentation Generation Integrity——「trace 是 Agent 自己埋的，谁审过那份埋点计划？」

- **时间及范围**：2026-11-27 01:00 档（`date` 取 01:32）；限 2026 年，重点近 30 天。
- **期号**：本实例上一期 322（11-25 10:00 信号可归因面）顺延 323；主线第 276 全新立面；字段族 244；本地连续第 199 期。E 盘并行实例另有不同序列，以文件戳 0100＋本实例序列标识。
- **划界**：#319 判定函数面问「什么算失败」；#322 信号可归因面问「数字记在谁头上」；#318 空窗期面问「无人时它改了什么」。本期只问更前面一步：**用来观察 Agent 的那套埋点，本身是 Agent 写的，选点理由与漏埋点谁验收**。

**题眼**：OpenTelemetry 11-12 官方博客首次公开一套由七个专职 Agent 生成插桩代码的 harness——研究、计划、编码、评审、端到端部署、观测各有分工，`execution-plan.md` 在写代码前固定埋点，Weaver 用注册表比对 OTLP 并以非零退出阻断违规。这是一次真实的方向反转：过去我们担心「Agent 篡改证据」，现在**证据的生产线本身被自动化了**。Weaver 能抓出「工具 span 被设成 OK」这类格式违规，却对「这个点根本没埋」「这个映射需要框架专家判断」只做 coverage 记录、不阻断。看得见「trace 齐全、字段合规」≠看得见「测量没被生成它的 Agent 悄悄改过」。

## 一、发展趋势

**趋势一：插桩从手工艺变成 Agent 流水线。** OTel 11-12 博客（阿里云 Huxing Zhang、Ziming Liu）给出的团队结构是：Team Lead 控循环状态；Instrumentation Research 克隆目标框架、优先找公开 hook/callback，只在生命周期无法覆盖时才方法包装；Plan Review 按复杂度、可维护性、覆盖率打分并写出细粒度 `execution-plan.md`；Coding 按计划实现；Code Review & Test Validation 与 Coding 反复往返；E2E Generation & Deployment 并行准备集成测试；Observation 在 K8s 跑样例、抓 OTLP 交 Weaver 校验并做内存泄漏 soak test。生成的插件已覆盖 CrewAI、LangChain、LangGraph、LiteLLM、AutoGen、AgentScope、Dify、Google ADK、Claude Agent SDK、Microsoft Agent Framework、MCP、mem0，以及 BFCL-v4、WebArena、MiniSWEAgent 三个基准，并在 PR 阶段经人工评审，正 upstream 到 `opentelemetry-python-genai#185`。资深贡献者过去要花数天埋一个框架，现在瓶颈前移到「计划审得对不对」。

**趋势二：一致性校验从模型判断退回确定性比对。** 该团队明确写出第一版失败教训：最初让评审模型判断遥测是否符合规范，模型「有时会批准违反约定的输出」，于是换成注册表比对＋违规时非零退出。这与本期之前的判定函数面结论同构：**评审者不能与被测同源**。实测抓到的违规是 Coding Agent 把 `execute_tool ping` 的 `status.code` 设成 `ok`，而插桩在成功时必须留 `UNSET`（`OK` 保留给应用代码）。Weaver 的 `missing_attribute`、`type_mismatch`  advisors 与 Rego 策略负责命名与格式，`--report-only` 会把语义发现降级为警告。

**趋势三：标准仍在移动，生成式插桩会被动累积债务。** 9io 11-05 梳理：GenAI 语义约定 2026-05-05 迁出核心仓库，至 11-05 无 tag 发布，未发布 changelog 79 条其中 17 条 breaking；已发布插桩仍在发 `gen_ai.client.token.usage`，而主分支 9 月已改名；`invoke_workflow` span 11-05 起并入 `invoke_agent`。DS Stream 指出首个独立版本 v0.1.0 以破坏性变更开场，建议钉版本、在自有命名空间建薄映射层。OTel 博客自己承认：Coding Agent 为 CrewAI 加了 `gen_ai.crewai.*` 自定义属性，而官方命名指南警告这类前缀可能与未来标准属性冲突。

**趋势四：测量入口正在对话化、通用化。** Virtana 11-16 发布（11-20 二次报道）把 Agentic Observability 放进 Teams、Slack 和 Claude，基于 System-Aware MCP Server 与 A2A 协议，用系统依赖图和 25,000+ 运维指标跨应用、数据库、计算、网络、存储追踪，在聊天线程里完成审批与修复，GA 定于 2027 Q1。火山引擎 VeOps CLI 把指标、日志、Trace、告警、集群巡检能力暴露给 Claude Code、Codex、Cursor、Trae 等通用 Agent，文档直陈要解决的正是「跨产品怎么关联、结论怎么审计」。腾讯云 11-03 升级 CloudQ 与 AI 可观测，主线是「用 AI 管运维，用可观测管 AI」，慢回答可下钻到具体调用节点。

## 二、技术现状

六家厂商在「测量由谁生成」上的现实位置差异很大。

Google 侧，《SRE》第二版（InfoQ 11-15 访谈）把可观测性配置下沉到内部开发者平台，Gemini CLI 已用于真实故障：拉取告警、因果分析、关联时序、提缓解方案，人确认后重启；但 Komodor CTO 称约 30% 案例可独立解决仅为演示口径。Anthropic 11-12 的 Claude Tag 更新版把指标定义收进语义层，把分析步骤写进 Markdown 版 Skills，每轮对话重新加载——**改一句 Markdown 定义，下一次查询就换口径**，却没有看到配套的「重定基线」动作。Databricks 11-03 把 Claude 原生 OTel 轨迹接入 MLflow，记录执行次序而非只记录最终答案。

OpenAI 11-09 的 Control Room 把信任边界放在推理网关：任务领唯一 ID、绑定已批准的安全论证，引擎每次生成前回查，停令到断供最长 35 秒；但它管的是「任务还能不能产出 token」，不管「观察它的测点是哪来的」。字节火山 DevOps Agent 处于公测，提供响应计划、RCA Harness 假设驱动下钻、专家 Agent 的 IAM 角色；VeOps CLI 解决数据稳定获取与结论审计。阿里云 AgenticOps 全栈（云监控 2.0、AgentLoop、STAROps、云效智能体）把 Agent 轨迹、成本与质量纳入观测，AgentLoop 用 AI 评估 AI 并回流知识库；其 LoongSuite 正是 OTel 这套生成式插桩的来源。腾讯云 CloudQ 以全景图谱组织资源、关系、状态与处置动作，既给人看也让 Agent 调用。

**共同现状**：每一家都能生成或导出大量遥测；没有一家公开「埋点计划的版本、选点理由对应的 on-call 问题、漏埋点是否阻断、自定义属性是否可能撞标准」这类字段。

## 四、技术挑战

**挑战一：合规≠有用。** Weaver 只比对寄存器里有的属性；没埋的点、映射错的语义（CrewAI 的 crew/task/agent/flow 哪些算 `invoke_agent`）不在 violation 之列。覆盖率矩阵是度量不是门禁，漏一个属性不会让构建失败——于是「weaver 全绿」会给出一种测量完整的错觉。

**挑战二：盲区不可被更聪明的 Agent 补回。** Claude Agent SDK 的 Python 包包裹闭源 CLI，Agent loop、工具分发与模型调用都在 CLI 内；插件只能报告跨进程边界的东西。博客直言研究与规划「无法恢复框架不暴露的数据」。这把可观测性从「Agent 能力问题」还原成「框架暴露面问题」。

**挑战三：套利的例外与移动的标准。** `expected_violations` 允许带着理由临时接受已知违规，且 Weaver 不再报告该违规时运行反而失败（防条目过期）——这是很好的机制，但行业里绝大多数白名单没有失效检测。同时 GenAI 约定 17 条 breaking、首个独立版本带破坏性变更、自定义前缀撞名，使「一次生成的埋点」天然有保质期。

**挑战四：评测侧同样缺少测量审计。** 近 30 天基准给出严厉数字：ORCA 榜 11-04 最好 50.2%，ITBench-AA 11-17 最好 56.2%（最新型号反降）；R2Act 类基准中模型定位对 91.4%–99.7%，但修复方案只有 36.8%–60.3% 被规则接受；SWEOps-Bench 55 个真实缺陷检出 72.7%–90.9%、端到端闭合仅 14.5%–52.7%，存在「告警清了但校验没过」。这些数字往期已多次使用，本期换一个角度读：**被测 Agent 的分数，同样来自一套需要被审计的测量管线**。

## 五、展望与建议

**新观点**：可观测性正在从「系统给 Agent 看的窗口」变成「Agent 写给系统看的代码」。前 12 期我们要求「行为可举证」，本期要求「测量可举证」——如果尺子是 Agent 自己刻的，达标率再高也只是自证。

**字段族 244 `instrumentation.generation.*`**（缺省 `INSTRUMENTATION_UNVERIFIED`）：`plan_id`／`plan_revision`；`instrumentation_points[]{extension_point,span_kind,attribute_source,question_answered}`（选点必须对应一条 on-call 问题）；`generated_by`（agent id＋model version）；`review_state ∈ HUMAN_REVIEWED|MODEL_REVIEWED|UNREVIEWED`（MODEL_REVIEWED 视同未审，承 #319）；`conformance.pin`（semconv registry SHA）＋`conformance.result`；`coverage.gating ∈ GATING|REPORT_ONLY`；`expected_violations[]{id,reason,expires_at,stale_check}`；`exposure_limit ∈ DECLARED_BLIND_SPOT|UNKNOWN`；`custom_attribute_ns[]`；`verdict ∈ MEASUREMENT_VALIDATED|CONFORMANCE_ONLY|UNREVIEWED_PLAN|UNVERIFIED`。门禁：verdict 不为 `MEASUREMENT_VALIDATED` 时，该遥测不得进入 SLO 判定、不得作为自治升档依据（承 #310~#322 逐层叠加）。

**四条最小动作**：①把 `execution-plan.md` 当契约进 CI，每点写清回答哪条 on-call 问题，删点与加点同等评审；②覆盖率矩阵至少对关键属性转 GATING，缺属性阻断而非记一笔；③自定义属性一律进 `custom_attribute_ns[]` 并设到期复核，撞标准即改；④对框架不暴露的区间写 `DECLARED_BLIND_SPOT` 并在报告显著位置声明，禁止用更自信的模型输出填补。

**采购三问**：埋点计划能不能导出并看到选点理由？漏埋点会不会阻断发布？自定义属性与例外有没有失效检测？

**评测与标准**：在 ITBench-AA／Cloud-OpsBench 之外增加「测量计划配对题」——同一框架两版插桩，一版漏关键属性、一版用自定义属性撞标准，看 Agent 能否指出差异；报 `coverage_gap_rate` 与 `plan_review_hit_rate`。OTel GenAI 提四点：`review_state`、`plan_revision`、`coverage.gating`、`expected_violations.stale_check`。信通院六维补「测量可举证率」格，与 #316 审批、#317 授权、#318 空窗、#319 判定、#320 自伤、#321 收口、#322 归因七格并列。

**本地知识积累**：第 199 期新角度重读肖汉松《从 Harness 到 Loop：阿福 Agent 小队如何处理持续涌入的线上 Badcase》——把「先 Harness 后 Loop」读作「先把测量装进可验收的 harness，再谈自动化闭环」，配何伟「生成与验证分离」、刘凯宁「结论／证据／待确认项」三分作选点理由卡骨架、赵恒「写入状态要有权威来源不能由写入器自报」。173 目录按目录级引用。
