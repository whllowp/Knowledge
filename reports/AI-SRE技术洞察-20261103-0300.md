# AI-SRE 技术洞察（2026-11-03 03:00 第 41 期）

## 生命周期面（退役面）运维——"下线"比"上线"更常态：模型一年一签、平台整装退役，发布日历里一半是别人写的

**主线定位**：第三十二条主线。与第 24 期分界=那期管"选谁"，本期管"选中的那个什么时候没"；与第 28 期分界=那期管 pin 什么版本，本期管版本的生命周期终点与被迫迁移；与第 34 期"换芯不换名"分界=那期管供应商悄悄替换，本期管公开的、有截止日期的强制替换。

### 一、发展趋势

**模型寿命正在坍缩为"一年一签"。** 新智元 11-01 统计 OpenAI 与 Anthropic 官方下线页：GPT-4.5 在开发者接口只活了 137 天（2025-02-27 上线、04-14 接到通知、07-14 停服）；Claude 3.7 Sonnet 存活 11.8 个月，Opus 4 恰好 12.8 个月，Opus 4.1 从 2025-08-05 到 2026-08-05 一天不多一天不少——Anthropic 现在给每个在岗模型写的下线日期是"不早于上线满一年"。Gemini 4 Carbon 距 Argon 发布仅 28 天，旗舰模型月度迭代成为节奏。**产品层退役更猛**：谷歌 11-01 宣布编码智能体 Jules 年底关停、11-11 起先行只读，全量并入 Antigravity；扣子（Coze）10 月底专业版停服、模型批量下架、触发器/记忆/多智能体/日志/评测功能整体砍半，引发企业迁移潮。连"规范层"也在退役：OpenAI 10-29 新版 Model Spec 一次性退役了大量细粒度风格指引。**结论：智能体运维的变更日历里，"别人的退役日"正在超过"自己的发布日"。**

### 二、技术现状

**退役协议正在分化为三种形态。** 合同式（Anthropic"满一年"条款、OpenAI 给 GPT-4o/4.1 固定退役日 2027-01-14、阿里百炼给 Qwen3.5 旧版 14 个月长预告至 2027-01-19）：窗口长、日期硬，企业可排期。运营式（火山方舟三段式下线：10-19 通知并停止新用户→11-02 14:00 正式停服，全程仅两周，公告明言"到期未迁移会影响业务"）：窗口短，实质是限时迁移令。节奏式（OpenRouter 聚合层用 changelog 流水化追踪，模型"连续三次 410 即除名"）：把退役变成可订阅的数据流。**"能上生产"本身也在获得判据语义**：谷歌 10-30 仅凭变更日志两行字将 Computer Use 转正 GA——预览版与 GA 的分界就是"可写进生产代码并可追责"；Anthropic 的 pass@k/pass^k 区分（偶然成功一次 vs 全部尝试稳定成功）与 Fiddler 研究给出的"演示单次 60%、生产连跑 8 次跌至 25%"共同构成上线判据的量化语言。但量产门槛依旧惊人：36 氪 11-02 汇总 Forrester/Anaconda 数据，86%-88% 的 Agent 试点从未进入生产；Nylas 调查显示 54% 企业 90 天内经历过 Agent 错误，事故率随规模从 45%（1-5 个）升至 70%（20 个以上）。

**退役信息的可达性同样分裂。** 火山方舟靠短信与站内信通知，OpenAI 靠 deprecation 页与开发者邮件，OpenRouter 靠聚合 changelog，扣子企业靠社区文章才知晓停服范围——同一类事件有四种触达通道、零种机器可读标准。对只依赖某一渠道的团队，退役通知的实际到达时间可能晚于窗口关闭：没有订阅机制的企业，往往在调用报错那天才知道模型已经死了。换言之，"退役可观测性"目前还是每个团队的自建工程，而它本应是供应商的义务。

### 三、技术竞争力

| 方案 | 退役预告机制 | 迁移支持 | "可上生产"承诺 | 本期判读 |
|---|---|---|---|---|
| OpenAI | deprecation 页+固定退役日（GPT-4o/4.1→2027-01-14） | 迁移指南+推荐替代模型 | 预览/GA 分级明确 | 合同式范本；但 reusable prompt objects 亦在弃用，注册表层不稳定 |
| Anthropic | "不早于上线满一年"成文政策 | 订阅迁移自动完成（Max→Ultra） | pass^k 判据输出者 | 确定性最强，一年窗口可排期 |
| Google | 模型月度迭代+GA 两行 changelog | Jules 给 11-11/12-31 双窗口导出 | GA 语义=可追责背书 | "转正即承诺"，但旗舰 28 天一换加剧下游重评 |
| OpenRouter 类聚合层 | changelog 流水化（410 三次除名） | 路由层多供应商兜底 | 无 | 把退役变成可订阅数据流，对冲价值凸显 |
| 火山方舟 | 三段式公告（通知→停新→停服），窗口仅两周 | 公告内附建议迁移模型 | 无 | 运营式限时迁移令，短窗口是 SRE 最大痛点 |
| 阿里云百炼 | 14 个月长预告（Qwen3.5 旧版→2027-01-19）+ 月报集中披露 | 下线清单+替换推荐 | 智能路由入口独立上线 | 长预告+路由对冲组合最完整 |
| 扣子→ADP/Dify 类 | 平台级停服 | 迁移对标表+自然语言重建 | 功能砍半后无 SLA | 平台退役=模型+功能+记忆数据一起没，杀伤半径最大 |
| 本地实践（飞猪交付大脑） | — | 交付 4 环节大闭环（澄清→共识→编码部署→测试） | 验收标准前置进需求共识 | 把"变更"锁进流程而非发布事件 |

### 四、技术挑战

**退役传导链是新的故障传播路径**：扣子依赖火山方舟，方舟下线 kimi-k2.7-code，平台随之批量下架，企业侧应用静默失效——模型退役 2 周内穿透三层到达业务。**任务遗产无标准出口**：Jules 用户须在 11-11 前导出历史任务，扣子企业要迁走长期记忆与工作流定义，但"智能体的运行历史与产出物"如何迁移没有任何行业格式。**预告窗口与回归成本不对称**：火山两周窗口意味着一次被迫的"全量评测+影子双跑+金丝雀"被压缩到 14 天内完成，而这套发布门禁本身就值一个月。**上生产率与被退役率双向挤压**：86-88% 卡在进不了生产，进了生产的每年至少被强制重上线一次（模型退役），可靠性建设被周期性清零。

### 五、展望与建议

1. **把退役日历接入变更日历**：订阅各家 deprecation 页与聚合层 changelog，退役截止日按变更单管理，逾期风险与错误预算同表。
2. **version digest 增加"退役日期"字段**（深化第 28 期六维 pin）：pin 对象必须携带 EOL 时间戳，评审时" pin 了 137 天寿命的模型"应被门禁拦下。
3. **多模型路由是对冲而非优化**：百炼智能路由独立成入口、ADP 用 TokenHub 兜底证明，路由层的第一价值是"单模型停服不影响业务"。
4. **季度退役演练**：随机挑一个核心依赖，按真实下线节奏走一遍迁移（与第 3 期演练纵轴合流），把 14 天窗口的合规性提前验证。
5. **上线判据 pass^k 化+连跑验收写进采购条款**：向供应商索要"连续 N 次稳定成功率"，拒绝单次演示分。
