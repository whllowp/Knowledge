# AI-SRE 领域技术洞察报告 · 第 166 期

> **题眼｜协同治理面（Collaborative Governance — 多智能体编排、人机指挥权与责任归因 / 自治权的"控制面"）**
> 首次把"运维智能体的**自治权如何被委托、撤回、归因**"立为一等运维治理对象；与 159(确定性策略执行点·能不能做)/160(归因诚实度·根因对不对)/162(Agent 自身可观测)/164(知识复利·经验存错)/165(对抗鲁棒性·喂毒遥测)显式划界：彼管"单个 Agent 的动作/诊断/可见性/知识/输入",本期管"**当多个 Agent 协同、且人与 Agent 共享指挥权时,授权从哪来、停在哪、出了事算谁的**"——这是自治进入生产后的"控制面",最容易被当能力开关而漏做。

---

## 一、发展趋势

1. **从"单个自治 Agent"转向"自治舰队（fleet）的治理"。** 2026 下半年主题剧变：Google Actus 把"red button"端点做成可跨 fleet 撤销 L3 自治的一等对象；Virtana AOEM（10 月 28 日）让 Agent 通过 A2A 在毫秒级"招募"第三方 Agent 组建战争室——单 Agent 能做事已不是卖点，"一群 Agent 听谁指挥、谁担责"才是。
2. **协议层根治"混淆代理（confused-deputy）"。** bex.co（2026-09）给出范式金句：**A2A 携带诊断、MCP 携带权限、凭证绝不随消息跨 Agent 流动**。编码 Agent 把 deploy 调查打包成 A2A task 交给运维 Agent，附自身身份、不带任何 bearer token；运维 Agent 用自己的窄权限 MCP 工具、按自己的凭证执行回滚。把"谁能动生产"的信任边界下沉到协议边缘。
3. **人机指挥权从"二元开关"变为"连续授权光谱"。** Google 五档自治（L0 全手动→L4 全自治，承认尚未到达 L4、最佳公开结果 44% MTTM 缩减仍在只读辅助）；双托管 HITL（dual-custody）在改 Agent 层级前强制 SRE 签字；OpenAI 按代码风险分级——低险区 opt-in 自动批准、高险区加审或人审。授权成为可测量、可收回的连续量。
4. **"评测即油门"成为治理闭环。** Google IRM Analyzer 用真实事故人类轨迹做金标准评估，其结论**直接决定 Actus 授予的自治等级**——自治不是某个乐观时刻的配置开关，而是测量的输出（接 162/165）。
5. **标准与治理成形。** A2A 于 2026-08 并入 Agentic AI Foundation（与 Anthropic 的 MCP 同屋），Linux Foundation 报告 150+ 支持组织、在 IT 运维已有生产部署；但"支持组织数≠部署数"的清醒提醒同步出现。

## 二、技术现状

- **国际厂商/研究**：Google "AI in SRE" 参考架构＝AI Operator(推理)＋Actus(执行/零信任控制面/red button)＋IRM Analyzer(评估决定授权)，Safety Trifecta（透明/实时风险评估/渐进授权），Agent 专属身份≠人、短时凭证、速率限制＋熔断；OpenAI Sevbot（基于 Codex）事故中"醒来"、并行收集上下文、列缓解方案但**不擅自执行**、工程师指令才动，目标"常规事故自主、人回看记录"；Anthropic Claude Tag 用编排 Agent 派发子 Agent 并行查依赖、617 行调查 Skill＋lessons.md 自改进循环、修复留人拍板、读-only 起步；Virtana AOEM 用 MCP＋A2A 让多 Agent 共享 25,000+ 信号组建"Agentic 战争室"；bex.co 给出"A2A 携带诊断/MCP 携带权限/无 token 跨 Agent"的混淆代理根治设计。
- **国内厂商**：阿里 STAROps 以"数字员工(SRE Agent)"为执行主体，自定义职责/权限/工具/技能，高风险操作 HIL 人工确认、命中拒绝规则直接拦截，多智能体协同"感知→决策→执行→验证"闭环；腾讯 CloudQ 多云 AIOps 智能体＋全景图谱，企业"AI 调用 AI"多智能体协作网络，2026-10-29 生态大会升级；腾讯云 ES Agentic AIOps 四层架构（数据感知/ Skills & MCP / Agent 引擎多 Agent 各司其职 / 接入层），Skill 按"只读/可写授权"两维划权；字节火山智能运维助手定位"AI-native 智能编排与决策中枢"，Connect→Diagnose→Act→Extend→Govern 闭环、专家 Agent 自定义 IAM 角色按需只读取证、响应计划触发 Runbook 自动取证后**人工确认**。
- **本地讲义原型（173/173-kb，第 73 期起成组启用）**：周昕毅 10（携程 AISRE）三层演进 L1 预制流程→L2 A2A 自主编排→**L3 SRE 数字分身（长期身份/持续闭环/责任边界明确）**，白名单动作、恢复失败转人工、不可逆动作仍由人工负责；朱革 15（百度 AgentOps）点明"生产写操作缺统一权限/审批/限流/审计/回滚控制是规模化最大拦路虎"，安全管控覆盖用户/模型/系统/并发四类高危；肖汉松 22（蚂蚁 阿福 Agent 小队）从 Harness（单 Agent 自主迭代）到 Loop（**多 Agent 协同：外循环任务流转＋内循环修复验证**），铁律"先 Harness 后 Loop——单次迭代不可信时持续流转只会放大错误"，人机分工"人定义问题＋验收上线、Agent 负责中间迭代"；蒋烁淼 23（观测云 AgentOps）统一目录补语义、兼容 OTel。

**判读（反转）**：最强协同治理来自"**协议层把授权与诊断分离**"——bex.co 设计的"A2A 携带诊断、MCP 携带权限、凭证绝不随消息流动"从根上消除了混淆代理；Google Actus 的 red button 把"撤回权"做成跨 fleet 的一等对象。而国内三家（字节/阿里/腾讯）在"**协议层授权隔离 / 跨 Agent 责任归因 / 显式 kill-switch**"三列几乎全空或最弱——即："能卖多 Agent 协同平台的多，能证'授权不随消息乱跑、出事能精准归因到哪个 Agent 身份'的零"。

## 四、技术挑战

1. **授权随消息流动＝混淆代理穿了 Agent 外衣**。naive 做法让编码 Agent 把 kubeconfig/bearer token 塞进交接消息，两个 Agent 共用一身份——事后审计无法区分"运维 Agent 调查+人批准"与"编码 Agent 的 token 泄漏被滥用"（bex.co）。
2. **跨 Agent 信任边界不清**。A2A 的 Agent Card 验证的是"身份"而非"意图"：知道谁发的消息，不等于消息安全；跨组织/跨团队 Agent 协作时，入站消息策略（认证+内容校验+上下文隔离）常被漏做（cloudandsre）。
3. **责任归因缺位**。多 Agent 共同处置一次事故时，若无 per-handoff 审计信封（调用者身份/工具/参数/审批引用），事故复盘无法定位"是谁的 Agent、凭谁的授权、按哪条策略"动了生产。
4. **kill-switch 非标准化**。六家中仅 Google 公开跨 fleet red button；其余"人掌握执行键"停留在人工层，缺统一、可程序化触发的自治撤回端点。
5. **编排非确定性放大调试成本**。MAST 研究（1,600+ 条轨迹、7 框架）结论：更强模型**不会**消除协调失败——漏掉的约束、被降级的断言、未指定的终止条件才是主因；每任务 50–200 次模型调用，成本与不可复现性双重爆炸（sukruyusufkaya）。
6. **评测-授权未闭环**。多数平台把评估当部署后补丁；自治等级仍靠人工乐观设定，而非 IRM Analyzer 式"用真实事故轨迹测、按结果放/收权"。

## 五、展望与建议

- 立"协同治理"为一等运维对象，定义 `gov.*` 字段族（**第 116 个可量化市场空白**，六家零公开）：
  `gov.authority_non_transferable_rate`(授权不可随消息转移率) / `gov.cross_agent_handoff_auditable_rate`(跨 Agent 交接可审计率) / `gov.kill_switch_coverage`(kill-switch 覆盖率) / `gov.least_privilege_agent_identity_rate`(最小权限 Agent 身份率) / `gov.human_approval_threshold_defined`(人工审批阈值定义率) / `gov.responsibility_attribution_clarity`(责任归属清晰度) / `gov.a2a_boundary_enforced_rate`(A2A 边界强制率)。
- **落地建议**：① 凭证只走 MCP（能力）边缘、身份只走 A2A（协调）边缘，消息内**绝不**携带 token（bex.co 范式）；② 每个 handoff 写审计信封（调用者身份/工具/参数/审批引用），接 165 净化与 159 闸门；③ kill-switch 做成可程序化跨 fleet 端点（抄 Actus red button），而非仅人工；④ 自治等级由"用真实事故轨迹的评估"输出，而非人工设定（接 162/164）；⑤ 多 Agent 编排先定 trust boundary：同 runtime 用框架内消息、跨团队/跨组织才上 A2A（cloudandsre 规则）；⑥ 编排可观测：entry 点发 `request_id` 贯穿每次 tool 调用/handoff/升级，用 OTel 追踪跨 Agent 调用（MAST 类别分诊）；⑦ 接本地三原型——周昕毅 10 的 L3 数字分身责任边界、朱革 15 的统一权限/审批/限流/审计/回滚、肖汉松 22 的"先 Harness 后 Loop"防错误放大。
- **本期新观点**：把"自治权"重新定义为**可委托、可撤回、可归因的授权**，而非能力开关；根治混淆代理不在模型层而在**协议层的权限/诊断分离**；"评测即油门"应把自治等级变成测量的输出而非乐观的配置；多 Agent 协同的可靠性瓶颈是**结构与契约**（身份/权限/审计信封），不是模型智商——更强模型救不了漏掉的约束。
