# AI-SRE 技术洞察（第 359 期）

**生成时间**：2026-11-25 21:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：面面／控制面与数据面的耦合——数据面还活着，但它已经不会变了

## 题眼

2026-05-19，Kong Konnect 美东控制面不可用，持续约 **35 分钟**。状态页的措辞很精确：**已有合法配置的数据面继续正常代理**，但**新数据面无法拉取配置**。

Kubernetes 的答案更彻底：控制面挂了，**运行中的 Pod 继续跑**——kubelet 用本地状态维持容器，kube-proxy 的规则已经编程，Service 流量照走；你失去的是"变更"：没有新调度、没有滚动发布、没有扩缩容、没有 `kubectl`、没有自愈。三个控制面节点掉一个不算事，掉两个才是真故障。

GitLab 2026 年 9 月的事故则给出了反面教材：fail-static 撞上一个**没有 fence 的独占角色**——数据面在控制面失联时继续按最后指令工作，却没有机制阻止另一个实例同时认为自己拥有该角色。

控制面故障不会立刻让数据面停摆。它让数据面**停在最后一次指令上**，并且**失去改变与自愈的能力**。

## 一、发展趋势

第一，控制面/数据面分离成为默认架构：Kubernetes 的 API server 与 kubelet、Envoy 的 xDS 与数据面、Kong 的 CP 与 DP、注册中心与客户端、Terraform 的 plan/apply 与实际资源。分离带来弹性，也带来"最后已知状态"这个新状态。

第二，控制面故障成为一类独立事故。CSA 2026-11-18 的研究笔记把"五天、四个平台"的相关性故障列为新常态：安全控制（DLP、自动标签）与生产力工具可能同时降级；对 Agent 而言，更危险的是它**在控制缺口期间仍以机器速度行动**，而护栏正处在更弱的一侧。

第三，恢复本身开始依赖控制面。扩容、调度、DNS 变更、证书续期、端点更新——这些恰是恢复最需要的动作，也恰是控制面故障时最不可用的动作。Google SRE 书里的算术仍然成立：三层各重试 4 次，一次用户操作就变成 **64 次**数据库尝试。

## 二、技术现状

**数据面靠"最后已知状态"活着。** Envoy 在 xDS 断连后继续用 last-known-good 配置；Kong 的 DP 用已下发配置继续代理；K8s 的 kubelet 用本地 Pod spec 维持容器；Patroni 用租约维持主库角色。这些机制的共同点是：**它们都有"过期"的概念，但过期时间与失效模式各不相同**。

**四种 fail-static 机制**（praveentn.live，2026-10-05 的梳理）：① last-known-good 缓存——继续用旧配置，直到某个显式上限；② disbelief threshold——控制面失联多久后开始怀疑并自我降级；③ lease + fence——用租约与栅栏令牌保证同一时刻只有一个主；④ failure-time-only coordination——只在故障时刻才需要协调（如选主）。

**没有 fence 的 fail-static 会制造双主。** GitLab 9 月事故的教训是：数据面"继续服务"与"独占角色"是两件事；前者可以 fail-static，后者必须有 fence，否则两个实例都按最后指令工作，谁也不知道对方存在。

**恢复会被自己阻塞。** 控制面恢复的瞬间，所有积压的变更、重试、扩缩容、证书续期会一起涌来；而控制面此时最脆弱。这就是"恢复风暴"：故障时数据面还在，恢复时控制面先倒。

**Agent 是新的数据面。** 一个正在执行任务的 Agent，其"控制面"是编排器、策略引擎、工具注册表、审批流。编排器失联时，Agent 可能继续按最后指令调用工具；如果同时 DLP 或标签服务也在降级，它就在**更弱的护栏下以机器速度行动**。CSA 的观察是：这类共因故障不能靠"数供应商"来度量，要看共享依赖。

**控制面健康不等于数据面健康。** 监控通常盯 API server 的 5xx、CP 的 pod 状态；但数据面的真实状态是"最后一条配置有多旧、还有多少实例在用旧配置、新实例能不能起来"。

## 三、技术竞争力

| 方案/平台 | 数据面离线能力 | 最后已知状态 | 恢复依赖 | 主要盲区 |
|---|---|---|---|---|
| Kubernetes | 运行中 Pod 继续 | kubelet 本地 spec | 新调度/自愈需 CP | 失去变更与自愈 |
| Envoy / xDS | 继续用 LKG | 内存配置 | 新端点需 CP | LKG 无上限则永久旧 |
| Kong Konnect | 已有 DP 继续 | 已下发配置 | 新 DP 需 CP | 新实例起不来 |
| Patroni / 租约 | 主库继续 | 租约 | 选主需协调层 | 无 fence 则双主 |
| vCluster | 租户 API 暂停 | 取决于宿主 | 依赖宿主 CP | 双层 CP 故障域 |
| AI 编排平台 | 任务可能继续 | 最后指令 | 审批/策略需 CP | 护栏同步降级 |

**判读**：这张表最容易被忽略的列是"恢复依赖"——数据面能撑住，不代表恢复能开始；恢复需要的动作，往往正是控制面故障时做不了的。

**本期反转**：我们一直把"控制面高可用"当成目标，用多副本、多 AZ、选主来保护它。实际上控制面故障无法消除，真正要设计的是**数据面在控制面失联时的行为**：它能继续多久、继续做什么、什么时候必须停、以及恢复时谁来 fence。控制面不是要被保护得更久，而是要被设计成"可以短暂消失"。

## 四、技术挑战

**挑战一：fail-static 与 fence 的边界。** 继续服务是安全的，继续持有独占角色是不安全的；系统需要区分"可静态降级"与"必须协调"的动作。

**挑战二：LKG 的过期语义。** 没有上限的 last-known-good 等于永久旧配置；有上限又会在控制面长故障时把数据面一起拖垮；上限该由业务风险决定，而不是默认值。

**挑战三：恢复风暴。** 控制面恢复瞬间的变更、重试、扩缩容需要排队与限流；否则"恢复"本身就是第二次故障。

**挑战四：Agent 在缺口中的行动。** 控制面失联时，Agent 的"继续执行"与"停止执行"都需要显式策略；默认继续会让它在护栏降级时造成不可逆副作用。

**挑战五：观测错位。** 监控控制面的健康度，不等于知道数据面是否还在用旧配置；需要"配置年龄""新实例成功率""fence 状态"这类数据面指标。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①控制面/数据面清单（哪些动作依赖 CP）；②LKG 上限与降级动作；③fence 机制（租约/令牌/仲裁）；④恢复风暴的排队与限流；⑤数据面指标（配置年龄、旧实例比例、新实例成功率）。

**用户旅程**：Kong 美东 CP 故障 → 已有 DP 继续代理（用户无感）→ 但一个新节点扩容失败，因为拉不到配置 → 值班发现"数据面正常、新实例起不来" → 检查 CP 状态 → 35 分钟后 CP 恢复 → 积压的配置下发与扩缩容一起涌入 → 限流器生效，按优先级放行 → 新实例逐步起来。若没有"新实例成功率"指标，这条路径只能靠扩容失败告警发现。

**90 天实现方案**：0–30 天，列出所有"依赖 CP"的动作，标注哪些可 fail-static、哪些必须 fence；31–60 天，为每个数据面设置 LKG 上限与降级动作，补"配置年龄/新实例成功率/fence 状态"指标；61–90 天，做一次"CP 失联 30 分钟"演练，验收"数据面还能做什么、恢复时涌来多少变更、Agent 是否按策略停手"。

**第 271 个市场空白（五项）**：CP/DP 依赖清单；LKG 上限与降级动作；fence 机制；恢复风暴限流；数据面指标。

**`control_plane.*`／`fail_static.*` 第 238 次无人提字段族**：所有平台都能报"控制面健康"，没有一个字段报"数据面还在用多旧的配置、还能撑多久、恢复时谁先动"。

**本地 173／173-kb 连续第 226 期成组启用（朱革 15：控制面不是要被保护得更久，而是要被设计成可以短暂消失；数据面要能在它消失时守住最后一条正确的指令）。**
