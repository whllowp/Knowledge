# AI-SRE 技术洞察（第 365 期）

**生成时间**：2026-11-27 05:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：磁盘面／空间耗尽与 inode——写满不是容量问题，是写入路径的下一笔

## 题眼

2026-11-12，Akamai 披露了一次事故：他们把一台 BGP 边缘路由器**在清理磁盘之前就重启了**，这台失败的路由器带走了全球约 **23%** 的流量，持续约三小时。诱因不是流量，是抓包文件（pcap）持续写入磁带设备，磁盘写满后触发一系列降级。

这并非孤例。Google SRE 书里"磁盘满"一节统计过 **36 起**相关故障：填满速度可以外推、多数系统只监控使用率不监控**填充速率**、ext4 默认给 root 预留 **5%** 空间——"df 还有 5%"与"应用能写"是两件事。

## 一、发展趋势

第一，磁盘故障从"容量不足"转向"写入路径异常"。2026 年的复盘里，写满的触发者多是日志、抓包、镜像缓存、`/tmp` 临时文件、core dump、node-exporter 的 textfile；它们都不是"业务数据增长"，而是**某个组件的写入没有上限**。

第二，inode 耗尽重新进入视野。2026-05-02 的一则案例：磁盘空间还剩 13%，但 inode 用尽，`du` 看起来"几乎为空"，应用报 `No space left on device`；加磁盘、扩容量都不解决，只能找"谁创建了海量小文件"。

第三，Kubernetes 的磁盘压力把问题放大。kubelet 的 eviction 阈值（如 `<10%` 持续 3 分钟、`<5%` 持续 1 分钟）会触发驱逐；2026-08-05 的分析指出，很多集群只看到"Pod 被驱逐"，看不到"节点磁盘在什么时候、被谁填满"。

第四，清理本身成为风险。2026-10-31 的一篇运维笔记提醒：按"文件年龄"清理 `/tmp` 可能删掉正在被进程使用的文件；正确的清理依据是**所有权与状态**，不是年龄。

## 二、技术现状

**两种耗尽，一个报错。** 空间耗尽（blocks）与 inode 耗尽（小文件数量）都返回 `ENOSPC`，但解法完全不同：前者删大文件/扩盘，后者删小文件/调 inode 比例。只监控 `df -h` 的团队，会在 inode 耗尽时看到"还有空间"。

**写满后的行为比空间更危险。** 磁盘满时，日志先丢（`Failed to write file ... No space left on device`），接着队列阻塞、数据库进入只读、容器无法创建临时文件、kubelet 无法写状态；这些次级故障往往比"磁盘满"本身更难定位。

**填充速率比使用率更早。** 使用率是滞后指标：从 80% 到 100% 可能只要几分钟（一次日志风暴、一次 core dump）。Google SRE 的建议是按"填满时间"（time-to-full）告警，而不是按百分比。

**预留空间不等于可用空间。** ext4 的 5% 预留、XFS 的保留块、Kubernetes 的 `imagefs`/`nodefs` 分离，都会让"df 显示有空间"与"应用能写"不一致；容器里看到的磁盘还可能是 overlay 的上层，与宿主机不是同一个文件系统。

**清理是变更，不是打扫。** 删除日志文件时，若进程仍持有句柄，空间不会释放（deleted but open）；按年龄清理 `/tmp` 会删掉正在使用的 socket/锁文件；清理脚本本身可能写满日志，形成循环。

**"写不进去"可能先于"满了"出现。** 2026-06-30 的一份 9P 存储代理记录里，后端在容量基线不足时直接拒绝写入，前端看到的是间歇性失败而非持续 `ENOSPC`；systemd 的日志也会把 `Failed to write file ... No space left on device` 藏在其他错误里。写满的早期形态是**丢日志、丢状态、丢临时文件**，而不是一个漂亮的磁盘告警。

## 三、技术竞争力

| 方案/能力 | 度量对象 | 预警时机 | 误报/漏报 | 主要盲区 |
|---|---|---|---|---|
| `df -h` 使用率 | blocks | 滞后 | 漏 inode | 看不到填充速率 |
| time-to-full 告警 | 填充速率 | 提前 | 需历史基线 | 突发写入 |
| inode 监控 | inode 使用率 | 滞后 | 小文件突发 | 需单独配置 |
| kubelet eviction | nodefs/imagefs | 接近阈值 | 驱逐而非根因 | 谁填满的 |
| 日志轮转 | 单文件大小 | 按配置 | 轮转失败静默 | 句柄未释放 |
| 临时目录清理 | 年龄/所有权 | 周期 | 误删在用文件 | 清理自身 |
| 容量规划 | 增长趋势 | 很提前 | 突变无效 | 非业务增长 |

**判读**：这张表最容易被忽略的是"误报/漏报"列——使用率告警会在 inode 耗尽时漏报，inode 告警会在日志风暴时漏报；两把尺子必须同时有。

**本期反转**：我们一直把磁盘当"容量"资源，用百分比阈值告警。实际上磁盘是**写入路径上的共享资源**：它的故障形态是"下一笔写失败"，而不是"空间为零"；它先影响日志与临时文件，再影响业务；它有两种耗尽方式，而多数监控只看得见一种。

## 四、技术挑战

**挑战一：inode 与 blocks 双维度。** 只监控其一，另一半耗尽时监控全绿；需要两个独立告警，且能回答"是谁创建了小文件"。

**挑战二：填充速率的基线。** time-to-full 告警需要按文件系统/挂载点建历史基线；新节点、新镜像、新日志级别都会让基线失效。

**挑战三：容器与宿主机的视角差。** 容器内 `df` 可能是 overlay 上层，宿主机 `df` 才是真实；imagefs 与 nodefs 分离时，镜像写满与日志写满的处置不同。

**挑战四：清理的副作用。** 按年龄清理会删在用文件；删除已打开文件不释放空间；清理脚本可能把日志写满——清理必须先 dry-run、按所有权、并验证句柄。

**挑战五：磁盘满的级联。** 日志丢失让排障失去证据，队列阻塞让上游超时，数据库只读让业务停写；这些次级故障需要单独的降级策略（如日志降级到内存、队列落盘到独立分区）。

**挑战六：远程文件系统的"不可见余量"。** NFS/9P/CSI 卷的可用空间由后端决定，前端 `df` 可能显示正常、写入却被后端拒绝；这类故障是间歇性的，重试有时成功，监控与重试策略都会误判。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①blocks 与 inode 双维度告警；②time-to-full 预测；③按挂载点/容器/租户的写入归属；④日志/抓包/临时文件的写入上限；⑤清理的 dry-run 与句柄检查；⑥写满后的降级路径。

**用户旅程**：值班收到"节点磁盘 92%"告警 → 查 `df -h` 与 `df -i`，发现 inode 98% 而 blocks 仍有空间 → 查小文件创建者，定位到某服务的临时文件未清理 → 先按所有权清理、确认句柄释放，再为该目录加 inode 配额与清理策略 → 补 time-to-full 告警与 inode 告警。

**90 天实现方案**：0–30 天，补齐 inode 与 time-to-full 告警，按挂载点标注归属；31–60 天，为日志/抓包/临时目录设写入上限与轮转，清理脚本加 dry-run 与句柄检查；61–90 天，演练"磁盘写满"（日志降级、队列落盘、只读切换），并把"谁填满的"纳入复盘模板。

**第 277 个市场空白（五项）**：inode 与 blocks 双维告警；time-to-full 预测；写入归属；清理 dry-run；写满降级路径。

**`disk_fill.*`／`inode.*` 第 244 次无人提字段族**：所有监控都报"磁盘用了百分之几"，没有一个字段报"按当前速率还有多久写满、是谁在写、inode 还剩多少、清理会不会删到在用的文件"。

**本地 173／173-kb 连续第 232 期成组启用（闪英迪 28：磁盘满不是"空间没了"，是"下一笔写失败了"；先坏的从来不是磁盘，是写日志的那只手）。**
