# AI-SRE 技术洞察（第 242 期）

**生成时间**：2026-11-17 06:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为 2026-10-18 至 2026-11-17
**本期主题**：回填面／重建索引（Backfill & Reindex）——换了嵌入模型，旧向量还算数吗

## 题眼

2026-10-28，Google Cloud 发布 AlloyDB AI「零停机升级嵌入模型」：不原地改向量，而是把查询侧嵌入收敛到一个数据库函数，新模型在新列上回填，最后交换列名、改函数指向，一次事务完成切换。2026-09-07 的 embedflow 0.5.0 走另一条路：新模型先只在旧索引的候选集上重排，目标文档向量后台渐进物化。RAG-094 把话说得更直白：不同模型即使维度相同，向量空间与距离分布也可能不同，旧文档向量与新查询向量**不可比较**。Drift-Adapter（EMNLP 2025）则用一层轻量变换把新查询映射回旧空间，把全量重算推迟。CIPBench（arXiv 2610.25108，2026-10-17）在 10 个仓库、2,366 个函数单元、8,936 次真实更新上问的是：哪些代码变更**真的**需要重嵌入。

## 一、发展趋势

**第一，索引从「一次建成」变成「持续迁移」。** 嵌入模型半年一换，索引不再是静态产物，而是带版本、可回填、可切换的派生物。过去两年团队争论「用哪个向量库」，2026 年的问题已经换成「换模型时怎么不停机、不降质、可回滚」。

**第二，三条迁移路线成型。** 全量重建最直白，也最贵最慢；影子索引蓝绿（vecbee、WFGY 的 build-and-swap）把重建放到旁路，验收后用单指针切换；空间映射（Drift-Adapter、isotrieve 的 Procrustes/仿射变换）连重算都想省，先用小样本学一个旧空间到新空间的映射，把「必须全量」推迟成「可以慢慢来」。

**第三，元数据先行。** `model_id`、`revision`、`dimension`、`normalization`、`distance_metric` 开始被要求写进每个 chunk 或集合级别。没有这五个字段，迁移第一天就答不出「这条向量是谁产的」——而这正是后面所有验收与回滚的前提。

**第四，验收从「跑完」变成「等价」。** 固定黄金 query set、Recall@k、MRR、引用正确率、孤儿向量数，成为切换的门禁；RAG-093 还要求同时记录全量基线与增量链路，用「单位有效更新成本」而不是「这次任务花了多少」来决策。

## 二、技术现状

**Google AlloyDB** 的做法最像「数据库迁移」：应用只调用 `product_reviews_query_embedding(q)` 这类函数，模型被函数抽象掉；回填完成后 `ALTER TABLE ... RENAME COLUMN` 加函数替换，在一个事务里完成，失败即回滚。它解决的是「查询侧模型切换」的原子性，文档侧仍要提前回填新列。

**embedflow** 解决的是「回填期间怎么服务」：查询用新模型嵌入，但只在旧索引召回出的候选上打分，随着后台把目标文档向量逐个物化，候选质量逐步逼近全量新索引。支持 FAISS、Qdrant、pgvector、Pinecone、Milvus、Weaviate，并提供迁移分析与持久缓存。

**isotrieve** 把「映射层」做成产品：几百篇文档校准、拟合变换（支持 384→1536 跨维）、原地改写存储向量、最后用留出 query set 测 Recall@k/MRR；不达标就大声失败，索引绝不停在半迁移态。**Drift-Adapter** 是同一思路的论文版，比较 Orthogonal Procrustes、Low-Rank Affine、Residual MLP 三种参数化。

**vecbee** 自称「向量库的 Alembic」：`up` 建影子集合、原子切换，`down` 回退最近一次迁移，`status` 对账本地迁移文件与实际状态。**CIPBench** 则提醒：代码检索场景里，并非每次提交都值得触发重嵌入，时间、检索暴露、仓库级信号能预测影响，但三层信号并不总对齐。

现状判断：**工具链已经齐了，证据链没有。** 每家都能演示「切换成功」，但「切换前后是同一个检索器」这句话，仍要靠各家自己写的验收脚本自证。

## 三、技术竞争力

| 方案 | 代表 | 迁移方式 | 停机 | 回滚 | 证据强度 |
|---|---|---|---|---|---|
| 数据库内双列切换 | AlloyDB AI | 新列回填＋函数改指向＋事务交换 | 近零 | 事务回滚／切回旧列 | 厂商博客，无第三方复现 |
| 渐进物化 | embedflow 0.5.0 | 新模型服务旧候选，后台物化 | 零 | 保留旧索引即回滚 | 工具自述，缺大规模数据 |
| 空间映射 | isotrieve | 小样本拟合变换＋原地改写 | 零 | 保留原向量副本 | 有 Recall@k 门禁，样本自选 |
| 变换层 | Drift-Adapter | 新查询映射回旧空间 | 零 | 摘掉适配器 | EMNLP 2025 论文，语料有限 |
| 蓝绿影子集合 | vecbee | 影子集合＋原子指针切换 | 零 | `down` 回退 | 工具自述 |
| 蓝绿＋单指针 | WFGY | 离线重建、验收、单指针切换 | 零 | 指针切回 | 社区文档，非产品 |
| 全量重建 | 自建脚本 | 停写、重算、重建 ANN | 小时级 | 恢复旧快照 | 取决于团队 |
| 双写新索引 | 自建 | 新写入双写，旧数据回填 | 零 | 停双写、切回 | 取决于团队 |
| 混合检索兜底 | 自建 | 向量＋关键词，降权旧向量 | 零 | 调权重 | 弱，掩盖问题 |
| 人工抽检 | 自建 | 抽样看答案 | 零 | 无 | 不可审计 |
| 冻结模型不迁移 | 自建 | 不换 | 零 | 不适用 | 技术债累积 |

**判读**：能力层已经商品化——向量库、嵌入 API、蓝绿切换、映射层都能买或能抄。真正的分水岭在「证据」：谁能拿出这次切换的模型版本、chunk 版本、黄金集、逐档指标与审批记录，谁才敢说「切换没有改变检索语义」。

**本期反转**：以前把重建当运维动作，现在要把它当**语义发布**。重建完的索引不是「恢复原状」，而是一个新检索器上线；「回滚」也不是回到过去，是发布一个旧版本。

**判词**：「向量库、嵌入 API、蓝绿切换、映射层」全部可采购，「本索引由哪个模型、哪版 chunk、哪次切换产生，且切换前后检索等价」不可采购。

## 四、技术挑战

**其一，语义不可比。** 同维不同空间是最危险的情形：不报错、不崩溃，只是检索悄悄变差。混存旧新向量，等于让两个坐标系共用一个距离阈值。

**其二，半迁移态。** 新旧向量并存时，查询该用哪个模型？答案必须是「查询与文档同空间」。一旦路由写错，召回率下降会被误判成「模型不行」。

**其三，回填成本与优先级。** 全量重算的 token、GPU、存储与时间都是硬账；按访问热度、新鲜度、业务关键性排序，比「从头到尾跑一遍」更现实。回填期间的写放大也常被漏算。

**其四，一致性窗口。** 双写期新写入走新模型、旧数据仍旧模型，两个空间并存；需要版本路由或影子读，切换前还得把窗口内的增量补齐。

**其五，验收无标准。** Recall@k 对哪个 query set？黄金集自己会不会漂移？「跑完了」和「等价」之间，隔着一次统计显著性判断。

**其六，回滚不彻底。** 切回旧索引容易，切回之后新写入的向量怎么办——丢弃、重嵌入，还是留在新空间当孤儿？

**其七，记忆库同病。** Agent 长期记忆同样按嵌入存储，换模型等于重写记忆；写入门（第 238 期）刚立起来，回填门还没人提。

## 五、需求分解、用户旅程与实现方案

**需求分解（五项）**：① 每个向量可回答「谁产的、哪版、什么归一化」；② 切换前后检索等价可举证；③ 半迁移态可检测、可阻断；④ 回填成本可核算、可分批；⑤ 回滚后新写入有明确处置。

**用户旅程（平台 SRE）**：看到模型升级公告 → 盘点受影响的索引与 chunk 量 → 小样本校准、估成本 → 建影子索引并回填 → 黄金集验收 → 灰度切读 5%→50%→100% → 切写、保留旧索引 → 观察期满后清理 → 归档切换证据包。

**90 天实现方案**：
- **0–30 天**：给全部索引补 `model_id/revision/dimension/normalization/distance_metric`；每索引建 ≥200 条黄金 query set 与 Recall@k 基线；产出索引清单与负责人。
- **31–60 天**：搭影子索引流水线（回填队列、断点续跑、双写开关）；映射层先试点，把「必须全量」推迟；写切换与回滚 runbook。
- **61–90 天**：灰度切读每档看 Recall@k、引用正确率、P95 延迟、单次查询成本；旧索引保留 30 天；每次切换产出「证据包」：模型版本、样本量、指标对比、审批人、回滚点。

**第 170 个市场空白（五项）**：索引版本台账、切换等价验收服务、半迁移态检测、回填成本核算器、回滚后新写入处置。
