# AI-SRE 技术洞察（2026-11-24 07:00）· 第 310 期

## 题眼：知识腐化面／过期但确定的知识比缺失的知识更危险（Knowledge Decay / Stale Grounding / Runbook Rot）

Mastering Observability 给出一句足以当本期题眼的话：**"把 Agent grounding 在过期的 runbook 上，它会以完全确定的语气告诉你，你的系统过去是怎么工作的。"** 过去十四期（#294～#309）我们追着"证据真不真、能不能举证"跑：证据保真、关联键、调查污染、检测来源、事故边界、撤销生效、举证负担、入场保真——都在问**观测与陈述的可信度**。本期换一个方向：Agent 的推理还要踩在一批**静态前提**上——runbook、知识图谱边、历史复盘、组织记忆、Skill——它们被默认静止，而系统、版本、架构每天都在变。一条已经失效却仍被引用、且没有失效日期的 runbook 步骤，会让推理链完整、引用可点开、每条证据都真，结论却整体指向过去。对两处 index 检索"知识腐化／knowledge decay／runbook rot／知识时效"均无主线命中，确认为全新立面。

## 一、发展趋势

1. **"每次变更后重验知识"开始写进流程，但只写在最佳实践里**。Qiita 的 2026 实操指南把"Stale runbook：Agent 遵循一条与当前架构不符的旧手册"列为首要失效模式，控制措施是给 runbook 版本化、重大变更后复审、并让 Agent 在步骤与现网不符时主动标记；one2n 在 OpenSRE 复盘里要求"Agent memory 可被查看、编辑、删除，陈旧知识定期清理"。这是行业第一次把**删除**当成知识治理的一等动作，而非只做新增。
2. **知识回写成为产品卖点，但回写的正确性无人背书**。阿里云 AgentLoop 把"AI 评估 AI、问题反馈沉淀回知识库形成循环"列为核心能力；STAROps 把处置轨迹与验证结果转为可复用经验；腾讯云 AIOps 共创计划要"把一线运维经验转化为可复用的智能体技能"。回写闭环方向对了：若回写的是一次被误判的成功，等于**加速腐化**。
3. **标准层仍没有知识的有效期**。OTel GenAI 11-05 仍全量 Development，79 条未发布变更中 17 条破坏性，Schema URL 尚为 TODO；字段里有 `gen_ai.request.model`、`input.messages_ref`，却没有 `runbook.version`、`knowledge.validated_at`。行业能追踪模型调了什么，追踪不了**它信了什么、那条知识上次被现实校验是什么时候**。

## 二、技术现状

知识腐化的破坏方式很特殊：**缺失的知识会触发追问，过期的知识触发确定性的错误**。Vedcraft 的 SRE Agent 五条经验把"Knowledge base：Freshness and retrieval quality——陈旧 runbook 误导系统"列为与工具数量、工具输出校验并列的检查项；Unblocked 的观察更直白："如果'知道我们过去的事故'指的是去年写在 wiki 里的那份，Agent 只有在有人链接或上传过时才拥有它们。"Stack Overflow 2026 调查里 61% 开发者用 AI 调试，只有 20% 用于生产部署/运维，93% 要求来源归属——运维侧的知识供给远未成熟。

11 月 21 日 OpenAI 的 211 分钟全站中断是一次鲜活的"组织知识过期"样本：两个 Postgres 只读副本同时失效，而它们在认知里是"备份"，实际上承担实时查询、且 Primary API 提供全栈用户认证与服务间认证——副本是**承重的**；跨区域拉起替换副本均失败。事后措施是暂停同类维护、按比例摘流开关、维护前评审与热备容量。这里暴露的从来不只是架构脆弱，更是"只读副本=闲置备份"这条**写进运维常识、却没随架构更新**的组织知识。Radar 在 SREGym 上的 CoreDNS 案例同构：任务把 Agent 指向 shop 命名空间，那里全是症状，真正原因在从未提及的 kube-system——按旧地图找，找到的每一条错误都是真的，却是别人的事故。

正面样例也开始出现。Chiron 的入场简报把"最新数据 1 秒前"和"Chiron 看不见什么"同时写进上下文，每条 lead 附为何关联，把**新鲜度显式化**；OTel Agent Harness 的 Weaver 检查里有个精巧设计：被临时接受的违规项记录在 `expected_violations`，**当 Weaver 不再报告该违规时构建失败**——因为那条豁免已经陈旧，应被删除。这正是知识条目"到期待复验"的机器化雏形。

## 四、技术挑战

- **确定性放大错误**：证据缺失会追问，知识过期会自信。openai 式"承重副本"的错误认知，配上一条完整推理链，比"不知道"危险得多。
- **回写闭环是双刃剑**：AgentLoop 把反馈沉淀回知识库，若反馈本身是被 #301 完成声明面／#294 证据保真面证伪过的假成功，回写就是把错误固化成权威；叠加 #308 举证负担，保持一条知识为真的成本随变更频率线性上涨。
- **知识边界不清**：Google 11-23 Agent Compute Engine 把 API key、OAuth 刷新令牌留在沙箱外由 Agent Gateway 注入——凭据分层已成共识；知识却仍被整体内化进 Skill 与权重，**外部易变知识没有对应的"网关"**。
- **评测装置自身会腐化**：SREGym 在 Agent 饱和后退役题目、Radar 95.2% 与 Chiron 100%（不同版本、不同客户端）不可相减；没有一套基准测"给同一事故配一条过期 runbook，Agent 会不会照做"。

## 五、展望与建议

提出第 231 个字段族 `knowledge.decay.*`：`knowledge_refs[]{id,type∈RUNBOOK|POSTMORTEM|SKILL|GRAPH_EDGE|AGENT_MEMORY,version,authored_at,last_validated_at,tied_change_id,owner}`、`freshness_days`、`changes_since_validation`、`live_state_probe[]{step_id,matches_live,observed_at}`、`feedback_writeback[]{source_incident,claim,validated_by,at,rollback_ref}`、`stale_removal[]{removed_ids,at,reason}`、`blind_spots[]`、`verdict∈FRESH|STALE|DRIFTED|UNVERIFIED`，缺省 `KNOWLEDGE_STALE_UNVERIFIED`。

具体动作：① 每条 runbook 步骤绑定变更 ID 与上次现网校验时刻，重大变更后强制重验；② Agent 引用知识前跑 live-state probe，步骤与现网不符即降级待确认并追问，不得进入 write≥act；③ 回写必须带来源事故号、验证者与时刻，错误回写可一键回滚；④ 建立"到期复验＋无人引用即删除"的知识清理器，借鉴 Weaver `expected_violations` 的自净模式；⑤ 评测新增"过期 runbook 注入"配对题，报 false-confidence rate 与跨运行一致性；⑥ 采购三问：能否导出每条知识的版本、有效期与校验记录？现网不符时是否自动降级？回写是否可追溯回滚？⑦ 信通院《云上 Agent 基准度量模型》"数据可信"一格扩为"数据与知识新鲜可信"，成十七层治理。

本地知识源（173 目录）本期首次重读余锦泽《Agent 的记忆不在对话里》：**记忆若只进不出、只写不验，就是确定性错误的生产线**；配刘凯宁三分扩第二十一分"这条结论依据的知识上次被现网校验是什么时候"、赵恒"知识的权威来源之外还要有失效日期"、蒋烁淼"秒查的前提是那张表还在"。
