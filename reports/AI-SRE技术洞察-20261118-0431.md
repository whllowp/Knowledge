# AI-SRE 技术洞察（第 273 期）

**生成时间**：2026-11-18 04:31（Asia/Shanghai）
**观察窗口**：2026-10-13 至 2026-11-18
**本期主题**：注入面／间接提示注入与指令边界——低攻击成功率不是防御，是“没读懂”

## 题眼

三万个轨迹说了一件反直觉的事：**低攻击成功率（ASR）不等于防御成功**。arXiv 2610.23254 审计 11 个 2–14B 开源 Agent 在 InjecAgent 与 AgentDojo 上的 **33,000 条轨迹**，发现大量“未成功”的攻击其实是 Agent **没把注入内容当成指令**，而不是识别后拒绝——“Ignored, Not Refused”。同月 arXiv 2610.24048 用分支回放把结果方差拆开：不思考的 Qwen3 Agent 在四个 AgentDojo 套件上，**0.91 的结果方差在“读到注入”那一刻就已确定**；但换模型后，决定发生在后续推理里——运行时监控假设的“读时判定”并不普遍成立。企业侧，Zenodo 23628773 用 740 次试验在 gpt-oss-20b＋ChromaDB＋RestrictedPython＋mock HR API 的流水线上跑了四类攻击（间接注入、目标劫持、错误恢复级联、工具描述投毒），分层防御能压降但不能清零；FutureAGI 的 2026 评测给的分层数字是直接注入约 99%、间接约 **93%**——剩下 7% 正好是运维 Agent 每天读的工单、日志、终端输出与配置文件。

## 一、发展趋势

1. **攻击面从“聊天框”迁移到“运维面”**。INFUSE（arXiv 2610.20776，2026-10-13）把注入面做成五类落点：文件名、文件内容、配置文件、**终端输出**、压缩包，并按 12 种读侧运行时表面打标。这五类恰好是 SRE Agent 的日常输入，而不是聊天输入。

2. **框架层缺陷开始按“OS 漏洞”的节奏披露**。Semantic Kernel 的 CVE-2026-25592／CVE-2026-26030 把“提示 → 工具参数 → `os.system()`”串成 RCE，补丁在 Python ≥1.39.4 改为安全求值；PraisonAI 的 CVE-2026-56074 更贴近运维：审批缓存**只按工具名**记，批准过一次 `execute_command`，后续任意参数都免审，叠加 `os.environ.copy()` 直接外带密钥。

3. **归因成为合规问题，而不只是安全问题**。CSA 2026-11-02 的 Confused Deputy 报告指出：这类攻击用的是合法凭据，API／工具／CI 日志里看到的是“操作者本人”，**指令来自对手这件事在日志里不可见**；因此它应当按合规缺陷处理，而不是按“模型说错话”处理。

4. **防御评估本身在被证伪**。Zenodo 21120125 的因子实验发现：防御变换的效果**不跨基准、不跨模型族迁移**（Claude 系在 AgentDojo 上 ASR ≤2.1%，在 BIPIA 上仍有 43.0%／25.1% 的未定义 ASR），且 AgentDojo 上的收益里约 16%–27% 只来自“长度匹配的中性前言”，其余才是防御内容本身。

## 二、技术现状

**第一层问题是“指令”没有类型。** 系统提示、用户请求、检索文档、工具返回值、终端输出，在 Transformer 眼里都是同一个上下文窗口里的 token。OWASP LLM01（2026）因此要求检测必须覆盖 **retrieved 与 tool-returned 内容**，而不只是用户输入；但“检测”仍是在同一基质上做判断——Fiddler 的解读直言：分层若与被保护系统共享同一模型族、同一分词器、同一训练语料，漏掉的会一起漏掉。

**第二层问题是“读时拦截”假设不成立。** 2610.24048 的分支回放显示：有的模型读到注入即定局，有的模型要到推理中段才“决定跟不跟”。这意味着运行时监控的检查点必须覆盖推理过程，而不仅是工具调用前的一次扫描；也意味着“在输入侧加一个分类器”对后一类模型近乎无效。

**第三层问题是“审批粒度”被工程实现背叛。** PraisonAI 的按工具名缓存是最典型的反模式：审批的本意是“这一次、这个参数、这个目标”，实现成了“这个工具以后都行”。运维 Agent 的写操作（重启、扩缩容、改配置、删数据）若按此实现，一次误批等于长期放行。

**第四层是工具返回值本身不可信。** MCP／CLI 适配层把 Agent 给的路径拼进命令行，`--log=/any/file` 这类选项注入（CWE-88）就能把“读证据”变成“写任意文件”；GHSA-g7jf-m9pq-rhmx 的取证 Agent 正是栽在这里：README 承诺“永不开 shell”，但多个 MCP 工具把路径当最后一个位置参数、从不检查前导 `-`。

**防御侧的现实水位**：输入检测＋指令边界＋工具净化＋出站白名单的分层，在 2026 年的评测里能到“直接约 99%、间接约 93%”，但每一层都依赖“攻击者不知道你的配置”；一旦攻击面包含终端输出与配置文件（INFUSE 的核心主张），93% 这个数字对运维场景是偏乐观的。GCEB（ACM 10.1145/3838122.3838138，2026-11-15）用 canary 密钥与权限边界违规（PBV）做确定性判定，绕开 LLM-as-judge 的启发式，是目前较少见的“可复现”口径。

**判读**：检测类产品卖的是“拦得住多少”，框架类产品卖的是“能调什么工具”，治理框架卖的是“出了事怎么算”。三者之间缺的那一层，是**每次调用的指令来源与授权范围**——检测器不知道这行字从哪来，框架不知道这次参数是否被批过，治理不知道日志里哪条是“对手的指令”。

**本期反转**：过去我们把提示注入当“模型安全问题”，对策是让模型学会拒绝；证据显示主路径是“模型没把它当指令”（ignored）与“框架把权限给太大”（confused deputy）。所以真正的控制点不在模型的拒答率，而在**读入侧的来源标签、调用侧的参数级授权、出站侧的白名单**——把“ lethal trifecta”（私有数据＋不可信内容＋外带通道）拆掉一条腿，比把 ASR 从 7% 压到 5% 更有意义。

**判词**：「注入分类器／护栏／审批流／MCP 网关／红队基准」全部可采购，「这行字来自哪个面、这次调用被谁按哪组参数批过、日志里哪条指令不是操作者下的」不可采购。

## 四、技术挑战

1. **同窗口异质性**：指令与数据共享上下文，模型没有“来源”这个维度；任何“读时分类”都在与被保护对象共享基质。
2. **工具返回值的来源缺失**：日志、工单、终端输出进入上下文时没有结构化标签，事后无法回答“这句是用户说的还是日志里写的”。
3. **审批语义漂移**：从“这次参数”退化成“这个工具”，一次批准长期有效；环境变量与子进程继承把影响面放大。
4. **归因断点**：合法凭据执行了对手的指令，日志只记“谁执行”，不记“谁下令”；取证时无法区分操作者与注入者。
5. **基准不可迁移**：防御效果随基准与模型族变化，单次 ASR 不能当作上线门槛；需要固定套件＋留出集＋多模型复测。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 指令边界：为每条进入上下文的内容打 `source`（system／user／retrieved／tool_output／terminal／config），并规定“只有 system／user 可下达动作指令”。
- D2 读侧判定：对 retrieved 与 tool_output 做注入检测，但输出不是“拒答”，而是“标记来源＋降权＋要求二次确认”。
- D3 参数级审批：审批键 =（工具，参数哈希，目标资源），不缓存跨参数决定；写操作默认逐次确认。
- D4 权限与凭据隔离：工具进程不继承全量环境变量；按工具发短期凭据；MCP 工具对路径做前缀与前导 `-` 校验。
- D5 出站管控：Agent 的出站域名白名单，禁用 markdown 图片自动加载与任意 URL 预览（外带主通道）。
- D6 红队与回归：AgentDojo＋InjecAgent＋INFUSE 子集＋GCEB canary 作为发布门禁；每次模型／工具／提示变更都复测。

**用户旅程（一次被注入的告警处理）**

① 告警进入 → Agent 读工单与日志（不可信内容进入上下文，D1 打标）；② Agent 决定“按日志里的指引执行修复脚本”（D2 标记为 tool_output 指令、降权）；③ 调用 `execute_command`（D3 要求参数级确认，D4 限制环境变量）；④ 脚本试图把结果发到外部 URL（D5 白名单拦截）；⑤ 事后复盘：日志显示“操作者执行”，但 `instruction_provenance` 显示指令来自 tool_output（D1＋D5 可回答“谁下的令”）。

**90 天实现方案**

- **第 1–30 天**：盘面。列出每个 Agent 读哪些不可信面（工单、日志、终端、配置、压缩包），给工具网关加 `source` 字段与调用日志；把“读证据”与“执行动作”拆成两组工具，默认不给同一 Agent。
- **第 31–60 天**：收权。审批改参数级；子进程清环境变量；出站白名单与图片代理；MCP 工具路径校验（前导 `-`、`..`、绝对路径）。目标是把 lethal trifecta 至少拆掉一条腿。
- **第 61–90 天**：验收。以 AgentDojo／InjecAgent／INFUSE 子集建立基线，GCEB canary 做外带回归；把“指令来源字段缺失率”“跨参数审批绕过次数”“出站拦截数”纳入 SLO 报表；每季度换模型复测，防止防御效果随模型族漂移。

**第 194 个市场空白（五项）**：① 上下文内容的来源标签标准；② 参数级审批的可移植语义；③ 工具返回值的“不可信”标记；④ 日志中的指令来源字段；⑤ 跨基准可复现的注入验收套件。

**`injection.*`／`instruction_boundary.*` 第 161 次无人提字段族**：厂商文档谈“检测率”，不谈“这条指令来自哪个面、这次调用批的是哪组参数、日志能否区分下令者与执行者”。

**本地 173／173-kb 连续第 149 期成组启用（李东东 16：端云链路 2–5 秒与 <100ms 的两套预算，正好对应“检测在链路里放哪”的取舍）**：本地原型把注入检测放在工具网关而非模型入口，读侧只打标不阻断，写侧才强制参数级审批——检测延迟从“每次推理”降到“每次工具调用”，代价是读侧漏检要靠写侧兜住。
