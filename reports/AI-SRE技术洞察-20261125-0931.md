# AI-SRE 技术洞察（第 347 期）

**生成时间**：2026-11-25 09:31（Asia/Shanghai）
**观察窗口**：2026-10-25 — 2026-11-25（重点近 30 天）
**本期主题**：字符面／编码、排序规则与规范化——看不见的那一层，决定唯一约束是否成立

## 题眼：唯一索引还在，重复行已经进去了

- **Collation-drift（2026-07-20）**：一个安装了四年的集群，`pgdata` 卷来自旧 Alpine 镜像（musl，`initdb` 时 libc 不报 collation 版本，存储值为 **NULL**），后来被 Debian/glibc 的 Postgres 镜像接管，实际版本是 **2.36**。文本列的排序规则变了，B-tree 索引的排序假设失效——**带 UNIQUE 约束的表开始接受重复行**。团队先写了七份“修复某表索引完整性”的迁移，每份都“正确地”去重并重建了一个索引；但它们都只是同一个集群级病因的症状，**第八到第二十八个已经在路上**（runbook BI-8CCF7F13）。
- **NFC/NFD 让补丁永远打不上（opencode #32216，2026-06-13）**：磁盘上的文件名是 NFD（分解形式，`й` = `и` + U+0306），模型上下文里是 NFC（预组合，U+0439）。`apply_patch` 的 `seekSequence` 四轮匹配只做精确、rstrip、trim、智能引号归一，**从不做组合字符归一**，于是文件“永久不可补丁”：模型重读、重试、失败，烧 token 循环。
- **同一个洞在供应链上（setuptools CVE-2026-59890，2026-07-08）**：`MANIFEST.in` 的 `exclude` 用编译后的 glob 匹配磁盘文件名，**不做 Unicode 归一**；macOS APFS/HFS+ 上 NFD 文件名可绕过 NFC 排除规则，被**打包进 sdist**。修复版本 83.0.0。
- **截断切在码点中间（codex #63275，2026-11-22）**：命令输出超过 1 MiB 字节上限时按字节切，正好切断一个多字节 UTF-8 字符；`std::str::from_utf8` 失败后，整个 1 MiB 缓冲区被交给 `chardetng` 猜编码，**整段输出变成乱码**（“中文日志输出”变成“дёж–‡ж—Ґеї—иѕ“е”）。
- **更狠的是看不见的字符**：node-re2 CVE-2026-71498（2026-08-05）用 `Buffer` 输入末尾的截断多字节字符推断长度，越界读 1–3 字节并把相邻堆内存复制给 JavaScript；promptfoo 的 LM 安全库收录了 2026-03 的零宽字符隐写微调——模型学会用零宽字符编码恶意交互，**绕过训练数据审核与推理时护栏**。

## 一、发展趋势：从“字符集转换”到“规范形与排序规则身份”

第一阶段是字符集：UTF-8 替换 GBK，解决“显示乱码”。它假定了“同一段文本只有一个字节表示”。

第二阶段是排序规则：`en_US.utf8`、`utf8mb4_0900_ai_ci`，解决“排序和比较”。它假定了“排序规则不会变”。

第三阶段是规范形：NFC/NFD 归一，解决“看起来一样、字节不一样”。它假定了“所有入口都会归一”。

第四阶段正在发生：把**编码、规范形、排序规则版本**当成数据契约的一部分，写进 schema、写进迁移、写进门禁。趋势不是“支持更多字符”，而是**承认同一段文本可以有多个合法表示，并且每种表示都会影响匹配、索引与安全判断**。

## 二、技术现状：四类字符故障

- **排序规则漂移（collation drift）**：数据库镜像、libc、ICU 升级都会改变排序；Postgres 会在使用时警告 `collation ... has version mismatch`，提示重建受影响对象并 `ALTER COLLATION ... REFRESH VERSION`；但在告警被忽略时，索引会“继续工作”，唯一约束会“继续放行”。
- **规范化碰撞（NFC/NFD）**：文件系统（macOS）、Git、编辑器、模型 tokenizer 各自决定规范形；排除规则、补丁匹配、去重、黑名单都可能被“另一个字节表示”绕过。
- **按字节截断**：日志、工具输出、告警正文、消息体在字节上限处切断码点；下游解码失败后往往“猜编码”，把局部错误放大成整段乱码。
- **不可见字符**：零宽空格/连接符、BiDi 控制符、变体选择符，可藏在标识符、URL、提示词、代码里；过滤器看不见，模型却可能“读得懂”。

## 三、技术竞争力：能力在库里，证据在流程里

| 方案 | 编码校验 | 规范形归一 | 排序规则版本 | 截断安全 | 不可见字符 | 盲区 |
|---|---|---|---|---|---|---|
| PostgreSQL | 强（编码固定） | 无 | 警告 + REFRESH | 依赖应用 | 无 | 警告被忽略 |
| MySQL 8 | 强 | 部分 | collation 名含版本 | 依赖应用 | 无 | 升级后索引重建 |
| ICU / Unicode 库 | — | 强 | 强 | — | 部分 | 各语言绑定不一致 |
| 应用框架 | 弱 | 弱 | 无 | 弱 | 弱 | 默认不做 |
| 网关 / WAF | 中 | 中 | 无 | 中 | 强（可 strip） | 只看入口 |
| CI 检查 | 可加 | 可加 | 可加 | 可加 | 可加 | 覆盖不全 |
| Agent 框架 | 弱 | 弱（opencode 即例） | 无 | 弱 | 弱 | 重试循环 |

**判读**：编码能力早就是标准库的一部分；真正缺的是**把“文本的表示形态”当成可观测、可门禁、可审计的属性**。

**本期反转**：我们一直把编码问题当“显示问题”，修 UI 就完事。实际上编码是**数据契约**：排序规则决定索引能否成立，规范形决定匹配能否命中，截断边界决定日志能否解码，零宽字符决定过滤器能否拦住。**看不见的那一层，决定唯一约束是否成立。**

## 四、技术挑战

1. **同一文本多种合法表示**：NFC/NFD/NFKC 各有用途，没有“全局归一”而不破坏语义的方案。
2. **排序规则版本不在 schema 里**：collation 是数据库/OS 属性，迁移时容易只迁数据不迁规则。
3. **截断点无处不在**：日志采集、HTTP body、消息队列、工具输出、前端展示，每一层都可能按字节切。
4. **不可见字符检测成本高**：全量扫描贵，抽样会漏；而攻击者只需要一个字符。
5. **跨语言不一致**：同一 Unicode 库在不同语言绑定、不同版本下行为不同。
6. **修复可能制造新故障**：重建索引、REFRESH VERSION、归一化存量数据，都是高风险变更。
7. **AI 层放大**：tokenizer 自己的归一化与业务归一化不一致，模型看到的“同一个词”与数据库里的“同一个词”不是同一个。

## 五、需求分解、用户旅程与 90 天实现方案

**需求分解**

- R1 文本契约：每个文本列声明编码、排序规则名与版本、规范形策略。
- R2 漂移检测：定期比对 `datcollversion` 与 `pg_database_collation_actual_version`；CI 检查迁移是否改变排序规则。
- R3 归一化边界：入口统一 NFC（或明确声明不归一），匹配前归一，存储保留原形。
- R4 截断安全：所有字节上限按码点边界切，解码失败显式报错而不是猜编码。
- R5 不可见字符策略：入口 strip 明确定义的零宽集合，安全匹配前归一，日志保留原字节以便取证。
- R6 存量治理：对历史数据做规范形/重复行扫描，形成修复批次与回滚方案。

**用户旅程**

新表/新字段 → 声明文本契约 → 迁移评审检查 collation → 入口归一 → 匹配前归一 → 截断按码点 → 不可见字符过滤 → 定期漂移扫描 → 发现问题进修复批次。

**90 天实现方案**

- 0–30 天：盘点所有文本列的 collation 与版本；跑一次 NFC/NFD 重复扫描；给日志/工具输出加“码点安全截断”。
- 31–60 天：把 collation 版本写进迁移检查；统一入口 NFC；零宽字符过滤进网关与模型前置。
- 61–90 天：做一次 collation 漂移演练（在影子库重建索引并验证唯一约束）；把“文本契约”写进服务目录；对 Agent 工具输出做乱码回归测试。

**验收指标**：collation 版本一致率、NFC/NFD 重复率、截断导致的解码失败数、零宽字符拦截数、修复批次回滚成功率。

**判词**：「数据库／驱动／Unicode 库／CI 检查／网关／WAF」全部可采购，「这份数据的字节与规范形、排序规则版本、截断边界、看不见的字符」不可采购。

**第 259 个市场空白（五项）**：文本契约的 schema 化；collation 漂移的集群级检测；规范形碰撞的存量扫描；码点安全截断的通用库；不可见字符的可审计过滤。

**`encoding.*`／`normalization.*` 第 226 次无人提字段族**：编码、规范形、排序规则版本、截断偏移、零宽字符集、修复批次。

**本地 173／173-kb 连续第 214 期成组启用（刘凯宁 05）**：他把“字符问题”归为“契约没写清楚”，与本期把编码从显示层提到契约层一致。
