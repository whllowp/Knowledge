> **题眼**：Google 的 Project Chrysalis 演示把"首次缓解时间从 15–45 分钟压到 1.8 秒、5xx 错误率从 72.7% 降到 0.0%"写进官方博客。独立复核指出，那 0% 里有相当一部分来自一处限流器**主动用 HTTP 429 丢掉了 50 个请求中的 40 个**，且 1.8 秒是否含检测与诊断未说明、数据是仿真。与此同时，AIOpsLab 试炼场四段打分里，模型"修复"拿 86%–93%，"根因分析"只有 23%–31%。两件事拼在一起，戳破了 Agentic Ops 最容易被忽略的一层幻觉：**动作成功 ≠ 指标回绿 ≠ 根因消除 ≠ 用户可服务**。真正没人回答的问题是——*指标绿了，真是你这个动作治好的吗？*

## 一、发展趋势

2026 下半年，"AI SRE 能不能自己修"从演示议题变成采购议题。最近 30 天的三条线索，把它从"敢不敢让它动手"推向了更硬的一问：动手之后，疗效怎么算。

其一，**厂商集体把执行权留在人手里，理由是责任而非能力**。Pragmatic Engineer 10 月 27 日的深访里，Rootly、incident.io、ResolveAI 三家都被问同一个问题：有没有 AI SRE 真在工程师睡觉时值过班？答案含糊。OpenAI 内部工具 Sevbot 会收集细节、判断缓解手段，但**从不执行**，被明确指示时才动手；Google 的 ProdAgent 只通过 MCP 暴露的工具提建议（重启 Borg 任务等），不生成代码，带策略执行与审计轨迹——评价是"更多脚本、更少 LLM 的随机性"，为的是把搞坏生产的风险压到最低。11 月 11 日 New Relic 发布的 Autopilot Kubernetes Agent 跑 90 多个诊断探测器、基于 OpenTelemetry 的 Ground Truth 上下文引擎生成修复代码，同样强调 human-in-the-loop：生成修复 ≠ 应用修复。

其二，**自愈叙事开始接受反事实拷问**。Google 10 月 22 日的 Chrysalis 参考架构给了自愈最漂亮的数字，也给了最锋利的反例：错误率归零，靠的是把 80% 请求挡在门外；它的真正贡献不是那个 1.8 秒，而是把"每个动作的边际功劳"用步级 Shapley 归因算出来，并用四道闸门（输入/AST 净化、KMS 签名、OPA 策略加双签、防篡改审计）把权力锁死。**当厂商自己开始算"这一步到底帮了多少"，疗效归属就已经成为一等工程问题。**

其三，**评测侧暴露"修复分与分析分倒挂"**。AIOpsLab 试炼场以 Chaos Mesh 注入真实故障、87 道题过检测→定位→分析→修复四关，同题同环境下三款模型修复分 86%–93%，分析分仅 23%–31%（gpt-5.4：检测 62%/定位 56%/分析 31%/修复 93%）。修复远易于解释，意味着高分很可能来自"动作碰巧有效"或"评测只验故障清没清、不验是不是你清的"。

趋势判断：**下一轮 Agentic Ops 的分水岭不是"能不能自动修"，而是"能不能证明这次好转是自己修出来的"**。谁把反事实对照、抑制/丢弃记账、分面验证做成可导出字段，谁就拿到下一张门票。

## 二、技术现状

把一次"自愈"拆成四个环节，断点就清楚了：

- **动作层**：执行能力已不稀缺。New Relic 的 K8s Agent、腾讯云 Chaos Lab（支持 kill pod、延迟、丢包，乃至 LLM timeout / tool timeout 这类 Agent 特有故障）、Google 的现场合成限流补丁，都能产出可执行动作。真正稀缺的是**动作与好转之间的因果锚点**：不做这个动作，系统会不会也自己恢复？Chrysalis 的 Shapley 归因是少数正面尝试，但它是仿真里的步级打分，不是生产上的反事实对照。
- **指标层**：四种"绿"被混为一谈。**真治愈**（根因消除）、**症状抑制**（限流压住错误率）、**需求销毁**（429 把用户挡在门外）、**观测致盲**（遥测通路断了看不见）。11 月 13 日 Anthropic 一天两起事故是活教材：上午认证故障 09:58–11:58 解除，下午 13:09 起 API 又降级，到 14:36 核心面恢复时 connectors、Managed Agents、Security 仍在降级，定时任务晚点两个多小时甚至被跳过。**一个面绿，不等于整体绿**；按单面 SLI 宣布"已治愈"是系统性误判。
- **验证层**：验证被系统性低配。腾讯云提出的 AIOps Score = 0.15 检测 + 0.25 诊断 + 0.20 动作 + 0.15 安全 + 0.15 验证 + 0.10 成本——**验证与成本合计只占四分之一**；Dynatrace 10 月更新明确写着 "A recommended fix isn't an applied fix"，要求先复核 SRE Agent 的调查发现再决定下一步，并把执行日志留痕。而 ResolveAI 第二代翻车正是**验证者不独立**：让同一 Agent 给自己提出的假设打分，它几乎总是确认第一个猜想。
- **基准层**：Edge Delta 的 AI SRE Arena 用 21 个标准故障场景、AI 裁判对固定答案打分，方向是中立化；但一旦"修复分"不与"分析分"分离上报，榜单就会系统性地奖励碰运气。AIOpsLab 的倒挂数据说明，当前基准测出的高分**不足以支撑"会修"的结论**。

## 四、技术挑战

**第一，反事实在生产上几乎不可做。** 事故不能重放两遍：一遍做动作、一遍不做。Chrysalis 用离线反事实模拟（BigQuery 回放 400 个候选限流策略，约 0.5 毫秒）绕开了这一点，但离线回放的前提是有导出的请求轨迹（exported request traces），且结论只对"同一流量模型"成立。多数团队没有这个底座，于是"修复有效"只能靠前后对比——而前后对比正好会被流量自然退潮、缓存自然回填、上游自行恢复污染。AIOpsLab 报告 gpt-5.4 平均 19 秒解题、glm 106 秒、deepseek 155 秒，速度差被解读为 MTTR 的量级差异；但如果慢模型只是等到了流量退潮，这个"快"就没那么值钱。

**第二，"绿"的定义权在出题人手里。** 429 丢弃换来的 0% 5xx，在错误率口径下是完美治愈，在用户可服务率口径下是 80% 失败。Splunk 的自动 RCA 只支持默认指标、自定义指标不支持；Rootly 被批"技术细节与评测方法披露有限"——口径不披露，分数就不可迁移。这与 #218（评测装置面）分工：那期管分数在什么装置下产生，本期管装置判"好"的那一列到底测的是治愈还是丢弃。

**第三，多面恢复缺乏汇总结论。** Anthropic 11-13 的复盘显示 API、connectors、Managed Agents、定时任务各自恢复时间不同，官方状态页四次更新逐步扩面。Agent 若以任一单面的 green 触发"已解决"并停止调查，就会把仍降级的面留在无人看管的角落——这正是 #224 灰失效在"恢复相位"的翻版。

**第四，验证者独立性与成本冲突。** 三家厂商的共识是验证者必须结构独立于调查者、最好换模型；但对抗代理有成本，而成本在 AIOps Score 里只占 0.10。于是真实系统里最常见的妥协，是让执行者顺手给自己打分——与 ResolveAI 第二代的翻车同构。

## 五、展望与建议

**新观点（对 #222 的镜像深化）**：#222 处理的是**坏事归因**——这次部署是不是这次事故的原因；本期处理**好事归因**——这次好转是不是这个动作的结果。两者共享同一条纪律：时间上先后发生，不构成因果。坏事故里我们把"最后一根稻草"误当负重的原因；好结果里我们对称地把"恰好在恢复前执行的动作"误当解药。**行业给坏事归因配了三段式报告，给好事归因连字段都没有。**

**建议一：立 `cure.attribution.*` 五字段（第 127 个无人提字段族）**——`action_to_recovery_causal_link`（有无反事实/回放对照，无则标 `ATTRIBUTION_UNKNOWN`）、`shed_vs_cured_ratio`（被丢弃或抑制的请求数 ÷ 真实治愈数，Chrysalis 仿真值 40/10）、`surface_level_recovery`（认证/API/连接器/定时任务分面恢复时间戳）、`analysis_repair_gap`（分析分与修复分之差，倒挂超阈值即禁止"会修"结论）、`verifier_independent_of_actor`（验证者是否换模型/换进程）。

**建议二：把"丢弃"从"治愈"里拆出来记账。** 任何限流、降级、熔断导致的成功，必须同时上报 `requests_shed` 与 `users_served`，否则 error rate 归零不许进 SLO 结算——直接堵住 Chrysalis 式的 0% 幻觉。

**建议三：恢复按分面宣告，禁止单面 green 触发结案。** 复用 #220 的 ack→acted 双时间戳，扩为 `degraded_at / mitigated_at / verified_at / all_surfaces_green_at`，缺最后一项不自动关单。

**建议四：本地知识的直接落地。** 第 116 期本地原型启用**泠乐 18《AI 写完代码，谁来验证？——手淘 TEKO「写—验—修」自主闭环》首次当主线**——全库唯一把"验"钉在"写"与"修"之间、而非附在末尾的实践（图片型讲义，正文据标题与笔记转述）；配 **17 李峥峰**（百万真实任务验证的确定性工程兜底）与 **05 刘凯宁**（结论/证据/待确认三分、工程交给工程）。判词：*本地把"验"做成闭环里不可跳过的一环，联网侧 2026 年才把"修复分≠分析分"测成倒挂、把"0% 错误率"拆出 40/50 的丢弃；两边都没把"指标绿了是你的动作治好的"做成反事实可举证字段。*

**下期候选**：`cure.attribution.*` 五字段 OTel GenAI 提案／限流-丢弃与治愈分离记账模板／分面恢复时间戳 SLO／自家历史事故"带动作 vs 不带动作"离线回放对照器／`analysis_repair_gap` 门禁与榜单脚注／独立验证者换模型最小实现／信通院六维补"疗效可举证率"格。
