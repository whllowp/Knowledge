# AI-SRE 技术洞察（第 128 期）

**生成时间**：2026-11-11 10:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：模型同一性面／静默更新面（Model Identity / Silent Update）——ID 没变，模型换了；pin 的是名字，不是权重

---

## 题眼

08-12 被 AIES-26 接收的 arXiv 2608.11803 做了一件审计式的事：抽查 9 家一方 API 供应商与 7 家第三方推理托管，问同一个问题——**你文档里评测的那个模型，和现在服务我的这个模型，能不能被外部证明是同一个？** 答案是不能：**没有一家发布了让外部验证「所服务制品＝文档所指制品」的信息**。供应商可以静默地改行为——微调、分类器更新、系统提示修订、检索变更、路由变更——**不披露、不升版本、不重评**。同月 09-15 的 κ-Identity 给出检测侧：客户端抽取每次输入输出的低分辨率结构特征，从自然流量学一个 per-agent 基线，用窗口化双样本检验检测**模型替换、持续注入与漂移**，判定结果签成 JWT（κ-Proof），任何第三方可离线验证。**SRE 的常识是「pin 版本」；这期说的是：你 pin 的只是一个名字。** 名字后面可以是同一套权重，也可以是昨天刚换的后端——**你没有任何外部可验的方式知道差别**。

## 一、发展趋势

**趋势一：托管模型的「链式保管」在实践上断裂。** 评测报告、系统卡、事故复盘都指向一个模型；但服务端可以换权重、换路由、换系统提示，**证据链只到名字，不到制品**。2608.11803 的结论不是「某家不透明」，而是「整类供应商都没有可验证的保管链」。

**趋势二：静默更新从「运维问题」升级为「治理问题」。** 论文提出三段式行为触发（Three-Part Behavioral Trigger）：达到某类行为变化就触发披露或重评义务；**把「何时该说」从公关判断变成可定义条件**。

**趋势三：行为指纹从学术走向可移植证明。** κ-Identity 的核心不是检测算法，而是**证明的形式**：第三方拿 JWT 就能验，不需要访问权重、原始提示或响应。**这让「模型同一性」第一次可以跨组织写进合同与审计。**

## 二、技术现状：四条静默路径，一条证据链

**路径一：权重微调。** 同名端点后端换 checkpoint，行为分布缓慢移动；**没有版本号，就没有变更事件**。

**路径二：分类器与安全层更新。** 拒答率、改写风格、工具调用倾向会变；这类变化常被当作「安全改进」，**不在变更单里**。

**路径三：系统提示修订。** 托管方在服务端加一句「优先简洁」或「不要执行危险命令」，**你的 prompt 没改，行为变了**。

**路径四：路由与检索变更。** 同一 alias 路由到不同后端（118 期：15 个 alias 只塌缩成约 5 种计费签名）；RAG 索引更新也会改答案。**alias 不是模型身份。**

**为什么供应商可以静默：因为没有「升版」这个动作。** 在线服务改权重不需要发版，改系统提示不需要发版，改路由更不需要；**「持续改进」在工程上是优点，在可验证性上是缺口**。供应商不是隐瞒，是压根没有一个「版本事件」可供披露。

**证据链现状：只能自证。** 供应商给评测、给系统卡、给版本说明；但这些都是**关于某个制品的声明**，不是**对所服务制品的证明**。κ-Proof 这类可验证凭证是第一个「外部可验」的形态，但作者自认仍是概念与架构，**检测性能留待后续实证**。

## 四、技术挑战

**一，pin 的语义太弱。** pin alias 不 pin 权重；pin 版本号不 pin 路由；pin 系统卡不 pin 服务端提示。**任何一层都能变。**

**二，静默更新不可见。** 没有变更事件、没有 diff、没有回归触发；SLO 与基线悄悄失效，**直到事故才被发现**。更麻烦的是基线本身：你上季度定的「正常拒答率 3%」，这季度可能已经是 5%，**而看板仍按 3% 报警**。

**三，检测与隐私冲突。** 行为指纹要采样输入输出；客户端特征化能降隐私风险，但**仍需要用户同意与留存策略**。

**四，证明的边界。** κ-Identity 自认四条结构限制：观测统计全同的系统不可区分、行为通道测不出意图、更深层替换无法靠访问基质恢复、跨模态组合才可辩护。**证明「是同一个」比证明「不是同一个」难。**

**五，合同没有触发条件。** 「重大变更需通知」是主观条款；没有三段式触发，供应商可以说「这次不算重大」。

**六，回归成本落在买方。** 每次静默更新都要重跑评测；**没有自动探针，就只能等下次事故当回归**。

**七，证明的信任根还是供应商。** JWT 由谁签？供应商自签只是「自证」的另一种形式；第三方公证、硬件 attestation 或跨供应商互验，才谈得上独立。**没有信任根，凭证只是一张更正式的声明。**

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `model_identity.*` 字段**：`endpoint`、`claimed_model`、`observed_fingerprint`、`baseline_window`、`drift_score`、`proof_ref`。
- **R2 连续探针**：固定探针集（行为、拒答、工具调用、格式）每日跑，与基线做双样本检验。
- **R3 制品钉版**：alias＋后端 commit／模型卡哈希＋服务端提示摘要，三者一起 pin。
- **R4 漂移门禁**：漂移超阈值 → 自动重跑评测 → 未过门禁则降级或切备用。
- **R5 合同条款**：披露义务＋三段式触发＋重评权＋证明格式（可验证凭证）。
- **R6 证明链**：跨组织用签名凭证（JWT/JWKS）交换，不传原始数据。
- **R7 探针集版本化**：探针题、阈值、基线窗口都带版本；改探针等于改量具，须同步更新历史对比。

### 5.2 用户旅程

- **平台工程师**：接入模型 → 跑 7 天基线 → 每日探针 → 第 23 天漂移分超阈值 → 自动重跑评测 → 发现工具调用率降 6% → 切备用端点。
- **SRE**：事故复盘怀疑模型变了 → 调出 `model_identity` 历史 → 确认 3 天前有静默更新 → 把回归加入探针集 → 通知所有依赖该端点的团队。
- **采购**：合同谈判 → 要求「三段触发＋重评权＋可验证证明」→ 供应商接受两条、拒绝一条 → 记录风险。
- **审计**：拿到供应商 κ-Proof → 用公钥离线验签 → 确认服务制品与声明一致 → 签字。

### 5.3 实现方案（90 天）

- **0–30 天：建基线。** 定探针集；采 7–14 天自然流量；算 per-endpoint 基线分布。
- **30–60 天：装检测。** 窗口双样本检验；漂移告警接评测流水线；记录 `observed_fingerprint`。
- **60–90 天：进合同。** 把三段触发、重评权、证明格式写进采购模板；季度验一次证明。
- **90 天后：证明。** 与供应商互换签名凭证；抽查一次离线验签；把「证明可验」纳入供应商评分。

**第 82 个市场空白（五项）**：制品可验证率、静默更新披露率、漂移检出率、证明可移植率、重评触发覆盖率——无一内建；`model_identity.*`／`drift.*` 为**第 51 次无人提字段族**。本地 173／173-kb 连续第 46 期成组启用：陈忻 29「源码注入评估，跨引擎一致率 100%」＝全库唯一把「同一性」做成可测一致率的实践，本期首次当主线；配马云雷 31「离线通过≠长期稳定（工具契约／环境快照／漂移监控）」、孙鹏 11「底座升级时评测平滑迁移」。判词：**本地把一致性做成跨引擎比对，联网侧 8 月才承认「没有一家能证明所服务模型＝文档模型」；两边都没把「此刻这个端点是不是那个模型」做成可验签的凭证。**
