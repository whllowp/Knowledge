# AI-SRE 技术洞察 · 第 55 期 · 身份面（凭证面）运维——"谁在动手"决定一切证据的效力

**期数**：第 55 期（2026-11-03 21:00）｜**主线编号**：第四十六条｜**周期**：2026 年，重点近 30 天

---

## 一、发展趋势

行业默认状态是"借用身份"：多数生产中的智能体跑在开发者的 token、共享服务账号或贴进配置的长期 API Key 上——出了事，审计里只有人，没有 agent，无人能说清哪个 agent 替谁、以多大权限动了什么（NHI Management Group 口径）。过去三个月的转折在于：**身份对象正从"配置项"升级为"一等目录对象"**。Microsoft Entra Agent ID 把 agent 做成特殊 service principal（blueprint / agent identity / sponsor 三件套）；AWS AgentCore Identity 维护可枚举的 workload identity 目录；Google Cloud 给每个部署的 agent 发放 SPIFFE 身份、24 小时自动轮换证书，并声明"agent 身份不可被冒充"。

协议层同步收紧。MCP 2026-07-28 修订把 OAuth 2.1 从推荐变为强制：MCP server 是 OAuth resource server、所有客户端强制 PKCE、强制校验 token 签发方（iss），并新增 Enterprise-Managed Authorization（EMA）扩展，把"每个员工对每个服务器各点一次同意"换成管理员经既有 IdP 统一供给。标准线上，IETF WIMSE 发布 AI agent 适用性草案，AIMS 提案明确"不发明新协议、组合 SPIFFE + WIMSE + OAuth 2.0"；NIST 发布 agent 身份概念论文；CSA 与 Okta 的 2026 研究共同指认一组剪刀差——agent 部署速度远快于身份治理速度。

时点锚点最锋利的一个：**10-12 Google 宣布 OAuth 客户端 is_agentic 标记，11-11（距今 8 天）起 Workspace MCP 服务器拒绝未标记客户端，11-12 该设置在既有客户端上永久锁死**。一个月窗口、不可逆——agent 身份分类第一次以"硬截止日"的方式进场。

## 二、技术现状

**三层模型已经收敛**：身份池（签发边界，组织级长期）→ agent 身份（与 agent 资产 1:1 绑定）→ 运行时短时 token（随会话结束）。火山引擎 AgentKit 的表述最直白，且明文规定"不要为 Agent 配置长期 AK/SK"；三朵云与火山殊途同归。值得注意的是火山的连带清理：Agent 删除时 WorkloadIdentity 一并删除——身份生命周期首次与 agent 资产生命周期显式对齐。

**委托与冒充的分界线**落在 RFC 8693 的 act claim：impersonation 模式下 agent 领取用户权利，审计里分不出人机；delegation 模式下 token 同时记录 subject（用户）与 actor（agent），"双主体进每一个 token"是现状里最值钱的一条线。Microsoft 的 OBO 流、AWS 的 GetWorkloadAccessTokenForJWT（绑定用户 iss/sub）、Google auth manager 的三腿 OAuth，都是在同一分界线上的三种工程化。

**凭证不出模型**成为共同设计：AgentCore token vault 保存第三方 OAuth token 与 API Key 并绑定 agent+user 组合；火山凭据托管四类 Provider（API Key / OAuth2 / User Credential / Role Credential，后者把身份 token 的 claims 映射为云厂商临时凭证）；Google auth manager 兼任凭证保管与代理。agent 的 context 里只有短时票据，凭证明文永不进入提示词、代码与记忆。

**无会话化的代价**同样清晰：MCP 去除 session 后，原会话开头做一次的检查变成每请求必查；state handle 从服务端内部状态变成明文传递——九月的分析一针见血："能被提示注入读到的 handle 就是凭证"。反向案例也有：Apps Script 的 client ID 在 GCP 中不可编辑，无法标记为 agentic——平台做身份分类时，存量资产没有逃生门。

## 三、技术竞争力

|---|---|---|---|---|---|---|
| Microsoft Entra Agent ID | blueprint + agent identity + 强制 sponsor | 零凭证，凭 blueprint 联邦换发 | OBO 流，subject/actor 分离 | blueprint 侧托管 | blueprint 按设计冒充其 agent | Conditional Access 复用 |
| AWS AgentCore Identity | workload identity 目录 + agent 属性 | IAM 控制的 workload token | token 绑用户 iss/sub | token vault 绑 agent+user 组合 | 依赖调用方权限 | Runtime/Gateway 代管 |

| Google Workspace is_agentic | OAuth client 层一刀切分类 | — | 不改 scope 不绕 consent | — | agent 流量与非 agent 隔离 | **11-12 永久锁死** |

判读：三家云重心不同——微软管目录治理（sponsor 强制具名责任人）、AWS 管出站凭证代理、Google 管密码学不可冒充；国内火山把三层模型+凭据托管做成开箱即用。**共同空白：跨云的 agent 清单、赞助人与访问评审没有任何一家提供**——多云部署下 inventory 仍是用户自己的作业。这是继此前十二个市场空白之后的第十三个，也是第一个"身份治理"类空白。

## 四、技术挑战

1. **借用身份的存量清算**：先建身份再上生产约 1–2 工程周，事后补装 3–6 周，且补装期旧凭证仍有效——双重窗口。NIST 审计的 Top 发现是多数组织根本没有 agent 吊销程序。
2. **不可逆配置**：is_agentic 11-12 锁死，分类错了只能新建 client 并全链路改造；Apps Script 类旧资产无处安放。
3. **每请求执法**：无会话化后网关成为新的高价值组件；handle 注入等于凭证伪造，"session 开头检查一次"的组织惯性必须拆除。
4. **根信任转移**：secretless ≠ trustless——AWS IAM role 与 GetWebIdentityToken 成为新根，围绕它的信任策略、STS 权限与 audience 条件需要按生产身份边界审查，多数清单没更新过。
5. **委托链传播**：orchestrator → sub-agent 每层都要携带用户授权上下文；JWT 嵌套 act claim 有协议积木、没有运维胶水，多数部署靠自研。
6. **清单前置**：IAM 团队数不出环境里有多少 agent，其余一切治理无从谈起；无主孤儿 agent 是"带活凭证的影子 IT"。

## 五、展望与建议

- **最小治理四件套**：每个 agent 一个身份（不共享）+ 具名 owner（对齐 47 期"属主是承诺"）+ 短时凭证 + 以 agent 自身身份落审计——记录 API 调用与参数，而非只记 prompt。
- **双主体审计四字段**：subject（人）/ actor（agent）/ scope / correlation ID 进每条出站调用日志。这是对 54 期"漂移归属不可分辨"的直接回应：Google 已把 is_agentic 做进 OAuth 层，配置层与日志层的同名字段应立即跟进，否则身份分类止步于网关。
- **两个到期日进发布日历**：11-11/11-12（Google is_agentic）、2027-07（MCP 旧修订弃用）；"一份 client 混跑人与 agent 流量"列入技术债。
- **handle 即凭证**：state handle 纳入与密钥同级审查——它会被注入读走。
- **身份 SLO 三指标**：借用身份占比（越低越好）、委托双主体覆盖率、**吊销演练时延**——陌生人按"owner 已离场"剧本吊销一个 agent 需要多久。这是 52 期"恢复可复现率"在身份面的镜像：可吊销性不能由当事人自证，只能靠演练。
