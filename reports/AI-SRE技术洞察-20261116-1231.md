# AI-SRE 技术洞察（第 214 期）

**生成时间**：2026-11-16 12:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：通信面／Agent 间协议（Inter-Agent Protocol）——A2A/MCP 让 Agent 互相调用；但消息没有签名、没有配额、没有审计

---

## 题记

92 期说「工具供应链」，144 期说「编队」，199 期说「工作负载身份」，211 期说「双向冒用」，105 期说「重放参照」。这五件事在 **Agent 间协议** 上合成一个新暴露面：**MCP 解决「Agent 调工具」，A2A 解决「Agent 调 Agent」**（A2A 在 03-12 发布 v1.0）。**能力通了，治理没通**：**A 发给 B 的消息没有签名、没有配额、没有审计**——B 不知道 A 是谁、A 说了多少次、A 说的是不是原话。**Agent 之间的信任，默认是「同一个内网就是可信」**；而 211 期已经证明，**内网里既有假 Agent，也有 Agent 假装人**。**协议解决的是「能不能通」，运维要解决的是「通了之后谁负责」。** **而「谁负责」的第一步，是「这条消息是不是它发的」。**

## 一、发展趋势

**趋势一：Agent 从「单体」进入「互联」。** A2A/MCP 让调用标准化；**调用图从树变成网**（144 期）。**网里的每一条边，都是一次信任决策。**

**趋势二：消息开始要求可验证来源。** 签名/身份；**否则 B 无法判断 A 是不是 A**（199 期）。

**趋势三：跨 Agent 的追踪成为刚需。** 一次任务跨五个 Agent；**没有 trace 就拼不出时间线**（105 期）。

## 二、技术现状：两种协议，三种风险

**MCP：Agent→工具。** 有 schema；**但工具侧信任模型简单**（92 期）。

**A2A：Agent→Agent。** 有任务/消息语义；**但来源验证、配额、审计都还在补**。

**三种风险，通常一种都不防。** **冒名**（B 以为是 A）、**重放**（旧消息再发一遍）、**无界委托**（A 让 B 再让 C，层层放大）。

**现状：内网即信任。** 没有签名；**审计只能到「某个服务」**（199 期）。

**三层信任，一层都比一层少人做。** 传输（mTLS）、身份（工作负载身份）、消息（签名+nonce）；**多数只做传输，少数做身份，几乎没人做消息**。

**判读与本期反转。** 把编队讲清的是 144 期，把身份讲清的是 199 期，把冒用讲清的是 211 期；**六家云厂商 Agent 平台「消息签名／配额／委托上限」三列全空**。与 144 的分工：144 管「编队划不划算」，本期管**「消息可不可信」**；与 199 的分工：199 管「谁在调」，本期管**「调的那条消息是不是原话」**；与 211 的分工：211 管「人对 Agent」，本期管**「Agent 对 Agent」**。**而协议层治理常被当成「中间件团队的事」，于是没人做。**判词：**「MCP」「A2A」「服务网格」「消息队列」全部可采购，「举证这条 Agent 消息确实来自它自称的那个 Agent、且没被重放」不可采购。**

## 四、技术挑战

**一，内网默认可信。** 没有 mTLS/签名；**B 无法验证 A**（199 期）；**而 mTLS 只证明「通道是谁」，不证明「消息是谁发的」**。

**二，重放没有 nonce。** 旧消息重发；**B 当成新任务**。

**三，委托无上限。** A→B→C→D；**一次请求放大成 N 次**（144 期）。

**四，配额按服务算。** 一个 Agent 刷爆全体；**没有按来源限流**（120 期）。

**五，trace 断在协议边界。** 跨 Agent 丢 span；**时间线拼不起来**（105 期）；**而 trace 是唯一能还原扇出的东西**。

**六，消息体不可审计。** 说了什么；**日志里只有「调用成功」**（166 期）。

**七，成本随扇出放大。** A→B→C 层层调用；**一次请求变成 N 次计费**（143 期）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `msg.*` 字段**：`from_agent`、`to_agent`、`signed`、`nonce`、`delegation_depth`、`trace_id`、`verdict`。
- **R2 签名**：消息级签名/mTLS；**B 验 A**（199 期）。
- **R3 防重放**：nonce＋时间窗；**旧消息拒绝**。
- **R4 委托上限**：深度与扇出（如深度≤3、扇出≤10）；**超限拒绝**（144 期）。
- **R5 按来源限流**：每 Agent 配额；**不共享**（120 期）。
- **R6 指标**：签名覆盖率、重放拦截率、委托深度分布、trace 完整率。

### 5.2 用户旅程

- **平台工程师**：接入 A2A → 要求签名 → 验签 → 记 trace → 设委托上限。
- **SRE**：跨 Agent 故障 → 顺着 trace 找断点 → 定位到具体 Agent。
- **安全**：发现重放 → nonce 拒绝 → 告警。
- **审计**：抽查一次跨 Agent 调用 → 签名/深度/trace 齐全 → 通过。

### 5.3 实现方案（90 天）

- **0–30 天：签名。** 关键链路 mTLS/签名；nonce。
- **30–60 天：限流与上限。** 按来源配额；委托深度上限。
- **60–90 天：trace。** 跨协议传播；审计字段；季度演练；扇出成本核算。

**第 152 个市场空白（五项）**：消息签名覆盖率、重放拦截率、委托深度可测率、按来源限流覆盖率、跨 Agent trace 完整率——无一内建；`msg.*`／`a2a.*` 为**第 119 次无人提字段族**。本地 173／173-kb 连续第 109 期成组启用：肖汉松 22「全局调度器：分派、等待」＝全库唯一把「分派与等待」写成组件的实践，本期首次当主线；配 144 期编队、199 期身份。判词：**本地把分派写进调度器，联网侧 2026 年才把 A2A 发到 v1.0；两边都没把「这条消息来自谁、可不可重放」做成消息字段。**
