# AI-SRE 技术洞察（第 240 期）

**生成时间**：2026-11-17 04:31（Asia/Shanghai）
**观察窗口**：2026 年内，重点 2026-10-18 至 2026-11-17（近 30 天）
**本期主题**：等待面／时延预算（Wait Budget）——先定“等多久算坏”，再选模型和架构

## 题眼

- **yaitec（2026-08-13）**：时延目标要跟着任务走，而不是套一个通用 AI 基准；在 50+ 个项目后他们的经验是——**先给每个工作流定“最大有用等待时间”，再去选模型、工具和编排框架**；同一个 Agent，网站销售助手 1–3 秒、5 秒进警告区，而法律文档流水线可以等更久。
- **Salesforce Agentforce 延迟排障指南（2026-08-20）**：三个数字回答三个问题——**TTFT**（多久开始出现，决定“感觉快不快”）、**TTLT**（多久完全结束，决定长答案与下游）、**端到端**（从用户发消息到完整交付，最接近真实体验）；文本/聊天场景的经验线是**5 秒以内**。
- **Deadline Propagation for AI Gateways（2026-10-17）**：**timeout 限制单个活动，deadline 约束整个操作**；只有 idle timeout 会让“涓涓细流”的流式响应永远活着；**先定完成契约**（首个可见 token / 完整且校验过的答案 / 已受理的后台任务），再谈超时；调用方给的 deadline 要在准入处校验并夹紧，**绝不向下游派发比父 deadline 更长的预算**。
- **FutureAGI《What Is a Tool Timeout》（2026-05）**：工具超时是 Agent 的一种失败模式——**超时不返回信息**，Agent 不知道是失败、慢成功还是部分执行；轨迹要么挂起、要么盲目重试、要么带着无用信号回到规划器。**它看起来像模型错误，实际是基础设施问题**。
- **Cordum（2026-03）**：**每次重试都消耗预算、队列容量，有时还消耗外部副作用**；deadline 必须跨 Agent 跳显式传播，否则一个慢依赖卡死整轮；用带抖动的指数退避加硬停止条件，而不是开放式循环。
- **CHI 2026（10.1145/3772318.3790716）与 NYU Tandon（2026-04-23）**：把 TTFT 固定在三档做实验，**等待感知随任务类型变化**；NYU 的结论更反直觉——**AI 不是确定性系统，“越快越好”不一定成立**，等待与信任、感知质量之间存在非单调关系。

## 一、发展趋势

**时延从“技术指标”变成“产品与架构参数”。** 过去 SRE 把延迟当 SLO 里的一个数；2026 年的材料把它往前推了一步：yaitec 说先定最大有用等待再选型，Salesforce 把体验拆成 TTFT/TTLT/端到端三个数，deadline 文章说先定完成契约再谈超时，CHI/NYU 说快慢对感知的影响取决于任务。四条线合起来是一个转向：**“等多久算坏”不是优化出来的，是先约定、再分配、最后才测量**。等待预算因此成了与成本、可靠性并列的第三条架构约束——本地 173 讲义里“纯云端 2–5 秒，经营操作等不起；端侧目标 <100ms”正是把等待当成了端云取舍的输入。

## 二、技术现状

**预算要分段，不能只有一个端到端数。** 排队 + 预填 + 解码 + 网络 + 工具 + 重试，每段都要有预算（第 221 期的 TTFT 拆解）。只有端到端超时的团队，故障时说不清慢在哪一段。

**timeout 与 deadline 是两种东西。** timeout 管单个活动；deadline 管整个操作并向下传播。缺 deadline 的系统会出现“上游已放弃、下游还在生成”的浪费，以及“流式响应永不结束”的僵尸连接。

**完成契约决定超时语义。** 首字可见、完整校验答案、后台任务受理——三种契约对应的“成功”不同，超时后的补偿也不同：首字契约可以重试，完整答案契约要防重复副作用，后台任务契约要能查询状态。

**超时是失败模式，不是错误码。** 工具超时不携带信息，Agent 无法判断是否已执行；盲重试可能把一次“慢成功”变成两次副作用（第 229 期重放面）。

**硬编码预算会成为绑定约束。** OpenClaw 的 `waitForRun` 硬编码 30 秒，直接卡死慢本地模型——预算写死在代码里，比模型本身更限制能力。

**判读**：超时、重试、退避、网关都是货架能力；**“这一轮 Agent 的预算是多少、花在哪一段、还剩多少”没有一家把它做成贯穿全链的字段**。本期反转：第 221 期说“Agent 慢，可能是 GPU 排队”，本期补一句——**慢不慢要先看契约：首字慢和答完慢是两种病**。判词：**「超时配置」「重试」「退避」「网关」全部可采购，「举证这一轮的时间预算如何分配与消耗」不可采购**。

## 四、技术挑战

1. **预算与正确率的交易**：多想几秒可能更准；快而错在故障场景里更贵。预算要按任务价值定，不是按模型能力定。
2. **分段预算难归因**：排队、预填、解码、工具各段由不同团队拥有，端到端 SLA 无法定位到段。
3. **deadline 传播缺失**：跨 Agent、跨工具、跨异步队列时，父 deadline 容易丢。
4. **超时不可区分**：慢成功、部分执行、彻底失败在超时后长得一样。
5. **重试放大**：重试吃预算、吃队列、可能重复副作用。
6. **感知非单调**：太快可能降低信任（NYU），太慢直接流失；需要按任务类型校准，而不是全局最小化。

## 五、需求分解、用户旅程与实现方案

**需求分解（P0→P3）**
- P0 完成契约：每个入口声明是“首字/完整答案/后台任务”，并绑定不同的成功与超时语义。
- P0 父 deadline：准入处生成 `deadline_at`，逐跳传播、逐跳夹紧，禁止下游比上游更长。
- P1 分段预算：`queue/prefill/decode/tool/retry` 五段各设预算并落 `wait_segment`。
- P1 超时可区分：超时后先查副作用状态（幂等键/执行记录），再决定重试或补偿。
- P2 重试预算：每次重试扣预算，硬停止条件；抖动退避。
- P3 感知校准：按任务类型测“最大有用等待”，把放弃率、重试率、TTFT/TTLT 纳入看板。

**用户旅程（四条）**
1. 用户问一个诊断问题：首字 1.5 秒内出现（进度），完整答案 20 秒内交付；超过 5 秒显示“还在查”。
2. 工具调用超时：先按幂等键查是否已执行，未执行才重试；已执行则返回“已做，结果稍后”。
3. 用户离开：后台任务继续，完成后通知（第 239 期送达）；不占用前台等待预算。
4. 慢本地模型：预算可配置，30 秒硬编码改为按模型能力与任务价值设定。

**90 天实现方案**
- 第 1–3 周：盘点所有入口的隐式超时，标注完成契约；上线父 deadline 传播。
- 第 4–6 周：五段预算埋点与看板；超时后副作用查询。
- 第 7–9 周：重试预算与硬停止；抖动退避；流式 idle timeout 与总 deadline 分离。
- 第 10–13 周：按任务类型做感知实验（TTFT 三档），校准“最大有用等待”；季度演练“下游慢依赖”。

**第 168 个市场空白（五项）**：`wait_budget.*` 预算声明覆盖率、`deadline_at` 跨跳传播率、`wait_segment.*` 分段归因覆盖率、`timeout_side_effect_checked` 超时后副作用核查率、`max_useful_wait` 感知校准覆盖率。`wait_budget.*`／`deadline.*` 为**第 135 次无人提字段族**；本地 173／173-kb 连续第 124 期成组启用（李东东 16“纯云端 2–5 秒、端侧目标 <100ms”重读为：**等待预算是架构决策的输入，不是运维的观测结果**——本地把等待写成了选型依据，却没把 deadline 写成可传播的字段）。
