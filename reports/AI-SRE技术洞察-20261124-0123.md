# AI-SRE 技术洞察（第 315 期）

- 生成时间：2026-11-24 01:23（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：恢复面／崩溃后的现场重建——恢复不是读检查点，是重建“发生了什么”的共识

## 题眼

2026-10-14，东北大学在 Zenodo 发布了一篇标题很准确的论文：**《Recovery That Re-Asks the Model: Duplicate and Lost Side Effects in Crash-Recovered LLM Agents》**。它的问题设定只有一句话：持久执行系统靠“重放已记录的决策”恢复；但 LLM Agent 的决策本身不确定——如果 Agent 在“工具已产生副作用、结果尚未记录”之间崩溃，恢复时重新问模型，模型可能给出**不同的决定**，于是外部副作用被重复执行或永久丢失。

论文研究的是两个变量的交互：**决策记录的粒度**（记录 prompt？记录推理？记录工具调用意图？）与**幂等键的派生方式**（从哪里生成、何时生成、是否持久化）。它做了三轮预注册实验，结论是：只在“步骤级”记录、并在恢复时重新询问模型的系统，会出现可观测的重复与丢失。

2026-10-13 的 IEEE DataPort 数据集给了更具体的场景：A2A 任务调用 MCP 工具，**副作用已提交、任务尚未 finalize** 时进程退出；作者用 SQLite 副作用账本与版本化任务存储做了 20 对（40 次）配对实验，比较“按操作键的幂等”与“不做任务对账”的差异。

2026-11-06 的一份框架文档则把正确做法写成了机制：每次迭代检查点；工具调用先做**预派发写入**，再做**终态结果写入**；恢复时如果记录显示“已成功”，就把存储结果注入、**不再执行**；如果只有预派发记录，则进入对账而不是盲目重放。

## 一、发展趋势

**第一，恢复单位从“步骤”转向“副作用”。** 重放 transcript 只能恢复“说了什么”，不能恢复“做了什么”。副作用是否有唯一键、是否已提交、由谁签收，才是恢复的最小事实单元。

**第二，幂等键必须在派发前派生并落盘。** 恢复时重新生成请求号，是 229 期重复退款案例的根因；本期把它推进到 Agent 场景：键的派生规则本身要版本化，恢复只能用当时那个键。

**第三，恢复被拆成三段：对账、重建、自检。** 对账（发生了什么）、重建（会话/工具状态/权限/路由）、自检（当前能力是否仍满足任务）。三段缺一，恢复就是“看起来回来了”。

**第四，协议层开始区分“未重建”与“失败”。** 2026-11-15 的 IETF 草案明确：任务没有在新对话中重建，**不能**仅因此被解释为丢失、取消或失败；但“断链”会让跨对话的断言无法验证。恢复语义正在从“状态枚举”走向“证据可关联”。

**第五，自动恢复开始默认开启。** 2026-11-21 的一个 Agent 发行说明把“网关重启后自动恢复被中断会话”列为特性；能力越自动，越需要“恢复后先对账”的门。

## 二、技术现状

**本地 transcript 是声明，不是证据。** 它记录模型说了要做什么；外部系统是否执行、执行几次、结果如何，只有对方账本知道。

**崩溃窗口在“提交后、记录前”。** 工具已扣款/已发消息/已建工单，但结果没写回；恢复若重问模型，可能换一种做法，造成二次副作用。

**幂等键易失。** 键在内存、由随机数生成、或在恢复时按当前时间重算，都会让“同一次操作”变成两次。

**恢复后能力漂移。** 停机期间模型路由、工具版本、权限、配额、数据可能变化；恢复的会话按旧假设继续，工具调用失败或行为改变。

**恢复状态不统一。** A2A 任务状态、MCP 工具会话、框架检查点、外部工单状态各有一套；恢复时缺一张“跨系统对账表”。

**“语义恢复”被当成卖点。** 有项目宣称“不是重放 transcript，而是语义恢复”，并给出 8 步运行崩溃后 8 次 LLM 调用降到 1 次的数字；但其基准脚本未随包发布，属自报。

## 三、技术竞争力

| 方案 | 恢复正确性 | 副作用安全 | 能力自检 | 实现成本 | 主要风险 |
|---|---|---|---|---|---|
| 重放 transcript | 低 | 无 | 无 | 低 | 重复/丢失副作用 |
| 步骤级检查点 | 中 | 弱 | 无 | 中 | 崩溃窗口内重问模型 |
| 检查点 + 预派生幂等键 | 中高 | 中高 | 无 | 中 | 键派生规则漂移 |
| 副作用账本 + 对账 | 高 | 高 | 中 | 高 | 账本本身要可靠 |
| A2A 任务存储 + 恢复 | 中高 | 中 | 中 | 中 | 跨系统状态不一致 |
| 语义恢复（自报） | 未知 | 未知 | 未知 | 中 | 基准不公开 |
| 人工恢复 | 高（人判断） | 高 | 高 | 高 | 慢、依赖人 |

判读：买得到检查点、任务存储、重试、幂等库；买不到“这次副作用提交了几次、恢复时用的是哪个键、外部系统如何签收、当前能力是否仍满足任务”。

本期反转：我们一直把“恢复”当读检查点、接着跑。实际上恢复是一次**跨系统对账**：本地记录只是声明，外部账本才是证据；恢复的第一动作不是继续，而是确认“已经发生了什么、还能不能做”。

判词：「检查点／持久执行／任务存储／A2A 生命周期／MCP 会话／幂等库／自动恢复」全部可采购，「这次副作用提交了几次、恢复用的是哪个幂等键、外部系统如何签收、恢复后能力是否仍满足任务」不可采购。

## 四、技术挑战

**其一，模型不确定性。** 恢复时重问模型会得到不同决定；记录太细（每步推理）成本高，太粗（只记目标）无法重放。

**其二，幂等键的“当时性”。** 键必须由派发前的意图派生并持久化；恢复时重新生成，等于换了一次操作。

**其三，跨系统对账。** 数据库、支付、消息、工单、A2A 任务各有状态；没有一个公共的“操作 ID”贯穿。

**其四，能力漂移。** 停机期间工具/模型/权限变化；恢复后自检缺失，会把“不可用”当成“没结果”。

**其五，账本可靠性。** 副作用账本如果和业务库同故障域，崩溃时一起丢；需要独立持久化与写入顺序保证。

**其六，协议语义。** “未重建”不等于“失败”，但断链后断言不可验证；恢复要能区分“未发生”“已发生未记录”“记录不可信”。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要崩溃窗口检测、对账报表、恢复门禁。
- Agent 团队：需要决策记录粒度策略、幂等键派生规则、能力自检。
- 业务属主：需要知道哪些副作用可能重复、哪些可能丢失。
- 安全/合规：需要副作用账本的不可篡改与留存。
- 协议实现者：需要任务状态与断链语义的可验证映射。

**用户旅程（一次“恢复后重复退款”）。**

1. Agent 调用支付工具，扣款成功；结果写回前进程被重启。
2. 恢复流程读取检查点，重问模型“下一步做什么”；模型给出新的调用参数。
3. 幂等键按当前时间重新生成，支付系统视为新请求，二次扣款。
4. 对账发现差额，人工退款；复盘写成“模型不稳定”。
5. 真正缺的是“派发前派生并持久化幂等键”与“恢复先对账”。
6. 下一次改成“恢复即重跑”，又出现重复工单。

**实现方案（90 天）。**

- 第 1–2 周：定义副作用清单——哪些工具调用有外部效果、哪些可重放、哪些必须唯一。
- 第 3–4 周：幂等键规范——派发前派生、持久化、版本化；恢复只读不重算。
- 第 5–6 周：副作用账本——独立存储、预派发/终态两次写、操作 ID 贯穿；外部系统回执入库。
- 第 7–8 周：恢复门禁——先对账（已提交/未提交/不可信），再重建会话与工具状态，最后能力自检（模型/工具/权限/配额）。
- 第 9–10 周：协议映射——A2A 任务状态、MCP 会话、工单状态的对账表；“未重建≠失败”写进流程。
- 第 11–12 周：演练——在“提交后、记录前”注入崩溃；验证不重复、不丢失、可解释。
- 第 13 周：度量——恢复对账耗时、重复副作用数、丢失数、能力自检失败率。

**验收标准。** 任一次崩溃恢复，能回答：副作用提交了几次、用的是哪个键、外部如何签收、哪些状态不可信、恢复后能力是否仍满足。

**第 227 个市场空白（五项）**：副作用账本与回执；幂等键派生规范；恢复对账门禁；能力自检清单；跨协议状态映射。

**`resume.*`／`effect_ledger.*` 第 194 次无人提字段族**：`resume.reconciled_at`、`resume.effect_key`、`resume.receipt_id`、`resume.capability_check`、`resume.untrusted_state` 在 Agent 框架、A2A/MCP 与业务系统之间没有统一语义；平台只报“会话已恢复”。

**本地 173／173-kb 连续第 182 期成组启用**（闪英迪 28）：本地知识库把“声明”与“回执”分开记账；本期把恢复落成对账门禁与能力自检。
