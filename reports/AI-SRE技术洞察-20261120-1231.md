# AI-SRE 技术洞察（第 303 期）

- 生成时间：2026-11-20 12:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：一致性面／读己之写与写后可见——写入成功不等于自己能读到

## 题眼

2026-06-05 一份 Postgres 15 场景记录：把读流量切到只读副本后，用户开始报“我保存了，但它没了”——资料编辑成功，下一次页面加载显示旧值。更糟的是非计划故障转移：主库宕机、一个**还没收到最近提交**的副本被提升，几秒内已提交的事务看起来**消失了**。同一个根因的两个面：读副本落后几秒；故障转移提升了落后的副本。

2026-05-31 一个开源项目的 PR 把 Redis 客户端的 `readYourWrites` 显式设为 `false`：读取目录改走最近区域副本，避开“持续心跳写入触发的同步令牌等待”，换来跨区读延迟下降。**为了延迟，主动放弃“写完立刻读到”**——这个取舍被写进了一行配置。

同期数据库文档把代价写得很直白：DynamoDB 默认最终一致读，**强一致读的 RCU 翻倍**（每 4 KB 从 0.5 到 1）；CockroachDB 的有界陈旧读用动态时间戳换可用性；D1 的 Sessions API 用 bookmark 在副本间追踪“这个会话已经看到哪一次写”。

## 一、发展趋势

**第一，“读己之写”从默认假设变成显式能力。** 过去单体数据库里，写完再读天然成立；读写分离、多区域副本、无服务器数据库把这个假设拆掉了。现在要保它，得用会话固定、bookmark、LSN/GTID 等待、或强一致读——每一种都有成本，且都要在代码里显式声明。

**第二，一致性级别开始按请求计价。** DynamoDB 的 0.5/1 RCU 是最清楚的例子：强一致不是“更安全”，是**更贵**。当团队按成本优化时，最先被砍的往往正是那些“用户刚写完就要看到”的路径。

**第三，故障转移把“延迟”变成“丢失”。** 副本落后是延迟问题；提升落后副本是**数据可见性问题**——已提交的写在新主上不存在。2026-06 的场景记录里，用户看到的不是“稍后出现”，而是“消失”。

**第四，有界陈旧成为可配置语义。** 2026-03 的一个数据库提交引入 `bounded_staleness:5s` 会话级读取，注释写得很清醒：**一个拒绝所有副本的界，和一个正常工作的界，看起来完全一样**——都会把读全部送回主库。可用性与新鲜度的边界需要被观测，而不是被假定。

## 二、技术现状

**应用侧。** 常见做法是“写走主库、读走副本”，但连接池、负载均衡、重试都会把同一个用户的两次请求送到不同副本。会话粘性只在有会话时有效；无状态的 API 调用没有“上一次读到哪”的记忆。

**数据库侧。** Postgres 的同步复制能保证主库提交前副本已落盘，代价是写延迟；异步复制延迟低，但副本可能落后数秒。MySQL 的 GTID 等待、CockroachDB 的有界陈旧读、D1 的 Sessions bookmark，都是把“读到哪”变成可传递的令牌。

**缓存侧。** 写后失效缓存是最常见的“读己之写”伪实现：删缓存与写库之间的窗口、缓存回填的旧值、多级缓存的传播延迟，都会让“刚写完就读到旧值”。2026-05 的 PR 说明另一面：有时为了延迟，团队会**主动**放弃读己之写，但必须知道放弃的是哪条路径。

**可观测性侧。** 副本延迟通常以平均值或 P99 上报，但**没有“这个用户的这次读落后了多少”**。故障转移时，仪表显示“复制正常”，因为副本确实在复制——只是落后。

**AI 运维场景的特殊性。** Agent 的“写—读”往往跨工具：先调用写 API，再调用查 API，两次调用可能落到不同副本、不同区域、不同租户缓存。Agent 看到旧值后会“合理地”重试或改写，把一次一致性延迟放大成一次错误动作。

## 三、技术竞争力

| 方案 | 读己之写保证 | 延迟代价 | 故障转移表现 | 可观测性 | 适用场景 |
|---|---|---|---|---|---|
| 同步复制 | 强 | 写延迟高 | 不丢已提交 | 复制状态可见 | 金融、账务 |
| 异步副本＋会话粘性 | 弱（同会话内） | 低 | 可能丢最近写 | 仅副本延迟 | 读多写少 |
| Bookmark／会话令牌（D1） | 会话内顺序一致 | 低 | 依赖提升策略 | 有 bookmark | 边缘应用 |
| 强一致读（DynamoDB） | 强 | 成本翻倍 | 取决于后端 | 计费可见 | 关键路径 |
| 有界陈旧（CockroachDB） | 有上限 | 中 | 可用性优先 | 需自建度量 | 跨区读 |
| Redis readYourWrites=false | 主动放弃 | 最低 | 可能回退旧值 | 无 | 目录类热路径 |

判读：每种方案都能买到“某种一致性”，但没有一种附带“这次读到底有多旧”的证据。成本与语义是显式的，**用户可见的陈旧度是隐式的**。

本期反转：我们把“写成功”当承诺，把“读不到”当 bug。实际“写成功”只承诺**持久化**，不承诺**可见性**；可见性是会话级、副本级、甚至故障转移级的独立承诺。系统默认最终一致，而 UI 与 Agent 默认强一致——**断层不在数据库，在假设里**。

判词：「主从复制／同步提交／会话粘性／bookmark／强一致读／有界陈旧读／缓存失效」全部可采购，「这个用户的这次读落后了多少、故障转移丢掉了哪几秒的写、哪条路径主动放弃了读己之写、Agent 看到旧值后做了什么」不可采购。

## 四、技术挑战

**其一，承诺的作用域不清。** “读己之写”是对会话、对用户、还是对全局？跨连接、跨设备、跨区域时，承诺是否延续，多数系统没有答案。

**其二，故障转移的“已提交”语义。** 提升落后副本会丢失已提交事务；这不仅是可用性问题，还是**正确性**问题，而演练通常只验证“能切”，不验证“丢了多少”。

**其三，陈旧度不可度量。** 副本延迟是聚合指标；单次读的陈旧度需要携带版本号（LSN/GTID/bookmark），多数应用没有把版本传到读侧。

**其四，成本与一致性冲突。** 强一致读更贵、更慢；成本优化会悄悄把关键路径改成最终一致，而没有人复核“这条路径是否依赖读己之写”。

**其五，Agent 放大。** 一次旧值读取会触发重试、改写、甚至补偿事务，把毫秒级陈旧放大成分钟级错误。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 应用团队：需要标注每条读路径的一致性要求（强一致／会话内／有界陈旧／可接受最终一致），并在代码里显式声明。
- 数据库团队：需要提供可传递的版本令牌（LSN／GTID／bookmark），并暴露“单次读陈旧度”。
- SRE：需要在故障转移演练中测量“丢失的已提交写”，而不只是“切换耗时”。
- Agent 平台：需要在写后读的链路里携带会话令牌，避免跨副本读到旧值后触发错误动作。

**用户旅程（一次“保存后消失”事故）。**

1. 用户保存资料，写请求落到主库并返回成功。
2. 下一次页面加载被路由到落后 3 秒的副本，显示旧值。
3. 用户再次保存，或认为系统坏了；客服收到“数据丢失”投诉。
4. 值班查看副本延迟，平均值正常；无法定位“这个用户的这次读”落后多少。
5. 若此时发生故障转移，落后副本被提升，最近几秒的提交真正消失。
6. 复盘只能写“复制延迟”，写不出“哪些用户的哪些写丢了”。

**实现方案（90 天）。**

- 第 1–2 周：盘点所有“写后读”路径，标注一致性要求；把“可接受最终一致”的路径显式列入白名单，其余默认会话内一致。
- 第 3–4 周：在写响应中返回版本令牌（LSN/GTID/bookmark），读请求携带令牌；网关按令牌路由到足够新的副本，不满足则回主库。
- 第 5–6 周：暴露“单次读陈旧度”指标（读到的版本与最新版本之差），按租户与路径分解；副本延迟保留为聚合指标但不作为唯一依据。
- 第 7–8 周：故障转移演练加入“已提交写丢失”测量：切换前写入带序号探针，切换后逐一核对；把“丢失条数”写进演练报告。
- 第 9–10 周：缓存与读己之写——写后失效要等到失效确认；对目录类热路径显式声明“允许旧值”，并设置最大陈旧时间。
- 第 11–12 周：Agent 链路——写后读携带会话令牌；读到旧值时禁止自动补偿写，先确认版本。
- 第 13 周：红蓝演练——模拟副本落后 5 秒与故障转移，验证系统能回答“谁读到了旧值、丢了哪几秒的写”。

**验收标准。** 任意一次“保存后看不到”投诉，10 分钟内能给出：这次读落后多少、走了哪条路径、是否在故障转移窗口内、丢失的写能否列出。

**第 215 个市场空白（五项）**：按路径的一致性声明；可传递的版本令牌；单次读陈旧度指标；故障转移丢写测量；Agent 写后读的会话绑定。

**`read_your_writes.*`／`staleness.*` 第 182 次无人提字段族**：`ryw.session_token`、`ryw.read_lag_ms`、`ryw.replica_id`、`failover.lost_commits`、`staleness.bound_s` 在本期引用的方案里均无统一字段；各家只报复制延迟。

**本地 173／173-kb 连续第 170 期成组启用**（李东东 16）：本地知识库把“写成功”与“可见”分开记账，强调“延迟不是错误，错误是把延迟当不存在”；本期把它从存储层扩展到会话与故障转移。
