## 一、发展趋势：三条曲线在同一个 30 天窗口里交汇

过去一个月，Agent 记忆领域出现了一个容易被误读为"又一次框架发布潮"的现象。但把时间戳排开看，三条互不相干的曲线在 10 月中到 11 月初同时拐弯：

**曲线一：写入决策从 harness 代码里被切出来，独立成一个可训练、可评测、可替换的部件。**

10 月 15 日，腾讯混元开源 Hy-Memory 2.0，最关键的不是框架，而是随框架一起发布的 **Hy-Memory-30B-A3B**——一个 30B 参数、约 3B 激活的 MoE 模型，唯一职责是"记忆写入"：判断什么值得记、以什么结构存、新事实如何覆盖旧事实。它不是更大的通用模型，而是一个专职的记账员。

三天前的 10 月 13 日，TencentDB Agent Memory 发布 v2.0.3-beta.1，把"决策服务"做成可插拔件，并加入会话轨迹记录。11 月 2 日，阿里云 Memory 升级，官方在 HaluMem-medium 上把**记忆提取的召回率、准确率、F1** 放在最前——而不是问答准确率。

三个动作，同一个方向：**记忆系统的质量瓶颈被判给了"写入那一步"，而写入正在从 prompt 与胶水代码，迁移为独立模型或独立服务。**

**曲线二：记忆从"产品功能"变成"有资产类型、有权限、有计量单位的资产"。**

TencentDB Agent Memory 把它管的东西明确切成四类资产：Chat Memory、Skill、Wiki、CodeGraph；配 Memory Hub 做 ACL 与团队共享；计量单位是"0.02 元/万条·小时（存储）+ 0.01 元/Credit·小时（模型调用）"。当记忆开始按"条·小时"计费，"记下多少"第一次成为一项持续持有成本，而不只是一次 token 支出。

**曲线三：记忆的存放位置从"应用内"迁到"用户可寻址的工作区"。**

OpenViking 用 `viking://` 虚拟文件系统把 Memory / Resource / Skill 统一成路径（11 月 1 日仍在提交，41.6k stars，v0.5.2.1）；ReMe 用 `.reme/` 四层目录 + Markdown 作为事实源；dsh-memory-evolve 更进一步，把记忆作用域绑到 **git 分支**——同一项目不同分支可以有不同记忆。11 月 4 日 Notion 宣布通过 MCP 让 ChatGPT、Claude、Muse 读写同一份 Memories 与 Skills，把"共享大脑"落在用户自己的 workspace 里。

**判读**：这三条曲线合起来在做一件事——**重新分配"记忆的所有权、写入权与迁移权"**。所有权从厂商移向用户工作区，写入权从对话轮次移向一个专门部件，迁移权则从"导出对话"移向"可寻址的条目"。

## 二、技术现状：读路径已经收敛，写路径仍在四派混战

**读路径基本标准化。** 今天主流方案的检索栈几乎同构：BM25 + 向量 + RRF 融合（TencentDB、ReMe、MemOS 均如此），叠加分层加载——OpenViking 的 L0 一句话摘要 / L1 概览 / L2 原文，TencentDB 的 L0 原始对话 → L1 原子记忆 → L2 场景块 → L3 画像；再叠加"三限"预算控制（条数、字符、超时）。差异只剩下工程细节（目录递归、wikilink 扩展、行号级召回）。

**写路径则是四派并存，且互不兼容：**

1. **模型写入派**（Hy-Memory）：写入判定由专用小模型完成。收益是写入质量与 token 效率同时改善——LoCoMo 72.6%，单题 token 从 1159 降到 703；代价是记忆进入权重，不可读、不可逐条删。
2. **管线写入派**（TencentDB、阿里云）：异步管线把 L0 逐级蒸馏，代表实现是"符号化短期记忆"——把冗长工具日志压成带 node_id 的 Mermaid 图，token 降 61.38% 且保留可追溯引用。
3. **作业写入派**（ReMe）：`auto_memory` 把对话转成 daily 卡片，`auto_dream` 隔日把 daily 蒸馏进 digest，写入是显式 Job，可重跑、可审计。
4. **闸门写入派**（dsh-memory-evolve）：写入前先问人。回合内自审每 N 轮提炼候选，进 pending 队列，用户确认后才落盘。

**存储形态于是分成三轨**：文件轨（Markdown + frontmatter + wikilink，可 diff、可 git）、分层轨（L0–L3 + 资产类型，可治理、可计量）、参数轨（权重，可泛化、不可审计）。这三轨不是实现风格差异，而是三种不同的"记忆本体论"——它们的"一条记忆"根本不是同一个东西。

**一个必须点明的口径问题**：本期引用的分数几乎全部来自厂商自测（腾讯的 55.49 宏观均分、阿里的 56.82、TencentDB 的 76.10%），彼此用的 judge、数据集版本、上下文长度都不同。唯一可横向比较的是 8 月 12 日首发的 AML（Agent Memory Leaderboard）：MemoraX 58.0 居首，MemOS 第二，网易 NTES-MEMORY-SMART 第三（个性化 57.0），TencentDB 41.5 排第八但"规则与工作流执行"28.7 分居工业榜第二，Mem0 第九、MemPalace 第十、Supermemory 第十五。**注意这个排序与厂商宣传的排序并不一致**——这正是本期要强调的方法论问题：记忆的"总分"没有意义，能力剖面才有。

## 三、技术竞争力：主要方案对比

| 方案 | 记忆载体 | 写入决策机制 | 分层/结构 | 冲突与时效 | 治理与权限 | 可携带性 | 最强项 / 主要短板 |
|---|---|---|---|---|---|---|---|
| **dsh-memory-evolve** | 本地文件（五轨：档案/全局事实/项目记忆/项目日志/日记） | 回合内自审 + 人工确认（默认关闭） | 五轨 + 四轨待办 + 技能库 | 靠 git 分支作用域隔离；无自动冲突检测 | 无 ACL；单用户 | 强（可 git 同步到远端仓库） | 最强项：作用域最细（分支级）、可零残留卸载。短板：无多租户、无治理 |
| **ReMe（agentscope）** | Markdown + `.reme/` 四层目录 | Job 写入（auto_memory / auto_dream / auto_resource） | session/daily/digest/metadata + wikilink 图 | 链接扩展 + 时间衰减；冲突靠人工编辑 | 弱（本地单人/小团队） | 最强（文件即真相，可 git、可手改） | 最强项：人类可读可改、记忆可当代码管理。短板：写入质量依赖 LLM Job，规模化治理缺位 |
| **OpenViking（火山）** | `viking://` 虚拟文件系统（AGFS：localfs/s3fs/memory） | 会话结束后台蒸馏 + 显式 commit | L0/L1/L2 + Resource/Memory/Skill 三类 | 目录递归检索 + 版本化；冲突处理偏弱 | 中（多租户 peer + 账号隔离） | 强（路径化、可 grep、可导出） | 最强项：统一寻址、token 效率（-34%~-91%）、生态最广（Claude Code/Codex/Cursor/TRAE/DSH）。短板：AGPLv3 + 禁止整体改写再开源 |
| **Hy-Memory 2.0（腾讯混元）** | SDK 内三类记忆（chat/working/coding） | **专用模型 Hy-Memory-30B-A3B（3B 激活）** | 三层记忆 + 双系统（快回忆/慢图式） | 支持新旧事实覆盖、事件脉络合并去冲突 | 弱（SDK 级） | 中（MemHub 本地汇聚，Windows 缺） | 最强项：写入质量与 token 效率、代码记忆的 diff 链留痕。短板：写入不可解释、记忆进权重后不可逐条删 |
| **TencentDB Agent Memory** | 服务端（MemoryCore + 向量库）+ 四类资产 | 异步管线 + 可插拔决策服务（v2.0.3-beta.1） | L0/L1/L2/L3 + Chat/Skill/Wiki/CodeGraph | 分层覆盖 + 版本；符号化压缩保引用 | **最强**（Memory Hub、四级可见性、RBAC） | 中（资产可导出，强绑腾讯云） | 最强项：团队级治理与流程型任务（规则执行 28.7 分工业第二）。短板：总分不高（41.5）、云绑定 |
| **阿里云 Memory** | 托管服务 + 用户画像 | 规则 + 提取管线（可自定义字段与规则） | 记忆条目 + 画像，未强调分层 | 变更前先确认再更新 | 中（控制台查看/调试/追踪变更） | 中（MCP/CLI 接入 Codex、DSH、Claude Code） | 最强项：PersonaMem-v2 56.82（8 系统第一，9 维中 7 维第一）、HaluMem 提取四项第一。短板：生态与治理深度不及腾讯 |
| **Mem0** | 混合存储（向量+图+KV） | LLM 抽取 + 压缩 | 用户/会话/Agent 三级作用域 | 自适应衰减；冲突合并靠 LLM | 中（托管版含 GDPR 删除、多租户） | 中 | 最强项：生态与集成广度（~67k stars）、$24M 融资。短板：AML 仅第九，高阶能力弱 |
| **Zep / Graphiti** | 时序知识图谱 | LLM 抽取 + 双时序标注 | 事件子图（事件时间 / 摄入时间） | **最强**（可推理追溯性修正） | 中 | 中（Graphiti 开源） | 最强项：时序与溯源，LongMemEval 63.8%、LoCoMo 75.14%。短板：图谱成本高、写入吞吐受限 |
| **MemOS / EverOS** | 图服务 / Markdown + 内嵌索引 | LLM 抽取 + Mem2Skill 技能结晶 | 记忆立方 / 案例-技能双轨 | 三层漏斗去重（哈希→余弦→LLM） | 中 | EverOS 强（Markdown 源 + SQLite/LanceDB 索引） | 最强项：记忆→技能转化、AML 亚军。短板：个性化与规则执行偏弱 |
| **Letta（MemGPT）** | 有状态运行时（core/recall/archival） | Agent 自主决定保留/归档 + sleep-time 计算 | OS 式三层 + MemFS 文件层 | 自我编辑；一致性靠 Agent 判断 | 弱 | 中（MemFS） | 最强项：长运行自主智能体的自管理。短板：不可预测、难审计 |
| **Reglos（研究原型）** | append-only 个人记录 + 可改 harness | 失败轨迹→打补丁→**跨模型家族 critic 审查** | 偏好可被覆盖、事实可遗忘 | 显式 supersede / forget | 无 | 弱 | 最强项：把"harness 过拟合"当一等问题（PersonaMem-v2 61.3 / LongMemEval-S 84.0）。短板：未产品化 |

**四条判读：**

**（1）检索精度已不再是区分度。** 十家方案的读路径几乎同构，LoCoMo 上 70%+ 已成及格线。真正的分化出现在三个新维度：写入判定质量、治理颗粒度、可携带性。

**（2）国内三家在"写入治理"上领先，海外在"开发者体验"上领先。** 阿里与腾讯把"提取准确率""规则执行""ACL"当做第一指标，Mem0/Zep/Letta 则把"接入 50 行代码""可换后端"当做第一卖点。这不是技术高低，而是客户结构差异：前者卖给流程型 Agent（工单、审批、SOP），后者卖给原型与个人助手。

**（3）参数轨只有腾讯一家，含义被低估。** Hy-Memory 是唯一把"写入质量"与框架解耦的方案——它可以插进 Mem0 或 MemOS 当写入器而不换存储。这意味着记忆层可能出现"控制面/数据面"分离：存储与检索商品化，写入判定成为可采购的模型能力。

**（4）记忆开始有"持有成本"。** 三种计量单位已并存：条·小时（TencentDB）、Credit·小时（模型调用）、月订阅（Mem0 $19–249）。当记忆按持有量计费，"多记"从优化目标变成成本项——这会倒逼"遗忘"从功能变成财务手段。

## 四、技术挑战：写入是唯一会把错误持久化的环节

**挑战一：记忆污染把"一次性攻击"变成"永久性妥协"。** OWASP 2026 版已把 Memory & Context Poisoning 单列为 ASI06，与提示注入（ASI01）分列，原因正是"注入面与执行面在时间上解耦"。PMPA 攻击（arXiv:2609.13889）在 OpenClaw 上注入成功率 73.7%、跨会话攻击成功率 55.5%，在 Claude Code 上 66.9% / **81.7%**；arXiv:2610.28810 在 ChatGPT Instant 5.3、Claude Sonnet 4.6、Gemini 3 Flash 上系统验证了跨会话注入。结论很硬：**输入侧过滤对已写入的记忆基本无效**，安全模型必须从"过滤输入"改为"审计状态"。而现有方案里，只有 dsh 的人工确认与 TencentDB 的白盒下钻算得上半个状态审计。

**挑战二：事实正确 ≠ 记忆一致。** 一条"优先速度而非安全"与一条"无安全审计不得上线"可以同时被存下，都"有出处"，但互相否定——检索到哪条，Agent 就变成哪个人格。已有分析给出 15 项校验（6 项技术校验 + 9 项伦理与一致性校验：矛盾检测、教条度、置信校准、偏见检测），并主张 GOLD/SILVER/BRONZE 三级信任分层；但目前主流记忆系统只做到前 6 项。**记忆系统缺的不是检索器，是"内部审计员"。**

**挑战三：评测本身失真。** 四个具体缺陷：①厂商自测口径不统一，AML 排序与宣传排序冲突；②benchmark gaming 已被实证——Reglos 之所以要引入"第二模型家族的 critic"来审补丁，就是因为单模型自评会把"只修好被测失败"当成进步；③权限维度全线失败——MemArena 发现连 Oracle 检索都大量越权泄露，其他后端又"过于胆怯不敢披露"，即同时过度分享与过度保留；④长程天花板明确——BEAM 在 128K/500K/1M/10M 四档上公开得分上限约 64 分，说明"真长程记忆"仍未被解决。

**挑战四：记忆通胀与删除失效。** 压缩率 61% 的另一面是"未压缩的 39% 仍在付费"；而删除普遍不可靠——ChatGPT 删对话不等于删掉由该对话生成的记忆，两个动作是分开的。更麻烦的是参数轨：进了权重的记忆无法逐条删除，这与 GDPR 的删除权存在结构性冲突。

**挑战五：可携带性出现"避锁定反踩空"。** 为规避锁定而选开源记忆层，本身可能踩空：ByteRover 于 9 月 27 日归档仓库，Meta 收购 Limitless 后关停了采集产品。数据转移倡议（DTI）已呼吁把"工具+记忆+工作区+护栏"整体作为可携带单元，欧盟 DMA 第 6(9) 条可能要求实时数据可携带，但"模型推断出的记忆"目前只落在访问权、而非携带权之下——这是一块明确的法律空白。

## 五、展望与建议

**一个判断**：把记忆当"数据库"来建，会持续陷入"检索精度军备竞赛"；把记忆当**账本（ledger）**来建，才与它真实的失效模式对齐——记忆的错误是**写进去就长期存在**的错误，账本的核心机制恰好是 append-only、追加更正而非覆盖、每条可溯源、可冲正。

由此给出"记忆三权"框架，作为选型与验收的最小检查项：

- **准入权（admission）**：谁有权决定"这条值得长期记住"？是模型、管线、Job，还是人？必须显式声明，且默认拒绝。
- **一致性权（consistency）**：新条目与既有条目冲突时，谁裁决？至少要能检测"互相否定的两条同时存在"。
- **授权权（authority）**：这条记忆能否成为"行动依据"？"记录了一句话"与"这句话获得执行许可"必须是两个操作、两份凭证。

**五条落地建议：**

1. **先建写入闸门，再谈检索优化。** 在记忆写入路径上加三道：来源标记（origin_id，且必须是写入必填字段而非约定）、与既有记忆的矛盾检测、分级信任（自动/待确认/仅参考）。没有 origin_id 的去重，会把"同一段投毒内容从两个页面进来"误判为两个独立证人。
2. **给记忆条目一个最小 schema**：`id / origin_id / provenance(引用原文位置) / authority_tier / supersedes / expires_at / confidence`。文件轨直接写进 frontmatter；分层轨需要为 L1 条目补稳定主键——否则 L2/L3 无法逐条授权或撤销。
3. **选型按"资产类型"而非"总分"决策**：流程与 SOP 密集 → TencentDB（规则执行 28.7）；个人偏好与陪伴 → 阿里云 Memory / NTES 类（个性化 57.0）；代码与工程记忆 → Hy-Memory 的 coding 记忆（diff 链留痕）；跨工具可携带 → ReMe / OpenViking（文件即真相）；时序与合规溯源 → Zep/Graphiti。
4. **双计量并行披露**：把"记忆持有量（条·小时）"与"记忆调用量（Credit）"分开核算。只报调用量会掩盖"记了一堆没用的东西"这类真实浪费。
5. **季度记忆体检**：去重率、矛盾条目数、过期未退役数、召回命中率、被撤销条目占比。这五项比任何单一 benchmark 分数更能预测线上表现。

**下期候选**：①记忆写入的"负事件"如何记录（拒绝写入、冲突驳回、过期退役的遥测格式）；②L1 条目稳定主键的三种实现与迁移成本；③参数轨记忆的"可删除性"工程方案（unlearning 与可撤销适配器）；④MemArena 权限维度失败的复现与修法；⑤AML 是否出现第二期榜单及其口径变化。
