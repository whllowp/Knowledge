# AI-SRE 技术洞察（第 345 期）

**生成时间**：2026-11-25 07:31（Asia/Shanghai）
**观察窗口**：2026-10-25 — 2026-11-25（重点近 30 天）
**本期主题**：到期面／到期清单与续期提前量——唯一可预测的故障，仍然按月发生

## 题眼：四张过了期的证书，与一个过了期的域名

- **英雄联盟 2026-01-04**：游戏客户端使用的 SSL 证书到期，全球玩家无法连接服务器；这张证书是 2016 年那次同类事故后签发的，**整整十年后同一天到期**（classmethod，2026-01-08）。
- **TeamDynamix 2026-05-21**：内部服务间认证用的 TLS 证书“在轮换前就到期”，19 分钟内出站邮件发不出、iPaaS 工作流步骤执行失败、工单日志出现缺口（官方状态页复盘）。
- **CERN VOMS 2026-04-21**：4 月 20 日续了新证书，4 月 21 日 07:30 **旧证书到期**，而在续期开始前签发的 VOMS proxy 全部开始失败——proxy 的有效期可以**长于签发它的那张证书**，校验时还要验签发者证书（WLCG 事故报告，2026-05-09）。
- **Beaker 2026-10-19**：一个主下载站点证书过期，Testing Farm 请求批量失败，1 小时 31 分恢复。
- **FreshDirect 2026-10-21**：域名续费失败，网站直接下线；**Little Creek** 2026-06-17 两个域名同时不解析。
- **OpenCode 2026-10-17/18**：所有个人 API key 到期，请求返回 `401 api_key_expired`，并明确写着“**重新登录不会续期这张 key**”。

这些不是“忘了续”的故事。它们是**清单、链条与提前量**的故事。

## 一、发展趋势：从“证书到期”到“到期资产”

第一代做法是日历提醒：谁签的证书、什么时候到期、提前三十天发邮件。它的问题是**清单靠人填**，于是内部 mTLS、客户端证书、测试环境、影子域名永远不在清单上。

第二代是黑盒探针：从外部连 443，看证书还有几天。它的问题是**只看得见入口**，看不见服务间调用、消息队列、数据库连接、对象存储端点。

第三代是自动化：ACME、cert-manager、云厂商托管证书，把“续”变成平台行为。它把故障从“忘记续”转成“**忘记监控续期是否成功**”，以及“新证书部署了、旧副本还在用旧证书”。

第四代正在成形：**到期资产清单**（certificate / domain / API key / token / license / 数据保留期 / 模型弃用日）＋ 每个资产的**续期流程与提前量**＋ 定期演练。趋势不是“更多自动化”，而是**把到期当 inventory 问题而不是提醒问题**。

## 二、技术现状：四代方案，四种盲区

- **ACME／Let's Encrypt**：域名校验、90 天短周期、自动续期；盲区是**内部服务、非 HTTP 协议、无法做 HTTP-01 的域名**。
- **cert-manager／云托管证书**：K8s 里自动签发与轮换；盲区是**证书更新了但工作负载没重载**，以及 **Ingress/Gateway 多副本各自缓存**。
- **域注册商自动续费**：默认开启，但**支付失败、邮箱失效、注册商被攻击**都会让域名进入赎回期；赎回期的宽限不是无限的。
- **API key／token 轮换**：多数平台能设过期时间，却没有“到期前 30 天通知所有依赖方”的机制；OpenCode 的报错已经把答案写死——**重新登录不续期**，依赖方必须改配置。
- **到期监控**：Blackbox exporter、SSL 探针、云厂商的到期通知；盲区是**监控本身被静默、告警被当成噪音、探针只覆盖已知端点**。

四种盲区指向同一个事实：**到期日不是起点，是终点**。真正的起点是“发现资产”，真正的终点是“旧副本停止被信任”。

## 三、技术竞争力：到期管理不是一个产品

| 方案 | 覆盖对象 | 自动续期 | 清单能力 | 提前量治理 | 盲区 |
|---|---|---|---|---|---|
| Let's Encrypt + ACME | 公网 TLS | 强 | 无 | 依赖客户端 | 内部服务、非 HTTP |
| cert-manager | K8s 证书 | 强 | 中（K8s 内） | 中 | 多副本重载、集群外 |
| AWS ACM / 云托管 | 云内证书 | 强 | 中（云内） | 中 | 跨云、自建 IDC |
| Venafi / 商业 PKI | 企业证书 | 强 | 强 | 强 | 价格、落地周期 |
| 域注册商自动续费 | 域名 | 中 | 弱 | 弱 | 支付/邮箱/注册商故障 |
| 密钥/令牌托管 | API key | 中 | 中 | 弱 | 依赖方改配置 |
| CMDB / 服务目录 | 资产 | 无 | 强（若维护） | 中 | 数据陈旧 |
| 到期探针/监控 | 已知端点 | 无 | 弱 | 弱 | 只看入口 |

**判读**：没有一家能同时给出“全部资产、续期步骤、旧副本退场、责任属主”。自动续期最强的地方，恰恰是清单最弱的地方。

**本期反转**：我们一直把到期当“运维日历上的一天”。实际上到期是**一个区间**——发现资产、申请签发、部署、传播、旧副本退场，每一步都要时间；**提前量必须 ≥ 这条链的总时长**，而不是“提前 30 天发邮件”。

## 四、技术挑战

1. **清单不完整**：影子证书、内部 mTLS、客户端证书、测试环境、第三方托管的端点，任何一类缺失都让“清单完整率”变成自我安慰。
2. **链式到期**：签发者证书、proxy、CRL/OCSP 响应、根证书，任何一环过期都会让下游一起失败；VOMS 的教训是**被签发物的寿命可以超过签发者**。
3. **自动续期静默失败**：ACME 校验失败、DNS API 权限过期、速率限制、磁盘满，都会让续期失败但不一定告警。
4. **传播与旧副本**：新证书生效不等于所有副本都用新证书；滚动发布、长连接、客户端缓存、服务网格 sidecar 都可能是旧副本。
5. **责任分散**：平台团队管 CA，业务团队管域名，供应商管托管端点，**到期日没有单一属主**。
6. **与冻结冲突**：变更冻结期正好覆盖到期日时，续期变成例外；例外流程往往比续期本身更慢。
7. **到期告警被静默**：到期提醒是高频低价值告警的典型，最容易被批量静默——然后真的到期。

## 五、需求分解、用户旅程与 90 天实现方案

**需求分解**

- R1 资产发现：CT log、网络扫描、云 API、代码仓库、服务目录五路合并，去重后形成“到期资产表”。
- R2 到期日历：90/60/30/7 天四档提醒，每档带属主、续期步骤、上次续期结果。
- R3 自动续期与失败告警：续期成功率、上次失败原因、依赖方是否已更新。
- R4 演练：每季度模拟一张证书/一个域名过期，验证发现、续期、回滚与客户沟通。
- R5 责任属主：每个资产一个 owner、一个 backup，写进服务目录。
- R6 冻结例外：到期日在冻结期内时，自动生成例外工单并走会签。

**用户旅程**

新服务上线 → 登记域名/证书/密钥 → 自动续期接管 → 到期前 30 天预演 → 到期日值班待命 → 过期后 15 分钟内回滚或切换 → 复盘更新清单。

**90 天实现方案**

- 0–30 天：跑一遍全量发现，建立到期资产表；给每个资产定 owner；把“未来 90 天到期”做成一张周报。
- 31–60 天：把公网 TLS 与域名迁到自动续期；给内部 mTLS 加证书签发与轮换；API key 建立到期通知与依赖方清单。
- 61–90 天：做第一次“模拟过期”演练；把“零非计划到期”写成 SLO；把到期告警从“每日提醒”改成“按提前量分级”。

**验收指标**：到期前 30 天清单完整率、自动续期成功率、非计划过期事件数、平均提前量（天）、依赖方更新完成率。

**判词**：「CA／ACME／cert-manager／域名自动续费／密钥托管／到期监控／CMDB」全部可采购，「未来 90 天有哪些资产到期、每个到期要几步、旧副本何时停止被信任、自动续期上次失败在何时、谁负责」不可采购。

**第 257 个市场空白（五项）**：到期资产的统一发现；续期链条的端到端可视化；旧副本退场的证据；自动续期失败的独立告警；到期责任的属主绑定。

**`expiry.*`／`renewal_calendar.*` 第 224 次无人提字段族**：到期日、提前量、续期步骤、上次续期结果、旧副本退场时间、依赖方确认。

**本地 173／173-kb 连续第 212 期成组启用（陶炳哲 30）**：他反复强调“过期不是事件，是流程”，与本期把到期拆成发现—签发—部署—传播—退场五步一致。
