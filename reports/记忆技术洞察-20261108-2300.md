# AgentMemory 技术洞察 · 第 40 期：记忆的查询语言——只有 find，没有 select

**2026-11-08 23:00 · 覆盖 2026 年 10 月中旬至 11 月 8 日公开动态**

前 39 期反复出现两个结构性观察：能做治理的都不在记忆产品里（"倒挂"已记三十次），能被计分的能力总缺一个维度（"口径缺口"已记三十一次）。本期换一个更低的层位看这两个观察的共同根因——**它们不是治理问题，是语法问题**。

核心命题：记忆系统几十个产品、上百篇论文都在优化"找得准"，但治理、审计、评测需要的从来不是"找到"，而是"**列出满足条件的全集并计数**"。前者是检索（ranking，返回 top-k，完整性不可判定），后者是查询（集合定义 + 谓词 + 投影 + 计数，完整性可判定）。整个行业只建了前者。

据此给出可证伪的判据：**记忆与数据库的分界不在存储引擎（向量 vs 图），而在有没有一个能返回全集并报数的接口**。称之为"完备性接口"。用它去测当前主流方案，结论是：绝大多数停在"分页 + 类型过滤"，只有数据库侧（GQL / Cypher）具备完备性，而它们不是记忆产品。

## 一、发展趋势：三件事同期发生，指向同一处缺口

**其一，GQL 从标准走进产品，agent 行为第一次成为"可查询图"。** Google BigQuery Graph 正式 GA，实现 ISO GQL，与 SQL 同引擎、无需搬数据；官方称 GQL 在公开基准上比预览版快 2 倍，无向遍历快 100 倍，新增 `CALL` 与更完整的子查询。更关键的是配套的 context graph：**把 agent 的动作、决策、被否方案记成可 GQL 查询的属性图**。这是"记忆的查询语言"第一次由云厂商在平台层提供，虽然它记的是动作日志而非用户记忆。Uber 的对照实验说明了这个方向的价值：同一个模型、同一个问题，挂上可 Cypher 遍历的上下文图 38 秒答对；不挂图 20 分 9 秒答错——原话是"未接地的 agent 不是廉价地失败，而是缓慢地失败"。

**其二，记忆库自己长出了结构化查询。** codebase-memory-mcp 把代码库结构抽成 SQLite 里的属性图，用 Cypher 风格查询替代逐文件读取：同一个问题 412,000 token 降到 3,400 token，约 120 倍，14 个 MCP 工具，已有 5,400 星与 arXiv 论文（2603.27277）。MEMIG（抗体优化）走的是同一条路但更彻底：给每条经验一个**领域锚定标识符**，把"检索"变成"精确查找"，并直接存量化效应与上位效应（Δab−(Δa+Δb)），明确主张记忆应从"描述"转向"测量"、从"重写"转向"累积"。

**其三，最"土"的接口被证明有效。** LongMemEval-V2 官方榜（451 题、最长 1.15 亿 token 轨迹）上表现最好的方法不是新检索器，而是**把轨迹当文件存、用编码 agent 去搜**：72.5% 对最强 RAG 基线 48.5%，高 24 个百分点。榜单已改为按 LAFS Gain 排序（1—200 秒时延预算内提升的准确率），Small 档首位 AgentRunbook-C v2 为 +2.82 / 75.6% / 130.5 秒，而准确率最高的 OPS-Agentic-Memory-v1（81.4%）增益仅 +0.32（153.6 秒）。

三条线索合起来：**竞争焦点正从"嵌入更好"转向"接口更强"**。方向不是把向量库换成图库，而是补一门语言。

## 二、技术现状：两个动词的系统

### 2.1 产品侧只到"过滤"

- **TencentDB Agent Memory v3**：`/v3/atomic/query` 与 `query_conversation` 提供的谓词是 `type`（episodic / persona / instruction）+ `time_start`/`time_end` + `task_id` + `limit`/`offset`。没有跨字段布尔组合，没有日期之外的比较，没有跨层 join，也没有返回总数的字段。
- **Mem0**：filters 支持 `AND`/`OR`/`NOT` 与 `in`、`gte`、`lte`、`gt`、`lt`、`ne`、`contains`、`icontains`，`get_all` 带 `count`——形式上最接近 Q2。但官方技能文档同时写着"metadata 过滤仅支持顶层键，运算符只有 eq/contains/ne"，两套口径并存；更麻烦的是一条已知坑：**跨实体 AND（user_id + agent_id）会静默返回空集**，需改用 OR。
- **OpenViking**：唯一把两种动词分开的方案。`ls`/`tree`/`read`/`write` 是遍历与定位，`grep` 是精确/正则，`find` 执行查询，`search` 结合会话上下文做语义检索；且主张"在目录里检索，而不是在整个索引里捞"——把子树当作用域。11 月 8 日 41,748 星，30 天 +2,310，周 +500，仍是增长最快的记忆仓。
- **ReMe / dsh-memory-evolve**：只有 `searchLimit`（默认 5）与 `recallMinScore`（默认 0）两个旋钮，加"会话搜索"。dsh-memory-evolve 645 星 / 71 fork / MIT，最后 push 10-29，仍是五轨文件式记忆，查询靠标签与路径而非谓词。

另有两类值得注意的偏差。Hindsight 把动词扩到三个：`retain` / `recall` / `reflect`，但第三个是"用 LLM 在召回结果上推理"——加的是"想"，不是"查"，能提升答案质量，却不能让任何治理动作变成可批处理。MemMachine 走另一头：原文逐字入库，由检索 agent 在三档路由（直接检索 / 并行分解 / 链式追问）间选择，实质是把"查询规划"交给模型而非语言——灵活，但不可复现、不可计数。两者都绕开了"谓词"这件事。

### 2.2 查询层自身的失败率被首次量化

CypherGuard（2610.41755，10-30）给出关键数字：Cypher-Bench 上小模型只答对 31.4%，强模型平台期 71.76%；无训练修正后达 88.50%（+25.08pp）。论文明确指出**主要失效模式是结构性的，不是语言性的**：生成的查询语法正确、符合 schema，却因沿存储方向的反方向遍历而返回零行；或对互反关系用无向匹配，把同一伙伴算两次——**不报错、不空集、答案错一倍**。这两类恰好是"检索不存在"的失败模式，只是搬到了查询层。

## 三、技术竞争力：四种接口形态，一级产品

按"查询能力四级"（Q0 语义 top-k / Q1 元数据过滤 / Q2 结构化图查询 / Q3 含时间与血统的声明式集合语言）对照：

| 方案 | 接口形态 | 谓词 | 时间 | 完备性 | 治理批处理 |
|---|---|---|---|---|---|
| TencentDB AM v3 | 分页查询 API | 类型+窗口 | 仅范围 | 无总数 | 弱 |
| Mem0 | search + list | AND/OR/NOT | 创建时间 | 有 count | 半 |
| OpenViking | 文件系统 | 路径+正则 | 无 | grep 可数 | 半（按目录） |
| Zep / Graphiti | 图 + API | 边属性 | 双时态 | 未披露 | 弱 |
| HydraDB | 时序图 | 遍历+时间 | Git 式版本 | 未披露 | 弱 |
| BigQuery Graph | ISO GQL | 完整 | 快照/历史 | COUNT 可判 | 强 |
| codebase-memory-mcp | Cypher/SQLite | 完整 | 弱 | 可判 | 强 |
| dsh-memory-evolve | 文件 + 工具 | 标签/路径 | git 分支 | 弱 | 弱 |
| ReMe | recall API | 阈值/条数 | 无 | 无 | 无 |

三条判读：

**第一，Q2 以上的方案全部不是记忆产品**（倒挂第三十一次）。GQL 在 BigQuery、Cypher 在代码图、SQL 在 SQLite——语言都是从数据库侧带进来的，没有一个记忆厂商自己发明谓词。

**第二，能力的分布是断裂的，不是渐进的。** Q1 到 Q2 之间不是"多支持几个运算符"，而是从"排序候选"跳到"定义集合"。Mem0 的 `count` 恰好卡在门槛上：它能告诉你"一共有多少条"，但不能告诉你"满足这个条件的有多少条"——前者是库存，后者是账。

**第三，文件系统是被低估的第四形态。** 它天然带谓词（路径、正则）、天然可数（`grep -c`）、天然可组合（管道），代价是没有时间语义与血统投影。这解释了 LongMemEval-V2 上"用文件搜"赢 RAG 24 个百分点：不是文件更聪明，是文件**有语言**。

## 四、技术挑战

**挑战一：键先于语言。** 谓词要有作用对象，就要有稳定标识符。而记忆条目在第 3 期就被证明主键会断（路径/序号/内容三种断裂模式），第 12 期证明缺的是 `owner` 而非 ACL。MEMIG 的"域锚定标识符"是唯一把这个前提讲透的实现：没有键，精确查找无从谈起，只能退回模糊匹配。**所以路线是 ID → 过滤 → 图 → 语言，四步不能跳**；现在多数产品直接跳到"上向量 + 加 filter"，缺的正是第一步。

**挑战二：空集有了第三个变体。** 第 7 期把"没有"分为未观测/未捕获/未召回/世界本无，四者在接口上塌缩成 `[]`。本期补上第五种：**谓词写错**（Mem0 的跨实体 AND）与**关系方向反**（CypherGuard）同样返回空或错误结果，且调用方无法区分。这意味着"查不到"这个信号在语法层也不可信——比语义层更危险，因为它发生在治理脚本里。

**挑战三：text-to-query 是读侧的第二个黑箱。** 第 20 期指出读路径第一个动作是"把需求翻译成查询"，无人审计。结构化接口并没有消除这层翻译，只是把它从"嵌入"换成"生成 DSL"：失真的性质从"排错序"变成"问错问题"，而返回的是结构化结果，**看起来更可信**。CypherGuard 的 88.5% 是当前天花板，不是起点。

**挑战四：计数与隐私正面冲突。** 一旦接口能 `count(where)`，它就变成侧信道：攻击者用计数差分推断某条记忆是否存在，无需读出内容。这与第 12 期"共享度与可切割性反向"同构——**越可查询，越难只读不泄**。可行的折中不是拒答计数，而是给计数加预算与噪声，但当前无任何记忆产品披露过这一点。

**挑战五：语言尚未收敛。** GQL 已是 ISO 标准、Cypher 是事实标准、各家 filter 方言互不兼容（Mem0 的运算符集与官方文档自相矛盾）。第 28 期判断"格式层窗口期 6—12 个月"，查询层大概同一量级；而记忆的 schema（墓碑三字段、`owner`、`as_of`）尚未定型，语言就无从标准化。

## 五、展望与建议

未来两个季度，最可能出现的不是"记忆图数据库"，而是**三条窄接口**：

1. **`memory_id` 稳定键**（不可变、可枚举、可引用），先于任何谓词；
2. **`count(where)` 与 `export(where)`**，两个动作把"库存"变成"账"，也是删除举证（第 2 期）与迁移（第 13 期）的共同前置；
3. **`as_of` 作为谓词而非参数**：把时间放进 where 子句，而不是加一个时间窗——这是"双时态"从存储能力变成查询能力的唯一路径。

对采购方的建议：把"能不能 count"写进 POC 清单，与"能不能 grep 我的库""能不能 as-of 查三个月前的状态"并列。这三问比任何榜单分数更能预测三个月后的运维成本。

对厂商的建议：不要先上图库。**先补 ID，再补谓词，最后才谈语言**。跳过前两步的图查询，只是把"排错序"换成"遍历错方向"。

一句话：记忆行业花了三年把"找得到"做到 90 分，却没意识到账本需要的从来不是"找得到"，而是"数得清"。**没有 select 的系统，不会有审计；没有审计的系统，不会被当成基础设施。**
