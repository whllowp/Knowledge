# AI-SRE 技术洞察（第 311 期）

- 生成时间：2026-11-20 20:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：偏斜面／版本偏斜与混合版本共存——“支持偏斜”不等于“测过这一对”

## 题眼

2026-11-15 更新的 Kubernetes 版本偏斜策略写得很具体：HA 集群里最新与最老的 `kube-apiserver` 必须在一个小版本内；`kubelet` 不能比 apiserver 新，最多可以老三个小版本（低于 1.25 时只能老两个）。2026-10-17 的一篇升级顺序指南把它压缩成一句操作纪律：**先升 apiserver，再升控制器，最后升 kubelet/kube-proxy；节点可以落后三个小版本，但永远不能领先；apiserver 不要跳小版本。**

这些是**支持矩阵**。矩阵回答“允许不允许”，不回答“测没测过”。你这一对具体的 1.x 与 1.y、这一版 Istio 控制面与那一版数据面、这一版 API 与那一版 worker，组合起来会不会静默出错，文档不负责。

2026-09-27 的 AKS Istio 升级文档把混合版本写成了流程本身：canary 修订的控制面与稳定修订**同时部署**，数据面手动滚动；可以跳一个版本升到 n+2，但前提是两个版本都还被支持。2026-10-29 的迁移文档则把顺序写死：先做扩展（expand），滚动 API 与 worker，**等旧二进制退场之后**才做收缩（contract）；两个版本必须同时能读能写。

**版本偏斜不是发布的异常，是发布的常态。** 本期要问的是：偏斜窗口里，哪些差异是设计好的，哪些是没人测过的。

## 一、发展趋势

**第一，偏斜从“组件属性”变成“发布属性”。** 滚动发布、蓝绿、金丝雀，本质上都在制造一个“新旧同存”的窗口；窗口长度由发布速度决定，窗口内的行为由两版兼容性决定。

**第二，支持矩阵开始显式化。** K8s 写清组件间最大偏斜；Istio 写清控制面/数据面的修订支持范围；数据库写清“混合版本集群”的支持窗口与 finalize 步骤。矩阵让“能不能升”可判断，但仍是**允许**而非**验证**。

**第三，扩展-收缩（expand-contract）成为 schema 变更的标准姿势。** 2026 年的迁移文档反复强调：滚动部署期间旧二进制与新二进制对同一 schema 读写；所以先加列/加表（扩展），等旧版本退场再删列/改类型（收缩）；同一次发布里做破坏性 DDL 是禁忌。

**第四，启动时准入开始检查“对端能力”。** 2026-11-13 的滚动升级文档描述了一种做法：每个进程启动时加载后端能力、缓存校验器、工作流模式与就绪契约；若后端或缓存满足不了 v2 契约，进程**在启动时就失败**，而不是在流量打进来之后才失败。

**第五，不可加性变更被允许“停世界”。** 同一份文档给出退路：规划阶段发现非加性变更，就为这次发布开一个 stop-the-world 窗口，下一次再回到滚动升级。承认“有些变更不能滚动”，比假装都能滚动更安全。

## 二、技术现状

**协议与 API 层。** gRPC/protobuf 的字段编号、JSON 的未知字段、HTTP 头的可选性，决定新旧版本能否互读；破坏性变更通常表现为“旧版本收到不认识的字段就丢弃/报错”。

**数据层。** 双写、回填、读修复、版本列；混合版本期间，旧 writer 不写新列，新 reader 读到 NULL；收缩阶段删列时，旧版本仍在跑就会崩。

**控制面/数据面。** Istio 的修订（revision）机制让两套控制面并存，数据面按标签滚动；Envoy 的 xDS 版本协商决定配置能否下发。

**缓存与序列化。** 缓存键格式、序列化默认值、压缩算法在版本间变化时，混合版本会互相读不懂对方的缓存，表现为命中率骤降或反序列化失败。

**Agent 舰队。** 工具 schema、提示词模板、记忆格式也有版本；Agent 版本偏斜时，同一任务在不同实例上行为不同，而日志只记“任务成功”。

## 三、技术竞争力

| 方案 | 偏斜窗口 | 兼容保证 | 回滚难度 | 验证方式 | 主要风险 |
|---|---|---|---|---|---|
| 滚动发布 | 长（逐批） | 靠 N-1 兼容 | 低（反向滚动） | 灰度观察 | 混合版本静默差异 |
| 蓝绿 | 短（切换瞬间） | 靠双环境一致 | 中（切回） | 全量对比 | 数据双向兼容 |
| 金丝雀 | 中（按比例） | 靠路由兼容 | 低 | 指标对比 | 小流量掩盖长尾 |
| 扩展-收缩 | 长（跨发布） | 显式两版读写 | 中（收缩前可退） | 契约测试 | 收缩时机早于退场 |
| 停世界升级 | 零 | 无需兼容 | 高（窗口内不可用） | 预演 | 停机成本 |
| 支持矩阵 | 不适用 | 只给“允许” | 不适用 | 无 | 把允许当验证 |

判读：买得到发布平台、服务网格修订、迁移框架、契约测试工具；买不到“这一对新旧版本组合在偏斜窗口里到底测过没有、哪些字段会被静默丢弃、回滚时反向偏斜会不会二次破坏”。支持矩阵是地图，不是脚印。

本期反转：我们习惯把“版本偏斜”当成要消灭的异常，追求“所有实例同版本”。但滚动发布、金丝雀、灰度天然要求新旧同存；真正的目标不是消除偏斜，而是**给偏斜定预算**：窗口多长、允许哪几对版本、每对跑过什么契约测试、收缩在何时才允许发生。没有预算的偏斜，就是把“支持”当成“验证”。

判词：「发布平台／服务网格修订／迁移框架／契约测试／特性开关／版本矩阵」全部可采购，「这次发布的新旧版本组合测过没有、偏斜窗口里哪些字段被静默丢弃、回滚时反向偏斜会不会二次破坏、收缩是否早于旧版本退场、Agent 舰队哪几版在同时跑」不可采购。

## 四、技术挑战

**其一，支持≠验证。** 矩阵只列允许范围；具体组合的兼容性要靠契约测试与灰度证据。

**其二，静默差异难观测。** 旧版本丢弃未知字段、新版本读到 NULL、缓存互不识别，往往不报错，只表现为“数据少了一点”。

**其三，回滚是反向偏斜。** 回滚把新版本换回旧版本，但 schema 可能已经扩展、缓存已被新格式写入；回滚不是“撤销”，是“再走一次偏斜”。

**其四，收缩时机难判断。** 旧版本何时算“完全退场”？长连接、异步消费者、定时任务、离线 worker 都可能还在跑旧代码。

**其五，Agent 舰队让偏斜多一维。** 工具 schema、提示词、记忆格式的版本偏斜不会体现在 Pod 版本里，却会改变行为。

**其六，测试环境不产生偏斜。** 预发通常一次只跑一个版本；真实偏斜只在生产出现。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 发布工程：需要偏斜预算（窗口、允许配对、契约测试清单）。
- 服务属主：需要“两版同时读写”的兼容性证明与回滚预案。
- SRE：需要偏斜窗口的可观测性（哪些实例在跑哪版、混合比例、异常是否集中在旧版）。
- 安全/合规：需要知道旧版本是否还在处理敏感数据、是否仍在支持范围内。

**用户旅程（一次“回滚后更糟”的事故）。**

1. 服务从 v1 滚动到 v2，schema 先扩展（加列），双写开启。
2. v2 全量后，团队按计划做收缩（删旧列）；此时一个离线 worker 仍是 v1，读旧列失败，开始丢任务。
3. 值班回滚到 v1；但 v2 已写入新格式缓存，v1 读不懂，命中率跌到 0，数据库被打穿。
4. 复盘发现：收缩早于“旧版本完全退场”；回滚没有考虑缓存格式的反向偏斜。
5. 文档里“支持 N-1”是对的，但没人测过“v1 读 v2 缓存”这一对。
6. 结论写成“回滚失败”；真正缺的是**偏斜预算与配对测试**。

**实现方案（90 天）。**

- 第 1–2 周：为每个服务建偏斜预算——允许的版本配对、最大窗口、契约测试清单、收缩前置条件（旧版本退场判据）。
- 第 3–4 周：契约测试矩阵——在 CI 里跑“旧客户端 × 新服务”“新客户端 × 旧服务”“旧 worker × 新 schema”，覆盖字段丢弃、NULL、缓存格式、序列化默认值。
- 第 5–6 周：退场判据——长连接、异步消费者、定时任务、离线 worker 的版本分布纳入观测；达到阈值才允许收缩。
- 第 7–8 周：回滚演练——不只演练“切回旧版”，还演练“旧版读新格式缓存/schema”的反向偏斜，验证降级路径。
- 第 9–10 周：启动准入——服务启动时校验对端能力（schema 版本、缓存格式、协议版本），不满足即拒绝启动并告警。
- 第 11–12 周：Agent 舰队版本——把工具 schema、提示词、记忆格式纳入版本台账，偏斜时限制路由或降级。
- 第 13 周：验收——任一次发布能回答：偏斜窗口多长、哪些配对测过、收缩依据是什么、回滚时反向偏斜是否验证。

**验收标准。** 每个服务有偏斜预算与配对测试记录；收缩前能证明旧版本已退场；回滚演练覆盖反向偏斜。

**第 223 个市场空白（五项）**：偏斜预算（窗口/配对）；新旧配对契约测试矩阵；旧版本退场判据；反向偏斜回滚演练；Agent 舰队版本台账。

**`skew.*`／`mixed_version.*` 第 190 次无人提字段族**：`skew.allowed_pairs`、`skew.window_started_at`、`skew.old_version_share`、`skew.contract_tests`、`skew.contract_ready` 在发布平台、服务网格与迁移框架之间没有统一语义；平台只报“发布完成”。

**本地 173／173-kb 连续第 178 期成组启用**（陶炳哲 30）：本地知识库把“支持矩阵”与“实测矩阵”分开记账；本期把偏斜从异常改写成预算。
