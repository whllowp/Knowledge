# AI-SRE 技术洞察（第 333 期）

- 生成时间：2026-11-24 18:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：评审 Agent 面／AI 代码评审的精度、噪音与信任——它不会漏掉你告诉它的问题，只会漏掉你没告诉它的问题

## 题眼

2026 年 6 月的 SWR-Bench（1,000 个已验证 GitHub PR、12 个 Python 项目、18 个 LLM）给出了一组很冷的数字：最好的系统（PR-Review + Gemini-2.5-Pro）只有 **F1 = 19.38%**（recall 23.18%），多数技术**精确率低于 10%**——也就是说，被标出来的问题里绝大多数是误报。作者的原话是“尚未准备好用于真实部署”。一个补充结论是：把多次评审聚合起来，F1 最多可提升 43.67%。

这与厂商口径形成对照。2026-09-15 的一篇统计梳理提醒：GitHub 的“71% actionable feedback”描述的是 Copilot 评审输出的**可操作性**，并不等于“71% 的评论是对的”，也不等于“71% 阻止了缺陷”。该文的核心句是：“它没有证明 71% 的评论是正确的。”

2026-11-20 的一份内部效果分析则展示了另一种统计：某组织 138 条 Copilot 评论，精确率 **97.3%**（72 条 helpful、2 条 incorrect），采纳率 78%，响应率 81.2%。但它的分母排除了“被忽略”和“未解决”的评论——被忽略的评论不计入错误。**精确率的分子分母由谁定义，决定了这个数字能不能用。**

更深的一层来自 2026 年 EMNLP 主会的一篇受控研究：216 个数据库支撑的任务，比较“开放式评审”与“定向检测”。结果是一个陡峭的发现鸿沟——最容易的类别 F1 从 0.91 掉到 0.85，而最难的类别从 **0.73 掉到 0.03**。模型能可靠识别被明确描述的问题，却很难在无人提示时**发现**它们。

## 一、发展趋势

**第一，评审 Agent 从“建议”走向“门禁”。** 越来越多团队让 AI 评论参与合并决策；但精确率与召回率的证据没有同步跟上。

**第二，评价口径从“采纳率”转向“发现率”。** 采纳率高的系统可能只是说了团队已经知道的事；真正稀缺的是发现未被告知的问题。

**第三，评审的上下文从 diff 扩展到系统语义。** 跨端点的数据层问题、状态持久化问题，单看 diff 看不出来。

**第四，评审本身成为攻击面。** 代码注释、测试数据、PR 描述都可能携带指令，影响评审 Agent 的判断。

**第五，评审噪音与开发者信任强相关。** 误报多了，团队会整体忽略，包括真问题。

## 二、技术现状

**指标体系混乱。** precision/recall、adoption、response rate、actionable rate 混用；分母常被静默调整。

**覆盖有限。** 多数工具只看 diff 与有限上下文；系统级语义与运行时行为不在视野内。

**发现能力弱于检测能力。** 定向提示下表现好，开放式评审下骤降。

**评审可被操纵。** 上下文偏差研究显示，同一漏洞在不同叙述框架下检出结果不同；注释/PR 文本可注入。

**聚合有效但昂贵。** 多次评审聚合能提升 F1，但成本与延迟上升。

**信任衰减。** 误报率高时，团队整体降低对评审的注意力。

**评审与测试的分工被模糊。** 评审 Agent 能指出“这里可能空指针”，但它没有运行代码；测试能证明某条路径可执行，但不能证明设计合理。把评审当测试用，会得到“看起来覆盖了”的错觉；把测试当评审用，会漏掉不可执行的语义问题。

**批量与延迟。** 大 PR 一次送审，上下文被截断，模型只看开头；小 PR 高频送审，评论碎片化、重复率高。评审的“粒度”本身就是一个未建模的变量。

## 三、技术竞争力

| 方案 | 精确率证据 | 发现率证据 | 可审计性 | 成本 | 主要风险 |
|---|---|---|---|---|---|
| 单模型评审 | 低（SWR-Bench <10%） | 弱 | 中 | 低 | 误报淹没 |
| 多轮聚合评审 | 中（F1 +43.67%） | 中 | 中 | 高 | 延迟/成本 |
| 定向规则+LLM | 中 | 中 | 高 | 中 | 规则覆盖有限 |
| 人机双评 | 高 | 高 | 高 | 高 | 人力瓶颈 |
| 只做门禁（不评论） | 中 | 弱 | 中 | 低 | 漏报不可见 |
| 评审+运行时验证 | 高 | 高 | 高 | 高 | 环境依赖 |

判读：买得到评审 Agent、聚合流水线、规则引擎、门禁集成；买不到“这次评审发现了哪些没人告诉它的问题、误报率多少、分母是否被人为缩小、评审是否被注释操纵”。

本期反转：我们一直用“采纳率”证明评审 Agent 有用。实际上采纳率衡量的是**共识**，不是**发现**；定向检测 F1 0.91 与开放评审 0.03 的落差说明，模型擅长确认你已知的问题，不擅长发现你未知的问题。评审 Agent 的价值不在“它说了什么”，而在“它有没有说出没人说过的话”。

判词：「评审 Agent／评论聚合／规则引擎／门禁／静态分析」全部可采购，「这次评审发现了哪些未被告知的问题、误报率与分母、评审上下文覆盖多少系统语义、评论是否可被注释操纵」不可采购。

## 四、技术挑战

**其一，发现率难测。** 没有 ground truth，就不知道漏了什么。

**其二，精确率分母可调。** 忽略、未解决、重复评论是否计入，结论不同。

**其三，上下文边界。** diff 之外的系统语义、运行时状态不在视野。

**其四，评审可被注入。** 注释、测试、PR 描述都是输入。

**其五，噪音与信任。** 误报多导致整体忽略。

**其六，评审通过≠批准。** AI 不评论不等于没问题。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 开发者：需要低噪音、可解释、可执行的评论。
- 评审负责人：需要精确率/召回率与分母口径。
- 平台/SRE：需要评审与门禁、运行时验证的衔接。
- 安全：需要评审输入的完整性与注入防护。
- 管理者：需要“发现率”而非“采纳率”。

**用户旅程（一次“AI 评审通过但线上出事”）。**

1. PR 提交，AI 评审给出 12 条评论，全部被采纳或忽略。
2. 合并；线上出现跨端点数据层 bug。
3. 复盘发现：该 bug 需要跨端点推理，评审只看 diff。
4. 另一条评论其实是误报，但没人有时间分辨。
5. 团队开始整体忽略 AI 评论，包括真问题。
6. 评审指标仍然漂亮：采纳率 78%。

**实现方案（90 天）。**

- 第 1–2 周：指标口径——precision/recall 分母写死；忽略与未解决单列；禁止用 adoption 代替正确率。
- 第 3–4 周：发现率评测——用历史缺陷构造留出集，测“未提示时能否发现”。
- 第 5–6 周：上下文扩展——跨文件/跨端点检索；系统语义检查作为独立通道。
- 第 7–8 周：评审输入防护——注释/测试/PR 文本的指令隔离；评审 Agent 只读结构化上下文。
- 第 9–10 周：聚合与成本——多轮评审聚合，按发现率/成本比取舍。
- 第 11–12 周：门禁衔接——AI 评论 + 规则 + 运行时验证；通过不等于批准。
- 第 13 周：信任校准——按误报率调整评论阈值，避免整体忽略。

**验收标准。** 任一次评审，能回答：发现了哪些未提示问题、误报率与分母、上下文覆盖范围、输入是否可能被操纵。

**第 245 个市场空白（五项）**：发现率评测；精确率分母口径；跨端点语义检查；评审输入防护；评审-门禁-运行时衔接。

**`review_quality.*`／`comment_precision.*` 第 212 次无人提字段族**：`review_quality.discovery_set`、`review_quality.precision_denominator`、`review_quality.context_scope`、`comment_precision.ignored` 在评审平台、门禁与研发度量之间没有统一语义；平台只报采纳率。

**本地 173／173-kb 连续第 200 期成组启用**（赵恒 25）：本地知识库把“评审意见”与“评审证据”分开记账；本期把评审质量落成发现率与分母口径。
