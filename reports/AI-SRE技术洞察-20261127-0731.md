# AI-SRE 技术洞察（第 367 期）

**生成时间**：2026-11-27 07:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：行级权限面／RLS 的默认放行与越权路径

## 题眼

2026-10-23 的一份多租户 RAG 基准把"行级权限"从配置题变成了测量题：50 组多租户配置、50 万文档，跨租户泄漏率在全文检索（FTS）下是 **86.7%**（95% CI 85.4–87.4），加上 RLS 过滤后降到 **8.7%**（8.3–9.1）；向量检索的泄漏率是 **44.1%**（43.2–45.2）。RLS 把 p50 延迟增加约 **10 ms**、p95 增加约 **40 ms**，但把 recall@10 从受影响的水平修回 **99%**。

这不是"RLS 没用"，而是"RLS 默认放行"：PostgreSQL 的 RLS 是 **fail-permissive**——表上没启用策略，或策略对当前角色不匹配，读到的就是全部行。

## 一、发展趋势

第一，多租户从"应用层过滤"转向"数据库层强制"。应用层 `WHERE tenant_id = ?` 依赖每个查询都写对；一条漏写的查询、一个拼接的报表、一次 ORM 的 `find_all`，就是跨租户泄漏。RLS 把这道门放进数据库，理论上无法被单个查询绕过。

第二，攻击面从"注入"转向"配置与角色"。2026-10 的一份威胁模型把多租户 RAG 的杀伤链拆成五段：弱隔离、受损租户身份、粗粒度访问控制、不可审计的跨租户遍历、配置漂移；它指出 RBAC/ABAC 在 RAG 里"难以强制执行"，真正可强制的是数据层谓词。

第三，RLS 的性能成本被量化。上述基准的 10 ms/40 ms 是"可接受"的量级，但前提是策略谓词能走索引；策略里写子查询、函数、`LIKE '%x%'`，成本会从毫秒变成秒。

第四，RLS 的测试开始"负向化"。不再只测"我能看到我的"，而是测"我看不到别人的"；并把 SQL editor、API、后台任务三条路径分开测。

## 二、技术现状

**默认是开的。** `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` 只是打开开关；没有 `CREATE POLICY` 时，普通角色看到 **0 行**（安全），但表所有者、`BYPASSRLS` 角色、超级用户看到 **全部行**（危险）。很多"RLS 已启用"的系统，真正跑在所有者连接上。

**策略是谓词，不是权限模型。** 策略里的 `USING` 决定"能看见哪些行"，`WITH CHECK` 决定"能写入哪些行"；只写 `USING` 不写 `WITH CHECK`，租户可以把行改成别人的 `tenant_id`。

**会话变量会漂移。** 常见的 `current_setting('app.tenant_id')` 模式依赖连接池在每次借出时 `SET`；连接复用、事务回滚、`SET LOCAL` 作用域、后台任务未设置，都会让变量为空或指向上一个租户——空值通常导致"看到全部"或"看到零行"。

**绕过路径不止一条。** 表所有者默认不受策略约束（除非 `FORCE ROW LEVEL SECURITY`）；`SECURITY DEFINER` 函数以定义者身份运行；`COPY` 可绕过部分策略；视图/物化视图可能把行"固化"下来；逻辑复制与备份不经过 RLS。

**测试路径不代表生产路径。** Supabase 的 RLS 测试助手文档写得很直白：在 SQL editor 里以 `postgres` 身份执行，`auth.uid()` 返回 `TRUE`；同样策略经 API 以 `anon` 身份执行返回 `FALSE`。本地"测过了"与线上"被拒了"可以同时成立。

**注入仍然能绕过。** 2026-11 的一份 Azure PostgreSQL 指南提醒：把用户输入拼进 SQL，等于让攻击者决定 `current_user`/`current_setting` 的上下文，RLS 再严也按攻击者构造的身份求值。

**策略是原子的，覆盖是组合的。** 一张表可能有多条策略（SELECT/INSERT/UPDATE/DELETE 各一条），漏掉一条就漏掉一种操作；策略按 permissive/restrictive 组合求值，新增一条 restrictive 策略可能让原本能跑的查询突然返回 0 行——上线前要用真实角色回放，而不是只看"策略存在"。

## 三、技术竞争力

| 方案/能力 | 强制点 | 默认行为 | 主要绕过 |
|---|---|---|---|
| 应用层 `WHERE` | 每条查询 | 漏写即全量 | ORM/报表/拼接 |
| RLS 策略 | 数据库谓词 | 无策略=0 行（普通角色） | 所有者/BYPASSRLS |
| `FORCE RLS` | 连所有者 | 需显式开启 | 超级用户/复制 |
| 会话变量 `tenant_id` | 连接 | 未设置=空 | 连接池复用/后台任务 |
| `SECURITY DEFINER` | 函数 | 定义者身份 | 函数内未过滤 |
| 视图/物化视图 | 查询 | 固化行 | 刷新/权限继承 |
| 逻辑复制/备份 | 复制流 | 不过 RLS | 恢复后泄漏 |

**判读**：这张表最危险的是"默认行为"列——RLS 的安全默认只对普通角色成立，而生产里最常见的连接恰恰是所有者或高权限角色。

**本期反转**：我们一直把 RLS 当"加一道门"。实际上它是"每张表上一组默认开着的门"：没建策略的表是开的，所有者连接是开的，会话变量为空是开的，`SECURITY DEFINER` 函数是开的。**审计要查的不是"哪些表有策略"，而是"哪些表没有策略、哪些连接绕过了策略"。**

## 四、技术挑战

**挑战一：策略覆盖的完整性。** 新表、新视图、新物化视图默认没有策略；迁移脚本 `CREATE TABLE` 后忘了 `ENABLE RLS`，就是一扇新开的门。需要 CI 检查"所有含 `tenant_id` 的表都必须有策略"。

**挑战二：连接身份的不可见性。** 连接池、ORM、后台 worker、迁移工具、BI 只读账号，各自以不同角色连接；RLS 的效果取决于"这条查询以谁的身份跑"，而日志里往往只有 SQL。

**挑战三：策略与索引的耦合。** 策略谓词要走索引，否则每次查询都全表扫描；`current_setting` 是稳定函数，但包在子查询里可能失去下推。

**挑战四：测试的负向覆盖。** 只测"租户 A 能看到 A 的数据"不够；要测"租户 A 看不到 B 的数据"、"改不了 B 的行"、"删不掉 B 的行"，并在 API 路径而非 SQL editor 里跑。

**挑战五：备份与恢复后的重放。** 备份不含 RLS 语义，恢复后若以高权限角色跑批处理，可能把跨租户数据写进缓存或报表；恢复后要重新校验策略与角色，并把“恢复后以受限角色连接”写进清单。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①策略覆盖率检查（表/视图/物化视图）；②连接角色清单与 `BYPASSRLS` 审计；③会话变量的设置与泄漏检测；④`WITH CHECK` 覆盖写路径；⑤负向测试（越权应失败）；⑥恢复后的策略重放。

**用户旅程**：安全团队在季度审计中发现某张新表没有策略 → 追查发现迁移脚本只 `CREATE TABLE` 未 `ENABLE RLS` → 进一步发现报表服务用所有者连接，即使有策略也会看到全部 → 修复：迁移模板强制 `ENABLE RLS` + `FORCE RLS`，报表改用受限角色，CI 加"无策略表"检查，负向测试纳入发布门禁。

**90 天实现方案**：0–30 天，盘点所有含 `tenant_id` 的表与视图，补策略覆盖检查；31–60 天，收敛连接角色、禁用不必要的 `BYPASSRLS`、统一会话变量设置；61–90 天，建立负向测试集与恢复后校验，把"越权查询必须失败"写进发布门禁。

**第 279 个市场空白（五项）**：策略覆盖率；连接角色审计；会话变量泄漏检测；写路径 `WITH CHECK`；负向测试门禁。

**`rls.*`／`row_policy.*` 第 246 次无人提字段族**：所有数据库都报"RLS 已启用"，没有一个字段报"哪些表没有策略、当前连接是否绕过、会话变量是不是空的、上次负向测试是什么时候"。

**本地 173／173-kb 连续第 234 期成组启用（蒋炎炳 23：RLS 不是一道门，是一排默认开着的门；审计要数的是没上锁的那几扇）。**
