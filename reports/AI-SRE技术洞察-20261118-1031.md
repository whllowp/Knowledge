# AI-SRE 技术洞察（第 279 期）

**生成时间**：2026-11-18 10:31（Asia/Shanghai）
**观察窗口**：2026-04 至 2026-11-18
**本期主题**：批处理等价性面／离线批处理与在线推理——同一把尺子，两种刻度

## 题眼

2026-06-25 的一篇推理经济学分析给了一组很直观的对照：同一个模型，**最大并发 128 时吞吐 670 tok/s，最大并发 400 时 7,470 tok/s**，差约 11 倍；而吞吐提升的代价写在另一段里——**连续批处理让请求结果不再确定**，同一 prompt 在不同并发下可能给出不同输出，因为 BF16／FP16 的浮点加法不满足结合律，归约顺序随 batch 形状变化。

这不是孤例。Kampfire（2026-09-20）记录的“同一 prompt、不同答案”有五个来源：动态批处理、KV 缓存复用（多轮前缀缓存）、采样与 seed、进程重启、部署变更；同一台机器上两个 server 进程对同一请求可以给出不同结果。Uplya（2026-04-28）在文档抽取场景里看到的是业务后果：去重、重排序、动态批处理、投机解码都会改变抽取值；更隐蔽的是**分块耦合**——上游分块边界一变，下游抽取结果就跟着变，而分块本身又受批处理调度影响。

于是“离线跑一遍、评测通过、再上线”这条最常识的流水线，建立在一个未声明的假设上：**离线与在线是同一个执行语义**。它们不是。

## 一、发展趋势

1. **批处理从“省钱手段”变成“第二种引擎语义”**。OpenAI 的 Batch API 用 24 小时窗口换折扣，vLLM 的离线 `LLM` 类与在线 server 走的是两套调度路径；离线追求吞吐会把并发拉到数百，在线为了延迟把 batch 压到个位数。两者对同一 prompt 的输出分布不同，而团队通常只用一个评测集。

2. **“可复现”被拆成“同硬件、同版本、同配置”三个限定词**。vLLM 的可复现性文档把范围限定得很清楚：同硬件、同版本、同参数；跨版本、跨 GPU、跨 batch 形状都不保证。Skalse（2026-04-28）进一步指出：随机性来源不只 sampling，**batch size 与调度器本身就会改变条件分布**——所以“固定 seed”远远不够，还要固定“同时还有谁在跑”。

3. **回填成为评测与合规的必经动作，也是成本黑洞**。Aviator（2026-04-24）描述的回填流水线：改了 prompt 或换了模型，历史记录必须重算才能比较新旧策略；10,000 张工单 × 8 次 LLM 调用就是 8 万次调用。合规场景更硬——“当时这条结论是怎么产生的”需要一个可重放的配置，而不只是“当时用的哪个模型”。

4. **缓存把“同一次请求”变成“两个世界”**。多轮对话复用 KV 前缀缓存时，命中缓存的请求与未命中的请求在数值上不同；离线回填如果共享同一个前缀缓存池，还会被在线流量污染。缓存本来是性能优化，现在成了等价性的隐藏变量。

## 二、技术现状

**第一层：评测集与线上流量不是同一分布，连执行配置都不是。** 离线评测常用固定 batch、固定 seed、关闭投机解码；线上是动态 batch、开投机解码、开前缀缓存。两者比的不是“模型 A 与模型 B”，而是“配置 A 与配置 B”。

**第二层：配置没有被哈希进结果。** 多数调用日志记录 model、prompt 版本、temperature；不记录 batching 配置、attention 后端、量化格式、投机解码开关、CUDA graphs 状态。事故复盘时无法回答“线上这条与离线那条，除了模型还差什么”。

**第三层：回填的等价性没人验证。** 回填通常只校验“跑完了、没报错、抽样看着像”，不校验与线上历史结果的一致性；而由于批处理差异，抽样看起来像、整体分布却可能偏。

**第四层：合规要求把这条缝变成硬约束。** “可解释”在监管语境里接近“可重放”：给定输入与配置，能重建输出。没有 config hash，回填只能证明“我们重跑过”，不能证明“重跑等于当时”。

## 三、技术竞争力

| 方案／机制 | 执行语义 | 确定性 | 与在线等价 | 成本 | 可审计性 | 运维适配度 |
|---|---|---|---|---|---|---|
| 在线 server（vLLM 默认） | 动态批处理 | 否 | 基准 | 高（延迟优先） | 需自建 | 高 |
| 离线 `LLM` 类 | 大 batch 吞吐 | 否 | **否** | 低 | 需自建 | 高 |
| Batch API（24h 窗口） | 厂商托管批处理 | 未承诺 | 否 | 最低 | 厂商日志 | 中（黑盒） |
| `VLLM_BATCH_INVARIANT=1` | 批不变 | 是（同版本同硬件） | 部分 | decode 性能降 | 可测 | 中 |
| 固定 seed＋temperature=0 | 采样确定 | 部分 | 否（批处理仍变） | — | 弱 | 高（常被误用） |
| 投机解码 | 加速 | 否 | 否（接受率随负载变） | 低 | 弱 | 中 |
| 前缀／KV 缓存 | 复用 | 否 | 否（命中与否不同） | 最低 | 弱 | 高（需隔离） |
| 配置哈希（config_hash） | 记录 | — | 可判定 | 极低 | 强 | 高（建议必建） |
| 双轨评测 | 同配置对照 | — | 可验证 | 中 | 强 | 高 |
| 回填流水线（Aviator 类） | 重算 | 否 | 需校验 | 高 | 中 | 中 |

**判读**：引擎卖吞吐，缓存卖延迟，Batch API 卖价格，评测框架卖指标；没有一家卖“离线与在线是否同一分布”的判定。这层只能由使用方自己补：config hash＋双轨抽样＋回填校验。

**本期反转**：我们默认“离线批处理＝同样的模型、更便宜的方式”，所以离线评测的结论可以外推到线上。实际上离线是**另一种执行语义**：输出不只取决于 prompt 与 seed，还取决于同一时刻 batch 里还有谁、缓存是否命中、投机解码接不接受。**离线与在线不是同一把尺子的两种刻度，是两把尺子。**

**判词**：「批处理平台／推理引擎／seed／temperature／缓存／评测框架」全部可采购，「这条结果是在什么 batching 配置下产生的、与线上那条是否同一个分布、回填后能否证明等价」不可采购。

## 四、技术挑战

1. **配置维度爆炸**：batching、量化、attention 后端、投机解码、CUDA graphs、缓存策略，组合数远超评测集覆盖能力。
2. **seed 的误导性**：固定 seed 只固定采样，不固定归约顺序；团队常把“可复现”误当成已解决。
3. **缓存污染**：离线与在线共享前缀缓存时，回填结果被在线流量影响；隔离又要付出内存代价。
4. **回填成本**：全量重算不可行，按 hash 定位受影响子集需要细粒度血缘。
5. **合规口径**：监管要“可重放”，工程只能给“可重跑”；两者之间的差距没有标准话术。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 配置哈希：每次调用记录 `exec_config_hash`（模型 digest、template hash、batching 配置、量化、attention 后端、投机解码开关、缓存策略、seed 策略）。
- D2 双轨评测：离线评测固定一套配置，同时用同一配置跑线上小流量对照，报告差异而不是只看绝对值。
- D3 回填校验：回填前后按 config_hash 分组抽样，比对分布（不只抽样目测）；差异超阈值阻断“新旧策略对比”的结论。
- D4 缓存隔离：离线回填使用独立缓存池，或在 config_hash 中显式标注缓存命中状态。
- D5 等价类声明：定义哪些变更（prompt、模型、量化、引擎）必须重跑，哪些可以复用历史结果。
- D6 证据链：每条历史结论可回答“输入＋配置＋版本”，支持合规抽检。

**用户旅程（一次“离线更好、线上更差”）**

① 团队用离线批处理跑 10 万条工单分类，batch=400、开投机解码，指标比线上高 3pp（D2 缺失）；② 上线后线上不达标，排查发现线上 batch=8、前缀缓存命中率高，两者执行语义不同；③ 想回填重跑历史，成本约 8 万次调用（D3 未做子集定位）；④ 回填结果与历史结果对不上，无法判断是策略改进还是批处理差异（D1 缺失）；⑤ 合规抽检要求“当时怎么产生的”，只能提供模型名与 prompt 版本（D6 缺失）。

**90 天实现方案**

- **第 1–30 天**：给调用日志加 `exec_config_hash` 与缓存命中标记；把离线与在线的 batching 配置写进同一张表；选一个高频任务做双轨对照。
- **第 31–60 天**：离线回填改用独立缓存池；回填按 hash 定位受影响子集；评测报告改为“同配置对照＋跨配置敏感性”两栏。
- **第 61–90 天**：定义等价类与重跑规则；把回填校验纳入发布门禁；合规抽检做一次演练，验证能重建“输入＋配置＋版本”。

**第 200 个市场空白（五项）**：① exec_config_hash 的字段标准；② 离线／在线双轨评测方法；③ 回填等价性校验口径；④ 缓存命中状态的可观测字段；⑤ 合规“可重放”的工程话术。

**`batch_semantics.*`／`offline_equivalence.*` 第 167 次无人提字段族**：平台文档谈“离线批处理更便宜”，不谈“它与在线是否同一分布、回填能否证明等价”。

**本地 173／173-kb 连续第 155 期成组启用（肖汉松 22：离线与在线要能对上同一口径）**：本地原型给每次调用打 `exec_config_hash`，离线评测固定配置并与线上 1% 流量对照；回填只跑 hash 变化的子集，差异报告附在发布单后。
