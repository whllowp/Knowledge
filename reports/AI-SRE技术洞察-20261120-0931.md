# AI-SRE 技术洞察（第 300 期）

**生成时间**：2026-11-20 09:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-20
**本期主题**：迁移面／在线 schema 变更与回滚——迁移是唯一同时改代码和数据的变更，而“回滚”本身也是一次迁移

## 题眼

2026-03-15，Autumn 在生产库上做了一次排序规则（collation）迁移，目标表是 `customer_entitlements` 与 `customer_products`。15:00 变更应用，数据库 CPU 立刻飙升、查询开始失败，约 **10% 的 API 请求**受影响。15:05 定位到问题，团队尝试用 `ALTER TABLE` 回滚——**被持有锁的活跃查询挡住，反复死锁**；15:20 试图在代码层显式 cast collation 绕开回滚，没有成功；15:48 在 PlanetScale 支持下**停掉全部应用连接**、回退 collation、跑 `ANALYZE` 恢复索引，16:15 恢复（Autumn 事故复盘，2026-03-14 发布）。

这个时间线值得逐行读：真正拖长故障的不是迁移本身，而是**回滚也需要锁**。迁移把表锁住、把查询拖垮，查询又持锁挡住了回滚——一个自我强化的死结。

2026-06-05 的另一份场景记录把机制写得更直白：给一张 6,000 万行的 `orders` 表加 `region` 列（`NOT NULL` 带默认值、随后 `UPDATE` 回填），单条迁移语句拿到 **AccessExclusiveLock** 并持有到整表重写完成，所有读写排在它后面，`lock_timeout`／`statement_timeout` 报错刷屏，应用停机约 **6 分钟**（RavenClaude 场景库，2026-06-05）。

工具的进展也是真的：pgfence 在 2026-03-04 整理了五类最危险的 Postgres 迁移，把“先加约束、后 `VALIDATE CONSTRAINT`”的拆分序列写成了可复制配方；caura 在 2026-04-26 的提交里给迁移加了 advisory-lock 加固——用 `pg_try_advisory_lock` 在 AUTOCOMMIT 里轮询、每 30 秒打一次进度日志，并加了 CI 守卫：从 005 号迁移起，**禁止在大表上走普通 `CREATE INDEX`**，必须 `CONCURRENTLY`。

但另一份课程文档（2026-08-20）写了一句最容易被忽略的话：**“存在 downgrade 函数，并不保证回滚在生产数据上是安全的。”**

## 一、发展趋势

1. **迁移从“发版的一部分”变成“独立的在线操作”**：expand/contract、在线 DDL、pgroll 等模式，把一次迁移拆成多步、每步都可独立回滚。

2. **锁开始被当成一等指标**：AccessExclusiveLock 的持有时长、等待队列深度、`lock_timeout` 触发次数，正在进入发布门禁。

3. **CI 开始拦截危险 DDL**：普通 `CREATE INDEX`、整表重写的 `ADD COLUMN`、未拆分的 `ADD CONSTRAINT`，被静态规则挡在合并前。

4. **回滚被承认为“另一次迁移”**：回滚同样要拿锁、同样受流量影响、同样可能不可逆。

5. **数据不可逆性被单独讨论**：删列、改类型、回填错误值，代码可以回滚，数据不能。

## 二、技术现状

**第一层：锁剖面。** 每条 DDL 拿到什么锁、持有多久、会不会排队，取决于表大小、是否有默认值、是否重写；文档给了锁级别，没给“在你这张表上要多久”。

**第二层：拆分执行。** expand（加新列/新表）→ backfill（分批回填）→ 双写/双读 → contract（删旧列）；每一步都要有进度、可暂停、可重试。

**第三层：回滚路径。** 迁移文件里的 `downgrade()` 只描述结构逆操作，不描述数据逆操作；回滚 `ADD COLUMN` 是 `DROP COLUMN`，数据直接丢。

**第四层：并发窗口。** 滚动发布期间，旧代码与新 schema 同时存在；课程文档提醒：单机编排通过健康检查，**不能证明两个应用版本能安全重叠**。

**第五层：证据层。** 事后能查到“哪个迁移文件、几点执行、耗时多少”，查不到“当时锁等了多久、谁在等、回填覆盖了多少行、回滚尝试失败在哪一步”。

## 三、技术竞争力

| 方案／机制 | 锁级别 | 是否重写表 | 可中断 | 回滚成本 | 在线工具 | 证据字段 |
|---|---|---|---|---|---|---|
| `ADD COLUMN` 带默认值（旧版） | AccessExclusive | 是 | 否 | 高（重写） | gh-ost/pt-osc | 弱 |
| `ADD COLUMN` 可空（新版） | AccessExclusive（瞬时） | 否 | 是 | 低 | 原生 | 弱 |
| `ADD CONSTRAINT` 直接加 | ShareRowExclusive/更强 | 否（但全表校验） | 否 | 中 | 拆 VALIDATE | 弱 |
| `CREATE INDEX` 普通 | ShareLock | 否（阻塞写） | 否 | 中 | CONCURRENTLY | 弱 |
| `CREATE INDEX CONCURRENTLY` | ShareUpdateExclusive | 否 | 是（失败留 invalid） | 低 | 原生 | 中 |
| 分批 backfill | 行级 | 否 | 是 | 低（可重跑） | 自研/工具 | 中 |
| 双写/双读 | 无 DDL | 否 | 是 | 中（窗口内不一致） | 应用层 | 中 |
| `downgrade()` | 同 DDL | 视操作 | 否 | 视数据 | 框架 | 弱 |

**判读**：每一档都能回答“这条 DDL 拿什么锁、会不会重写”。没有一档能回答“**在你这张表、这个流量、这个复制拓扑下，锁会持有多久、队列会积多深、回滚时还拿不拿得到锁、已回填的数据能不能还原**”。而这些恰恰决定故障是 6 分钟还是 75 分钟。

**本期反转**：我们一直把迁移当成“发版时顺手做掉的一步”，默认它快、可回滚、失败就重来。实际迁移是唯一同时改**代码语义**和**数据内容**的变更：结构可以 downgrade，数据不能；回滚要拿的锁，可能正被迁移拖垮的查询持有。Autumn 的 75 分钟不是被迁移本身拖长的，是被“回滚也要排队”拖长的。**迁移的可靠性不取决于 upgrade 写得多对，而取决于 downgrade 在最坏时刻还拿不拿得到锁。**

**判词**：「迁移框架／在线 DDL 工具／锁监控／backfill 库／双写框架／CI 规则」全部可采购，「这条迁移在目标表上的锁剖面、回填覆盖到哪一行、回滚时锁是否可得、已改数据能否还原、新旧版本重叠窗口有多长」不可采购。

## 四、技术挑战

1. **锁不可预测**：同一句 DDL 在 6,000 万行表和小表上的持锁时间差几个数量级。
2. **回滚被锁挡住**：迁移拖垮的查询持有锁，回滚排在其后，形成死结。
3. **数据不可逆**：`downgrade()` 只逆结构，不回数据；删列/改类型直接丢信息。
4. **重叠窗口**：滚动发布期间新旧代码并存，单机健康检查证明不了兼容。
5. **回填无进度语义**：跑到哪、跳过哪些行、失败重试几次，缺少标准字段。
6. **复盘口径漂移**：有复盘把“表被重写”写成根因，锁日志却显示没有重写——证据不齐时，叙事会替代事实。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 锁剖面预演：迁移前在影子库/统计信息上估算锁级别、持有时长、队列深度。
- D2 分段可停：expand/backfill/contract 每段独立、可暂停、可重试，带进度。
- D3 回滚可达性：回滚前检查目标表锁是否可得，必要时先摘流量再回滚。
- D4 数据可逆性声明：迁移文件声明“数据是否可还原”，不可逆操作必须备份并双人确认。
- D5 重叠兼容测试：旧代码×新 schema、新代码×旧 schema 两组兼容用例进 CI。
- D6 迁移取证：记录锁等待、回填行数、回滚尝试与失败点，复盘引用原始锁日志。

**用户旅程（一次“回滚排不上队”的迁移）**

① 迁移在高峰期执行，`ALTER TABLE` 拿到 AccessExclusiveLock 开始重写（D1 缺失）；② 读写全部排队，超时错误刷屏，10% 请求失败（D2 缺失）；③ 团队立刻回滚，回滚语句排在查询队列后面，反复死锁（D3 缺失）；④ 只能停掉全部应用连接，业务硬中断，再回退并 `ANALYZE`（D3 缺失）；⑤ 复盘时只有“迁移导致锁”，没有锁等待曲线与回填进度（D6 缺失）；⑥ 下次仍按“发版窗口”排期，而不是按“锁剖面”排期。

**90 天实现方案**

- **第 1–30 天**：为大表迁移加锁剖面预演（D1）；把 expand/backfill/contract 拆成可停步骤（D2）。
- **第 31–60 天**：回滚前锁可得性检查与“摘流量再回滚”剧本（D3）；不可逆操作备份+双人确认（D4）。
- **第 61–90 天**：新旧版本重叠兼容用例进 CI（D5）；迁移取证字段与复盘引用规范（D6）。

**第 212 个市场空白（五项）**：① 迁移锁剖面预演标准；② 分段迁移的进度与暂停语义；③ 回滚锁可得性检查；④ 数据可逆性声明与备份门禁；⑤ 迁移取证字段（锁等待/回填/回滚失败点）。

**`migration.*`／`lock_profile.*` 第 179 次无人提字段族**：文档谈“怎么写 upgrade/downgrade、怎么用 expand/contract”，不谈“锁会持多久、回滚排不排得上、数据能不能还原”。

**本地 173／173-kb 连续第 167 期成组启用（陶炳哲 30：迁移先算锁）**：本地原型给每个迁移写 `migration_plan{table, rows_est, ddl, lock_level, lock_hold_est_s, rewrite: bool, backfill_batches, backfill_done, rollback_lock_available, data_reversible: bool, overlap_tested: bool, evidence_log}`；发布门禁要求大表迁移 `lock_hold_est_s` 有估算、`data_reversible=false` 时必须备份并双人签。
