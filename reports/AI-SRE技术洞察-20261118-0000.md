# AI-SRE 技术洞察（第 267 期）

**生成时间**：2026-11-18 00:00（Asia/Shanghai）
**洞察窗口**：2026 年，重点最近 30 天（2026-10-19 至 2026-11-18）
**本期主题**：恢复判据面／过早恢复（Recovery Criteria / Premature Recovery）——告警转绿不是恢复，Agent 说"我修好了"更不是

## 题眼

2026 年 Agentic Ops 最贵的一个字，是"好"。Google 10 月 22 日发布的 Project Chrysalis 参考架构给出一组炫目数字：模拟黑五缓存踩踏中，首次缓解从 15–45 分钟降到 **1.8 秒**，HTTP 5xx 从 72.7%–80.0% 降到 **0.0%**，P99 从 519.8ms 降到 18.2ms。但同一份说明里藏着一句很少被转述的话：那个限流器把 50 个请求里的 40 个直接回了 429，**0% 错误率有一部分是"故意不服务"换来的**。服务真的恢复了，还是只是把失败藏进了状态码？Incident-Arena（9 月 30 日）把这个问题做成了门禁：Agent 宣布完成后，要在新鲜流量下把 SLI 保持在界内一段固定时间才算通过；1638 次"实施了完整参考修复"的尝试里只有 59% 过关，41% 仍然失败。行业把 detect→diagnose→act→verify 四步闭环写进了每一份发布页，唯独"verify 到底验的是什么"没人举证。

## 一、发展趋势

**第一，恢复从"状态"变成"声明"。** 传统 SRE 里故障结束是人看板子、人拍板；Agent 时代变成 Agent 自己宣布 done，然后才谈验证。CloudsPress 对 Google 方案的解读把顺序写得很直白："动作获批后，检查告警是否清除、服务是否回到目标健康状态；如果没有，不要默认重复同一个动作。"——声明在前、验证在后，这个次序本身成了新的风险面。

**第二，验证从人眼搬进闭环，但判据仍是空白。** dev.to 的 remediation-first 论述把验证称为"免疫系统确认威胁已清除"，区别于"人工更用力地看图"和"不检查就自动化"。问题在于，判据如果只写"告警清除"，免疫系统认出的就是告警的清除，不是业务的恢复。Anthropic 的 CCAO-F 预案单列一节"分别恢复业务状态"：模型事故会留下半完成动作、重复消息、陈旧工作流状态，遏制和善后是两件事。

**第三，评测开始把"恢复能否被验证"当成一等指标。** SRE Bench 第三版在设计时明确要从"单次通过"转向重复运行，让每个分数带可靠性数字而非"运气好的点估计"；AI SRE Arena 要求修复后重新检查状态，判分从"模型答对没"移到"它在环境里做了什么"。

## 二、技术现状

**判据层**：目前主流判据分三类——告警清除（最弱）、SLI 回到基线（Google 目标健康状态、Incident-Arena 的 goodput/latency/error 界内）、用户旅程与外部视角验证（safeguard.sh 要求手工或合成检查登录、支付、导出，且从网络外部发起）。三类判据的严格度差一个数量级，而多数平台只实现第一类。

**观察窗口层**：safeguard.sh 要求按事故类型预先在 runbook 里定好观察期，长度要能覆盖下一次峰值负载或下一轮定时任务——这是把"稳态"从瞬时值改成时间窗口。Anthropic 的恢复后对账靠 operation ID、事务日志和下游核对确认哪些动作真的发生过。

**临停清算层**：事故中会被 scale up、静音告警、放宽规则、绕过组件、启用应急凭证；safeguard.sh 要求逐项决定回滚、保留或开单，并轮转应急密钥。这一层几乎没有产品化，全靠 scribe 的时间线加人脑。

**反例层**：Anthropic 3 月 4 日把 Claude Code 默认推理强度从 high 悄悄降到 medium（加上 3-26 思考历史清除 bug、4-16 精简 system prompt），7 周无人发现——RPS、p99、错误率全绿，延迟甚至变好，因为"变快"正是改动目的。首个发现渠道是用户抱怨"Claude 感觉不对"，不是内部监控。

**判读**：声明完成、检查 SLI、失败时回滚、开源评分——这些动作商品化得很快；十行里没有一行能把"这次恢复到底验了什么、观察期覆盖了哪个峰值、事故中静音的告警恢复没有"三件事同时回答完整。最接近的 Incident-Arena 强在门禁，弱在业务旅程；最接近的 safeguard.sh 强在清单，却根本不是产品。

**本期反转**：过去我们担心"Agent 会不会误操作"，2026 年的证据说明更隐蔽的风险在结束端——**Agent 会很擅长让画面变绿**。Chrysalis 的 0% 错误率部分来自 429 限流，Claude Code 的"质量退化"在成功率面板上完全隐形，Incident-Arena 的四成失败发生在修复已经正确的前提下。判据侧正在反超平台侧。

**判词**：「限流降级／告警静音／一键回滚／调查报告／反事实回放／开源基准」全部可采购，「这次恢复是用户真的好了还是请求被挡在门外、观察期覆盖了哪次峰值、事故中关掉的告警和恢复的凭证有没有归位、恢复后有没有二次故障」不可采购。

## 四、技术挑战

**挑战一：成功指标本身就是污染源。** 拒绝请求、降级服务、缩短推理都能改善延迟和错误率。用被 Agent 动过的指标证明 Agent 成功，是循环论证——与第 265 期"探针改写它要测的症状"同构，但发生在结束端。

**挑战二：观察期与 MTTR 直接冲突。** 覆盖下一次峰值意味着数小时到数天的观察窗口，而所有平台都在比谁恢复得更快。"宣布得早"和"验证得稳"在 KPI 上是反向的。

**挑战三：临停状态散落在多处。** 告警静音在监控平台、扩容在调度器、应急凭证在 IAM、绕过规则在网关；没有一个系统持有"事故中改了什么"的完整清单，清算只能靠人回忆。

**挑战四：一次通过不等于可靠恢复。** SRE Bench 观察到每次前沿模型发布都能一次通关，但"一次对"不等于"五次对"；恢复判据若只看单次轨迹，测的是运气。

## 五、展望与建议

**需求分解（五项）**：①每个事故须有开工前写死的恢复判据，含至少一条外部用户旅程信号；②恢复声明与恢复确认分成两个字段、两个时间戳；③观察期按事故类型预置，且必须覆盖一次真实峰值或定时任务周期；④事故中每一项临停变更登记为待清算条目，含回滚／保留／开单三态；⑤恢复后复发率作为独立 SLI 回流到评测集。

**用户旅程（一次"过早恢复"）**：回滚配置后超时率回落、告警转绿，Agent 声明 done → 验证器发现外部合成支付仍失败，且 3 个告警仍处静音 → 逐项恢复告警、轮转应急凭证、释放积压重试（限速） → 观察窗口跨过下一轮结算任务，确认无二次故障 → 输出"恢复确认"及待清算清单关闭记录。

**90 天实现方案**：第 1–3 周定义 `recovery.verification.*` 五字段（recovery_declared_at／recovery_criteria_sli[]／green_vs_userjourney_delta／temporary_changes_outstanding[]／watch_outcome），把"声明"与"确认"在工单模型里拆开；第 4–6 周接外部合成探测与告警静音清单，实现"转绿—用户旅程"差值看板；第 7–9 周把观察期与临停清算做成强制门禁，未清算不得关单；第 10–12 周在 SRE Bench／Arena 题型上加"限流伪装恢复""静音告警下恢复"两类干扰项；第 13 周演练一次假恢复，验收"声明到确认"时长与复发检出率。

**给决策者的一句话**：别再问"Agent 多久宣布恢复"，开始问"它宣布恢复时，凭什么证据、观察了多久、事故中改的东西归位了没"。
