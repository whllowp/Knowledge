# 记忆技术洞察 第60期：记忆的可逆性工程——回滚不是删除：非破坏性版本化与依赖传播

> 生成时间：2026-11-12 10:00 ｜ 固定四维：发展趋势 / 技术现状 / 技术竞争力 / 技术挑战
> 覆盖来源：arXiv 记忆论文（ChronoMem 2607.27773、BPMA/Memora、BVC、StateGraph 2611.02912、Rollback Repair 2608.10502）、OpenViking、Hy-Memory、TencentDB-Agent-Memory、ReMe、dsh-memory-evolve

## 主线与新观点

前 59 期把"记忆主权"拆到了删除权（第2期）、Ghost Memory（第55期）、整库时间旅行（第47期）。本期指出三者共享一个错配的底层原语：**行业用"删除"去实现"改错了能退回"，而删除是破坏性回滚，版本化才是非破坏性回滚**。核心反共识观点——**用户要的从来不是"销毁一条记忆"，而是"带着完整历史把它退回到某个可信状态"；'删除权'是错配的诉求，'可撤销的版本化'才是真实诉求**。这把第2期（删除举证）、第47期（整库 PITR）、第55期（状态协调失败）三者收敛到同一个更对的原语：回滚。

## 发展趋势

版本化正从论文走进框架。ChronoMem（集成进 Google Agent Development Kit，2607.27773）每次写入提交整库快照、支持自然语言回滚，并引入"暴露后评测"验证回滚后能否反事实地行为一致；BPMA/Memora 把记忆改写为只追加事件记录（事实/摘要/图/索引全是可重放的派生投影），对"谁在何时从何源学到、替代了哪条信念"类查询命中 100% vs 破坏式存储 19.2%。BVC（Behavioral Version Control）进一步把 agent 自我修改渲染成可评审 diff＋只追加变更日志＋风险分级审批闸＋commit 级回滚。

## 技术现状

五家产品的"回退"能力严重不均。Hy-Memory 2.0.13 的 chatdelete() 修复版本链、保留原始 L1 与 history.db——已是**非破坏性删除**的雏形；OpenViking 以 viking:// 虚拟文件系统＋每次写入 commit＋archive 回退，版本化 by design；dsh-memory-evolve 用 git 分支标签作最廉价历史与审计；ReMe 的 .reme/ Markdown 文件天然可被 git 跟踪；TencentDB 靠 node_id 下钻链与迁移工具保可追溯。但**无一产品做到"依赖传播式回滚"**：改一条事实，依赖它的信念、计划、动作仍活跃。

## 技术竞争力

"论文先于产品"的倒挂在此局部反转——git 化项目（OpenViking/dsh/ReMe）与 Hy-Memory 版本链已具备版本底座，比 ChronoMem 的整库快照更细粒度。真正的空位是**依赖传播**：StateGraph（2611.02912，11-02）用反事实验证分离"支撑依赖"与"语义相关"，较深依赖 Impact-F1 +26.0pp；Rollback Repair（2608.10502，v2 10-22）建类型化记忆-动作图、保留独立可信支撑、即时恢复 85.3% vs LLM-judge 77.3%，但选择性重放使复发率 26.6% vs 12.1%——目标修复与全局重算的权衡首次被量化。六家产品对"回滚一致性"零披露，AML 无版本/回滚维度（口径缺口延续）。

## 技术挑战

①粒度错配：托管服务只给 per-entry target_revision_id，全局一致性（历史摘要、派生索引、工具副作用）需整库快照，局部回滚留下"半恢复真相"；②依赖传播工程化缺失，回滚常复活 Ghost Memory；③参数轨记忆（Hy-Memory 30B、TencentDB）最难版本化，第50期"固化账"的资产折旧在此升级为"版本不可见"；④回滚的外部副作用边界（工具调用、账单、跨系统）无人定义。

## 需求分析

企业最怕的不是"记错"，而是"记错后无法可信地退回且波及未知"。合规（GDPR 第17条删除）的真实动作应是"回滚到未受影响状态并留痕"，而非物理销毁；审计要求"这一版记忆由谁在何时基于哪条源改出、能否一键回退"。需求本质是：**非破坏性、可审计、可依赖传播的撤销**。

## 用户旅程

开发者发现 agent 因一条被投毒的偏好连续出错 → 在 Hy-Memory 用 history.db 定位该版本、chatdelete 非破坏撤销并保留原始 L1 → 若波及下游计划，在 StateGraph 式依赖图上标记受其支撑的信念一并失效 → 在 OpenViking viking:// 用 git 历史 checkout 到某次 commit 反事实复盘 → 确认无误后保留新状态，全程不丢历史、不污染其他会话。

## 具体实现方案

1. **只追加事件源**：以 BPMA 为基线，每条 Memory Event 带 principal＋模型版本＋双时间（event/ingestion）＋血缘，所有检索结构为可重放投影。
2. **非破坏性删除**：删除＝新增一条 supersede/revoke 事件并修复版本链（仿 Hy-Memory），原始记录永留，满足 GDPR 第17条且可反事实。
3. **依赖传播回滚**：为每条记忆维护 typed 依赖边（仿 StateGraph/Rollback Repair），回滚时反事实验证下游是否仍有独立支撑，无则一并失效，避免 Ghost Memory 复活。
4. **commit 级闸门**：git 化记忆（OpenViking/dsh/ReMe）用 commit 作回滚点＋风险分级审批（仿 BVC），外部副作用显式列清、回滚有界。
