## 一、发展趋势

过去一个月，Agentic Ops 的治理叙事出现了一次不易察觉的**前置化转向**。10 月 29 日 MIT Technology Review 刊发 Partnership on AI 的研究，把「持久 Agent 身份、人工干预记录、权限／记忆变更记录」列为四大框架共同缺失的遥测信号；11 月 4 日起的两周内，Sysdig、Okta、Microsoft、Snowflake 相继把「Agent 清单／注册表」做进产品；11 月 19 日 groundcover 发布 Investigations，用第二个 Agent 复核证据才接受根因。这些动作表面各说各话，实则都在补同一个空洞：**在问「它有身份吗、分工对吗、结论准吗、哪个模型在服务」之前，先得知道「此刻有哪些 Agent 在跑」。**

这是本系列前几期共同的隐含前提。#199 身份面问「用谁的凭据」，#289 分工面问「哪步是规则哪步是模型」，#290 证据通道面问「沉默是不是没送到」，#292 干预信用面问「好转算谁的功劳」，#295 置信度面问「它说多准和实际多准是否一致」，#296 底座漂移面问「实际推理的是哪个模型」——**六者都默认责任主体已知、在册、可寻址**。一旦跑着一个没人登记的 Agent，这些字段要么锚定到错误主体，要么根本没有主体可锚。在场性不是第七个并列维度，而是前六者的存在论前置层。

国内侧同步推进但侧重不同：阿里云 11-11 发布 AgenticOps 全栈能力，以 OTel／UModel／BRiSE 统一数据模型，明确把「Agent 自身的运行轨迹、成本与质量」纳入可观测；火山引擎智能运维助手在「深度调查」中追加 RCA Harness 排障约束层，并允许专家 Agent 通过自定义 IAM 角色按需跨服务取证；腾讯云 CloudQ 把告警命中后的根因分析自动推送到群。三家都在扩张「看得见 Agent 做了什么」，尚未见一家把「这个 Agent 在不在册、谁认领、是何时被谁发现的」做成一等字段。

## 二、技术现状

**名册正在从「人填的清单」变成「观测算出的判决」。** 传统 CMDB 式登记依赖团队主动申报，而 Agent 便宜到随时可造、空闲时不可见，名册天然腐烂。新一代做法从节点而非从 Agent 读信号：eBPF 与进程检查读出「连了哪个模型端点、进程里加载了什么 Agent 框架、配置里点了哪家供应商」，再与注册表比对，给出 `registered / shadow / unknown` 三态判决；身份由基础设施签发（SPIFFE、OIDC 或 pod-owner 绑定），网关默认拒绝并逐请求记录调用方、目标与操作。判决写在执行面，不由 Agent 自述——这一点是它与「读 transcript」的根本区别。

**发现点是多源的，任何单一产品都看不见全境。** 注册表只收录被主动登记者；AI／MCP 网关只看得见经过网关的流量，直连供应商密钥、本地 stdio MCP、端侧模型一律不入账；身份侧看 OAuth 新授权与服务账号；端点侧看 AI 工具配置文件与进程；SaaS 侧看 Copilot Studio、Agentforce、n8n 之类构建器；云账号与代码库看 service principal、部署流水线、git 里的 Agent 定义。业界已形成共识做法：**对账而非枚举**——把各源取并集，命中即 in-register，未命中即 shadow，并双向检查（在认证却未登记、登记了却 90 天未认证）。

**标准仍在「草案未定稿」状态。** OTel GenAI semantic conventions 已定义 `create_agent`／`invoke_agent`／`execute_tool` 与 `gen_ai.agent.name` 等属性，但状态仍是 development，属性名可跨版本变动，Agent tracing 的共享格式尚未 final。NIST 的 AI Agent Standards Initiative 停在概念文件阶段，IETF WIMSE 草案要求 Agent 必须可唯一标识，A2A 1.0 支持签名 Agent Card。PAI 明确警告：**不要把 traceparent／baggage 当作「谁调用的」证据**，那是授权缺陷。

**反转**：发现工具与身份标准都在被采购、被推进；但「把影子判决当一等事故字段、双向对账、发布 delta 而非总数、身份权威来源扎根节点而非 transcript」——九家几乎全空。海外赢节点级观测与标准草案，国内赢把 Agent 轨迹纳入统一数据模型。新观点：**看得见动作 ≠ 看得见执行者**（遥测问题 vs 存在论问题）。

## 四、技术挑战

1. **判决的时效与空转**：节点检测依赖窗口内「调用过模型」，空闲 Agent 不出现；gRPC 或未列入观察名单的端点直接漏检；凭据若不经 Secret 引用注入，会被长期误判为 shadow。首周检出往往是一张「要跑去问人」的清单，而人决定是否合规——工具不会替你签字。
2. **名册腐烂的不对称**：新增无人管，退役无人删。「14 个 Agent 在册」对治理委员会毫无信息量，「6 新增／2 退役／3 未登记发现」才是决策级报告；但多数组织仍在报总数。
3. **身份与授权割裂**：即使判定为 registered，也不等于「这次调用确实来自它自称的身份」；把传播上下文当授权依据是当前最普遍的越权形态。
4. **审计三问之外的第四问**：监管会问「哪个 Agent 建议拒贷、谁批准的」，紧接着问「它是否用了不该用的数据」；而影子 Agent 让第一问就没有答案。PAI 指出，接近一半有记录的 Agent 故障**根本没有攻击者**——不是被攻击，是没人登记。
5. **发现导致的治理滞后**：Gartner 称 59% 企业怀疑或已有证据表明员工在用未授权 Agent；IBM 2026 报告称遭遇 AI 相关泄露的组织中 92% 缺乏恰当访问控制、近 66% 没有检测影子 Agent 的治理政策。能发现不等于能处置，挂起动作需要不依赖重新部署的网关＋内核双层抓手。
6. **成本归因失真**：发票仍是一行。绕过 AI 网关的直连调用不计入任何 Agent 账单，成本与责任同时漏账。

## 五、展望与建议

提出第 218 个字段族 **`agent.presence.*`**：`registry_state ∈ {registered, shadow, unknown}`／`stable_agent_id`（跨重部署稳定，非 session id）／`named_owner`（自然人，非共享邮箱）／`observation_evidence`（节点 eBPF／OAuth 授权／网关出口／账单，须写明如何发现，禁自述）／`last_authenticated_at`＋`reconciled_at`／`presence_verified_at`。缺省 **PRESENCE_UNVERIFIED**：未声明在场状态者不得进 `write ≥ act` 自治档，其结论不得写入语义记忆、干预信用或置信度校准记录。

落地四步：**（1）发现即判决**——五源取并集、双向对账，shadow 发现当日指派属主，未认领的授权视同活凭据；**（2）发布 delta 不报总数**，登记设到期日、季度复核、有生产写权限者月度复核；**（3）权威来源下沉**——身份与判决写在执行面，网关默认拒绝，禁止把 traceparent 当授权；**（4）采购第六问**（承接 #296 第五问）：「你能否导出此刻生产里**所有** Agent（含未登记的）的判决与依据？」五闸门、逐例 diff、serving fingerprint 各家都有，唯独在场名册是空白。

**本地原型（第 173 期新角度）**：闪英迪《AgentENV：面向智能体的超大规模智能体执行环境架构与实践》过去被读成成本与稳定性（35% 执行场开销、约 5% 节点日宕），#98 又把它升格为信任边界；本期首次读作**「执行场是唯一能在 Agent 不合作时读出『谁在跑』的地方」**——节点侧观测正是 Tigera Lynx 判决的物理基础。配刘凯宁蚂蚁 SRE「结论／证据／待确认三分」扩出第十二分「这条结论由哪个 Agent 给出、它在册还是影子」，配周昕毅「白名单动作」——白名单默认行动者已在名单上，而影子 Agent 恰恰不在。

**注意**：Gartner 59%、IBM 92%／66% 为第三方调研转述，样本与口径需回原文；Sysdig／Okta／Tigera 能力多为厂商自述，未见独立横评；groundcover／New Relic 的「第二 Agent 复核」「90 余诊断探测器」同为厂商口径；PAI 研究是框架文档审计而非运行时实测，且属观点性文章；OTel semconv 未定稿，属性名会变；各基准分数不可直接相减。「在场性面／第 218 空白／在场名册是存在论前置层」为本文归纳。本地 173 讲义为目录级引用；字节跳动本期以火山引擎产品文档列主行。未采信 SEO 农场。

**下期候选**：`agent.presence.*` 的 OTel GenAI 提案与 PRESENCE_UNVERIFIED 门禁最小实现／五源发现对账器与 delta 报告模板／节点级判决与网关默认拒绝的落地清单／影子 Agent 发现当日属主指派流程／在场状态与 #199 身份／#296 底座的联合审计主键／信通院补「在场可举证率」格成九层治理。
