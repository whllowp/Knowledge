# AI-SRE 技术洞察（第 329 期）· 跨源证据冲突面 / Cross-Source Evidence Conflict Integrity
## 「指标说正常、日志说报错、Trace 说没调用、用户探针说失败——Agent 采信哪一路，凭什么？」

> 期号说明：`date` 取 2026-11-27 08:11→0800 档；本实例上一期 328（07:00 决策可复演面）顺延 329；主线第 282 个全新立面；字段族 250；本地连续第 205 期。

**题眼**：行业已把「三支柱」接进 Agent，但一次调查里指标、日志、追踪、变更事件、用户侧结果常对**同一个事实**给出互相打架的说法。现有体系默认「多路信号齐全＝真相更近」，却从不问：打架时谁说了算、优先级谁定的、换一条会不会翻案。本期首次把**跨源证据冲突与信源优先级**立为一等运维对象：与 #84 时间基准面（哪一时刻为真）、#262 数据龄期面（证据有多旧）、#286 证据托管面（记录能否被改写）、#319 判定函数面（谁定义失败）、#321 结论汇聚面（多个调查者竞争假设谁收口）、#322 信号可归因面（信号归哪段代码）、#323 测量生成面（谁写的埋点）、#325 因果排序面（时间戳与 parent_id 谁为真）、#328 决策可复演面（同证据重跑是否稳定）逐条划界：那些立面问的是某一路信号或决策本身，本期只问——**多路信号互斥时，裁决规则本身是否显式、可版本化、可独立复核**。grep 索引「信号冲突/证据冲突/数据源冲突/一致性校验/以谁为准/遥测源仲裁」均为 0，全新立面确认。

## 一、发展趋势

**趋势一：可观测性重心从「采集三支柱」移到「跨源对账与证据通道自观测」。** OpenTelemetry 官方 2026-11-10 博文《When Missing Telemetry Is the Signal》给出本期最锋利的一句：**"The application may be healthy while its telemetry path is not."** 空面板既可能是「什么都没发生」，也可能是「系统停止上报」，两者在图上同形；其解法不是再加一个 Agent，而是把对账规则工程化——`accepted = completed + rejected + still processing`，按固定间隔往真实链路发一条合成事件，盯住 Collector 自身的 receiver/exporter 计数器，并「尽可能独立地观测这条路径，免得一次故障把它自己的健康信号一起藏掉」。Mastering Observability 11-13 以 Google 伦敦区故障收束同一主题：控制器整夜都在读电源，传感器、信号、规则三者都尽职，**唯独规则指向了那根还带电的线**，两条真正馈线已死而它报告电源正常。作者的结论直指本期题眼：「人人都在给系统装仪表，几乎没人给证据走过的路装仪表」；并警告——把沉默交给凌晨四点的 Agent，它会用像样的英文、带着理由，报告一切正常。

**趋势二：语义层正在成为跨源冲突的实际裁决点。** Anthropic 11-12 更新的 Claude Tag 给出最具体的冲突样本：同一张事实表按「注册」「登录」「付费」三种锚点可得到三种「活跃用户」定义；表单提交与账号创建是两个时间戳，看板算后者、Agent 算前者，数字立刻分叉，时区与基线同样改变跌幅。其应对是把分析师认可的定义收进语义层、把取表与分析步骤写成可重加载的 Skills——**改定义即改口径，下次查询立即传播**。阿里在云栖（11 月）给出同构底座：LoongSuite/OBI 标准化采集、UModel 关联多源数据并维护统一语义与拓扑、BRiSE 做可复现评测，明确点出「语义不统一，Agent 仍可能把无关事件拼成一条因果链」。腾讯 CloudQ（11-03）把全景图谱做成推理前必查的事实源 RAG。Google《SRE》二版（11-15/17）则把可观测性改写成以 OTel 和自动异常关联为中心。

**趋势三：治理开始要求「权威不住在模型里」，但尚未管到信源优先级。** Pulumi（11-16~18）让每个 Agent 有独立身份、权限写进代码、扩权需评审 PR；InfoQ 受监管电力架构进一步要求控制平面阻止 Agent 直碰生产、版本化动作目录的风险等级模型不可自行降级、所有动作经单一网关校验留证、自治从只读起步逐类放宽。信通院《云上 Agent 基准度量模型》从六维评估并配数据可信、流程贯通、权限可控、过程可审计、结果可评价五项要求。然而这些框架都没有一格回答：**当指标与用户探针互斥时，裁决权归谁。**

## 二、技术现状

**已可采购的部分**：跨源接入（火山 DevOps Agent 公测版以 Connect→Diagnose→Act→Extend→Govern 编排，工具横跨云监控指标、APM 日志/Trace/服务拓扑；阿里 Connector + Fabric；腾讯全景图谱）；语义层钉口径（Anthropic Skills 以 Markdown 承载定义、每轮对话重加载；阿里 UModel 维护实体关系）；对账与合成探针（OTel Collector 内部遥测、`accepted = completed + rejected + processing`、端到端合成事件）；跨信号关联（火山 11 月新增 Trace↔TLS 日志字段映射与服务概览里的 Trace 写入量/Metrics 上报量）；对抗复核（OpenAI Performance Factory 派独立 Codex 审查员专事反驳初步诊断，据 VentureBeat 转述打回约 25%）。

**仍空白的部分**：把上述能力拼起来仍答不出本期问题。OpenAI 披露的真实打脸现场极具代表性——调查 Codex 凭图片下载报错宣布「根因已找到」，审查 Codex 却发现定位文件的内部服务**早已恢复**而前端图片请求仍在失败；两路信号对同一时刻给出相反陈述，被对抗复核偶然抓住，但系统没有「服务状态 vs 前端错误率」的优先级字段，更没有换一路是否翻案的记录。Anthropic Claude Tag 只把支付事故列为「待验证线索」并保留缺哪些证据——优先级仍由语义层隐式决定。火山文档明确写着 RUM 与 CloudDetect **尚未接入** DevOps Agent：用户侧结果那一路恰好不在 Agent 手里。Datadog 11-17/20 在线实验给出另一冲突样本：两版调查质量分 3.84 对 3.86 几乎相同、新版便宜约 44.3%，但 Trace 检查发现新版更频繁传入非法工具参数、靠重试恢复——**评分与轨迹互斥**。

## 三、技术竞争力：主要厂商 / 方案对比

| 方案 / 厂商 | 跨源接入 | 冲突裁决机制 | 优先级是否显式/版本化 | 沉默与缺失信号检测 | 换优先级是否反事实改判 | 本期视角下的缺口 |
|---|---|---|---|---|---|---|
| OpenTelemetry 官方《When Missing Telemetry Is the Signal》(11-10) | Collector 统一管线＋内部遥测 | `accepted=completed+rejected+processing` 三方对账 | 否（规则主张，非字段） | 是（合成事件＋队列/导出计数器） | 否 | 最强的通道自观测；但无「哪一路赢」的裁决语义与导出契约 |
| Google 伦敦区 RCA＋《SRE》二版（11-04/15） | 遥测、日志、BigQuery 会话 | 自动异常关联；事故复盘揭示「控制器读错线」 | 否 | 部分（事后才发现） | 否 | 说明了冲突的破坏力，未把优先级立为对象 |
| Anthropic Claude Tag＋Skills（11-12） | 数仓＋事件索引＋变更记录＋发布记录 | 语义层钉定义；分组比较验证归因；保留待验证线索 | 部分是（Skills 可改定义即改口径，未版本化） | 否 | 否 | 三种「活跃」定义并存时谁是权威由隐式语义层定，无反事实 |
| OpenAI Performance Factory（11-19） | 指标＋代码＋日志＋请求链＋CPU/内存账 | 独立 Codex 对抗复核，打回约 25%（二手） | 否 | 否 | 部分（检查反事实条件，但不切信源） | 抓到「内部已恢复 vs 前端仍失败」却未沉淀为跨源字段 |
| 阿里云 AgenticOps：LoongSuite/UModel/BRiSE（11 月） | Connector＋Fabric，多源统一建模 | UModel 统一语义、实体关系与动态拓扑 | 部分是（统一语义，非优先级规则） | 否 | 否（BRiSE 复现的是评测条件） | 消除「无关事件拼成因果链」，但冲突时的裁决权未显式 |
| 腾讯云 CloudQ＋AI 可观测（11-03） | 全景图谱＋监控/日志/调用链/变更/企业知识 | 推理前查图谱的事实源 RAG＋可追溯证据链 | 部分是（图谱为事实源，仅覆盖资源事实） | 否 | 部分（复测比改动前后） | 离「显式优先级」最近，但只覆盖资源关系，不覆盖互斥遥测 |
| 火山引擎 DevOps Agent（公测/11 月） | 云监控/APM/VMP/云监控四产品；RUM、CloudDetect **未接入** | Runbook 响应计划＋人工确认；Trace↔日志映射 | 否 | 部分（用量/写入量可见） | 否 | 工具最全，但用户侧那一路明确缺席且未声明为盲区 |
| Datadog Agent Observability 在线实验（11-17/20） | 评分器＋Trace＋Token/成本/工作流错误 | 版本对照、特性开关分流、Trace 巡检 | 否 | 部分（错误显示为成功时靠 Trace 发现） | 部分（A/B 换版本，非换信源） | 揭示「评分高而轨迹差」，但无跨源冲突指标 |

**判读**：把「接入—关联—治理—复核—判分」做满的方案已近全覆盖；把「互斥时采信哪一路、优先级谁定的、换一路是否翻案、败方证据是否留存」写进产出的，九列几乎全空。这不是某家缺功能，而是共同建模缺口：**行业把多源当作证据量的叠加，而不是需要仲裁的证词集合**。

## 四、技术挑战

**挑战一：200 只证明受理，不证明可用。** Mastering Observability 的信号核查说得很直接：服务端 Trace 说成功而用户浏览器说失败时，Trace 止于你的责任边界，用户体验不止于此；要记录 outcome 而非 status code，并从用户所处位置探测——区域降级对不出机房的探针不可见。**两者可以同时为真**，「差距」本身才是发现。ORCA-bench 论文把「把下游症状当根因」列为高频失败模式；ITBench-AA 上过度调查的模型也倾向把共现症状写成根因——这正是跨源未对位的直接症状。

**挑战二：沉默不等于没事，且沉默会被自信地叙述。** Collector 停导出的空面板与慢周二同形；伦敦区控制器整夜在读错的那根线；OTel 明确要求「观测这条路径时尽可能独立，免得故障把自己的健康信号一起藏掉」。把这种沉默交给 Agent，它会以完整条理报告平静——这不是幻觉，是输入缺失被自然语言流畅性掩盖。本期把它与 #262 数据龄期面区分：那里问证据有多旧，这里问**证据通道是否还在说话**。

**挑战三：同一事实的多种口径，且裁决者自己会过期。** Claude Tag 的三种「活跃」定义、两个时间戳、时区与基线选择，都说明冲突常在**定义层**而非数据层。语义层可作裁决者，但也会腐化：表弃用、定义改动、Skills 改了就改口径，与 #323 同源。若裁决规则无版本、无审批、无重定基线，所谓「统一口径」只是临时共识。

**挑战四：复核者可能只在自己那一路上自洽。** 若复核者与被复核者读同一路被污染的指标，冲突就消失，复核退化为同源自我确认（与 #321 收口权、#328 复演者独立性同一病灶）。R2Act/SWEOps 给出警示：模型找对服务达 91.4%–99.7%，修复方案通过规则仅 36.8%–60.3%；SWEOps 中**存在清掉告警却没通过故障检查的运行**——告警与故障判据两路互斥，只盯前者就会误宣布恢复。

**口径边界**：Google 87%（AAD）为厂商自测第三方基准口径；OpenAI 1700 起调查/600+ 定位/100 份抽检 70%/约 25% 打回/约 15 个直接合入 PR 为内部计数与媒体转述，不可相除；ORCA Fireworks 榜单 50.2% 是 avg@3 口径，论文 25.3%/10% 来自 19 微服务、50GB、6 天测试床，且作者明示非生产；ITBench-AA 56.2% 为 11-17 榜单快照；满帮「1 分钟/准确率>90%」、畅游「3.9 倍/3.1 倍」、MCP SDK「>99.5%/80%」为厂商自述或二手编译；`pass^k`、R2Act/SWEOps 来自论文测试床。厂商分母不同不可相减，上述数字只用于说明机制。

## 五、展望与建议

**新观点**：可观测性的下一站不是「再多接一路信号」，而是「多路信号打架时谁说了算」。Agent 看到的从来不是世界本身，而是被某一条信源裁剪过的证词；跨源冲突不是需要抹掉的噪声，而是最有价值的告警——它精确标记了口径分叉、证据通道损坏或责任边界的尽头。不声明优先级的系统，等于让模型在冲突处自由裁量；而在事故现场，自由裁量就是伪精确。

**本地知识再开采（第 205 期新角度）**：赵恒《如何构建 AI Native 的数据语义层：从 Data Agent 实践到可执行的 Semantic Runtime》此前多从「让数据查得到」一侧引用，本期首次改读为——**语义运行时的第一职责不是把数据取回来，而是把「同一事实的多种定义」显式化并钉住版本，成为模型之外唯一可被工程审查的跨源裁决者**；配刘凯宁「结论/证据/待确认」三分（把互斥证据放进待确认而非硬选一路）、何伟「生成与验证分离」（裁决规则不得由被裁决的 Agent 生成）、周昕毅「人进闭环不是把自己移出闭环」（裁决者要长在 Agent 够不到的地方）。

**建议一：第 250 字段族 `source.precedence.*` 与门禁。** 十字段：`conflict_id`／`fact_key`（争议事实）／`claims[]`（每路 `{source_type∈METRIC|LOG|TRACE|PROBE|CHANGE_EVENT|GRAPH|USER_REPORT|AGENT_SUMMARY, source_id, value, observed_at, scope}`）／`precedence_rule∈DECLARED|SEMANTIC_LAYER|MOST_RECENT|MAJORITY|TRUST_RANK|FIRST_FOUND|UNDECLARED`／`precedence_declared_by`（模型之外的权威）／`arbiter_ref`（语义层/图谱/人）／`reconciliation_check`（如三方对账或 200-vs-outcome）／`contrary_evidence_retained`（败方证据是否留存）／`counterfactual.source_swapped_root_cause_changed`／`verdict∈PRECEDENCE_ADJUDICATED|CONFLICT_MASKED|SILENT_SOURCE|UNVERIFIED`，缺省 `SOURCE_PRECEDENCE_UNVERIFIED`；承 #310~#328 叠加，`verdict≠PRECEDENCE_ADJUDICATED` 不计入「已独立复核」合规声明、不作自治升档。

**建议二：四条最小动作。** ①关键事实强制两路异源对账（用户侧 outcome 探针配服务端指标；管道侧跑三方对账公式），差距随决策落盘；②优先级规则写进语义层并版本化，定义变更视为口径变更须审批并重定基线（承 #323）；③冲突时保留败方证据并做换优先级反事实——根因翻转则转人工；④沉默三态化（真没有／未采到／采集中），合成探针走真实路径，未接入的用户侧信号声明为盲区。

**建议三：采购三问与评测。** 三问：能否导出「采信哪一路、否掉哪一路、依据什么规则」？优先级规则能否版本化并在模型外审查？用户探针失败而服务端 200 时会否改判？配对题（一路全绿 vs 加入用户侧失败探针）报 `cross_source_conflict_rate`、`precedence_switch_flip_rate`、`silent_source_false_calm_rate`。

**建议四：信通院补格。** 在六维模型之外补「跨源冲突可举证率」一格，与 #316~#328 已累计的十三格并列。
