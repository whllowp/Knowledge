# AI-SRE 技术洞察（第 321 期）

- 生成时间：2026-11-24 06:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：记忆边界面／共享记忆的租户与权限——scope 是约定，不是边界

## 题眼

2026-10-26，Mem0 披露了 CVE-2026-116575。漏洞不在模型，在拼接：`_build_session_scope()` 把调用方可控的 `user_id`、`agent_id`、`run_id` 用**未转义的 `&` 与 `=`** 拼成一个 session scope 键。调用方只要在一个受控标识里嵌入另一个 scope 分量，两组本来不同的租户元组就会生成**同一个键**；而 `add()` 与 `POST /memories` 用这个键读写最近消息，于是出现跨租户会话泄露、以及对方历史被驱逐或交错。修复版本是 Python SDK 2.0.18 / TypeScript SDK 3.1.6。

这不是孤例。2026-11-07 的 Mem0 文档写得很清楚：多参与者对话里，“哪条记忆属于谁”**由调用方在每次 `add()` 时用 `user_id`、`agent_id`、`run_id` 指定，Mem0 不会从对话里自动推断 scope**。换句话说，边界是调用方的责任，不是存储的强制。

2026-06-13 的 FragFuse 论文则从攻击侧给出了更难的形态：无特权用户利用长期记忆引入的**时间信道**，把越权查询拆成碎片、在多个会话里分别写入，再在后续会话里融合，从而绕过 Agent 的访问控制。

2026-09-21 的《A Survey on Long-Term Memory Security in LLM Agents》把这些现象收拢成一个框架：**可验证记忆治理（Verifiable Memory Governance）**，并列出五个原语——写入授权（WA，每条进入长期记忆的条目必须可归因到已认证来源并通过显式授权）、来源可见（PV，每条记忆带可查询、血缘完整的来源记录）、主体范围检索（PS，检索只返回调用主体有权看的条目）等。

再往外一层，2026-10-15 的 Google Advent of Agents 用银行场景说明风险不是抽象的：企业记忆库把每个用户的事实放在一个共享池里，提示注入可以让 Agent 去工具里取另一位客户的账户详情，也可以让财富管理 Agent 用零售银行的 scope 标签去读或污染那些记忆，还可以让美国 Agent 查询欧洲客户数据而违反 GDPR。**系统提示词拦不住这些，因为模型本身无法执行租户与地域边界。**

## 一、发展趋势

**第一，记忆从“功能”变成“数据层”。** 它有自己的写入路径、读取路径、保留策略、删除义务与审计需求，不能再当作“对话历史的一个缓存”。

**第二，scope 从“约定”变成“强制边界”。** 靠调用方传 `user_id` 不是隔离；靠元数据过滤也不是隔离——过滤条件写错一次就全泄漏。

**第三，治理原语开始成形。** 写入授权、来源可见、主体范围检索、可验证清除，正在从论文概念变成平台能力。

**第四，污染恢复需要度量。** 记忆被投毒后，“清理干净了吗”不能靠感觉；PurgeBench 提出用协议与指标衡量恢复的完整度。

**第五，跨会话身份解析成为双刃。** 把匿名浏览与登录后的身份合并，能减少“失忆”；合并错了就是泄露。

## 二、技术现状

**scope 靠拼接。** 分隔符未转义、标识可注入、大小写/编码不一致，都会让不同主体碰撞到同一个键。

**retrieval 不看权限。** 向量检索按相似度返回，权限往往在应用层再过滤；过滤遗漏或顺序错误就泄漏。

**写入不审来源。** 工具输出、网页内容、其他 Agent 的消息都可能被写成“用户事实”；写入授权缺失。

**删除不彻底。** 记忆条目、摘要、嵌入、缓存、备份多副本；删除 API 成功不等于不可再生（307 期同构）。

**污染会“洗白”。** 转述、摘要、压缩后的投毒条目，字节级清理抓不到；需要语义级检测与恢复度量。

**观测缺口。** 平台通常只报“记忆条数/命中率”，不报“跨主体检索次数”“写入来源分布”“清除验证结果”。

## 三、技术竞争力

| 方案 | 隔离强度 | 越权检测 | 可审计 | 实现成本 | 主要风险 |
|---|---|---|---|---|---|
| 调用方传 scope | 低 | 无 | 低 | 低 | 拼接/注入/遗漏 |
| 元数据过滤 | 低-中 | 弱 | 中 | 低 | 过滤 bug 全泄漏 |
| 应用层命名空间包装 | 中 | 中 | 中 | 中 | 存储层 bug 绕过 |
| 每租户独立库/索引 | 高 | 中 | 中 | 高 | 运维成本 |
| 主体范围检索（PS） | 高 | 高 | 高 | 高 | 需改造检索层 |
| 写入授权 + 来源可见 | 高 | 高 | 高 | 高 | 需改造写入层 |
| 污染恢复度量（PurgeBench） | 不适用 | 高 | 高 | 中 | 指标尚新 |

判读：买得到记忆库、向量库、scope 字段、过滤 API；买不到“这条记忆是谁写的、谁有权看、检索有没有跨主体、清除是否彻底、污染恢复了多少”。

本期反转：我们一直把记忆当“Agent 的笔记本”。实际上它是**影子数据存储**：写入由模型/工具决定，读取由相似度决定，权限靠调用方传参；一个分隔符 bug 就能让两个租户共用一个键。记忆的边界不是 scope 字段，是存储层的强制与检索层的主体绑定。

判词：「记忆库／向量库／scope 字段／元数据过滤／命名空间／删除 API／污染检测」全部可采购，「这条记忆是谁写的、谁有权看、检索有没有跨主体、清除是否彻底、污染恢复是否完整」不可采购。

## 四、技术挑战

**其一，键拼接的脆弱性。** 未转义分隔符、可注入标识、编码差异，都会造成主体碰撞。

**其二，检索与权限解耦。** 相似度先行、权限后置，中间任何遗漏都是泄漏。

**其三，写入来源不可信。** 工具输出、网页、其他 Agent 都能写“事实”；没有写入授权就没有可信记忆。

**其四，跨会话身份合并。** 合并阈值过松则泄露，过紧则失忆。

**其五，清除不可验证。** 多副本、摘要、嵌入、备份；删除成功不等于不可再生。

**其六，污染恢复无基准。** 直接、休眠、洗白、纠缠四类投毒，清理效果难以量化。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要跨主体检索告警、scope 碰撞检测、清除验证。
- 安全：需要写入授权、来源血缘、越权检测与审计。
- 业务属主：需要知道哪些记忆属于谁、谁能看、保留多久。
- Agent 团队：需要 principal-scoped retrieval 与污染恢复流程。
- 合规：需要删除/保留/地域边界的可验证证据。

**用户旅程（一次跨租户记忆泄漏）。**

1. 两个租户的标识里分别含 `&` 与 `=`，拼接后 session scope 相同。
2. 租户 A 的最近消息被租户 B 的会话读到；B 的历史被 A 覆盖。
3. 平台只报“记忆命中率正常”，没有跨主体检索指标。
4. 复盘发现是键拼接问题；修复后仍靠调用方传参。
5. 另一次，工具输出被写成“用户偏好”，后续会话按它执行。
6. 团队加来源字段，但没有写入授权与清除验证。

**实现方案（90 天）。**

- 第 1–2 周：scope 审计——键生成方式、分隔符转义、标识规范化；禁止字符串拼接，改用结构化键/哈希。
- 第 3–4 周：存储级隔离——高敏感租户独立库/索引；应用层命名空间包装作为第二道。
- 第 5–6 周：主体范围检索——检索接口强制传入主体，返回前做权限校验；记录跨主体拒绝次数。
- 第 7–8 周：写入授权——每条记忆带来源、写入者、授权依据；工具/网页内容标记为“不可信来源”。
- 第 9–10 周：清除验证——条目、摘要、嵌入、缓存、备份的删除回执；恢复后仍遵守删除。
- 第 11–12 周：污染恢复——按 PurgeBench 四类投毒做演练；度量恢复完整度。
- 第 13 周：演练与审计——注入 scope 碰撞、跨主体检索、投毒写入，验证边界与证据。

**验收标准。** 任一条记忆，能回答：谁写的、依据什么授权、谁有权看、检索是否跨主体、清除是否彻底、污染恢复多少。

**第 233 个市场空白（五项）**：scope 碰撞检测；principal-scoped retrieval；写入授权与来源标记；清除验证回执；污染恢复度量。

**`memory_scope.*`／`principal_binding.*` 第 200 次无人提字段族**：`memory_scope.scope_key`、`memory_scope.collision_check`、`principal_binding.write_authority`、`principal_binding.retrieval_principal`、`memory_scope.purge_evidence` 在记忆库、向量库与 Agent 框架之间没有统一语义；平台只报“记忆条数与命中率”。

**本地 173／173-kb 连续第 188 期成组启用**（余锦泽 03）：本地知识库把“记忆”与“权限”分开记账；本期把记忆落成主体绑定与清除证据。
