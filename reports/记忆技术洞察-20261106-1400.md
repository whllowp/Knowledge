# 记忆技术洞察（第 11 期）· 2026-11-06 14:00

**主线：记忆的时延账本——"记到了"不等于"到了"**

## 一、发展趋势

前十期分别处理了写入、删除、寻址、切分、成本、接入、空集、并发、闭环、时效，全部共享一个从未被写出的预设：**记忆在需要它的那一刻已经在那里**。本期拿掉这个预设。记忆不是"存在"，而是"到达"；到达需要时间，而这段时间在行业里被系统性地隐藏——它既不出现在榜单上，也不出现在报价单上。

三个趋势信号：

1. **"写在后台、读在热路径"已成行业共识**，代价无人认领。Delos 的生产手册把这条写成铁律：用户等待一次抽取调用，等于等待一件不改进当前答案的工作；AWS 官方博客同样写明抽取→整合→反思三步流水线是异步的，"**写入后要过一段时间才能检索到**"。共识是对的，但共识把成本从时延账户转移到了**新鲜度账户**，而后者没有账本。
2. **检索正在从"一次向量查询"变成"多轮工具往返"**。OpenViking 的 viking:// 文件系统要求 l0→l1→l2 逐层下钻，jipika/dsh-memory 只把"分片·关键词·数量·最新日期"的活地图注入提示词、再靠 grep+read 取条目，Hy-Memory 的 coding 场景要求按文件/函数/分支坐标定位。往返次数取代单次延迟，成为时延的第一性变量。
3. **评测合同里没有时间参数**。AML 二期把接口固定为 `Add`（写）与 `Search`（返回证据），下游 Answer/Eval 由平台统一——契约里没有任何时间预算。这意味着即使时延恶化十倍，分数也不动。这是本系列第三次遇到同构缺口：第 7 期"弃答被口径切除"、第 8 期"冲突无评测位"、本期"时延无计价位"。

## 二、技术现状

**第一份完整的时延剖面来自 MEMOIR（arXiv 2611.07631 附录 Table 11，1,905 条 LoCoMo QA）**，它把生命周期每一段都报了 P50/P95：

| 阶段 | P50 | P95 | LLM |
|---|---|---|---|
| 在线写入 | 6.8ms | 10.5ms | 无 |
| 检索 k=5 | 10.5ms | 未报 | 无 |
| 词法归因 TRACE | 6.7ms | 11.5ms | 无 |
| 反事实归因 TRACE-CF | 67.0ms | 84.5ms | 额外打分 |
| 离线巩固（每 8 次查询） | 2.85s | — | 异步 |
| 写时抽取基线（对照） | ~110ms | — | 必需 |

两组数字值得单独抽出来。其一，**110ms 对 6.8ms 是 16 倍**，差额全部是"想"（LLM 抽取）；也就是说零 LLM 写入在工程上完全可行，MEMOIR 的做法是把"想"推迟到事后，用检索结果反过来修正重要性。其二，**检索这一行只报了 P50，没有 P95**——最有长尾的阶段恰好没有尾部数据。这一点放到后文说。

**Mem0 侧给出了最刺眼的可见性数字**：写入异步化后，一条记忆"尚不可检索"的窗口在 p95 上为 **6.1–86.5 秒**（随抽取模型而变）。同期它的同步 `add()` 阻塞 **800ms–2.5s**，全上下文 p95 17.1s 对记忆层 1.44s。换言之，Mem0 用 6–87 秒的陈旧换掉了 15 秒的等待，这笔交易划算，但**没有人告诉用户前 87 秒里 agent 是聋的**。

**OpenViking 的 PR #7078 提供了"钱花在哪"的解剖**：一次 commit 写入从 42.565ms 降到 22.951ms（−51.9%），但其中 **30.093ms（71%）是 schema 编译**——`generate_all_models()` 占 62%，纯 Pydantic 类构造与模板渲染，与记忆内容零关系。同一份 PR 明确写着 `retrieval path: unchanged (157.797ms → 154.083ms, within noise)`。**写入优化了 52%，读路径一分未动，而读路径占总时延 79%。**

**MemArena（2608.02613）给出反证**：在 Spark GB10 端侧节点上，记忆检索的固定开销为 BM25-RAG 87ms、MemSearch 48ms、Memobase 7ms，"在大多数配置下不构成时延瓶颈"，推理才是；后端替换带来的精度增益约为扩大 reader 模型的三倍。它的附带结论同样重要：**所有被测配置在权限感知访问上全部失败**，Oracle 检索泄漏受限信息，其余后端又过度遮蔽。

## 三、技术竞争力

时延维度上的方案对比（"—"表示未公开；可见性延迟指写入完成到可检索的窗口）：

| 方案 | 写入模式 | 写入 p50 | 可见性延迟 | 检索 p50 | 报 P95 | 热路径 LLM 次数 | 时延档位 | 新鲜度可测 |
|---|---|---|---|---|---|---|---|---|
| Mem0 v2 | 异步/可同步 | 0.8–2.5s（同步） | 6.1–86.5s | 1.44s 端到端 | 是 | 1–3 | 无 | 部分（可查未写） |
| Zep / Graphiti | 异步图构建 | 未公开 | 未公开 | 90%↓ vs 全上下文 | 部分 | 1–2 | 无 | 双时态可推 |
| MEMOIR | 同步零 LLM | 6.8ms | ≈0（写即可见） | 10.5ms | 仅部分阶段 | 0 | 归因可选 | 结构上可测 |
| Scalaris | 双管线分离 | 未公开 | 未公开 | 4,145 token 级 | 否 | 1 | 无 | 弱 |
| OpenViking 0.5.x | 同步 commit | 22.9ms | ≈0 | 154–158ms | 否 | 1（抽取） | 无 | 文件可枚举 |
| TencentDB AM | 异步代理 | 未公开 | 未公开（Proxy 缓冲） | 未公开 | 否 | 1–2 | 无 | 面板规划中 |
| Hy-Memory | 分档 | lite 近零 | lite≈0 / ultra 滞后 | 未公开 | 否 | 0–2 | **lite/pro/ultra** | 弱 |
| AWS AgentCore | 异步三步 | 未公开 | "一段时间"，不可控 | 未公开 | 否 | 0（读侧禁 LLM） | 无 | 策略可观测 |
| jipika/dsh-memory | 同步写文件 | 磁盘级 | ≈0 | 多轮 grep | 否 | 0 | 无 | 目录即索引 |

分三档看：

- **第一档：把写入从热路径摘掉且公开了代价**。MEMOIR（6.8ms、写即可见）、OpenViking（22.9ms）、jipika（写文件）。共同点是写入不需要 LLM，因此**同步也不贵**——它们证明"写必须异步"是个伪命题，真正贵的是"写时必须想"。
- **第二档：异步化换成本，但延迟不可度量**。Mem0、AWS AgentCore、TencentDB。Mem0 是唯一把 6–87s 写进文档的，这一列的诚实度高于其绝对数值。
- **第三档：多轮往返型**。文件系统与工具总线形态天然把一次检索摊成 3 次以上 RPC，p95 由目录深度决定。MemArena 的端侧结论对它们有利（reader 更慢），云端小模型高频场景对它们不利。

一个必须说清的口径问题：**厂商的时延数字互不可比，因为时延是比值不是绝对值**。MemArena 说"检索 7–87ms 不是瓶颈"，前提是 reader 为 Qwen3-0.6B 且跑在 GB10 上；同一套后端放到云端 200ms 首 token 的链路上，87ms 就是 43%。**记忆开销应当以"占首 token 时延的比例"报告，而不是毫秒。**

## 四、技术挑战

**挑战一：仪式成本远大于有效载荷。** OpenViking 的 71% 不是孤例，它只是第一个被公开解剖的。schema 编译、提示词渲染、去重判断、类型路由——这些"为了让记忆成立而做的准备"在每次写入都要重跑。推论很反直觉：**换更小的抽取模型收益有限，先砍仪式**。PR 里 8 条 LRU 缓存就换回 52%，比任何模型替换都便宜。

**挑战二：可见性延迟对正确与错误是对称的。** 延迟生效的正确，等于延迟失效的错误。用户说"别再用那个旧地址"，若这条纠正落在 60 秒的后台队列里，agent 会在接下来若干轮继续用旧地址——这正是第 9 期"记忆陷阱"的时延版本：**闭环的危害窗口被异步化拉长了**。而纠错类写入占比极小，同步它的代价（~110ms）完全可付。行业一刀切异步，切掉的恰是最该同步的那 5%。

**挑战三：复核与热路径不可共存。** 第 9 期论证了复核侧必须存在，AWS 则明确"不要把 LLM 放在读取路径上，它增加延迟和新的故障点"。两条都对，冲突真实。唯一出路是**把复核整体搬到离线**——MEMOIR 的 offline sleep（每 8 次查询、2.85s、异步）是这一路线目前最干净的实现。这修正了第 9 期"装阀"的默认位置：阀不在读路径上，在夜里。

**挑战四：所有 benchmark 都在单租户空载下测。** Agent Memory Costs（2606.06448）测了"十个独立构建共享一个后端"的吞吐，相对单构建明显下降；论文给出的 per-session 构建成本跨度是 **~1ms 到 ~10s**。两条合起来意味着：SaaS 记忆的 p95 必然劣于自建，而评测从不复现这一点。比"不报 P95"更严重的是**不报共租**——一个慢连接器就能让整个部门停在旧事实上（Sentra 的观察）。

## 五、展望与建议

**判断一：时延将分裂为两个市场。** 端侧（reader 慢）记忆可以奢侈，云端高频小模型（reader 快）记忆必须极简。同一个后端无法同时服务两者，这意味着"通用记忆层"的叙事会在 2027 年破裂，退化为"按 reader 规模定制的两层产品"。

**判断二：新鲜度会成为采购条款，而不是技术指标。** Sentra 已给出可执行的三件套：**canary facts**（种入已知变更日期的假事实，按计划改动，看 agent 多久跟上）、**superseded-fact rate**（抽样回答中依赖已失效事实的比例）、**freshness lag**（改一个源值到 agent 答对新值的时间，按源报中位数与最慢值）。这三项成本极低，却能把"新鲜"从形容词变成 KPI。建议团队本周就种十条 canary。

**判断三：调度应按"失效代价"分层，而非按"内容类型"。** 现行动作是把 chat/working/coding 分流（Hy-Memory 的场景路由），这是按内容分；正确做法是按"这条记忆错了以后多久会被发现"分。四象限：

| | 可预测 | 不可预测 |
|---|---|---|
| **读** | 预取（零感知时延，代价是误取率与白付的 token） | 同步（唯一无法回避的同步点） |
| **写** | 批处理（会话边界提交，最省钱） | 同步（纠正/禁忌/删除，占比 <5%） |

这张表的价值在于它否定了"读同步/写异步"这条铁律：**读可以预取，写必须分级**。预取尤其被低估——用户开口前，会话上下文已能预测大半检索意图，MEMOIR 的 TRACE-UCB 甚至已在做"按使用计数探索"以防检索锁定。

**给落地团队的四条**：①先数同步点，再谈优化单点——删掉一个同步点是乘法收益；②把仪式成本单列监控，schema 编译与提示词渲染超 30% 就是架构债；③任何异步写入都必须给出可见性延迟的上界，并对纠错类写入开同步通道；④时延按"占首 token 比例"报告，同时报 P95 与共租降级值。

**下一期优先**：AML 二期出榜口径复核（11 月中，仍为最高优先）；预取命中率首个实测；共租降级的公开数据；`as_of` 参考时间在主流 SDK 的落地情况；可观测面板是否纳入 freshness lag。
