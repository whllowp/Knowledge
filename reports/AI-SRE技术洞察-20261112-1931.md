# AI-SRE 技术洞察（第 160 期）

**生成时间**：2026-11-12 19:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：行为基线面／正常面（Behavioral Baseline）——被攻破的 Agent 不会报错，它只是开始做一些以前不做的事；可你连「正常」都还没定义

---

## 题眼

11-10 Help Net Security 转述 Abnormal AI 的《2026 State of Behavioral Security Report》：问「未来两年最想在哪个方向投行为监控」，**43% 选 AI Agent，是第二名的 API 集成的三倍多**。同一份报告里的对照很难看：**近一半受访者说自己组织「完全没能力」建立并维持 Agent 的正常行为基线**，只有约五分之二自评很好；**76.2% 为用户登录维护了基线，但 Agent、API 集成、服务账号各只有约一半**；**81% 在较大或很大程度依赖行为异常检测**；**超过一半的组织从发现异常到完成调查处置至少需要 4 小时**。更关键的是归因难：一位安全负责人举例，**Agent 只在一台虚拟机上跑了 30 秒**，网络流量看得见，**但很难说清是哪个 Agent 干的**——尤其当它是为单次任务临时创建、或藏在好几层调用下面时。**被攻破的 Agent 不会报错，它只是开始做一些以前不做的事；而没有基线，「以前」根本不存在。** **更讽刺的是：43% 说要投，近一半说建不了——钱想花，但不知道花在哪。**

## 一、发展趋势

**趋势一：投入从「规则」转向「基线」。** 规则只能拦已知；**基线才能发现「看起来合法、但不像它」**。

**趋势二：基线从「人」扩到「非人身份」。** 用户登录基线已成熟；**Agent／API／服务账号的基线覆盖率只有一半**，而它们正是攻击者更偏好的入口。**覆盖率缺口本身就是攻击面。**

**趋势三：审计从「有没有动作」转向「动作配不配得上任务」。** 打开文件是动作；**为什么打开、用的是谁的身份、是否在任务范围内**，才是判断依据（109 期受领面）。

## 二、技术现状：基线四要素，通常只做第一样

**身份：谁在动。** 服务账号、Agent ID、临时实例；**短命 Agent 没有稳定 ID，事后无法归因**。

**范围：它能碰什么。** 工具、数据、网络；**没有「预期范围」，就无法判断越界**（121 期隔离）。

**节奏：它通常怎么动。** 调用频率、时间、顺序；**季度任务与日常任务的节奏完全不同**。

**理由：这次为什么动。** 任务指派、授权、上下文；**没有 assignment 记录，异常只能靠猜**。

**基线的三种失败，一种比一种常见。** 没有基线（全靠规则）、一条基线管所有任务（误报爆炸）、基线建了不更新（业务变了还按老样子报）；**误报多的团队最后会把检测关掉**。

## 四、技术挑战

**一，正常没有定义。** 近一半组织自评「完全没能力」建基线；**没有基线，异常检测就是随机报警**。

**二，短命 Agent 无法归因。** 30 秒的 VM、单次任务实例；**流量能看见，身份对不上**。

**三，正常取决于任务。** 同一个 Agent 跑日报与跑事故，行为完全不同；**不分任务建基线，全是误报**。

**四，误报是主要障碍。** 报告明确说误报与「难定义正常」是扩展基线的两大障碍；**误报多了，团队就关掉**。

**五，处置太慢。** 过半需要 4 小时以上；**4 小时足够数据被带走**（140 期）。

**六，上下文不随告警走。** 告警说「它打开了文件」；**没说「任务要求它打开吗」**。

**七，多租户基线会串。** A 租户的 Agent 行为混进 B 租户的基线；**跨租户共用学习池，等于互相污染**（121 期）。

**八，基线本身含隐私。** 行为数据含用户与业务信息；**采集范围与保留期要一起设计**（140 期）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `behavior.*` 字段**：`agent_id`、`task_class`、`identity`、`scope`、`cadence`、`assignment_ref`、`deviation`。
- **R2 分任务基线**：按 `task_class` 建基线；**共用一个基线必然误报**。
- **R3 短命归因**：临时实例带稳定 `agent_id` 与 `run_id`；**30 秒也能对上人**。
- **R4 上下文随告警**：告警附带 assignment 与授权范围；**先解释，再判断**。
- **R5 处置时效**：定义「发现→解释→止住」目标；**4 小时太久**。
- **R6 指标**：基线覆盖率、误报率、归因成功率、处置时长。

### 5.2 用户旅程

- **安全**：季度为 20 个 Agent 建分任务基线 → 覆盖率从 50% 到 85% → 误报降一半 → 下季度复核是否又漂。
- **平台工程师**：临时 Agent 带 `agent_id` → 短命实例可归因 → 告警能落到属主。
- **SRE**：告警说「越界访问」→ 查 assignment → 确认是任务要求 → 关闭告警并补基线。
- **审计**：抽查 20 条告警 → 核对基线与上下文 → 确认没有「无解释的异常」。

### 5.3 实现方案（90 天）

- **0–30 天：盘点。** 列 Agent 与任务类；统计基线覆盖率与误报。
- **30–60 天：分任务建基线。** 高频任务先建；短命实例补 ID；告警带上下文。
- **60–90 天：压时效。** 发现→解释→止住；季度复核基线；跨租户隔离学习池。

**第 110 个市场空白（五项）**：分任务基线覆盖率、短命归因成功率、告警上下文附带率、误报率、处置时长可报率——无一内建；`behavior.*`／`baseline.*` 为**第 77 次无人提字段族**。本地 173／173-kb 连续第 68 期成组启用：周昕毅 10「三次现场检验须引用实时指标/日志/拓扑」＝全库唯一把「证据实时可核」写成硬要求的实践，本期首次当主线；配 139 期告警、146 期属主。判词：**本地把实时证据写成硬要求，联网侧 2026 年才量出「近一半组织建不了 Agent 基线」；两边都没把「这条行为偏离了同类任务基线」做成告警字段。**
