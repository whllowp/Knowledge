# SRE Agent 领域技术洞察 · 第 234 期

**主题：修复采纳面／建议到执行的"最后一公里"（Remediation Adoption Gap）——修复方案生成得越来越准，但"生成了、批准了、却没落地、落地了又没留住"这一段，是全行业没有分母、没有字段、没有值守的暗区**

> 期号说明：`date` 01:03→0100 档；最新本期 232（22:00 例行承诺面）、并行实例 233（22:31 代理支付面），本期顺延第 234 期；市场空白第 165 项；字段族第 131 次无人提；主线第一百九十七条全新立面；本地连续第 120 期成组启用。
> 时间范围：限定 2026 年，重点最近 30 天（10-18～11-17）。

## 题眼

2026 年 11 月的 KubeCon North America 上，所有事故响应 Agent 都学会了同一件事："动手前先问人"。New Relic 11-11 发布的 Autopilot Kubernetes Agent 跑 90 多个诊断探测器、生成"可直接运行的修复代码"，但明确写"由工程师自己审阅并执行"；Dynatrace 的 SRE Agent 全面可用，回滚和 PR"等待批准"；Virtana 把客户分成"建议→批准的修复→让 Agent 解决特定类型事故"三段推进。当"会提正确修复"变成行业标配，真正决定 MTTR 的就不是诊断准确率，而是那条几乎无人度量的漏斗：**提出（proposed）→审阅（reviewed）→批准（approved）→执行（applied）→留住（persisted）**。把"人类注意力是自治上限"讲透的是第 10 期审批经济学，把"批准之后修没修好"讲透的是第 226 期疗效归属；本期只问中间那一段——**修复方案到底有没有被采纳、采纳了有没有被执行、执行了有没有被回退**。这一段在六家平台的产品页上，是彻底的空白。

## 一、发展趋势

**趋势一：行业收敛到"只查不改"的默认姿势，采纳率在结构上被压到接近零，却没人上报这个数字。** The Pragmatic Engineer 10-27 的深访给出一线共识："先按只查不改上线，任何写操作都走人；等连续几个月在同一类事故上被验证正确，再考虑交出缓解这一步——交接对象应是已有的变更流程，不是它自己的 shell。"这意味着 Agent 的"修复"从交付物降级为建议书。Incident-Arena（09-30，20 个人工构建事故、3000 次试验）披露：即便在智能体完整实现参考修复的 1638 个回合里，也只有 59% 通过双门——**41% 的"正确修复"仍然失败**；但该基准量的是"执行后是否越界、是否留住"，并没有量"有多少正确修复压根没被采纳"。前一段（采纳）仍是盲区。

**趋势二：批准正在从单一按钮裂变为多段控制面，采纳路径被拉长、被切碎。** Google 10-22 的 Project Chrysalis 立了四道防线（Model Armor／Cloud KMS／Binary Authorization／OPA Policy Controller）与 Dual-Custody HITL——永久性变更需 SRE 明确签字；Red Hat 11-09 GA 的 OpenShift MCP gateway 按凭据过滤 Agent 可达工具、可按人批准任何改变系统的动作；Azure SRE Agent 有 Review／Autonomous 两模式、工具可 allow/ask/deny；AWS DevOps Agent 对缓解提议"人审阅后决定是否应用"。控制面越厚，从"提议"到"生效"经过的闸门越多，采纳漏斗每一段的损耗就越需要被单独计量——而现状是没有任何一家给出分段漏斗。

**趋势三：采纳权明确归属人类并写进标准，但"人批了≠执行了"这件事被制度性地忽略。** 中国信通院《云上 Agent 基准度量模型》建议"辅助诊断→审批执行→限定自治"分阶段落地并保留人工接管兜底；阿里云 STAROps 把执行分"自动执行／人工确认／强制拦截"，且明确"人工确认不能突破原有权限边界""工具调用成功本身不足以说明问题解决"；腾讯云 CloudQ 走"受控执行"。标准把"人批准"写成闸门，却没有写成一条需要计时、需要留痕、需要对账的数据流。

## 二、技术现状

把采纳链路拆开看，生产系统实际具备的能力与缺口错位明显：

- **提案生成**：已成熟。STAROps 先形成处置计划、明确操作对象／动作／影响范围；Dynatrace 返回可能原因、证据、受影响服务与用户、建议以及"排除了什么"；新 Relic 生成上下文相关修复代码。
- **审阅与批准**：普遍具备但形态不一。Dynatrace 的修复"等待批准"；Uma Shankar 的 SRE Agent 把每个动作做成 Slack 审批、绑定到计划摘要（plan digest）；Azure Review 模式下写动作须管理员批准。
- **执行**：刻意收窄。多家默认"由工程师自己运行"（New Relic），或只放行高置信、低风险动作（最多 3 次尝试、自动回滚、熔断器）。
- **执行后留存与回执**：最薄。Incident-Arena 的安全门专门检查"修复能否挺过服务重启或触发器重放"、是否在许可范围内、受保护数据与护栏是否完好——结果 329 个回合栽在安全检查上，其中 145 次把维护窗口挪到不安全时段、38 次把连接池抬过上限。这类"执行了但没留住"的失败，此前被归入 #226 疗效归属；本期指出它同时是**采纳质量问题**：采纳时审的是意图，执行时改了取值，留存时又漂了一层。

一句话概括现状：**行业把预算全押在"提案"这一格，却让"采纳"这一格连分母都没有。**

## 四、技术挑战

1. **分母缺失导致收益无法归因。** 没有 proposed_count，就没有 adoption_rate；行业讲"MTTR 降 50%"（携程披露），但降幅里有多少来自真正落地的修复、多少来自"只查不改"减少的无效动作，无法拆分。这是第 185 期度量主权在采纳段的具体显现。

2. **批准与执行之间的静默断链。** 人在 Slack 点了批准，Agent 报告"已审批"，但执行器因权限、幂等键、目标资源变更而静默 no-op——系统里留下一条"已批准"的绿记录，没有任何"未执行"信号。它与第 232 期例行承诺的"缺席二义性"同构，只是对象是变更而非例程。

3. **采纳时的意图与执行时的取值漂移。** Incident-Arena 的维护窗口挪位、连接池抬顶说明：审的是"调大连接池"的意图，执行的是"抬过数据库上限"的取值；规则是部落知识，没有编码成机器可校验的形态。更深的挑战是"谁改的"——人改、Agent 改、策略引擎改，改后责任归属与 #231 问责面直接耦合。

4. **未采纳样本不回流，形成自我确认闭环。** 被拒绝、被搁置、被回退的修复方案，几乎不进 golden 集、不进评测、不进下一次检索上下文；于是 Agent 反复提出同一类"看起来正确但从未被采纳"的方案，并用"提案被生成"当成功。这是第 230 期知识保鲜在提案侧的镜像。

5. **控制面越厚，采纳路径越难端到端追踪。** 四道防线、MCP 网关、RBAC、双签字各自留痕，但没有一个 adoption_id 把它们串成一条链；跨系统对账时，"审批记录在某系统、执行记录在另一系统、回退记录在第三系统"，举证成本指数上升。

## 五、展望与建议

- **立 `fix.adoption.*` 五字段并进 OTel GenAI 提案**：`proposed_count`／`approved_count`／`applied_count`／`persisted_count` 按 adoption_id 配对，派生 `adoption_rate`（applied/proposed）；缺省 `ADOPTION_UNVERIFIED`，只有审批记录一律不算采纳。
- **补两个时序字段**：`approval_to_apply_latency`（批→执行时延）与 `silent_defer_rate`（已批准但未执行／仅被查看）；两者进值守 SLO，由外部变更系统回执驱动，而非 Agent 自报。
- **执行-留存双校验**：执行体必须绑定 plan digest（借鉴 Uma Shankar 的逐动作绑定），回写"实际取值 vs 提议取值"；重启与触发器重放后复检，未挺过即记 `revert_after_apply_rate`，并入 #226 疗效归属验收。
- **未采纳原因枚举与回流**：`not_reviewed`／`rejected_risk`／`rejected_permission`／`approved_not_applied`／`applied_then_reverted`；每类进 golden 集反例与检索上下文，杜绝自我确认。
- **交接给已有变更流程而非 Agent 自己的 shell**（Pragmatic Engineer）：采纳的最终执行点必须是企业变更系统，Agent 只提供端到端可追踪的 adoption_id；信通院六维可增补"修复采纳可举证率"一格。
- **基准补题**：Incident-Arena／SRE-Marathon 增加"正确修复未被采纳""批准后静默未执行"两类题，把采纳漏斗变成可比较的分数，而非脚注。

**新观点小结**：2026 年的瓶颈已经从"能不能想出正确修复"移到"正确修复有没有走完最后一公里"。把"采纳"立为一等运维对象，就是把 MTTR 治理从提案端延伸到执行端——**生成可以被采购，采纳只能被举证**。
