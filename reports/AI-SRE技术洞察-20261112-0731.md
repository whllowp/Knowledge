# AI-SRE 技术洞察（第 142 期）

**生成时间**：2026-11-12 07:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：数据契约面／schema 漂移面（Data Contract Drift）——列名一改，Agent 的答案悄悄错；数据契约是 Agent 的输入接口

---

## 题眼

01-26 Bytebase 的一篇工程稿把一个「人人都见过」的事故拆得很细：后端把 `orders.amt` 改名成 `total_amount`，应用测试全过、发布成功；几小时后同步任务按旧列名找不到字段，**要么失败，要么新建一列、把旧列当删除——历史数据变成 NULL，而且不报错**。dbt 模型还在 `SELECT amt`，直接 `invalid identifier`；等到财务打开看板，**昨天的收入显示为 0**。作者的归因是三句话：**没有可见性**（改名的后端不知道下游依赖）、**没有护栏**（没人拦住破坏性变更）、**schema 是隐式契约**（列名就是 API，却没人写下来、没人执行）。到了 Agent 时代，这三句话全部放大：**Agent 一次会话发 6–11 次查询、每次重新决定 join 与过滤**（25 期），**一个改名可以让一整类回答悄悄错**。**最危险的不是报错，是 NULL：NULL 会被 Agent 读成「零」，零会被解释成「业务归零」。**

## 一、发展趋势

**趋势一：数据契约从「治理文档」变成「运行时接口」。** 过去契约写在 wiki 里；现在它必须被 Agent 在查询前校验——**否则 Agent 会把「NULL」当「零」，把「分」当「元」**。**契约至少要管三样：结构（列/类型）、语义（单位/口径/分母）、新鲜度（as_of）。**

**趋势二：schema 变更开始被当成一等事件。** Bytebase 这类工具在变更成功后发 **webhook（库、环境、项目、表、列、执行人、时间戳）**，触发下游同步、dbt 校验、数据质量检查与看板复核；**变更本身成为触发器，而不是等下一次定时任务**。

**趋势三：语义漂移比结构漂移更难防。** 列名没变、类型没变，但**单位从分变元、口径从 GMV 变净额**；结构检查全绿，Agent 的答案已经错了（25 期：同一问题三个消费者三个数）。

## 二、技术现状：结构有工具，语义没字段

**结构层：rename/type/drop 可检测。** schema diff、迁移评审、变更 webhook；**但检测到之后，Agent 的查询不会自动失效**。

**语义层：单位/口径/枚举靠人记。** 没有 `unit`、`currency`、`denominator` 字段；**Agent 只能从列名猜**（25 期：`revenue` 三种写法）。

**新鲜度层：迟到数据看起来像真实下跌。** 数据没到，看板显示 0；**Agent 会把它解释成「业务归零」**（134 期：旧文档；116 期：记录缺失）。

**契约层：没有运行时校验。** 契约写在目录里，查询时不校验；**Agent 生成的 SQL 直接打到库上**。

**答案怎么被验证：只能对账。** 结构测试测不出「单位错」；语义错只能靠与源系统抽样对账——**而对账要先知道「该对哪条」**。

**三种改名，三种坑。** 直接 rename（下游全断）、加 alias 视图（旧列还在但语义变了）、双写过渡（两列不一致）——**Agent 分不清「旧列」和「兼容列」**。

**Agent 的查询模板是隐藏依赖。** 它把「列名＋join 路径」写进提示或代码；**schema 变了，模板不会自己失效**，除非有事件通知。

## 四、技术挑战

**一，静默失败优先。** rename 后同步新建列、旧列当删除——**NULL 不报错，比报错更危险**。

**二，语义无字段。** 单位、币种、口径、分母没有机器可读定义；**Agent 只能猜，猜错不报错**。

**三，Agent 放大查询面。** 一次会话 6–11 条 SQL，每条都重新决定 join/过滤；**一个改名污染一整类回答**。

**四，变更事件与 Agent 不同步。** webhook 触发了 dbt，**没有触发 Agent 的查询模板失效**。

**五，对账成本高。** 要知道「答案错了」，得拿源系统对账；**没有抽样对账，就只能等用户发现**。

**六，契约版本与运行时脱节。** 契约 v3，Agent 还在用 v1 的列名；**没有 `contract_hash` 绑定查询**。

**七，跨库/跨租户 schema 分叉。** 同一逻辑表在 A 库叫 `total_amount`、B 库叫 `amt`；**跨库 join 的 Agent 两边都错**（121 期隔离在数据层的变体）。

**八，契约维护成本。** 每张表都要写结构/语义/owner；**没人维护的契约，比没有契约更危险**（因为它给人虚假的安全感）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `data.*` 字段**：`table`、`contract_hash`、`schema_version`、`unit`、`currency`、`freshness`、`null_semantics`。
- **R2 契约哈希**：结构＋语义一起 hash；查询前校验，不匹配则拒绝并提示。
- **R3 变更事件**：schema 变更发事件，**同时失效 Agent 查询模板与缓存**。
- **R4 语义字段**：单位/币种/口径/分母进契约；Agent 生成 SQL 时强制带单位换算。
- **R5 对账**：抽 5% 查询与源系统对账；差异超阈值告警。
- **R6 新鲜度**：数据迟到标记 `stale`，**不把「没数据」当「零」**。
- **R7 契约 owner**：每张表有 owner 与复核日期；到期未复核自动降级为「不可信源」。

### 5.2 用户旅程

- **数据工程师**：改名 → 变更事件 → 自动失效受影响 Agent 模板 → 通知 owner。
- **Agent**：查询前校验 `contract_hash` → 版本匹配 → 带单位换算执行 → 结果标注 `as_of` 与 `unit` → 举证时可复算。
- **SRE**：看板收入为 0 → 查契约 → 发现单位从分变元 → 修正换算并补对账 → 把该查询加入常驻对账集。
- **审计**：抽查 20 条查询 → 核对契约版本与单位 → 确认没有静默错值；契约过期仍被使用的，记一次违规。

### 5.3 实现方案（90 天）

- **0–30 天：盘契约。** 给 top 20 表定结构＋语义契约；算 hash。
- **30–60 天：接事件。** schema webhook → 失效模板；查询前校验；单位换算。
- **60–90 天：对账。** 5% 抽样对账；stale 标记；季度契约复核；契约变更进发布门禁。

**第 94 个市场空白（五项）**：契约哈希可导出率、语义字段覆盖率、查询前校验率、变更事件到达率、对账覆盖率——无一内建；`data.*`／`contract.*` 为**第 62 次无人提字段族**。本地 173／173-kb 连续第 56 期成组启用：赵恒 25「语义层不是 Agent 的另一个 prompt，而是每一条都用同一份定义」＝全库唯一把「口径统一」做成执行层的实践，本期首次当主线；配余锦泽 03「SQL 执行前做本体约束校验」、朱革 15「统一版本边界」。判词：**本地把口径统一写进语义层，联网侧 2026 年才把「schema 是隐式契约」写成事故复盘；两边都没把「这条查询用的契约版本」做成运行时字段。**
