## 一、发展趋势：可观测性从 agent 层下沉到记忆内容层

2026 把可观测性从调用链推到记忆层，但主流只做了"运维半层"：你能看 Add 日志和延迟面板，看不到库内容。本周信号表明产品侧开始补"内容半层"——OpenViking v0.5.4.1（11-11）把 MCP 工具挂成可读 Markdown 节点、检索可限定子树、只读/写分道，本质是"像查文件一样查记忆"；ReMe（agentscope-ai/ReMe）内置 `reme status`/`traverse`/`graph_snapshot` 与"运维与恢复"诊断；dsh-memory-evolve 给项目日志打 `[git main]` 分支标签。但 AML Cycle 2（**11-19 预期出榜**）协议仍只暴露 Add/Search，无"列出我记忆"的契约。判断：记忆可观测性正从"系统级"走向"内容级"，但标准尚未出现。

## 二、技术现状：三档可见性，主流停在第一档

**结构可见**（Cognee 节点边+溯源、Zep 时间戳关系、Letta 可编辑内存块）：能看到"有什么"。**血缘可见**（Hy-Memory history.db+版本链、dsh 项目日志+git 分支、TencentDB 迁移工具）：能看到"怎么变来"。**失败可见**（Memograph 访问模式异常检测、memdebug 旁观账本）：能看到"哪里坏"。问题是：八家产品以 Add/Search 为唯一接口，无 introspection 端点——能检索不能审计、看延迟不看内容。更深一层：Hy-Memory 删除后 raw L1、history.db、cache.db 全部留存，说明**血缘必须包含"没被删掉的东西"**，而现有 schema 只记"删了"。

## 四、技术挑战：写入可见、内容不可见

① 无标准内省 schema（AML 契约无"列出记忆"接口，与第 35 期"面板即合同"互补——面板管健康、内省管内容）；② **可观测性 ≠ 评测**（深化第 42 期：评测给答案打分，内省回答"库里现在有什么、为什么"，AML 有评测契约无状态查看契约）；③ 血缘部分（删除留残，第 51 期来源三态须补 `deletion_residue`）；④ 记忆时间旅行只在 agent 层（Orchid）不在 store 层；⑤ 隐私/可见张力（看记忆=看 PII）；⑥ **倒挂第 43 次**（内省最完整在调试工具 Memograph/Orchid/AgentRx 与论文，产品侧近乎零）；**口径缺口第 44 次**（AML 无内容可见维度，"库里存了什么"无处表达）。

## 五、需求分解 · 用户旅程 · 实现方案

**需求**：R1 内省 API（list/inspect 任意记忆元数据）；R2 血缘（origin+编辑史+谁/何时+`deletion_residue`）；R3 召回解释（matched_query/score/path/reason）；R4 drift/health 监视；R5 时间旅行回放。

**用户旅程（D0→D7）**：开发者怀疑坏答案 → 查"为何召回 X"（retrieval_explanation）→ 看 lineage（含 deletion_residue）→ 发现重复/陈旧/越权 → 提交修正 → 重审计通过转 adopted。

**实现方案**：新增 `memory_inspect` 端点 + `visibility.*`（level: hidden/listed/auditable）、`lineage.*`（origin/created_by/created_at/last_accessed/access_count/supersedes/superseded_by/deletion_residue）、`retrieval_explanation`（matched_query/score/path/reason）三字段族；以 OpenViking 式 `viking://memory/{id}` 为通用内省接口；Memograph 式访问模式基线做 drift 检测；检索响应强制附带 explanation。
