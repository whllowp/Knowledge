# AI-SRE 技术洞察 · 第 76 期

**中止面（叫停面）——"停"不是一次事件，是一次协商；被停掉的是执行，不是副作用**

> 时间：2026-11-04 22:00（UTC+8）｜覆盖窗口：2026 年 10 月上旬至 11 月 4 日，含 2026 全年背景

---

## 一、发展趋势

三段时间轴终于补齐。第 75 期写"禁"（冻结，事前不让开始），第 52 期写"撤"（恢复，事后把已发生的退回去），中间那一段一直空着：**已经开始、还没结束、现在要它停**。11 月的行业动态把这段空白照得很亮，照出来的却不是能力不足，而是**语义缺失**——"停止"在 2026 年是一词三义。

监管侧先把话说明白了。欧盟 AI Act 第 14(4)(e) 要求高风险系统的人类监督者能"通过停止按钮或类似程序中断系统"（Annex III 自 2027-12-02 适用）；美国 2026-07-23 由 Lieu 与 Moran 提出的《AI Kill Switch Act》，Sec. 2220F(b)(1)(A)(i) 直接指向推理过程本身，要求覆盖主体保留"节流、暂停、关闭"的技术能力，不服从按日计罚最高 2000 万美元，且企业申诉不中止命令执行。加州 9-18 的第 N-9-26 号行政令，把建议提交期限定在 11-16——十二天后。

产业侧给的却是另一件事。Google Cloud Deploy 的 abandon release 文档写得毫不含糊：发布被废弃后，"任何由该发布创建的、正在进行或排队中的 rollout 仍会继续完成——它们不会被取消"。Google 实现的"停"是**禁新增**（deny-new），不是**止在途**（abort-in-flight）。这个区别在监管文本里没有，在产品宣传里也没有，只在行为里有。

所以趋势不是"停止能力在增强"，而是**"停止"正在被迫拆成三个谓词**：禁新增、止在途、撤授权。谁先把这三个词分开，谁才能回答"你到底能不能停"。行业里已有一句更锋利的判断：一个没人按过的急停开关，是假设，不是控制。

## 二、技术现状

**（1）可中止性在提交时就已决定。** OpenAI Responses API 的 cancel 端点只有一句前提：只有以 `background: true` 创建的响应才能被取消；前台请求根本没有 cancel 接口。这意味着 11 月 3 日凌晨你想叫停一个跑飞的调查任务时，能不能停，取决于三个月前写这段代码的人有没有加那个参数。**停止不是运行时开关，是接口选型**——这是本期最不舒服的一条。

**（2）取消是传输层的副作用，不是应用层的事件。** MCP 2026-07-28 修订把这条写进了规范：Streamable HTTP 下"关闭 SSE 响应流就是取消信号，服务端必须把客户端断开视为该请求被取消，不需要也不期望发送 notifications/cancelled"。只有 stdio 才发通知；服务端主动取消现在仅允许一个用途——拆订阅流。规范同时保留 best-effort：取消可能在处理完成后才到，接收方"可以忽略"（请求未知、已完成、不可取消）。

后果是运维性的：**取消不产生消息**。不产生消息，就不进 trace、不进审计、不进变更记录。唯一能证明"停过"的东西，被设计成不可记录。规范里那句"发送方应忽略此后到达的响应"，翻译过来是：结果丢掉，副作用留下。

**（3）协作式取消：SDK 明确不强制终止。** MCP Ruby SDK 文档把话挑明："取消是协作式的，SDK 不会强制终止工具代码"，靠工具自己在循环里轮询 `cancelled?` 退出。这把"已取消"降级成一个意图声明。A2A 更谨慎：`CancelTask` 只是一次请求，终态任务返回 `TaskNotCancelableError`(-32002)，且协议语义里没有"回退已完成副作用"的位置——那被明确划给调用方自己的业务域。

**（4）停止的作用域追不上执行的作用域。** 10-09 Anthropic 给 Claude Managed Agents 上了动态工作流：agent 自己写一个程序，服务端在后台当作 workflow run 跑。三周后的文档里出现了一句代价：**"如果有 workflow run 处于打开状态，interrupt 不会结束其中任何一个"**；而且"正在运行的 run 可以让会话保持 running，所以那个 status_idle 事件可能不会来"。新能力先到、控制语义后到，中间这段就是无人区。

**（5）停止与完成在遥测上同值。** 同一份文档：interrupt 之后，空闲事件的 `stop_reason.type` 仍是 `end_turn`，"与自然完成的轮次同值"。于是一个被叫停的任务，在指标里长得和一个干完活的任务一模一样。这不只是缺个字段，是**事件语义缺一个枚举值**——"任务完成率"这个 SLI 从定义上就把被叫停算成了完成。

**（6）"停"留下的不是状态，是一处不一致。** Argo Rollouts 的 abort 停推进、把流量切回 stable，但不改 `.spec.template`。结果是 Rollout 长期 Degraded：stable 在服务，live 不等于 desired；而 Argo CD 的 selfHeal 不会修它，因为 Git 里本来就是那样。**abort 是运行时事实，期望态里没有它的位置**——第 54 期"期望态 vs 实际态"的二元对立，在这里需要第三格。同一份社区文档还给了一句最诚实的话："abort 能把流量移回去，但移不回数据。"

**（7）形式化答案已有，但停在论文里。** arXiv 2607.14166（Stop Means Stop，v3 8-08）用无模型差分探针测了六个主流开源框架：**没有一家满足它自己文档承诺的屏障语义**。核心是"兄弟泄漏"——审批门只挂起触发它的那条分支，并行兄弟分支照样执行副作用；215/1200 次真实模型运行泄漏了被门控的副作用，条件泄漏率 1.00；另加重放双执行、取消孤儿、超时僵尸三类。修复件 SOUNDGATE 把闸门外置到环境层，强制四条不变量：hold-until-decided、reject-cancels、dedup-on-replay、**fence-on-cancel**，Verus/TLA+ 机检，约 1ms/次写入、12k 次/秒。

arXiv 2610.01160（10-01）给了另一半：在 vLLM 里把"请求持有资源"与"执行版本持有发布权"拆开，旧版本被撤的是**发布权**而不是进程，剩余执行被限界，已完成前缀认证后交给后继版本继承，改版到后继首 token 中位降 17.1%。

两句合起来是一条运维原则：**先撤发布权，再谈杀进程**。进程你未必拥有（跨组织、SaaS、子 agent、别人的集群），但发布权总落在某个你够得着的地方。

## 三、技术竞争力

| 方案 | 停止原语 | 生效范围 | 在途工作如何处理 | 停止后状态 | 副作用是否撤销 |
|---|---|---|---|---|---|
| Google Cloud Deploy | abandon release | 发布 | **继续跑完，不取消** | 版本永久停用、不可回滚到 | 不处理 |
| Argo Rollouts | abort | 一次 Rollout | 流量回 stable，不等 AnalysisRun | 长期 Degraded（desired≠live） | **明示不回退数据** |
| Kubernetes | SIGTERM + grace（默认 30s） | Pod | preStop + 排空，超时 SIGKILL(137) | 容器消失 | 进程内未刷盘即丢 |
| Anthropic Managed Agents | user.interrupt | 会话 / turn | 工具调用"可能更慢生效"；**不结束 workflow run** | stop_reason=end_turn | 子线程待办工具调用以 error 关闭 |
| OpenAI Responses | POST /cancel | 单个响应 | 仅 `background:true` 可停 | status=cancelled、output 空 | 已发生的工具调用不撤 |
| MCP 2026-07-28 | 关 SSE 流 / cancelled 通知 | 单请求 | best-effort，可被忽略 | 无响应返回 | 仅"释放资源"无保证 |
| A2A | CancelTask | Task | 请求式，终态报 -32002 | canceled（终态不可再转） | 明示由调用方自行回退 |
| 火山引擎 | CancelTask / StopInvocation / 批量终止 | 任务 / 实例 | 未开始的变更不再进行 | 不可恢复，需重新发起 | 已变更实例不自动回滚 |
| SOUNDGATE（研究） | fence-on-cancel | 全部出网副作用 | 被围栏，无法逃逸 | 拒绝即取消 | **唯一覆盖副作用层** |

判读三条：

**一，"我们有一键停止"在采购里几乎无信息量。** 上表真正分歧的是"在途工作"和"副作用是否撤销"两列，而这两列没有一家填满。Cloud Deploy 选了禁新增，Argo 选了止在途但留不一致，OpenAI 选了只有异步可停，MCP 选了停但不记录。四种选择各有道理，但都不是"停住"。

**二，能力按层分工。** 云厂商卖策略层停止（发布/实例维度，可 RBAC、可审计，但不进业务副作用）；模型厂商卖会话层停止（细、快，作用域只到 turn）；协议层卖传输层停止（最通用、最不可观测）；研究原型卖副作用层停止（唯一填上最后一格，代价是所有出网流量必须收进同一个闸门）。

**三，国内侧停在控制台维度。** 火山引擎文档最实在：Computer Use Agent 有独立 CancelTask，云助手有 StopInvocation，批量任务"终止后未开始变更的实例不再进行，且不能恢复"。语义清楚，但清楚的是"不再开始"，不是"撤销已写"。阿里与腾讯截至检索未见同粒度的公开停止语义（此为本期检索结论，非产品能力判断）。

## 四、技术挑战

**其一，停止覆盖率的分子分母不同单位。** cancel_rate = 取消请求数/总请求数，泄漏率 = 已执行副作用/应阻止副作用。一个被取消的 run 可能已经发出三次写。**cancel_rate 很高，可能一次都没停住**——这是第 75 期"冻结计量单位失配"在中止维度的重演，也是本期与前一期互为镜像的地方。

**其二，停止的证据必须来自被停方之外。** 静默不等于停止，可能是排队、限流，或者对方压根没收到信号。承接第 52 期的"外部证人"，停止回执至少四字段：作用域（停到第几层）、对象（哪个执行版本）、生效时刻、残留清单。

**其三，停机策略无人定义。** 合规清单里有一句最容易被跳过的话：要说明"在途任务如何被保持、回滚或安全完成"。三种处置代价完全不同，却没有框架提供这个选择点——它散落在每个团队的 runbook 里，且多数写着"人工确认"。

**其四，停止后的重启是第二次授权缺口。** 13 起公开事故语料佐证了重放与取消失败；恢复时"检查点记了工具调用但没记拒绝结果"，被拒的调用会再执行一遍。停完再启，等于把闸门重开一次而无人复核。

**其五，第三十个市场空白**：停止传播深度、孤儿率、停止-完成混淆率、停止后不一致持续时长——四项无一厂商内建，对比表"副作用是否撤销"整列只有研究原型填得上。

## 五、展望与建议

1. **把"停止"拆成三个字段进工具描述**：`cancel.mode = deny_new | abort_inflight | revoke_authority`，并强制声明作用域。智能体读得懂"停止"，但读不懂"停止哪一类"。
2. **停止前先撤授权。** 短时凭证加 fence-on-cancel 是唯一能跨组织生效的停止；第 55 期讲"凭证不出模型"，这里补一句：**凭证过期是最靠谱的停止按钮**。
3. **给遥测补一个枚举值。** 让 `cancelled` 与 `end_turn` 分开，是让"任务完成率"恢复可解释的最低成本改造；顺带把中断做成 span（`cancel.*` 四字段：发起方/作用域/目标/残留数）。
4. **停止演练进季度日历。** 抽一个真在跑的 workflow run，要求 60 秒内停住并交回残留清单；停不住的组件，按不可用处理。
5. **采购四问**：停的是禁新增还是在途？在途副作用谁负责回滚？停止事件可导出吗？停止后重启是否重新授权？

一句话收束：**能停住的从来不是按钮，是授权；按钮只是通知。**
