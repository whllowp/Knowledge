# AI-SRE 技术洞察（第 308 期）

- 生成时间：2026-11-20 17:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-21 至 2026-11-20）
- 本期主题：容量面／预留与超卖——预留卖的是“容量存在”，不是“现在能跑”

## 题眼

2026-10-31，InfoQ 报道 AWS CEO Andy Jassy 的说法：AWS 的大宗承诺容量**到 2027 年基本售罄**，2028 年也已分配掉一大块，同时仍在为 On-Demand、EC2 与 Bedrock 预留余量。报道同时点出 AWS 卖容量保证的两种形态：On-Demand Capacity Reservations，以及按固定窗口预订的 Capacity Blocks for ML。

但 2026-11-15 韩国 ITWorld 的评论给了一句冷水：**“容量紧张”与“容量售罄”不是同一句话**。面向 AI 训练的大块 GPU 配额确实难拿，但把“售罄”当成“拿不到任何容量”，是把市场信号读成了物理事实。

这正是 SRE 在 2026 年要处理的容量语义：**预留（reservation）承诺的是“这份容量存在”，不是“这份容量此刻可调度、可跑满、可隔离”**。而超卖（overcommit）承诺的是平均值，不是峰值。

## 一、发展趋势

**第一，容量从“按需购买”变成“按合同预订”。** 云厂商把稀缺性产品化：容量预留、ML 容量块、承诺用量折扣。SRE 的输入从“需要多少核”变成“要订多少、订多久、订在哪个可用区”。

**第二，预留与超卖开始被同一份文档放在一起讲。** Azure 的容量预留文档明确：预留不限制 VM 部署数量，超出预留量的部分叫**超分配（over-allocation）**；这些额外 VM 不受容量可用性 SLA 覆盖，且仍受配额与云厂商实际库存约束。换句话说，预留给你的是“额度”，超出的部分回到“尽力而为”。

**第三，K8s 侧的超卖被讲清楚了。** 2026-11-06 的一篇资源模型长文给出关键推论：**集群真实利用率上限由 requests 决定，而不是 limits**——所以会出现“节点 CPU 监控只有 20%，却再也调度不进 Pod”。requests 是调度承诺，limits 是运行时约束；CPU 可压缩（超限被 throttle），内存不可压缩（超限 OOMKill）。

**第四，GPU 共享把超卖推到显存层。** 2026 年的系统论文在讨论“带超卖的容量隔离”：同一张卡上高优先级推理与低优先级任务共存，靠显存重分配与批大小调整保隔离；一旦超卖比例超过隔离能力，优先级承诺就失效。

**第五，市场开始区分“预留”“保证”“余量”三个词。** 厂商留 On-Demand 余量、卖多年预留、按窗口卖容量块——三者对应不同的失败模式，但合同与仪表里经常只写一个“capacity”。

## 二、技术现状

**云容量预留。** 预留绑定机型、区域、可用区与时间窗；预留内跳过配额检查，预留外走正常配额与库存。预留可以改数量，但改机型/位置通常要新建再迁移——迁移窗口本身就是风险。

**K8s requests/limits。** requests 决定调度与 QoS 权重；limits 决定 cgroup 上限。把两者设成一样，等于既没有弹性又容易被杀；只设 limits 不设 requests，调度器按 0 算，节点被压爆。超卖内存是事故高发区：节点 allocatable 被 requests 占满，实际内存却可能被所有 Pod 峰值叠加打穿。

**显式超卖开关。** 有的平台提供“让调度器忽略 requests/limits”的总开关（如 Hydrolix 的 `overcommit`），文档自己标注“不推荐用于生产”——它解决的是“小集群演示时 Pod Pending”，代价是把调度承诺清零。

**GPU 层。** MIG、时间片、显存池化、批处理共享，各自提供不同粒度的隔离；超卖比一高，尾延迟首先崩，而监控通常只看平均利用率。

**Agent 负载。** 推理请求是峰值驱动、突发、可重试的；按平均 QPS 做容量规划，在 Agent 扇出（一次任务触发几十次工具调用）时会系统性低估。

## 三、技术竞争力

| 方案 | 承诺的是什么 | 超卖边界 | 故障形态 | 可观测性 | 适用场景 |
|---|---|---|---|---|---|
| 云容量预留（按 AZ/机型） | 容量存在 | 超出部分无 SLA | 预留内也调度失败（库存/配额） | 中（实例视图） | 稳定基线负载 |
| ML 容量块（固定窗口） | 窗口内可用 | 窗口外无保证 | 窗口错配、迁移成本 | 中 | 训练/批推理 |
| K8s requests | 可调度 | 由 requests 总和决定 | Pending、节点利用率虚低 | 高 | 通用工作负载 |
| K8s limits | 运行时上限 | 内存不可压缩 | OOMKill、CPU throttle | 高 | 有峰值保护需求 |
| 显式 overcommit 开关 | 无 | 全部 | 节点级雪崩 | 低 | 演示/测试 |
| GPU 共享/MIG | 隔离粒度 | 显存/算力比例 | 尾延迟、优先级反转 | 低 | 多租推理 |
| 优先级+抢占 | 高优先级可运行 | 低优先级被驱逐 | 驱逐风暴、状态丢失 | 中 | 混合关键性 |

判读：没有“买够容量”这回事；只有“买哪种承诺、接受哪种失败”。预留保证的是存在性，requests 保证的是可调度性，隔离机制保证的是性能不被邻居吃掉——三者不能互相替代，而账单上通常只体现第一个。

本期反转：我们习惯用“预留了多少核/多少卡”回答“容量够不够”。实际容量是**三本账**：合同上的预留量、调度器认的保证量、运行时真正能跑满的量。三本账对不上时，事故现场看到的是“明明预留了却起不来”，而复盘看到的往往只是“扩容不及时”。

判词：「容量预留／ML 容量块／K8s 调度器／VPA／优先级抢占／GPU 共享／云监控」全部可采购，「这份预留此刻能不能真的起实例、超卖后谁在吃谁的余量、峰值时哪个租户先被挤掉、预留与保证量差多少、下一次窗口切换会不会断」不可采购。

## 四、技术挑战

**其一，预留≠可用。** 预留绑定机型与位置，库存、配额、底层故障都可能让预留内实例起不来；SLA 只覆盖“容量可用性”，不覆盖“你的部署成功”。

**其二，超卖不可观测。** 超卖比、被挤掉的请求、邻居造成的尾延迟，很少进入统一仪表；平均利用率掩盖峰值冲突。

**其三，requests 与真实用量脱节。** 照模板抄 requests 的集群，调度层被占满而物理层空闲；反过来，requests 设太小会在峰值时把节点打穿。

**其四，Agent 负载的峰值不可预测。** 扇出、重试、长上下文让单请求成本方差极大；按平均数规划必然在尾部翻车。

**其五，窗口与迁移。** 容量块按窗口卖，预留改机型要迁移；窗口切换、迁移窗口与业务高峰叠加时，容量“在账上”但“不在路径上”。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要容量三本账（预留量、调度保证量、实测可跑量）与差异告警。
- 财务/采购：需要把预留、按需、超卖的实际成本与风险对齐，而不是只看单价。
- 业务属主：需要知道自己的峰值由谁兜底、被挤掉时的降级策略。
- 安全/合规：需要知道超卖是否跨越租户隔离边界。

**用户旅程（一次“预留了却起不来”的事故）。**

1. 团队为推理服务预留 20 台 GPU 实例，合同写明可用区与机型。
2. 大促前把副本数从 20 提到 28；超出的 8 台走“超分配”，无 SLA。
3. 大促当天可用区库存紧张，8 台起不来；预留的 20 台里又有 2 台因底层故障重建失败。
4. 调度器显示节点 CPU 只有 30%，但新 Pod 一直 Pending——requests 已被占满。
5. 值班按“扩容”处理，继续加副本；驱逐与重试把尾延迟推高，SLO 破裂。
6. 复盘发现：预留量、调度保证量、实际可跑量三本账从未对齐；超卖部分没有降级预案。

**实现方案（90 天）。**

- 第 1–2 周：建容量三本账——合同预留量、调度器保证量（requests 总和）、实测可跑量（压测/历史峰值）；按服务标注差异。
- 第 3–4 周：把超卖显式化——每个池子记录超卖比、SLA 覆盖范围、被挤掉的请求数；禁止“隐式超卖”（文档里不写、配置里开着）。
- 第 5–6 周：requests/limits 治理——按 P95 设 requests、按 P99+缓冲设内存 limits；CPU limits 放宽或不设；用 VPA recommend 但不自动应用。
- 第 7–8 周：峰值模型——把 Agent 扇出、重试、长上下文纳入容量模型；按峰值而非均值做预留，并保留按需溢出层。
- 第 9–10 周：降级预案——超卖部分无 SLA 时，明确先降哪个功能、哪个租户、哪类请求；优先级与抢占规则写入 runbook。
- 第 11–12 周：窗口与迁移演练——容量块切换、预留改机型迁移各演练一次，记录“账上有、路径上没有”的时段。
- 第 13 周：验收——任一次容量事件能回答：预留多少、保证多少、实际可跑多少、超卖多少、谁被挤掉、降级是否按预案执行。

**验收标准。** 每个关键服务都有三本账与超卖比；峰值事件能定位“卡在库存、配额、调度还是隔离”；降级预案经过演练。

**第 220 个市场空白（五项）**：容量三本账；超卖比与 SLA 覆盖登记；峰值驱动的预留模型；超卖降级预案；窗口切换/迁移演练记录。

**`reservation.*`／`overcommit.*` 第 187 次无人提字段族**：`capacity.reserved`、`capacity.schedulable`、`capacity.actual_runnable`、`overcommit.ratio`、`overcommit.sla_covered`、`capacity.evicted_requests` 在云账单、K8s 调度器与 GPU 共享层之间没有统一语义；账单只报“预留了多少”。

**本地 173／173-kb 连续第 175 期成组启用**（刘凯宁 05）：本地知识库把“容量”拆成合同、调度、隔离三层记账；本期把它落成三本账与超卖比。
