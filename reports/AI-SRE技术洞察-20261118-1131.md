# AI-SRE 技术洞察（第 280 期）

**生成时间**：2026-11-18 11:31（Asia/Shanghai）
**观察窗口**：2026-09 至 2026-11-18
**本期主题**：冻结期面／变更冻结与例外——冻结了人，没冻结 Agent

## 题眼

2026-11-02 一篇标题很直白的文章给出今年冻结期最尴尬的事实：**“变更冻结两周后开始，你的 Agent 没收到通知。”** 冻结邮件写的是“11 月 15 日至 1 月 5 日，禁止非关键发布，例外需总监审批”；但这套语言假设变更来自人、走 PR、留审批记录。Agent 的变更不从这个口子进：它改的是模型别名、提示词版本、自动扩缩容镜像、SaaS 里的工作流配置，以及它自己“自愈”时写回的参数。

同一周，两个工具文档把“冻结”的技术边界写得很清楚：Featureflip（2026-11-15）的冻结**只挡 flag 写操作**，读、求值、SDK 流量不受影响；Infrawrench 的冻结**只挡 destructive 动作**（删除资源、删索引、清缓存、删微调模型），重启与快照照常；两者都提供 break-the-glass 单次放行并审计。也就是说，“冻结”在实现上是**一组动作类型的白名单**，不是“系统不变”。

还有一条更硬的经验来自十六根柱子（2026-10-08）：峰值冻结如果没有**应急放行路径**，“你不是降低了风险，而是移除了在最重要的一天修东西的能力”。而 2026-09-18 的一档意大利播客用讽刺把结局说透了：冻结执行两周后，“只有纸面上被遵守——所有发布都作为紧急修复通过；策略随后更新，加了例外章节，而那一节是全文被读得最多的部分”。

## 一、发展趋势

1. **冻结从“流程约定”变成“服务端强制”**。Featureflip 与 Infrawrench 都把冻结做成 API 层拒绝（423 Locked），并覆盖 Web、API、SDK 与 MCP/AI 聊天工具；这解决了“人忘了”的问题，但没解决“动作类型没被枚举”的问题。

2. **Agent 侧开始有自己的冻结策略**。Reflex（2026）给 AI 编码 Agent 配 change window：窗口内，**非只读且触碰生产**的命令要么询问人要么拒绝；支持周窗口与日期区间（如 2026-12-20 至 2027-01-03 全拒），可先 shadow 再 enforce，且只能收紧。这是把冻结从“平台侧挡写”延伸到“动作侧挡执行”。

3. **冻结期本身在制造漂移**。冻结只停“有审批的变更”，停不下证书到期、密钥轮换、模型别名重指、云厂商默认值变更、自动扩缩容拉起旧镜像、供应商侧滚动升级。于是冻结期结束时，系统与冻结开始时已不是同一套东西——只是没人越过那条线。

4. **解冻日成为第二个风险高峰**。冻结期积压的变更在同一小时放量，依赖顺序被打乱；意大利播客里“所有发布都按紧急修复走”的结局，和解冻日的放量是同一枚硬币的两面。

## 二、技术现状

**第一层：冻结的定义是“部分覆盖”。** 平台挡 flag 写、挡删除；但改 prompt 模板、改路由权重、改超时、改自动扩缩容镜像、改 SaaS 工作流不在“写 flag”里。团队以为冻结了“变更”，实际上冻结的是“变更的一个子集”。

**第二层：Agent 的变更没有审批面。** Agent 的写回常常落在配置中心或平台 API 上，日志里是“服务账号改了 X”，不是“谁批了 X”。冻结期问“这周有没有变更”，答案取决于你查的是哪张表。

**第三层：冻结期的漂移无人巡检。** 证书剩余天数、密钥轮换、别名指向、镜像 digest、依赖版本，这些量在冻结期继续变；多数团队没有“冻结期漂移巡检”这一项。

**第四层：例外的成本被低估。** 例外申请、审批、执行、回看四步，在冻结期被压缩成“口头同意＋直接执行”；审计时只能证明“有人同意过”，不能证明“改动范围就是批准范围”。

## 三、技术竞争力

| 方案／机制 | 冻结对象 | 覆盖 Agent 变更 | 例外路径 | 审计粒度 | 漂移检测 | 运维适配度 |
|---|---|---|---|---|---|---|
| 硬冻结（全锁流水线） | 发布流水线 | 否 | 无（或手工改） | 弱 | 无 | 低（无法救火） |
| 平台侧 flag 冻结（Featureflip） | flag 写 | 部分 | break-glass | 单次变更 | 无 | 高 |
| 平台侧 destructive 冻结（Infrawrench） | 删除类动作 | 部分 | 管理员覆盖 | 动作级 | 无 | 高 |
| Agent 侧窗口（Reflex） | 非只读生产命令 | **是** | 询问人 | 命令级 | 无 | 中（需部署） |
| 白名单例外表 | 例外条目 | 否 | 人工 | 工单级 | 无 | 中 |
| 变更冻结＋解冻节流 | 时间窗 | 否 | 有 | 工单级 | 无 | 中 |
| 冻结期漂移巡检（自建） | 证书/镜像/别名 | 是 | — | 指标级 | **是** | 高（建议必建） |
| 供应商侧冻结 | 不可控 | 否 | 不可见 | 无 | 依赖状态页 | 低 |
| 只读演练（冻结期） | 应急路径 | 部分 | 演练 | 演练报告 | 无 | 高 |

**判读**：平台卖“冻结执行”，Agent 工具卖“动作拦截”，但没有一家卖“**冻结期系统实际变了什么**”——因为那需要把变更定义扩展到配置、别名、镜像与供应商，而这些东西不在任何单一平台的管辖内。

**本期反转**：我们把冻结当成“让系统保持不变”，于是把风险预算全押在“没人动”上。实际上冻结期系统仍在漂移，只是漂移不经过审批；冻结降低的是“人类变更风险”，抬高的是“不可变更风险＋解冻放量风险”。**冻结不是把变更归零，是把变更挪到看不见的地方。**

**判词**：「发布冻结／flag 冻结／destructive 拦截／Agent 动作窗口／例外工单／解冻节流」全部可采购，「冻结期内这个系统实际发生了哪些变化、哪些是批准的例外、哪些是漂移、解冻时按什么顺序放」不可采购。

## 四、技术挑战

1. **变更定义不一致**：平台、Agent、供应商三套“变更”定义，冻结范围取交集还是并集，没人声明。
2. **Agent 身份与审批脱节**：Agent 用服务账号写配置，审批记录挂在人身上，冻结期审计对不上。
3. **漂移不可见**：证书、密钥、别名、镜像 digest 没有统一的“冻结期基线”。
4. **例外膨胀**：例外一旦比正常变更容易，冻结就退化成“给每次变更盖个章”。
5. **解冻节流**：积压变更的依赖顺序、冲突检测、分批放量，缺少标准做法。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 冻结清单：把“变更”定义为发布＋配置＋提示词＋模型别名＋扩缩容镜像＋供应商滚动升级，逐项标注是否在冻结范围内。
- D2 Agent 侧窗口：非只读且触生产的 Agent 动作，在冻结窗口内询问或拒绝；先 shadow 观察，再 enforce。
- D3 漂移巡检：冻结期每日比对证书剩余天数、密钥轮换、别名指向、镜像 digest、依赖版本与冻结基线。
- D4 例外台账：每次 break-glass 记录批准人、时长、目标、改动前后值，并与动作日志对账。
- D5 解冻节流：按依赖顺序分批放行，禁止同一小时全量；冲突检测在放行前跑。
- D6 只读演练：冻结期内演练一次应急放行路径，确认“能救火”而不是“只能等”。

**用户旅程（一次冻结期内的静默漂移）**

① 11-15 冻结生效，团队把发布流水线锁死（D1 只覆盖发布）；② 12-02 自动扩缩容拉起旧镜像，缺一个 11 月的补丁——没有发布，所以没有审批（D1 缺口）；③ 12-10 Agent 自愈把超时参数写回配置中心，日志显示服务账号，没人认领（D2 缺失）；④ 12-20 证书续期任务被冻结期收紧的防火墙规则挡住，剩余 7 天才发现（D3 缺失）；⑤ 1-5 解冻，47 个变更同一小时上线，两个互相覆盖（D5 缺失）；⑥ 复盘问“冻结期到底改了什么”，只能拉出发布记录（D4/D6 缺失）。

**90 天实现方案**

- **第 1–30 天**：定义冻结清单与基线（D1）；给 Agent 动作加窗口策略的 shadow 模式（D2）；建立冻结期漂移日报（D3）。
- **第 31–60 天**：例外台账与动作日志对账（D4）；解冻节流的依赖排序与冲突检测（D5）；做一次只读演练（D6）。
- **第 61–90 天**：把漂移日报接入值班；复盘一次真实冻结期，回答“哪些变化没经过审批”；把 Agent 窗口从 shadow 切到 enforce。

**第 201 个市场空白（五项）**：① 跨平台“变更”统一定义；② Agent 动作与审批记录的关联 ID；③ 冻结期漂移基线标准；④ 例外台账与动作日志对账方法；⑤ 解冻节流的依赖排序规范。

**`freeze.*`／`change_window.*` 第 168 次无人提字段族**：平台文档谈“冻结会挡住写”，不谈“冻结期系统实际变了什么、哪些变化不在冻结定义里”。

**本地 173／173-kb 连续第 156 期成组启用（朱革 15：冻结期要能回答“这周到底改了什么”）**：本地原型在冻结期每日生成漂移日报（证书/镜像/别名/配置），并把 Agent 动作与例外台账按 change_id 关联；解冻前跑一次依赖排序演练。
