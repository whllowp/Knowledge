# AI-SRE 技术洞察（第 230 期）

**生成时间**：2026-11-16 21:00（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：知识保鲜面／知识漂移与腐化（Knowledge Freshness / Runbook & Memory Decay）——「跑得起来的 Agent」不等于「读着最新知识的 Agent」：runbook 在腐化、记忆会过期、知识图谱会失真，而六家把知识当不动产，没人把「这条知识还成不成立」做成可上报字段

---

## 题眼

2026 年 11 月，三件事撞到一起。Anthropic 在 11-06 公开 Agent 记忆实验：旧模型在《宝可梦 红》里存了 413 份记忆文件、拿到 1 个徽章，新模型只存 9 份、拿到 4 个——差别不在记得多少，而在**「一份存错的笔记会被注入到往后每一轮会话」**，于是一次 Mt. Moon 里写错的「宝可中心在洞东侧」让 Agent 三次掉下悬崖，直到后台的「做梦（dreaming）」流程对照原始会话把它改过来。同一周，Sourcegraph 与 InMobi 的 SRE 实践几乎异口同声：**runbook 从写完那一刻就开始烂，AI 把代码改动速度提高十倍，也把知识腐化速度提高十倍**——「我们翻开的 runbook 几乎总是滞后于代码」。而 Google 开源的 AQuA 干脆把答案写进架构：诊断时用**部署那一刻冻结的源码快照**去比对失败会话，而不是信今天这份可能已经过期的文档。

三条线指向同一个被忽略的一等对象：**Agent 的可靠性，取决于它读到的知识有多新鲜**。可观测性解决「发生了什么」，因果闭合解决「是不是蒙对的」，本期解决一个更底层的问题——**「你据以判断的那条知识，是不是已经过期了」**。

## 一、发展趋势

**趋势一：从「有知识库」转向「知识有保鲜期」。** 2026 年的 AIOps 平台普遍把知识图谱、runbook 库、记忆系统当卖点，但新的工程共识是：知识不是一次写入的不动产，而是会随时间衰减的资产。Google SRE Workbook 早写明「playbook 细节的过时速度与生产环境变化速度相同」，每日发布意味着 playbook 可能每天都在过期；InMobi 干脆把 runbook 做成与代码同仓库的「一等公民」，每次 PR 都由 Agent 判断「这次改动是否大到需要同步改 runbook」。

**趋势二：从「读时信任」转向「写时同步 + 读时校验」双环。** Sourcegraph 把方案拆成两层：**写时（write-time）**在代码变更的 PR 里同步更新文档、开自动 PR；**读时（read-time）**在事故中按告警错误文本跨所有服务仓库/脚本检索，把「文档 + 可解析引用」交给工程师核对。两者不互相替代——写时环减少腐化，读时环在写时环还没赶上时兜底。

**趋势三：从「记忆越多越好」转向「记忆可被证伪、可被回收」。** Anthropic 的实验给出反直觉结论：少而精的 9 份文件胜过 413 份；后台「做梦」流程的作用是**拿原始会话核对笔记、纠正错条目、重建索引**。记忆被明确定义成「会被写入、被检索、会过期、会错误传播的持久化存储」，而非上下文的延伸。

## 二、技术现状：三种腐化，一条盲区

**Runbook 腐化。** 斯坦福 2022 年对 top1000 GitHub 项目的研究发现 19.2% 的文档含至少一处对代码元素的过时引用、28.9% 的项目至少有份过时文档；SRE 从业者自述「近一半的排查步骤得自己现推、或去找写它的人」。腐化的隐蔽之处在于：告警还挂着这条 runbook、链接还打得开，于是「可达」被误当成「有效」。

**记忆腐化。** Anthropic 把记忆分四层——会话记录、Agent 自写笔记、由笔记构建的 wiki、每次会话注入的一小块上下文——其中**注入层 token 最少、看起来最无害，但一条错的会被带到每一次会话**。多 Agent 共用一份记忆表还会互相覆盖：一次并购简报实验里，多个 Agent 写共享表只留下 41/57 个事实，改成「每份合约一页」后恢复到 57/57。

**知识图谱腐化。** GraphRAG / 本体驱动观测把调用链建成三元组图谱（Netflix E2EGraph 用 RDF/OWL/SHACL/SPARQL 与 QuipuDB，关联 13 类信号支撑 AutoRCA）。但 Netflix 自己强调：**图提供结构化上下文，不自动证明因果**；而满帮/AgentCore、腾讯 CloudQ 的实践都要求「知识由业务团队持续抓取清洗、粒度细化到接口级」——图谱的新鲜度取决于背后那条人工维护流水线，而非图结构本身。

**共同盲区**：三者都没有把「最后验证时间 / 依据的代码版本 / 是否仍可解析」做成可上报、可告警的字段。腐化是默认状态，发现它靠的仍是「3 点在事故现场翻文档的人」。

## 四、技术挑战

1. **腐化不可见**：没有「最后验证时间 + 依据版本 + 负责人」三元组，runbook「看起来权威」直到它在事故里失效，验证成本被推迟到最贵的时刻。
2. **错误记忆的自我确认**：一条写错的笔记被注入每一轮，后续推理都建立在它之上；「做梦」能修，但需要原始会话可追溯、且修正本身有算力与延迟成本。
3. **写时同步的归因盲区**：PR 改了脚本名，Agent 要判断「这是否大到要改 runbook」——判断错了要么漏更、要么文档噪音泛滥，InMobi 承认这是「几十年经验都没解决」的难题。
4. **图谱不等于真相**：GraphRAG 能给出结构化的漂亮因果图，但图节点指向的服务可能已经下线、依赖可能已改；网飞明说图不自动证明因果，Agent 仍须拿实时遥测验证。
5. **指标盲区**：现有评测测「答对没有」，不测「依据的知识过没过期」。Cloud-OpsBench 显示最强 Agent 的联合根因准确率 0.68–0.76，而证据闭合率仅 0.15–0.38；暂无任何基准测「知识鲜度」。

## 五、展望与建议

**提出 `knowledge.freshness.*` 字段族（本期第 163 个市场空白、第 129 次无人提字段族）**，建议五项：`last_verified_at`（最后验证时间）、`evidence_source_revision`（依据的数据/代码/文档版本）、`reference_resolvable_rate`（脚本/链接/服务引用仍可解析比例）、`staleness_score`（基于被描述系统变更频率的腐化评分）、`correction_reverted_count`（错误记忆被纠正/回收次数）。配套建议：

- **把 runbook 与代码同仓、同 PR 更新**（InMobi 模式），PR 模板加「Runbooks affected」一栏；
- **读时 grounding 兜底**：事故中按错误文本跨仓库检索，返回「文档 + 可解析引用」，工程师验引用而非验结论；
- **记忆分层 + 注入层最小化**：注入上下文保持小而精（Claude Code 用 200 行/25KB 索引上限），并保留原始会话供「dreaming」式离线核对；
- **知识设保鲜期与责任人**：无 owner、超过两个季度未验证、或晚于其描述代码的最后变更，自动降权并告警；
- **依据版本冻结**：关键诊断参照部署时源码快照（AQuA 模式），而非活文档；
- **把鲜度纳入评测**：基准加「依据过期知识」陷阱题，信通院六维补「知识保鲜可举证率」格。

**本期新观点（深化）**：往期 #213「因果闭合」问「命中是不是蒙的」，#208「遥测供给」问「看到的证据被谁裁过」，本期再往下挖一层——**「证据背后的知识本身有没有过期」**。三者构成递进链：供给决定看见什么、闭合决定推理是否扎实、鲜度决定推理的地基是否还是新的。**一个因果链完美闭合、证据引用可解析的诊断，仍可能建立在三个月前就被改掉的 runbook 上——闭环完整而地基已朽，这是比「蒙对」更危险的失效。**
