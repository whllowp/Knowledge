## 题眼

11-12 Help Net Security 的访谈问了一个很尖的问题：**如果一个 AI 生成的补丁关掉了一个 CWE、却悄悄打开了另一个，这算谁的？是合并它的开发者、开启功能的 AppSec，还是 GitHub？** GitHub 产品 VP 的回答是三分：**GitHub 对「建议的修复质量」负责，客户决定「合并什么」**——和任何代码变更一样。他给的工程细节更值得记：Agentic Autofix **会自动重跑检测引擎与项目测试**，确保修复有效且不引入破坏；相比「只给建议」的旧版，**安全积压修复率高 4 倍**；2025 年 Autofix 省下 **150 万小时**安全审阅时间。但同一段话里也藏着新瓶颈：**如果 Agent 一夜开 2,000 个 PR，瓶颈就从「修」变成「审」**。**AI 把「写」变成了流水线，却没把「署名」变成流水线——Git 里仍然只有一个人的名字。** **责任有四段：生成、提交、批准、启用；四段都该有人，但现在只有第三段有记录。**

## 一、发展趋势

**趋势一：作者从「一个人」变成「一条链」。** 生成者（模型＋harness＋工具）、提交者（committer）、批准者（reviewer）、责任方（厂商/客户）——**四个角色，Git 只记一个**。**只记一个，复盘就只能问一个人。**

**趋势二：审阅成为新的稀缺资源。** Agent 能批量开 PR，**人不能批量审**；风险从「修不完」转成「审不完」。

**趋势三：度量从「修得多快」转向「暴露少没少」。** GitHub 明确说不要只看 MTTR，要看**高风险暴露随时间是否下降、有多少漏洞被引入或流入生产**；**已验证的修复要与「被压制/被重分类的告警」分开算**。

## 二、技术现状：Git 记录的是「谁提交」，不是「谁生成」

**提交者：有名字。** `author`/`committer` 是人；**模型、prompt、harness 版本都不在 commit 里**（128 期模型身份、137 期工具身份）。

**生成者：无记录。** 哪个模型、哪次检索、哪个工具生成了这段代码；**复盘时无法回答「它当时看到了什么」**（116 期记录）。

**批准者：有记录但无深度。** 点「approve」的人和「真的审过」的人，Git 分不清；**审阅深度没有字段**。

**责任方：合同里。** 厂商对建议质量负责、客户对合并负责；**事故归因时，这条链没有结构化记录**（125 期赔付）。

**三种补丁，三种署名难度。** 全自动生成并提交（最难追溯）、AI 建议人改（中）、人写 AI 审（易）；**越是全自动，越需要附注**。**签名与匿名并存。** GPG 签名能证明「谁提交」，**证明不了「谁生成」**；**没有生成者字段，签名反而给人虚假的确定性**。

## 四、技术挑战

**一，生成者不可见。** 模型版本、prompt、检索内容都不在提交记录里；**复盘只能靠猜**。

**二，审阅深度不可测。** 「approve」不等于「审过」；**没有「看了几行、跑了什么测试」的记录**。

**三，批量开 PR 会淹没审阅。** 2,000 个 PR 一夜到来；**限速是产品策略，不是治理**。

**四，证据不随补丁走。** 修复时跑了测试，合并后证据就散了；**审计时无法复现「当时为什么认为它安全」**。

**五，度量会被「关告警」污染。** 把告警压制/重分类，MTTR 会变好看；**必须区分「验证修复」与「告警消失」**（GitHub 原话）。

**六，责任链跨组织。** 厂商、客户、AppSec 三方；**没有结构化字段，事故归因只能靠会议**。

**七，开源供应链让链更长。** AI 补丁改的是上游依赖；**下游拿到的只有 diff，没有生成者**。

**八，附注可被删。** commit trailer 是文本，**可以改写、可以 squash 掉**；需要签名或不可变记录。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `author.*` 字段**：`commit`、`generator`（model/harness/tool 版本）、`prompt_ref`、`retrieval_ref`、`approver`、`review_depth`、`evidence_ref`。
- **R2 提交附注**：commit trailer 记录生成者与证据链接；**无附注的 AI 补丁视为来源不明**。
- **R3 每补丁证据**：风险说明＋「移除弱点」证据＋「未破坏行为」证据（重跑测试）。
- **R4 审阅容量**：按风险分批；**限速与优先级，而非无脑批量**。
- **R5 度量换轨**：高风险暴露趋势、已验证修复率、回归率；**MTTR 只作参考**。
- **R6 事故归因**：按「生成/提交/批准/启用」四段定位；**每段有具名人与证据**。

### 5.2 用户旅程

- **开发者**：收到 AI 补丁 → 看风险说明与证据 → 跑测试 → 合并并签名 → 在提交里补生成者附注。
- **AppSec**：批量补丁按利用证据/可达性/关键性排序 → 分批放行 → 记录批准深度。
- **SRE**：事故复盘 → 查 `generator` 与 `evidence_ref` → 定位是模型、prompt 还是审阅。
- **审计**：抽查 20 个 AI 补丁 → 核对生成者、批准者、证据 → 确认没有「无名补丁」。

### 5.3 实现方案（90 天）

- **0–30 天：加附注。** commit trailer 记录模型/harness/证据链接；统计 AI 补丁占比。
- **30–60 天：证据化。** 每补丁附风险与测试证据；批准记录深度。
- **60–90 天：换度量。** 暴露趋势与已验证修复率上线；季度抽查归因链；附注纳入门禁。

**第 106 个市场空白（五项）**：AI 补丁生成者可溯率、批准深度可报率、每补丁证据覆盖率、已验证修复率、四段归因完整率——无一内建；`author.*`／`provenance.*` 为**第 73 次无人提字段族**。本地 173／173-kb 连续第 65 期成组启用：刘凯宁 05「结论/证据/待确认项三分」＝全库唯一把「证据随结论走」写进交付的实践，本期首次当主线；配 124 期参数溯源、125 期赔付。判词：**本地把证据随结论走写成模板，联网侧 2026 年才问出「坏补丁算谁的」；两边都没把「这个补丁由谁生成、谁审到什么深度」做成提交字段。**
