# AI-SRE 技术洞察（第 277 期）

**生成时间**：2026-11-18 08:31（Asia/Shanghai）
**观察窗口**：2026-03 至 2026-11-18
**本期主题**：升级等价性面／推理引擎升级——同一个模型，换个引擎就不是同一个模型

## 题眼

先看三条互相独立的证据，它们指向同一件事。

**第一条**：vLLM 论坛《Degraded RL training with v0.10.2》——团队把引擎从旧版升到 0.10.2，CI 里的 reward 曲线变差；他们怀疑是采样器与 logprobs 的导出逻辑变了（新版在 top-k／top-p 截断后导出处理后 logprobs），但把代码改回“截断前导出”**并没有让 reward 恢复**。也就是说：**升级确实改变了行为，连团队自己都无法把它定位到某一处改动**。

**第二条**：llama.cpp issue #27506（2026-08-20）——同一模型、同样参数，ROCm 后端从 build b10040 起 perplexity 爆炸式上升，上下文理解显著退化、工具调用频繁失败；同样的权重换 Vulkan 后端一切正常。**“同一份代码”在不同后端上不是同一个模型。**

**第三条**：Qwen3-Embedding 的 HF 讨论（2026-06-11）——同模型在不同 vLLM 版本、不同 GPU 上得到不同的嵌入向量；官方回复很干脆：**固定 seed 不能保证跨 vLLM 版本或跨 GPU 一致**，vLLM 的可复现性指南把范围限定在“同硬件＋同版本”。

三条说的是同一句话：**推理引擎不是模型的容器，是模型的一部分。** 升级引擎，等于换模型。

## 一、发展趋势

1. **确定性从“默认”变成“可选项”，且有价格**。vLLM 的 Batch Invariance 文档（2026-11-15）给出两个开关：关掉多进程让调度确定，或设 `VLLM_BATCH_INVARIANT=1` 让结果与调度无关。代价写在 PR #51292 里：在张量并行下 `fuse_allreduce_rms` **按构造就是非确定性的**，mnnvl 与 trtllm 两个后端在 H100／0.25.1 上都不 bit-exact——8 次相同运行得到 **8 组不同的 logprobs**。批不变性要靠关掉融合内核换取，decode 密集型负载代价最大。

2. **跨版本漂移已被官方承认**。vLLM 可复现性指南的适用范围是“同硬件、同版本”；PyTorch 也有类似的跨版本／跨平台限制。这意味着“升级后输出变了”不是 bug 报告，而是**规范允许的行为**——验收责任因此落回使用方。

3. **后端与内核级回归是常态**。TensorRT-LLM 的 release notes 里，accuracy 修复与回归按模型、按内核逐项列出（deepseek-r1 精度、Mistral Small 3.1 精度测试、70B GSM8K 掉点、Qwen3 因精度问题禁用 deep_gemm）。这类条目说明：**引擎升级的“变更集”里，精度变化与性能变化是并列的一等公民**。

4. **升级也会改训练**。上面 vLLM 0.10.2 的例子发生在 RL 训练里：rollout 引擎升级后，训练看到的策略分布变了，reward 曲线随之变差。这与第 276 期 FourSight 的“rollout 引擎与训练引擎 token 级错配”是同一问题的两面——**训练与推理必须锁同一套引擎语义**。

## 二、技术现状

**第一层：等价性没有定义。** 团队说“升级后效果没变”，通常指“抽了几条 prompt 看着差不多”。真正的等价需要声明维度：输出分布（top-k logprobs 的 KL）、任务指标（golden set 通过率）、工具调用序列、拒答率、嵌入余弦相似度。没有维度声明，“等价”只是印象。

**第二层：同版本也不保证同输出。** 批不变性缺失意味着“同一请求、同一版本、不同 batch 组合”会得到不同结果；TP 归约顺序、CUDA graphs、连续批处理都会引入差异。生产里用同一版本复现线上问题，经常复现不出来，原因不在模型，在调度。

**第三层：漂移检测缺工具。** 目前主流做法是“上线后看业务指标”，滞后且混淆因素多。arXiv 2603.19022 的 Behavioral Fingerprints 提供了另一条路：用固定 prompt 集生成端点行为指纹（只用首个 token，成本低），按固定节奏重采，用 e-value 累积证据判断“输出分布是否发生变化”，超过阈值即宣告变更事件并重置基线。这把“升级是否等价”变成一个**可持续监测的统计问题**，而不是一次性验收。

**第四层：回滚路径依赖旧内核还在。** 升级后若旧版本镜像被清理、旧 CUDA 驱动不兼容新卡、旧量化文件被覆盖，“回滚”就只剩重装。第 276 期讲的六元组在这里再次生效：引擎升级的回滚，必须能重建旧引擎的运行时。

## 三、技术竞争力

| 方案／机制 | 管什么 | 跨版本一致 | 批不变 | 代价 | 可验证性 | 运维适配度 |
|---|---|---|---|---|---|---|
| vLLM（默认） | 推理引擎 | 不保证 | 否 | — | 需自建 | 高（生态大） |
| vLLM `VLLM_BATCH_INVARIANT=1` | 批不变 | 不保证 | 是 | decode 性能下降 | 可测 | 中 |
| vLLM 单进程调度 | 调度确定性 | 不保证 | 部分 | 吞吐下降 | 可测 | 中 |
| llama.cpp（后端相关） | 推理引擎 | 不保证 | 否 | — | PPL 可测 | 中（后端差异大） |
| TensorRT-LLM | 推理引擎 | 按版本 | 部分 | 构建复杂 | release notes 逐项 | 中 |
| SGLang | 推理引擎 | 不保证 | 部分 | — | 需自建 | 中 |
| 嵌入服务（同模型） | 向量 | **漂移** | — | — | 余弦可测 | 低（需 pin） |
| 行为指纹（arXiv 2603.19022） | 漂移检测 | 不适用 | — | 采样成本 | 强（统计） | 高（建议必建） |
| golden set 回归 | 任务指标 | 不适用 | — | 标注成本 | 强 | 高 |
| 金丝雀＋影子流量 | 上线风险 | 不适用 | — | 双跑成本 | 中 | 高 |

**判读**：引擎厂商卖“更快”，可复现性文档卖“范围限定”，行为指纹卖“看得见变化”。三者之间缺的是**升级验收的判定标准**：哪些维度允许变、变多少算等价、超了怎么回。

**本期反转**：我们默认“模型不变、引擎可换”，所以升级评审看的是性能与稳定性。证据说明引擎是模型的一部分——内核融合、归约顺序、采样器、量化路径都会改输出分布。**升级的验收标准不该是“吞吐提升、无报错”，而该是“行为指纹未变，或变化落在批准范围内”。**

**判词**：「引擎／镜像 digest／指纹工具／金丝雀／回滚」全部可采购，「这次升级后哪些内核路径变了、输出分布偏了多少、偏差是否在批准范围内、旧路径还能不能回去」不可采购。

## 四、技术挑战

1. **等价维度未声明**：没有 KL／通过率／调用序列／拒答率的阈值，“等价”无法判定，也无法在事故后复盘。
2. **批不变性与吞吐冲突**：开批不变性要牺牲 decode 性能，团队必须在“可复现”与“便宜”之间做显式选择，而不是默认。
3. **后端碎片化**：ROCm／Vulkan／CUDA／TP 组合各自有回归，验收矩阵随硬件扩张而爆炸。
4. **训练与推理不同步**：rollout 引擎升级会让 RL 训练分布漂移，训练侧必须锁引擎版本或做等价校准。
5. **旧路径消失**：镜像清理、驱动升级、量化文件覆盖，让“回滚到旧引擎”在物理上不可能。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 等价维度：为每个服务声明（输出分布 KL、golden set 通过率、工具调用序列一致率、拒答率、嵌入余弦）及阈值。
- D2 行为指纹：固定 prompt 集＋首 token 指纹，按日／按升级重采，e-value 判变更；基线随批准变更重置。
- D3 内核清单：记录实际走到的内核路径（融合、量化、注意力后端、TP 归约），升级时对比差异。
- D4 双跑验收：新引擎与旧引擎影子双跑，按 D1 维度比对，超阈值阻断发布。
- D5 回滚保留：旧镜像、旧驱动、旧量化文件保留 N 个版本；回滚路径纳入演练。
- D6 训练侧锁定：RL／蒸馏流水线锁定 rollout 引擎版本，升级需重跑 reward 基线。

**用户旅程（一次“无感”升级）**

① 平台把 vLLM 从 0.9 升到 0.10.2，压测显示吞吐 +12%、无报错，评审通过（D3 缺项）；② 上线后业务指标两周内缓慢下滑，归因困难（D1 未声明、D2 未建）；③ 复盘发现采样器与 logprobs 语义变化，但无法量化影响面（D3）；④ 想回滚，旧镜像已被清理、驱动已升级（D5）；⑤ 最终靠重新构建旧版本＋重跑 golden set 才恢复，耗时远超升级本身。

**90 天实现方案**

- **第 1–30 天**：选 3–5 个核心模型服务，声明 D1 维度与阈值；采集一次升级前行为指纹作为基线；把内核路径写进启动日志。
- **第 31–60 天**：上线影子双跑（D4）与指纹日报（D2）；旧镜像／驱动／量化保留三个版本；TP 场景评估 `VLLM_BATCH_INVARIANT` 的吞吐代价，形成明确取舍。
- **第 61–90 天**：把“升级等价性”纳入发布门禁；RL 流水线锁引擎版本并重跑 reward 基线；做一次“回滚旧引擎”演练，验证 D5 可用。

**第 198 个市场空白（五项）**：① 引擎升级等价性的维度标准；② 行为指纹的基线治理；③ 内核路径的可观测字段；④ 训练-推理引擎版本锁；⑤ 旧运行时保留策略。

**`engine_version.*`／`upgrade_equivalence.*` 第 165 次无人提字段族**：厂商 release notes 写“性能提升、精度修复”，不写“这次升级让输出分布偏了多少、哪些内核路径变了、旧路径还能不能回去”。

**本地 173／173-kb 连续第 153 期成组启用（周昕毅 10：变更前后要有可比的基线）**：本地原型把“行为指纹”做成升级单的必填附件——升级前后各跑一次固定 prompt 集，KL 与通过率差异超阈值即打回；指纹文件按引擎 digest 存档，回滚时直接比对。
