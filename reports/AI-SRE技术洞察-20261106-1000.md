# AI-SRE 技术洞察 · 第 85 期（2026-11-06 10:00）

## 在途面（运行中换版 / In-flight Revision）——同一条 run 里，第 7 步用的已经不是第 1 步的规则

> 本期主线：第七十六条。前 84 期默认「一次运行有一条连续的线」，本期第一次问：**这条线中途被改过几次、每次从第几步开始算数、trace 里有没有留下这次改写**。与 82 缺省面（没有人表态的静态默认值）、84 时间基准面（证据上的钟与 as-of 边界）、61 压缩面（上下文被少记）、42 自治面（等级升降）、39 复现面（证据能否复用）逐条划界：那几期管的是「值是什么／何时发生／能否重放」，本期管的是**规则在运行中途被替换，且替换没有生效边界**。视角从 79 组织层、80 执行层、81 验收层、82 配置表、83 样本框、84 时间坐标系，落到六者共用的容器——「一次运行」本身。

## 一、发展趋势：从「启动前定死」转向「运行中可改」，但版本制度还没跟上

最近 30 天，四家把「改配置」从部署动作做成了运行时 API。10-05/06 Cursor SDK 上线 `run.steer()`，可在活跃 turn 内注入新指令而不取消任务；前台子智能体被转向后转后台继续跑，其结果以 follow-up turn 回流**同一条 run**，`run.wait()` 因此等到子任务结束才 resolve；1.0.32 又改了「等待后台子智能体时」的转向生效时机，10-20 Agent SDK GA。10-22 Google 发布 Agent Compute Engine 与开源 Agent Substrate：每 agent 独立 microVM、copy-on-write、快照暂停恢复、clone/fork/**rewind and rollback**，自报 20 万 agents / 500 激活每秒 / 恢复 <500ms / 10 倍密度。10-31 OpenAI Python SDK 3.42.0 一次给出 `review`（none / auto_review）、`compaction`（后台 / 阻塞）、`experimental.time_awareness` 与 `agent.tools` 热替换四组开关。国内侧：11-03 火山 AgentKit 新增执行超时与「中间层 Agent」访问规则，11-05 Seed-Evolving 升级多步骤任务的规划与结果验收；10-29/30 腾讯 CloudQ 升级多云全景图谱与受控执行，11-02 信通院《云上 Agent 基准度量模型》六维五要求首批认证。

判断：**能力曲线已拐到「在途可改」，制度曲线仍停在「发布前审批」**。前 79 期讨论的台账、变更单、CAB、灰度都假设配置在 run 开始前冻结；现在改配置发生在第 7 步，而验收、审计、回放、评测仍按「一次运行 = 一个版本」建模。79 期「能力上线了编制制度还没上线」、80 期「写序制度还没上线」、81 期「不写的制度也还没上线」，推到这里是：**「换版的制度也还没上线」**。

## 二、技术现状：四种生效点并存，版本挂在对象上、不挂在事件上

**① 一次运行里同时跑着四种生效点。** 3.42.0 的类型文档写得极直白：改 `review` 只对「新的 root turn」生效，「Existing turns and their subagents keep their review mode」；改 `agent.tools` 时函数与 MCP 工具「change on the next model call」、内置工具「change by the next turn」；压缩在后台异步发生，官方自认「Background compaction may increase token usage」却未给量级。于是一次事故调查可能出现：父 turn 已升到自动复核、子智能体仍跑无人复核，函数工具与内置工具的切换还差一轮。`auto_review` 附带「Deny manual approval fallbacks」——本该等人批的动作直接被拒，而哪些动作算「eligible」未定义。

**② 能不能在途换工具，本身在 10-31 被改了。** 一份 Agents API 实战教程仍写「instructions、tools、multi_agent 固定会话生命周期，要改就新建会话」，并称这恰是「审计问某次 run 被允许做什么」时最有用的性质；同周 3.42.0 的 `agent.tools` 已允许替换。同一平台两份公开材料给出相反答案，说明**「审计可依赖的不变性」成了版本相关属性**——82 期「查文档本身不再可靠」在配置层的复现，且这次连生效边界都随版本漂移。

**③ 唯一做对的是不可变版本 + 会话钉版。** Claude Managed Agents 把每次 `agents.update` 生成新的不可变版本，`sessions.create` 用「ID + 版本号」选版：**在途会话保持钉版、新会话取最新**，版本回退只需把调用指回 v1，且版本号变更本身就是可追溯操作（第三方对厂商文档的整理，非一手规范）。对照之下，OTel GenAI 虽有 `gen_ai.agent.version`、阿里 LoongSuite 给 Skill 记 `name/id/description/version`、用 Entry/Step 折叠长 trace，但**版本挂在资产定义上，不挂在「第 7 步实际生效的是哪一版」这个事件上**；规范仍是 Development、6 月已迁独立仓库，无 `effective_revision` / `boundary` / `summary.version` / `branch.parent_snapshot` 字段族。

**④ 三种静默换版不进 trace。** 压缩：0.24.0 写明「Automatic compaction is deferred for pending approvals」，压缩与审批已被当状态机耦合，但 span 无 `summary.version`，61 期「记住了什么」无法归因到具体步骤。时间：3.42.0 的 `time_awareness` 给模型「periodic current-time reminders」，默认关、标实验、频率未公开——84 期问「证据上的时间戳是谁的钟」，这里的答案是**钟是平台周期性注入的一段提示文本**，与 trace 的钟之间没有 join key。转向：`systemPrompt` 替换不持久化，`Agent.resume()` 必须重传，否则恢复出来的不是同一个 agent；`run.steer()` 返回 `complete_delivered` / `revert_to_followup`，云端 run 恒返回后者。父 turn 结束不再是完成信号（45/52 期的运行层镜像）。

**⑤ 安全遥测撤版不重算历史。** Claude Code 2.1.312（10-27）停发六天前才加的 `claude_code.safety_event` OTel 事件，无理由、无替代；2.1.314 才补上「resume/continue 进入的 worktree 未受沙箱保护」「Bash hooks 不覆盖 Monitor 启动的命令」，2.1.316 又把 `managed.policy_mode` 从「首个命中」改为逐层合并。策略语义在一次升级中变了，历史结论不重算、不标注——62 期元观测面与 78 期到期面（这次连日期都没有）的合流。

**⑥ 分叉让血缘从链变成 DAG。** Google ACE 的 fork/rewind 使回滚只回收进程不回收世界（80 期已证），更缺的是「这个结论由哪个快照派生」；官方称编排层与执行沙箱的边界能产出一条把 harness 工具调用连到沙箱内活动的审计轨迹，但这条轨迹是**会话内**的，不是**跨分支**的。Anthropic 10-14 OTel 公测为 best-effort、默认仅元数据，且 Managed Agents 的 model request span 不导出内部 prompt 与响应——trace 是事后活动重建，不是运行记录，用它取证「当时生效了什么」结构上不可能。

## 三、技术竞争力（主要厂商 / 方案对比）

| 方案 | 在途换版能力 | 生效边界是否声明 | 运行/步骤级钉版 | 换版进 span 与变更记录 | 回放冻结整套装配 | 关键缺口 |
|---|---|---|---|---|---|---|
| Google ACE / Agent Substrate（10-22） | 极强：fork/rewind/快照 | 否（仅会话内审计轨迹） | 否，无 parent_snapshot | 否 | 进程可回滚、世界不可 | 分支血缘不在遥测层 |
| Google Gemini Enterprise 治理五件套 | 策略层（Gateway/Registry/Identity） | 部分 | 否 | 否 | 否 | Registry 记「批准了什么」，不记「哪步生效」 |

| OpenAI Agents API · SDK 3.42.0（10-31） | 强：review/compaction/time/tools | 部分：四种边界写在类型文档 | 否（仅新 root turn 受影响） | 否 | 否 | 文档互相矛盾、生效点不统一 |

判读：**模型派分化最明显**——Anthropic 用「不可变版本 + 钉版」把问题消灭在设计期，OpenAI 把可变性做成一等 API 却没给统一生效边界，Cursor 把转向做成一等 API、又用 `revert_to_followup` 诚实暴露了本地/云的能力分裂。**云厂商执行层最强、遥测层最弱**：Google 把 20 万 agent 的分叉做到极致，却没有一处记录结论由哪个快照派生；阿里是国内最接近「按调查层级留痕」的一层，但 version 仍挂在 Skill 上。国内平台派可控性最好（火山把超时写进「使用限制」、腾讯信通院六维含数据可信与过程可审计），**却无一维度问「运行内换过几版」**。最完整可执行的答案来自工程实践侧：开源 apogee 明确「换工具 idle-only、拒绝 mid-Exchange，子智能体从 next spawn 见新集合、在途者保持原集合」；中文工程稿要求先存运行快照、列差异清单、标影响任务、定生效窗口、分批灰度——「配置保存成功不等于所有任务已安全切换」。三者都不可采购。分野不在诊断分数，而在三问：**每一步能否机器读出生效的修订号／换版是否作为变更事件进记录／重放能否冻结整套 release assembly**。

## 四、技术挑战：第三十九个市场空白

运行修订号覆盖率、生效点一致性、摘要版本可见度、分支血缘可追溯——四项无一厂商内建；上表「运行/步骤级钉版」「换版进 span」两列几乎全空。OTel GenAI 在 72 期 `agent.identity.*`、79 `billing_unit`、80 `attempt`、81 `abstain`、82 `config.effective`、83 `sampling`、84 `time.*` 之后，仍无人提 `run.revision.*` / `boundary` / `summary.version` / `branch.parent_snapshot`。后果是取证口径塌方：审计要的是「03:12 生效的是哪一版 prompt、工具 schema 与策略」，今天只能靠猜；行业分析主张把 **MTTA（平均归因时间）独立于 MTTD/MTTR**，并把 prompt、工具 schema、权限、检索配置、模型版本、策略规则整套「release assembly」与 trace 一起留存——「没有版本化的 agent 只能被归责，不能被归因」。EU AI Act Art.12 / Art.26(6) 的日志保留要求（二手转述，仅取方向）指向同一处。

**本地 173 库连续第六期成组启用，且首次升级为「生效治理原型」**：余锦泽 03 给出「当前生效版本 ＝ 基线 ＋ 编辑日志回放」，并记录了题眼级事故——「人工否决一条关系后图谱已剔除，问数仍按被否决的关系给出连接提示」「**否决只在图谱视图生效**」，修复方式是收敛到「单一读取入口：基线＋日志回放」与写—读—撤销—读一致性测试；何伟 02「固定需求与现场，对比规则更新前后版本」「配置组合、缺失值、默认值与回退」进专项检查；朱革 15「热更新：天级发版 → **秒级生效**」；马云雷 31「环境与版本快照」「版本化 Benchmark、变更差异与同题回归」；赵恒 25「决策只做一次、写进定义、处处生效」；肖汉松 22「约束已生效 · 回测仍 0/3」＝生效不等于生效到正确对象；刘凯宁 05 单 Trace 分阶段耗时＝生效窗口可测量；周昕毅 10「规则决定何时继续何时停止」写进流程。判词：**联网侧在争论能不能在途改，本地工程实践派早在解决「改了之后谁读到了」**——与 80~84 期一致，仍是项目内约定而非平台能力。

## 五、展望与建议

1. **运行修订账本**最小 schema：`run_id / revision / effective_from_step / boundary(next_model_call|next_turn|new_root_turn|async|pinned) / config_digest / parent_snapshot / actor / reason`；换版必须发一等事件 `revision.changed`，与 38 期变更信封并列。
2. **默认钉版**：会话启动时冻结整套装配，变更只对新 root turn 生效且必须显式声明；子智能体继承父 turn 的 revision，升降单独记账（补 79 期编制台账）。采购条款写明「在途会话不受新版本影响」。
3. **每步 span 记 `effective_revision` + `config_digest`**；`summary.version` / `summary.built_at_step` 进 span，重放必须 pin 压缩策略与摘要快照（接 39 期断网重放、84 期 as-of 冻结）。
4. **steer / resume 契约化**：把 `complete_delivered` 与恢复所需配置一起写进 run 状态；「父 turn 结束 ≠ 完成」写进 SDK 消费方验收，避免 45 期沉默态变体。
5. **提 OTel genai 字段族** `run.revision.*` / `boundary` / `summary.version` / `branch.parent_snapshot`，纳入信通院六维补格与采购三问；评测基准新增「在途换版」题型：第 7 步换工具集／审批模式／压缩策略，验收结论是否自相矛盾。
6. **把 MTTA 设为独立 SLI**，目标 15 分钟内定位到 agent、步骤与授权版本；混沌注入目录新增「运行中换版」与「安全遥测撤版」两类，并验证历史结论是否随规则升级被重算。
