## 题眼

2026-09-24 的一篇一线排查记录从一句很日常的抱怨开始：同一句 SQL，周二跑 50 毫秒，周三跑 5 秒；SQL 没改、表结构没动、数据量也没涨多少，变更单和发布记录里什么都没有。把两天的 `EXPLAIN` 并排一放，差别只有三列——`type` 从 `ref` 变成 `ALL`，`key` 从 `idx_status` 变成 `NULL`，`rows` 从 1,200 涨到 **2,100,000**。

表总共两百多万行，实际符合条件的只有一万多条。优化器凭什么觉得这个条件要命中几乎整张表？因为它**不是数的，是估的**：InnoDB 默认只随机抽 20 个索引页（合计约 320 KB）去推算整张几个 G 的表；`status` 这类严重倾斜的列，采样页稍微偏一点，基数就能差出好几倍。基数估错，代价模型就会做出“诚实但错误”的选择：以为走索引+回表很划算，实际要回表两百万次随机 I/O，比全表顺序扫描还慢。

2026-11-18 更新的云厂商 PostgreSQL 排障文档补了另一个反直觉点：**autovacuum 跑了，统计信息也可能过期**。因为 autovacuum 依据“插入/更新了多少行”触发 `ANALYZE`，而不是“分布是否真的变了”。当应用开始查询另一个值区间或时间窗口时，规划器的成本估计可能已经不匹配新分布；如果同时有表膨胀，一个次优计划会扫描更多死数据，影响被放大。

2026-11-08 的一篇 MySQL 直方图分析则拆了“直方图能治计划漂移”的误解：直方图只覆盖**单列过滤**；高基数列在桶数不足时直接失效；函数包装或分区未命中时，优化器**根本不读**直方图。换句话说，直方图不是万能药，它只在“单列、倾斜、被读取”三个条件同时成立时有效。

更隐蔽的一种是“统计会丢”。2026-11-07 的一个 issue 记录：Windows 上的嵌入式 PostgreSQL 每次停止都被 `taskkill /f /t` 硬杀，Postgres 来不及写关闭检查点，也来不及写 `pgstat.stat`；下次启动做崩溃恢复，**累计统计被清零**（`n_live_tup`、`n_mod_since_analyze`、`last_autoanalyze` 等）。autovacuum 正是根据这些计数器决定何时分析，于是每次重启都从零开始，频繁重启的实例上大表很少甚至从不被分析——他们的 `activity_log` 实际 10.5 万行，规划器却以为只有 7 行。

## 一、发展趋势

**第一，计划劣化被当作独立故障类。** 不是“数据库慢”，而是“估计错了，计划换了”。

**第二，统计的“新”与“对”被分开。** 刚跑过 ANALYZE 不等于分布被代表；采样页数、倾斜、关联列都会让统计失真。

**第三，直方图的边界被讲清。** 只救单列过滤；桶数、函数包装、分区裁剪都会让它失效。

**第四，统计丢失场景被重视。** 硬杀、崩溃恢复、恢复备份、升级迁移，都会让累计统计归零，进而让 autovacuum 失明。

**第五，计划回归开始被监控。** 用 `pg_stat_statements`、plan hash、EXPLAIN 基线做漂移检测，而不是等用户投诉。

## 二、技术现状

**采样偏差。** 小样本 + 倾斜列 = 基数估计差几倍；默认采样页数对小表够用、对大表不够。

**触发条件错位。** 按变更行数触发分析，不按分布变化触发；参数化查询换值区间时最容易踩。

**直方图边界。** 单列、桶数、表达式、分区；任一不满足就不生效。

**统计丢失。** 硬杀/崩溃/恢复/升级后计数清零；autovacuum 从零开始。

**计划翻转。** 行数估计从 100 变 10,000 就可能把索引扫描换成全表扫描；关联表越多越敏感。

**止血与治本混淆。** hint、plan freeze、强制索引是止血；统计、索引、查询改写才是治本。

## 三、技术竞争力

| 方案 | 估计准确性 | 覆盖倾斜 | 维护成本 | 主要风险 |
|---|---|---|---|---|
| 默认采样统计 | 中 | 低 | 低 | 倾斜列失真 |
| 提高采样页数/统计目标 | 中高 | 中 | 低 | 分析时间 |
| 直方图（单列） | 高（单列） | 高 | 中 | 表达式/分区不生效 |
| 扩展统计（多列相关） | 高 | 高 | 中 | 需识别相关列 |
| 计划冻结/hint | 不适用 | 不适用 | 中 | 掩盖真实劣化 |
| 自动索引/索引顾问 | 中 | 中 | 中 | 建议质量 |
| 计划回归监控 | 高（检测） | 中 | 中 | 需基线 |

判读：买得到数据库、直方图、扩展统计、索引顾问、监控；买不到“这次计划为什么换、换之前估计错在哪、统计是否代表当前分布、恢复后统计还在不在”。

本期反转：我们一直把“数据库慢”当容量或索引问题。实际上很多事故是**估计错误在特定参数下显形**：SQL 没变，数据分布变了；autovacuum 跑了，统计仍不代表新分布；直方图建了，优化器根本没读。

判词：「数据库／直方图／扩展统计／索引顾问／计划监控」全部可采购，「这次计划为什么换、估计错在哪一列、统计是否代表当前分布、恢复后统计是否还在、止血方案掩盖了什么」不可采购。

## 四、技术挑战

**其一，倾斜列。** 小样本推大表，基数差几倍是常态。

**其二，触发机制错位。** 变更行数不等于分布变化；参数化查询换值区间时最危险。

**其三，直方图边界。** 表达式包装、分区键、多列相关都不在覆盖内。

**其四，统计丢失。** 硬杀、恢复、升级迁移后累计计数清零，autovacuum 失明。

**其五，计划不稳定性与可复现性。** 同一 SQL 在不同参数、不同统计下计划不同；复现要固定统计与参数。

**其六，止血的副作用。** plan freeze/hint 能稳住当前计划，但会掩盖后续真实劣化。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- DBA/SRE：需要统计新鲜度、分布代表性、计划漂移检测。
- 应用团队：需要知道参数化查询换值区间的影响。
- 平台：需要恢复/升级后自动 ANALYZE 与统计校验。
- 复盘者：需要区分“数据增长”“统计失真”“计划翻转”。
- 容量规划：需要区分“容量不足”与“计划错误”。

**用户旅程（一次“SQL 自己变慢”）。**

1. 周二 SQL 50 ms；周三同 SQL 5 秒，变更单为空。
2. EXPLAIN 对比：`ref`→`ALL`，`idx_status`→`NULL`，估计行数 1,200→210 万。
3. 根因是统计采样偏差 + 分布倾斜；ANALYZE 后恢复。
4. 几天后又漂移；建直方图仍不生效（列被函数包装）。
5. 另一次重启后统计清零，autovacuum 不再分析大表。
6. 真正缺的是“统计代表性 + 计划回归监控 + 恢复后校验”。

**实现方案（90 天）。**

- 第 1–2 周：统计盘点——采样页数、统计目标、直方图覆盖、扩展统计；标出倾斜列与相关列。
- 第 3–4 周：关键查询计划基线——`pg_stat_statements`/plan hash/EXPLAIN 基线；漂移告警。
- 第 5–6 周：恢复与升级后自动 `ANALYZE`；校验累计统计是否存在；硬杀场景改为优雅停止。
- 第 7–8 周：参数化查询审计——值区间变化的查询单独看；必要时用 `plan_cache_mode`/绑定变量窥探策略。
- 第 9–10 周：直方图与扩展统计——只对“单列/相关列 + 被读取”的场景建；定期校验生效。
- 第 11–12 周：止血规范——hint/plan freeze 必须附失效日期与复核人；禁止长期冻结。
- 第 13 周：演练——注入分布倾斜、统计清零、参数区间变化，验证监控与恢复。

**验收标准。** 任一次计划劣化，能回答：估计错在哪、统计是否代表当前分布、计划何时翻转、恢复后统计是否还在、止血覆盖了什么。

**第 239 个市场空白（五项）**：统计代表性检查；计划回归基线；恢复后统计校验；直方图生效验证；止血到期复核。

**`plan.*`／`statistics.*` 第 206 次无人提字段族**：`statistics.sample_coverage`、`statistics.distribution_drift`、`plan.baseline_hash`、`plan.flip_reason`、`statistics.post_restore_present` 在数据库、监控与发布平台之间没有统一语义；监控只报“慢查询”。
