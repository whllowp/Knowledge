# AI-SRE 技术洞察（第 127 期）

**生成时间**：2026-11-11 09:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：发布面／行为发布面（Behavior Release）——代码有流水线，行为只有热更新；prompt、skill、memory 都是生产变更，却没有一版可签名的制品

---

## 题眼

Microsoft Learn 的 GenAIOps 课程里有一句很朴素的话：**prompt 改动「立即生效」，没有编译与测试这一关；改一个词，就改变了成千上万用户的体验**。它给出的四个失败形态也朴素：静默退化（措辞小改让准确率下滑，直到用户投诉）、环境漂移（开发改了生产没改）、危机恢复（出事时找不回上一版）、知识丢失（几个月后把关键安全指令当「多余」删掉）。**这四种都不报错，只在用户那里报错。**同月 ManageEngine 的 CAB 文章从另一头补刀：AI 能帮 CAB 做风险关联、自动放行低风险变更、持续核对执行偏差，但前提是「变更与配置数据准确完整」——**未记录的影子变更会让 AI 误判**。两边说的是同一件事：**Agent 的行为变更已经是生产变更，却没有生产变更的发布面。** 发布面的最低要求只有三件：**可指名（这一版是哪个制品）、可复现（同 digest 跑出同行为）、可撤回（回滚到上一版且状态一起回）**——三件都缺。

## 一、发展趋势

**趋势一：行为变更从「配置」变成「发布」。** 过去改 prompt 像改文案；现在 prompt 决定工具调用、审批边界与成本，改一个词就是一次行为发布。**发布需要制品、通道、审批、回滚；prompt 目前四样都没有。** 这不是工具缺失，是**把「行为」当成了「配置」的范畴错误**。

**趋势二：CAB 开始被 AI 改造，但改造的是「评审」，不是「制品」。** ManageEngine 描述的是 AI 做风险关联、自动放行、执行期核对；**这些能力都假设变更单里写着这次改了什么**——而行为变更往往根本没有变更单。

**趋势三：供应链先有了包，运行时还没有锁。** Cloudsmith 把 Skill 做成可钉版、可禁、可审计的包（118 期）；但运行时动态加载技能、写记忆、路由模型 alias，**三条暗道都不经过这个包管理器**。

## 二、技术现状：四种制品，只有一种有包装

**prompt：存在仓库里，但不一定是制品。** Microsoft 的建议是把 prompt 放 GitHub、走 review、分环境、可回滚；现实中大量团队仍在控制台直接改，**没有 digest、没有签名、没有依赖锁**。

**skill：有包，没有发布记录。** Cloudsmith 能按名与版本 allow／deny，但「这一版 skill 何时被哪个运行时加载、加载后行为变了多少」没有记录；118 期的跨运行时行为差 7.13 点，说明**同一个包在不同壳里不是同一个行为**。

**memory policy：写入即生效。** 111 期的记忆写入、61 期的压缩，都是「没有变更事件的变更」；改一条注入规则、清一次缓存，行为立刻变，**没有版本号，也没有回滚点**。

**tool description：描述即指令。** 92 期讲过工具描述是能力来源；改一句描述等于改模型的行为先验，但它挂在工具注册表里，**通常不在代码仓库、也不在 CAB 里**。

**三个存储，一个 digest 都没有。** prompt 在控制台或仓库、skill 在对象存储或包管理器、memory 在数据库；三处各有各的版本机制，**没有一个共同的 `artifact_digest` 能把「这一版行为」指出来**。于是「回滚到上一版」只能回滚其中一处，另外两处继续漂移。

**没有通道，就没有「灰度」这个概念。** 代码可以先 1% 流量；prompt 一保存就全量。Microsoft 列的「环境漂移」正是这个后果：开发环境改了、生产没改，或者反过来，**两边跑的不是同一个行为**。

## 四、技术挑战

**一，行为没有制品。** prompt 是文本、skill 是目录、memory 是行；没有统一 digest，就没有「这一版」这个概念。

**二，三条暗道绕过发布。** 动态加载 skill、写记忆、路由 alias，都不经过流水线；**发布面管得住包，管不住运行时。**

**三，回滚不完整。** 回滚 prompt 文本，不会回滚已写入的记忆、已缓存的会话、已产生的副作用；**行为回滚≠状态回滚**。

**四，CAB 看不见。** 行为变更通常不是 RFC；ManageEngine 自己承认「影子变更」会让风险模型误判。

**五，没有 DORA 口径。** 变更前置时间、变更失败率、恢复时长，对行为变更没有定义；**无法度量，就无法改进。**

**六，审批者不懂行为变更。** CAB 成员熟悉基础设施变更的风险分类，但「这句提示改动的爆炸半径」没有现成量表；结果不是拒批，就是橡皮图章。**没有风险分类，就没有真审批。**

**七，多环境多租户放大漂移。** 开发、预发、生产各一份 prompt，租户级又有覆盖配置；**任何一处漏改，都会让「同一版」在不同环境里表现不同**，而排障的人以为它们在跑同一版。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `release.*` 字段**：`artifact_id`、`digest`、`channel`、`approved_by`、`rollback_ref`、`loaded_at`。
- **R2 行为制品化**：prompt、skill、memory policy、tool description 四类统一打包，带 digest 与依赖锁。
- **R3 发布通道**：dev→canary（5% 影子）→prod；每级有验收与自动回退。
- **R4 回滚语义**：文本回退＋记忆快照＋缓存刷新＋副作用清单，四件一起回。
- **R5 变更记录**：行为变更进 CAB（或等价评审），记录改了什么、为什么、影响面。
- **R6 冻结覆盖**：封网期同样冻结行为变更，不只冻结代码发布。
- **R7 影子变更检出**：定期比对「运行时实际加载的制品」与「登记在册的制品」，不一致即报 shadow change。

### 5.2 用户旅程

- **平台工程师**：改一版 skill → 打包出 digest → 走 canary → 看行为差 ≤2pp → 推生产 → 记录 approved_by。
- **SRE**：事故中怀疑是 prompt 改动 → 查 `release.*` → 定位到 3 小时前那版 → 一键回滚文本＋记忆快照 → 恢复。
- **审计**：抽查一次行为变更 → 核对制品、审批、加载记录、回滚点 → 签字。
- **CAB**：收到行为变更单 → 看影响面与回滚方案 → 批准或要求补 canary。

### 5.3 实现方案（90 天）

- **0–30 天：盘制品。** 列出四类行为制品与当前存放位置；把控制台直改的收进仓库。
- **30–60 天：建通道。** 打包＋digest＋依赖锁；dev/canary/prod 三级；接 5% 影子流量。
- **60–90 天：补回滚。** 记忆快照与缓存刷新进回滚脚本；行为变更进 CAB；季度演练一次「回滚到上一版」。
- **90 天后：度量。** 定义行为变更的四个 DORA 指标（前置时间、发布频率、失败率、恢复时长），按季度公布。

**第 81 个市场空白（五项）**：行为制品可签名率、发布通道覆盖率、回滚完整率（文本＋状态）、行为变更入 CAB 率、变更前置时间可报率——无一内建；`release.*`／`artifact.*` 为**第 50 次无人提字段族**。本地 173／173-kb 连续第 45 期成组启用：何伟 02「Harness 双循环、约定验收标准」＝全库唯一把「约定→验收→回流」写进交付的实践，本期首次当主线；配朱革 15「Agent、Skill、Prompt、工具和知识缺少统一版本边界」、casa 01「已验证的重复步骤才固化成命令」。判词：**本地把版本边界写成规模化第一障碍，联网侧 2026 年才由厂商培训材料承认「prompt 改动立即生效、没有编译测试」；两边都没把「这一版行为」做成可签名、可回滚的制品。**
