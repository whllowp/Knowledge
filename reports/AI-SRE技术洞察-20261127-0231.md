**本期主题**：节流面／CPU 配额与 CFS 节流——利用率没打满，为什么还会被掐

## 题眼

2026-11-19 的一篇排查笔记把现象写得很具体：接口延迟**隔一会儿抖一下**，节点上还有空闲 CPU，`kubectl top` 里这个容器的用量也**低于它的 CPU Limit**。原因不是下游变慢，而是 CFS 把 Limit 收成了**周期配额**——本周期配额用完，线程被掐到下一个周期，整机空着也没用。

一个可复算的例子：周期 100ms、Limit 200m，配额是 0.2 × 100,000 微秒 = **20,000 微秒（20ms）**。单线程请求需要 40ms CPU，本周期只能跑 20ms，剩下的要等配额刷新，墙钟至少跨过一次周期边界。这一秒里若只有这一次请求，平均用量约 **40m**，只有 Limit 的**两成**——监控曲线是窗口平均，对不齐这几十毫秒。

## 一、发展趋势

第一，CFS 节流从"资源保护"变成"延迟故障源"。延迟敏感在线服务设 CPU Limit 的代价，正在被越来越多的生产复盘记录：arXiv 2605.15866 的一组约束实验里，0.5 CPU、512MB 的配置把中位延迟推到 **103,447ms**，作者估算约 **98%** 的总延迟来自 CPU 节流而非计算本身。

第二，节流的层级语义被重新审视。2026-07-24 提交的 cgroup v2 文档补丁指出：多层 `cpu.max` **每一层独立计费**，与 `memory.max`/`io.max` 只取最严限制不同；一个进程可能同时被父层和子层节流，`cpu.stat` 里能看到合并效果。这意味着"我只设了一个 limit"往往不成立。

第三，在线/离线分池成为共识。2026-11-05 的一场讨论里，实践者的结论很直接：延迟敏感的在线业务**别设 CPU Limit**，或走 Guaranteed + Static 绑独占核；离线批处理正常设 Limit 防吵闹邻居；设了 Limit 就"必踩 CFS 节流的长尾"。

## 二、技术现状

**利用率是窗口平均，节流是周期事件。** `kubectl top` 与多数监控面板给的是 1 分钟或 5 分钟平均；CFS 的判定发生在每个 100ms 周期里。四个线程跑 20ms 就能烧掉 500m 窗口预算，而一分钟平均看起来只有 16%——"图上没打满"与"没有节流"是两件事。

**节流不杀进程，只冻结线程。** 超配额时内核不会 OOMKill，只是把可运行线程推迟到下一个周期；表现是**周期性抖动**、P99 飙升、GC 变慢、健康检查超时。JVM 尤其敏感：2026-08-21 的一则 EKS 排查里，Kotlin/Spring Boot 服务把 requests/limits 调到 3000m 仍只是缓解，新 Pod 承接流量后延迟从 7–20ms 飙到 300–400ms，持续 2–3 分钟。

**CPU request 与 limit 是两种承诺。** request 影响调度权重与最低保障，limit 是硬上限；burst 高于 request 的部分是"机会性"的，永远不保证。把 request 设成"能启动的最小值"、把 limit 当成"够用"，等于让服务在基线附近持续踩线。

**多层级联让根因难定位。** 父 cgroup 的配额、子容器的 limit、QoS 类的 pod 配额、节点上的系统预留，任何一层都可能触发节流；`cpu.stat` 里的 `nr_throttled`/`throttled_usec` 是合并结果，不能直接归因到某一层。

**监控指标错位。** 需要的是 `container_cpu_cfs_throttled_periods_total`（被节流的周期占比）、`container_cpu_cfs_throttled_seconds_total`（被推迟的时间），以及按 Pod 的 throttling ratio；CPU 平均利用率只能回答"用了多少"，不能回答"被掐了多久"。

**配额不是"排队"，是"冻结"。** 与内存不同，CPU 是压缩性资源：超内存会被 OOMKill，超 CPU 只是让线程在下个周期继续。这意味着节流不会留下崩溃日志，也不会触发重启计数；它只把延迟分布改写成双峰——正常请求与被推迟的请求混在一起，p50 可能完全正常。

## 三、技术竞争力

| 方案/平台 | 节流语义 | 可见性 | 缓解手段 | 主要盲区 |
|---|---|---|---|---|
| Kubernetes（CFS） | 100ms 周期硬配额 | cAdvisor 指标 | 去 limit/提 request/Guaranteed | 多层合并难归因 |
| cgroup v2 | 层级独立计费 | cpu.stat | 调 cpu.max/权重 | 需逐层排查 |
| 在线分池（独占核） | 无 CFS 配额 | 低 | Static/Guaranteed | 成本更高 |
| 离线批处理 | Limit 防吵闹 | 中 | 分池/优先级 | 长尾不影响在线 |
| 托管 K8s（TKE/EKS） | 默认继承上游 | 平台指标 | 参数可调 | 默认值未必适合 |
| 监控平台 | 只展示平均 | 强弱不一 | 告警 | throttling 指标常缺 |

**判读**：这张表最容易被忽略的是"可见性"——多数团队有 CPU 利用率面板，没有 throttling 面板；而节流恰恰是平均值看不见的那一类故障。

**本期反转**：我们一直把 CPU Limit 当"防坏邻居"的保险，把利用率当"够不够用"的证据。实际上 Limit 是**把时间切成 100ms 预算**：它不关心你平均用了多少，只关心这一周期有没有超；它不杀你，只让你周期性停摆。利用率没打满还会被掐，不是异常，是这套机制的正常工作方式，也是长尾延迟最隐蔽的来源之一。

## 四、技术挑战

**挑战一：平均值掩盖周期事件。** 监控采样与 CFS 周期不同频，抖动在图上被抹平；必须用 throttled_periods 而不是 CPU 平均。

**挑战二：多层配额合并。** 父层、子层、QoS、节点预留都可能触发；`cpu.stat` 只给合并结果，归因要逐层读 `cpu.max`。

**挑战三：request 与 limit 的错配。** request 太低会让 Pod 被调度到已经紧张的节点，limit 太低会让它在基线附近持续踩线；两者要分别按"基线性能"与"峰值容忍"来定。

**挑战四：JVM/GC 的放大。** 节流拖慢 GC 线程，GC 变慢又拉长暂停，暂停又让请求堆积；同一个配额在 JVM 上的表现比在 Go 上更差。

**挑战五：在线/离线混部。** 同一节点上离线批处理的 burst 会挤压在线服务的可用配额；不分池时，limit 只是把冲突从"抢 CPU"变成"轮流被掐"。

**挑战六：扩容也会被节流拖慢。** HPA 按 CPU 利用率扩容，而节流让利用率看起来不高——被掐的进程没机会把 CPU 用满，指标因此低估真实需求；扩容决策与节流指标脱钩，形成"越掐越不扩、越不扩越掐"的循环。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①按 Pod 的 throttling ratio 与 throttled seconds；②多层 `cpu.max` 清单与归因；③request/limit 的基线校准（按 P95 用量而非启动最小值）；④在线/离线分池与 Guaranteed 策略；⑤节流相关的 SLO（throttled periods < X%）。

**用户旅程**：值班看到某服务 P99 周期性飙到 400ms，CPU 平均只有 30% → 查 `container_cpu_cfs_throttled_periods_total`，发现 40% 的周期被节流 → 读容器 `cpu.max`，limit 500m、周期 100ms，单请求峰值需 80ms CPU → 结论：limit 太低而非节点不够 → 先提 request 到基线、去掉 limit 或改 Guaranteed → 观察一周 throttling ratio 降到 1% 以下。

**90 天实现方案**：0–30 天，接入 throttling ratio/throttled seconds 指标并按服务排名；31–60 天，按 P95 用量重定 request，在线服务评估去 limit 或 Guaranteed，离线单独分池；61–90 天，设"throttled periods > 5%"告警，做一次"节点空闲但容器被掐"的演练，验证监控能定位到 cgroup 层。

**第 274 个市场空白（五项）**：按 Pod 的节流画像；多层配额归因；request/limit 基线校准；在线/离线分池；节流 SLO。

**`throttle.*`／`cfs_quota.*` 第 241 次无人提字段族**：所有平台都报"CPU 用了多少"，没有一个字段报"这一分钟里有多少个 100ms 周期被掐、每个周期被掐了多久、是哪一层配额触发的"。

**本地 173／173-kb 连续第 229 期成组启用（赵恒 25：CPU Limit 不是保险丝，是秒表；它不问你平均跑了多少，只问这一周期有没有超）。**
