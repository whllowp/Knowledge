# AI-SRE 技术洞察（第 293 期）

**生成时间**：2026-11-20 02:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-20
**本期主题**：缓存越权面／共享缓存与租户边界——命中率是省钱的指标，也是泄漏的指示器

## 题眼

2026-09-24，LiteLLM 修复了一个语义缓存层的租户隔离绕过（CVE-2026-89032）：`_get_semantic_cache_tenant_scope()` 与 `_get_metadata_variable_name()` 对元数据键的取法不一致，持有合法虚拟键的租户只要提交语义相似的提示，就能在 `/v1/responses`、`/bedrock/*` 等路由上读到**别的租户**缓存下来的回答——里面可能有 PII、财务数据或源码；更严重的是，Agent 前端会把缓存里的 `function_call`／`tool_calls` **以受害者的凭据自动执行**（CVSS 4.0 高）。2026-11-01，云安全联盟的一份研究笔记记录了 SGLang 的两条跨租户 KV 缓存暴露路径：两者都返回**格式正确、状态成功**的响应，其中 RDMA 竞态“不留取证痕迹”；Cloudflare 那次暴露的前提是缓存池小于上下文窗口——而权重、量化、并行度、显存设置一变，这个前提就变。2026-11-14 的论文把这件事推到理论层：只要一个租户能从共享内容中获益，这个获益本身就是信号；要让租户“分不清两个世界”，就必须限制速率与时机；零泄漏时，节省全部留在提供方手里（arXiv 2611.20291）。

命中率是共享度的度量。我们一直用它证明省钱，却不用它证明“共享了什么”。

## 一、发展趋势

1. **缓存从“性能细节”变成“租户边界”**。CSA 的结论很直接：KV 缓存隔离应当被当作与存储、网络同级的租户边界，而不是推理引擎的内部优化。

2. **节省与隔离在理论上冲突**。跨租户复用前缀能省钱，但复用越多，租户能观测到的“别人写过什么”的痕迹越多；论文证明，若要完全隐藏，提供方必须牺牲租户侧的收益（2611.20291）。

3. **失败是静默的**。SGLang 的两条路径都返回成功响应，竞态无日志；LiteLLM 的越权读取在应用层看是一次正常的缓存命中；缓存命中率仪表不会因为“命中了别人的内容”而变化。

4. **缓存开始承载动作**。语义缓存不只缓存文本，还缓存 `tool_calls`；Agent 前端若按缓存内容直接执行，一次命中就变成一次以受害者身份发生的工具调用。

## 二、技术现状

**第一层：键的构造决定边界。** 前缀缓存通常按 token 前缀哈希命中，语义缓存按向量相似度命中；两者都可能不带租户维度，或带了但取法不一致（LiteLLM 的 CVE 正是两个函数取键不一致）。键错一位，边界就没了。

**第二层：即使键正确，时序也会泄漏。** 共享前缀让后来的请求更快；快多少，就是“别人是否写过这段”的信号。论文指出经典防护要么让租户得不到收益，要么在边界或释放时刻不精确时从时序泄漏（例如 GPU 空闲后的加速步）。

**第三层：KV 缓存的边界是配置的函数。** CSA 记录的前提“池小于上下文窗口”会随权重、量化、并行度、显存设置变化；这意味着一次通过的安全测试，在下一次调参后可能不再成立。

**第四层：测试很难发现。** 两条 SGLang 路径都返回格式正确、状态成功的响应；常规功能测试看到的是“正常”，只有专门的跨租户探针才能看到“内容来自别人”。

**第五层：命中率与正确性指标分离。** 平台报 hit rate、节省 token、TTFT 改善；不报“命中内容的属主”“跨租户命中比例”“命中后执行了谁的动作”。于是 SRE 的仪表全绿，安全的事件为零。

## 三、技术竞争力

| 方案／机制 | 缓存粒度 | 租户维度 | 隔离验证 | 命中内容可归因 | 命中即执行防护 | 泄漏可取证 |
|---|---|---|---|---|---|---|
| 前缀缓存（vLLM/SGLang） | token 前缀 | 视部署 | 无标准 | 无 | 无 | 竞态无痕 |
| 语义缓存（LiteLLM 等） | 向量相似 | 元数据键 | CVE 后修复 | 弱 | 无 | 日志可查 |
| 应用层响应缓存 | 请求键 | 通常有 | 有测试 | 中 | 无 | 有 |
| 向量库检索缓存 | 查询向量 | 视实现 | 弱 | 弱 | 不适用 | 弱 |
| 嵌入缓存 | 文本哈希 | 常无 | 无 | 无 | 不适用 | 无 |
| 网关/CDN 缓存 | URL/头 | 视配置 | 有 | 弱 | 不适用 | 有 |
| 命中率仪表 | 聚合 | 无 | 无 | 无 | 无 | 无 |

**判读**：每家都能回答“命中率多少、省了多少 token、TTFT 改善多少”。没有一家能回答“**这次命中读的是谁写的内容、跨了哪个租户、命中的提速是否可被其他租户观测、以及命中后执行的是谁的动作**”。而在越权与合规里，要的正是后者。

**本期反转**：缓存一直被当作“读优化”——同样的内容不重复计算。实际上缓存是**写的回放**：命中意味着你读到了别人（或别的租户）写下的内容，甚至执行了别人写下的动作。命中率越高，系统越“共享”；共享度既是省钱指标，也是暴露面指标。**不能同时证明“省了”和“没串”的命中率，只是一个好看的数字。**

**判词**：「缓存库／向量库／语义缓存／KV 复用／前缀缓存／网关缓存／命中率仪表」全部可采购，「这次命中是谁写的内容、跨了哪个租户、提速是否可被他人观测、命中后执行了谁的动作、泄漏发生在哪一层」不可采购。

## 四、技术挑战

1. **键的一致性**：多函数、多路由取租户键的方式必须统一，否则一处错位全局失效。
2. **时序侧信道**：命中带来的加速本身就是信息，限速会侵蚀收益。
3. **配置耦合**：KV 隔离依赖池大小、量化、并行度，调参即改变安全前提。
4. **静默成功**：越权读取与竞态都返回成功响应，功能测试看不见。
5. **动作缓存**：缓存的工具调用若被自动执行，命中变成提权。
6. **指标缺维**：命中率不携带属主与租户维度，无法用于审计。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 缓存键规范：所有缓存层必须显式携带 tenant_id 与内容属主，键构造集中到单一函数。
- D2 跨租户命中探针：以租户 A 写入、租户 B 读取，断言不可见，并纳入回归。
- D3 时序泄漏评估：测量“命中 vs 未命中”的延迟差，判断该差值是否可被外部观测。
- D4 动作缓存隔离：`tool_calls` 缓存必须绑定原租户与原授权，禁止跨主体回放。
- D5 指标加维：命中率按租户、按内容属主、按跨租户命中拆分；跨租户命中单独告警。
- D6 配置基线：把池大小、量化、并行度纳入缓存隔离的安全基线，变更即复测。

**用户旅程（一次“命中别人的回答”的事故）**

① 租户 A 的客服 Agent 缓存了一条含 PII 的回答；② 租户 B 提交语义相似问题，语义缓存按向量命中，返回 A 的回答（D1/D2 缺失）；③ B 的前端看到 `tool_calls`，按当前凭据执行了本该属于 A 的动作（D4 缺失）；④ 命中率仪表显示“节省 18%”，无人察觉异常（D5 缺失）；⑤ 一周后运维调小缓存池，KV 路径的隔离前提被打破，重新暴露（D6 缺失）；⑥ 事件被发现时，日志里只有“cache hit”，没有“谁的内容”。

**90 天实现方案**

- **第 1–30 天**：统一缓存键与属主字段，收敛到单一构造函数（D1）；建立跨租户命中探针并接入 CI（D2）。
- **第 31–60 天**：测量并限制时序差（D3）；禁止 `tool_calls` 跨主体回放，缓存条目绑定授权（D4）。
- **第 61–90 天**：命中率加维与跨租户告警（D5）；把缓存池/量化/并行度写入安全基线，变更自动复测（D6）。

**第 205 个市场空白（五项）**：① 缓存键的租户与属主规范；② 跨租户命中探针标准；③ 命中时序泄漏的评估方法；④ 动作缓存的授权绑定模型；⑤ 跨租户命中率指标与告警口径。

**`cache_scope.*`／`tenant_hit.*` 第 172 次无人提字段族**：文档谈“如何开缓存、命中率多高”，不谈“命中的内容属于谁、跨没跨租户、提速能不能被看见”。

**本地 173／173-kb 连续第 160 期成组启用（何伟 02：缓存命中要能回答“这是谁写的”）**：本地原型给每个缓存条目写 `cache_entry{key_hash, tenant_id, owner_id, content_type, created_at, auth_scope}`，命中时同时落 `cache_hit{entry_id, reader_tenant, latency_gain_ms}`；跨租户命中触发“缓存越界”事件；`tool_calls` 条目只允许同租户同授权回放。
