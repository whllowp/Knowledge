# AI-SRE 技术洞察 第 319 期

**生成时间**：2026-11-25 07:00（bash `date` 取值）
**主线**：判定函数面／谁定义"失败"——Agent SLO 里的 `evaluate_outcome()` 没有验收，"99.9% 达标"和"用户还在骂"可以同时为真（Failure-Definition Integrity / The Unverified SLI Contract）

**题眼**：过去十四期我们追问"证据能不能被举证"，本期退到更前面一步：**证据到了、结论也出了，可"这次到底算不算失败"这件事，是由一段藏在应用代码里、没有版本、没有验收、没有分母的函数判定的**。行业把 SLO 与错误预算从微服务搬进 Agent（Grafana 行为 SLO、任务完成率 ≥95%、四层 SLI、Google SRE 第二版），却没人给"判定什么算失败"的那一层发验收证。看得见"达标率 99.9%"≠看得见"这个 99.9% 是同一把尺子在量，而且量的正是用户感受到的失败"。

---

## 一、发展趋势

三条趋势在本期交汇。

**其一，SLO 从"系统可用性"扩到"行为正确性"。** Grafana Labs 把幻觉、任务完成、毒性、PII、提示词注入、成本分别做成 SLI，以 30 天 95% 为目标、5% 为错误预算，明确拒绝合成"Agent 质量总分"——Agent 可以有据可依但烧钱、有帮助但偶尔有毒、准确但慢[11][12]。CSDN 清单给出初值：可用性 ≥99.5%、P95 ≤8s、任务完成率 ≥95%，并强调"不要一上来设 99.99%"——设成 100% 等于放弃"何时可以冒险发布"的判断依据[13]。zicode 主张四层 SLI，并给出关键改动：**状态页出现 degraded 就按权重扣预算，哪怕端点全部返回 200**，把激励从"别中断"改成"别降级"[14]。

**其二，判定权正从代码搬到平台，但判定标准仍需人来写。** Anthropic 与 Databricks 11 月 3–4 日把 Claude 原生 OTel trace 接入 MLflow：Issue Detection 为反复出现的失败模式建 scorer、用近期 trace 建基线、对新 trace 抽样打分；Review Queues 让领域专家写期望答案[5][16]。报道逐字点出边界：**"团队仍然要决定哪一种行为算失败"**[5]。这不是缺陷，而是趋势本身——证据采集平台化后，稀缺品正是判定标准。

**其三，"用户侧结果"开始顶替"状态码"成为分母。** Mastering Observability 11 月 13 日在拆解 Google 伦敦区故障后给出两条纪律：记录 outcome 而非 status code——200 只证明调用被接受，不证明返回可用；并从用户所在位置而非自家数据中心内跑检查[2]。zicode 提出用户侧黑盒探针 + 双口径对账（状态页、自有探针、自有预算同板），差异超阈值即切换[14]。《SRE》第二版亦承认：模型在服务正常时自信地给出错误答案，可用性指标识别不了[1]。

## 二、技术现状

**判定函数的四种典型失效，行业都见过，但没人把它们当一类问题管。** 工程实践总结得很直白[10]：一是**永不响**——成功定义过宽（"Agent 返回了任意字符串"），SLI 长期停在 100%，用户持续投诉而错误预算纹丝不动；二是**总在响**——要求精确匹配预期输出，非确定性 Agent 天天失败，告警一天内就被静音；三是**重试污染**——第三次才成功算不算成功？任务级成功与尝试级成功混算；四是**评委漂移**——用 LLM 当裁判时，裁判模型升级会让测得的成功率在无任何 Agent 变更的情况下移动，正确做法是把 evaluator 版本钉住、把它的变更当作 SLO 变更重新定基线。同一来源还给了最小自检：合成已知好/已知坏的 trace 走真实插桩，断言 `sum(agent_task_success_total)` 等于合成成功数——这能抓到"判定函数对了、但 early-return 路径上 `record_outcome` 从没被调用"这类分母造假[10]。

**判定覆盖率与判定边界是两件事。** 本期与第 98 期（一半 episode 没打分）划界：98 期管"判了多少"，本期管"按什么判"。第 176 期把决策质量立成新 SLO 基元（量什么），本期再退一步：量出来的数，分子由一个布尔函数决定，而这个函数通常比它所判定的系统更少被测试。`evaluate_outcome(trace) -> {success, tool_calls_valid, terminated_cleanly}` 被建议写成"契约本身"[10]——但契约目前无人验收。

**厂商现状一句话概括：判定证据越来越丰富，判定函数的可审计性几乎为零。** Google 把真实事故因果分析交给 Gemini CLI、约三成案例 Agent 独立解决且人只收到知会[1]；Cloud Assist 用 MCP 同读日志与源码、建议加 `token_threshold` 并自动部署[4]；Anthropic 的 OTel 导出可进 MLflow 做 scorer 与基线；OpenAI Control Room 在推理层做 job_id 授权与 35 秒停输出、不可用时 fail-closed[7][8]；腾讯云 CloudQ 以全景图谱支撑"AI 调用 AI"、可观测把用量/性能/Token/工具调用与任务质量关联，信通院六维标准提"结果可评价"[15]；火山智能运维助手在推理外加 RCA Harness、输出"步骤可复核、结论有置信度"并支持关键节点人工确认[18]。

## 四、技术挑战

**挑战一：判定函数的正确性无法从判定结果反推。** 永不响与总在响两个极端都能产出"稳定的指标曲线"——前者平，后者被静音后也平。它们不触发事故，只会让用户投诉与仪表盘的落差越来越大。这与第 285 期（健康系统被误报事故）构成正反两侧：285 问"没事会不会报出事"，本期问"有事会不会被判成没事"。

**挑战二：判定器与被判定者共域。** 裁判是另一个 LLM、与被测 Agent 共用提示词工程甚至同一模型家族时，"评测共谋"与"换模型即漂移"同时成立[9][10]。第 114 期立过"计价器长在被测系统里"，本期是同一结构在判定层的复现：判据写在被测应用代码里，`record_outcome` 与被测逻辑一起 early-return。

**挑战三：判定口径没有版本，跨版本分数不可比。** 第 156 期已立 `bench.provenance.*`（分数是模型×harness×工具权限×评分规则×评分器版本的函数）；生产 SLO 缺的正是同一件事——评分器升级后成功率移动，团队当成"Agent 变差"去回滚，真正变化的是尺子[10]。处方是把 evaluator 变更视为 SLO 变更、显式重定基线[10]；本期把这条从评测期前移到运行期。

**挑战四：状态成功、结果可用、用户可感三层被压成一层。** Google 伦敦区故障里，控制器整晚有传感器、有信号、有规则，只是规则指向一条仍带电的线[2]；对应 Agent SLO，就是"200 + span 全绿 + 评分器判成功"同时发生，而用户拿到的答案不可用。Anthropic 亦指出：看起来合理的答案可能漏掉决定性来源，执行记录只是让诊断有具体对象[5]。

**挑战五：预算耗尽后的行为没有纪律。** Grafana 设想预算宽裕时改 prompt/模型、见底时转向质量[11][12]；但没有一家把"判定函数可疑"列为停止发布条件——预算耗尽一律解释成 Agent 变差，而不是尺子坏了。

## 五、展望与建议

**提出第 240 个空白字段族 `failure.definition.*`（本期归纳，缺省 `FAILURE_DEFINITION_UNVERIFIED`）**，建议至少十字段：`definition_id`（判定函数版本与哈希）、`outcome_basis ∈ HTTP_STATUS|SPAN_GREEN|RUBRIC|USER_OBSERVABLE|HYBRID`、`predicate_version` + `evaluator.model_version` + `evaluator.rebaseline_at`、`denominator{scored, total, unscored_reason}`、`retry_accounting ∈ ATTEMPT|TASK`、`degraded_minutes.counted_in_budget`、`sli.fires ∈ NEVER|NORMAL|ALWAYS|MUTED`、`probe{known_good,known_bad,last_run_at,through_real_instrumentation}`、`independent_verified_by`（≠ 判定函数作者）、`verdict ∈ CONTRACT_VALIDATED|NEVER_FIRES|ALWAYS_FIRES|EVALUATOR_DRIFT|UNVERIFIED`。

**四条最小动作**：① 把 `evaluate_outcome()` 当契约验收——CI 中合成好/坏 trace 走真实插桩并断言计数器，专抓 early-return 漏记账；② 判定口径变更（评分类别、裁判模型、重试与降级分钟口径）一律视为 SLO 变更，重定基线并留旧口径对照；③ 每次失败判定附一行"依据哪一层：状态码/span/rubric/用户可感结果"，禁把 200 当结果；④ 判定函数作者不得是唯一验收者，复用第 292 期"判据长在 Agent 够不到处"原则。

**评测采购两问**：这个成功率的分子由哪个函数判出、能不能导出它的版本与分母？裁判模型升级后系统会不会自动重定基线、还是把漂移当成 Agent 回归？**评测改造**：给长事故题加"回答合理但漏掉决定性来源"与"200 但结果不可用"两类配对题，同时报判定一致率与"用户可感失败被判成功"的漏判率；沿用第 310–318 的叠加门禁，`verdict≠CONTRACT_VALIDATED` 的判定不得回写确定知识、不得进自治升档。

**信通院六维建议补一格"判定可举证率"**，与第 316 期"审批可举证率"、第 317 期"执行中授权可举证率"、第 318 期"空窗期可举证率"并列：前几格管"人有没有真的看图签字"，本格管"图上的那个失败到底是谁、按什么、判了多少次算出来的"。

**本地知识积累（第 195 期新角度）**：施宏斌《金融 Agent 开放问题 Eval》过去读作"尺度来自专家经验"，本期首次改读为"判定式本身也要有可验证的持续改进"——专家经验能定义什么叫开放问题，却不能给判定式发免检证；配刘凯宁"结论/证据/待确认项"三分做判定卡骨架、赵恒"状态要有权威来源不能由写入器自报"、何伟"可验证持续改进前提是验证环境可信"；本地 173 按目录级引用。
