# AI-SRE 技术洞察（2026-11-24 06:00）· 第 309 期

## 题眼：入场保真面／Agent 收到的不是事故，而是被压缩过的问题陈述（Intake Fidelity / Problem-Statement Integrity）

ORCA-bench 给出的对照极其刺眼：同一批真实故障，工单描述清楚时前沿 Agent 根因准确率 25.3%，**报告含糊时只剩 10%**，最弱模型 40% 的报告编造根因；而给它一份预关联好的入场简报（症状＋为何关联的线索＋看不见什么），准确率 30.9%→46.2%、token 从 143 万降到 15.4 万（Chiron 自测）。两者共同指向同一件被行业忽略的事：**推理的起点不是遥测，而是遥测被写成"问题"的那一刻**。本期首次把"入场"立为一等对象：与 #49 对抗面（输入是不是指令载体）、#101 线索稀缺面（有没有线索）、#208 遥测供给面（供应商让看什么）、#215 顺从面（人给的暗示弯结论）、#304 调查污染面（查的过程制造伪因果）逐条划界——前五者管"证据是什么/怎么查"，本期管**"事故被翻译成哪一句话交给 Agent，以及这句话是否还能被追溯"**。对两处 index 检索"入场保真/问题陈述/工单描述/原始文本"均无主线命中，确认为全新立面。

## 一、发展趋势

1. **上下文工程从"加"转向"管"**。过去一年主流做法是把更多日志、拓扑、历史工单塞进上下文；近 30 天出现反向证据：Chiron 的流式关联简报以"少而带出处"胜过多而全，腾讯云 AIOps 实战文明确提出"证据不足或冲突时自动重构问题表述并发起新一轮查询"——**问题陈述已被承认为运行时变量，却仍没有版本、没有原文对照、没有审计**。
2. **入场从人工动作变成自动触发**。腾讯云 CloudQ 11-16/17 配置告警命中即自动发起根因分析并推送 IM；字节 AgentKit 响应计划"告警触发后自动取证与根因分析"；Anthropic Claude Tag 指南描述 Agent "reads each alert or ticket as it lands"。入口越快，入口错误的复制速度越快。
3. **标准层仍无位置**。OTel GenAI 有 `gen_ai.input.messages`（opt-in）、`input.messages_ref`、`conversation.id`、`invoke_agent` span，却没有 `alert.id`／`incident.id`／问题陈述版本；规范仍为 Development、独立仓 11-05 时 79 条未发布变更中 17 条破坏性。**行业能追踪模型调用了什么，不能追踪事故是怎么被递到模型面前的**。

## 二、技术现状

入场材料实际经过四次有损变换：**字段化**（告警规则把现象压成 service/指标/阈值）、**摘要化**（IM 转发、工单模板、LLM 摘要丢掉未写入字段的细节）、**归一化**（把"买东西卡住"翻译成服务名与指标名）、**时序压缩**（事件发生时间写成观测时间，与 #303 的时间戳问题同源）。四次变换任何一次错位，后面推理再严谨也是在解另一道题。

各家已各自摸到这个问题的一部分。Google Cloud 11 月发布的自有故障六阶段手册把 P1 报障必填项写得很实：项目 ID、区域/可用区、**带时区的时刻**、错误串或日志片段、影响范围；并要求先看 Personalized Service Health 判定"是 Google 坏了还是你坏了"——这是把入场表单一等公民化，但第一个诚实信号落在供应商认证控制台里。Google 内部 Gemini 四步法（11-18 二手报道）先把截图与工单灌进 Sheet 对齐错误码，再从**已关闭工单的解决备注**中排序修复步骤并写手册：入场语料天然偏向"以前修好过的那类故障"。

Anthropic 的两条 11-12 动态形成互补：Claude Tag 的 on-call 模式被要求"缺细节就问，不要猜"、来源冲突时查代码并标出过期文档；自托管 Managed Agents 把会话历史放进客户数据库、工具调用与结果经 OTel 导出——**原文留在带外**具备了工程条件，但 OTel GenAI 的默认 opt-in 意味着多数团队仍然只留元数据。OpenAI Control Room（11-09）则暴露另一半：9 月事故中监控器 10:02 报高级告警、人 3 分钟确认，运行却到 12:34 才被手动终止；系统把"停止决定→切断模型输出"压到 35 秒，**"告警→决定"这两小时半仍无结构化入场记录**。

**判读**：自动触发、上下文简报、引用式因果链、工具钉时刻、Trace 回流各有一家在做；**"原始入场文本＋四次变换链＋对象/时间对账＋未来信息旗标"可导出成同一份证据，全表无人填满**。新观点：看得见"Agent 从告警开始调查"≠看得见"它开始调查时手里那句话还等于现场"。

## 四、技术挑战

- **双向失真**：入场既丢信息（摘要压缩），也会夹带未来信息。SRE-1 从 1663 个候选事故里剔除 63 个"答案泄漏"样本——若 Agent 入场材料含事故后才写的提交说明或复盘，等于开卷考试；Google 内部四步法又主动从关闭工单备注取先验，两者方向相反。
- **改写无痕**：问题陈述在 ReAct 循环里被反复重写，原始工单与最终 hypothesis 之间缺少 diff；于是"查得越多越像对的"（#304）从调查阶段提前到入场阶段。
- **隐私与可追溯冲突**：OTel GenAI 默认不记 prompt/工具内容，只有 ref；把原文留在带外是正解，但 ref 失效就等于入口丢失。
- **评测装置**：ITBench-AA 用准备好的快照、ORCA 用真实模糊工单、SRE-1 用 49 起自选自评案例，三者不可相减；"报告质量"这一自变量在多数榜单里根本没被分层。

## 五、展望与建议

提出第 230 个字段族 `intake.fidelity.*`：`raw_intake_ref`（原文/截图/告警 JSON 带外引用＋hash）、`intake_source∈ALERT|TICKET|HUMAN_CHAT|SUMMARY|STATUS_PAGE`、`transform_chain[]{transformer_id,version,digest}`、`fields_dropped[]`、`problem_statement_version`、`statement_rewrites[]{who,why,before,after}`、`object_time_alignment{alert_object,analysis_object,event_at,observed_at}`、`future_info_flags[]`、`blind_spots[]`、`verdict∈FIDELITY_OK|COMPRESSED|BIASED|LEAKED|UNVERIFIED`，缺省 `INTAKE_UNVERIFIED`。

具体动作：① 告警与工单模板强制最小入场六字段（原文引用、对象、时间窗、业务影响、已知变更、看不见的面），沿用 Google P1 必填项；② 把腾讯云"对象一致/时间一致/依据充分"三问做成自动对账器，任一不吻合即补现场信息重判而非继续推理；③ 每次问题陈述改写留 diff 并回引原文哈希，禁止静默覆盖；④ 工具与文档按告警时刻快照，事后复盘/提交说明隔离，报 `future_info_flags`；⑤ 评测新增同一故障的"清楚/含糊/摘要/带事后文档"四版配对题，报准确率差、幻觉率与 leakage 率；⑥ 采购三问：能否导出原始入场文本、全部变换步骤与对象时间对账结果？改写是否可回溯？含糊报告下准确率掉多少？⑦ 信通院成本效益维度补"入场可举证率"一格，成十六层治理。

本地知识源（173 目录）本期首次重读吴垚《从接住告警到自我进化：快手智能运维助手实践》："接住"那一瞬决定了后续全部推理的起点；配周昕毅"关键决策前先有关键信号"、刘凯宁三分法扩第二十分"原始入场材料与问题陈述是否逐字留存"、蒋烁淼"秒查的前提是入场对象对"。
