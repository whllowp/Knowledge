# AI-SRE 技术洞察 第 289 期（2026-11-18 20:00）

## 分工面：确定性规则与 LLM 的职责边界（Deterministic–Probabilistic Division of Labor）

> **题眼**：一条运维流水线至少有六个可分工节点——归因、检测、根因推理、修复生成、审批、验证。2026 年的行业叙事是"全程 Agent 驱动、端到端自治"，但一线真正跑通的系统反而在做相反的事：把能规则化的步骤锁死成毫秒级确定性代码，只把开放集推理留给 LLM。分工对错的两种错误都是静默的——**把确定性问题交给 LLM，得到"能跑但会幻觉"；把概率问题固化成规则，得到"稳定但漏诊"**。谁划下这条线、模型换版后有没有复核，当前无人举证。这是本期首次立为一等对象的"分工面"，与第 159 期（推理-执行分离的执行点护栏）、第 163 期（经济性护栏）、第 288 期（多智能体目标冲突）严格划界：前两者管单点与成本，后者管"谁的目标算数"，本期只问一件事——**这一步，到底该由谁做？**

---

## 一、发展趋势

2026 年 11 月，Agentic Ops 的分工形态出现三股清晰支流。

**其一，"确定性优先"从经验默契上升为显式工程设计。** 腾讯云一线告警治理实践给出了本期最锋利的证据：告警归因明确"不用 LLM"——栈帧解析、文件定位、git blame 全是确定性规则，毫秒级、零幻觉、不花 token，LLM 只留给它擅长的事（读代码做根因分析）；并采用双通道分层，重分析走 Coding Agent，轻任务（分类、手册归纳、话术抽取）走轻量模型的结构化输出。另一篇腾讯云工程文章把边界写得更直白：持续性过滤本质是低通滤波器，把召回让渡给精确率以换取自愈管道不被噪声淹没；执行层按读操作自动、低风险写护栏内闭环、标准修复限变更窗口并强制人工审批、高风险默认禁止自治。"模型可以犯错，但系统必须在模型犯错时仍然安全"——这句话的前提正是分工边界被显式写在架构里。

**其二，平台开始把概率能力封装进确定性接口。** Google 在 11 月 12 日把 Gemini 支持的分类与结构化抽取做成 AlloyDB 的 SQL 函数（`ai.classify`、`ai.extract`，PostgreSQL 18 预览）——调用方看到的是确定性函数签名，模型的不确定性被藏在接口背后。同月 Google 为 BigQuery/Looker 增加跨自研与 ADK/LangGraph 第三方 Agent 的可观测与评测，遥测写入客户自有表；Gemini for healthcare 则内置每 Agent 身份、继承式 RBAC 与中央策略。这是分工的一种成熟形态：**把 LLM 约束在可审计的函数/身份边界内，而不是让它自由漫游整条流水线**。

**其三，多 Agent 编成成为发布页标配，但编成即分工。** 微软 11 月 17 日 GA 的 Perception 把安全运维拆成红（评估弱点）、蓝（分诊调查）、绿（优先级与响应协调）三支 Agent 团队，用 playbook 在团队间传递证据与建议，高危动作强制人工审批，约八百万条 Defender 告警样本中 80% 落在分诊 Agent 覆盖内（该数字是覆盖份额，非准确率）。OpenAI 11 月 10 日部署的"控制室"则展示了另一种分工：任务需先申请唯一 ID 并附着到推理请求，引擎每次咨询控制室才能输出，停止指令经缓存层最长 35 秒生效——**"能否继续输出"被从模型自身剥离，做成外部确定性门**。阿里 STAROps 的升级同样以分工叙事展开：人设目标、边界与关键决策，Agent 承担数据查询、证据收集、调查分析与处理跟进。

## 二、技术现状

把上述动态按流水线节点铺开，可以看到一张尚未被任何平台完整交付的分工地图。

**归因与检测层，确定性几乎全面胜出。** 栈帧解析、git blame、配置规格比对（华苏科技案例中智能体登录官网确认型号最高支持 64G 内存）都是可判定、可复现、零 token 的操作。腾讯云的兜底链设计——blame 失败依次退回日志文本 grep、历史处理人、当日值班表、兜底处理人——本质是"确定性规则优先、逐级降级、保证每条告警落到人"的分工梯度。相反，把这一层交给 LLM，既引入幻觉又消耗预算，且失败不可预测。

**根因推理层，是 LLM 的真正战场，但边界在收缩。** 静态因果图在滚动更新与金丝雀发布中迅速过时，会把根因误判给下游症状最明显的服务；2026 年前沿转向状态化、动态图的因果发现——TopoEvo 用拓扑约束的多智能体"假设-证据-测试"工作流分离初始异常与级联症状，StaR 用时序图网络替代静态格兰杰因果。这些工作的共同结论是：RCA 可靠性不取决于模型规模，而取决于是否承认拓扑流动、故障有记忆。也就是说，即便在 LLM 主场，真正起决定作用的仍是拓扑约束这类**结构性先验**。

**审批与验证层，正在被做成独立控制面。** 观测云 AI Agent Teams 把写操作交给独立受控 MCP，只开放白名单动作，并施加 Namespace、RBAC、审批口令与非生产环境限制；执行后 Agent 继续检查接口、Pod、发布状态与错误率。源码侧由 Codex/Claude Code 理解代码、RCA Agent 查询真实日志，形成"代码推理 Agent 与生产证据 Agent 分工"；微软 Perception 更把高危动作的审批权保留给人。OpenAI 的控制室则把"停止权"外包给中央服务。分工的粒度，正从"哪个 Agent 做"细化到"哪类动作归哪个执行主体"。

**值得注意的反例是字节。** 飞书 8.0 与豆包工作伙伴主打"AI 持有状态"——豆包主动巡视群聊、判断工期、沉淀选题并排期提醒；字节在 Agent Runtime 岗位描述中强调分级自治（人工确认→半自动→全自动）。这是把 LLM 推向"持状态、做协调"的概率侧极端，与腾讯云"归因不用 LLM"的确定性侧克制形成鲜明对照——恰说明**分工线划在哪里，是当前行业最大的未收敛分歧**。

## 三、技术竞争力：主要厂商／方案分工边界对比

两列"分工可导出""边界换版可复核"几乎全空——平台能买到 Agent 编成、受控执行与分级自治，买不到一张声明"哪步是规则、哪步是模型、谁划的线、换模型后是否重审"的清单。

## 四、技术挑战

**分工错误是静默失败。** 把确定性问题交给 LLM，系统照常运行、只是偶尔幻觉；把概率问题固化成规则，系统稳定漏诊。两类错误都不会触发"分工错了"的告警，只会以"效果不好"的面目弥散在指标里。这正是分工面与第 285 期（健康态误诊）的根本区别：后者问"该不该动手"，前者问"该谁动手"。

**边界无人署名，且会漂移。** 分工线往往藏在 prompt 与配置组合里，不是一等配置项。模型换版后，原本必须 LLM 的步骤可能已被小模型结构化输出稳定替代，原本规则化的步骤可能因新故障类型失效需要 LLM 接管——边界漂移无人复核。第 165 期本地讲义中，何伟《Harness For Hybrid Coding》的"生成与验证分离"提供了最可迁移的形态：把 LLM 输出交给版本化、可验收的确定性 harness；周昕毅《AI + SRE ≠ AISRE》则强调人做关键决策。二者的共同点是**分工被写成契约，而非留在默会经验里**。

**评测基准测不到分工。** 现有基准只评端到端答案对错，不评"这一步选择执行主体是否恰当"。一个全程 LLM 的系统若碰巧答对，与正确分流的系统得分相同，掩盖了分工质量的差异。这是继第 218 期（榜单可比性）之后，评测维度的又一处系统性空缺。

## 五、展望与建议

1. **确立第 158 字段族 `execution.division.*`**：`deterministic_steps[]`、`llm_steps[]`、`assignment_owner`、`assignment_rationale`、`division_reviewed_at`；缺省 `DIVISION_UNVERIFIED`，未举证分工的自治流程不得进入高等级授权。
2. **默认"能规则化就不 LLM"**：流水线每步标注 executor_kind（rule/llm/human），清单随每次发布导出；LLM 只接开放集推理，确定性可判定步骤锁死为代码。
3. **双通道成本—能力模型**：重分析走 Coding Agent，轻分类/归纳走轻量模型结构化输出；既降本又让轻任务结果更稳。
4. **分工复核触发器**：模型换版、新增故障类型、规则命中率跌破阈值时强制重审边界，并留 `division_reviewed_at` 时间戳。
5. **评测增"分工正确性"维度**：在 SRE-bench/ITBench 类基准中，除端到端答案外，标注每步期望执行主体，单独计分。
6. **信通院六维补「分工可举证率」格**：与第 288 期「目标可仲裁率」并列，形成"目标—分工"双层治理。

本期新观点在于把"分工"从设计默契提升为**可举证、可复核、可评测的一等治理对象**：可采购的是编成与自治，不可采购的是那条线的来龙去脉。
