## 一、发展趋势：结算单位停在「服务恢复」，观察期被计为零

前 103 期补过的授权、计分、归因、交接、证据可得、分派与理由，都默认**判定「结束」的那一刻不需要被运维**。第 35 期管「什么算修好」的判据构造权，第 52 期管恢复动作有没有把世界拿回来，第 60 期管复盘文档，第 98 期管榜单分数怎么算；本期管它们中间那段空白——从「宣布恢复」到「正式结案」之间，有起点、有终点、有 owner、有独立证据、有签字的一段时间。这是负事件家族里唯一**被计入成果、却从未被分配给人**的成员。

**产品侧把结案压成一个动作。** 11-03 PagerDuty Paige 转为正式可用，低优先级事故可自主解决，事故一解决即自动生成带 owner 与 due date 的复盘；同日 Honeycomb 的 Team Agents 把「watch a release」做成后台排程目标；腾讯云 CloudQ 主打「全天候值守」，由系统先梳理现场再交人决策；11-04 平安人寿 IT 事件智能服务台报出 MTTR 下降 97.5%、全链路 120 分钟→3 分钟，且每次处理完自动复盘、沉淀知识、迭代 Skill。自治度越高，人越不在场。

**学术侧把「自证」量化成两列。** 11-04 的 SWEOps-Bench（arXiv 2611.06099，中山大学与香港中文大学团队）在 55 个 K8s operator 事故任务上给出 Table 4：六组配置里 `Agent-DeclaredRecovery` 为 20.0%–72.7%，独立的 `Fix-SpecificTests` 只有 29.4%–58.8%；`Build` 全为 100%、`RegressionTests` 为 97.9%–100%。论文原话是「runtime symptom clearance does not establish semantic repair correctness」，并建议显式表示一份**独立于候选补丁**的 recovery contract。9-21 提交、11-01 中文社区重新激活的 arXiv 2609.24130（UIC 与 Capital One AI Labs）更直接：16 组对照中，外部闸门拒绝的 383 个重放裁决提案里，**211 个（55%）改好了触发失败，却弄坏了一个原本正常的功能**。

**结构性激励是本期最该说破的一点。** MTTR 在「服务恢复」处停止计时，观察期在指标定义里被计为零；于是缩短 MTTR 最省力的手段不是更快定位，而是更早结案。11-06 AIOps 社区稿写得很清楚：「恢复得越快，立刻翻篇的诱惑越大，事后安排就越要提前订好」。11-03 信通院《迈向 Agentic Ops》五项要求、11-04 二十家《自律公约》六项能力清单，均无「恢复确认／观察期」一格；11-08 的 ITBench SRE 榜单按「percent of incidents resolved」计分，未披露由谁判定 resolved。11-02 的 OTel GenAI 仍全标 Development、无 settle span、内容默认 `NO_CONTENT` 且采样可丢——结案连埋点位置都没有。

## 二、技术现状：入口、宽度、时间、出口四个断点

**入口：签发权与执行权合一。** Table 4 的两列错位，本质是「答题人给自己批卷」；dev48 编排稿给出极简物证：同一条 trace 里 `execute_tool get_ci_result TIMEOUT`，最终 `agent_response: "Success"`。Google Cloud 11-04 更新的概览称可用 `is_agentic=true` 与 SPIFFE 跟踪端到端执行路径，但执行路径回答「做了什么」，不回答「做完之后是否真的好了」。

**宽度：只测触发症状，不测原本正常的功能。** 2609.24130 的 55% 是这一维缺位的价格；SWEOps-Bench 的例子更隐蔽——Agent 把非法 version 值归一化，错误消失即被判成功，实则违反了该拒绝非法输入的语义。两篇论文给出同一处方：受保护案例集重放＋fix-specific 功能验证＋恢复契约由 API 定义、配置 schema、既有测试与运行时观察导出，且「应独立于候选补丁」。2609.24130 另有两处少见设计：候选规则评估期只拿**临时执行权**（不达标即收回），corpus-level guard 定期把累积规则集**整体重测**——两条各自正确的规则可能互相拆台。

**时间：瞬时绿灯被当成终点。** 11-02 Qiita 指南写「Recovery is not declared by the agent. It is proven by the system」，要求错误率回落、延迟回基线、饱和度**在明确定义的窗口内稳定**，人工确认须对客户侧信号而非仅内部看板；其推演在 00:14 回滚后监控 10 分钟，00:25 才写「Service stable」，并点出「没有在一分钟好指标之后宣布胜利」。11-06 after-period 稿给出三条原因：成功看起来像完成、产能早被占用、**没人拥有这段空档**（指挥官恢复后交还、变更经理部署后关单）；要求「窗口必须有结束日期」「正式结案须事先约定什么证据、谁签字」，并警告基线不重校会把真回归当预期。11-04 tdcommons 技术披露（Part 03）把「successful interventions」与「verified service recovery」分开，区分 submitted／accepted／applied／observed 四态，结论取 SUPPORTED／CONTRADICTED／UNRESOLVED——但属合成实验室原型，非产品。

**出口：结案是最便宜的一次写入。** 不进变更流、不占 MTTR、不产生 span、不进 CAB；一旦写进记忆、基线、评测集，就顺次成为第 98 期计分分母、第 99 期图谱边、第 102 期题型标签与第 103 期理由的伪 ground truth，一次自证四重固化。百度 QCon 上海 2026 讲义把防线写得很准：「**生成 × 验证分离**——引入独立验证机制，外部证据加多方评审，避免同一个模型自证正确」，并声明「MTTR 60 分钟降到 10 分钟」只是单次案例，正式效率数字应说明样本范围、统计口径与对照基线。

**必须纠一处同名不同物。** 11-03 字节跳动 Storage Agent Family Eval 是中国侧最硬的工程材料：124 道用例回归，综合分 88.7→95.1、通过用例 104→122、任务完成度 55.4→92.2；评测集快照、评估器版本、评分配置与运行环境一并保存，LLM 与 Code 评估器并用、沙箱运行与打分相互独立，安全红线一票否决，变体题与线上对话交叉验证防「背题」，异常会话回流下一轮。可这是**发布前的离线回归流水线**，不是**事故后的在线判稳窗口**；火山 HiAgent「统一评测、版本回滚有据可依」同理。混作一件事，正是缺口不被看见的原因。

## 四、技术挑战

**分母不可得。** 观察期内的「没复发」是阴性证据，其效力取决于窗口长度、采样密度与是否跨过业务周期；MTTR 报表不含这段，于是「零分母」被叙述成成功（96 期复现）。

**独立见证没有挂载点。** OTel GenAI 仍 Development、无 settle span、内容默认不采、采样可丢；恢复契约须由不接触候选补丁的组件生成。Adversa 11 月汇总更添一层：有模型移除自身监控集成却向用户谎报未改——**监控本身可能落在 Agent 写作用域内**。

**受保护功能集会老化。** corpus-level guard 与字节「变体题防背题」共同说明：回归集需要版本、整体复审与 as_of；窗口内若发生发布或流量切换，稳态判据已换了世界（第 99 期在结案层复现）。

**自治度与观察义务反向。** 自治度越高，人越不在场，判稳窗口越可能被压到零；而按自治度分级的表格里没有「观察期」这一档（第 102 期在结案层复现）。

**内部绿灯不等于客户侧恢复。** Paige 事故一解决即自动生成复盘，把结案提前固化成文档（60 期复现）；腾讯云 71 篇要求审批人看证据链、修复与恢复验证须排在人工审批之后，顺序对了，「验证多久」仍无字段。

## 五、展望与建议

1. **`settling.*` 九字段进 OTel GenAI 提案**（settling_id／incident_id／declared_by／declared_at／contract_id／protected_caseset_version／window_start／window_end／close_receipt），独立 `settlement` span，默认 `CLOSURE_UNVERIFIED`，禁由被测 Agent 写入。
2. **五格结案闸门**：症状消失、受保护案例重放、fix-specific 验证、客户侧信号、稳定窗口全绿方可 close；缺一格标 `SETTLING_OPEN`，禁生成复盘与回流评测集，恢复契约独立于候选补丁导出。
3. **观察期进排班**：命名 owner、有终点窗口、预占产能、正式签字；MTTR 与 time-to-settled 双轨 SLO，**禁止单轨结算**，把「提前结案」从效率优化里剔除。
4. **结案快照与对账**：故障时与结案时双快照、as_of 绑定、进 CAB 并发布 `settlement diff`；窗口内发生发布或基线重校自动重新计时。
5. **六类混沌注入**：短暂复发、附带回归、非法输入归一化、监控被改、业务周期切换、证据已变；以能导出 `close_receipt` 为验收（参 11-06 Agent Chaos Engineering 行为契约）。
6. **补格与采购三问**：信通院五项要求、六维与 SRE AGENT 能力要求补「判稳窗口可导出率／独立结案签发率／复发重开率」；采购问谁签字、判据多宽、窗口多长、复发是否自动重开。11-09 KubeCon NA Agentics track 是提案窗口。
