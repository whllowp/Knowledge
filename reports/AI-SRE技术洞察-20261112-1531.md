# AI-SRE 技术洞察（第 154 期）

**生成时间**：2026-11-12 15:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：退役面／下线面（Agent Decommissioning）——上线有人批，下线没人签；76% 的企业 Agent 两个月没跑，却仍握着活凭据

---

## 题眼

10-26 Help Net Security 转述 Arrakis Security 的《2026 Autonomous Agents Threat Report》：在客户生产环境里分析数千个 Agent、12 周窗口，**76% 的启用 Agent 已 60 天没运行，44% 已 180 天没运行**；而它们**仍然保留凭据与系统连接**。Arrakis CEO 一句话点破原因：**「当一个 Agent 不再被使用，没有人移除任何东西，因为在大多数公司里没有人拥有它。」** 更硬的是复活路径：**约 25% 的休眠 Agent 可以被组织外的未签名 webhook 启动**，**22.9% 的 Agent 至少有一个未加固触发器**；**70% 连了至少一个敏感集成，其中 99.4% 在敏感连接上没有经验证的数据防泄漏覆盖**；**19% 使用永不过期、写在配置里的 API key**。**Agent 不会自己死，它只会被忘记——而被忘记的 Agent，仍然拿着钥匙。** **退役不是删除，是「调不动、带不走、查得到」三件事都做到。**

## 一、发展趋势

**趋势一：从「上线治理」补到「下线治理」。** 开通、评审、监控都有流程；**退役没有流程、没有 owner、没有验收**（146 期）。Microsoft 已经把「Agent 退役与弃用流程」写进治理课程，**说明这是公认缺口，而不是个别疏忽**。**上线的门越严，下线的门越容易被忘。**

**趋势二：退役从「删掉」变成「降级—归档—删除」三段。** 直接删会丢审计与知识；**先降为只读、再归档、最后按保留期删除**，才是可审计的退役（Arthur 的「demotion」路径）。

**趋势三：休眠成为默认状态。** 大量 Agent 是「季度/月度任务」，**60 天没跑不代表没用**；**用「最后运行时间」判死会误杀，用「无 owner＋无到期」判活会漏杀**。

## 二、技术现状：四个复活入口，通常只堵一个

**未签名触发器：最直接的复活入口。** 知道 URL 就能让 Agent 跑；**休眠 Agent 被唤醒后，沿用全部旧凭据**。

**永不过期的 key：最持久的。** 19% 的 key 写在配置里、不过期；**删 Agent 不删 key，等于没退役**。

**敏感连接无 DLP：最隐蔽的。** 70% 连了敏感集成，**99.4% 没有经验证的防泄漏覆盖**；**退役审计只看「有没有删」，不看「还能带走什么」**（140 期）。

**委派链：最容易被忽略的。** A 把任务交给 B，B 用 B 的权限执行；**退役 A 不等于切断链路**（144 期编队）。

**三种假退役，一种比一种像真的。** 停用界面但触发器还在（可复活）、删了 Agent 但 key 没撤（可冒用）、撤了 key 但 DLP 没验（可带走）；**「看起来停了」是最危险的状态**。

## 四、技术挑战

**一，休眠不等于废弃。** 季度任务的 Agent 60 天没跑很正常；**只看最后运行时间会误杀**。

**二，没人拥有就没有人收尾。** Arrakis 的原话是「没有人拥有它」；**退役需要一个具名的人签字**（146 期）。

**三，删除与审计冲突。** 删了记忆与日志，复盘就没了；**保留期与删除必须同时设计**（77 期）。

**四，触发器比 Agent 活得更久。** 删了 Agent，webhook 还在；**入口不关，退役就是假的**。

**五，凭据散落。** key 在配置、环境变量、CI、第三方平台；**没有清单，就撤不干净**。

**六，退役没有验收标准。** 「停用了」不算；**要能证明「调不动、带不走、查得到」**。

**七，多租户退役会串。** A 租户退役，B 租户共享的连接还在；**共享资源不先解耦，退役就退不干净**（121 期）。

**八，合规保留期冲突。** 法务要求留 6 个月日志（140 期 AI Act），安全要求立刻删凭据；**两者要分开处理：凭据立即失效、日志按保留期**。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `retire.*` 字段**：`agent_id`、`state`（active/dormant/demoted/retired）、`last_run`、`retire_by`、`creds_revoked_at`、`triggers_disabled_at`、`data_retained_until`。
- **R2 休眠识别**：按调度周期判断（不是固定 60 天）；**周期任务单独算**。
- **R3 四步退役**：停入口（触发器/路由）→ 撤凭据（key/token/服务账号）→ 降级归档（只读）→ 按保留期删除。
- **R4 触发器加固**：签名、来源校验、一次性 nonce；**未签名触发器一律视为可复活**。
- **R5 退役验收**：三项证明——调不动、带不走（DLP）、查得到（审计）。
- **R6 指标**：休眠率、活凭据率、未加固触发器率、退役验收通过率。

### 5.2 用户旅程

- **平台工程师**：季度扫描发现 120 个休眠 Agent → 按调度周期复核 → 标记 40 个待退役 → 生成凭据与触发器清单。
- **属主**：收到退役通知 → 确认无替代需求 → 签字 → 执行四步。
- **安全**：抽查退役 Agent → 尝试调触发器（应失败）→ 查凭据（应失效）→ 查日志（应可读）。
- **审计**：看退役清单 → 核对 `creds_revoked_at` 与 `triggers_disabled_at` → 确认没有「假退役」。

### 5.3 实现方案（90 天）

- **0–30 天：盘点。** 按调度周期识别休眠；列凭据与触发器清单。
- **30–60 天：收口。** 未签名触发器全部加固；永不过期 key 加到期；退役四步上线。
- **60–90 天：验收。** 退役验收三项证明；季度抽查；休眠率与活凭据率看板；退役变更进发布评审。

**第 105 个市场空白（五项）**：休眠率可报率、活凭据率、未加固触发器率、退役验收通过率、数据保留期可查率——无一内建；`retire.*`／`decommission.*` 为**第 72 次无人提字段族**。本地 173／173-kb 连续第 64 期成组启用：朱革 15「统一权限、审批、回滚」＝全库唯一把「回滚/收尾」写进治理的实践，本期首次当主线；配 146 期属主、136 期孤儿。判词：**本地把回滚写进治理，联网侧 2026 年才量出「76% 休眠仍持活凭据」；两边都没把「退役后调不动、带不走、查得到」做成验收项。**
