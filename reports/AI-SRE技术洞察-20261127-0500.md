# AI-SRE 技术洞察 第 327 期（2026-11-27 05:00）

## 升级分诊面／Escalation & Triage Integrity——「Agent 说『我搞不定』，不等于它在对的时刻、把对的上下文、交给了对的人，而且人真的接住了」

> **题眼**：#310～#326 连续十七期都在问「Agent 给出的结论可举证吗」，#326 又补问「还有没有人能验收」。本期再往前推一环——**在 Agent 决定交棒给人的那一刻，交接本身是可举证的吗**。行业把「升级率」「自治率」当指标，却几乎没人计量「升级有效性」：触发是否正当、路由是否找对人、上下文是否足以续查、人是否 ack、接手后有没有返工与二次升级。一个 `escalated=true` 的布尔值，掩盖了整条监督链。

---

## 一、发展趋势

2026 年，「人在回路」从一句口号变成了一个需要独立校准的工程对象。

**第一，交接被拆成一条链，而不是一个开关。** Agentic Work Atlas（10-05 汇总）明确：例外升级不能建模为 `escalated=true`，稳定分析单元是 `trigger/failure type → route/receiver → handoff packet → human action → outcome`，横切变量是 `timing / queue state / expert capacity`。它给出一句本期题眼式的判断——**「接到 ≠ 接住」**：消息送达只是传递动作，不等于人形成了有效复核。同一份汇总里 AWS 把 packet 定义为 versioned data contract，Google 给出生产锚点，Alibaba 给出唯一的现场实验证据。

**第二，厂商把「升级路径」写进文档，但只写到触发条件为止。** CIOAge 的三层权限模型（自主修复／AI 主导＋人工审核／人工调查）要求 Runbook 必须写明触发条件、证据、参数、范围、停止条件、验证、回滚**和升级路径**；同时明确破坏性数据操作、凭据变更、安全策略变更、不可逆数据库迁移、对外客户沟通、重大跨服务变更默认不给自主权，且「调级必须经正式评审，不能因模型某次置信度变化私自调整」。这是目前中文材料里对升级边界写得最清楚的一份，但它管的是「何时该交」，不管「交出去之后怎样」。

**第三，三家头部公司的案例给出了同一个分工形状。** 11-22 的横向拆解（Anthropic Claude Code 压测两周、OpenAI Performance Factory、腾讯开源 LoopForge）指出：人的工作集中在开跑前与交接点，能撤销的 agent 自己做、不可逆的那一步留给人，复核与执行由不同主体完成；分歧只在任务状态放哪——Anthropic 让一个会话守目标两周，OpenAI 与 LoopForge 把状态写进任务记录或产物文件，每步起新 agent，因而「人随时可以接手，agent 也能在人处理完之后接着做」。后者才是长期运行流程该照搬的形态，因为它天然要求可续接的交接包。

**第四，基准开始暴露「会诊断、不会交付」。** ITBench SRE(AA) 榜单（11-23 快照，45 个配置）最高 56.2%；R2Act 的五个诊断最优模型在「方案被规则接受」上只有 36.8%～60.3%，755 份被拒方案里 513 份选了事故不需要的操作；SWEOps-Bench 的 55 个真实算子缺陷中，故障检出 72.7%～90.9%、端到端闭合仅 14.5%～52.7%，96 个域名类故障无一在线上回放中恢复。**一个按「找对服务」计分、却不为「是否接住」负责的行业，正把升级包当成最后一块没人验收的拼图。**

## 二、技术现状

把近 30 天的公开材料按「交接是否被当作一等字段记录」重切，会看到整齐的空白。

Google 是唯一给出生产设计锚点的一家：AI Operator 升级时把**完整 investigation history 写入 incident UI**，让人从当前调查状态继续而非从头重做；Google SRE 团队用 Gemini CLI 处理真实故障，Agent 拉告警、做因果分析、关联时序、给缓解建议，人回一句「SGTM，执行重启」即触发操作，Komodor CTO 称约 30% 案例可独立解决、人只收 FYI（二手转述，分母口径不明）。这里的关键不是自动化程度，而是「续查状态」第一次被当成交付物。

AWS 在 `AGENTOPS01-BP02` 里把 packet 写成版本化数据契约：接收者发现字段 `capability / availability / acceptance criteria`，packet 记录 `task description / completed work / memory artifacts / handoff reason`，并把 `handoff latency / context-transfer completeness / collaboration success` 设为一等指标。更值得注意的是一条负面结论：packet 不是越完整越好，`recommendation` 必须与 evidence 分离显示——2021 年的选择性预测实验表明，展示 AI 预测会把人锚定到错误方向。这恰好戳中多数自研交接包的软肋：把模型结论和证据混排在一段 Markdown 里。

Alibaba 的现场实验（客服运营，随机化的是 AI 部署而非 timing/type）是唯一的效果证据：人工介入的效果依赖**失败类型、介入时机与接管后的实际投入**——技术能力不匹配型升级更容易靠人工维持服务质量，情绪型升级往往更晚发生、接管后投入更少；更早介入与更高的接后投入相关，但 timing 未被独立随机化，不能写成「越早越好」的因果律。汇总页同时提示：全局置信度校准会掩盖类别依赖的误校准，把对的 case 留给专家、把错的留给模型；升级条件不能只靠单一阈值，须按 failure type / subgroup / risk tier 审计。

中国云厂商的落地形态高度一致地把最后一步留给人：阿里云 STAROps 的 Agentic Ops 闭环「人设目标、执行边界与关键决策」，跨域因果链能追到 OSS 连续前缀导致分区限流这类根因，但仍需审计、审批、回滚与「能对结论负责的人」；腾讯云 CloudQ 以全景图谱支撑「AI 调用 AI」、受控执行，联合信通院推六维基准，其中含人工接管兜底；火山引擎 DevOps Agent 的响应计划按 Runbook 自动取证后「输出修复建议，供人工确认和修复参考」，专家 Agent 可通过 IAM 角色按需读跨服务数据而不扩大人员权限。这些设计的共同点是：把「交给人」画成了流程终点，而不是需要度量的起点。

## 四、技术挑战

**挑战一：升级触发的误校准是双向的。** 漏升级（该交没交）比误升级（不该交乱交）更危险，但两者在日志里同样只是 `escalated=false/true`。全局置信度阈值会掩盖类别依赖的误校准；供应链场景的触发设计提示，当 agent 能写 ERP/WMS 时，触发条件至少应包含 `action × financial exposure × service impact × counterparty trust`，而不只是模型 confidence。

**挑战二：packet 本身是人为干预变量。** 展示 AI 预测会把人锚定到错误方向；「unknowns: none」出现在两次修复失败的 agent 汇总里，本身就是一句谎话——但只有审计日志能证伪。多数团队把 summary 当作交接的终点，而不是需要交叉核对的证词。

**挑战三：timing 与容量是不可转移到结论里的隐变量。** 同一个触发、同一个 packet，在不同 queue state、receiver availability、intervention timing 下会产生不同的人类行为；Alibaba 随机的是部署而非时机，所以「早升级更好」目前只是相关性。把升级效果写进 KPI 而不记录接手时的值班队列，等于把排班噪声当成 agent 质量。

**挑战四：验收证据的边界必须诚实标注。** 现有证据里，Google 与 AWS 主要是一方工程设计，Alibaba 现场实验随机化维度有限，NEJM AI 的快速响应收益来自培训＋流程＋算法的组合；没有一项实验在固定 agent 输出、接收者与队列状态后，同时随机化 packet 内容与 handoff timing。因此本期主张的是「应当记录并校准」，而不是「某种交接设计已被证明最优」。

## 五、展望与建议

**新观点（本期提出）**：行业把「自治率」当进步指标、把「审批格」当安全指标，却漏掉了夹在两者之间的**升级有效性**。升级不是安全阀，是一条需要独立校准的监督链。看得见「它把事故交给了人」，不等于看得见「触发正当、上下文可续查、接收者当时有容量、人真的接住了」。这是 #326「验收者可能已退化」的前置问题：**如果任务根本没交到一个接得住的人手里，验收者的能力就无从谈起。**

**第 248 个空白字段族 `escalation.handoff.*`（本文归纳，缺省 `ESCALATION_UNVERIFIED`）**：`trigger.type ∈ GUARDRAIL_DENIAL|REMEDIATION_REPEAT|SEVERITY_BUMP|CUSTOMER_IMPACT|CONFIDENCE|LOOP_DETECTED|HUMAN_REQUEST`、`trigger.failure_type`、`receiver{id,capability,availability,acceptance_criteria,queue_state}`、`packet{version,visible_evidence[],recommendation_separated,investigation_history_ref,memory_artifacts[]}`、`handoff.time`、`ack.time`、`human.action ∈ ACK|START|APPROVE|REJECT|OVERRIDE|NO_ACTION`、`agent.frozen`、`rework.count`、`re_escalation`、`intervention.timing`、`resolve{quality,latency}`、`verdict ∈ HANDOFF_CAUGHT|DELIVERED_NOT_CAUGHT|MIS_ROUTED|TOO_LATE|ANCHORED_PACKET|UNVERIFIED`。**门禁**：`verdict ≠ HANDOFF_CAUGHT` 不得计入「人工监督已生效」合规声明，不得作为自治升档依据（承 #310～#326 叠加）。

**四条最小动作**：① 交接包拆成 facts／state／reason／recommendation／version 五段，建议与证据物理分离，并附 `investigation_history_ref`；② 交接即冻结 agent 写权限，ack 之前不得双司机；ack 超时自动升副值班而非静默挂起；③ 记录 handoff→ack 时延、接收者队列状态与接后返工次数，把这三项设为一等指标；④ 每次升级留「反事实」判据——若换一个接收者或改一次 timing，结论会不会变，用于校准阈值而非追责个人。

**采购三问**：升级触发条件是按 failure type / risk tier 分层，还是单一置信度阈值？交接包是否版本化、建议与证据是否分离？你们能否给出「交接后被接住率」而非只有「升级次数」？

**评测建议**：给 ITBench/R2Act 类基准加一对交接题——同一诊断结论配完整证据包与「建议混排」包各一版，报 `anchored_packet_rate` 与 `handoff_resume_latency`；再注入接收者忙碌队列，报 `missed_escalation_rate` 与 `re_escalation_rate`。**信通院六维**建议补一格「升级可举证率」，与 #316 审批格、#317 授权格、#318 空窗格、#319 判定格、#320 自伤格、#321 收口格、#322 归因格、#323 测量格、#324 可读性格、#325 因果格、#326 接管格并列。

**本地知识源的新读法（第 203 期新角度）**：朱革《百度 SRE Agent 规模化落地实践——大模型 Agent 的安全托管与自主进化探索》首次改读为「**安全托管的边界不画在 Agent 永不越界，而画在它越界前把指挥权交出去、且交得干净**」——托管的可信度不看 autonomous rate，看交接那一刻的状态可续性；配周昕毅《AI + SRE ≠ AISRE》「人进闭环不是把自己移出闭环」、刘凯宁蚂蚁根因「约束长在 Agent 够不到处」（冻结写权限正是这样一个约束）。173 目录按目录级引用。
