# AI-SRE 技术洞察（第 298 期）

**生成时间**：2026-11-20 07:31（Asia/Shanghai）
**观察窗口**：2026-01 至 2026-11-20
**本期主题**：可复现面／构建证明与“同源同物”——签名证明谁构建了它，可复现才证明它等于源码

## 题眼

2026-05，Debian 发布团队做了一个安静但决绝的决定：**不可复现的包不再允许进入 testing**。当时的基线是 amd64/forky 上 **97.02%** 的包可复现（17,586 个），511 个失败，另有 30 个连构建本身都失败；剩下这约 3% 的维护者，不解决复现性问题就无法上传新版本（Debian 复现性状态页，2026-05 数据；韩文报道，2026-05-11）。

2026-09-22 至 27 日，Reproducible Builds Summit 在哥德堡开了六天。会议纪要里有一组很适合当尺子的数字：F-Droid 的 Client 2.0 已就绪，仓库 35% 可复现；学界验证了 1.9 万个包，其中 83% 构建成功、成功者里 94% 可复现（reproducible-builds.org，2026-09）。也就是说，即使在“最关心复现”的社区，**全量可复现仍是一个正在接近、尚未达到的目标**。

同一年，构建证明（attestation）在主流生态里铺开：PyPI 自 2024 年起支持 PEP 740 数字证明，发布时即超过 2 万条；2026-11-06 PyPI 改版，把安全信号（含证明）放到项目页显著位置。Temurin 则把“可复现验证构建”做成第三方可复核的流程：JDK 21+ 构建完全可复现，IBM 作为工作组伙伴独立验证了 JDK 21/25 在 Windows x64、Linux x64 上的发布，并发布签名的 CycloneDX 证明（Adoptium，2026-08 与 2026-10 更新）。

看起来证据链已经很完整：有证明、有签名、有第三方复核。但 2026-08-08 一份 SLSA 参考文档写了一句关键限定：**provenance 证明的是“来自某个仓库、由某个工作流构建”——构建来源，不是代码安全**；它还点出最经典的事故形状：你给本地构建出了证明，却推了另一个 manifest，多架构 index 与平台 manifest 的 digest 对不上（SLSA reference，2026-08-08）。

## 一、发展趋势

1. **证明成为默认**：PyPI、npm、容器仓都在发 attestation；“有没有证明”正在变成“有没有发布”的一部分。

2. **可复现从“学术兴趣”变成“发布门禁”**：Debian 直接把不可复现挡在 testing 之外；这比任何“建议”都硬。

3. **第三方复核成为信任来源**：Temurin 由 IBM 独立验证并发布 CDXA 证明，把“厂商自证”变成“外部可验”。

4. **多架构让 digest 对齐变难**：镜像 index 与平台 manifest 是两层 digest，证明常常只覆盖其中一层。

5. **AI 制品复用同一条链**：Agent 镜像、推理引擎 wheel、模型权重包，都开始走同一套 attestation；但它们对“构建环境”的依赖更重（CUDA、驱动、量化工具），可复现更难。

## 二、技术现状

**第一层：签名层。** 签名回答“谁签的、内容有没有被改”，不回答“内容是不是源码的忠实产物”。签名可以完美覆盖一个错误构建。

**第二层：证明层（provenance）。** in-toto/SLSA 证明记录 builder、source repo、commit、构建参数、材料清单；它回答“在哪构建、用什么输入”，不回答“同样的输入能否得到同样的字节”。

**第三层：可复现层。** 只有重建才回答“同源同物”。Debian 的 97.02% 是用重建跑出来的；剩下 3% 正是“证明齐全但无法重建”的那部分。

**第四层：环境层。** 可复现要求工具链、时间戳、路径、locale、依赖版本全固定；CUDA/驱动/量化内核让 AI 制品的环境固定尤其难，很多团队只能做到“同机器可复现”。

**第五层：取证层。** 事故时能查到“镜像 digest、签名、证明”，查不到“这个 digest 能否由该 commit 重建”；证明链止于 builder 的声明。

## 三、技术竞争力

| 方案／机制 | 证明什么 | 等价源码 | 含构建环境 | 多架构覆盖 | 校验时机 | 失败可发现 |
|---|---|---|---|---|---|---|
| Sigstore/cosign 签名 | 谁签、未篡改 | 否 | 否 | 逐 digest | 部署/拉取 | 签名错配 |
| SLSA provenance | 构建来源与输入 | 否 | 部分（参数） | 需分别出 | 准入策略 | 来源不符 |
| in-toto 布局 | 步骤与材料链 | 否 | 部分 | 需分别出 | 策略校验 | 步骤缺失 |
| PyPI/npm attestation | 发布者与工作流 | 否 | 否 | 单包 | 安装时 | 证明缺失 |
| 可复现重建（Debian） | 同源同物 | 是 | 是 | 按架构 | 构建后 | 字节差异 |
| Temurin 第三方复核 | 可复现+独立验证 | 是 | 是 | 多平台 | 发布时 | 复核失败 |
| 镜像 digest 固定 | 部署的是哪份 | 否 | 否 | 单平台 | 部署时 | 漂移 |
| SBOM | 包含哪些组件 | 否 | 否 | 不适用 | 扫描时 | 组件缺失 |

**判读**：每一层都能回答“这是谁做的、由什么输入做的、包含什么”。只有可复现重建能回答“**它是否等于源码**”；而能回答“这个镜像在多架构下每一层 digest 都与证明对齐、且能在干净环境重建”的，几乎没有。SRE 排障时需要的正是最后这句：不是“谁签了名”，是“我能不能自己造一个一样的”。

**本期反转**：我们把“签名 + 证明”当成供应链安全的终点，默认有 attestation 就等于可信。实际证明是**声明**，可复现是**验证**；声明可以被完美地签在一个错误构建上。Debian 的 97.02% 之所以有分量，不是因为证明多，而是因为它敢把剩下 3% 拦在门外。**构建证明回答“谁造的”，可复现回答“是不是同一个东西”——后者才是事故里要的那句话。**

**判词**：「Sigstore／SLSA／in-toto／PyPI 证明／npm provenance／镜像 digest 固定／SBOM」全部可采购，「这个 digest 能否由该 commit 在干净环境重建、多架构每一层是否与证明对齐、重建差异出在工具链还是源码」不可采购。

## 四、技术挑战

1. **声明≠验证**：证明齐全但无法重建，是最常见的“合规但不可信”。
2. **多架构错配**：index 与平台 manifest 的 digest 是两层，证明常只覆盖一层。
3. **环境不可固定**：CUDA/驱动/量化内核、时间戳、路径，导致只能“同机复现”。
4. **dirty build**：本地未提交改动进入构建，provenance 只记 commit，不记工作区。
5. **AI 制品更重**：权重包、量化产物、推理引擎 wheel 的可复现成本远高于普通包。
6. **证据断点**：事故时只有 digest 与证明，没有“重建尝试”的记录。

## 五、需求分解、用户旅程与实现方案

**需求分解（D1–D6）**

- D1 重建门禁：关键制品发布前在干净环境重建一次，比对字节；不一致即阻断。
- D2 多架构对齐：证明覆盖 index 与每个平台 manifest 的 digest，逐层校验。
- D3 环境指纹：记录工具链、驱动、CUDA、量化工具版本，作为可复现的前提。
- D4 工作区洁净断言：构建输入必须来自 commit，dirty build 禁止发布或显式标注。
- D5 差异归因：重建不一致时，输出差异类别（时间戳/路径/工具链/源码），而不是只报失败。
- D6 事故取证：取证包包含 digest、证明、重建结果三段，缺一段即标“未验证”。

**用户旅程（一次“证明齐全但重建失败”的发布）**

① 制品发布，签名、SLSA 证明、SBOM 齐全，准入策略全绿（D1 缺失）；② 线上故障，怀疑镜像被替换，团队查 digest 与签名，全部匹配（D2 部分）；③ 安全团队尝试用该 commit 重建，发现字节不一致——差异来自构建机的时间戳与本地未提交的 patch（D3/D4 缺失）；④ 没人能判断“不一致是环境噪声还是源码被改”，只能整体回滚（D5 缺失）；⑤ 复盘写“供应链证明完整”，但无法回答“这个镜像到底是不是这份源码”（D6 缺失）。

**90 天实现方案**

- **第 1–30 天**：对核心制品加重建门禁，先做“同机重建”，再做“干净机重建”（D1）。
- **第 31–60 天**：证明覆盖多架构 digest 并逐层校验（D2）；记录环境指纹（D3）。
- **第 61–90 天**：禁止 dirty build 或显式标注（D4）；差异归因（D5）；取证包三段式（D6）。

**第 210 个市场空白（五项）**：① 重建门禁与“干净环境”定义；② 多架构 digest 与证明的逐层对齐规范；③ 构建环境指纹字段；④ dirty build 的发布策略；⑤ 重建差异归因与取证三段式。

**`reproducible.*`／`build_provenance.*` 第 177 次无人提字段族**：文档谈“如何签名、如何出证明、如何固定 digest”，不谈“能否重建、差在哪、差的是环境还是源码”。

**本地 173／173-kb 连续第 165 期成组启用（蒋炎炳 23：制品要能自己造一遍）**：本地原型给每个制品写 `build_evidence{artifact_digest, source_commit, builder, toolchain_fingerprint, rebuilt: bool, rebuild_diff: none|timestamp|path|toolchain|source, multiarch_aligned: bool, verified_at}`；发布门禁要求 `rebuilt=true 且 rebuild_diff=none`；事故取证包同时给出 digest、证明、重建结果。
