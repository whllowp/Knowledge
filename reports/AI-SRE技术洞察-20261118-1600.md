## 题眼

把 SRE Agent 放到一台健康的系统上，看它 24 小时会不会凭空报出一起事故、并对着不存在的故障"修"点什么——这件事，主流平台不发布、主流基准不打分、主流评测不设这一格。行业度量的是召回（注入 21 个故障抓到几个），几乎不度量特异度（138 个无故障静默窗口里，Agent 会不会捏造根因）。本期首次把"无故障时的正确沉默"立为一等对象，论证它不是"少做事"的消极指标，而是决定是否敢给 Agent 写权限的正面能力。

与往期划界：#260 置信度校准问"0.85 是否真对应 85%"、#267 恢复判据问"何时算修好"、#269 存续面问"哪些证据活下来"、#282 探针面问"合成监控是不是只走自己的路"、#265 诊断扰动问"取证有没有改写现场"——本期只问一件事：**当什么都没坏时，Agent 会不会制造出一个"坏"，并据此改动健康系统**。索引中"假事件／零假设／健康集群／静默对照"均为 0，"误报"31 处、"假阳性"5 处皆指告警层或评测饱和度，未成独立立面，确认为全新角度。

## 一、发展趋势

三条方向在最近 30 天同时浮出水面，把"静默"从工程细节推成独立议题。

**其一，基准开始偷偷塞入"无故障对照"。** ChironVision 11 月在 ORCA-bench 上跑 526 张公开事故工单时，特意并列了 **138 个 quiet-window controls（未注入故障的静默对照）**，并把"Correctly quiet on controls"单列成一行指标：Sonnet+Grafana 为 57.9%，加上下文层后升到 67.4%。这是罕见的、把"正确沉默"写进成绩单的做法——即便如此，仍意味着健康系统上有三到四成窗口被 Agent 报了不该报的东西。SREGym 把噪声从 72.6% 降到 62.6%/60.7% 降到 53.7%，本质上也是在度量 Agent 抗"假信号"的能力，只是没改名。

**其二，"拒绝执行"被承认为成熟度标志。** 腾讯云开发者社区 11 月《智能运维的工程约束》给出的判断很直白：智能运维的成熟度体现在系统**拒绝执行**的能力，而非执行的能力；其 SAFE-HealCloud 分级自治加 AURA 确定性闸门在一次混沌演练中检出 7/7 故障、执行 6/6 范围内修复、**零误修复**，DNS 故障因超出白名单被正确拒绝并升级人工。这与"准确率越高越好"的单轴叙事分道扬镳：拒绝，是静默面的执行侧投影。

**其三，降噪诉求从告警层卷到 Agent 层。** NeuBird 援引 2026 状态报告称 83% 组织跑四套以上可观测工具、工程师 40% 时间花在事件管理、超 70% 告警无需行动；Grafana 与 Cyera/PlayHQ/NAB 的 8 月圆桌把"给分诊 Agent 建记忆注入、节点例行轮换直接静默"列成可执行项。但降噪的对象是**告警**，不是**Agent 自己产出的假事故**——后者是把噪声重新放大一遍的新源头。

## 二、技术现状

当前技术栈在"检测—诊断—执行"三环上都已产品化，唯独在"否"这一环留白。

**结构上，Agent 没有"什么都不报"这个一等输出。** 主流编排是每轮产出假设／报告／动作，ReAct 每轮工具调用即新证据，Anthropic 自托管 Managed Agents 甚至承诺"每一步都经 OpenTelemetry 导出"——可导出的都是"做了什么"，没有"决定不做"。当一个框架的 API 里没有 `noop` 这个合法终态，Agent 在被唤醒后就必须给出点什么，行动偏误（action bias）是被架构制造出来的，不是模型脾气。

**因果层在补位，但补的是"别修错服务"而非"别修健康服务"。** Causely 在 OpenTelemetry Astronomy Shop 上的四配置对照很说明问题：无因果上下文时正确回答因果问题 75%，加 MCP 后 100%；单次调查工具调用 19→4、token 308K→123K、诊断耗时 73s→25s，最关键是**健康集群上的假事故从 12 次运行里 4 次降到 1 次**。这说明假事故有一部分不是"看错了"，而是"把相关当因果、重启了一个恰好能解释错误的依赖"——那条 checkout 案例里，团队为一个不需要的变更耗掉一个评审周期，交易仍在失败。Causely 的自查清单直接问："过去十个可靠性 PR 里，有几个改的是告警的那个服务而不是致因的那个服务？"

**评测层的口径尚未统一。** SWEOps-Bench（arXiv 2611.06099）用 16 个 operator 仓库、55 个真实历史缺陷做端到端评测，明确写"症状消失不等于解决，表层补丁或 Pod 重启可能掩盖故障并引入回归"，并要求 fault oracle 加端到端管理检查双重验证；ORCA-bench 用 19 微服务、50GB 数据、1079 个根因任务（中等难度最佳 25.3%、困难 10.0%，幻觉不合理根因 7%–40%）；Traversal 以 10 亿美元估值完成 1.2 亿美元 B 轮，正是要把这套因果系统推到自动驾驶生产，但论文作者自己提醒：公开受控平台分数不代表生产表现。假事故率，在这类基准里大多只是"幻觉率"的一个附注。

## 四、技术挑战

**第一，指标结构的系统性偏斜。** 召回是分子分母都清楚的 KPI，特异度需要主动构造"什么都没坏"的分母，而构造静默窗口的成本被当成浪费——没有故障就没有演练价值。结果是整个行业优化一个只有正样本的目标函数。

**第二，假事故不是空操作，是有下游伤害的变更。** SWEOps-Bench 已证明表层补丁和 Pod 重启会掩盖故障并引入回归。把这条链倒过来看：健康系统上的假事故若触发了自愈，Agent 就从"观察者"变成"致因者"——它在健康体上制造了一个需要被修的新故障，然后很可能还被自己检出、自转自修，形成闭环的自我确认。这与 #265 诊断扰动同构，但后果更重：那里是探针改写症状，这里是处置改写系统。

**第三，归因口径分裂。** 状态词"degraded"能指延迟、登录失败或例程迟到（#284），"误报"在索引里 31 处分别指告警层假阳性、阈值噪声、评测污染、探针失真——同一个词盖着五种机制，谈"降误报"时各方其实在解不同的题。静默面要求把这几种机制拆成互不替代的字段，而不是合并成一个百分比。

**第四，权限与"否"的错配。** 行业给 Agent 写权限的依据是检测准确率高，但决定是否安全的恰恰是健康态误诊率：一个召回 95%、假事故率 4/12 的 Agent，比召回 75%、假事故率 1/12 的 Agent 更危险。当前没有任何认证把这两个数并排。

## 五、展望与建议

**1. 立字段族（第 154 个无人提字段族）**：`quiescence.verification.*`——`quiet_window_count`（健康态对照窗口数，永不采样也要计数）／`false_incident_rate`（每健康窗口假事故数）／`correctly_quiet_rate`（正确沉默率，对标 ORCA-bench 57.9%→67.4%）／`noop_decision_logged`（是否把"决定不行动"记为带理由的一等决策）／`false_incident_downstream_changes[]`（假事故触发了哪些变更、被哪道闸拦下）。缺省 `QUIESCENCE_UNVERIFIED`，不进自动执行门禁。

**2. 给编排框架加 `noop` 终态**：让"检查完毕，未发现可归因异常，不做变更"成为可审计、可计量、可评测的合法输出，而非超时或空报告。把 Causely 的"说清排除了什么"写进这个终态的必填项。

**3. 评测改造**：ORCA-bench 的 138 个 quiet-window controls 应升为标准题型，SREGym／SWEOps-Bench 增设"健康双跑"——同环境注入与不注入各跑 N 次，出召回—假事故二维曲线，而非单点准确率；把"表层补丁引入回归"计为比漏检更重的失败。

**4. 门禁与权限**：写权限审批表把召回率与假事故率并排，设假事故率红线（如 <1/12）；沿用 AURA 思路，静默面证据不足时默认降到"只读+人工审批"，把模型自报风险与确定性闸门分离。

**5. 标准补格**：信通院《云上 Agent 基准度量模型》六维之外，建议补"健康态特异可举证率"一格，与 #267 恢复可举证率、#269 证据存续可举证率配套。

**本地知识沉淀**：本期第 161 期启用腾讯云开发者社区《智能运维的工程约束》作"拒绝即成熟度"主线注脚，配刘凯宁《蚂蚁 SRE 基于 Agent 的应急根因定位实践与踩坑》——把"结论/证据/待确认项"三分扩出第四分"未被报出的健康窗口"，让沉默也进复盘台账。
