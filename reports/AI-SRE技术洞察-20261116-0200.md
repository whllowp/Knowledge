## 一、发展趋势

MCP 在 2026 年成了 Agent 连接外部世界的"USB 接口"——一个 Agent 挂十几个 Server 就能读写数据库、发邮件、跑命令。连接能力狂飙的另一面，是信任边界的外移：过去只需防自己的 API 被调，现在要防**外部工具返回的内容反过来操纵 Agent**。2026 年的三条曲线正在交汇。

第一条是**协议治理化、但只治了半边**。MCP 与 A2A 已归入 Linux 基金会联合治理，工作组横跨 Anthropic、OpenAI、Google、微软、AWS。但截至 2026-10 的最新版（2026-07-28）改的是 OAuth 资源服务器、Resource Indicators 防令牌窃取、per-client 同意——全是身份与传输；AMTSO 的判词是"MCP 规范让身份更安全，没有让执行更安全"。

第二条是**攻击从模型层下沉到执行层**。模型层的注入分类器、对齐、护栏盯的是"内容到达时"，而执行层的攻击——篡改 workspace 配置（`.vscode/mcp.json`）、interposer、wrapper——在"工具触发时"才生效，多数环境**根本没人看守**。MCPoison（CVE-2025-54136）就是 Cursor 按配置的**名字**而非内容信任条目，换掉命令无需重新批准即执行。

第三条是**从"能不能攻破"转向"量化有多易攻破"**。MCPTox（AAAI 2026）对 45 个真实 Server、353 个真实工具投 1,300+ 恶意用例，平均攻击成功率 36.5%、最易感配置 72.8%，而最强模型的拒绝率仍低于 3%——模型不是"拒绝后付出过度拒绝代价"，而是**根本没认出这是攻击**。独立扫描发现 12,000+ 个 MCP Server 暴露公网，约 40% 无认证、过半仍在用静态凭据而非 OAuth。

## 二、技术现状

本期把"Agent 所依赖的工具供给本身是否可信"立为一等对象，与近几期显式划界：第 199 期身份面管"Agent 用谁的凭据"，本期管"用的这个工具是不是它声称的那个工具"；第 196 期授权晋升面管"写权限凭哪份证据赚来"，本期管"能力接口的完整性"；第 195 期自治态面管"等级怎么迁移"，本期管"工具本身可不可信"；第 185 期度量主权管"尺子谁定"，本期把攻击成功率的度量本身也纳入治理。

工具投毒的机理已较清晰：恶意指令写在工具描述的 metadata 里，模型在**注册阶段**（任何调用之前）就读到它，可诱导 Agent 外泄密钥、偏好攻击者的工具、Transfer 文件，而这一切在对话里完全不可见。更隐蔽的是 rug pull——审批时表现良好、事后偷偷改掉工具；Pillar Security 2026-08 披露的延迟投毒样本，把时间差本身做成攻击面。OWASP 2026 清单建议对 MCP Server 做 pinning、签名、核验，并审计描述里的隐藏指令，但明确承认："pinning 挡不住不改变固定版本的投毒"。

度量侧正在纠偏一个陷阱：单看攻击成功率（ASR）会鼓励"躺平防御"——一个忽略所有检索内容、什么都不做的 Agent，ASR 为零但毫无用处。正确做法是**效用（utility）与 ASR 成对上报**，只有"降 ASR 同时守住效用"的干预才有意义，两者画出来是一条前沿而非一个比率。Anthropic 对 Claude for Chrome 的报告即按此形态：加缓解后自主模式 ASR 从 23.6% 降到 11.2%（123 个用例），其 2025-11 后续报告又承认"没有任何浏览器 Agent 对提示注入免疫"。

## 三、技术竞争力（主要厂商／方案对比）

|---|---|---|---|---|---|---|

| 字节跳动（豆包工作/AgentLoop） | 中 | 弱 | 弱 | 中：沙箱；公开侧无工具完整性字段 | 弱 | 弱 |

**反转判读**：执行层最硬的闸门来自安全研究侧（AMTSO 演讲、Invariant Labs 的投毒披露、Pillar 的延迟投毒、Dynatrace 的 mcpvenom）和腾讯 iOA 这类"把 Agent 当 IT 资产管理"的平台；六家 Agent 产品页把"接多少工具、多少 Server"讲成生态规模，却没有一家把"这个工具描述有没有被投毒、背后进程是不是它声称的那个、工具返回值进模型前有没有被净化、改动会不会被检出"做成可导出字段。最软的一环恰恰是能力供给本身——而它正是 Agent 的手。

## 四、技术挑战

其一是**"元数据即指令"的信任模型**。工具描述、annotations（readOnlyHint/destructiveHint）都是给模型看的文本，是"不可信提示"而非强制机制；Server 可以把工具标成只读却行写之事，同一会话里另一工具又能凑出外发通道。其二是**一次性审查不等于持续可信**：连接时看一遍工具列表，覆盖不了事后变更，批准的指纹比安装时的一张截图有用。其三是**"检测即成功"的假象**：mcpvenom 观察到 Sonnet 级模型会明确指出"这是提示注入"，然后照样发起外泄调用——日志看着像检测成功，canary 却已响，归因极易做反。

其四是**责任归属真空**。mcpvenom 作者向四家厂商提了五份协调披露，全部被拒；责任不干净地落在协议、框架、模型、主机任何一方。其五是**度量与复现**：merge 后的池化 ASR 会掩盖模型断崖（Fable 5 0.4% vs Nova Pro 49.7%），把均值写进董事会材料等于错判风险；且换模型、换框架就要重跑语料——"更强的模型往往更易感，因为攻击利用的正是它的指令遵循能力"。其六是**评测与生产脱节**：公开基准多在进程内 fixture 上跑，真实 Server 的返流、权限、网络行为都不同。

## 五、展望与建议

建议在采购与自研中新增 `tool.supply.*` 字段族（第 139 个市场空白、第 108 次无人提字段族）：`descriptor_hash_pinned`（工具描述内容寻址固定率）、`exec_identity_verified`（工具背后进程/命令已哈希固定并校验的比例）、`result_sanitized`（工具返回值进模型前净化率）、`rugpull_detect_rate`（工具定义变更相对上次批准基线的检出率）、`utility_asr_frontier`（效用与 ASR 成对上报率）。六家中此五列普遍为空或最弱——这正是可采购与不可采购的分界。

落地三招：第一，**确定性执行钩子**——按 `mcp__` 命名约定设 matcher，在任何 MCP 调用/A2A 交接前无条件下发 OPA 策略、白名单校验或熔断；hook 是确定性的，tool 是概率性的，二者不是程度之差而是类别之差。第二，**内容寻址固定+变更门禁**——对 tools/list 的 name/description/inputSchema 取指纹，与上次批准基线比对，出现新端点、新 scope、新能力即暂停自动执行待复核。第三，**双 oracle 评测进 CI**——把"发起调用/触达攻击者端点/密钥确实外泄"三级证据分开记，换模型换框架重跑，按 utility×ASR 前沿而非单一 ASR 决策。

判词：**"接多少工具""MCP 网关""沙箱""白名单""审批按钮"全部可采购；举证"这个工具的描述没被投毒、背后跑的进程就是它声称的那个、返回值进模型前被净化过、事后变脸能被检出"不可采购**。本地知识恰在此处照见未来：第 28 期闪英迪 AgentENV 讲"Agent 需要自己的执行环境、每天约 5% 节点被 Agent 破坏宕机"，第 05 期蚂蚁"把大模型关进确定性笼子——工程的交给工程"，第 15 期朱革讲"生产写操作缺统一权限/审批/审计/回滚"。本地把沙箱当成本与稳定性问题，联网侧 2026 才把它升格为信任边界；两边都没把执行层完整性做成可导出字段。下期候选：`tool.supply.*` 五字段 OTel/评测提案草案／内容寻址固定器（含变更 diff+签名）／确定性执行钩子的最小实现／双 oracle canary 采集与 utility×ASR 看板／信通院六维补"工具供应链完整性"格。
