# SRE Agent 领域技术洞察 · 第 237 期

**主题：基数面／维度爆炸面（Telemetry Cardinality / Dimension Explosion）——Agent 把 session_id、user_id、prompt 挂上指标标签的那一刻，"指标全绿"就不再是"系统健康"：OpenTelemetry 默认 2000 组合上限一溢出，总量照常正确，按维度的分组却悄悄少算；被切掉的维度连一条"我被切掉了"的记录都不留**

## 题眼

过去两百多期，本系列反复拆穿"指标全绿"的各种假象：#162 可观测黑洞说 Agent 自己不留遥测，#201 观测成本面说看清它的账单先烧穿，#83 采样面说没被抽中的那部分连"没记录"都没有。本期拆的是另一层、且更隐蔽的一层：**不是没采集、不是没记录，而是记录了、总量还是对的、唯独"按哪个维度切"这件事被 SDK 在内存里静默改写了**。2026 年 8 月 6 日 OpenTelemetry 专门发布基数限制指南：指标 SDK 默认每条 metric stream 只保留 2000 种属性组合，超出的组合折叠进一个 `otel.metric.overflow=true` 的点，**原始属性被抹掉**。于是"请求总数"仍然分毫不差，可"按 outcome=success 切片""按 model_family 分组""按 route 看 P99"全部开始少算——而 SLO、告警、看板正是按这些维度切的。Agent 尤其危险：它的 GenAI 语义约定天然带 `session.id`、`conversation.id`、tool-call id、原始错误信息，这些标识符"每次请求都不同"，是教科书级的无界维度。一句话立题：**对传统服务，高基数是成本问题；对 Agent，高基数是正确性问题——因为它的诊断完全依赖按维度切片。**

## 一、发展趋势

**趋势一：OpenTelemetry 把"基数"从调优细节抬成安全边界，并明确警告"总量对不代表分组对"。** 8 月 6 日的基数限制指南与同期指标规范把机制讲透：超过上限时测量值不丢、总量守恒，但整组属性被替换成溢出点，因此"只要其中一维溢出，连 `success` 这种低基数布尔维度也一起不可靠"。指南还点破两个反直觉点：一是 delta 时序下同一进程可跨周期导出不同组合，1000 个 pod × 每 pod 上限 2000，后端序列仍远超 2000——"SDK 上限不等于后端上限"；二是 Resource 与 instrumentation scope 属性不参与溢出替换，measurement 属性才参与，这是建模问题不是权宜之计。

**趋势二：Agent 语义约定自身进入"变动期"，基数治理失去稳定锚点。** 截至 v1.42.0（2026-06-12），全部 `gen_ai.*` 与 `mcp.*` 约定从主线规范迁出到独立仓库 `open-telemetry/semantic-conventions-genai`；截至 10-29 该仓库无正式 tag，处于"Development、未版本化"状态——无法 pin 一个约定版本，只能 pin 某个 commit 或快照。这意味着今天按某版约定设的"低基数标签白名单"，明天约定加字段就可能破防；属性名会漂移，基数预算却没有随之重审的机制。

**趋势三：中国厂商在 2026 下半年集体把"高基数预聚合"写进 Agent 可观测底座，但只讲吞吐、不讲被裁掉的维度。** 火山引擎 QCon 2026 北京站（钱世俊《给 Agent 做"CT"》）披露：把指标标签从 map 改成可排序 slice，编码效率提升 30% 以上，200K QPS 下 OneAgent 吞吐约为 OTel Collector 的两倍，并对"高基数、高密度原始数据做预聚合以加快查询"。腾讯云 9 月 21/23 日上线 Agent 可观测服务，基于 OTel GenAI 语义约定做统一数据模型，覆盖 16 种主流框架。二者共同点是：把基数当性能工程解决，"哪些维度被预聚合掉、谁批准的、还能不能查回"没有字段。

## 二、技术现状

把 Agent 遥测链路拆开，能力分布是"采集强、归位弱、举证空"：

- **采集与语义**：已较成熟。Google Cloud ADK 基于 OTel，Application Monitoring 从 trace 按语义约定标签过滤聚合出派生指标（错误率、token 用量）；Anthropic Claude 的 OTel SDK 默认 metadata-only、可选全内容；OpenAI Agents tracing 提供 session/turn/span 与 OTLP JSON 导出。三家都遵循 GenAI 约定，但如上所述约定本身未版本化。
- **基数控制**：散落在采集器与后端。主流做法是 Collector 层丢弃/重写非法标签、集约定白名单、后端配额与降采样限流；InfoQ 9 月 17 日的实务总结给出一句可当纪律的话——"把动态会话 ID 放进指标标签会产生高基数时间序列，可能压垮指标服务器；细粒度会话上下文应严格留在 trace 或结构化日志"，即"追踪用于调试，指标用于告警"。
- **溢出可见性**：最薄。SDK 暴露 `otel.metric.overflow=true`，但多数后端不把它做成一等告警信号；谁、哪个 metric、哪个 instrumentation 触发了溢出，通常要人工翻。更关键的是——**没有任何一家把"本次 SLO 判定所依赖的维度，是否落在溢出里"做成可上报字段**。

现状可一句话概括：**行业把基数当成本与性能问题在解，却没人把它当诊断正确性问题在举证。**

## 四、技术挑战

1. **总数正确是最危险的伪装。** 溢出设计保证 Sum/Count 守恒，因此一切以总量为分子分母的看板都"看起来健康"；但告警、SLO、分组成本归因全按维度切，维度被抹即少算。这与 #83 采样面是镜像：采样丢的是"没被抽中的记录"，溢出丢的是"记录里被切掉的分组"——后者更隐蔽，因为记录本身还在。

2. **阿姆达尔式乘法放大。** 单个维度取值不多，但多个维度相乘即爆炸：10 路由 × 5 状态 × 4 区域 = 200 序列，加一个 10000 取值的 `customer.id` 就成 200 万。逐个审查属性"看起来都合理"，组合起来压垮后端；而 Agent 的 session/user/prompt 正是天生高基数的那一类。

3. **语义约定漂移使白名单风化。** GenAI 约定迁仓且未版本化，属性名随快照变化；基于旧快照的"低基数白名单"可能在新快照下失效，而没有任何机制在升级时重审基数预算——这是 #230 知识保鲜在遥测 schema 上的翻版。

4. **"归位到 trace"在实践中常常落空。** 教科书答案是"高基数标识符放 trace/日志"，但 trace 有采样率、有留存期、有访问权限；一旦被采掉或过期，那个"被从指标裁掉的维度"就彻底无处可查。把维度从指标挪到 trace，不等于维度还在。

5. **预聚合是一次无人署名的语义决策。** 火山引擎把高基数数据预聚合换吞吐、观测云用流式聚合复用换秒查——都是正当工程，但"保留哪些聚合、丢弃哪些切片"本质是替未来的排障者做选择。没有 `aggregation_manifest`，事后无人能还原"当时是按什么维度聚的"。

## 五、展望与建议

- **立 `cardinality.*` 五字段并进 OTel GenAI 提案**：`active_series_per_stream`（每流活跃组合数）、`cardinality_limit`（上限配置）、`overflow_datapoint_rate`（溢出点占比）、`overflow_affected_dimensions[]`（被抹掉的维度名）、`dimension_query_undercount_rate`（分组查询相对总量的少算率）。缺省 `CARDINALITY_UNVERIFIED`。
- **把 overflow 升为 SLO 一等信号**：不是"raise the limit"，而是"溢出即告警"；一个 metric stream 出现 `otel.metric.overflow=true`，就必须回答"哪条 SLO 依赖的维度受影响"。
- **建立双层基数预算**：技术天花板（SDK 上限）+ 语义预算（诊断/SLO/业务关键旅程必须保留的维度），两者分开配置、分开审计；白名单随 GenAI 约定快照一起版本化，升级时强制重审。
- **预聚合署名**：凡做预聚合/降采样，产出 `aggregation_manifest`——保留维度、丢弃维度、决策人、生效时间、可否回溯原始组合；把"用维度换吞吐"从隐形工程变成可举证的运维决策。
- **归位要可查**：高基数标识符下沉到 trace/日志时，同步登记采样率与留存期，确保"被裁掉的维度"在留存窗口内确可查回；否则不算归位。
- **基准补题**：SRE-Bench／o11y-bench 增加"总量正确但分组被溢出"题型——只报总量分的 Agent 应判失败；信通院六维可增补"基数可举证率"一格。

**新观点小结（本期相较往期的角度深化）**：往期把"绿"拆成真绿与假绿，本期再切一刀——**总量绿、分组绿、证据绿是三种独立的绿**。传统可靠性看总量绿，Agent 诊断看分组绿，事后问责看证据绿；基数溢出专打中间那层，且用最外的总量绿做掩护。把这个层次分清，才不会把"总数分毫不差"误当成"诊断论据齐全"。**总量守恒可以被采购，分组可信只能被举证。**
