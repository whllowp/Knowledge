# AI-SRE 技术洞察（第 199 期）

**生成时间**：2026-11-16 02:31（北京时间）｜**窗口**：2026 年，重点最近 30 天
**本期主题**：身份面／工作负载身份（Workload Identity）——Agent 用谁的凭据？共享 key 让审计归零

---

## 题眼

72 期说「治理发给的身份与遥测记录的身份，中间没有 join key」；163 期说「凭据要被发现、轮换、回收」；166 期说「说过不等于能证明说过」。三件事在**身份**上合成一个基础问题：**Agent 执行动作时，用的是谁的凭据？** 常见答案有三种：**人的凭据**（把用户的 token 透传给 Agent）、**共享的服务账号**（一个 key 所有 Agent 用）、**每个 Agent 自己的身份**（最少见）。前两种的代价是同一个：**审计里看不出是哪个 Agent 做的、轮换时不知道影响谁、出事时只能定位到「某个服务」**。**身份不是登录问题，是归因问题：没有独立身份，就没有独立责任。** **而共享 key 的审计，只能写到「某个服务」。**

## 一、发展趋势

**趋势一：从「共享服务账号」转向「每 Agent 一个身份」。** 工作负载身份、短期令牌；**可归因、可轮换**。

**趋势二：从「长期 key」转向「短期凭据」。** 分钟级有效期；**泄漏窗口小**（163 期）。**长期 key 是「永不过期的信任」。**

**趋势三：身份进入审计主键。** 每条动作带 `agent_id`；**没有它，日志只是故事**（166 期）。

## 二、技术现状：三种身份，通常混成一种

**人的身份：最常被透传。** 用户 token 给 Agent；**审计看起来像用户自己做的**（109 期）。

**共享服务账号：最省事。** 一个 key 全员用；**归因只能到「服务」**（72 期）。

**每 Agent 身份：最少见。** 独立身份、独立权限；**建设成本高，但可审计**。

**现状：日志里有「谁」，但没有「哪个 Agent」。** 身份字段缺失；**join 不上**（72 期）。

**三种身份错法，一种比一种难查。** 透传（像用户做的）、共享（像服务做的）、幽灵（没有身份）；**三种都让归因断链**。

## 三、技术竞争力：主要厂商／方案对比

**判读与本期反转。** 把「join key」讲清的是 72 期，把「轮换」讲清的是 163 期，把「举证」讲清的是 166 期；**六家云厂商 Agent 平台「每 Agent 身份／动作归因／审计主键」三列全空**。与 72 的分工：72 管「身份对不上」，本期管**「身份根本不存在」**；与 163 的分工：163 管「key 怎么轮换」，本期管**「key 属于谁」**；与 109 的分工：109 管「委托范围」，本期管**「以谁的名义执行」**。判词：**「IAM」「OAuth」「密钥管理」「审计日志」全部可采购，「举证这个动作是哪个 Agent 以谁的名义做的」不可采购。**

## 四、技术挑战

**一，透传用户 token。** 审计像用户做的；**Agent 的错误记在人头上**（109 期）。

**二，共享 key 无法归因。** 只能定位到服务；**五个 Agent 共用一个**（72 期）。

**三，轮换影响面不清。** 换 key 影响谁；**没有依赖图就只能全换**（173 期）。

**四，委派链太长。** 人→Agent→子 Agent→工具；**每层都可能换身份**（144 期）。

**五，短期凭据有成本。** 每次签发/校验；**高频调用下开销明显**。

**六，跨系统身份不统一。** 云上/云下/第三方；**同一 Agent 三个身份**。

**七，身份与成本脱节。** 成本按服务记账；**分不清哪个 Agent 花的**（165 期）。

## 五、需求分解、用户旅程与实现方案

### 5.1 需求（按优先级）

- **R1 `identity.*` 字段**：`agent_id`、`delegator`、`credential_type`、`ttl`、`scopes`、`audit_key`。
- **R2 每 Agent 身份**：独立身份与权限；**不共享 key**。
- **R3 短期凭据**：分钟级；**自动续期**（163 期）。
- **R4 动作归因**：每条动作带 `agent_id`＋`delegator`；**审计主键**（166 期）。
- **R5 轮换影响面**：按身份查依赖；**灰度轮换**（173 期）。
- **R6 指标**：独立身份覆盖率、共享 key 残留率、归因完整率、轮换影响可查率。

### 5.2 用户旅程

- **平台工程师**：新 Agent 上线 → 签发独立身份 → 绑定权限 → 记录委派链 → 成本标签。
- **SRE**：异常动作 → 查 `agent_id` → 定位到具体 Agent → 不影响其他。
- **安全**：轮换 → 查影响面 → 灰度替换 → 回收旧身份。
- **审计**：抽查动作 → 核对身份与委派 → 确认可归因。

### 5.3 实现方案（90 天）

- **0–30 天：盘点。** 列 Agent 与凭据；标共享 key。
- **30–60 天：独立。** 每 Agent 身份；短期凭据；动作归因。
- **60–90 天：轮换。** 影响面查询；灰度轮换；指标上线；成本按 Agent 分摊。

**第 140 个市场空白（五项）**：独立身份覆盖率、共享 key 残留率、动作归因完整率、短期凭据覆盖率、轮换影响可查率——无一内建；`identity.*`／`workload.*` 为**第 109 次无人提字段族**。本地 173／173-kb 连续第 99 期成组启用：周昕毅 10「白名单动作、危险动作需审批」＝全库唯一把「危险动作」写成硬规则的实践，本期首次当主线；配 72 期对齐、163 期凭据。判词：**本地把危险动作写成白名单，联网侧 2026 年才量出「身份与遥测没有 join key」；两边都没把「这个动作是哪个 Agent 以谁的名义做的」做成审计主键。**
