# SRE Agent 领域技术洞察（第 228 期）

**主题：检测—拦截面 / 事后标记幻觉（Detection–Interception Gap / Post-hoc Flagging Illusion）**
**时间范围：2026 年（重点最近 30 天）｜生成时间：2026-11-16 20:00**

> **题眼**：Google 在 11-12 亲手把自己的 87% 拆开——那不是"拦截率"，是"有害指令执行成功之后被标记出来供调查的比率"。检测回答"出事后我能不能认出来"，拦截回答"出手前我能不能挡住"。这是两条独立的轴：一个系统可以检出率 99% 而拦截率为 0%。把检出率当拦截率汇报，等于把"事后能破案"包装成"当场拦得住"。异步分析的设计又决定了——结果出现时，钱已经转走、信已经发出。

---

## 一、发展趋势

最近 30 天，Agent 安全与运维的可观测叙事出现一次重要的口径修正。过去厂商比拼"能发现多少异常"，如今头部机构开始主动承认"发现"与"挡住"不是同一件事。

Google 于 2026-11-12 公布 Agent Anomaly Detection 的第一份外部基准评测，用五个非 Google 制定的公开基准（AgentDojo、InjecAgent、ASB、AgentDyn、AgentHarm）跑出 1774 段 session，并把失败案例与误报率一并摊开。新闻里最醒目的 87%，官方定义是"有害指令确实执行成功的案例中，被标记出来可供事后审查的比率"。把模型没读到、读到但抵抗掉的攻击放回分母，整体标记率落到 45%–62%。Google 明确写道：这套服务在代理执行流程之外**异步**分析，"结果出现时操作多半已经完成"，扮演的是事后调查角色；转帐、寄信、大量改文件之前的挡关，靠的是事前权限与核准程序。报告把两种能力明确分开，"锁与监考官各司其职"。

同一时间轴上，OpenAI 于 11-09/10 披露内部 Control Room：每个研究任务申请唯一 job_id 并绑定已批准的安全论证，推理引擎在返回输出前必须向 Control Room 校验权限，撤销后最长 35 秒停止输出，且采用 fail-closed——服务不可用时拒绝一切请求。它管的是"inference 该不该继续生成"，而非"事后标记了什么"。这两个动作构成一条清晰的分界线：**一个缩短反应时间，一个负责完整重建过程，二者互补而非替代**。国内侧，火山引擎 AgentSentry、大模型应用防火墙、飞连 Agent 行为护栏把策略执行动作分成"审计／提醒／拦截／安全代答"，腾讯云 AI Agent 安全网关于 2026-10 上线，阿里 AI 安全护栏在 WAF 侧做 SSE 实时检测。行业正在把"观察"和"阻断"拆成两个可分别采购的能力。

## 二、技术现状

把"检测"与"拦截"混成一个"异常检测"按钮，是当前产品页最普遍的口径模糊，具体表现为五个可观测缺口：

**其一，分母切换。** 同一个服务，87%（已执行攻击被标记）、45%–62%（全部攻击被标记）、18 案查出 4 案（毒记忆）是三个不同问题的三个答案。引用哪一个，取决于你把谁放进分母。87% 是"已穿过模型层、有害操作真发生了"之后的可调查率，不是防线强度。

**其二，时间差是架构决定的危险窗口。** 异步分析不占用每次工具调用的等待时间，代价是结果出现时操作已完成。这不是工程优化能抹掉的延迟，而是"流程之外分析"的固有属性。用检出率去论证"我们挡得住"，在时间维度上就是错的。

**其三，检测器的沉默是二阶盲区。** 约 6% 的 session 没有得到任何检测结果。Google 自己提醒：监控面板上"没有告警"与"分析没有完成"应该是两个不同的字段，否则检测服务本身故障时，画面看起来反而最平静。这与第 220 期"告警收敛面的沉默"是同一类病、不同对象——那里是基础设施被判不算数，这里是检测器自己没跑完。

**其四，可见性取决于攻击藏在哪里，而非攻击本身。** 写在用户消息里的有害要求约 55% 触发标记（服务读得到）；藏在工具输出深处、被模型抵抗掉的指令只有 11%–25% 触发。同一类攻击，检出率相差一倍以上——检出率不是攻击的属性，是"攻击在遥测里露没露脸"的属性。

**其五，暖机悖论与毒记忆盲区。** AgentDyn 上正常历史从约 220 段增至 360 段时，已执行有害指令检出率从 33% 跳到 99%——新 Agent 最需要保护的初期恰恰最看不见，而风险与新颖度正相关，保护却与历史长度正相关。毒记忆 18 案只查 4 案，因为有害内容先存进记忆、后在别的工作里发作，单看一段 session 的异常度很低；session 级检测器切断了跨 session 的因果链。

## 三、技术竞争力（主要厂商 / 方案对比）

| 方案 | 事后标记 / 检出 | 事前拦截能力 | 拦截率是否独立上报 | "无结果≠无告警" | 暖机 / 毒记忆披露 |
|---|---|---|---|---|---|
| Google Agent Anomaly Detection | 87% 已执行标记；全攻击 45%–62%；毒记忆 4/18 | 不拦截；事前靠 Semantic Governance Policy、Model Armor、真人核准 | 否（官方主动拆口径，但无拦截率字段） | 是（明确提示约 6% 无结果） | 是（220→360 段、33%→99%；误报 2%–16%） |
| OpenAI Control Room | 失配监控标记率另计（往期 42.9%/57.1%） | 强：任务 ID + 推理前鉴权，fail-closed，35 秒→目标 0 | 部分（停指令到拦截时延有报，拦截成功率无独立字段） | 否 | 否 |
| Anthropic Claude OTel → Databricks MLflow | 原生 trace / span 记录执行序列，供事后证据调查 | 无拦截内含；靠外部护栏与自托管 | 否 | 部分（提示默认 NO_CONTENT，缺证据可见） | 否 |

| 腾讯 AI Agent 安全网关 | 提示注入 + MCP Tool 投毒双防线 | 中：入口治理、"谁能用／能访问什么"，2026-10 上线 | 否 | 否 | 否（公开细节有限） |

**本期反转**：把高检出率写进发布材料的，是各家 Agent 平台；而亲手把"87% 不是拦截率"拆清楚的，是 Google 自己的技术博客——它同时交出外部基准、失败案例、误报率和 6% 无结果。最锋利的对照是：越接近生产，越把"标记"与"拦截"分开报（OpenAI Control Room 的 fail-closed、火山的四档动作）；越靠近产品页，越把两者糊成一个"智能检测"按钮。判词：**"异常检测、87% 检出、告警分级、行为护栏、审计日志、安全代答"全部可采购，举证"这次高危动作是在执行前被挡下的、不是执行后被标记的""检测器失联时你收到了信号"不可采购。** 六家在"拦截率独立上报／无结果与无告警分离／毒记忆跨 session 检出"三列几乎全空。

## 四、技术挑战

挑战不在"能不能检测"，而在"检测与拦截之间那条没人负责的缝"。

第一，**时间差无法用调参消除**。异步分析的结果天然滞后于操作完成，除非把检测移到执行路径内——那又会引入延迟与可用性耦合。这是一道架构取舍，不是 KPI 问题。

第二，**"拦截"本身会造成体验与成本副作用**。火山的"安全代答"用安全回复替代原始回复以减轻阻断冲击，说明直接拦截并非免费；误报率 2%–16% 直接吃掉工程与安全人员时间。给低权限摘要 Agent 设的阈值，搬给能对外付款的 Agent 就会既漏又扰。这笔"误报税"目前无人记账。

第三，**检测器自身没有独立 SLO**。约 6% session 无结果、fail-closed 一旦自身不可用就全面拒绝——检测/鉴权服务从"observer"变成"关键路径上的单一故障点"，它的存活性、覆盖率、暖机状态都需要被单独观测，而多数产品没有把这些做成可导出字段。

第四，**跨 session 因果链断裂**。毒记忆类攻击把 harmful 内容先写进长期记忆、后在无关任务里发作，session 级标记器的观察窗口小于攻击的时间跨度。这与第 213 期因果闭合、第 200 期工具供应链信任同源，但本期具体在"检测器的观察窗口"这一层。

第五，**责任边界模糊**。Google 报告明说Unsafe 内容先存进记忆再发作——写入时像合法偏好、发作时才显形。谁来标定"这一刻的异常源自那一次的写入"？链条缺环，检出率再高也只是事后标签。

## 五、展望与建议

提出五项 `detect.intercept.*` 字段族建议（本期第 128 次无人提字段族），对应第 162 个市场空白：

1. **`detected_at` 与 `blocked_at` 分离时间戳**——高危动作必须同时记录"何时被标记"与"何时被挡下"；只有 `detected_at` 的动作，一律归入"事后标记"，不计入拦截率。缺 `blocked_at` 标 `INTERCEPTION_UNKNOWN`。
2. **`interception_rate` 独立上报**——分母是"全部试图的高危动作"，与检出率并列展示，禁止用检出率代替。引用第三方 87% 类数字时，强制标注分母口径。
3. **`no_result` 与 `no_alert` 分列**——检测器没跑完（约 6% session）必须单独成一个字段并触发自身告警；面板把两者混为一谈时，检测服务故障会伪装成"最平静"。
4. **`warmup_history_count` 声明**——检测/鉴权服务暴露当前 Agent 的基线历史段数；低于阈值（如 300 段）时输出"覆盖不完整"，并禁止把初期表现外推为稳态水位。
5. **`cross_session_causal_link`**——对记忆类攻击，把"写入 session"与"发作 session"双向锚点记入 trace，让单看一段看不出异常的案例仍可被串起；毒记忆检出率单列，不与整体检出率混算。

配套动作：把事前控制（最小权限工具集、工具调用前的策略校验、付款/外发真人核准）排在检测器之前部署——这是 Google 报告与国内厂商四档动作的共同结论；对自家 Agent 重放几组已知任务，分别量出"标记质量"与"拦截质量"两套数字；把检测/鉴权服务本身纳入值守 SLO，与第 220 期沉默验证、第 227 期工具熔断串成一条"看门人也要被看"的闭环。

> **本地知识沉淀（连续第 117 期启用）**：29 陈忻《B2B 跨境支付的 AI 驾驭实践》首次当主线——全库唯一把"严格指标 100% 通过才放行"写成硬门禁、把 AST 确定性红线放在 LLM 复审之前的实践；配 05 刘凯宁"工程交给工程"的确定性笼子、09 吴垚"接住告警—打标—沉淀真实根因"的反馈闭环。判词：**本地把"先拦截、后复审"做成放行门禁，联网侧 2026 年才用 87% 这个数字把"事后标记≠事前拦截"拆开；两边都没把"这次高危动作是在执行前挡下的还是执行后标记的"做成可导出字段。**
