# 记忆技术洞察 · 第156期（20261127-0200）

> 洞察范围：2026 年、尤其近 30 天，AgentMemory 发展趋势／技术现状／技术竞争力／技术挑战四维度。主线：arXiv 2611.34624（11-25 提交），系往期仅作工程侧记的 HoMe 首次深度专题。本期已与本地 C/E 双版索引及知识台账比对，未重复前期主题。

## 一、发展趋势
长程助手的记忆行为由 harness——构造、维护、检索与作答的代码、提示和配置——决定，而 harness 调优长期靠手工。11-25《HoMe》（arXiv 2611.34624，上海交大／阿里／北大，Yifei Xu 等九人）把优化器本身工程化：不设计新架构，而在已调优的强 harness 上做评测驱动迭代。与 #143 划界：#143 让优化器记住"改动理由与预测—实测"，本期追问的是优化控制面——如何诊断、准入、采样、版本化与停止。

## 二、技术现状
HoMe 以文件原生记忆系统 ReMe 为底座，拆为共享 runtime 与插件，令评测差异只来自 harness。Optimizer 与 Diagnoser 两代理协作：初始 harness 全量评测后存为 Git 根提交，每条分支检验一个假设；每会话后提交记忆文件，相邻 diff 恰是该会话的全部变化。失败由低分查询沿轨迹回溯，定位到构造／检索／作答部件并跨案例归并共享机制。候选先过冒烟测试与准入闸门：前半预算只收改运行时机制者，拒绝纯提示或参数微调；后半才放开。正式评测用 EMA 损失、陈旧度、观测不确定度、未复核错误与 ε 均匀探索引导两级采样；构造过程未变时按概率 ρ 复用祖先记忆态。

## 三、技术竞争力
LongMemEval-S 由 0.888 升至 0.916，查询 token 由 43.9K 降至 17.9K；BEAM-1M 由 0.650 升至 0.704，101.8K 降至 60.4K，且训练只用 100K 上下文、测试历史约长八倍。第二次独立搜索达 0.720／68.3K，配对自助法增益 +0.054（p=0.0002）与 +0.070（p<0.0001）。较自动优化基线 MemPro，LME 高 10.4 点、token 少 81.5%，BEAM 高 1.1 点、少 7.6%。跨基准迁移更显著：在 BEAM-100K 上搜出的 harness 直接测 LME 得 0.908／26.6K，反超起点 ReMe 的 0.888／43.9K。优化耗时 10.4 小时对 11 小时 23 分，优化 token 185.2M 对 331.2M（−44.1%）；每次 BEAM 正式评测 10 例／100 问，案例减半、问题减 75%。

## 四、技术挑战
末两个候选不再扩展帕累托前沿，继续迭代易被采样噪声与过拟合吞噬；均值上涨并非处处上涨，LME 多会话题、BEAM 知识更新与信息抽取反而退步，须设分类别护栏。分数由 LLM 裁判给出，且各轮采样子集不同、聚合分不可直接比较，最终选择仍依赖共同案例与覆盖度的人工式裁决。记忆态复用按概率执行，以防构造随机性丢失；提示微调虽被延后半程，仍可能诱导对基准的钻空。产品侧尚无自动诊断、准入与评测成本账。

## 五、需求分析
部署方要的不是又一个"更强架构"，而是能在自有数据与模型上复现的调优闭环：一次失败可定位到具体会话与部件，每次改动的效果与 token 代价同账记录，换基准或换模型后能判断哪些 harness 仍适用。审计方需要分类别不退步的证据，而非单一均值。

## 六、用户旅程
接入 ReMe runtime→全量评测初始 harness 并建立 Git 根提交→线上失败连轨迹回流→Diagnoser 跨案例归并失效机制→Optimizer 提交候选→冒烟测试＋门控裁决准入→自适应抽样评测→收益保留、退步也留档→按帕累托前沿冻结→跨基准迁移复用。

## 七、具体实现方案
①runtime／plugin 分离，候选只改插件；②记忆目录按会话提交，diff 支撑可回退归因；③门控分相：前半预算只准改表示／构造／检索等运行时机制，后半放行提示与配置；④采样器按 EMA 损失、陈旧度、观测次数与未复核错误排序，保留 ε 均匀探索；⑤构造未变时按 ρ 复用祖先记忆态，只重跑检索—作答—评分；⑥验收同时看分数与查询 token，并设类别退步闸门；⑦AML 补 harness-optimization 维度：机制命中率、门控拒绝率、复用率、每提升一点的评测 token、类别退步率。

## 本期新观点
1. **记忆优化的对象上移到"外壳"**（接 #143 划界、深化 #155）——#143 记的是优化器的编辑理由与预测—实测，本期优化的是诊断／准入／采样／版本化／停止这套控制面；harness 是被评测搜索的一等对象，而非背景代码。
2. **结构探索必须先于参数微调**（反直觉、深化 #94 gaming）——便宜的提示与阈值改动会垄断候选、且会被后来的代码改动作废；HoMe 用前半预算的门控制度性延后它们，把搜索推向共享失效机制而非局部补丁。
3. **诊断单位是跨案例的"机制"而非单个失败**（接 #110 划界）——#110 诊断解题 agent 的失败阶段，HoMe 诊断记忆系统自身的构造／检索／作答部件；会话级 Git 版本让中间记忆态按需可取，失败才能从个案上升为机制。
4. **评测成本进入搜索目标本身**（深化 #5 记忆税）——冒烟测试、两级自适应采样与按 ρ 复用构造态，使 10 例／100 问的短评测选出跨基准可用的 harness；预算不是外部限制，而是决定候选质量控制面的设计变量。
5. **验收必须是分数—token 帕累托双轴并设类别护栏**（深化 #150／#155）——均值涨而多会话、知识更新、信息抽取退步，单看总分会验收出退步系统；末两候选不扩前沿提示停止条件应进优化器。
6. **研究到开源的落地周期缩短，但产品侧仍缺半条链路**（五项目倒挂）——五家无新主线版本；ReMe 11-26 README 已把 HoMe 作为插件发布（LME 91.6%／17.9K、BEAM 70.4%／60.4K），但其公开能力是代码／提示／配置搜索，无自动机制诊断、准入闸门与评测账，更无 #155 的模型级采用门控。AML 补 harness-optimization 维度。
