# AI-SRE 技术洞察 · 第 37 期

**主题：运行态面运维——当智能体从"一次调用"变成"一台常驻的机器"**

- 期次：2026-11-02 22:00（第 37 期）
- 覆盖窗口：2026-10-03 ~ 2026-11-02（重点为最近 30 天，核心事件集中在 10-27 ~ 11-02）
- 本期定位：前 27 期管的是智能体"想什么、记什么、说什么、花了多少"（内容与决策层）；本期换到载体与进程层——它在哪台机器上、还活着吗、睡着时占多少、醒来还是不是同一个、跑的是哪个版本。

## 一、发展趋势

三周之内，"智能体跑在哪"从一个部署细节变成了三家云厂商各自押注的产品命题。10 月下旬到 11 月初，Google 的 Agent Compute Engine（ACE）给每个 agent 一台硬件隔离的 microVM，模型或人回话时唤醒、空闲时休眠、亚秒级恢复，还能快照、分支成并行副本、回滚；AWS 开源 Infinity，用 UC Berkeley Hydro 的思路让等待中的 agent"几乎无重量"，8GB 内存装下约 7.5 万个空闲 agent；腾讯云在 10-29/30 数字生态大会上整体升级 Agent Runtime 矩阵，CubeSandbox 最快 60 毫秒起沙箱、同构镜像每分钟交付 60 万个，任务等待时暂停并释放 CPU 与内存，恢复后接着干。

三家在回答同一个问题：一个会等人、会跑几小时、会中途断线的进程，该按什么单位被供给、计费、恢复。这问题在传统云上不存在——云原生三十年的默认前提是无状态请求，进程随时可杀，状态在数据库里。智能体的默认前提正相反：有状态、高空闲、长驻留。

第二个变化在负载侧。腾讯 11-02 一篇 MaaS 长文披露了 MiniMax 后训练的环境账单：500 万条轨迹、两周周期的数据合成对应约 1.48 万个并发沙箱；在线强化学习 2000 任务、每任务 32 路 rollout 需要约 6.4 万个并发沙箱；后训练镜像已到 500 万量级并奔向千万级，而每次启动通常只读取镜像约 6%。这组数字说明：**沙箱的第一大客户不是生产运维，是训练与评测**。运行态的启动时延、镜像分层与成本曲线，被训练负载而非 on-call 塑造——生产运维顺带受益，也顺带排队。

第三，架构共识已成但命名混乱。Anthropic 把 Managed Agents 讲成 brain/hands 分离，状态放在上下文窗口之外，harness 只把下一步需要的部分重新注入；腾讯叫 Brain–Hands 分离，与 Agent-in-Sandbox 并列；DeepSeek 的 Super Agent 更直白——大脑在云上、任务记录单独存、代码文件留在原来那台电脑，另配一个看"进展有没有跑偏"而不是只看"有没有宕机"的 Watchdog。说法不同，内核一致：进程可以死，状态必须活。

第四，标准层与运行态解耦。10-22 Anthropic 把 Agent Skills 捐给 Linux 基金会下的 Agentic AI Foundation，规范、名称、Logo 与域名一并交出，官方称 70 多个平台集成（厂商自述，未独立核实）。能力包一旦跨平台可携带，"身体"的差异就变成选型变量。

## 二、技术现状

**（1）空闲的三种经济学。** ACE 卖的是"一台电脑"：硬件隔离、密钥不进沙箱、出站由网关按 agent 的临时身份校验并代注入凭据、无直连互联网，计费概念上按机时。Infinity 卖的是"让它几乎不存在"：idle 时近乎零内存占用，卖密度。腾讯卖的是"沙箱秒"：暂停释放算力、恢复续跑，配合镜像预热与模板快照把启动压到 60ms。同一个"空闲一小时"，在三种账单上是三个数。

**（2）状态被拆成三层，但只有两层有产品。** 进程态（快照：内存、文件系统、描述符）、语义态（checkpoint：计划、已完成步骤、待确认项）、世界态（外部副作用与被改动的记录）。腾讯与 ACE 给第一层，LangGraph 式 checkpointer 与 Anthropic harness 给第二层，第三层无人提供——theCUBE Research 在 25 位企业技术与安全负责人的访谈中把这句话说得最清楚："恢复一个 agent，不会撤销它已经改过的记录和交易。"

**（3）启动时延进入 SLO。** 60ms 起沙箱、亚秒级 pause/resume、镜像按需加载只读 6%——这些数字此前只属于函数计算，现在直接决定 agent 的 TTFT。第 28 期把它记进等待预算；本期补一句：它也是运行态成本，预热是把钱从时延账户挪到内存账户。

**（4）版本边界成了最薄的一层。** 百度 AgentOps 把问题点得最准：Agent、Skill、Prompt、工具与知识"缺少统一版本边界，调试容易污染线上"。一个镜像就是一个版本、回滚原子；智能体的版本是这五类的笛卡尔积，回滚只能回滚其中一层。百度的解法是平台化托管——20+ 个 SRE Agent、50+ 个公共 Skill、3 套模板，迭代周期天级降到小时级，示例场景 MTTR 60 分钟降到 10 分钟；安全侧用 L1 构建时约束、L2 第三方意图审计、L3 本地 Hook、L4 网关代理四道防线。

**（5）"谁来运维运维者"开始有产品。** Virtana 允许其他厂商的 agent 通过 MCP 或 A2A 加入同一场事故，带 token 与审批上限；Monte Carlo 的 Bayes 主动发现已部署的 agent、诊断并修复其失败；New Relic 让 Change Tracking 读一个 PR、写一份监控计划、在 10 分钟到 72 小时六个点给部署打分。观测量正从"请求"移到"实例与会话"。

**（6）范式之争有一组硬对照。** Meta 的 onboarding agent 把某子系统的规则套到另一个子系统上；事故后 Meta 没有继续加提示词，而是重构成 14 个专用 agent 加一个小型确定性编排器，配置时间从三四天降到一小时以内。这与第 29 期"去编排器省 50%"方向相反但不矛盾——规模上去后，编排器不是成本项，是收敛项。

## 三、技术竞争力（主要厂商/方案对比）

| 方案 | 运行单元 | 空闲处理 | 状态与恢复 | 启动时延 | 版本/回滚边界 | 平台自监控 |
|---|---|---|---|---|---|---|
| Google ACE（+开源 Agent Substrate） | 每 agent 一台硬件隔离 microVM | 唤醒/休眠，亚秒级 | 快照、分支并行副本、回滚；密钥在沙箱外 | 亚秒级 | 快照级，绑定 agent 身份 | 网关按临时身份逐请求校验 |
| AWS Infinity + AgentCore | 可承载数十万 agent 的运行时 | idle 近乎零重量（8GB≈7.5 万） | 运行时/网关/身份/记忆/评测分项计费 | 未公开 | 分层计费但版本语义弱 | 各子服务独立 |
| 腾讯云 Agent Runtime | 沙箱 + AgentCBS/CFS/Bucket | 暂停释放 CPU 与内存 | 快照/克隆/暂停恢复；凭证沙箱外按任务授权 | 60ms（同构 60 万/分钟） | 沙箱镜像 + 状态分存 | AgentObs 会话·轮次·步骤 |
| 百度 AgentOps | 托管运行实例 | 健康检查、依赖切换 | 会话状态持久化、实例恢复 | 未公开 | 五类资产统一版本边界（自述） | 五大中心：管理/安全/变更/评估/知识 |
| Anthropic Managed Agents | 托管 harness | 会话空闲保留 | 状态在上下文外，按需重注入 | — | harness 版本 | 无独立运行态面板 |
| Azure Foundry hosted agents | 容器计算（按容器计费） | 平台托管 | Agent 引用 + previous_response_id | — | agent 名称+版本号 | Azure Monitor / App Insights |
| Akamai Agent Sandbox | WebAssembly 隔离 | 按 Functions 计费 | 无长驻状态 | 毫秒级 | 函数版本 | 计算/内存/出网上限可配 |
| Kiro Crew / 开源 harness | 常驻编排层（Apache 2.0） | 异步持久会话 | 编排层状态自持，推理走 Bedrock | — | 开源层可改，运行时闭源 | 依赖外部可观测 |

**判读一：三家在答三个不同问题。** Google 答"隔离与凭据"——沙箱里没有密码，网关按临时身份代注入，把"边界"做进了运行态；AWS 答"密度"——把空闲成本压到接近零，让"多智能体"在账上成立；腾讯答"交付速度与续跑"——60ms 与快照恢复直接对应"接得住洪峰、断得了线"。买哪家，等于先承认最怕哪种失灵。

**判读二：开源的是身体，闭源的是大脑。** AWS 开源 Infinity 运行时、Google 开源 Agent Substrate 供自有 K8s、腾讯开源 CubeSandbox 底层，但推理侧都牢牢收在自家（Bedrock、Gemini、混元）。Kiro Crew 的"open harness, closed engine"是同一结构的另一种写法：编排层可审计，推理层按量计费且不可替换。

**判读三：能力分布不对称。** 海外强在隔离与身份（ACE 无密钥、Akamai 的 WASM 上限、CNCF 那句"agent 的身份不得修改定义它自身权限的对象"）；国内强在状态工程与训练负载的规模实践（腾讯快照克隆、百度五类资产版本、MiniMax 6.4 万并发沙箱）。

**判读四：共同空白是"恢复是否真的一致"。** 八家都在做"能恢复"，没有一家把"恢复后与恢复前是否等价"做成指标或承诺。

## 四、技术挑战

**（1）恢复点分裂。** 进程快照恢复到 t₁，语义检查点恢复到 t₂，外部世界已走到 t₃，三个时间戳从不相等，也没有哪家在恢复流程里同时记录三者。第 28 期讲"检查点不知道世界是否已变"，本期更进一步：即使进程被完美恢复，恢复的也不是同一个智能体——凭据可能已轮换、记忆可能已被别的实例写过、上次的外部写可能已被人工回滚而它不知道。

**（2）空闲的计量单位未定。** vCPU·秒、内存字节、沙箱个数、并发会话数四种口径并存，导致三件事同时失效：容量规划无法跨平台比较、成本无法归因到业务、第 33 期的配额账本与第 36 期的查询预算无法并入同一张账单。

**（3）版本矩阵不可 pin。** 六维（模型 × harness × Prompt × Skill × 知识 × 工具）里任何一维变动都会改变行为，对外却只有一个名字。"换芯不换名"在运行态重演：回滚镜像回滚不了 Prompt，回滚 Prompt 回滚不了知识库。语义约定还能按 commit pin，Agent 的版本至今没有 digest。

**（4）托管集中化悖论。** AgentOps 把 N 个 agent 的故障域合并成 1 个平台故障域，单 agent 可靠性上升、组织级共模风险同步上升。而 theCUBE 的 25 家里只有 4 家演练过 agent 事故，11 家承认无法还原 agent 跨系统做过什么，12 家没有异常行为检测计划。**最该被演练的新单点，恰好最少被演练。**

**（5）快照与克隆制造平行世界。** 分支副本用于并行探索很有效，但每个分支都在真实世界里留下痕迹；"回滚"只回收了进程，回收不了分支已经发出的请求。第 31 期"可放弃 ≠ 可回滚"在这里变成"可回滚 ≠ 可撤销"。

**（6）观测语义错配。** APM 以请求为单位，agent 以实例、会话、轮次为单位。用请求口径看长驻 agent，会把"健康地睡着"算成"低流量"。

**（7）训练负载挤压生产供给。** 后训练的 6.4 万并发沙箱与 on-call 时临时起沙箱争同一池资源，这是第 33 期"配额串扰"在运行态的版本，且更隐蔽——争抢发生在调度器里，不在账单上。

## 五、展望与建议

1. **把实例做成一等观测对象。** 新增 `agent_instance` 语义：uptime、snapshot_age、idle_seconds、restart_count、version_digest、last_restore_reason。现有 APM 语义表里没有这些字段。
2. **恢复三时间戳对账。** 每次恢复输出（进程 / 语义 / 外部世界）三元组，把"恢复一致率"做成 SLI，而不是复盘时的一句话。
3. **空闲预算并入配额账本。** 按沙箱秒折算，与第 33 期配额、第 36 期查询预算合成一张"运行态总账"；预热成本单独归集。
4. **版本 digest 作为唯一可 pin 对象。** 六维哈希，发布与回滚按层提交、按层回退；对不齐的部分显式标注"不可回滚层"。
5. **演练"平台停摆日"。** 选一天让整条 agent 链路不可用，验证 agent-free 降级路径（静态看板、CLI、人工 runbook）还能不能撑住 P1；并把平台自身 SLO 写进被运维系统的 SLO 表，承认"生产可用性 = min(系统, agent, 运行平台)"。
6. **判断。** 2027 年运维对象的粒度会往下走一层：从"服务"到"实例"，从"请求"到"会话"。谁先把实例变成有 SLO、有 owner、有变更记录的对象，谁就先拿到 Agent 时代的运维主语——那时被运维的不只是业务系统，还包括那群替我们值班的进程。
