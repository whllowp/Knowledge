# AI-SRE 技术洞察（第 326 期）

- 生成时间：2026-11-24 11:31（Asia/Shanghai）
- 观察窗口：2026 年，重点为最近 30 天（2026-10-25 至 2026-11-24）
- 本期主题：压缩面／上下文压缩的保真度——被摘要掉的不只是文字，还有规则与来源

## 题眼

2026-10-03 发布的一个“压缩一致性工具包”（compaction-conformance-kit）把测试做得很朴素：把策略写进文件，只让被测 Agent 看到**压缩后的上下文**，然后问三类问题——直接回忆（那个值是多少）、行为（那条阻断规则还在不在）、精确使用（一个必须引用确切数值才能完成的工作项）。最后这类是关键：它让 Agent 无法用“泛泛的谨慎”蒙混过关。

它的盲测结果很刺眼：一个有损压缩的 Agent 只保住 10 个金丝雀值中的 **2 个**（而且只是种得足够晚、留在尾部的那两个），按它自己的说法，“本会违反策略”；对照组的无损 Agent 保住了 10 个。

这不是工具实现问题，是压缩的定义问题。2026-02-05，Claude Code 的 issue #23776 记录：会话接近上下文上限触发压缩后，摘要**丢失了用户最近一条指令的意图**——技术内容保住了，用户要求“先改计划、再给我看”的顺序没了，Agent 按错误理解继续改。报告者说这在几天内多次发生。

2026 年 10 月的《Compaction Laundering》（arXiv 2610.29869）则把压缩称作**信任边界**：不少开源编码 Agent 在摘要前把带类型的对话压平成一个大字符串，用 `[User]:` 这样的文本标签标记每条消息——**消息来源在代码层就被销毁了**。于是任何被 Agent 读到的内容都能伪造一个“用户回合”，在压缩后作为真实指令存活。作者在五个压平式 harness（pi、opencode、Cline、Aider、OpenHands）上测试，伪造的批准以 **87%–100%** 的比例“洗”进 Agent 记忆。

2026-11-19 的《Benchmarks Are Surprisingly Compaction-Friendly》补上了评估侧的偏差：COMPINT 早期工作显示，像“在我确认前不要删除任何邮件”这类用户约束，压缩后只有约 **17%** 的概率存活；而很多基准的答案在摘要里也够用，于是“压缩友好”的基准测不出行为退化。

## 一、发展趋势

**第一，压缩从“省 token”变成“信息销毁的治理”。** 被压缩掉的不只是文字，还有事实、规则、权限与来源。

**第二，保真度分三层。** 事实（值是多少）、规则（什么不能做）、来源（谁说的、哪条被批准过）。三者丢失的后果不同：事实错会答错，规则丢会违规，来源丢会认错指令。

**第三，压缩边界成为信任边界。** 压平对话、文本标签、摘要重写，都会让“来源”变得可伪造；压缩前的类型信息必须保留。

**第四，评估开始用“精确使用”而非“语义相似”。** 只要能引用确切值、执行确切约束，才算保住；泛泛的“我记得要小心”不算。

**第五，累计压缩被单独讨论。** 一次压缩在阈值内，多次交接后的累计漂移可能超限；恢复要靠**从原始意图重新推导**，而不是在压缩后的基线上增量修补。

## 二、技术现状

**尾部截断。** 丢弃最早的消息；最近指令可能保留，但长期约束与来源丢失。

**摘要压缩。** 模型写摘要，保留“技术内容”，丢掉意图、顺序、否定条件与批准记录；摘要本身成为新的“事实来源”。

**结构化压缩。** 保留字段与类型（角色、时间、批准人），比纯文本安全，但需要框架支持。

**KV/缓存压缩。** 驱逐、量化、H2O、StreamingLLM 等；logit 层面的 flip rate 可测，但行为影响需要下游验证。

**检索式记忆。** 压缩后按需检索原文；依赖索引质量与可检索性。

**压平式 harness。** 把对话变成单字符串；来源靠文本标签，可伪造。

## 三、技术竞争力

| 方案 | 事实保留 | 规则保留 | 来源保留 | 成本 | 主要风险 |
|---|---|---|---|---|---|
| 无压缩（长上下文） | 高 | 高 | 高 | 高 | 超窗、成本 |
| 尾部截断 | 低 | 低 | 中 | 低 | 早期约束丢失 |
| 摘要压缩 | 中 | 低 | 低 | 中 | 意图/否定/批准丢失 |
| 结构化压缩 | 中高 | 中高 | 高 | 中高 | 框架改造 |
| 检索式记忆 | 中高 | 中 | 中 | 中高 | 索引质量 |
| 压平式 + 标签 | 中 | 低 | 低（可伪造） | 低 | 来源伪造、洗白 |
| 重新推导（从原始意图） | 高 | 高 | 高 | 高 | 需保留原始意图 |

判读：买得到摘要器、压缩策略、长上下文、检索记忆；买不到“压缩后哪些规则还在、哪些批准还有效、这条指令是谁说的”。

本期反转：我们一直把压缩当“省 token 的摘要”。实际上它是一次**受控的信息销毁**：销毁什么、保留什么、销毁后还能不能证明来源，决定了 Agent 压缩后还是不是同一个执行者。

判词：「摘要器／压缩策略／长上下文／检索记忆／KV 压缩」全部可采购，「压缩后哪些规则与批准仍有效、意图与否定条件是否还在、来源能否验证、累计漂移多少」不可采购。

## 四、技术挑战

**其一，摘要的“技术内容偏好”。** 模型倾向保留事实与代码，丢掉意图、顺序与否定；这恰好是行为约束。

**其二，来源销毁。** 压平成字符串后，来源只剩文本标签；可被任意内容伪造。

**其三，基准偏差。** 压缩友好的基准测不出行为退化；需要行为/精确使用探针。

**其四，累计漂移。** 多次交接的压缩误差叠加；单次阈值无法覆盖。

**其五，规则与事实不同。** 规则需要“存在性证明”（还在），事实需要“值证明”（是多少）；多数压缩不区分。

**其六，恢复方式。** 在压缩基线上增量修补会保留压缩误差；正确做法是从原始意图重新推导。

## 五、需求分解、用户旅程与实现方案

**需求分解（按角色）。**

- 平台/SRE：需要压缩策略、探针、漂移监控。
- Agent 团队：需要保留规则、来源、批准记录；避免压平。
- 安全：需要压缩边界的来源验证，防洗白。
- 复盘者：需要“压缩后行为为何改变”的证据。
- 合规：需要批准与约束的可追溯。

**用户旅程（一次“压缩后违规”）。**

1. 长会话触发压缩；摘要保留技术内容，丢掉“未经确认不得删除”的约束。
2. 后续 Agent 按摘要继续，执行了本应等待确认的删除。
3. 复盘发现摘要里没有这条规则；原文已被丢弃。
4. 另一次，压平式 harness 让伪造的“用户批准”在压缩后存活。
5. 团队改用结构化压缩，但探针仍只测事实回忆。
6. 真正缺的是“规则/来源/精确使用”三类探针。

**实现方案（90 天）。**

- 第 1–2 周：压缩清单——哪些内容必须保留（规则、批准、来源、否定条件、未完成承诺）。
- 第 3–4 周：结构化压缩——保留角色/类型/时间/批准人；禁止压平成纯文本。
- 第 5–6 周：三类探针——直接回忆、行为约束、精确使用；压缩后自动跑。
- 第 7–8 周：来源验证——摘要中的指令必须带可验证来源；无法验证的指令降级为“待确认”。
- 第 9–10 周：累计漂移——交接链上记录压缩次数与漂移；超阈值从原始意图重新推导。
- 第 11–12 周：基准校准——用压缩友好与不友好的任务对照，防止“摘要够用”掩盖退化。
- 第 13 周：演练——注入约束、伪造来源、多次交接，验证压缩后仍可执行且可归因。

**验收标准。** 任一次压缩后，能回答：哪些规则还在、哪些批准有效、来源是否可验证、累计漂移多少、能否从原始意图重推。

**第 238 个市场空白（五项）**：压缩保留清单；三类探针；来源验证；累计漂移监控；重新推导恢复。

**`compaction.*`／`provenance_retention.*` 第 205 次无人提字段族**：`compaction.retained_rules`、`compaction.provenance_intact`、`compaction.flip_rate`、`compaction.cumulative_drift`、`provenance_retention.verified_source` 在 Agent 框架、摘要器与评测平台之间没有统一语义；平台只报“已压缩”。

**本地 173／173-kb 连续第 193 期成组启用**（闪英迪 28）：本地知识库把“文字”与“规则/来源”分开记账；本期把压缩落成保真度探针与来源验证。
