# AI-SRE 技术洞察（第 30 期）：知识供给面运维

**时间**：2026-11-02 14:00（GMT+8）
**主题**：当 runbook 成为智能体的教科书——教科书在腐烂，而智能体在替它圆谎
**范围**：2026 年，重点为最近 30 天

---

## 一、发展趋势

过去 30 天里三件事同时发生，指向同一个长期被忽视的对象：**组织既有的知识资产本身**。

**第一，知识从"人查的文档"变成"智能体执行的前提"。** 腾讯云 ES 的 Agentic AIOps 把 Skill 按只读/可写切成四类，其中"知识库 Skill"（官方文档、运维手册、历史故障案例、内核原理）内部统计承载约 **70% 的使用率**，远高于根因分析、自动化运维、实例管理三类可写能力。阿里云 STAROps 则把 Skill 与 Runbook 列为巡检计划的组成单元，用 "Learning" 把人工确认过的业务语义回写进后续巡检。

由此得出一个反直觉结论：**在今天的运维智能体里，读知识比动手更值钱**。但所有面板都在监控工具调用成功率，没有一个在监控"被读到的知识是否还成立"。

**第二，供给方式从"wiki 归档"变成"随代码变更的检查点"。** InMobi 把 runbook、运维上下文、事件数据全部搬进服务代码所在的同一个仓库，让文档获得与代码同等的所有权、版本史与 PR 评审；更关键的是**每个 PR 都触发一次"这次变更是否重要到需要改 runbook"的判断**。Sourcegraph 的判断更尖锐：AI 让代码变更快了十倍，而文档在慢速时代就已跟不上——这不是懈怠，是更新路径与致变路径分离的结构性后果。

**第三，度量从"文档覆盖率"变成"证据链闭合率"。** Cloud-OpsBench（754 用例）给出本期最硬的一根钉子：最强 agent 的联合根因准确率（JRA）在 Online Boutique 达 0.76、Train-Ticket 达 0.68，而对应**证据链闭合率（ECR）仅 0.38 与 0.15**。论文原话是"仅看最终答案正确性，会实质性高估智能体做证据落地诊断的能力"。阿里云同期开源的 BRiSE 与 RCA100/200 走同一条路：把对象、时间窗、工具、证据来源、评分规则全部固化。

知识供给面由此从"文档管理"这个后台职能，变成决定智能体上限的前台变量。

## 二、技术现状

### 2.1 腐化率已被量化，且比直觉严重

Tan 等（2022）对 GitHub 前 1000 个热门项目的研究：**19.2% 的文档至少含一处指向代码元素的过期引用，28.9% 的项目至少有一份过期文档**。这还只是能被静态检出的那一类；runbook 里"命令还在、语义已变"不在统计内。

检索侧更隐蔽：2026 年一项评测显示，**被要求作答时 RAG 有 15%–40% 的概率返回已被取代的旧值**。原因不是检索坏了，而是"检索没有时间模型"——同一事实新旧两版 embedding 分数几乎相同，向量搜索把两者一起召回，再由排序噪声决定谁进上下文。

智能体侧的失效被两组基准钉死。STALE（arXiv:2605.06527）用 400 个专家校验冲突场景、1200 条查询，把能力拆成三维：状态解析（察觉旧信念过期）、前提抵抗（拒绝"旧状态仍成立"的错误预设）、隐式策略迁移（在后续行为中真用上新状态）。**最强模型总体准确率仅 55.2%，多数专用记忆框架低于 10%**。其命名的失效模式是 "Implicit Conflict"：后出现的观测**没有明确否定**先前记忆，却已使其失效，需语境推断才能发现。ForgetEval（arXiv:2606.15903）补了一刀：13 种记忆配置的生产故障**以"遗忘失败"为主**（已轮换的凭据仍被推荐、已删除的记录仍浮出）；更要紧的是，**当测试用例改由第三方而非系统作者编写，分数从 63–68% 掉到 28–33%**。

需说明边界：这两组基准测的是智能体记忆而非运维 runbook，但失效机制同构——存储的信念停止为真，而检索与排序完全无感。这也解释了知识库为什么"看起来很健康"：它的指标是命中率，而命中率对"命中了旧版本"是盲的。

### 2.2 三种落地形态

**同仓文档（write-time 治理）**：InMobi 模式，把"是否需要更新"塞进本来就会发生的动作（PR 评审）里；Swimm 用活引用在 IDE 内提前拦截，Mintlify 由 agent 提 PR 并用 CLI 校验文档仍能构建，GitHub Agentic Workflows 给出周扫七天变更、开草稿 PR 的范式。

**检索层时间治理（read-time 治理）**：给每条断言一个复核状态，与检索分数分离——`pending_review` / `supported` / `superseded` / `unresolved_conflict`。要点是**超替必须结构化判定**：为每条断言建立 subject + relation 键，键相同而断言不同即由新者取代旧者，与相似度无关。相似度在这里是错的工具，因为它在结构上就没有时间维度。相应地，"新版本入库"不等于"旧版本退场"，必须显式 retire，否则旧 chunk 会与新 chunk 长期并列且同样可信。

**语义运行时（context 治理）**：阿里云 UModel（2026 年 5 月开源，同时发起企业通用语义标准 USS 倡议）把服务、Pod、节点、Agent Thread、Skill 与其 Log/Metric/Trace 集组织成一张关系图，解决"runbook 里的 checkout 服务、CMDB 里的 checkout 应用、trace 里的 checkoutservice 是否同一个东西"——第 29 期的"仲裁真空"在这里有了工程解。但它只保证指得准，不保证这段操作说明仍然成立。

### 2.3 检测走了三代，却漏掉一个新盲区

检测手段已走过三代：链接与构建检查（只能抓描述型腐化）→ PR diff 语义比对（能抓过期债，但最危险的是"自信地写错"）→ 需求信号（Context7 类 MCP 让"问了但答不上来"变成可采集信号，Docs7 已把它做成按需求排序的待办队列）。

这里藏着本期最值得警惕的机制：**当文档缺步骤，智能体不会卡住，它会用记忆补全。** 用户拿到流畅、自信、可能过时的答案，而缺口从未被人看见。人读文档时"卡住"的摩擦，本是组织的免费检测器；智能体把这个摩擦消掉了，腐化就从"可见的断裂"变成"不可见的填充"。

**判读一：没有一家把"知识的有效性"做成一等对象。** 云厂商在"指得准"上最好，工具厂商在"改得动"上最好，模型厂商在"读得省"上最好；而"这条知识现在还算不算数"——需要断言级的键、状态、超替链——三边都没产品化。腾讯云知识库 Skill 拿到 70% 使用率，却仍是只读文档集合，这与它 3700+ 集群、2800+ 次自动扩盘的自愈成熟度形成明显落差。

**判读二：中国厂商押"语义层 + 评测集"，海外押"工作流 + 工具链"；前者死于建模成本，后者死于流程回滚。**

## 四、技术挑战

**一、三类知识债的检测信号完全不同，不能用一套工具治。** 缺失债（该有的没有）没有变更信号可挂，只能靠"问了答不上来"的需求日志；过期债靠 diff 与引用可解析性；冲突债靠结构键。统称"文档腐化"，就会采购一个只治中间那类的工具，然后以为问题解决了。

**二、检索层在结构上无法自证新鲜。** 向量检索没有时间模型，新旧同分；更好的 embedding、chunk、rerank 都不改变这一点——recency 重排只在日期元数据准确时有效，而日期元数据恰恰最先腐化。

**三、批准吞吐是知识系统的真实上限，失败延迟六周才显现。** 一个 agent 一夜能提 200 条待确认断言，人的批准速率不变。摄入快于批准，队列变积压、积压变未核实内容、未核实内容变成没人信的库——"看起来像成功了大约六周"。这与第 20 期的"演练赤字"同源：**自治不能超过核实能力**。

**四、知识腐化的责任没有主人。** 文档 owner、服务 owner、事故 owner 常是三个人。InMobi 把三者压到同一仓库同一 PR，但对已有数千服务的组织，这等于重写所有权模型；而智能体依据过期 runbook 造成破坏时，"谁该更新这份文档"在追责链上没有答案。

## 五、展望与建议

**1. 把知识债拆成三个科目单独记账。** 缺失债按"未答问题日志"计；过期债按"引用不可解析率"计；冲突债按"同键异断言数"计。三张表、三个 owner、三种修复节奏——这是把文档工作变成可运维对象的最小一步。同时按可执行性而非覆盖率排序，只写契约型、执行型、故障史三类；判据一句话：**违反它会导致 bug、安全问题或部署失败，就该纳入变更管理**。

**2. 给知识条目加"复核状态"，与检索分数分离。** 落地顺序照搬已验证路径：先建 join key（代码模块 ↔ 文档分类的映射表），再开需求信号采集，再种 10–15 个节点（只种两个信息源已重叠的概念），最后才建队列与冲突检测器。**先自动化批准、再让人批过一次，等于自动化了一个错的仪式。**

**3. 建立知识 SLO 四指标。** ①库龄：p95 文档"最后实质复核时间"与服务变更频率的比值（超 2 倍变更周期即告警）；②引用可解析率；③命中率：分前缀/块两口径，且须与"命中版本是否为当前版本"交叉；④推翻率：被人工标注为错误的答案占比。前三个可自动采集，第四个必须有人，但它是唯一能证伪前三个的指标。

**4. 把"圆谎"变成可观测事件。** 在检索工具上记录三类信号：检索为空、检索到但未被引用、被引用但置信度低。价值不在修文档，而在**恢复被人机协作消掉的那份摩擦**，让缺口重新可见。

**总结**：前 29 期在管智能体做什么、怎么批、怎么算账、怎么交接；本期要管的是**智能体凭什么知道该做什么**。而现状是：教科书在腐烂，检索层看不见腐化，智能体在替教科书圆谎，而所有面板都是绿的。
