> **本期视角**：前 79 期问过智能体"看见什么、记住什么、被谁供养"，本期首次问**它把同一件事做了几次**。与第 76 期划界：那期管"叫停一次执行"，本期管"没叫停、两次都成功"；与第 79 期划界：重复动作在账单上是自付费回路（成本），本期是状态正确性（计费只是次生）；与第 60 期划界：共享资源导致性能劣化，本期共享状态导致数据错误；与第 73 期划界：验收尺不齐，本期所有尺都绿；与第 40 期划界：多个原因同一时刻，本期多个执行者同一意图；第 22／77 期的共享记忆池事故只是本期的一个实例。

## 一、发展趋势

10 月 22 日是个密集窗口。Google Cloud 在 AGNTCon+MCPCon 发布 Agent Compute Engine：每个智能体一台硬件隔离 microVM，靠 copy-on-write 共享内存与**快照式暂停/恢复**把空闲会话挂起，公开基准为 20 万智能体、每秒 500 次激活、挂起恢复低于 500ms、密度提升 10 倍；同时开源 Agent Substrate，并明确提供 clone、snapshot、fork、**rewind and rollback** 能力。同日 IETF 的 `Idempotency-Key` 草案更新到 draft-08（10-26 仍标 Internet-Draft，非 RFC）。一边把"恢复"做成基础设施，一边给"重复"补词汇表——两件事在同一个月撞上，却没人负责中间那一层：**快照保存的是进程内存与工作区，不是已经发出去的副作用**。

其余线索同窗落地。Anthropic 10-09 Dynamic Workflows 公测（64 并发线程／单次运行 1000 个 agent），官方文档自认"重试时工具调用可能执行两次，外部动作应当幂等"；10-21 其 Python SDK 修复一个更微妙的缺陷：一轮三个并行工具调用，`get_session_messages` 只返回其中一个结果——**磁盘 transcript 一直完整，是读取器把证据丢了**。OpenAI Agents SDK 自 v0.23.0（10-01）起把工具异常脱敏为一句 "Please try again."，不再附 `str(error)`；10-31 开发者社区专帖 "Tool calls that fire twice" 的共识是 `tool_call_id` 只标识会话里的块，不是业务幂等键。

国内侧同月靠拢：阿里 STAROps 10-26 写明"低风险自动放行、关键变更人工确认、禁止操作直接拦截"；火山引擎（10-20）深度调查用"**并行取证**"；腾讯 10-29／30 升级 CloudQ 后，其开发者社区编排复盘说得最直白——"两个 Agent 各自生成的键互不识别，同一件事会被做两次，去重就失效了"。

趋势判词：**能力上线了，写序制度还没上线**。基础设施开始比拼谁能更快地把智能体暂停、fork、回滚，但"回滚到上一个检查点"与"撤销上一笔变更"是两件完全不同的事。

## 二、技术现状

这不是新难题，是被新架构重新制造的老难题。工程界把"两次"拆成五种：重复的 HTTP 请求、重复的编排层工具调用、**重复的推理决策**（语义相同、字节不同）、at-least-once 消息重放、两次独立的业务事务。标准 API 幂等只挡第一种。智能体特有的恰恰是第三种：模型重新组织一次自由文本，"Refund for duplicate charge" 变成 "Refunding duplicate charge on order 456"，参数哈希立即改变，任何基于入参的去重都被击穿。

故障也不止一种：重复写需要 `Idempotency-Key`，两个智能体 read-modify-write 同一记录的**丢失更新**需要 `If-Match`，跨对象多步编辑交错需要租约或单写者。三者守护互不通用，"两次 200、trace 干净、系统记录却是错的"正是都缺的现场。根因在抽象层：框架把 tool call 当函数调用，而写 CRM、工单系统是**对共享状态发起的网络请求**——支付领域二十年前解决的 bug 在机队里集体回归。

因此第一原则是**键由意图生成，不由尝试生成**：`run_id | step_id | tool | target_id | 结构化意图字段`，由编排层铸造、模型不得参与。每次调用生成 UUID 等于没加；Anthropic 的 `tool_use_id` 与 OpenAI 的 `tool_call_id` 都是 transcript 内块 ID，重试即新块；`PreToolUse` 钩子位于进程内、在网络之前，看不见上一次请求的响应是否丢了。真正能让第二次无害的只有持有键并在存储层原子执行的那一端。

第二个空档是时间。**幂等窗口短于人工审批窗口**：Stripe v1 键可在 24 小时后清除、v2 保留 30 天，draft-08 只要求服务端"公布过期策略"，并不要求它与 HITL 审批周期对齐；而一个跨周末等待人工确认的变更，回来重试时键已失效，被当成一次全新写。第 79 期说"人必须保留事故所有权"，这里补上代价：**等人这件事本身会穿透去重**。

协议层明显不对称。MCP 2026-07-28 给出 `readOnlyHint`／`destructiveHint`／`idempotentHint`／`openWorldHint` 四个布尔值，幂等默认 false，且要求客户端"除非来自可信服务端，否则 MUST 视注解为不可信"，又规定重试时 JSON-RPC id MUST 不同——协议自带重试形状，却把"能否重试"交给对端自报的布尔。**两层、一个布尔、没有契约**。遥测同样跟不上：OTel GenAI 约定（2026-09 仍为 Development）字段族围绕 model／token／conversation，缺 `intent_key`、`attempt`、`effect_committed`；只有私有扩展在记，如 Databricks 的 `databricks.action = initial_attempt | retry`。Google 10-30 GA 的推理元数据日志只记模型、区域、token、延迟与错误码，不含 prompt 与响应体——合理，但"动作是否真的落了"不在默认可观测面里。

本地 173 库反而早就写对了答案。周昕毅（携程 AISRE 闭环）把自愈拆成预检→分级→审批→**执行（幂等／超时）**→验证→回滚六步，服务层单列"并发·超时·事件转发"，五项工程基础之三是"工具：动作标准化、**幂等化**、可审计、可回滚"，并披露 5,638 次任务／3,452 次配置自愈；朱革（百度 AgentOps）把"用户／模型／系统／**并发**"并列为写失控四层来源，案例是智能体试错后直接 DROP 库重建表；余锦泽（共享语义记忆）状态机明写"并发修改时返回冲突，**不静默覆盖**"；casa 工作流把"防止重复创建／重试不重复扣费"列为验收项。这些不是新发现，是被"自主度"叙事盖过去的旧功课。

**判读**：九家里没有一家同时回答四问——重复动作率、意图键覆盖率、窗口差、冲突检出率。云厂商把并发做成**隔离**（一台 agent 一台 VM），协议层做成**声明**，模型层把责任推给应用，国内平台派把顺序写进审批流却少有键的工程语义。最接近正确答案的是本地 173 实践派：不谈隔离，直接把幂等放进执行步骤、把并发写冲突当作必须返回的错误。**分野不在诊断分数，而在谁肯承认工具调用是一次网络写**。

## 四、技术挑战

1. **恢复即重放，而重放是最隐蔽的第五种"两次"**。ACE 的 clone／fork／rewind 让会话回到任意检查点，但回滚 microVM 不会撤销已创建的工单、已发出的退款、已提交的变更单；Temporal 文档也承认 activity 至少执行一次，"持久化执行只是把问题下移，没有消灭下游幂等需求"。**可回滚的是进程，不是世界**。
2. **并行让证据变少，也让证据变假**。10-21 的 SDK 修复说明三路并行时审计可能只读到一路；DZone 另指出三个 agent 一致归因到同一次发布，可能只共享了同一时间线与协调者假设——**共识不是独立确认**。读丢与同源让"多智能体交叉验证"失去统计基础，比第 49 期日志污染更无辜。
3. **双层重试叠加**。推理层与 HTTP／编排层重试同时发生，确定性 cron 任务没有这一层；v0.23.0 去掉异常细节后，模型默认拿不到"哪里错"，只剩 "Please try again" 一条可行动作。对非幂等写工具，**提高可用性等于提高重复率**。
4. **验收全绿**。两次 200、两个干净 span、任务完成率把重复算作成功；OpenNash 复合案例里退款重复与标签丢失都无报错。比第 73 期更极端：三把尺同时指向"通过"，错的是被写对象本身。
5. **第三十四个市场空白**：重复动作率／意图键覆盖率／窗口差／冲突检出率四项无一内建；OTel GenAI 约定缺 `intent_key`、`attempt`、`effect_committed` 字段族。厂商自报的 500 激活/s 与 10x 密度均无第三方复核——密度越高，同一记录被并发写的概率越大。

## 五、展望与建议

- **把意图键做成一等运维对象**：所有写工具上线门禁强制携带 `intent_key`（结构化字段哈希，禁止自由文本）与 `If-Match` 版本前置条件；缺一不发生产权限。键由编排层铸造，模型只读。
- **建 effect ledger 六态**：planned／approved／submitted／committed／reconciled／delivered，检查点只记事实不记"叙事"；恢复时先对账 unresolved 操作，禁止模型生成的效果 ID。把 `attempt`、`intent_key`、`effect_committed`、`key_expiry` 四个字段提进 OTel genai 约定提案，与第 72 期 `agent.identity.*`、第 79 期 `billing_unit` 并列。
- **采购条款硬约束**：要求公布键过期策略且窗口不短于人工审批 SLA；要求并行取证披露证据时间窗与来源独立性；把"快照回滚是否撤销外部副作用"写进验收问答。
- **演练替换口号**：在 `timeout_after_commit` 边界 kill worker，验证效果计数仍为 1；再制造两个 agent 对同一记录并发写，验证冲突被检出而非静默覆盖；把"重复动作率"纳入 SLI，与第 79 期 `self_inflicted=true` 打标合流。

一句话收束：第 79 期的结论是"能力上线了，编制制度还没上线"；本期把它推到执行层——**写序制度也还没上线**。智能体不需要更快的恢复，它需要一本比会话活得更久的副作用账。
