# AI-SRE 技术洞察 第 332 期（2026-11-27 11:00）

## 共因失效面 / Common-Mode Failure & Isolation Integrity

> **题眼：三路信号都说"正常"，是因为它们真的独立，还是因为它们共用同一块电池？** ——第 329 期问的是"信号互斥时采信谁"，本期问反面的那一半：**信号一致时，凭什么相信这不是同一个错误被读了三遍？** SRE Agent 把"多路交叉验证""双副本""多云多活"当成 independence 的默认值，却没有人把"故障域"做成一等字段。2026 年 11 月 21 日 OpenAI 的 211 分钟全站故障，把这个默认值摆到了台面上。

---

## 一、发展趋势

11 月的三条一线动态，从反面和正面同时逼近"独立性是不是幻觉"。

**反面：OpenAI 11-21 全站故障（211 分钟，失败率峰值 75%）。** 官方状态页复盘显示，触发点只是一次例行数据库维护：Primary API 所用 Postgres 的两个只读副本**同时**失效。关键在"同时"二字——两个副本并非闲置冷备，而是实时承载查询的组件，且被同一次维护编排放进了同一个故障域；副本延迟无限增长，认证网关后面"门口的路全堵了"，于是对话、API、语音、文件这些看似互不相关的功能集体倒下。跨区域拉起替换副本均未成功，最后靠同区域新建两个副本才恢复。一句话被多家转述反复引用："**单点的定义不在于组件数量，而在于它挂了以后谁也绕不过去。**"整改包括按比例摘流开关、维护前评审、热备容量、副本快速恢复自动化——但"两套副本其实是一套"这个独立性假设，直到撞上维护窗口才被证伪。

**正面之一：Google Agent Compute Engine（11-23 披露）**把独立性做成了架构边界：API key、OAuth 刷新令牌不进沙箱，留在外部 Agent Gateway，认证后再注入；编排 harness 完全跑在沙箱外，只下发明确指令、接收输出流，形成确定性审计链。凭据的故障域与执行的故障域被物理拆开——这是"共因"问题第一次被主流云厂商用隔离架构而非监控指标来回答。

**正面之二：东北大学与斯坦福的 Shepherd（arXiv 2605.10913，NeurIPS 2026-12）**把智能体每个动作连同状态、环境快照记成不可变提交，元智能体可回滚/分叉；发邮件等高危动作被透明沙箱拦截，worker 以为执行成功，实则由元智能体或人决定放行。论文数据：结对编程通过率 28.8%→54.7%，Terminal-Bench 2.0 上比 MetaHarness 提升 12.8% 且 wall-clock 降 58%，回滚速度约为 docker commit 的 5 倍。**但回滚图与被回滚的世界若共享同一故障域，回滚同样是假的**——这正本期要看穿的地方。

三件事指向同一条尚未被计量的轴：行业在给 Agent 装更多"眼睛"和"备份"，却很少问这些眼睛是否共用同一块视网膜。

## 二、技术现状

现状一句话：**冗余与交叉验证做得很厚，故障域的独立性却是空白。**

可观测性侧，OTel GenAI 语义约定把追踪从单次模型调用扩展到 orchestrator→sub-agent→tool→MCP Server 的完整调用图，出现了 faithfulness、groundedness、tool-call correctness、trajectory adherence 等"质量信号"。但这些 span 绝大多数仍汇聚到**同一个 collector、同一个后端、同一套身份与采集中断逻辑**——路径画得再细，只要共用落点，一次后端抖动就会让所有"独立信号"同步沉默。Grafana 与 Cyera/PlayHQ/NAB 的圆桌（讲者反复强调"先把遥测统一到一块面板，再让 AI 干活"）道出了另一面：统一是效率的前提，却也把数据面收敛成了单点；分诊智能体再聪明，也只能在它那一块面板上看世界。

平台侧，腾讯云 CloudQ 以"全景图谱"统一管理多云资源、关系、状态与处置动作，中国信通院《云上 Agent 基准度量模型》给出功能/安全/可靠/体验/性能/成本六维与"辅助诊断—审批执行—限定自治"分阶段、人工接管兜底；阿里云 AgenticOps 用 LoongSuite/OBI、UModel、BRiSE 三道墙保证"事实可采、故障可读、能力可验"；微软 365 本月一次 36 小时断网让 Outlook、Teams、Copilot 一起回归正常——又一个"看似独立的产品共享同一身份/认证平面"的活样本。**"多云"不等于多故障域，"多产品"不等于多控制面。**

评测侧更明显：ORCA-bench、ITBench-AA、CTBench、R2Act、SWEOps-Bench 在 11 月持续发酵，衡量的是"这一次答得对不对""标注者之间一致不一致"（第 330 期），却几乎没有一道题问"**当你给出的多路证据其实同源时，你会不会更有信心地答错**"。第 329 期解决了"跨源冲突如何裁决"，本期要指出它的盲区：一致比冲突更危险，因为一致会关闭怀疑。

## 三、技术竞争力：主要厂商/方案对比

下表按"是否标注故障域、能否举证独立、切换是否实测、一致时能否排除共因"比较，而非按功能丰富度——这是本期提出的新评价维度。

| 方案 | 冗余/多路的形态 | 是否标注故障域 | 独立性举证 | 切换/回滚是否实测 | 共因可举证性 |
|---|---|---|---|---|---|
| OpenAI（11-21 事故架构） | 两只读副本 + 认证网关 | 否（同维护编排/同存储） | 无；灾后才发现共享故障域 | 跨区拉起失败，同区重建才恢复 | 反面样本：一致即同瘫 |
| Google Agent Compute Engine | 沙箱外网关 + microVM | 是（凭据域≠执行域） | 强（密钥不进沙箱、harness 外部审计） | 检查点挂起/恢复已设计 | 部分（域分离可查，跨服务共因未覆盖） |
| Shepherd（Northeastern/Stanford） | 提交图回滚 + 透明沙箱 | 部分（状态/环境快照入 commit） | 中（动作与放行分离） | 有基准数据（28.8%→54.7%） | 部分（回滚域若同域则失效） |
| 腾讯云 CloudQ / 全景图谱 | 多云统一管理 | 否（图谱未声明故障域） | 未见 | 巡检/处置能力已沉淀，切换未举证 | 空白 |
| 阿里云 AgenticOps 三道墙 | OTel 采集 + 语义层 + 评测 | 否（统一即收敛） | 未见 | 三道墙保入库质量，不保独立性 | 空白 |
| OTel GenAI 语义约定 | 跨 Agent 调用图 + 质量信号 | 否（span 未带 fault_domain 字段） | 未见 | 无共因实验 | 空白（细路径、单落点） |
| Grafana AI Triage（三家案例） | 统一面板 + 分诊智能体 | 否（面板即单点） | 未见 | 元监控 bot 盯重复模式 | 空白 |
| 微软 365 / Copilot | 多产品线共享身份平面 | 否 | 无（36 小时同瘫已证伪） | 事后恢复 | 空白 |
| 本地 173：周昕毅《AI + SRE ≠ AISRE》 | 人在环兜底 | 未涉及 | 主张人接管，未问人是否与 Agent 同域 | 未涉及 | 空白（新角度见下） |

**结论**：可采购的能力集中在"把动作拆开"（沙箱、提交图、审计链），没有任何一家把"这几路证据是否共因"做成一个可查询、可门禁的一等字段。下一轮竞争不是"能接几路信号"，而是"敢不敢声明这几路信号不共因"。

## 四、技术挑战

**挑战一：一致性是共因最好的伪装。** 两路信号同报正常，既可能是世界真正常，也可能是它们读同一块存储、走同一个 collector、挂在同一个认证网关。OpenAI 的双副本就是"冗余"在维护窗口里塌成一个点的实例；Agent 若把多路一致当成交叉验证通过，恰好会在最需要怀疑的时候关闭怀疑。

**挑战二：冗余形态没被区分。** 冷备、热备、实时承载副本、共享底层存储的多副本，在架构图上都是"两个盒子"，在故障面前却是四种东西。没有 `redundancy_type` 字段，"我们有双副本"这句无法被审计。

**挑战三：切换/回滚从未在共因条件下实测。** 故障切换演练常在主链路故障时做，却很少在"主链路与备链路共同的依赖"故障时做；Shepherd 的回滚很快，但若提交图与环境快照共用同一存储后端，回滚只是回到同一个坑里的上一格。

**挑战四：多供应商也是伪独立的重灾区。** 把业务挂在两家模型供应商上，若两家共用同一云区域、同一认证 IdP、同一可观测后端，宕机时照样一起倒。微软 365 的多产品线同瘫与 OpenAI 认证单点，是同一逻辑的两种尺度。

**挑战五：责任与口径空白。** 事故复盘停在"双副本同时故障"，没人记录谁在何时把两路放进同一维护编排、谁签署过"独立"假设。没有故障域属主，独立性就永远是口头承诺。

## 五、展望与建议

**提出第 253 个空白字段族 `isolation.fault_domain.*`**（承 #310~#331 可举证率系列叠加）：

```
isolation.fault_domain.* {
  signal_sources[]{source_ref, fault_domain_ref},
  shared_dependencies[],        // 两路之间共享的存储/认证/collector/维护编排/供应商/可用区
  independence_evidence,        // 不同AZ？不同控制面？不同供应合同？还是仅"两个进程"？
  redundancy_type ∈ COLD_STANDBY | LIVE_BEARING | SHARED_BACKEND | UNKNOWN,
  failover_tested_at, failover_test_under_shared_cause,
  correlated_failure_observed[],
  counterfactual.dependency_separated_still_agrees,
  verdict ∈ INDEPENDENCE_VERIFIED | COMMON_CAUSE_SUSPECTED | SHARED_FATAL | UNVERIFIED
}
缺省 ISOLATION_UNVERIFIED；verdict≠INDEPENDENCE_VERIFIED 的多路一致不得作为"交叉验证通过"的证据、不计入已独立复核声明、不作自治升档。
```

**四条最小动作**：① 每路信号与每个副本入库即标 fault_domain_ref，共享依赖显式列出；② 维护/变更窗口把"两路是否同域"设为强制门禁，同域即禁止把它们当互备；③ 切换演练增加"共同依赖失效"的反向用例，记录 rollback 是否真的跳出同一故障域；④ 采购多供应商时，把 IdP、云区域、可观测后端一并纳入独立性审计，而非只看合同主体不同。

**采购三问**：你们能否导出任意两路信号的共同依赖清单？双副本的 redundancy_type 是什么、切换在共同依赖失效下测过吗？两路"一致"时，系统会不会主动怀疑共因？

**配对评测题**：给同一诊断任务做 A/B——A 组两路证据来自真正分离的控制面，B 组只把 A 组的落点合并到同一 collector（证据文本不变）。测量 `false_agreement_rate`（B 组被当成交叉验证通过的比例）与 `common_cause_suspicion_rate`。建议信通院六维评估补一格"隔离可举证率"，与 #316~#331 的十五格并列。

**本地原型（第 208 期新角度）**：重读周昕毅《AI + SRE ≠ AISRE》——过去读成"人必须进闭环"，本期改读为"**人要站在与 Agent 不同的故障域里才算兜底**"。如果验收的人、被验收的 Agent、以及他们共同看的面板挂在同一个认证平面和同一个供应商上，"人在环"只是同一故障域里的第三个副本；人进闭环的价值不在人多聪明，而在他能否在别人都沉默时从另一条路拿到真相。

**新观点收束**：**多路一致不是独立性的证据，只是一次尚未被证伪的共因假设。** 可观测性走到"信号有主人"（#322）、"结论有保质期"（#331），下一步必须走到"独立有出处"——否则我们用更多眼睛把同一个盲点看得更清楚，还给它起了个名字叫交叉验证。
