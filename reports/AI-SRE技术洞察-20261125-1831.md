# AI-SRE 技术洞察（第 356 期）

**生成时间**：2026-11-25 18:31（Asia/Shanghai）
**洞察窗口**：2026 年，重点为最近 30 天
**本期主题**：序列化面／字段号与协议兼容——删掉的字段，地址还在

## 题眼

一份 2026-11-08 的工程问答记录了一个真实的错位：C++ 端把 `work` 绑定在 **ID=4** 上序列化，Java 端把 **ID=4** 定义为 `currency`。二进制流到达后，Java 把工作内容**静默存进了币种字段**；Java 回传时，C++ 端把币种读成工作，而 C++ 真正的 `work`（ID=5）保持默认空值。整个过程**没有任何序列化错误**——Protobuf 的容错机制无提示地完成了值的错配。

GitHub 上 2026-11-19 的兼容性检查清单把这条列为"二进制线格式不安全"的第一项：**复用已删除或曾经发布过的字段号**。并补了一句更关键的：*永远不要假设一个看起来未使用的 tag 没有历史数据——旧二进制、日志、队列、回滚产物里可能还带着它。*

## 一、发展趋势

第一，协议从"内部实现"变成"跨组织契约"。gRPC、Connect、MCP 工具、事件总线、Agent 间消息都依赖同一套线格式；一个字段号的含义一旦发布，就不再由发布方单方面决定。

第二，schema 演进工具开始把"线格式兼容"与"语义兼容"分开检查。Buf、protolock、`buf breaking` 能告诉你"这次改动会不会破坏线格式"，但它们看不到队列里积压的旧消息、日志里的旧 payload、备份里的旧快照。

第三，`protobuf Editions` 把过去绑在 proto2/proto3 关键字上的行为拆成可逐项开关：field presence（IMPLICIT/EXPLICIT）、enum 类型（OPEN/CLOSED）、repeated 编码（PACKED/EXPANDED）。灵活性提高的同时，"同一个 `.proto` 在不同 edition 下语义不同"成为新的兼容性维度。

## 二、技术现状

**字段名不上线，字段号才是身份。** 线格式编码的是 `(field_number, wire_type, value)`；字段名只存在于本地代码生成。所以"改个名字"通常无害，"改个编号"必然致命——而且不会报错，只会错值。

**删除字段不是删除地址。** 删除一个字段后，它的编号仍然是"已用过的地址"；正确做法是 `reserved`，并在注释里写清用途。复用它，等于把旧数据解释成新含义。旧二进制、Kafka 里没消费完的消息、对象存储里的归档、回滚时拉起的旧版本，都会继续按旧含义写入或读取。

**类型变化的静默性被低估。** `int32 → int64` 在线格式上兼容，但一旦有符号/无符号或浮点参与，值会被重新解释；`string` 与整型互换则直接改变线格式类型。工具会报"wire-compatible"，但业务会看到"值变了"。

**第三个写入方是回滚产物。** 兼容性讨论通常只算"旧代码"和"新代码"两个写入方，但回滚镜像、灾备副本、离线重放任务都会按旧 schema 继续写；一次回滚之后，新字段可能在几小时内被旧版本按旧编号覆盖，而监控只看到"数据回退"。

**unknown fields 在中间层被丢掉。** proto3 的未知字段会被保留在解析结果里，但很多网关与代理默认丢弃：一份 2026-03-29 的 gRPC-JSON 网关配置里同时出现 `allow_unknown_fields=true` 与 `strict_mode=false`——这意味着旧字段经过网关后消失，下游看到的是"字段不存在"，而不是"字段被删除"。

**presence 语义决定"零值"与"未设置"。** proto3 的 implicit presence 无法区分"从未设置"与"显式设为零"；Editions 的 EXPLICIT presence 可以。这个差异会直接影响"部分更新"类接口：客户端只想改一个字段，服务端却把未传字段当成"设为默认值"。

**enum 的未知值有两个去处。** OPEN enum 把未知值保留在字段里，CLOSED enum 把它移入 unknown fields；跨版本升级时，旧服务读到新枚举值的行为取决于这个开关，而不是"枚举兼容"这句口号。

## 三、技术竞争力

| 方案/厂商 | 检查对象 | 覆盖存量数据 | 语义检查 | 主要盲区 |
|---|---|---|---|---|
| Buf breaking | `.proto` 变更 | 否 | 部分 | 看不到队列/日志/备份 |
| protolock | 线格式快照 | 否 | 弱 | 不覆盖运行时 |
| Confluent Schema Registry | 消息 schema | 部分（注册表内） | 兼容级别 | 仓外/旁路写入 |
| gRPC-JSON 网关 | 运行时转换 | 否 | 否 | 可能丢弃 unknown fields |
| 自建兼容性 CI | 代码层 | 否 | 可定制 | 依赖规则完整度 |
| 契约测试（Pact 等） | 接口交互 | 否 | 语义层 | 只覆盖已声明消费者 |

**判读**：这张表最一致的"否"是**存量数据**。所有工具都在检查"新代码能否读旧 schema"，没有工具在检查"旧数据会被新 schema 读成什么"。

**本期反转**：我们一直把兼容性当"schema 是否兼容"的问题，用 lint 和 breaking-change 检查守住。实际上兼容性是**地址簿**问题：字段号是地址，删除字段只是把住户搬走，地址还在；新住户搬进来，所有寄往旧地址的信都会送到新住户手里，而且邮局不会告诉你送错了。

## 四、技术挑战

**挑战一：存量数据不在 CI 的视野里。** 队列积压、日志归档、备份快照、回滚镜像都带着旧编号的语义；CI 只看代码。

**挑战二：静默错值比报错更难查。** 错位不会抛异常，只会让两个字段交换内容；监控看到的是"业务数据异常"，不是"协议错误"。

**挑战三：presence 与默认值的歧义。** 部分更新、补丁语义、Agent 的工具参数都依赖"未设置"与"零值"的区分；proto3 implicit presence 让这个区分消失。

**挑战四：工具链的"兼容"定义不一致。** 不同工具对"兼容"的判定不同（线格式/源码/语义），团队容易把某一个绿灯当成全部绿灯。

## 五、需求分解、用户旅程与实现方案

**需求分解**：①字段号登记（含已删除编号与 reserved 原因）；②存量数据扫描（队列/日志/备份中的旧 payload）；③presence 语义声明（哪些字段必须区分未设置）；④unknown fields 策略（保留/转发/拒绝）；⑤回滚兼容验证（旧版本读新数据会怎样）。

**用户旅程**：服务端要删掉 `currency` 字段，把编号 4 让给 `work` → 兼容性 CI 报"wire-compatible" → 平台要求查存量：Kafka 里还有 3 天积压的旧消息、S3 里有 90 天归档、回滚镜像还是旧版本 → 结论：编号 4 不能复用，改用 5 并 `reserved 4` → 新字段上线，旧消费者继续读 4（unknown，忽略）→ 回滚演练验证旧版本不会把 5 读成别的字段。

**90 天实现方案**：0–30 天，建立字段号登记表（含已删除编号、reserved 原因、首次发布日期），CI 阻断编号复用；31–60 天，扫描队列与归档中的存量 payload，统计"仍在使用旧编号"的比例与保留期；61–90 天，为关键消息声明 presence 语义与 unknown fields 策略，做一次跨版本回滚演练（旧代码读新数据）。

**第 268 个市场空白（五项）**：字段号登记与 reserved 审计；存量 payload 扫描；presence 语义声明；unknown fields 策略；回滚兼容演练。

**`wire_identity.*`／`field_number.*` 第 235 次无人提字段族**：所有工具都记录"字段叫什么、类型是什么"，没有一个字段记录"这个编号曾经属于谁、现在还有谁在按旧含义读它"。

**本地 173／173-kb 连续第 223 期成组启用（周昕毅 10：协议兼容不是让新代码读懂旧 schema，是让旧数据不被新代码读错）。**
