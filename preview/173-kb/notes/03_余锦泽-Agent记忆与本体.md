# 03 · Agent 的记忆不在对话里：把企业数仓沉淀为可治理的共享语义记忆

- **来源文件**：余锦泽-Agent的记忆不在对话里.pdf
- **厂商/讲者**：余锦泽 博士（大规模个性化定制系统与技术全国重点实验室 工业智能首席科学家；早稻田大学客座研究员；原亚马逊云科技日本生成式 AI 创新中心高级应用科学家）
- **主题领域**：**Agent 记忆 / 本体（Ontology）/ 语义层 / 数据治理** —— 与「运维本体与知识图谱」高度同构
- **页数/文本量**：52 页 / 17950 字

## 核心观点
- 企业的指标定义与表间关系**不应只靠对话记忆或自动生成**；Agent 的「记忆」应是企业级可治理的共享语义记忆。
- AS-IS 痛点：同一问题四种算法「都没算错」却得出不同结果（1.15% / 1.23% / 1.25% / 1.29%），根因是指标定义散落在表结构、代码与文档中。
- TO-BE（本体辅助记忆）：对话与反馈进入**动态记忆**；**指标定义与表间关系写入本体**，并附数据 / 代码 / 文档证据；LLM 只提候选，程序用**数据核对**给出「已验证 / 候选」，由业务人员确认或否决；SQL 执行前做**本体约束校验**；人工否决可即时撤销并作为下一轮反例。

## 关键事实/数据
- 实测：仅补实体与关系 → 8 题答对 2 道；补上指标定义与校验 → **8 题答对 6 道**（同一合成库、同一模型）。
- 真实案例：某能源管理平台近 **600 张表无声明外键**；某电子制造数仓连接条件分散在**十余个代码文件**。
- 工具：开源 **Cosmo DataMind**；验证覆盖合成库、公开基准 **BIRD**、真实平台。

## 主要踩坑/风险
- 错误的关系若留在记忆里，后续查询会**反复出错**（记忆污染）。
- 语义层工具生成的关系多靠人工核对，写入缺乏程序化校验。

## 可引用结论（三段对照）
> 记忆从哪来 / 谁决定写入 / 出错以后：AS-IS 靠 LLM 自行判断、错误滞留；TO-BE 用数据核对 + 业务否决 + 反例回流，形成可治理闭环。
