## 核心观点
- 背景痛点：阿福线上 badcase **平均修复耗时 12.6 天**，每天仅完成 1 轮实验，修复一类问题约需 3 人日，人工串联「发现→分析→分派→修复→验证→关单」全流程，人力已明显超过团队可投入。
- 架构演进：**Harness 支撑修复迭代（单 Agent 自主迭代：工具接入 + 长程执行 + 评测机制），Loop 推动问题持续流转（多 Agent 协同：外循环任务流转 + 内循环修复验证）**。
- 实施顺序铁律：**先 Harness，后 Loop。单次迭代的结果不可信时，持续流转只会放大错误。**
- 人机分工：人定义问题、验收上线；Agent 负责中间的迭代（分析 badcase→改 prompt→部署→评测→未达标继续下一轮）。

## 关键事实/数据（已核验）
- 当前效果：**覆盖约 20% 的 badcase，1–3 天形成可复核结果**。
- 评测护栏：虚构「降低 89% 聚集性疫情」被扣分 → 规则「无来源时，不得虚构降低 89%」；训练集 101.6、相对擂主 −0.4%（第 2 轮）/ −2.0%（第 3 轮最低点）/ +2.5%（晋升新擂主）。
- 工具接入四关：环境与代码（预发环境、固定代码库分支）、部署能力（发布/部署技能）、评测能力（发起/跟踪/下载）、分析能力（分析与优化技能 + 鉴权与评测配置）。

## 主要踩坑/风险
- 长程执行中的「等待」是主要耗时：每天 1 轮实验、人工衔接部署/评测/分析导致 12.6 天均值。
- 单 Agent 无法解决时须「携带证据改派」，Loop 承接每一次交接。

## 可引用结论
> 先 Harness，后 Loop；单次迭代结果不可信时，持续流转只会放大错误。
