背景与规模化挑战
从单点试用到规模化托管：企业 Agent 落地的新矛盾
接入与部署问题
• 不同团队重复准备环境、配置运行实例和
接入消息通道，交付周期长
配置与版本问题
• Agent、Skill、Prompt、工具和知识缺
少统一版本边界，调试容易污染线上版本
运行与观测问题
• 实例状态、会话、工具调用和执行结果分
散，出现 bad case 后难以定位
安全与权限问题
• 生产操作缺少统一的权限、审批、限流、
审计和回滚控制
能力复用问题
• 公共工具、业务知识和历史经验难以沉
淀，场景建设依赖少数专家
质量与演进问题
• 没有稳定的 Case、回放和评估体系，无
法判断版本是否真的变好
• 当 Agent 从"单点试用"走向"规模化生产"，接入部署、版本边界、运行观测与安全管控的缺失集中爆发——
企业用得起来，却管不住、不敢放大

安全管控：Agent 执行的四类高危风险
• Agent 能自主调用工具、执行写操作——用户、模型、系统、并发四个层面，都可能让一次写操作失控
案例一 Agent自主升级到高危操作
• 场景：Agent迭代后与 DB 交互，数据字典
不匹配，insert 持续失败
• Agent 动作：多次试错无果后，直接 DROP 
库、重建 table
• 后果：数据库被删，数据丢失，甚至导致业
务中断
• 问题本质：为达成目标自主升级到高危写操
作，全程无人把关
案例二　Agent 超出指令边界"误
伤"
• 指令：把配置里 A 字段 从 v1.32.0.1 改成 
v1.33.0.1
• Agent 动作：配置里 B 字段 恰好也是 
v1.32.0.1，Agent 顺手把 B 也改了
• 后果：B 被误改，引入非预期变更
• 问题本质：超出指令作用域，关联误伤，无
精确范围控制

安全管控：前置约束 + 分层运行时治理，定义安全治理全局流程
• 不是单点拦截，而是从构建时到运行时的四道防线——四类高危风险在 L1–L4 被逐层覆盖
L1 构建时
• 事前约束——声明允许/禁止的动作
与边界(用户输入)
L2 意图审计
• 第三方专家 Agent 比对"需求 ↔ 产
出"，产出评审意见(Agent产出)
L3 本地 Hook
• 审计 Agent 产出 runbook 的动作与
对象（Agent产出）
L4 网关代理
• 代理所有 API/HTTP 调用，审计接
口、参数、QPS（Agent产出）
• 安全不是最后一道闸，而是从构建到执行的全程护栏
安全管控：身份可信 + 操作可审计、可回滚
• 让每一次操作都"知道是谁、代表谁"，所有托管 Skill 经智能评审，天然可审计、可回滚
身份与令牌
• 委托令牌承载双身份（具体用户 + 发
起 Agent）并加密防盗用；
• 用委托而非冒充，完整保留"谁代表
谁"
价值：调用链定责，越权可拦
执行审计
• 5W 审计（谁 / 哪个 Agent / 何时 
/ 对哪些对象 / 做了什么）
• 日志落本地并持久化
• 单操作可回滚，可撤销最近一次写操
作
价值：可追溯，可分析，可回滚

场景仿真回放：Agent / Skill 迭代之痛--为什么需要评估中心
• 场景难复现、改动难验证、效果难评估——每次迭代都要人工兜底
改动验证难
• 变更影响难验证 —— 改一处，牵一
发而动全身，人工回归范围有限
• 场景难复现 —— 切流、回滚等高危
写操作不能在线上跑
• 验证环境不一致 —— 同一个 Agent 
验证memory / session 干扰结果
• 问题难准确定位 —— 只看最终结果
看不出偏差在哪
效果与效率难
• 结果难验证 —— 更新后只能人工逐
条 review 才敢确认
• 效果难评估 —— 缺乏量化指标与统
一标准，好坏全靠主观感觉
• 人工建 Case 成本高 —— 靠经验、
难为继
• 迭代速度慢（综合后果）：以上问题
叠加，每次更新都要人工仔细 
review，Agent / Skill 无法快速迭代
上线

场景仿真回放：真实场景驱动的 Agent 评估闭环
• 高危场景离线复现、变更后可复现验证、执行过程可观测——让 Agent 的每次发布都有量化依据
真实场景沉淀
• 从线上告警与多轮会话中自动记录 
Trace，真实映射运行时行为链路，
为评估提供可靠依据
Case 生成
• 从多轮会话中选取高价值 Trace，沉
淀为含「输入/上下文/工具快照/期
望结果/期望过程」5 要素的标准 
Case，提供基础Trace集
Agent 迭代与 Case 回放
• 将线上 Agent 部署到回放沙盒，沟
通迭代后对当前版本执行 Case 回
放，不碰生产即可验证
Trace 调试
• 回放过程中实时展示 Trace 概览与逐
步详情，精确定位到工具调用、参数
错误与异常步骤
评估报告
• 输出总体得分与过程对齐（期望 vs 
实际），给出问题诊断与优化建议，
支撑"继续迭代 / 达标发布"的决策
场景仿真回放：Case 生成与治理--可沉淀、可复现、可扩展的评估资产
• 多来源汇聚、人工把关、沙盒验证后入库，沉淀为通用底座，并运行在安全中心之上
全流程治理
• 多来源汇聚 → 审核 → 沙盒验证 → 
入集，质量可控、来源可信
通用底座复用 
• 平台沉淀 + 业务按需拼接，Case 可
复用、可扩展
安全是前提 
• 能力建立在安全中心之上——拦得
住，才敢跑 
• Case 不是一次性用例，而是持续沉淀、安全可控的资产

经验沉淀：四大核心权衡，在矛盾中找到工程上的平衡点
• 做 Agent 平台，难的不是单点能力，而是一组互相拉扯的权衡——我们的做法是"用机制让两端协同"，而不是取其一
智能性 × 确定性
• 规划与执行解耦，高风险动作收口到
工具与控制面——既留灵活，又守可
预测
安全 × 效率
• 按风险分级处置（自动放行 / 人工
确认 / 强制审批 / 强制阻断）——
低风险快、高风险稳
知识多 ≠ 高质量
• 知识必须带来源、适用条件、版本与
验证状态——宁可少而准，不要多而
误导
生成 × 验证分离
• 引入独立验证机制（外部证据 + 多
方评审），避免同一模型自证正确
• 好的平台不是消灭矛盾，而是把每一组权衡都变成可控的工程选择
从知识到价值，构建可用、可管、可
评、可复用的能力

AgentOps 总结与展望

• 一套平台托管 Agent 全生命周
期，解决"能跑、敢用"

化，以回放通过率、采纳率衡
量，持续提升

• Agent 辅助管 Agent，人只定目
标与边界，运维走向自治
• 让每一次执行都更安全，让每一份经验都可复用，这就是 AgentOps 想要的未来
