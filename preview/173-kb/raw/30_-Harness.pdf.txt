01
智能路由成立的
三个前提
Part 01 · Why
智能路由要成立，依赖三个前提
尺寸差
小模型通常更快、推理成本更低；大模型承担更复杂的工作。
同尺寸也分岔
数据配方、架构设计、推理引擎适配，改变能力、价格与速度。
harness × 目标任务
同模型、同思考力度，换执行框架，部分场景成本差 2 倍以上而质量不变。
03
1.1 尺寸差：计算与资源是两本账
简化估算有架构与 batch 前提，最终回到任务实测
激活参数 → 边际成本
每 token 算力约为 2 倍激活参数；decode 吞吐上限约为显存带宽 / 激活权重体积。
总参数 → 固定成本
MoE 稀疏主要省计算；常见高性能部署仍需在集群中存放专家权重。
27B 与 13B / 284B
稠密 27B 每 token 算力，约为激活 13B、总参 284B MoE 的 2.1 倍。

08
真正的命题：匹配模型 + harness
不充分的简化
“难的给大模型，不难的给便宜模型”只考虑了复杂度。
复杂度不是全部答案
长上下文不一定需要复杂推理；短指令也可能推进大型工程。
路由的是执行方案
把适合的任务，交给适合的模型 + harness，并满足质量、预算与供给约束。

Part 03 · How
3.1 会话一致性是第一条硬约束
缓存代价
换模型或不共享缓存的端点，可能重新支付长前缀
输入成本。
行为漂移
命名、格式、工具协议与上下文理解可能变化。
默认绑定，必要时交接
切换必须有状态交接、预算与验证；正常绑定与检
查点 → 故障恢复 → 一致性验收。

3.1 档位不是全模型搜索
每档 1 主力 + 1 验证备用是工程建议；离线候选池 → 在线供给选择 → 会话绑定版本
cheap
质量过线后，比较完整任务成本；包含缓存、重试与平台费用。
fast
区分首字延迟与完工延迟；在合格池里按服务状态选择端点。
quality
用自有 eval 定义质量门槛，不默认选择参数最大的模型。

4.1 选择表达偏好，结果验证效果
留什么
任务特征 / 候选与建议；用户选择与覆盖原因；质量、成本、延迟与返工。
怎么用
显式选择优先于自动推荐；按任务建默认项，不贴死标签。
产品边界
经用户授权、最小化留存；选择不直接当成功标签；默认不留敏感原文，并支持删除和退出。
26
4.2 好的路由，是持续迭代的方案
专业名词解释 ≠ 系统设计；
领域相同，能力要求不同。
任务分类
同样一句“继续”，可能在
推进，也可能在返工。
状态判断
速度 / 质量 / 风格权重不
同；同一任务也有不同选
择。
用户偏好
模型、价格和任务分布变
化，旧边界需要不断更新。
持续校准
分别建模任务、状态与偏好，再用真实结果持续校准

4.3 路由做得好不好，最终看任务总账
净收益 = 路由节省 − 决策 / 切换 / 重试等开销
规则 / 本地小模型
本地推理 + 部署维护；成本低，但不是零。
LLM 判断
额外调用 + 网络等待；准确之外，更要算净节省。
Advisor 协作
子推理 + 误判升级；设置预算与调用边界。
28
4.3 验收净收益，而不是便宜调用占比
警惕单向变贵
只升不降，以及“升档更保险”的反馈偏置；不满意有反馈，可以更便宜却常被忽略。
同一套 eval
质量不降，完整任务成本下降；不存在通用的固定决策成本占比门槛。
守住交付指标
同时守住完工延迟与稳定性；缓存损失、重试和返工也要入账。
