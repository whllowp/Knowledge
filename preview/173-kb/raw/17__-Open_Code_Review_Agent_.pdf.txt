OpenCodeReview：确定性⼯程 x Agent 协同
边界交给⼯程，决策留给 Agent
从通⽤ Agent 的⼤量评审轨迹中收敛提⽰词、⼯具与流程：确定性问题交给⼯程，动态决策交给 Agent。

Less is More：让 Agent 专注做它擅⻓的事
四个机制相互配合，让 Agent 执⾏更专业、更安全、评审效果更稳定、响应与 token 成本更可控。

专项模型的尝试：把⾼频⼦任务做准、做快
针对评论定位与误报过滤两类⾼频、边界清晰的⼦任务，利⽤真实业务数据微调专项模型，在提升任务效果的同时降低处理时延。
反思模型：Qwen3-30B-A3B
利⽤⽤户反馈收集带标注（采纳、误报、忽略）的数据，训练⼀个反思
模型作为过滤器来拦截误报。针对⽣产环境标注噪声⾼、清洗成本⼤的
挑战，我们以少量专家及⽤户反馈数据为锚点，通过多模型协同标注从
噪声中提取可靠样本，训练反思模型拦截误报。最终有效过滤了⼤模型
幻觉，误报拦截率从30.09%提升⾄52.63%，耗时由5s降⾄500ms内。
定位模型：Qwen3-8B
利⽤线上真实数据（定位成功、定位失败、使⽤ SOTA 模型纠正失败）
进⾏训练，⽤于传统算法定位失败时使⽤⼤模型重建⽬标代码⽚段。该
任务训练后，相⽐基模的成功率从 37.35% 提升到 85.65%，平均耗时从
⼤尺⼨主模型的 3s 降低到 1s 内。

⼀次评审不只有报告，还有可追踪、审计的 Manifest
⼈们越来越依赖 AI 评审报告，也越来越多地让另⼀个 Agent 应对评审报告。报告反应了评审过程发现了哪些问题，Manifest 则交代哪些⽂件审
完、哪些未完成以及原因，让⼈和下游 Agent 都能核对评审范围，才能更好地信任、复查与修复。

OpenCodeReview ⾃身的 RSI 实践
热度的背后是前所未有的迭代速度
⼀个备受关注的开源项⽬，⼏乎每天都在接收变更、验证变更、发布变更。在这个过程中，我们探索了激进的 All in AI 研发流程。

⽆⼈值守的⾃进化（RSI）存在哪些问题？
实现正确 ≠ 需求正确 风险堆积到未来⼀起做，还是分开做？
测试和 AI 评审能验证实现的正确性，却难以判
断需求的正确性。看似正确的改动，可能⼀开始
需求就是不成⽴的。
多个 PR 各⾃评审通过，合在⼀起却可能功能性
冲突。如果推进，需要⼤局观判断，AI 往往缺乏
这些。
AI 倾向最快的⽅式实现需求、解决问题，缺乏⼤
局观；每次看似过关，却把隐患持续堆积到了未
来。
Codex：
⼈类介⼊的⾃进化（RSI）流程
给⼤模型提供⾜够的结果、过程轨迹、归因脚本等，由⼈类专家在关键决策节点介⼊审批，最终提升整体的迭代效率与稳定性。
合⼊前质量把关：从⾃动筛查到⼈⼯决策
分层检查变更质量，识别对评审 Agent 的能⼒影响；⼈⼯结合各层结论做出合⼊决策，任何⼀层出现问题都要打回重来。

思考与展望
代码评审⼯具，不必是单选题
1. 不替代编码 Agent，专注做好评审
很多⽤户习惯让⼀个 Agent 写代码、另⼀个 Agent 
评审，避免⾃写⾃评。OpenCodeReview 正是这样
的⾓⾊：OpenCodeReview 专注于代码评审，为已
有开发流程补充检查与验证。
2. 评审⼯具不是单选，多⽅发现相互补充
在评审环节，⽤户往往会同时选择多个 CR ⼯具。
⼯具之间可以互补，⽽不只是相互替代。
3. 开源热度，折射出更强的验证需求
AI ⽣成越多代码，开发者越需要多⽅验证，缓解
“能否放⼼合⼊”的焦虑。
⾯向 AI ⾃主开发时代的下⼀代评审模式探索
AI 正从“辅助”⾛向“⾃主”，⼈的参与越来越少，但每次合⼊代码依旧如履薄冰，未来 AI 代码评审会往什么⽅向演进？从发现代码问题，⾛向为变更决策提供依据。

评测的下⼀步：拉开差距，对⻬体验，持续演进
⼤模型和 Agent 都在持续进步，评测也需要保鲜，我们后续的⽅向是基本对齐⽤户使⽤体验的同时，扩充数据集，挖掘更⾼价值的难题。
从垂直 Agent，⾛向评审专⽤模型
垂直 Agent 的价值已在⽣产中得到验证；下⼀步，让模型与评审任务、⼯具和流程共同优化。在评审效果、推理时延与 token 成本之
间，寻找更好的平衡。⽬前已经和 Qwen 基模团队达成合作，⼀起探索 CodeReview 场景专⽤的⾼性能模型。
