# SDD：规格驱动的交付流程（v2）

> 一句话：**把"想清楚"和"做对了"变成可验证的产物。** 每个闸门交出一个产物和一份证明，下一闸门在两者都存在前不开始。

## 0. v2 的变化：把流程写成脚本

v1 是纯文档驱动：代理读 SKILL + references，然后手写 brief、spec、票、台账、评审、复盘。v2 保留同样的骨架，但把**重复的写操作**交给 `scripts/sdd.py`（Python 3，无依赖）：

| 闸门 | v1（手工） | v2（一条命令） |
|---|---|---|
| G0/G1/G2 | 手写 brief/spec/tickets，容易漏节、占位符残留 | `sdd.py init --slug <slug> --name "<title>" --mode <mode>` 生成全部骨架与 `.gitignore` |
| G3 | 跑命令、复制输出、手写台账行、易漏 exit code | `sdd.py run --slug s --ticket 01 --criterion "<c>" --label red -- <cmd>` 写日志、追加台账、返回原退出码 |
| G2/G3 校验 | 人工逐条核对 | `sdd.py check --slug s [--gate G3]` 断言式检查，缺证据即退出 1 |
| G3 收尾 | 手改状态、写 verdict、写 retro、再提交 | `sdd.py finish --slug s --ticket 01 --message "..." --verdict ship --retro "..." -- <最终证明命令>` 一次完成 |
| G4 | 自己在记忆里拆分三轴评审 | `sdd.py review --slug s --fixed-point <ref>` 校验 fixed point 与 diff，生成三份评审 prompt |
| G2 前沿 | 人工读阻塞边 | `sdd.py next --slug s` 打印当前可开工票 |
| G0 提问 | 想到哪问到哪 | `sdd.py ask --slug s` 把 brief/spec 里的未决项收敛成 ≤4 个带假设的问题 |
| 成本/健康 | 无 | `sdd.py bench` 报告上下文成本；`sdd.py doctor` 比对源与安装副本、检查预算 |

度量与 10 次迭代记录见仓库根的 **`ITERATIONS.md`**。v2 的 lite 闭环（同一任务）实测 **6 次工具调用**（v1 为 9 次），手写的流程产物从 6 个降到 1 个。

脚本是可选加速器：不装它，按本文手工走完全相同。装了它，闸门仍然是闸门——`check`/`finish` 只认证据，不认叙述。

## 1. 为什么要融合

两套来源各有硬伤，正好互补。

| | 强项 | 硬伤 |
|---|---|---|
| 可组合的工程技能（spec → 票据 → 实现 → 评审） | 交付骨架干净：规格做决策、tracer bullet 切垂直片、任务图有前沿、TDD 绑在约定接缝上、双轴评审、子代理全新上下文 | 证明靠散文：评审读的是叙述，"完成"是个状态词，会话结束后什么都不剩 |
| 操作型知识系统（证据、记忆、闸门、协议） | 诚实骨架完整：引用到来源、先查后问、先测量后修复、破坏性操作要同意、失败有类型和处理路径、决策带来源、输出不注水 | 不会交付：能告诉你什么是真的，但不能把工作切开、排序、实现、合并 |

融合不是折中，是把两套骨架接起来：**工程技能负责"工作怎么走"，知识系统负责"每一步凭什么算数"。**

## 2. 十条不变量

在流程被压缩、时间不够、压力很大时，守这十条；其余可以删。

1. **没证据就是没发生。** 一个说法没有命令和观测输出，就只是假设。状态行、CI 绿灯、自信的措辞都不是证据；截断的日志里报"通过"不算通过。
2. **先查后问。** 仓库、文档、历史、工单、持久记忆都查完再问；问的时候带假设和 2–4 个选项，不丢一个裸的"未知"给用户。
3. **传指针，不传正文。** 给子代理和未来的会话的是产物路径和提交哈希，不是粘贴的上下文。一个事实只有一个归属文件。
4. **每个工作单元一个全新上下文。** 子代理必须从零开始；继承了父上下文的子代理叫复制，不叫委派。
5. **失败关闭。** 产物缺失、歧义无法解决、证明无法复现，就停下来，不给自己找体面的出口。
6. **先测量，后修复。** bug、回归、性能问题，先拿到失败态的测量结果。没有测量的修复只是穿着 diff 外衣的猜测。
7. **破坏性操作必须过闸。** 删数据、不可逆迁移、强推、大额花费：每次具体动作都要有明确、限定范围的确认。代理的自信不能替代用户的同意。
8. **动作之后要回读。** 任何写入之后重新读取结果；如果回读看不到自己写的东西，就如实说明，不要宣称成功。
9. **小产物、单一归属。** 意图在规格，范围在票据，证明在台账，理由在决策记录。不要互相转述。
10. **流程本身可改。** 摩擦写进复盘，然后改进技能或项目约定。从不触发的规则应当删除；只增不减的流程等于噪音。

## 3. 结构

一个特性一个目录：`.sdd/<feature-slug>/`。

```
.sdd/<slug>/
  brief.md               G0 立项
  spec.md                G1 规格
  tickets/NN-slug.md     G2 票据（一票一文件）
  decisions/NNNN-slug.md 决策记录，只追加
  evidence.md            台账，只追加
  evidence/              原始命令输出、日志、截图（git 忽略）
  review.md              G4 评审
  pr.md                  G5 发布文案
  retro.md               G5 复盘
  waivers.md             显式、带期限的豁免
  map.md                 仅 wayfinder 模式：决策地图
```

**断点续跑**：按顺序读，停在第一个没有 `Status: accepted` 的产物。

| 闸门 | 已存在的判据 | 从这里继续 |
|---|---|---|
| G0 | `brief.md` 有验收行 | G1 |
| G1 | `spec.md` 已验收且接缝已确认 | G2 |
| G2 | 票据 DAG 无环，前沿已写出 | G3 |
| G3 | 所有票 `done`，或 `blocked` 且有原因 | G4 |
| G4 | `review.md` 有裁决行，台账覆盖每条验收标准 | G5 |
| G5 | `pr.md`、`retro.md`、决策记录完成 | 关闭 |

文件存在 ≠ 闸门通过。看验收行。

## 4. 六个闸门

### G0 立项（Frame）

**进入**：用户提出需求。
**动作**：先跑查询链（仓库 → 历史 → 工单原文 → 持久记忆 → 外部来源），把能自己回答的都回答掉；然后写立项书。
**产物**：`brief.md` —— 问题、受影响者、可观测的成功、范围、非目标、约束、已解决事实（带来源）、未知（带归属）、风险与可逆性。
**退出证据**：没有 `TBD`；成功是可观测的而不是形容词；非目标明确；可逆性已声明；模式已选。
**人工检查点**：只在"只有用户能决定"的问题上。

**常见失败**：把方案塞进问题（"我们需要 Redis"不是问题，"p95 读 900ms"才是）；把努力当成功（"迁移模块"不是成功，"所有调用方编译通过且旧导出已删除"才是）。

### G1 规格（Specify）

**进入**：立项书已验收。
**动作**：写规格 —— 问题、方案、用户故事、实现决策、测试决策、范围外、假设与证据。
**产物**：`spec.md`（七节 + 假设表 + 验收预览）。
**退出证据**：每个决策都有备选与可逆性；接缝（测试点）已列出并与用户确认；测试决策点名了可模仿的既有测试；范围外非空；假设已验证或已排期。
**人工检查点**：**流程中唯一强制的人工设计检查** —— 接缝与范围，一次问清。

规则：**规格里不写文件路径、不贴代码片段**（会过期）。唯一例外：原型里能比散文更精确表达决策的片段（状态机、schema、类型形状），裁到承载决策的那几行并注明来自原型。

**接缝**：能观察行为而不用伸手进内部的点。优先用已有接缝，优先用最高的接缝，一次变更理想的新接缝数量是 **1**。

### G2 拆票（Decompose）

**进入**：规格已验收。
**动作**：切成 tracer-bullet 垂直片，声明阻塞边，算出前沿。
**产物**：`tickets/NN-slug.md`，一票一文件，按依赖顺序从 `01` 编号。
**退出证据**：DAG 无环；每票验收标准都可检查（命令或观测 + 期望结果）；每票能塞进一个全新上下文；并行票不撞同一批文件；前沿已写出。
**人工检查点**：粒度、阻塞边、是否合并/拆分。这是构建前最后一个设计检查点。

**垂直片规则**：每票切一条穿过所有相关层的窄而完整的路径，完成后能独立演示或验证。**横向分层票**（"加数据库列"、"加接口"、"加界面"）是拆解缺陷，不是进度。

**大范围重构例外**：一次机械改动炸穿全库、没有任何垂直片能单独变绿时，用 **扩展 → 迁移 → 收缩**：先加新形态并存，再按爆炸半径分批迁移调用方，最后删旧形态。每批一票，都阻塞于扩展票；收缩票阻塞于所有迁移票。若连分批都无法独立保持绿色，就让它们共享集成分支，并加一张"集成并验证"终票 —— 绿色只在那里承诺，而且 PR 里要写明。

### G3 构建（Build）

**进入**：票在前沿上。
**动作**：认领一票 → 独立分支/工作树 → 红-绿-重构 → 记录证据 → 合并。
**产物**：提交 + `evidence.md` 行。
**退出证据**：每条验收标准都有一行台账（命令 + 观测输出 + 原始日志路径 + 日期）；先红后绿有记录（或带期限的豁免）；破坏性步骤有确认记录；分支能干净合并。
**人工检查点**：无（除破坏性操作与范围变化）。

- **一票一个工作树**，绝不两个实现者在同一个 checkout（共享 index/HEAD/stash 是并行工作互相踩踏的根源）。
- **先红**：先写一个在约定接缝上失败、且失败原因正确的测试。变更前就通过的测试不是在测这个变更。
- **模拟的边界**：只模拟你不拥有的边界（网络、时钟、随机、第三方）。不要模拟被测模块，更不要为了让断言通过而模拟。
- **并行**：前沿有多票时，一票一个全新实现者子代理，后台并发；先合并集成分支再报完成；一次只合并一票；每合并一次重算前沿。
- **卡住时**：缺信息 → `blocked` + 问题（带假设）；规格与代码矛盾 → 规格优先，若规格错就先改规格；发现范围外的活 → 新开票，不扩张当前票。

### G4 评审（Verify）

**进入**：所有票 `done`。
**动作**：在固定点上做三轴评审，各自独立上下文，**永不合并排序**。
**产物**：`review.md`。
**退出证据**：固定点可解析且 diff 非空；每条验收标准有可复现的证据行；回归测试被证明有判别力（在基线会失败）；边界被点名（授权、身份、并发、重试、崩溃恢复、幂等、数据留存、回滚）；每个发现都有裁决与归属。

三轴：

- **标准（Standards）**：是否符合仓库书面规范？工具已强制的跳过；Fowler 味道基线只作判断项，永不当作硬违规；书面规范永远压过基线。
- **规格（Spec）**：是否实现了规格要求、且只实现了这些？缺项/半成品、范围蔓延、实现了但做错了。
- **证明（Proof）**：每条声称是否有可复现的证据？回归测试在基线会不会失败？边界是否被攻击过？日志是否被截断、输出是否被编辑、断言是否被模拟掉？

固定点必须用三点语法：`git diff <fixed-point>...HEAD`。

### G5 发布与学习（Ship & Learn）

**进入**：评审裁决为 `ship`。
**动作**：写 PR 文案、关票、复盘、沉淀决策与记忆。
**产物**：`pr.md`、`retro.md`、`decisions/`、术语表更新。
**退出证据**：PR 有摘要、证据、合并风险（单向门/双向门 + 爆炸半径 + 回滚）、后续项；票全部关闭；`.sdd/<slug>/` 归档而非删除；复盘至少一条具体环境改进（或明确写"无"）。
**人工检查点**：合并/发布由用户决定。

PR 的四段：**摘要**（让变更一目了然的最小可视化：前后截图、日志行对比、数值表）、**证据**（台账里最有价值的两三行）、**风险与合并危险**（单向门还是双向门、谁受影响、怎么回滚）、**后续项**。

## 5. 证据制度

台账 `.sdd/<slug>/evidence.md`，一行一条验收标准，只追加：

| Ticket | Criterion | Command | Observed | Raw output | Date |
|---|---|---|---|---|---|
| T03 | 退款落 settled，总额减 1200 | `pnpm test billing/refund -t settled` | exit 0，12 passed，总额 8800 | evidence/t03-refund.txt | 2026-11-16 |

- **命令**要能原样重跑，写清执行目录。
- **观测**要有数字、状态或具体值；"通过"不算观测。
- **原始输出**保存完整日志，不做 `head`/`tail` 截断；脱敏要标注。
- **判别性**：bug 修复与回归测试必须有两行 —— 变更前失败、变更后通过，同一命令。拿不出基线就在评审里标 `not yet proven`。
- **豁免**：无法满足的闸门写进 `waivers.md`（缺什么、替代检查是什么、谁批准、何时过期），不静默跳过。

## 6. 知识沉淀

- **决策记录**：一决定一文件，`accepted` 后不改决策，只做"被 NNNN 取代"。必须写备选与可逆性。
- **术语表**：新词或词义变化进 `GLOSSARY.md`（术语、一句话定义、它**不是**什么）。两个代理用同一个词表达不同意思，是多会话项目里最贵的 bug。
- **持久记忆**：只存跨特性的持久事实（用户确认过的约定、环境怪癖、外部约束），带来源；不存任务状态、凭据、个人数据，也不存规格或决策记录已经拥有的内容。
- **占位符是缺陷**：`TBD`、`[待填]`、空小节都是缺陷；真正的未知写成 `unknown: <归属>`。

## 7. 失败处理

先分类，再反应：

| 类别 | 例子 | 反应 |
|---|---|---|
| 缺输入 | 文件不存在、密钥没配 | 说清缺什么，不猜 |
| 假设错 | API 行为与假设不符 | 记下更正、改规格假设、继续 |
| 环境坏 | 工具链、网络、权限 | 诊断，不要绕过它写代码 |
| 真缺陷 | 被改的东西本身错了 | 先测量、再修复、再证明 |
| 不稳定检查 | 无改动却时绿时红 | 当成检查本身的缺陷，不要重试到绿 |
| 状态陈旧 | 缓存、旧构建、脏工作树 | 清理、重建、从头重跑 |

**绝不**用削弱断言、跳过测试、缩小查询范围、或报告上一次绿灯来把失败变成成功。降级结果不是空结果，部分结果要说"部分"。修复后必须回读或重跑；没观测到的修复只是理论。

**何时停下来问**：会改变规格范围、动作不可逆、需求互相矛盾、缺凭据/环境、只有用户能决定（产品行为、风险偏好、花费、合并、延期）、同一失败在两次不同修复后仍复现。
**何时不要停**：仓库里怎么实现、约定是什么、依赖的 API 是什么、测试怎么跑 —— 这些靠检查就能解决。

## 8. 三种模式

| 模式 | 适用 | 产物 |
|---|---|---|
| `lite` | 单个垂直片，约一个文件或一个行为，一次会话 | 一张票（内含简短规格）+ 台账 |
| `standard` | 默认。多文件、多票、合并前要评审 | 完整 `.sdd/<slug>/` |
| `wayfinder` | 一次会话装不下，或目的地本身不清楚 | 决策地图，一次会话解一个决策，雾散后收敛到 `standard` |

`wayfinder` 绝不直接进入构建。`lite` 不是跳过证据的借口。

## 9. 与两个来源的对照

| 机制 | 来源 | 在 SDD 里的处置 |
|---|---|---|
| 规格七段式 | 工程技能 | 保留，增加"假设与证据""验收预览" |
| tracer bullet + 阻塞边 + 前沿 | 工程技能 | 保留，作为 G2 的核心 |
| 扩展-迁移-收缩 | 工程技能 | 保留，作为大范围重构的唯一序列 |
| 双轴评审（标准/规格） | 工程技能 | 保留，加第三轴"证明"；仍不合并排序 |
| 全新上下文 + 指针通信 | 工程技能 | 保留，升级为不变量 |
| 强制人工逐阶段触发 | 工程技能 | 改为"仅人工决策点"，其余自动 |
| 依赖 issue tracker 与标签 | 工程技能 | 丢弃，改为仓库内文件；tracker 作为可选后端 |
| 证据+引用、先查后问、先测量后修 | 知识系统 | 保留，写成 G0/G3/G4 的硬规则 |
| 破坏性操作闸门 | 知识系统 | 保留，G3 强制 |
| 有类型的失败 → 修复 → 验证 | 知识系统 | 保留，改写为失败分类表 |
| 带来源的持久记忆 | 知识系统 | 保留，收敛到"一个事实一个归属" |
| 技能 16KB 预算、锁文件、路由评估 | 知识系统 | 丢弃（那是分发机制的产物），只留"规则要短、不触发就删" |
| 以知识为中心的操作循环 | 知识系统 | 不作为交付流程使用；只取其诚实机制 |

## 10. 第一天怎么用

1. 把 `sdd/` 放进技能目录（DSH：`~/.dsh/skills/sdd`）。
2. 在一个真实的中等需求上试一次 `standard`：`python scripts/sdd.py init --slug <slug> --name "<需求名>" --mode standard --tickets "first;second"`，然后观察代理会不会在 G1 停下来问你接缝。
3. 看 `evidence.md`：如果某一行的"观测"只有"通过"，说明规则没被遵守，回去收紧 G3。
4. 结束后读 `retro.md`：只采纳一条改动，改到技能里。
5. 两周后再决定是否推广；没有摩擦证据的推广是仪式。

## 11. 常见问题

**Q：这和普通"先写计划再写代码"有什么区别？**
区别在闸门的**关闭条件**。计划写完了还能继续猜；SDD 的闸门要靠产物和证据关闭，缺一样就停。

**Q：小改动也要六个闸门吗？**
不用，用 `lite`。判断标准是"能不能证明它只是一个垂直片"；不确定就用 `standard`。

**Q：没有 issue tracker 能用吗？**
能。SDD 默认就是仓库内文件；tracker 只是可选后端。

**Q：用户不想被反复打断怎么办？**
SDD 只在两类点停：只有用户能决定的决策，和不可逆动作。其余靠检查解决。如果你发现代理问的是仓库能回答的问题，那是不变量 2 被违反了。

**Q：证据台账会不会变成形式主义？**
会，如果"观测"列允许写"通过"。把命令和输出写死，形式主义就没有藏身处。

**Q：怎么知道流程有效？**
看三个数字：评审发现中"本可被自动检查抓到"的比例是否下降；规格返工次数是否下降；证据行中需要补跑的比例是否下降。

## 12. 演进规则

- 每次复盘只提一条改动，写明它修复的具体摩擦。
- 一个月内从未触发的规则删除。
- 项目约定可以覆盖本流程的默认值，但必须在项目里写明覆盖了哪一条、为什么。
- 版本号与变更历史写在技能 frontmatter 的 `metadata` 与 `PROCESS.md` 顶部。
