Multica 是什么：把 AI 智能体变成看板上的同事

Multica = Multiplexed Information and Computing Agent（多路复用的信息与计算智能体）， 一个源码公开、可自托管的团队工作区。你把任务交给 Claude Code、Codex、Cursor、Kimi 等 26 种 AI 编码智能体， 它们像同事一样接活、边做边汇报、卡住主动说、做完交回来给你审——所有上下文、决定和代码改动都挂在同一个任务下。

一句话设计哲学：把 Multics 的「分时」带回今天——被多路复用的「用户」，既是人，也是能自己干活的智能体。 小团队不该因为人少，就只能干出小团队的量。

1系统架构图

三层客户端 → Go 后端 + PostgreSQL（服务端）→ 本地守护进程 → 你机器上的智能体 CLI。 关键信任边界：后端和数据库在「服务端」，守护进程和智能体 CLI 在你「自己的机器」上跑，代码与密钥不出本机。

图 1：Multica 分层架构。三个客户端经 HTTPS/WebSocket 连到 Go 后端与 PostgreSQL；后端再经一条 WebSocket「隧道」把任务下发给运行在用户本机的守护进程，由守护进程拉起任意一种智能体 CLI。

🧑 小白怎么理解

  • 想象一个公司群：你在网页/电脑/手机上发任务，就像在群里@一个同事。
  • 「服务端」是公司的中央办公室（存数据、记台账），「你的机器」是你自己的工位。
  • 那个真正干活的 AI（比如 Claude Code）不是 Multica 养的，它住在你自己的电脑里——所以你的代码不会上传到别人那里。
  • Multica 的角色是把活派下去、盯着进度、把结果摆回看板给你审。

🔧 专家抓重点

  • views → core + ui 严格分层：core 无 UI/无 react-dom/无 localStorage，靠 StorageAdapter 注入；ui 不准写业务逻辑。
  • 客户端态用 TanStack Query（服务端数据）+ Zustand（客户端态）；WebSocket 事件只打补/失效 Query 缓存，不写 Zustand。
  • 服务端两条 WS 通道分离：realtime hub 推送给客户端，daemonws hub 与守护进程做 RPC（dispatch / completion / runtime_gone）。
  • 数据库零外键、零级联；索引一律 CONCURRENTLY 且独立迁移文件——为在线 DDL 与零停机迁移设计。
  • X-Workspace-ID 选租户，所有查询按 workspace_id 过滤，membership 门控访问。

2任务流程图（一次任务的生命周期）

从「人创建议题」到「人验收合并」，全程留痕、人在回路。智能体干完不直接上线，先进入「审核中」等你拍板； 运行中你能随时插话；失败有看门狗和自动重试。

图 2：任务生命周期。状态键为 backlog → todo → in_progress → in_review → blocked（外加工作流自定义步骤）。 关键设计：智能体完成只进「审核中」，不自动上线；失败由看门狗/超时触发自动重试或停下说明原因；运行中人可插话。

🧑 小白怎么理解

  • 你建一个任务，把它交给某个 AI 同事，它就开始干。
  • 它干活的每一步（用了什么工具、跑了什么命令、报了什么错）都被记下来，像监控录像，可回放。
  • 它干完不会自己把代码发上线，而是先放到「审核中」等你点头——这就叫人在回路。
  • 卡住了它会喊你；中途你想改主意，直接发消息它就收到，不用等它下一轮。

🔧 专家抓重点

  • 状态机在 issueworkflow：固定锚点 backlog / blocked + 工作流自定义步骤；issueguard 做转移权限校验。
  • 派发是推拉结合：服务端 WS 唤醒（daemonws RPC dispatch），守护进程再批量 claim；30s 轮询仅是丢信号/断连的兜底，不抬升常规认领延迟。
  • 可观测性来自 attribution：每次工具调用/命令/错误带时间戳、可完整回放；用量按智能体/任务统计。
  • 弹性：空闲看门狗 2h、工具看门狗、Codex 语义不活跃超时；失败自动重试或停下报因（delegatedrecoverybackfill）。
  • 验收是硬边界：in_review 不自动合 main，上不上线由人决定（issueactivity 记录）。

3设计理论（为什么这样造）

Multica 不是又一个聊天机器人，而是一套「人机协作的操作系统」。下面 10 条原则，前几条是哲学，后几条是工程落地。

🔁

1. 多路复用（Multiplexing）

向 Multics 致敬：当年多人共享一台机器却像独占；今天多个人和多个智能体共享一个工作区却各忙各的。小团队也能跑出大团队的吞吐。

🤝

2. 智能体即队友

负责人是「多态」的——人或智能体都能被指派。它们共用同一块看板、同一条任务生命周期，没有特殊通道。

🔒

3. 代码不出本机

智能体的「工位」是你的机器。守护进程跑在本地，Agent CLI 在你的环境里执行，代码与密钥不离开你的基础设施。

🧑‍⚖️

4. 人在回路 / 可审计

任何东西不经人点头不能上线。每次工具调用、命令、报错都带时间戳；把智能体也算进去的审计记录完整保留。

🎛️

5. 厂商无关

Multica 不自带模型，它驱动你已装好的 26 种 Agent CLI。换提供方就是切个下拉框，谈不上迁移。

🗂️

6. 工作区隔离

按团队隔离智能体、任务与设置。X-Workspace-ID 选租户，membership 门控，所有查询按 workspace 过滤。

🧠

7. 保存共同理解

目标、决定、diff、产出全部挂在同一个任务下，会话结束也不丢。下一个智能体不用从零猜，新人也能看懂为什么走到这里。

⚡

8. 实时推送，而非轮询

服务端经 WebSocket 唤醒守护进程与客户端；realtime 用分片流 + Redis relay 横向扩展，事件直接打补前端 Query 缓存。

🧱

9. 严格分层单体仓库

pnpm + turbo；views→core+ui 单向依赖。core 无 UI、靠适配器注入；ui 不写业务；平台差异用 Navigation/Storage 适配器隔离。

🏠

10. 整套可自托管

Docker Compose / Helm 装在你自己的基础设施；接你自己的 Git（GitHub/GitLab/Gitea/Forgejo）和 IM（Slack/飞书/钉钉/企微/Telegram）。
