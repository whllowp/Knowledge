成品实测：`dist` 打包版 137.5 FPS、中位帧 7.3 ms、p95 10.6 ms、脚本 2.32 ms/帧；
dev 全量回归 23/23 通过、0 报错。

**最后一轮的关键突破**（前几轮一直卡在「裁 GLSL → 画面全空」）：

三处 chunk 是通过 **`ShaderChunk['name']` 中括号取值**（而不是 `#include <>`）
被 `WebGLProgram` 的前缀代码引用的，例如 `tonemapping_pars_fragment`、
`colorspace_pars_fragment`。之前的闭包只走 `#include`，于是把这些「没被 include 但确实要用」
的片段也置空了 —— 着色器能编译、无报错，但什么都不画。补上中括号取值的种子后，
闭包变完整，置空 41 个无用 shader 后画面正常，体积一次到位。

同时清掉了两处「纯数据、从未渲染」的字段（85 条 `latin` 学名、15 条钓点 `desc`），
以及 2 条无引用的 CSS 规则。

## v6.2.1 — 体积排查记录（ShaderChunk 裁剪）

第三轮继续尝试把 `ShaderChunk` 表裁剪到「在用着色器所引用的 chunk 闭包」——
这一步能把 raw 压到 **859,025 B（−11.1%）**，但游戏画面变空，本轮做了以下隔离：

| 实验 | 结果 |
|---|---|
| 用同一份裁剪后的 three 起一个最小页面（`/three-check.html`） | **正常渲染**（读回像素为橙色立方体） |
| 未裁剪 three 的游戏构建 | 正常渲染 |
| 裁剪 three 的游戏构建 | 只有背景色，109 次 draw call、264k 三角形仍在提交 |
| 关闭 terser 压缩（`--minify false`） | 仍然空白 → 排除压缩 |
| 关闭 treeshake（`treeshake: false`） | 仍然空白 → 排除 tree-shaking |
| low 画质（关阴影） | 仍然空白 → 排除阴影路径 |
| 隐藏天空穹顶 | 仍然空白 → 不是天空遮挡 |
| 阅读实际编译的 GLSL | 顶点着色器完整（14.7 kB，含 `gl_Position`），无残留 `#include`，无编译错误 |

结论：裁剪后的 three 单独使用没问题，但作为**游戏 bundle 的一部分**时渲染不出东西，
且与压缩/treeshake/阴影无关。剩余怀疑方向是 Rollup 处理该文件时的模块合并顺序，
或游戏特有的 `ShaderMaterial`（水面/天空）与裁剪后的 chunk 表交互。

产物保持安全配置：**924,562 B（raw，−4.3%）/ 262,044 B（gzip，−6.1%）/ 213,597 B（brotli，−6.5%）**，
已用生产包冒烟测试确认可正常渲染与游玩。

保留的诊断工具：`three-check.html`（`?m=` 指定 three 模块路径即可对比原版/裁剪版）、
`scripts/trim-three.mjs`（`TRIM_CHUNKS=1` 开启有风险的分支）。

### 第四轮补充（v6.2.2）

新增 `BLANK_SHADERS=1` 分支：不改表结构，只把「没有任何 `#include` 引用」的
40 个根着色器 GLSL 置空（省 28 kB）。结果：**单页测试正常、游戏 bundle 仍然空白**。
结合前几轮，规律已经很明确：

- **删除 `ShaderLib` 里的条目**（unused 材质定义）→ 安全，游戏正常；
- **任何修改 GLSL 字符串内容/表的做法**（裁剪表、置空根着色器）→ 游戏渲染全空，
  但单页测试正常、shader 源码完整、无编译错误、无异常。

为了不再靠猜，`trim-three.mjs` 现在会把模式写进产物
（`globalThis.__THREE_TRIM__ = 'lib' | 'lib+chunks'`），运行时可直接确认用的是哪份 three。

## v6.2.0 — 体积第二轮：−4.3%（raw）/ −6.1%（gzip）

在第一轮 −3.7% 的基础上继续压缩，现已 **924,562 B**（原始 966,105 B）。

**新增的压缩手段**
1. **`three` 的 ShaderLib 裁剪**（`scripts/trim-three.mjs`）：游戏只用到
   basic / lambert / points / sprite / depth / shadow / background / cube 八种着色器，
   构建时生成一份去掉 phong / standard / toon / matcap / normal / dashed 的 three，
   并删除 three 在字面量之后追加的 `ShaderLib.physical = {...}`
   （它引用了已删除的 `ShaderLib.standard`，不删会在启动时抛
   `Cannot read properties of undefined (reading 'uniforms')`）。
2. **移除 `three/addons/utils/BufferGeometryUtils`**：道具合并改用自研的
   `mergeGeometriesSimple()`，少打包一整个 addon 模块。
3. terser（passes 3 + `_` 前缀属性混淆）、`esnext`、lightningcss、HTML 压缩、
   生产构建剥离 `__DEBUG`。

**尝试过但回滚的方案**：把 `ShaderChunk` 表裁剪到「仍在用的着色器所引用的
chunk 闭包」，理论上能再省 ~63 kB（raw 到 859 kB，−11%）。实测**画面全空**
（天空之外什么都不渲染），但：
- 场景对象齐全（734 个）、draw call 正常（109）、三角形 264k 都在画；
- 控制台 **0 报错**、0 异常、0 shader 编译错误；
- 离线模拟 `#include` 闭包检查结果为「无缺失 include」；
- 同一探针指向 dev（未裁剪 three）时画面完全正常。

因此问题不在 include 缺失，更可能在重建 `ShaderLib`/`ShaderChunk` 字面量时的
文本拼接。该分支由 `TRIM_CHUNKS=1` 控制，默认关闭，留待下一轮定位。

## v6.1.0 — 性能：流畅度 +51%、CPU −34%、体积 −3.7%

目标：体积 −10%、流畅度 +50%、CPU 利用率 −10%。本轮达成后两项，体积部分达成（见末尾）。

**测量方法**（新增 `scripts/bench.mjs` / `ab.mjs` / `profile.mjs` / `size.mjs`）：
同一台无头 Chrome（ANGLE/D3D11，1280×800，`--disable-frame-rate-limit`），
`?opt=0` 关闭全部优化、`?opt=1` 开启，各跑 4 次取**中位数**，比较帧间隔与
CDP `Performance.getMetrics` 的 `ScriptDuration`。

| 指标（high 画质，中位数 4 次） | 优化前 `opt=0` | 优化后 `opt=1` | 变化 |
|---|---|---|---|
| 帧率 | 98.0 FPS | 148.0 FPS | **+51.0%** |
| 每帧脚本耗时 | 9.40 ms | 6.24 ms | **−33.6%** |
| p95 帧时间 | 14.2 ms | 9.9 ms | −30.3% |

**做了什么**

1. **植被空间分块 + 距离 LOD**（最大收益，植被原本占 ~45% 帧时间）：
   原本每种植物是**一个覆盖全岛的 InstancedMesh 且 `frustumCulled = false`**，
   每帧把 33,372 个实例全部提交。现在按 110–240 m 分块，逐块视锥剔除，
   并按距离隐藏（草 85 m / 芦苇灌木 160 m / 岩石 240 m / 树 340 m，雾在 ~550 m
   才完全遮挡，看不到突然消失）。
2. **阔叶树冠减面**：三团叶簇 → 两团（轮廓基本不变），直接砍掉约 1/3 树冠三角形。
3. **道具实例合并**：74 个静物按「材质 + 260 m 空间格」合并成少量网格
   （`src/core/merge.js`，保留索引缓冲——早期无索引版本反而慢了 18%）。
4. **静态矩阵冻结**：地形/道具/植被的 `matrixAutoUpdate = false`，省掉每帧的矩阵重算。
5. **阴影降频**：shadow map 每 3 帧更新一次（太阳移动很慢，肉眼无差）。
6. **小地图节流**：重绘降到 ~10 Hz，并缓存 `getBoundingClientRect`（此前每帧强制 relayout）。
7. **打包压缩**：terser（passes 3、`_` 前缀属性名混淆）+ `esnext` + lightningcss +
   生产构建剥离 `__DEBUG` 调试块（19 kB）+ 关闭 console。

**体积**：966,105 → 930,207 B（−3.7%）；gzip 279,124 → 263,231 B（−5.7%）；
brotli 228,394 → 214,527 B（−6.1%）。

体积 **未达到 −10%**：打包产物中 three.js 占 504 kB（54%，已 tree-shake 到只剩
渲染器核心、无 GLTF/骨骼/XR/音频），游戏代码 376 kB（数据文案仅 9 kB），
CSS 26 kB 中只有 2 条未使用规则。要再压 65 kB 只能删功能或裁剪 three 的
ShaderLib（风险高）。`?opt=0` 保留下来，供后续继续 A/B。

## v6.0.0 — RSI：会自我进化的老渔夫

参考两篇论文的机制，给岛上增加了一个**每天自动演进的对手**：

- **Dream-RSI（arXiv:2609.14858）**——「在回放里做梦」：老渔夫把每天真实的
  作钓情境（钓点 / 时段 / 天气 / 深度）记进**回放池**，候选策略先在回放池上离线打分，
  不必真的下水就能比较优劣；被采纳的策略第二天才投入实战，实战又扩充回放池，
  形成自我改进的闭环。
- **Harmony Harness（arXiv:2610.15150）**——**多目标分解演化**：
  - 7 组目标权重（收益 ↔ 鱼种多样性）构成 MOEA/D 子问题集，
    用 **Tchebycheff 标量化**比较父代与子代；
  - **因子化变异**：一次只改「通用基因」（技巧 / 耐心 / 装备档位）或
    「环境基因」（时段偏好 / 水深偏好 / 各钓点权重），两种作用域分开演化；
  - **精英档案**保存历史上所有非支配个体，让**帕累托前沿**不会塌缩成一个点；
  - **留出验证（held-out gate）**：子代必须在没参与调优的那部分回放样本上
    仍然能钓到鱼，否则以「覆盖率崩塌」为由否决——防止它靠只刷一个钓点刷分。
- **玩法接入**：老渔夫现在会参加钓鱼比赛（第 5 名选手「老渔夫」，
  节奏由其策略估算），并根据演化代数提升技巧；新增面板页 **「老渔夫 · RSI」**
  展示代数、回放样本数、帕累托前沿散点图、当前部署策略与最近世代日志。

实测（无头 Chrome，连续演化 28 代）：前沿从 1 个点扩展到 **10 个点**
（收益 86,525 / 多样性 18 ↔ 收益 4,903 / 多样性 25 的完整权衡曲线），
每日收益 7,226 → 45,662，被否决的变异以 `held-out: coverage collapsed`
和 `not-better` 为主。

## v5.1.0 — 搏斗手感重调

- **卸力曲线重做**：旧公式 `0.55 × 线组比值` 对任何有分量的鱼都会撞到 0.2 下限，
  大魚几乎 2 秒就把线拉光。新公式 `0.26 + 0.55 × min(1.2, 比值)` 保底给一点卸力，
  装备不足变成「难打」而不是「瞬间结束」。
- **出线机制放缓**：单次冲刺的收线量上限 0.07（不再按鱼力无限放大）、
  放线速率降到原来的约一半、脱钩阈值 1.2 → 1.35。
- **化解事件有回报**：成功拆招除了让对方掉体力，还能夺回 0.035 的线；恢复阶段也会慢慢收线。
- 冲刺型重新标定（runPower 1.35 → 1.15，runFreq 1.3 → 1.15），金枪鱼/旗鱼不再三秒必死。
- 实测（每种 1 次，自动读招机器人）：虹鳟 9.8 s / 鲈鱼 12.1 s / 鲤鱼 5.3 s /
  金枪鱼 24.1 s / 虎鲨 21.6 s / 石斑 16.2 s / 旗鱼 26.7 s，全部成功上岸，
  评级在 S/A/B 之间浮动。

## v4.4.0 — 修复：视角无法转动

- **根因**：某次重构后 `input.requestLock()` 再也没有被任何地方调用，指针永远不锁定，
  `mousemove` 里的 `movementX/Y` 也就永远不累积——鼠标视角彻底失效。
  同时 `player._handleLook()` 依赖的 `input.dragging` 从未实现，拖动兜底也是死代码。
- **修复**：
  - 恢复指针锁定流程：点击画面 / 点击提示 / 按任意键 / 进入游戏时都会请求锁定，
    锁定后隐藏系统光标，未锁定时显示「点击画面锁定鼠标视角」提示。
  - 新增 `input.dragging`：浏览器拒绝锁定时，**按住右键拖动**即可转视角。
  - 新增键盘兜底：`[` / `]` 左右转身，`,` / `.` 抬头低头（拍照模式同样适用）。
  - `pointerlockerror` 时给出一次提示（5 秒节流），不会刷屏。
- **验证**：键盘转身 yaw 1.396 → 0.066；右键拖动转身 yaw 1.396 → 1.732；
  点击确实落在 `game-canvas` 上并触发了锁定请求（`pointerlockerror` 证明请求已发出）。
  注意：本机是无头/隐藏窗口的 Chrome，Chrome 自身会拒绝指针锁定
  （`document.visibilityState === 'hidden'`），所以锁定的最终成功与否需要在你的真实浏览器里确认。
