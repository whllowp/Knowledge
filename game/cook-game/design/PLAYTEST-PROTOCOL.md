# 真人试玩协议 — SIZZLE! 灶台风暴

> 目的：用**真人**的完成单数、超时率、分数分布重标三个班次的 1★/2★/3★，并验证手柄、触屏和重绑后的可玩性。
>
> 当前状态（2026-11-02）：环境里没有真人试玩条件。仓库里已有自动记录器、导出和机器人模拟，但**还没有真人样本**；`src/core/data.js` 的阈值是模拟校准版，不能当作最终结论。

## 1. 需要多少样本

| 班次 | 模式 | 最少样本 | 目标样本 |
|---|---|---:|---:|
| Shift 01 | 沉浸厨房 | 5 | 8 |
| Shift 02 | 沉浸厨房 | 5 | 8 |
| Shift 03 | 沉浸厨房 | 5 | 8 |
| Shift 01 | 街机厨房（1P） | 5 | 8 |
| Shift 02 | 街机厨房（1P） | 5 | 8 |
| Shift 03 | 街机厨房（1P） | 5 | 8 |
| 任意 | 街机厨房（2P） | 3 组 | 5 组 |

- 同一个人可以玩多个班次，但**每个班次第一次尝试**单独标记为首玩样本；重试样本只用于看进步。
- 新手定义：没玩过本作、没看过攻略；不要找项目组成员充当“新手”。
- 至少 3 名不同玩家覆盖“键鼠 / 手柄 / 触屏”三种输入，否则输入方式会混进难度结论。

## 2. 场地与设备

1. Chrome 或 Edge，桌面端优先；移动端单独做触屏样本。
2. 全屏（F11），分辨率 ≥ 1280×720；移动端横屏优先，竖屏也记录。
3. 清除或确认试玩记录为空：设置 → 试玩数据 → 清空记录。**不要清空最佳成绩**（除非要做首玩样本；首玩样本请用全新浏览器 profile）。
4. 在 **设置 → 试玩数据 → 本次试玩标记** 填参与者编号（如 P01）、经验（新手/普通/熟练）和“首次玩本作”。**每换一个人就更新一次**，否则 CSV 的经验分组会混。
5. 确认“设置 → 记录试玩数据”为开。
6. 手柄：标准 XInput / DualShock，插上后按任意键，HUD 应切换为手柄提示；触屏：确认出现左下摇杆和右下互动键。
7. 录屏可选；如录屏，先征得同意，且不要录到个人信息。

## 3. 主试脚本（逐字可念）

### 开场

> “这是《灶台风暴》，一个做菜游戏，有两种模式。今天不是考试，我想看你第一次玩时的真实反应。遇到不懂的可以问，但我会先记下来，尽量不直接教你。全程大约 15 分钟。”

### 操作说明（只讲 30 秒）

- 沉浸厨房：WASD 移动，鼠标转头，E 拿起/放下/上菜，按住左键或 E 切菜，Shift 冲刺，Esc 暂停。
- 街机厨房：P1 WASD + 空格，P2 方向键 + Enter；按住互动键切菜。
- 手柄 / 触屏：只指出摇杆、互动键、暂停键，不讲策略。

### 试玩顺序

1. **Shift 01 沉浸厨房**：完整玩一局（180 秒），不打断。
2. 问 3 个问题（见第 4 节），记录。
3. **Shift 01 街机厨房 1P**：完整玩一局。
4. 如时间允许，玩 Shift 02 或 2P；每个班次都记录。
5. 结束后打开设置 → 试玩数据，确认场次增加；点“导出 CSV”。

### 禁止事项

- 不在第一局中途提示“肉饼要糊了”“去拿盘子”等策略。
- 不替玩家操作，不调整灵敏度/FOV 除非玩家主动要求。
- 不把机器人/自动化截图的数据当真人样本。
- 不把玩家的姓名、联系方式写进 CSV 或文件名。

## 4. 观察记录（每局一行）

| 字段 | 说明 |
|---|---|
| participant | 匿名编号，如 P01 |
| first_time | 是否首次玩本作 |
| input | keyboard / gamepad / touch |
| mode / shift | fp/arcade + 1/2/3 |
| completed | 是否在时间内完成至少 1 单 |
| first_serve_s | 第一单出餐用时（秒，估算即可） |
| confusion | 卡住/误操作的时间点（如“找不到盘子”“不知道要按住切”） |
| felt_rushed | 1–5 |
| wants_replay | 是/否/也许 |
| notes | 原话或观察 |

自动化字段（CSV 里已有）：`participant, skill, firstTime, duration, firstServe, pauses, difficulty, wantReplay, score, stars, served, expired, wasted, burnt, maxCombo, timeoutRate, device, source`。

其中 `firstServe` 是首单出餐秒数、`pauses` 是暂停次数、`difficulty` / `wantReplay` 来自结算页小调查；观察表只需补主观原话和“卡在哪里”。

## 5. 导出与归档

1. 设置（或结算页）→ **试玩数据**。
2. 确认“真人样本”数量正确；`automation` 不计入。
3. 点 **导出 CSV**；文件名改为 `sizzle-playtest-YYYYMMDD-<场地>-<主试>.csv`。
4. 同时导出 JSON 备份（字段更全）。
5. 上传到团队共享目录；不要只留在试玩机上。
6. 清空本机记录前确认 CSV 已备份。
7. 合并多台机器的 CSV：在数据页点 **导入 CSV**，重复 id 会自动跳过；再点 **计算建议**。

## 6. 分析规则（重标阈值）

按 `mode + level + players + source=human` 分组，至少计算：

- 完成单数 `served`：p25 / p50 / p75；
- 超时率 `timeoutRate`：p25 / p50 / p75；
- 分数 `score`：p25 / p50 / p75；
- 星级分布；首单时间；不同输入设备的差异。

建议阈值：

- **1★ = 新手组分数 p50**：一半新手能拿到第一颗星。
- **2★ = 普通组分数 p50**：有经验但不熟练的玩家能稳定拿到。
- **3★ = 熟练组分数 p75**：需要熟练路线/连击，不是人人可拿。
- 同时检查超时率：如果熟练组 p50 超时率 > 25%，优先放宽订单耐心/同时订单数，而不是继续降分。
- 如果 2P 样本明显高于 1P，保持“合作奖励”，不要为 2P 单独抬阈值；在文档里说明。

> 机器人模拟 `npm run balance` 只用于**下限检查**：它证明“路径规划机器人”能拿多少分。真人通常会因路线优化更高、因紧张/误操作更低。两者不能互相替代。

### 用脚本算

```bash
npm run analyze -- sizzle-playtest-YYYYMMDD.csv --min=3
npm run analyze -- sizzle-playtest-YYYYMMDD.csv --players=all --min=5 --out=report.md
```

脚本会：

- 默认只统计 `source=human`、`players=1`；
- 按模式 + 班次 + 经验分组，输出出餐/超时/分数的 p25/p50/p75；
- 1★ = 新手 p50、2★ = 普通 p50、3★ = 熟练 p75（取整到 25）；
- 任一组少于 `--min` 时拒绝给建议，并列出缺哪组；
- 熟练组超时率 p50 > 25% 时提醒先放宽订单，而不是继续降分。

`--min=3` 用于中途看看趋势；正式重标用 `--min=5`，与第 1 节的样本目标一致。

也可以在游戏内完成：数据页 → **计算建议** → 对可重标的班次点 **应用**。这只写入本机覆盖，下一班生效；**恢复官方** 会清掉覆盖。跨机器合并时先 **导入 CSV** 再计算。
